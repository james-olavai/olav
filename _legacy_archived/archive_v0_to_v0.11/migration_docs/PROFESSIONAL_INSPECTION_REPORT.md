# Professional Inspection Report System - OLAV v0.9.8

## Overview (总览)

The inspection report system has been upgraded to **production-grade professional standards**, providing comprehensive multi-layer network health analysis with:

- **Executive Summary** with health scoring (0-100%)
- **L1-L4 Multi-Layer Analysis** covering Physical, DataLink, Network, and Application layers
- **Expected vs Actual State** comparison for each anomaly
- **Root Cause & Impact Analysis** with LLM-powered global correlation
- **Actionable Recommendations** prioritized by severity
- **Next Steps** with executable commands

## Report Structure (报告结构)

### 1. Executive Summary 📊
**Purpose**: Provides at-a-glance health status

**Contents**:
- Overall Health Score (0-100%)
- Device distribution: Normal ✅ / Warning ⚠️ / Critical 🔴
- Health status indication

**Example**:
```
| Metric | Value |
|--------|-------|
| Overall Health Score | **85%** ⚠️ WARNING |
| Normal Devices | 8/10 ✅ |
| Warning Devices | 1/10 ⚠️ |
| Critical Devices | 1/10 🔴 |
```

### 2. Inspection Scope & Methodology 🎯
**Purpose**: Explains what was checked and why

**L1-L4 Framework**:
| Layer | Scope | Items Checked |
|-------|-------|---------------|
| **L1 Physical** | Device Health | Uptime, CPU, Memory, Temperature, Power Supply, Fans |
| **L2 DataLink** | Interface Status | Interface State, Errors, Drops, VLAN, STP |
| **L3 Network** | Routing Health | Route Table, OSPF Neighbors, BGP Sessions, VPN Status |
| **L4 Application** | Service Status | Protocol Sessions, Queue Depth, Service Health |

### 3. Device Status Matrix 📱
**Purpose**: Shows per-device health across all layers

**Format**: Device × Layer matrix showing:
- L1 Physical layer status
- L2 DataLink layer status
- L3 Network layer status
- L4 Application layer status
- Overall device status

**Status Indicators**:
- ✅ = HEALTHY / Normal
- ⚠️ = WARNING / Degraded
- 🔴 = CRITICAL / Failed

### 4. Expected vs Actual State Analysis 📋
**Purpose**: Details each anomaly with clear comparison

**For Each Issue**:
```
**Device - Metric** [Layer]

- **Expected State**: Normal/Healthy value
- **Actual State**: Current measured value
- **Severity**: CRITICAL/WARNING
- **Details**: Specific description
```

**Organized by Severity**:
1. 🔴 Critical Issues (require immediate action)
2. ⚠️ Warning Issues (should be addressed soon)

### 5. Root Cause & Impact Analysis 🔎
**Purpose**: Global correlation across all anomalies

**Contains**:
- **Root Cause Analysis**: Are there cross-device related failures?
- **Business Impact**: What could these issues cause?
- Generated by LLM for intelligent correlation

### 6. Recommendations & Action Plan 💡
**Purpose**: Actionable next steps organized by priority

**Priority Levels**:
1. **🚨 Immediate Actions** (priority=critical)
   - Must be done right now
   - Example: "Restart failed BGP session on R1"

2. **📅 Planned Actions** (priority=warning)
   - Should be done within next maintenance window
   - Example: "Update interface configuration on SW2"

3. **🔧 Optimization Suggestions** (priority=info)
   - Nice to have improvements
   - Example: "Consider implementing QoS on core links"

### 7. Next Steps 📞
**Purpose**: Enable follow-up analysis with actual commands

**Commands Provided**:
```bash
# Query inspection database for specific device
olav query --inspection --device <device_name>

# Search for specific metric anomalies
olav search --metric <metric_name> --severity critical

# Compare current vs previous inspection
olav inspect --compare-baseline

# Run focused inspection on specific layer
olav inspect --layer L1 --device-group test

# Export detailed report for analysis
olav export --inspection --format json > inspection_$(date +%Y%m%d).json
```

**Note**: These use template variables (like `<device_name>`) that are replaced with actual values.

## Execution (执行)

### Run Full Inspection
```bash
uv run olav inspect
```

**Output**:
- Full report saved to: `exports/reports/inspection/report_YYYYMMDD_HHMMSS.md`
- Latest symlink: `exports/reports/inspection/latest.md`
- Console preview of report

### Run Test Mode Inspection
```bash
uv run olav inspect --test
```

**Features**:
- Uses test device group
- Shorter dataset
- Still generates full professional report
- Good for validation

### Run Focused Inspection
```bash
uv run olav inspect --device-filter R1,R2,R3
```

**Benefits**:
- Filter to specific devices
- Faster execution
- Focused analysis

### Run Layer-Specific Inspection
```bash
uv run olav inspect --layer L1 --device-group test
```

**Scope**:
- L1: Physical layer only
- L2: DataLink layer only
- L3: Network layer only
- L4: Application layer only

## Report Generation Code (报告生成代码)

### Location
[report_formatter.py](src/olav/tools/report_formatter.py) - `generate_professional_inspection_report()`

### Function Signature
```python
def generate_professional_inspection_report(
    metadata: dict[str, Any],           # {timestamp, device_count, all_devices}
    anomalies: dict[str, list[dict[str, Any]]],  # {device: [{metric, severity, ...}]}
    llm_analysis: dict[str, Any],       # {root_cause, impact, recommendations}
    layers_config: list[dict[str, Any]] | None = None,  # Optional L1-L4 config
) -> str:
    """Returns markdown report string"""
```

### Integration Points
1. **inspector.py** - `ReportRenderer.render()`
   - Calls `generate_professional_inspection_report()` with inspection results
   - Receives formatted markdown report

2. **report_formatter.py** - Orchestrator
   - Formats metadata into health score
   - Organizes anomalies by severity and layer
   - Incorporates LLM analysis for recommendations

## Health Score Calculation (健康分数计算)

### Formula
```
health_score = 100 - (critical_count * 20 + warning_count * 5)
health_score = max(0, min(100, health_score))  # Clamp to [0, 100]
```

### Interpretation
| Score | Status | Interpretation |
|-------|--------|-----------------|
| 90-100% | ✅ HEALTHY | Green - All systems normal |
| 70-89% | ⚠️ WARNING | Yellow - Some issues need attention |
| 0-69% | 🔴 CRITICAL | Red - Immediate action required |

### Examples
- 10 devices, 0 critical, 0 warning → 100% HEALTHY ✅
- 10 devices, 0 critical, 2 warning → 90% HEALTHY ✅
- 10 devices, 1 critical, 1 warning → 75% WARNING ⚠️
- 10 devices, 2 critical, 3 warning → 55% CRITICAL 🔴

## Database Views Used (使用的数据库视图)

The inspection system uses these DuckDB views:
- `v_device_status` - Device uptime, CPU, memory
- `v_interfaces` - Interface states, errors, drops
- `v_bgp_neighbors` - BGP session status
- `v_ospf_neighbors` - OSPF neighbor states
- `v_routes` - Routing table information
- `v_vlans` - VLAN configuration

See `src/olav/tools/inspection_views.py` for view definitions.

## Customization (自定义)

### Custom Thresholds
Edit `.olav/skills/network-inspection/SKILL.md`:

```yaml
inspection:
  thresholds:
    - metric: cpu_usage
      warning: 50
      critical: 80
    - metric: memory_usage
      warning: 75
      critical: 90
    - metric: temperature
      warning: 60
      critical: 70
```

### Custom Layers
Add or modify layers in SKILL.md:

```yaml
inspection:
  layers:
    - name: L1_Physical
      description: "Device health"
      sql: |
        SELECT device, cpu, memory FROM v_device_status
```

### Custom Report Template
Create new template in `generate_professional_inspection_report()` or override `ReportRenderer`.

## Troubleshooting (故障排查)

### Issue: "No anomalies detected" always
**Cause**: Database views not created or data not loaded
**Solution**: 
```bash
uv run olav knowledge index  # Regenerate views
uv run olav snapshot --group test  # Collect new data
```

### Issue: Layer data not showing
**Cause**: SQL queries in SKILL.md reference non-existent columns
**Solution**: Check view column names in `inspection_views.py`

### Issue: LLM analysis fails
**Cause**: LLM service not available
**Solution**: Check LLM configuration, fallback uses default recommendations
