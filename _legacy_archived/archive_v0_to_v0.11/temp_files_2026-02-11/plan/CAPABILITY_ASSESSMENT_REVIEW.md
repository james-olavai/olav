#### ❌ 3. 失败模式和诊断方法缺失 (权重: 中)

**问题**: 如果某个测试失败了，怎么诊断？

**应该补充**:
```markdown
## 常见失败模式和诊断

### 失败模式 1: 输出文件不存在
**可能原因**:
- Agent没有理解用户的意图 → 检查Agent的中间日志
- Query执行失败 → 检查数据库SQL错误
- 输出路径错误 → 检查文件系统权限
- 超时 → 观察执行时间是否> Level预期

**诊断方法**:
```bash
# 1. 检查Agent日志
tail -100 logs/query_agent.log | grep "test_case_id"

# 2. 检查数据库是否有结果
duckdb .olav/db/main.duckdb "SELECT COUNT(*) FROM devices"

# 3. 检查输出目录
ls -lah exports/ | grep "all_devices"

# 4. 重新运行一次
uv run olav ask "列出所有设备"
```

### 失败模式 2: 输出行数不对
**典型原因**:
- DISTINCT/GROUP BY逻辑错误
- JOIN错误导致重复或遗失
- WHERE条件过滤不对

**验证方法**:
```bash
wc -l exports/all_devices.csv  # 应该≥80行
# 如果只有1行（header），说明查询结果为空

# 对比预期
# SELECT COUNT(*) FROM devices → 应该80个
```

### L2特定失败 - 时间范围理解错误
**高发场景**: "过去10天" "上周" "本月"
**诊断**:
```bash
# 看生成的CSV的日期范围
head -5 exports/last_10_days_traffic.csv
# 应该看到日期都在[CURRENT_DATE-10, CURRENT_DATE]范围内

# 对比系统时间
date  # 检查服务器时间是否正确
```
```

**为什么需要**:
- 测试失败时能快速定位根因
- 减少重复测试的时间
- 区分"Agent理解错误"vs"数据库问题"vs"输出格式问题"

## 性能基准 (SLA)

| Level | 预期执行时间 | 说明 |
|-------|-----------|------|
| L1 | <100ms | 单表简单查询，应该很快 |
| L2 | <500ms | 多表JOIN，有聚合，允许稍长 |

### 验证方法
```bash

# real 0m0.087s  ← 应该< 100ms

# real 0m0.342s  ← 应该< 500ms
```

### 失败标准
- ❌ 任何L1用例 > 500ms → Agent性能问题
- ❌ 任何L3用例 > 5000ms → 需要优化
```

**为什么需要**:
- 不查性能，可能Agent已经慢到不可用
- 这是"能力验证"的一部分
- 网络工程师需要在合理时间内获得答案
