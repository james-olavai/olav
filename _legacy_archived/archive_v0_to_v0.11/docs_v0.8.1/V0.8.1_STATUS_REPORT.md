## 1. 核心架构改进：拓扑数据“导入时丰富” (Enrich-at-Import)

为了解决渲染侧逻辑过重且数据不全的问题，我们将数据处理前移至导入阶段。

### 原有问题
- 可视化脚本 (`topology_viz.py`) 需要在渲染时动态计算 BGP 类型、查找 OSPF 对应的 IP 等，逻辑复杂且脆弱。
- CDP/LLDP 只有物理接口，没有 IP 地址。
- OSPF 链路只有单侧信息完整。

### 解决方案：三阶段导入器
重构了 `TopologyImporter` (`src/olav/tools/topology_importer.py`)：

1.  **阶段一：收集 (Collect)**
    - 遍历所有 parsed JSON，收集原始链路数据。
    - 暂停插入数据库。

2.  **阶段二：交叉引用与丰富 (Cross-Reference)**
    - **OSPF**: 建立 `(local, remote)` 索引，反向查找对端接口和 IP，补全链路信息。
    - **CDP/LLDP**: 引入 ARP 表查找机制 (`_build_arp_tables`)，通过接口名标准化 (`Ethernet0/0` vs `Eth0/0`) 查找对应 IP 地址。
    - **BGP**: 在导入时根据 AS 号直接计算 `bgp_type` (iBGP/eBGP) 并存入元数据。

3.  **阶段三：验证与存储 (Insert)**
    - 使用 Pydantic 进行最终数据校验。
    - 将丰富后的元数据 (`local_ip`, `remote_ip`, `bgp_type`, `local_as` 等) 存入数据库 JSON 字段。

**结果**: Visualization 脚本现在只需从数据库“读取并展示”，不再需要进行复杂的业务逻辑计算。

---

## 2. 命令白名单升级：模板与安全机制

解决了 `show interface*` 等通配符命令在 Sync 过程中导致 "Invalid input" 的问题，同时保留了 Agent 的灵活性。

### 改进措施
1.  **移除通配符**: 从 `cisco_ios.txt` 白名单中移除了所有 `*` 结尾的命令。
2.  **引入模板机制**: 
    - 创建 `imports/commands/cisco_ios_templates.txt`。
    - 使用 `!VARIABLE` 语法 (如 `show interface !INTERFACE_NAME`) 替代 `$VARIABLE`。
3.  **三重安全保障**:
    - **Loader 过滤**: 自动忽略包含 `!` 的模板命令，防止进入 Sync 自动执行列表。
    - **Skill 教育**: 更新 Quik Query Skill，通过 Prompt 引导 Agent 将 `!VARIABLE` 替换为实际值。
    - **CLI 容错**: `!` 在 Cisco/Huawei CLI 中是注释符。即使 Agent 意外直接发送了模板，设备也会忽略该行，不会报错。

## 4. 架构演进：废弃 Grep，拥抱 SQL 数据仓库

计划在后续版本 (v0.8.2+) 彻底改变数据检索方式，从基于文件的文本搜索进化为基于 SQL 的结构化查询。

### 核心变更
- **引入 Warehouse**: 利用 DuckDB 的 JSON 和全文检索能力，通过 `read_json_auto` 等函数直接将 `data/sync/` 目录下的 Parsed JSON 和 Raw Text 映射为数据库视图。
- **废弃工具 (Deprecated)**: 
    - 计划淘汰基于 `grep` 命令行的文件搜索工具 (`grep_search` 等)。
    - 原因：Grep 只能返回孤立文本行，无法处理结构化数据 (如 "找出 version < 12.0 的设备")，且无法进行跨设备关联分析。

### 实施路径
1.  **统一 Schema**: 定义 `device_snapshots` (JSON) 和 `raw_logs` (Text) 视图结构。
2.  **新工具**: 开发 `query_network_data(sql)` 工具，赋予 Agent 完整的 SQL 数据分析能力。
3.  **零拷贝**: 利用 DuckDB 零拷贝特性，直接查询文件系统，避免繁重的 ETL 过程。

## 4.1 架构演进：Template-Driven Data Lake v2 (规划中)

> **状态**: 🔬 设计阶段 (2026-01-15 提出)  
> **目标版本**: v0.9.0  
> **预期收益**: 代码减少 60%+，命令覆盖率提升 30x (50 → 1500+)

### 核心设计理念

基于 DB Federation 验证成功，进一步简化架构：**用 SQL 替代 Python 业务逻辑**。

### 4.1.1 Per-Command 并行采集策略

**现有方式 (Per-Device)**:
```
Device1: cmd1 → cmd2 → cmd3 (串行)
Device2: cmd1 → cmd2 → cmd3 (串行)
```

**新方式 (Per-Command)**:
```
cmd1: [D1, D2, D3, D4, D5, D6]  ← 全设备并行
cmd2: [D1, D2, D3, D4, D5, D6]  ← 全设备并行
cmd3: [D1, D2, D3, D4, D5, D6]  ← 全设备并行
```

**优势**:
- 最大化 Nornir worker 利用率
- 流水线化：cmd1 采集完立即入库，同时 cmd2 开始采集
- 失败隔离：单命令失败不影响其他命令

### 4.1.2 Schema-less 核心 + 物化视图

**废弃固定 Schema**:
```sql
-- ❌ 旧方式：每增加命令需改代码
CREATE TABLE bgp_neighbors (
    device_id TEXT, neighbor_ip TEXT, remote_as INT, ...
);
```

**采用 Schema-less**:
```sql
-- ✅ 新方式：统一事实表
CREATE TABLE raw_outputs (
    device_id    TEXT,
    command      TEXT,           -- 'show ip bgp summary'
    template     TEXT,           -- 'cisco_ios_show_ip_bgp_summary'
    output_json  JSON,           -- TextFSM 原始输出
    collected_at TIMESTAMP
);

-- 按需提取 (DuckDB JSON 函数)
SELECT 
    device_id,
    json_extract_string(elem, '$.bgp_neigh') AS neighbor,
    json_extract(elem, '$.state_pfxrcd')::INT AS prefixes
FROM raw_outputs, 
     unnest(json_extract(output_json, '$')::JSON[]) AS elem
WHERE command = 'show ip bgp summary';
```

**物化视图层 (L1-L4)**:
```sql
-- L1 物理层
CREATE VIEW v_l1_interfaces AS ...;
CREATE VIEW v_l1_cdp AS ...;

-- L2 数据链路层
CREATE VIEW v_l2_vlans AS ...;
CREATE VIEW v_l2_mac_table AS ...;

-- L3 网络层
CREATE VIEW v_l3_routes AS ...;
CREATE VIEW v_l3_bgp AS ...;
CREATE VIEW v_l3_ospf AS ...;

-- L4 传输层/服务层
CREATE VIEW v_l4_acls AS ...;
```

**方案对比**:
| 方案 | 灵活性 | 性能 | 维护成本 |
|:---|:---:|:---:|:---:|
| 固定 Schema | ❌ 低 | ✅ 最快 | ❌ 高 (每命令改代码) |
| Schema-less JSON | ✅ 高 | ⚠️ 中等 | ✅ 低 |
| Schema-less + 物化 | ✅ 高 | ✅ 快 | ✅ 低 |

### 4.1.3 废弃 Topology/Routing Path 模块

**用 SQL 视图替代复杂 Python 代码**:

```sql
-- 拓扑链路发现 (替代 topology_importer.py ~400行)
CREATE VIEW v_topology_links AS
-- BGP 链路
SELECT 
    device_id AS local_device,
    neighbor_ip,
    'BGP' AS protocol,
    CASE WHEN local_as = remote_as THEN 'iBGP' ELSE 'eBGP' END AS link_type
FROM v_l3_bgp

UNION ALL

-- OSPF 链路 (自动交叉引用)
SELECT 
    a.device_id AS local_device,
    b.device_id AS remote_device,
    'OSPF' AS protocol,
    a.area_id
FROM v_l3_ospf a
JOIN v_l2_interfaces b ON a.neighbor_ip = b.ip_address

UNION ALL

-- CDP/LLDP 物理链路
SELECT 
    device_id,
    neighbor_device,
    'CDP' AS protocol,
    local_port || '↔' || remote_port AS link_desc
FROM v_l1_cdp;

-- 路由路径分析 (替代 routing_path_analyzer.py)
WITH RECURSIVE route_path AS (
    SELECT device_id, network, nexthop_ip, 1 AS hop
    FROM v_l3_routes 
    WHERE network = '10.1.1.0/24'
    
    UNION ALL
    
    SELECT r.device_id, r.network, r.nexthop_ip, rp.hop + 1
    FROM v_l3_routes r
    JOIN route_path rp ON r.device_id = (
        SELECT device_id FROM v_l2_interfaces WHERE ip_address = rp.nexthop_ip
    )
    WHERE rp.hop < 10  -- 防止环路
)
SELECT * FROM route_path;
```

```python
# === 新文件: src/olav/tools/react_query.py (~100行) ===

import duckdb
from langchain_core.tools import tool
from pathlib import Path

SNAPSHOTS_DIR = Path("exports/snapshots")

@tool
def discover_data(pattern: str = "*/parsed/*/*.json") -> str:
    """发现可用的 JSON 数据文件，返回文件列表和示例 schema。"""
    import glob
    files = glob.glob(str(SNAPSHOTS_DIR / pattern))
    if not files:
        return "No files found"
    
    # 返回文件列表 + 第一个文件的 schema
    sample_sql = f"SELECT * FROM read_json_auto('{files[0]}') LIMIT 1"
    sample = duckdb.query(sample_sql).df()
    return f"Found {len(files)} files\n\nSample from {files[0]}:\n{sample.to_markdown()}"

@tool  
def query_network(sql: str) -> str:
    """执行 DuckDB SQL 查询网络数据。支持 read_json_auto() 直接查询 JSON。"""
    try:
        result = duckdb.query(sql).df()
        if len(result) > 100:
            return f"返回 {len(result)} 行 (显示前 50):\n{result.head(50).to_markdown()}"
        return result.to_markdown()
    except Exception as e:
        return f"SQL Error: {e}\n\nTip: 使用 read_json_auto('exports/snapshots/.../*.json')"

@tool
def inspect_file(file_path: str) -> str:
    """查看单个 JSON 文件的结构和完整内容。"""
    sql = f"SELECT * FROM read_json_auto('{file_path}')"
    return duckdb.query(sql).df().to_markdown()
```

使用 ReAct 模式自主查询网络数据，无需预定义 Schema。

### 工具
1. `discover_data(pattern)` - 发现可用数据文件
2. `query_network(sql)` - 执行 DuckDB SQL
3. `inspect_file(file)` - 查看文件详情
4. `nornir_execute(device, cmd)` - 实时采集 (回退)
5. `list_devices(...)` - 列出设备

### 查询示例

#### 示例 1: BGP 邻居状态
```sql
SELECT * FROM read_json_auto('exports/snapshots/*/parsed/*/show-ip-bgp-summary.json')
WHERE state_or_prefixes_received NOT LIKE '%Established%';
```

#### 示例 2: 跨设备路由对比
```sql
SELECT 
    regexp_extract(filename, 'parsed/([^/]+)/', 1) AS device,
    network, next_hop, metric
FROM read_json_auto('exports/snapshots/2026-01-15/parsed/*/show-ip-route.json')
WHERE network LIKE '10.%';
```

#### 示例 3: 拓扑发现 (替代 topology_importer.py)
```sql
-- CDP 邻居
SELECT device, neighbor, local_interface, neighbor_interface
FROM read_json_auto('exports/snapshots/*/parsed/*/show-cdp-neighbors*.json')
UNION ALL
-- BGP 邻居
SELECT device, bgp_neighbor AS neighbor, 'BGP' AS local_interface, neighbor_as
FROM read_json_auto('exports/snapshots/*/parsed/*/show-ip-bgp-summary.json')
UNION ALL
-- OSPF 邻居
SELECT device, neighbor_id AS neighbor, interface, state
FROM read_json_auto('exports/snapshots/*/parsed/*/show-ip-ospf-neighbor.json');
```

#### 示例 4: 历史趋势对比
```sql
WITH 
    snap1 AS (SELECT * FROM read_json_auto('exports/snapshots/2026-01-14/parsed/*/show-ip-bgp-summary.json')),
    snap2 AS (SELECT * FROM read_json_auto('exports/snapshots/2026-01-15/parsed/*/show-ip-bgp-summary.json'))
SELECT 'Prefix Change' AS metric,
       s1.bgp_neighbor, 
       s1.state_or_prefixes_received AS before,
       s2.state_or_prefixes_received AS after
FROM snap1 s1 JOIN snap2 s2 ON s1.bgp_neighbor = s2.bgp_neighbor
WHERE s1.state_or_prefixes_received != s2.state_or_prefixes_received;
```

5. 如果查询失败，分析错误并重试 (ReAct 自愈)

## 6. Sync 功能机制深度分析

### 启动机制
- **入口**: 通过 `sync_all` 工具触发，通常绑定 CLI 的 `/sync` 命令。
- **流程**: 采用 **Stage 1 (Blocking) + Stage 2 (Async)** 双阶段设计。
  - Stage 1: Nornir 并发采集 (IO密集型)，阻塞返回。
  - Stage 2: 线程池后台处理 (CPU密集型)，含 Parsing、Report Generation、Topology Import。

### 回落与容错 (Fallback)
- **Query (智能混合)**: 计划调整为 **"Cache First, Real-time Fallback"** 策略。
  - *默认行为*: 优先查询 Sync 本地快照（毫秒级响应），极大提高查询效率。
  - *回落机制*: 若本地无数据，自动降级为实时连接设备采集。
  - *强制实时*: 仅当用户明确要求（如 "live", "real-time", "now"）时，才跳过缓存进行实时采集。
  - *实现路径*: 通过优化 Skill Prompt (如 `quick-query`) 引导 Agent 优先检查数据库，而非修改底层代码。
- **Analysis (宏观)**: 定位为基于 Sync 数据的全网/历史趋势分析工具，专注于宏观层面，不处理单点实时诊断。

### Diff 功能状态
- **状态**: 已启用 (`diff_configs` 工具存在)。
- **风险**: 路径配置可能存在不一致。
  - `sync_all` 输出路径: `raw/{device}/running-config.txt`
  - `diff_configs` 读取路径: `configs/{device}_running.txt`
  - **严重性**: 高。若无中间搬运逻辑，Diff 功能由于找不到文件将**完全失效**。需在本次发布前修复路径对齐问题。

基于用户反馈，**已完成** 数据目录名称和结构的语义化重构，消除歧义并匹配实际功能。

### 核心变更建议
1.  **更名 `sync` -> `snapshots`**:
    - **原理**: `sync` 是动词（操作），`snapshot` 是名词（结果/制品）。
    - **动作层变更 (Skills/Commands)**:
        - Skill: `daily-sync` -> **`network-snapshot`** (强调生成快照的能力)
        - Command: `/sync` -> **`/snapshot`** (如 `/snapshot take`)
        - Workflow: `run_sync` -> **`create_snapshot`**
    - **制品层变更 (Directories)**: 
        - `data/sync/YYYY-MM-DD` -> `exports/snapshots/YYYY-MM-DD`

2.  **重组用户目录 (`data` -> `exports`)**:
    - **原理**: 根目录 `data/` 含义模糊，包含 raw logs、reports 和 viz。建议改为 `exports/`，明确这是用户可消费的输出。
    - **结构映射 (Skill-Based Mapping)**:
      ```text
      exports/
      ├── snapshots/        (← network-snapshot skill: 纯数据快照，Raw/Parsed)
      ├── reports/          (← 交付给人的 Markdown/PDF 报告)
      │   ├── snapshots/    (周期性快照报告, e.g., Daily Health Check)
      │   └── analysis/     (即时分析报告, e.g., BGP Troubleshooting)
      └── visualizations/   (← visualize skill: HTML 拓扑图)
      ```

3.  **解决 "Reports" 目录歧义**:
    - **问题**: `sync/.../reports` (存放过程元数据) 与 `data/reports` (存放最终报告) 易混淆。
    - **设计优化**: 
        - 快照内的元数据目录更名为 `meta/`。
        - 结构示例:
          ```text
          exports/snapshots/2026-01-14/
          ├── raw/          (CLI 原始输出)
          ├── parsed/       (JSON 结构化数据)
          ├── meta/         (原 reports: 存放 summary.json, process logs)
          └── db/           (可选: 该快照特定的 sqlite/duckdb dump)
          ```
        - `exports/reports/` 细分为 `analysis/` (专项分析) 和 `snapshots/` (例行巡检)，分别对应不同的 Skill 输出。

4.  **重组内部目录 (`.olav/data` -> `.olav/db`)**:
    - **原理**: `.olav/data` 实际存放的是 DuckDB 文件，更名为 `db` 更准确。
    - **数据库重命名**:
      - `topology.db` -> **`network_warehouse.duckdb`**: 存放拓扑、设备清单、Sync 元数据（不仅是拓扑）。
      - `capabilities.db` -> **`registry.duckdb`**: 存放 Command 定义、API 注册表。
      - `knowledge.db` -> **`knowledge.duckdb`**: 存放 RAG 向量和文档索引。

5.  **数据库文件审计**:
    - 发现存在文件碎片化问题，需归拢：
      - `data/sync/.../reports/topology.db` (Sync 生成的临时库) -> 应合并入 `network_warehouse.duckdb`。
      - `.olav/checkpoints.db` (LangGraph 状态) -> 移入 `.olav/db/`。
