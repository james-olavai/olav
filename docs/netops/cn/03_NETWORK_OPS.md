# Network Ops Agent 用户指南

**Ops Agent** 是为网络工程师设计的**深度问题解决工具**。它不是简单的数据查询，而是一个能思考、能分析、能规划的助手。当你面对：
- **生产故障** - 需要找到根本原因
- **复杂变更** - 需要评估所有影响
- **网络规划** - 需要验证设计可行性

就是用 Ops Agent 的时候。

### 🚀 Ops Agent 是一个高维度的故障处理 AI

不同于 Quick Agent 的"浅层数据库查询"，Ops Agent 运作在**多个维度**：

| 维度 | 能力 | 例子 |
|------|------|------|
| **厂商融合** | 跨越多厂商（Juniper、Cisco、Arista等）数据库的联合查询 | "R1 (Juniper) 和 R2 (Cisco) 的路由策略冲突在哪里？" |
| **时间回溯** | 历史数据穿梭，对比任意两个时间点的配置和状态变化 | "这三天 BGP 邻接变化的趋势是什么？" |
| **状态探查** | 主动探测（Ping、Traceroute、端口扫描）实际网络状况 | "从运维机到 DC 的路径实际延迟是多少？" |
| **CLI 执行** | 并行执行 show 命令收集实时数据 | "同时查询 5 台核心路由器的路由表" |
| **日志关联** | 跨设备日志分析，找出时间相关的事件 | "BGP 宕机时，哪些设备日志显示异常？" |
| **数字孪生** | 模拟网络行为（故障、变更），预测实际影响 | "假如我关闭 R1-R2 链接，会影响哪些前缀的可达性？" |

这些维度联合起来，才能完成 Quick Agent 无法做的**深度分析**。

## 🎯 为什么需要 Ops Agent？

### 当你遇到这些问题...

| 问题描述 | Quick Agent | Ops Agent |
|---------|-----------|-----------|
| "BGP 在 R1 上又宕了，这次为什么？" | ❌ 只能查条件 | ✅ **根本原因分析** |
| "我想升级 R1-R2 的链接，会有什么影响？" | ❌ 无法仿真 | ✅ **变更影响分析** |
| "网络有没有环路？在哪里？风险大吗？" | ❌ 只能看拓扑 | ✅ **深度拓扑分析** |
| "我们的网络在核心链路故障时会怎样？" | ❌ 无法模拟 | ✅ **故障场景仿真** |
| "这三天配置和路由表怎么变化的？" | ❌ 只能按查询 | ✅ **时间序列分析** |

### Quick Agent vs Ops Agent

```
Quick Agent 回答"是什么"和"有多少"：
✅ "R1 的 BGP 邻接有几条？"         → 立刻返回数字
✅ "S1 第 1-5 端口的接口状态？"       → 列表展示
✅ "数据中心有多少设备？"           → 直接查询

Ops Agent 回答"为什么"和"会怎样"：
✅ "BGP 为什么宕了，怎么修？"        → 多步推理 + 方案
✅ "变更一条链接，整个网络会怎样？"  → 全量仿真 + 风险评估
✅ "我要做一个网络设计改变，会不会破裂？" → 验证 + 对标
```

## 🚀 真实场景 1：生产 BGP 故障排查

### 问题场景
周一下午 2 点，告警来了：**数据中心无法访问**。

你的第一反应：检查核心路由器 R1，发现 BGP 邻接表一片红。`olav "Show BGP status on R1"` 只能告诉你现在的状态，但解决不了根本问题。

你需要知道：
- **为什么** BGP 从稳定变成宕了？
- **昨天有什么变化** 引起的吗？
- **物理链路本身没事吗？**
- **怎么最快修复？**

### 使用 Ops Agent

```bash
$ olav --agent ops \
  "BGP session to data center keeps flapping for 3 hours. \
   Root cause analysis: config change? hardware issue? network problem? \
   How to fix?"
```

### Ops Agent 的分析过程

1. **路由检查** - 查询 BGP 路由表、邻接状态、AS-PATH
2. **历史对比** - 对比 3 小时前的配置和路由，发现变化
3. **拓扑验证** - 确认 R1 到数据中心的物理链路实际可达
4. **链路探测** - 主动 Ping 和 Traceroute 确认网络连通
5. **综合诊断** - 关联所有信息，找出根本原因

⚠️ 进一步验证（做完立刻修复后）：

   3. 查一下谁在 11:15 做的这个修改（审计）

   1. 建立 BGP timer 标准（建议 keepalive 30, hold 90）
   2. 在 Ansible playbook 中强制一致性
   3. 添加告警：如果 BGP 邻接连续抖动 3 次，立刻通知

## 🔄 真实场景 2：变更规划与影响评估

### 问题场景
你是网络规划工程师，需要做一个**核心网络升级**：

把 R1 和数据中心之间的链接从 1G 升级到 10G。这听起来很简单，但风险呢？
- 新的 10G 链接会不会改变流量走向？
- 如果新链接坏了，备用路由会怎样？
- 是否会产生新的拥塞点？
- 要准备回滚方案吗？

### 使用 Ops Agent

```bash
$ olav --agent ops \
  "Plan: Upgrade R1-DC_GW link from 1G to 10G. \
   Simulate the change, show routing impact, identify risks, \
   provide rollback plan."
```

### Ops Agent 的仿真流程

1. **当前状态快照** - 记录升级前网络状态（拓扑、路由、成本）
2. **变更仿真** - 虚拟修改链接 BW，重新计算 OSPF/BGP
3. **影响分析** - 哪些流量会改路由？新路由的成本和延迟？
4. **故障场景仿真** - 新链接假设故障，网络会降级吗？
5. **对标验证** - 新配置是否符合网络设计标准？

## 🛡️ 真实场景 3：网络风险评估与规划

### 问题场景
你是运维主管，老板问了个问题：

> "我们的网络有多稳定？核心链路故障了会怎样？"

这不是一个快速查询能回答的。你需要：
- **全面评估** 网络中的单点故障
- **找出风险** 在哪些地方
- **规划改进** 如何提升冗余度

### 使用 Ops Agent

```bash
$ olav --agent ops \
  "Network resilience assessment: \
   1. Identify single points of failure \
   2. Simulate each critical link/device failure \
   3. Show impact on data center connectivity \
   4. Recommend improvements"
```

## ⚡ 快速开始

### 基本用法

```bash
# 命令行界面
cd /home/yhvh/Olav
olav --agent ops "你的问题"

# 例子
olav --agent ops "为什么 BGP 在 R1 宕了？"
olav --agent ops "分析网络韧性，找出所有单点故障"
olav --agent ops "模拟升级 R1-R2 链接，预测影响"
```

### Python 代码

```python
from olav.agents.ops import OpsAgent

agent = OpsAgent()

# 故障排查
result = agent.run("为什么 BGP 在 R1 宕了？")
print(result)

# 变更规划
simulation = agent.run("模拟 R1-R2 链接从 1G 升到 10G，预测影响")
print(simulation)
```

## 💡 最佳实践

### 1. 提供充分的上下文
**好：**
```
"BGP session to DC went down 3 hours ago and keeps flapping. 
 The link is 1G, connect to DC_GW. We depend on this for DC traffic.
 Root cause + fix recommendation?"
```

**差：**
```
"Why is BGP down?"
# 系统不知道你说的哪个 BGP
```

### 2. 明确指定时间范围
**好：**
```
"R1-R2 link was stable yesterday but started having issues 
 since this morning. What changed?"
```

**差：**
```
"What changed on R1?"
# 太宽泛，无法指定分析范围
```

### 3. 说出你的目标
**好：**
```
"I want to upgrade our DC link from 1G to 10G. 
 Show me the routing impact, failure scenarios, and migration plan."
```

**差：**
```
"Upgrade DC link"
# 系统不知道该分析什么方面
```

### 4. 如果是变更规划，明确受影响的业务
**好：**
```
"Plan: enable OSPF graceful restart on all core routers. 
 Impact on: DC connectivity, internet egress, local site traffic?"
```

**差：**
```
"Change OSPF settings"
# 系统可能漏掉某些业务
```

## 🎬 何时使用 Ops Agent？

| 情景 | 判断 | 行动 |
|------|------|------|
| "R1 现在 BGP 状态是什么？" | 快速查询 | → Quick Agent |
| "R1 为什么 BGP 宕了？" | 需要分析 | → **Ops Agent** |
| "有多少条路由？" | 统计查询 | → Quick Agent |
| "如果删掉链接 R1-R2，流量怎么走？" | 需要仿真 | → **Ops Agent** |
| "接口有没有错误？" | 事实查询 | → Quick Agent |
| "为什么接口状态抖动？"  | 需要根因分析 | → **Ops Agent** |

## 🔧 配置与优化

### 修改仿真深度（api.json）

```json
{
  "agents": {
    "ops": {
      "max_reasoning_steps": 5,          // 最多推理 5 步
      "simulation_iterations": 1000,     // 仿真迭代次数
      "include_failure_scenarios": true  // 是否模拟故障
    }
  }
}
```

### 查看分析过程

```bash
# 启用详细日志
export OLAV_DEBUG=1
olav --agent ops "你的问题"

# 查看分析日志
tail -f .olav/logs/users/$(whoami).log | grep ops
```

## 🚫 能力边界

### ✅ Ops Agent 能做

- ✅ **故障根因分析** - 配置、拓扑、状态变化对比
- ✅ **变更影响评估** - 仿真路由、流量、故障转移
- ✅ **网络韧性评估** - 单点故障分析、风险识别
- ✅ **规划建议** - 基于仿真的网络设计优化
- ✅ **性能影响预测** - 延迟、吞吐量、收敛时间

### ❌ Ops Agent 不能做

- ❌ **配置推送** - 仅规划和分析，不执行变更
- ❌ **流量抓包分析** - 没有 pcap 数据采集
- ❌ **安全审计** - 不专注于安全角度（建议用 Quick Agent 查配置）
- ❌ **实时监控告警** - 基于快照分析，不是实时流

## 🆘 常见问题

### Q: Ops Agent 分析结果和实际情况不符？

**A:**
1. 检查数据新鲜度：`olav "When was the last snapshot?"`
2. 可能是数据采集不完整（比如没采集 BGP 邻接）
3. 重新触发一次快照：`olav snapshot now`
4. 再运行 Ops Agent

### Q: 大网络（> 500 设备）怎么用？

**A:**
- 分段仿真：`"Simulate failures in northeast region only"`
- 降低仿真深度：调整 `api.json` 的 `simulation_iterations`
- 在离线模式下缓存拓扑

### Q: 仿真花了 30 秒还没出结果？

**A:**
这是正常的。Ops Agent 在做深度分析，包括：
- 多路径计算
- 多个故障场景仿真
- 历史数据关联

如果超过 2 分钟，可以 `Ctrl-C` 中断，降低复杂度重试。
