# 106. Presales LLD — validation-driven + experience-grounded (supersedes §98 §4)

**Status**: Implemented + scoped. Phase 1 (generic validation-driven LLD +
structured handoff) done; product boundary set at the structured, validated LLD
(no deployment-plan generation — 2026-07-23).
**Date**: 2026-07-23
**Supersedes**: dev_docs/98 §4 (the spine-leaf "fat-tool, correct-by-construction" LLD)
**Builds on**: [104](104.%20PRESALES_RESEARCH_AND_SELECTION_ANALYST.md) (grounding),
[105](105.%20PRESALES_E2E_RUNSHEET.md) (the limitations this closes)

## The problem

The LLD generator was a **hardcoded, per-topology Python tool**: `plan_fabric` /
`build_spine_leaf_skeleton` bake the spine-leaf graph, ASN scheme, and /31 P2P
into code; `render_lld_markdown` hardcodes "Spine-leaf (Clos) … eBGP underlay";
`render_fabric_configs` renders spine-leaf Arista configs. Adding a topology
(campus 3-tier, WAN hub-spoke) meant **another hardcoded generator** — the
anti-pattern (dev_docs/105 #3). It violates the generality principle: topology
knowledge lived in Python, not data.

## The reframe

**Correctness comes from VALIDATION (generic), not from GENERATION (hardcoded).**
OLAV's simulators are networkx, Batfish, and (future) CLAB — generic oracles that
validate *any* topology. So:

- The **LLM designs** the topology + addressing + routing, **grounded by injected
  experience** (RFC 7938 ASN scheme + no-summarization + ECMP; the oversubscription
  calc; design-pattern guides; the expert_knowledge flywheel). The design knowledge
  that *was* in `plan_fabric` now lives as **memory/references** — so adding a
  topology is adding *experience*, not Python.
- **Generic deterministic math** still owns what small models can't: exact IP /
  subnet allocation over an explicit skeleton (`plan_ip_allocation`). This is NOT
  hardcoded-per-topology — it takes any device/link list. It stays.
- **networkx validates the DESIGN** (presales's own rung): connectivity /
  redundancy / SPOF over the persisted topology. This is the validation presales
  owns — it proves the *design* is sound.
- **Deployment is out of scope — presales stops at the structured, validated
  design.** The deliverable is the networkx-validated LLD + a field-aligned
  structured handoff (`presales.topology_*`); the deployment narrative/execution
  is handled by the human + vendor tools + the customer's own model, fed by that
  export. A prose "deploy runbook" was rejected (not productive, not verifiable, a
  frontier-model commodity, worst fit for OLAV — see Product boundary below). Any
  beyond-design work is **conditional** and must be machine-actionable + validatable
  (configs / API-intent / IaC), landing in netops/olav-ent — never prose. netops
  owns Batfish (presales only *borrowed* `batfish_q`); presales does NOT run it
  (removed 2026-07-23).
- **Loop**: propose (grounded LLM) → networkx validate → revise → converge; then
  hand off. The design/implementation split keeps presales light.

This keeps the fat-tool discipline where it belongs (deterministic IP math) and
removes it where it was hardcoding (topology structure + config semantics).

## The generic skeleton contract

The LLM produces one topology-agnostic object; every generic primitive consumes it:

```yaml
skeleton:
  devices:  [{name: sw1, role: spine|leaf|core|access|hub|spoke|...}]   # any roles
  links:    [{a: sw1, a_iface: Eth1, b: sw2, b_iface: Eth1}]            # any graph
  p2p_scheme:      {pool: 10.0.0.0/24, prefix_len: 31}
  loopback_scheme: {pool: 10.0.255.0/24, prefix_len: 32}   # optional; every device
  routing:  {protocol: ebgp, asn: {sw1: 65000, sw2: 65001}}  # optional; LLM-produced,
                                                             # grounded by RFC 7938 §5.2
```

- `plan_ip_allocation(skeleton)` — P2P from `links` (already generic) + loopbacks
  from `devices` + `loopback_scheme` (was spines/leaves — made generic).
- `generate_bgp_sessions(skeleton, ip_allocation)` — one session per P2P link,
  ASN from `routing.asn` (LLM-produced map, grounded) — was the hardcoded
  spines-share / leaves-increment rule.
- `inspect_topology_health` — networkx over the persisted graph (already generic).
  **This is presales's only validator.**
- `render_lld` — a generic doc from skeleton + allocation + (optional) a
  `propose_structure` profile — no topology-name baked in.
- Config-layer validation (Batfish) + lab (CLAB) are **not presales** — the LLD
  hands off to netops (below).

## What is deleted vs kept

| Deleted (topology-hardcoded) | Kept / made generic |
|---|---|
| `fabric.py` `build_spine_leaf_skeleton` + `plan_fabric` | `plan_ip_allocation` (generic IP math) |
| `render_lld_markdown` spine-leaf text | generic `render_lld` (skeleton-driven) |
| `_as_map` spines-share/leaves-increment | `generate_bgp_sessions` reads `routing.asn` |
| `plan_ip_allocation` spines/leaves loopbacks | loopbacks over generic `devices` |
| **`batfish_validate.py` + `validate_lld.py` (config-layer)** | **removed from presales → netops** (implementation) |

The LLM produces the skeleton (the deleted logic's knowledge is now injected
experience). The deterministic math + the networkx validator are generic and stay;
config-layer validation left the domain entirely.

## Rollout + product boundary

- **Phase 1 (implemented)** — the generic skeleton path + **networkx** validation
  (presales's only rung). Deleted the spine-leaf builder/renderer AND the
  presales Batfish (`batfish_validate.py` / `validate_lld.py`);
  `generate_lld(skeleton, …)` runs generic allocation → persist → render;
  `inspect_topology_health` validates any topology. The engineer designs the
  skeleton grounded by the references. Verified topology-agnostic via a hub-spoke
  WAN (not spine-leaf) through the real entry point.
### Product boundary (decided 2026-07-23): stop at the structured, validated LLD

The presales deliverable is the **structured, networkx-validated LLD + a
field-aligned structured handoff** — NOT a generated deployment plan.

**A prose deployment runbook was considered and rejected as low-value:**
- **Not productive** — prose is not executable; it does not do work.
- **Not verifiable** — the LLD has networkx and configs have Batfish, but a prose
  runbook has no validation oracle; its correctness can't be checked.
- **Implementation is project-specific human judgement** — maintenance windows,
  existing state, cabling, change control, per-site staging — a canned plan can't
  capture it; the field engineer adapts regardless.
- **It is a frontier-online-model commodity, and the worst fit for OLAV** — open-
  ended narrative generation is exactly where small local models are weakest AND
  where there is no verification. OLAV's thesis is deterministic / structured /
  validatable output; a prose runbook is the opposite. Pasting the LLD into an
  online model already yields a decent narrative.

So the **deployment narrative + execution are out of scope**: handled by the
human + vendor tools + the customer's own (online) model, **fed by OLAV's
structured export** (`presales.topology_*` + the LLD). OLAV's job is the precise,
validated design + a machine-consumable handoff — the narrative is a commodity.

**Handoff contract — structured LLD (DONE 2026-07-23)**: `generate_lld` persists
the addressing/routing to queryable, field-aligned tables (not just doc prose) —
`topology_nodes.loopback_ip` + `.bgp_asn`, `topology_links.source_ip` +
`.destination_ip`. The full eBGP matrix + per-device interface spec are
reconstructable from these + the graph (verified: rebuilt purely from the two
tables). Any downstream (netops, the customer's automation, or an online model)
consumes this.

### Optional beyond-design (conditional — only where it is machine-actionable AND validatable)

Build past the LLD **only** for a specific platform where the artifact is
**structured + has a validation oracle** — never prose:
- device configs (Batfish-validatable), or controller **API payloads / IaC**
  (Terraform/Ansible — schema- + dry-run-validatable) for Mist / DNAC / Central.
These are productive (executable) AND verifiable. Gated on a real customer
automation need. Lands in **olav-ent**, calling netops baseline primitives;
config/deploy validation (Batfish for CLI-parseable, CLAB, controller dry-run) is
management-plane-specific and lives in netops. **networkx validates the DESIGN
and is universal** — it stays presales's rung regardless.

**Grounding input (if beyond-design is ever built)**: products move fast, so
never trust the model's parametric knowledge — ground in ingested docs at
runtime. **User download-import is primary** (Docling ingest → §2.6 project
recall, or `olav kb import-kb` → expert_knowledge), because it controls freshness
AND because **many vendor manuals are non-public** (partner portal / NDA /
pre-release) — web search cannot reach them. That non-public, curated manual
corpus is exactly the **commercial content layer** (dev_docs/104 §9). Allowlisted
vendor-official **web fetch is secondary**, for public docs only (dev_docs/104
§8.1). Ingested docs carry `source + retrieved_date`; re-import on a new release;
artifacts cite the doc version (§2.7 staleness).

(Empirical note: netops's only change-plan tool today is a CLI-upgrade generator
reading existing `netops.devices` — it cannot consume an LLD; any beyond-design
work is new, and only justified by the machine-actionable+validatable bar above.)

## Enterprise positioning + open-source isolation (2026-07-23)

presales is an **enterprise feature**, and the LLD→change-plan (greenfield
deploy) lands in the enterprise tier. Decisions + isolation:

1. **License**: olav-presales → **Proprietary** (was BSL-1.1, the olav/olav-netops
   baseline). `License :: Other/Proprietary License`.
2. **Distribution**: bundled with **olav-ent** (private channel); never public PyPI.
3. **Deploy-plan placement**: presales stops at the structured, validated LLD
   (no deployment plan generated — see Product boundary). Any conditional
   beyond-design artifact (machine-actionable + validatable configs / API-intent /
   IaC — never prose) lands in **olav-ent**, calling netops baseline primitives.
   netops stays generic/BSL; curated grounding manuals are the commercial layer.
4. **Entitlement gate**: future (olav-ent has none built yet; today's isolation is
   license + distribution + entry-point discovery).
5. **Docs**: presales dev_docs stay in the monorepo — gitea is the internal forge
   and is not isolated.

**Isolation mechanism** (the leak point was the public monorepo mirror, which
strips only credentials): `scripts/publish_github_mirrors.py` now strips the
enterprise/private delivery units (`_ENTERPRISE_UNIT_PATHS` = olav-ent,
olav-presales, olav-post) from the public GitHub mirror via
`git-filter-repo --invert-paths` + a verify gate. gitea keeps full source; the
public mirror never receives presales (177 tracked enterprise-unit files stripped;
also closes a pre-existing gap where olav-ent's tracked files were mirrored).
Guarded by `tests/governance/test_enterprise_mirror_isolation.py`. Entry-point
discovery already isolates at runtime: a baseline install (olav + olav-netops)
has no presales package → no presales agent.

## Honest risks

1. **Small-model reliability at scale.** The LLM emitting a large exact skeleton
   (60-device edge/ASN lists) may not converge. Mitigations: IP math stays
   deterministic; the LLM works at design-intent level; validate + iterate. For
   large regular graphs a **generic** graph expander (e.g. networkx's built-in
   `complete_bipartite_graph` — graph theory, not OLAV topology code) can
   materialise edges from an LLM-chosen pattern + params. Needs N≥3 behavioural
   validation.
2. **Trade**: hardcoded generation is "correct by construction"; validation-driven
   is "converges under validation". More general + principle-aligned, but with
   convergence risk instead of construction guarantees.
3. **Deployment is deliberately out of scope** — modern new-builds are
   controller/cloud-managed (Mist/DNAC/Central/Meraki/CloudVision), so neither a
   per-vendor CLI synthesizer NOR a prose runbook is worth building (not
   verifiable; a frontier-model commodity). The product stops at the structured,
   validated LLD + handoff; deployment is the customer's + vendor tools' + an
   online model's job. Residual: beyond-design is built only when it is
   machine-actionable + validatable (configs / API-intent / IaC), and even then is
   grounding- and oracle-dependent.
