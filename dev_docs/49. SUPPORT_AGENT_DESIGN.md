# 49. Support Agent — toB 自助支持与脱敏诊断

**Date:** 2026-04-23
**Status:** Draft / 待评审（未实施）
**Scope:** 新增 `core/support/` 子技能，提供 `/support` 一键自助支持：
issue triage、文档 RAG 问答、诊断脚本运行、脱敏 bundle 升级给人工。
**Origin:** toB 商业化场景讨论 —— 降低 L1 人工支持成本。
**Package:** olav 核心包（无新顶级 agent，不触发 ADR-0004）。

---

## 1. 定位

| 现有 agent | 做什么 |
|-------|--------|
| core（quick） | 快速查询 + 默认路由 |
| ops / audit / devops / infra | 领域工作流 |
| **support（新）** | **用户遇到问题时的第一站** —— 回答"怎么做"、诊断"为什么坏"、打包"我该给谁什么" |

**判断：作为 `core/support/` 子技能而非顶级 agent。**

理由：
1. `core` 已经有 `api_query` / `db_query` / `remote` / `admin` / `writer` 多个子技能并列，新增一个不改顶层架构；
2. 不触发 ADR-0004（新顶级 agent 扩展政策）的流程；
3. `/support` 可由 core 路由器直接分发，与 `/catalog`、`/refresh_workspace` 等内置 slash command 对齐；
4. 诊断工具（`check_health` / `analyze_logs` / `audit_workspace`）目前散在 `audit/` 与 `core/admin/` 中，借本次引入做一次内聚。

---

## 2. 四层能力拆分

不把"support"塞进一个 prompt 里。四层独立工具，LLM 只负责编排：

```
用户 /support "我的 netops_init 卡在 Stage 3 不动了"
        │
        ▼
┌──────────────────────┐
│ 1. TRIAGE            │  LLM 分类：install / config / query-error / bug / usage
│                      │  决定下一步：查 KB / 跑诊断 / 升级
└──────────┬───────────┘
           │
    ┌──────┴──────┬──────────┬──────────┐
    ▼             ▼          ▼          ▼
┌────────┐  ┌─────────┐ ┌────────┐ ┌────────────┐
│ 2. KB  │  │ 3. DIAG │ │ 4. ESC │ │ (CONTINUE) │
│ 检索   │  │ 诊断   │ │ 升级  │ │  继续对话  │
└────────┘  └─────────┘ └────────┘ └────────────┘
   │            │            │
   ▼            ▼            ▼
 answer     artifacts    bundle.tar.gz
```

| 层 | 输入 | 工具 | 输出 |
|---|---|---|---|
| 1. Triage | 用户自由问题 | LLM + routing prompt | category + 推荐动作 |
| 2. KB 检索 | 问题 + category | `search_docs` (RAG) | 引用片段 + 答案 |
| 3. Diagnostics | 诊断方向 | `check_health` / `analyze_logs` / `audit_workspace` | 结构化报告 |
| 4. Escalation | 诊断结果 + 用户同意 | `build_support_bundle` | 脱敏 tarball |

## 4. 工具签名

### `search_docs`

```python
@tool
def search_docs(query: str, lang: str = "en", k: int = 5) -> list[dict]:
    """Semantic search over the packaged olav-doc knowledge base.

    Returns up to k chunks, each with {title, url, excerpt, score}.
    KB is an embedded DuckDB table shipped inside the wheel (see §6).
    """
```

### `run_diagnostic_suite`

```python
@tool
def run_diagnostic_suite(scope: str = "all") -> dict:
    """Run a sequenced diagnostic battery and return one structured report.

    scope ∈ {"all", "install", "collect", "db", "workspace"}

    Internally calls check_health + analyze_logs + audit_workspace and
    normalises their outputs into:
      {
        "status": "healthy" | "degraded" | "broken",
        "checks": [{name, status, detail, evidence}...],
        "timestamp": ISO-8601,
        "suggested_action": "self-serve" | "escalate",
      }
    """
```

### `build_support_bundle`

```python
@tool
def build_support_bundle(include: list[str] | None = None) -> dict:
    """Assemble a redacted tarball at exports/support/<ts>/bundle.tar.gz.

    include defaults to ["diagnostics", "audit_logs", "workspace_manifest",
                        "recent_errors", "version_info"]

    Redaction rules (see BUNDLE_SCHEMA.md):
      - Strip Nornir credentials, api_keys, tokens, passwords
      - Hash device hostnames + IPs (keep structure, kill identity)
      - Drop raw_output_store contents; keep only row counts per device
      - Drop secrets.*, *.env, credentials/
      - Preserve: audit logs (already redacted), health reports, manifest

    Returns {path, sha256, redacted_items_count, entries_count}.
    """
```

## 5. `/support` 交互流程

### 5a. 快速路径（KB 答得了）

```
$ olav /support "怎么添加一个 Palo Alto 设备？"

support > 这是"usage / extensibility"类问题，查文档。
          [search_docs → 3 chunks from netops/concepts/extensibility.en.md]

          按 OLAV 文档的 Step 1-3：
          1. 在 Nornir inventory 加一行 `platform: paloalto_panos`
          2. 如果要 model/version：加到 platform_profiles.yaml
          3. 命令会自动从 ntc-templates 扫描填充 netops.commands 表

          📎 完整步骤：docs.olavai.com/netops/concepts/extensibility#add-a-new-vendor
```

### 5b. 诊断路径（问题不在文档里）

```
$ olav /support "netops_init 跑了 10 分钟还没结束"

support > 这是"collect / performance"类问题。先跑诊断。
          [run_diagnostic_suite scope=collect]

          ⚠ 发现 2 处异常：
          1. 设备 R3 SSH 超时（60s × 3 retries），占用 180s
          2. Stage 3.5b PaC-Learner 对 "show lldp neighbors detail" 卡在
             LLM 调用（超过 300s 的 config ceiling）

          建议：
          - 临时跳过 R3：`.olav/config/nornir/hosts.yaml` 里置 `platform: null`
          - 提高 LLM 超时：`OLAV_PAC_LEARNER_TIMEOUT=600`
          - 如需我打包诊断包给 support？输入 `yes`
```

### 5c. 升级路径（确认要人工）

## 6. KB 索引策略（olav-doc → DuckDB）

### 索引构建

olav-doc 里的 80+ 个 markdown 文件 → DuckDB 向量表，**打包进 olav wheel**（离线可用）。

```
src/olav/data/kb/
├── docs_en.parquet       # {doc_path, heading_path, chunk_text, embedding(768)}
├── docs_zh.parquet
└── index_meta.json       # {commit_sha, embedding_model, build_date, chunk_count}
```

**Chunk 策略**：按 H2 / H3 切块，保留 heading_path（`getting-started/installation > Step 2`）做引用。

**Embedding 模型**：默认用 `text-embedding-3-small`（API），离线环境可切 `BAAI/bge-small-en-v1.5`（本地）。模型 ID 记在 `index_meta.json`。

### 索引刷新流水线

1. **olav-doc 仓库 CI**：每次 merge 到 main 时，触发 `build_kb.py` → 生成 parquet
2. **发布**：parquet 作为 GitHub release asset 附到 olav-doc 的 tag
3. **olav wheel 打包**：`pyproject.toml` 的 build hook 在打包时 `wget` 最新 parquet 塞进 `src/olav/data/kb/`
4. **运行时加载**：`search_docs` 启动时把 parquet load 进 DuckDB in-memory（~10 MB，一次）

**新鲜度退化方案**：index_meta.json 里的 `build_date` 超过 90 天 → `/support` 启动时提示 "KB 已过期，查最新文档请访问 docs.olavai.com"。

## 7. 诊断 Bundle 脱敏（BUNDLE_SCHEMA.md 摘要）

**必删**：
- `.olav/config/api.json` 的 `api_key` / `token` 字段
- `.olav/config/nornir/hosts.yaml` 的 `password` / `ssh_key_path`
- `.olav/logs/` 中匹配 `(password|token|api[_-]?key|secret)=\S+` 的行
- `raw_output_store` 表的 `raw_text` 字段（可能含 running-config / 密码）
- 所有 `.env` 文件

**必 hash**：
- 设备 hostname → `sha256(hostname)[:12]`（保持引用一致性但不暴露身份）
- 设备 IP → `hash` 到同一 /24 的随机 IP
- 用户邮箱 → `user_<sha12>@redacted`

**保留**：
- 审计日志（`audit_events` 表 —— 已经是脱敏格式）
- 健康诊断报告（`diagnostics.json`）
- `ownership_manifest.yaml`
- version info（`olav --version`、wheel SHA、python version）
- workspace 结构清单（只目录，不文件内容）

**校验机制**：
- bundle 生成后自动跑 `grep -iE '(password|api_key|token|secret|bearer)' bundle/**/*.{json,yaml,md,log}`，非零匹配 → 阻塞输出，要求人工复核
- SHA-256 + manifest 写进 bundle 元数据，可追溯

## 8. Triage Rubric（TRIAGE_RUBRIC.md 摘要）

LLM 用这个 rubric 分类：

| Category | 典型问题 | 下一步 |
|---|---|---|
| `install` | "wheel 装不上"、"olav init 报错" | KB → install 章节 + `check_health --scope=install` |
| `config` | "我的 API key 在哪里配置"、"怎么加设备" | KB → extensibility / configuration |
| `collect-error` | "netops_init 失败"、"设备 SSH 不通" | `run_diagnostic_suite --scope=collect` |
| `query-error` | "execute_sql 报 schema 错误" | `check_health --scope=db` + KB → database-schema |
| `usage` | "怎么用 topology agent" | KB → guides / |
| `bug-report` | 明显的 Python traceback | `analyze_logs` + `build_support_bundle` |
| `unknown` | 分不清 | 追问一个澄清问题，最多 2 轮 |

**升级规则**：连续 2 次诊断仍 `degraded` 或 `broken`，主动建议 bundle。

## 9. 风险与权衡

| 风险 | 缓解 |
|---|---|
| KB 过期：doc 频繁改版，embedding 表滞后 | `build_date` > 90 天时提示用户访问在线版；CI 自动重建 |
| 脱敏不彻底：bundle 泄露密钥 | 生成后强制 grep 验证；非零匹配阻塞输出 |
| Triage 误分类：把 bug 当 usage | category = `unknown` 时只澄清不猜，最多 2 轮；保守路由 |
| 诊断工具散布：迁移破坏现有 audit agent 依赖 | 迁入时保留 entry-point shim，audit agent 继续 import；2 个 release 后再 deprecate |
| 离线环境无 embedding API | `BAAI/bge-small-en-v1.5` 本地模型 fallback（~130 MB，可选依赖） |
| B2B SLA 要求响应延迟 | KB 走 parquet in-memory（~10 ms）；诊断 ≤ 30s；bundle ≤ 60s |

## 11. 非目标（本轮不做）

- **Agentic 自动修复**：不做"发现问题后自动执行 fix"。support agent 只诊断与建议，不改用户环境。
- **实时日志流**：`/support` 不做 `tail -f` 交互，logs 一次性 snapshot。
- **多租户支持**：本轮假定单机单用户。enterprise 多租户是 olav-ent 范畴。
- **ticket 回传**：本轮 bundle 是 tar.gz 文件，不做 API 直连 WWT support 系统（Phase 5）。

## 12. 对现有架构的影响

| 组件 | 影响 | 缓解 |
|---|---|---|
| `core/admin/tools/` | 3 个诊断工具有复制品 | 2 release cycle 后删除 admin 侧，改 import shim |
| `audit` agent | 如果引用 `core/admin/tools/analyze_logs` —— 不影响（shim）| N/A |
| `pyproject.toml` | 新增 build hook 下载 KB parquet | 失败时 fallback 到空 KB（search_docs 返回空 + 提示在线文档） |
| olav-doc CI | 新增 `build_kb.py` step | 单文件，不影响现有 MkDocs build |
| olav wheel size | +10~30 MB（embedding parquet） | 可接受；离线价值 > 体积成本 |
| ADR-0004 | 不触发（不是新顶级 agent） | — |

## 13. 验证清单

实施后必须通过：

- **V1 KB 命中率**：20 个真实 FAQ，`search_docs` Top-3 命中率 ≥ 80%
- **V2 诊断覆盖**：人工构造 10 个已知故障场景，`run_diagnostic_suite` 正确识别 ≥ 8 个
- **V3 脱敏零泄露**：把 `.env` + `api.json` 全填充假密钥后跑 `build_support_bundle`，grep 校验 0 匹配
- **V4 离线可用**：断网情况下 `/support "..."` 仍能从本地 KB 给出答案
- **V5 响应延迟**：KB 答案 ≤ 500ms，诊断 ≤ 30s，bundle ≤ 60s
- **V6 triage 准确率**：50 条标注样本，category 分类准确率 ≥ 85%
