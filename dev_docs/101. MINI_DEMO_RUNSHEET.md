# 101. OLAV Mini Demo Runsheet — the 12-minute network-engineer wow

**Date**: 2026-07-18
**Version**: v0.23.1 (public PyPI: `olav` + `olav-netops`)
**Duration**: ~10–13 min (6 beats)
**Companion to**: `dev_docs/100. DEMO_RUNSHEET_V3.md` — that is the full ~50 min
capability sweep; **this is the tight cut**: only the beats that make a network
engineer lean in, each verified end-to-end on a small local model this cycle.

> **Why a mini runsheet.** The full V3 sweep is comprehensive but long. For a
> cold audience (a network engineer who's never seen OLAV), the story lands in
> ~11 minutes if you show exactly six things: it installs itself, ingests a
> real fleet with no SSH, answers in plain language + exports, draws the core,
> **writes a BGP change and then formally validates it**, and runs the morning
> NOC inspection from a versioned Profile. Everything below was run on
> `gemma4-31b` and produced correct output — no frontier model required.

## Setup (off camera)

**LLM backend.** `gemma4-31b-it-qat` at an OpenAI-compatible endpoint
(`http://<host>:11433/v1`, `api_key: local`, `llm.timeout: 600`). This is the
headline claim — a **local ~30B model** runs the whole demo. Do NOT use a
"flash"/tiny model for the agentic beats: in testing `deepseek-v4-flash`
flailed (146 tool calls vs gemma4's 16 on the same task). gemma4-31b or a
frontier model; nothing in between is needed.

**Demo data.** A 339-device campus/DC fleet already imported (Ch1 shows the
import live, or pre-load it). Batfish image cached locally so the
self-service deploy is fast on camera.

**One health line before you hit record:**

```bash
olav doctor          # must be all ✓ — agents/subagents/tools/memory/recall
```

## Ch0 — A clean machine installs and configures itself (2 min) ★

```bash
mkdir ~/olav-demo && cd ~/olav-demo
or
mkdir ~/olav && cd ~/olav
python3 -m venv .venv && source .venv/bin/activate
pip install olav "olav-netops[sim]"  # [sim] = pybatfish, needed by Ch5's formal validation
olav                                  # just run it — it bootstraps + asks once for the LLM key
olav skill install olav-netops        # deploy the network agents from the installed package
olav doctor                           # 8 zero-LLM checks, all ✓
```

**Why they care.** Zero-touch. No `git clone`, no editing YAML. `olav doctor`
proves the whole stack is wired (agents, sub-agents, tools, experience layer,
recall) before you ask it anything — an ops person trusts a tool that
self-diagnoses.

## Ch1 — Ingest a real fleet, no SSH (2 min) ★

```bash
olav --agent netops "Import the network backup at <path-to-archive>.tar.gz"
olav "How many devices and what platforms did we just import?"
```

**Why they care.** You hand it a raw collector dump (a `.tar.gz`); the importer
extracts + normalises + parses (TextFSM) + builds the topology automatically.
339 devices land with zero device access — safe to run against production
backups.

## Ch2 — Ask in English, get a CSV (1.5 min)

```bash
olav "List every device with its model and mgmt IP, and export it to CSV"
```

**Why they care.** The NL question becomes SQL over the parsed inventory and
drops a real `exports/*.csv` — no query language to learn, but the data is
exact, not hallucinated.

## Ch3 — Draw the core network as a draw.io diagram (1.5 min) ★

```bash
olav "Draw the core network topology as a draw.io diagram"
```

Open the resulting `exports/diagrams/core_topology_*.drawio` in diagrams.net.
**Why they care.** A scoped, correct topology (Cisco stencils, real
adjacencies) they can drop straight into a Confluence page. The agent scopes it
sensibly (the core layer, ~16 nodes) instead of dumping the whole fabric.

## Ch4 — Write a BGP change and formally validate it, one command (3 min) ★★★

```bash
# First, the platform stands up its own validation engine — no manual docker:
olav --agent services "Deploy batfish/allinone, ports 9996 9997"
# Then ONE command drafts the change, sanity-checks it, and formally validates
# it with Batfish — a declarative workflow runs analyzer → reporter → simulator:
olav --agent netops "Write a change plan to add a redundant eBGP uplink on the alpha border router, mirroring the existing AARNet peer"
```

**Why they care.** This is the killer beat. That single change-plan request
fans out into three verified sections, stacked in the reply:

- **Draft** — analyzer reads the device's **actual** running-config (not a
  template), finds the real `router bgp <asn>` + the existing neighbour's
  style, and emits mirroring CLI + rollback, saved to `exports/change_plans/`.
- **Pre-check (reporter)** — device/interface/IP sanity against live state +
  an independent blast-radius number ("removing this isolates N nodes").
- **Formal verification (Batfish)** — subnet/overlap conflicts, BGP
  compatibility, reachability — a real verdict, on the agent's **own**
  self-deployed Batfish.

An AI that writes a change **and then formally proves it out** — draft,
pre-check, and Batfish verification from one sentence — is a different
category of tool. (Batfish must be running before this command; the deploy
line above handles it. If it isn't, the workflow still returns the draft +
pre-check and tells you how to bring Batfish up.)

## Ch5 — Scheduled-style audit inspection (1.5 min) ★★

```bash
olav --agent audit "Run the interface_health audit profile and give me the findings"
```

**Why they care.** This is the Day-2 ops loop: a **Profile** (a YAML file of
SQL health checks with severity rules — `.olav/workspace/audit/profiles/`) is
executed deterministically against the state DB, and the agent returns an
executive summary plus a saved report (`exports/audit_reports/*.md` + a
findings JSON). Profiles are plain files: engineers review them, extend them
via the audit author agent ("add a check for X"), and can schedule them with
`olav cron` — the same inspection your NOC runs every morning, but the
checks themselves are versioned, auditable artifacts. Two tool calls,
zero-LLM evaluation — the LLM only narrates findings it can cite.

## Notes / honesty

- Every beat above was run on `gemma4-31b` this cycle and produced correct
  output. Batfish models **BGP** well and EIGRP poorly — keep the Ch4
  change-plan + validation beat on **BGP**, not EIGRP.
- **Ch4 ordering matters**: deploy Batfish *before* the change-plan command —
  the command triggers the analyzer→reporter→simulator workflow whose final
  step formally validates against a running Batfish. `olav doctor` should show
  batfish reachable before you run it (or the deploy line in Ch4 brings it up).
- Ch5 must use **interface_health** (or device_inventory): this dataset has no
  BGP/OSPF TextFSM views, so `bgp_health`/`ospf_health` profiles error out
  (`v_show_ip_bgp_summary_auto` does not exist). Interface/inventory views are
  fully populated.
- For the full capability sweep (KB, conversational HITL memory, drift,
  blast-radius, audit profiles, syslog) see `dev_docs/100. DEMO_RUNSHEET_V3.md`.
