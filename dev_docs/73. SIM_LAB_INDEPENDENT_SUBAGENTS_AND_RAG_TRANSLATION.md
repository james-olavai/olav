## 0. Why

Today's analyzer refactor proved a pattern: a 30B-class LLM can run
`COLLECT → PLAN (L1-L4 layered) → ACT → REFLECT → SYNTHESISE → EMIT`
reliably when the workflow is inlined in `system.md` (not RAG), tools
are narrow (≤6), and `thinking_mode: enabled`. The analyzer now
produces engineer-readable Markdown change plans and audit reports
end-to-end from `execute_sql + describe_table + query_evidence +
inspect_drift_configs + format_and_export`.

The two downstream sub-agents — `sim` and `lab` — are still in their
R-CAB-THREE-STAGE form:

- `sim` is a heavy Python pipeline (`olav.core.cab.sim.finalize`)
  bundling per-intent feasibility + render + lab_subnet allocation +
  rejection-loop wiring. ~2000 LoC of CAB-specific code, much of
  which is reinventing what Batfish and SQL-derived views already
  provide. It runs on a typed `DraftChangePlan` envelope analyzer no
  longer produces.
- `lab` is a single skill-script (`tcf_validate.validate_tcf_in_lab`)
  that folds load→topology→srl→save→deploy→verify→record→destroy
  into one atomic call. Engineer-visible output is a JSON envelope;
  there is no Markdown lab report.

**Problems**:

1. **TCF schema coupling**: both sim and lab assume a Pydantic
   `CabTcf` spec on disk. Analyzer no longer produces one.
2. **Single-purpose**: sim and lab were built for CAB only. The
   "logical validator" and "experimental validator" capability they
   embody is useful for fault analysis, control-plane verification,
   and what-if questions — none of which today have a path through
   sim/lab.
3. **Hardcoded translation**: `postcheck_translate._PROD_TO_SRL_RULES`
   is 50+ regex lines hand-maintained for Cisco/Junos → SRL. New
   vendors require code change. No SRL doc grounding.
4. **DB coupling**: sim queries `netops.devices`, `netops.v_show_*`
   to look up facts the analyzer already collected. Duplicated work.
5. **30B-unfriendly lab**: lab's atomic skill_script can't surface
   intermediate failures cleanly; failure mode is "phase=X error",
   no diagnosis, no markdown narrative.

## 1. Design principles (the contract)

Both new `sim` and `lab` follow the same five rules:

### Principle 1 — Independent
No DB queries. No `execute_sql` in tool list. They operate on the
**user-provided input** (typically a Markdown change plan / audit
finding / fault hypothesis) plus the **RAG knowledge base** (vendor
CLI manuals, SR Linux reference, OSPF/BGP RFC summaries).

### Principle 2 — Sub-agent of equal rank
Sim and lab are not "downstream of analyzer". They are peer
sub-agents reachable from the orchestrator. Analyzer can produce
input for them, but a user prompt like *"verify R3-R4 OSPF is
configured correctly"* routes directly to sim (logic check) without
going through analyzer.

### Principle 3 — Three data substrates → three sub-agents

Different question types live on different data substrates with
incompatible query languages.  Forcing them through one sub-agent
bloats the tool list past the 30B-friendly ceiling and pollutes
each substrate's RAG with the others' noise.

| Substrate | Data shape | Query language | Sub-agent |
|---|---|---|---|
| **Structured DB state** | `netops.v_*_auto` views, `parsed_outputs`, `topology_links`, `devices` | SQL JOIN/WHERE | `analyzer` |
| **Config-as-program** | running-config parsed by Batfish vendor parsers into vendor-neutral model | Batfish question API (`bf.q.<name>(...).answer()`) | `sim` (Batfish-backed) |
| **Raw text streams** | syslog Parquet, `raw_output_store`, config text, command outputs | grep / regex / time window | `investigator` |
| **Experimental** | live SRL containers, real packets | clab deploy + SSH push + show | `lab` (see dev_docs/74) |

Each sub-agent stays at **≤4 tools** because it owns one substrate.
The orchestrator dispatches per query intent; cross-substrate questions
go through analyzer-lead delegation (§2.6).

Sim characteristics: **fast + offline + deterministic** (no infra
beyond a Batfish service; question results are reproducible).
Lab characteristics: **slow + real** (clab containers, 2-10GB RAM,
boot time, real timing artifacts).  Use sim before lab; use lab only
when experimental verification adds value beyond what Batfish can prove.

### Principle 4 — Data-sufficiency protocol
If the user's input is missing facts the sub-agent needs (e.g.
"verify iBGP" but no loopback IPs given), the sub-agent **does NOT
query the DB itself**. It returns:

```yaml
status: insufficient_input
needs:
  - "loopback IPs for R1 and R3"
  - "OSPF area covering both devices"
suggested_next: 'task("analyzer", "investigate R1+R3 loopbacks and OSPF coverage")'
```

The orchestrator (main router) sees this and re-dispatches to
analyzer with the specific gap. Analyzer fills it (it has SQL +
inspectors), produces a supplementary Markdown, and resubmits to
the original sub-agent. **This keeps each sub-agent focused on its
core competency.**

### Principle 5 — `collect → plan(L1-L4) → act + reflect → emit`
Both sub-agents use the same plan-act-reflect loop, instantiated for
their concern:

| Phase | Sim | Lab |
|---|---|---|
| Phase 0 COLLECT | parse user-provided Markdown (change plan / fault hypothesis); pull RAG context for relevant vendors/protocols | parse Markdown; pull RAG for SR Linux translations |
| Phase 0a SCHEMA | identify which RFC / vendor docs apply to this change | identify which lab platform (SRL vs vrnetlab) per device |
| Phase 1 PLAN | per-layer logical checks (L1: interface presence; L2: VLAN/STP; L3: subnet/IGP; L4: BGP/ACL); skip layers untouched | per-layer execution stages: translate → push → observe → reflect |
| Phase 2 ACT | check each logical assertion in order | for each layer: translate prod CLI → push to lab → run that layer's post_checks → reflect |
| Phase 3 REFLECT | between layers: does L<n> verdict open or close issues for L<n+1>? | between layers: did the last layer fail? if so, diagnose before continuing or aborting |
| Phase 4 SYNTHESISE | combine per-layer verdicts into overall "logically valid / blockers / questionable" | combine per-layer pass/fail into overall lab verdict + diagnosis |
| Phase 5 EMIT | `format_and_export(subdir="sim_reports")` Markdown | `format_and_export(subdir="lab_reports")` Markdown |

## 2. Sim sub-agent (Batfish-backed config evaluator)

**Revised 2026-05-14**: the original design (LLM + RAG-only reasoning
over user-provided input) was replaced by a **Batfish-backed**
design.  Reasoning:

- LLM-only reasoning is heuristic; it misses corner cases that
  Batfish's formal evaluation catches (recursive route resolution,
  AS-PATH semantics, ACL conjunction effects, multipath ECMP).
- A Batfish service is already deployed at `192.168.100.12:9996-9997`.
- OLAV already has `olav-netops/src/olav_netops/export/batfish.py`
  (R74) that exports snapshot configs to Batfish-compatible layout
  — zero extra collection cost.

### 2.1 Tool list (2 total)

```yaml
name: sim
agent_type: api
thinking_mode: enabled
tools:
  - batfish_q          # generic Batfish question runner.  RAG guide enumerates
                        # the top-10 question names + arg schemas.
                        # Internal: lazy-init snapshot from netops + run bf.q.<name>(...).answer()
                        # Supports differential queries via optional reference_snapshot arg.
  - format_and_export   # emit Markdown report
```

**Why 2 tools** is enough: Batfish is the data backend; agent picks a
question + args.  RAG guide (`sim/guides/batfish_question_catalog.guide.yaml`)
documents the top-10 questions (bgpSessionStatus, bgpSessionCompatibility,
ospfSessionCompatibility, reachability, traceroute, routes, differentialReachability,
testRoutePolicy, searchFilters, definedStructures) with arg schemas.

**Why no SQL / no recall_memory direct tool**: Batfish already parses
the configs into a queryable model.  Metadata sim needs (snapshot_id,
scope) is passed in by orchestrator dispatch prompt or by the analyzer
when sim is invoked via cross-domain delegation (§2.6).

### 2.2 Workflow F — CAB pre-flight validation

User input: scope + change description (typically delegated by analyzer).

```
Phase 0: parse scope (devices, snapshot_id) from invocation prompt
Phase 1 PLAN:
  per-layer assertions backed by Batfish questions:
    L4 BGP same/diff ASN intent? → bgpSessionStatus + bgpSessionCompatibility
    L3 IGP carrying loopback? → routes(network=<loopback>/32)
    L3 reachability post-change? → reachability(srcIps, dstIps)
    L4 policy correctness? → testRoutePolicy
Phase 2 ACT:
  batfish_q each assertion; collect rows
Phase 3 REFLECT: per-assertion PASS/FAIL/INDETERMINATE
Phase 5 EMIT: sim_reports/<topic>_sim.md
```

### 2.3 Workflow G — Control-plane fault analysis

User input: "Why is OSPF R1-R3 stuck in Init?" (typically delegated).

```
Phase 0: parse symptom + scope
Phase 1 PLAN:
  Stage 1: batfish_q(question="ospfSessionCompatibility", nodes="R1|R3")
           → returns interface-pair compatibility (AREA_MISMATCH, MTU_MISMATCH, ...)
  Stage 2: if INCOMPATIBLE → identify which field
           if COMPATIBLE → config says ok but reality says Init → 
             likely L1/L2 (delegated to analyzer for state confirmation)
Phase 5 EMIT: sim_reports/<topic>_fault.md
```

### 2.4 Workflow H — Differential reachability (what-if)

User input: "If I push this change, will R1 still reach R4?"

```
Phase 0: parse change CLI + scope
Phase 0a: (typically: lab Twin Builder has the candidate snapshot;
          for sim-only what-if, analyzer provides the candidate via
          delegation envelope)
Phase 1 PLAN:
  reference snapshot = current snap
  candidate snapshot = current + change applied (Batfish supports this)
Phase 2 ACT:
  batfish_q(question="differentialReachability",
            snapshot_name=candidate, reference_snapshot=baseline)
  → returns prefixes whose reachability changed between snapshots
Phase 5 EMIT: sim_reports/<change>_reachability.md
```

For real-world experimental verification, hand off to lab (dev_docs/74).

### 2.5-aside — Why Batfish ≠ Lab (clarifying)

| | Sim (Batfish) | Lab (clab Twin Builder + Runner) |
|---|---|---|
| Asserts | Config-layer determinism ("according to your configs, X reaches Y") | Behavioural truth ("when you push and wait, BGP comes Established") |
| Speed | <1s per query after snapshot init | Minutes (clab boot + push + observe) |
| Faithful to vendor quirks | High (Batfish has vendor parsers) | Medium (SRL approximation) |
| Cost | CPU + Batfish service | CPU + 256MB×N RAM + clab |
| Use when | "Will this work logically?" / what-if / policy | "Will the push actually succeed?" / real timing |

**Added 2026-05-14**.  Owns the third data substrate: raw text
streams.  Replaces the current `investigate` sub-agent + claws back

### 2.5.1 Tool list (3 total)

```yaml
name: investigator
agent_type: api

```

## 2.6 Cross-domain synthesis pattern — analyzer-lead

A real investigation often needs all three substrates:
- "Why is iBGP R1-R3 down today?" needs SQL state + Batfish config
  check + syslog timeline.

Three architectural options were considered (orchestrator synthesises
/ analyzer leads / dedicated reporter sub-agent / per-section files
stitched).  **The chosen pattern is analyzer-lead with explicit
delegation**.

### 2.6.1 Principle

When the prompt is a multi-substrate investigation, the orchestrator
routes to `analyzer`.  Analyzer is the report author: it does its
own SQL work, and when its plan-act-reflect loop identifies a need
for config-evaluation or text-search evidence, it delegates via
`task("sim", ...)` or `task("investigator", ...)`.  The delegated
sub-agent returns a Markdown chunk that analyzer cites in its final
synthesised report.

### 2.6.2 Implementation via deepagents native `task()` tool

deepagents `SubAgentMiddleware` (in
`deepagents/middleware/subagents.py:_build_task_tool`) natively
provides a `task(description, subagent_type)` tool to any agent
that declares its own `subagents:` list.  The middleware:

- Returns the sub-agent's **final message text** directly as the
  tool result (no separate `read_subagent_output` wrapper needed).
- Supports parallel dispatch (TASK_TOOL_DESCRIPTION explicitly
  encourages launching multiple concurrent subagents in one message).
- Is stateless per call (each subagent invocation gets a fresh
  state; only the description prompt is passed).

**Current OLAV wiring** (`src/olav/agents/agent.py:620`): only the
**top-level** `create_deep_agent(...)` call gets SubAgentMiddleware
+ `subagents=[...]`.  Sub-agents themselves are built via
`create_agent(...)` (line 1033) and therefore do **NOT** receive
the `task` tool today.

**Required code change** (~15 lines in `agent.py`): when a sub-agent
declares its own `subagents:` list in SKILL.md, build it via
`create_deep_agent` instead of `create_agent`.  Recursive deep-agents
are supported by deepagents — no framework patching needed.

```python
# agent.py:_build_subagents (sketch)
sa_subagents_paths = sa_config.get("subagents", [])
if sa_subagents_paths:
    # This sub-agent itself has children → recursive deep_agent
    sa_children = self._build_subagents_recursive(sa_subagents_paths, sa_llm)
    runnable = create_deep_agent(
        model=sa_llm, system_prompt=prompt, tools=tools,
        subagents=sa_children, middleware=_middleware, name=name,
    )
else:
    # Leaf agent (current behaviour)
    runnable = create_agent(
        sa_llm, system_prompt=prompt, tools=tools,
        middleware=_middleware, name=name,
    )
```

### 2.6.3 Analyzer SKILL.md (updated, 4 explicit tools + auto task())

```yaml
name: analyzer
# drop "agent_type: api" — analyzer needs TodoListMiddleware for the
# planning-and-delegation workflow; SubAgentMiddleware adds task() auto
thinking_mode: enabled
subagents:                       # ← NEW: declares peers analyzer may delegate to
  - path: ../sim/SKILL.md
  - path: ../investigator/SKILL.md
tools:
  - execute_sql                  # own SQL on netops.* (analyzer's core substrate)
  - describe_table               # schema introspection
  - format_and_export            # final Markdown report
  # NOTE: `task` is auto-injected by SubAgentMiddleware because
  # `subagents:` is non-empty.  Don't list it explicitly.
```

Tools **removed from analyzer** (moved to investigator):
- `query_evidence`        → now investigator's
- `inspect_drift_configs` → now investigator's

Net analyzer surface: **3 explicit tools + 1 auto `task` = 4 tools
visible to LLM**.  Cleaner than the prior 5-tool design (which was
mixing substrates).

### 2.6.4 Analyzer Workflow D — extended with Phase 2.5

```
Phase 0  COLLECT_BROAD       (own execute_sql)
Phase 0a SCHEMA              (own describe_table + cheat-sheet)
Phase 1  PLAN (L1-L4)        (decide which substrates needed for THIS investigation)
Phase 2  ACT — SQL stage     (own execute_sql per stage)
Phase 2.5 DELEGATION         (NEW)
  if scope touches config-evaluation:
    sim_md = task("sim", "<specific question>; snapshot_id=<id>")
  if scope touches logs / events / config drift:
    log_md = task("investigator", "<specific search>; device=<X>")
  read returned markdown chunks
Phase 3  REFLECT — multi-source
Phase 4  SYNTHESISE — cross-source anomalies (cross-layer + cross-substrate)
Phase 5  EMIT — single markdown citing all sources
```

### 2.6.5 Hard rule — no recursive delegation

Sim and investigator **MUST NOT** call `task("analyzer", ...)` back.
They are leaves; analyzer is the only delegator.

Enforcement (physical, not just convention):
- sim and investigator do NOT declare `subagents:` in their SKILL.md
  → `agent.py` builds them via `create_agent` (not `create_deep_agent`)
  → SubAgentMiddleware never instantiated for them
  → `task` tool physically absent from their tool list
  → recursion impossible at the framework level.

### 2.6.6 Sub-agent output contract

Sim and investigator return **Markdown chunks**, not JSON, so analyzer
can cite verbatim:

```markdown
# Final Report (analyzer-written)

## SQL Findings (this agent)
…

## Config-layer Findings (delegated to sim)
> Returned by sim, snapshot snap_X, batfish_q questions used: …
…

## Event Findings (delegated to investigator)
> Returned by investigator, source=syslog, time_range=7d
…

## Cross-source Synthesis (this agent's reasoning)
SQL says BGP Established 0 prefixes; sim says config compatible;
investigator says no syslog flap → **Root cause: route-map RM-IN
filtering all prefixes from neighbor 1.1.1.1**.
```

### 2.6.7 When NOT to delegate

If user prompt is a single-substrate query ("show R3 BGP state",
"diff R3 config between snap_42 and snap_47", "what-if reachability"),
the orchestrator routes directly to the matching sub-agent.  Analyzer
delegation is for genuine multi-substrate synthesis.

## 3. Lab redesign — see dev_docs/74

The original §3 design (lab as a single LLM sub-agent that translates
+ deploys + pushes + observes in one workflow) was **superseded
2026-05-14**.  Reasoning:

- Translation is slow and error-prone but **cacheable**; doing it
  inside every experiment wastes minutes and risks new translation
  errors per run.
- The change must run against a **base config**, not an empty SRL
  container.  Building that base belongs in a different lifecycle
  than running experiments.
- Vendor-faithful images are also not a clean answer (interface
  mismatch / missing features / limited vendor coverage / heavy RAM).

**Current lab design**: dev_docs/74 — `lab` becomes a top-level agent
with two sub-agents:
- **Twin Builder** (slow / batch / cacheable): snapshot config →
  SRL-translated digital twin artifacts on disk.
- **Experiment Runner** (fast / on-demand): loads a twin → deploys →
  pushes change delta → observes → emits lab report.

See dev_docs/74 for the full design.  This section is intentionally
short so the original wrong design isn't perpetuated.

## 4. RAG-only translation (no regex)

### 4.1 The principle

`postcheck_translate._PROD_TO_SRL_RULES` (50+ regex) is replaced by
a curated knowledge guide loaded into LanceDB memory. Lab agent does:

```python
hits = recall_memory("srl translate show ip bgp summary")
# RAG returns the relevant chunk of the SRL CLI reference guide.
# LLM reads it and writes:  show network-instance default protocols bgp neighbor
```

When the user adds support for a new vendor (Arista EOS, Palo Alto),
they add a `<vendor>_to_srl_translation.guide.yaml` in
`workspace/lab/guides/`, re-prime KB, and translation works
immediately. **No Python code change.**

### 4.2 SR Linux CLI reference (initial corpus)

Drawn from Nokia official documentation
(https://documentation.nokia.com/srlinux/) and learn.srlinux.dev:

#### Config-mode entry / commit (vs Cisco/Junos)

| Source | SR Linux |
|---|---|
| Cisco `configure terminal` ... `end` ... `write memory` | `enter candidate` ... `commit save` |
| Junos `configure` ... `commit and-quit` | `enter candidate` ... `commit save` |

#### Show command mapping

| Concept | Cisco IOS | Junos | SR Linux |
|---|---|---|---|
| BGP summary | `show ip bgp summary` | `show bgp summary` | `show network-instance default protocols bgp neighbor` |
| BGP neighbor detail | `show ip bgp neighbors X` | `show bgp neighbor X` | `show network-instance default protocols bgp neighbor X` |
| OSPF neighbors | `show ip ospf neighbor` | `show ospf neighbor` | `show network-instance default protocols ospf neighbor` |
| Routing table | `show ip route` | `show route` | `show network-instance default route-table ipv4-unicast` |
| Specific prefix | `show ip route X.X.X.X/Y` | `show route X.X.X.X/Y` | `show network-instance default route-table ipv4-unicast prefix X.X.X.X/Y` |
| Interfaces brief | `show ip interface brief` | `show interfaces terse` | `show interface` |
| Interface detail | `show interfaces X` | `show interfaces X detail` | `show interface ethernet-1/X` |
| ARP table | `show arp` | `show arp` | `show network-instance default protocols arp ipv4 neighbor` |
| LLDP neighbors | `show lldp neighbors` | `show lldp neighbors` | `show system lldp neighbor` |

#### Config command mapping (BGP example)

| Concept | Cisco IOS | SR Linux |
|---|---|---|
| Declare BGP process | `router bgp <as>` | `set / network-instance default protocols bgp autonomous-system <as>` |
| Set router-id | `bgp router-id X.X.X.X` | `set / network-instance default protocols bgp router-id X.X.X.X` |
| Add neighbor | `neighbor X remote-as Y` | `set / network-instance default protocols bgp neighbor X peer-as Y` |
| update-source loopback | `neighbor X update-source LoopbackN` | `set / network-instance default protocols bgp neighbor X transport local-address X.X.X.X` |
| Activate session | (implicit) | `set / network-instance default protocols bgp admin-state enable` + per-neighbor `admin-state enable` |

#### Config command mapping (interface IP example)

| Concept | Cisco IOS | SR Linux |
|---|---|---|
| Interface IP | `interface X` / `ip address X.X.X.X Y.Y.Y.Y` | `set / interface ethernet-1/N subinterface 0 ipv4 address X.X.X.X/prefix` |
| Enable | `no shutdown` | `set / interface ethernet-1/N admin-state enable` + per-subinterface |
| Add to default network instance | (implicit) | `set / network-instance default interface ethernet-1/N.0` |

#### Output formatting

SR Linux supports `| as json`, `| as yaml`, `| as table`, `| more`.

For `expected_pattern` matching in post_checks: SR Linux output is
YANG-tree-styled — fields like `state: established` line up vertically
on their own row. Patterns should match the value verbatim
(`"established"` not `"Established"` — SR Linux uses lowercase by
default unlike Cisco).

### 4.3 Guide format

`olav-netops/.olav/workspace/netops/lab/guides/srl_cli_translation.guide.yaml`
(new file, chunked by concept for retrieval granularity).

The guide above gets split into ~8 chunks (config-mode, bgp, ospf,
route, interface, arp, lldp, output-format) each ~500-1000 chars so
RAG can return just the relevant chunk.

### 4.4 Failure mode

If LLM doesn't find a translation in RAG (e.g. obscure Cisco command
not yet documented), `device_push_config` should accept the
un-translated command **literally**. SR Linux either accepts it (some
Cisco/Junos-isms are silently supported) or errors out. The error
goes into `device_push_config` return + lab agent reflects on it.

This is **safer than regex** which silently passes wrong translations.

## 5. Multi-purpose use cases (not just CAB)

The 3 + 1 architecture (analyzer / sim / investigator + lab) handles
**five** patterns of network operator request:

| Pattern | First-line sub-agent | Cross-domain delegation? |
|---|---|---|
| **Simple state Q&A** ("show R3 BGP state") | analyzer (SQL only) | No |
| **CAB pre-validation** ("can I push this?") | analyzer → sim (Batfish bgpSessionStatus / reachability) | Yes |
| **Fault analysis** ("why is X stuck?") | analyzer → sim (config feasibility) + investigator (event timeline) | Yes |
| **Control-plane / data-plane reachability** | sim (Batfish) | Direct |
| **Experimental verification** ("does it actually work in lab?") | lab (dev_docs/74 Twin + Runner) | Direct |
| **Event / log timeline** ("what happened on R3 last week?") | investigator | Direct |
| **Config drift between snapshots** | investigator (inspect_drift_configs) | Direct |

Orchestrator routing table excerpt:

```
| Intent | First call |
|---|---|
| "show / current state / inventory" (single substrate) | task("analyzer", ...) |
| "investigate / audit / comprehensive report" (multi-substrate) | task("analyzer", ...) — analyzer delegates from there |
| "why down / fault analysis"                             | task("analyzer", ...) — delegates to sim + investigator |
| "can A reach B (logical) / what-if / pre-flight"        | task("sim", ...) |
| "show events / syslog / log search / config drift"      | task("investigator", ...) |
| "push to lab / experimental verify / reproduce in lab"  | task("lab", ...) — see dev_docs/74 |
```

## 6. Implementation plan

### Phase 1 — analyzer side (prereq, ~1h)

Modify analyzer `system.md` Workflow A Phase 6 EMIT template:

1. Add `## Topology Context` section listing topology_links rows for in-scope devices.
2. Tag verification table rows by layer (L1/L2/L3/L4).
3. Tag implementation CLI per-device blocks by layer (CLI lines preceded by `# L<n>`).

(Analyzer does **not** emit a clab YAML block — that is the lab
Twin Builder's job per dev_docs/74.)

This makes the Markdown the **single source of truth** for both sim
and the lab Experiment Runner. No further data layer needed.

### Phase 2 — RAG corpus (~2h, scope shrunk per Batfish pivot)

- `sim/guides/batfish_question_catalog.guide.yaml` — top-10 Batfish
  questions (`bgpSessionStatus`, `reachability`, `routes`,

## 8. Open questions

1. **lab_subnet allocation owner**: Today sim has `lab_subnet_pool`.
   After refactor, lab owns lab allocation. But analyzer's Markdown
   change plan suggests CLI using prod IPs — does lab translate
   prod_ip → lab_ip on the fly, or does analyzer pre-allocate? Pre-allocate
   simpler; on-the-fly more flexible.

2. **Sim Markdown report shape**: Should sim emit a full Markdown
   audit-style report (like analyzer's Workflow D), or a compact
   verdict-style envelope (`PASS / BLOCKED with blockers list /
   QUESTIONABLE with concerns list`)? Probably both: short verdict
   header + detailed Markdown body.

3. **Differential lab**: Should lab support "compare prod baseline vs
   candidate" mode out of the box, or only single-snapshot run? The
   `inspect_drift_configs` capability already exists in analyzer for
   config drift; lab differential adds runtime behavior comparison.

4. **`request_analyzer_help` as @tool vs convention**: The structured
   envelope `{status: insufficient_input, needs: [...]}` could be
   returned via `format_and_export(..., subdir="needs_analyzer")`
   and the orchestrator polls — or a dedicated `@tool` that posts
   the request explicitly. Tool is cleaner; convention is lighter.

5. **What's the difference between sim's `describe_concept` and
   `recall_memory`?** `recall_memory` is generic LanceDB search;
   `describe_concept` could be a tighter wrapper that only hits
   `category=design_rules` guides. May not be worth the second tool.

6. **Should sim ever call lab directly?** Some validations require
   experimental confirmation (e.g. "OSPF MTU mismatch suspected ↔
   reproduce in lab"). Today the user picks. Could sim escalate
   automatically when its confidence is "questionable".
