# R-AGENT-HIERARCHY — Workspace consolidation + responsibility split

**Status:** Phase A SHIPPED (`ad99eee`); Phase B+C SHIPPED (`0bad5c3`); Phase D SHIPPED + **gemma4:31b nothink in-vivo PASS** (`fd130e4` + `4f84fb5`); Phase E (audit Designer) and Phase F (schema-in-config framework) deferred. R100 local-small-model end-to-end milestone hit on the CAB workflow.
**Author:** OLAV Team (J. Chen).
**Trigger:** Three failed CAB-emission experiments on gemma4:31b nothink
(2026-05-09) revealed the LLM was carrying multi-responsibility agent
contexts (`ops/analyze` does TCF emission + routing analysis + simulation
+ topology viz + drift) plus orchestrator route bloat (16-line schema
cheatsheet in `prompts/orchestrator.md`).  Compounded by post-2026-05-01
top-level workspace scattering (`devops_scripts`, `devops_infra`,
`netops_topology`, `netops_learner` were spun out because pre-Patch D'
their tool registrations bloated the parent orchestrator's prompt).

**Enabling work:** Patch D' Steps 1–5 (2026-05-08) decoupled tool
**implementation sharing** from **registration scope** — sub-agents now
declare their own tools list explicitly, and a sub-agent's tools no
longer leak into the parent orchestrator's prompt.  This removes the
2026-05-01 reason to keep `devops_*` / `netops_*` agents at top level.

## TL;DR

Consolidate 7 scattered top-level agents → **3 user-facing
orchestrators** (`audit`, `devops`, `netops`), each with focused
sub-agents.  Split `ops/analyze` into `analyser` (read-side: BGP /
drift / topology investigations) and `sim` (write-side: change
planning, what-if).  Decouple CAB workflow: sim outputs prose change
plan; a deterministic Python `tcf_writer` renders the TCF YAML — LLM
no longer composes TCF directly.

## Rationale — why now

| Driver | Pre-Patch D' status | Post-Patch D' status |
|---|---|---|
| Sub-agent tools polluted orchestrator prompt | Yes (so we spun things out 2026-05-01) | No (registration scope isolated; `format_and_export` lives in `core/tools/` but only declared in writer + analyze + lab) |
| Memory recall → wrong sub-agent | Yes (multiple agents claim "TCF / change plan") | Improved by Patch C2 keyword boost; further reducible by domain prefix |

| Orchestrator prompt bloat | Yes (101-line `ops/prompts/orchestrator.md`) | **Still yes** — fix is content cleanup |

The architectural dividend from Patch D' is the freedom to consolidate
and re-split based on **responsibility**, not **token budget**.  This
refactor cashes that dividend.

## Phase B — Split `ops/analyze` → `analyser` + `sim` (½ work unit)

**Goal:** separate read-side analysis from write-side change planning.

Today's `analyze` SKILL.md description (verbatim):

> "TCF emission (emit_tcf) for change plans / CAB. Routing analysis.
> Deterministic simulation. Topology viz. Snapshot drift."

This is **5 distinct responsibilities** packed into one sub-agent.
The 2026-05-09 CAB experiments showed gemma4:31b nothink can't reliably
hold all five contexts simultaneously — it makes wrong tool picks
(format_and_export instead of emit_tcf), wrong arg shapes (hallucinated
ASNs), or fails to converge (18-min investigation loop).

Split into:

**`netops/analyser`** — read-side
  - Routing analysis (BGP attribute investigation, AS_PATH walks)
  - Snapshot drift detection (`diff_*` primitives)
  - Topology Q&A (Mermaid diagram, blast-radius reachability)
  - Tools: `run_python_simulation` (read-only DuckDB), `format_and_export`

**`netops/sim`** — write-side
  - What-if simulation (sim.clone + mutate + observe)
  - Change planning (output: PROSE change plan; **NO emit_tcf**)
  - Tools: `run_python_simulation` (read + simulate), `format_and_export`
  - SKILL.md prompt explicitly forbids producing structured TCF;
    the agent's deliverable is a `## Change Plan` Markdown document.

Both share the unified sandbox (R102), so prompt-side they're nearly
identical except for purpose framing.  The split's value is in
**memory routing**: the recall guides for "drift detection" route
to analyser, "change plan" routes to sim.  No more cross-context
contamination.

Verification gate B:
- Memory recall for "add eBGP between R1 and R3" → returns sim's
  guide top-1 (currently `change_plan_emit_tcf`).
- Memory recall for "diff snapshots t1 vs t2" → returns analyser's
  guide.
- Both sub-agents start with `run_python_simulation` (no skill picks
  emit_tcf yet — that step is Phase C).

## Phase C — Decouple CAB: prose plan → deterministic TCF writer (1.5 work units)

**Goal:** remove TCF schema burden from the LLM entirely.  The LLM
outputs prose; deterministic Python composes TCF.

**Components:**

1. **`src/olav/core/cab/tcf_writer.py`** (NEW)
   ```
   render_tcf_from_change_plan(plan_text: str) -> dict
   ```
   - Parses the `## Change Summary` block at end of prose plan
     (intent, devices, optional fields).
   - Calls existing `_db_facts(...)` (move from today's emit_tcf
     plumbing) to ground ASN / loopback / platform from DB.
   - Renders implementation + rollback CLI from per-intent +
     per-platform templates (ebgp_direct → Junos / IOS templates).
   - Calls existing `tcf_emit_from_sim(...)` to produce the YAML.
   - Returns `{spec_path, facts, warnings}` envelope.
   - Pure Python; **no LLM call**.

2. **`render_tcf` skill-script** (NEW, for sim agent)
   - One-line wrapper: read plan_path → call tcf_writer → write
     spec.tcf.yaml.
   - sim agent's only TCF-producing call:
     `execute_skill_script("render_tcf.py", script_args={...})`.

3. **sim's SKILL.md prompt change**
   - Add: "Your deliverable is a Markdown change plan ending with a
     `## Change Summary` YAML block.  Do NOT call any TCF emitter
     yourself."
   - Remove emit_tcf from sim's tools list.

4. **HITL hook**
   - Orchestrator pauses after sim returns prose plan, asks user
     for approval, only then calls `render_tcf` skill-script.
   - User reviews **prose** (human-friendly), not YAML.

5. **`change_plan.guide.yaml`** — rewrite to teach sim how to write
   the `## Change Summary` block, not how to call emit_tcf.

Verification gate C:
- gemma4:31b nothink → `netops/sim` for `r1-r3-ebgp` request
  produces a parseable prose plan with grounded facts (R1, R3 both
  AS 65000 → eBGP feasibility blocker explicitly stated, NOT
  hallucinated as 65001/65003).
- HITL: user sees prose, approves, render_tcf produces valid TCF
  YAML that ops-lab consumes successfully (verdict=PASS or explicit
  feasibility-block reason).
- ISSUE-CAB-DATA-NOT-GROUNDED closed.

## Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Memory recall keys break post-rename (e.g. `ops` → `netops`) | High | Phase A includes `kb import-guides` reprime + verification step on top-3 memory queries per agent |
| `olav --agent <name>` CLI usage breaks for users | Medium | Maintain old prefixed names as aliases in the CLI router for one release |
| sim's prose `## Change Summary` block format drifts (LLM creativity) | Medium | tcf_writer parser fails fast with clear error → sim retries; also test with both DeepSeek and gemma4 |
| Phase B introduces guide collision (analyser + sim both claim "what-if") | Low | analyser's "what-if" is post-hoc analysis; sim's is forward-looking. Split keywords explicitly in `ops_*.guide.yaml` |
| Splitting `audit/auditor` regresses today's working 2-call audit run | Low | Keep run-path fully in `auditor/` (no behaviour change there); only move profile-write tools into `designer/` |

## Rollback

Each phase is reversible by `git revert` at file-move granularity:
- Phase A reverts the workspace moves; `olav refresh` rebuilds.
- Phase B reverts `sim/` directory creation; analyse stays merged.
- Phase C reverts tcf_writer.py creation; sim falls back to direct
  emit_tcf (today's path).

No data migration required — memory entries are keyed by
`guide_<agent>_<intent>`; the `import-guides` step at end of each
phase re-keys them to the new names.

## Phase D — Structured-output refactor (`submit_change_plan` tool)

**Trigger (2026-05-09 user feedback):** Phase B+C still has TCF
format leakage in sim's prompt — the `## Change Summary` YAML
block requirement makes the LLM aware of TCF schema field names
(`intent_type`, `devices`, `feasibility`).  Plus the YAML block
is a "gentleman's agreement": the LLM may forget the block, mis-
indent, or get field names wrong, breaking the parser.

**Insight:** LLMs natively support **JSON-schema-constrained
output** via tool-calling.  LangChain's `@tool` decorator
introspects function signatures + Pydantic models to build a
JSON schema in the tool definition; the LLM is grammar-
constrained at decode time when filling tool args.  Using this
channel for sim's deliverable replaces the brittle Markdown+YAML
gentleman's agreement with hard schema enforcement.

**Why not "thin emit_tcf" again?** That earlier 2026-05-09
experiment failed because the agent had nowhere to put its
analytical work — 4 args + no free-form output → 18-min
investigation loop.  Phase D adds free-form prose **inside**
the tool args (`rationale: str`, `steps: str`), giving the LLM
a container for its reasoning that ends naturally with the
tool call.

### Design

Replace the `## Change Summary YAML block` + `render_tcf`
skill-script pattern with a single `submit_change_plan` @tool:

```python
@tool
def submit_change_plan(
    intent: Literal["ebgp_direct", "ibgp_direct", "vlan_add"],
    devices: list[str],            # required, len 1-4
    summary: str,                  # one-line title
    rationale: str = "",           # FREE-FORM markdown prose
    steps: str = "",               # FREE-FORM markdown prose
    feasibility: Literal["OK", "BLOCKED"] = "OK",
    feasibility_reason: str = "",
) -> dict:
    """Submit your change plan.  rationale + steps are free-form
    Markdown — write your analysis there.  Schema fields drive
    deterministic TCF rendering.
    """
    # 1. Save prose plan to exports/change_plans/<change_id>.md
    # 2. Internally call render_tcf_from_change_plan with structured args
    # 3. Return {plan_md_path, spec_path, facts, warnings}
```

**Constrained metadata** (intent enum, devices list, feasibility
enum) + **free-form prose** (rationale, steps) = two-channel
output where each channel uses the LLM's strength.

### Files

* `olav-netops/.olav/workspace/netops/sim/tools/submit_change_plan.py`
  (NEW, ~80 LOC) — wraps `render_tcf_from_change_plan` with
  structured args.  Saves prose to `exports/change_plans/`.
* `sim/SKILL.md` — replace `execute_skill_script` in tools list
  with `submit_change_plan`.  Drop YAML block requirement from
  the prompt.
* `sim/prompts/system.md` — workflow becomes "investigate →
  call submit_change_plan(...) with prose in rationale/steps".
* `sim/scripts/render_tcf.py` — DELETE (subsumed by tool).
* `change_plan.guide.yaml` — rewrite for tool-call workflow.

### Verification gate D

* `submit_change_plan` tool exposed; LangChain JSON-schema test
  shows enum + types correctly inferred.
* gemma4:31b nothink E2E: change-plan request reaches a tool
  call (not stuck in investigation) and produces a TCF YAML.
* Same DB-grounding behaviour as Phase B+C (R1+R3 same-AS
  → BLOCKED with grounded reason).

## Phase E — Audit subsystem reuses Phase D pattern

**Same problem class** in audit/auditor (Designer mode):

The auditor agent currently authors profile YAML files by hand
(via `save_profile`, `append_jobs` tools).  Profiles have a
strict frontmatter schema:

```yaml
---
name: <profile_name>
version: '4.0'
jobs:
  - name: <unique_id>
    type: sql | anomaly | incident | baseline
    severity: Critical | Warning | Info
    section_prompt: <markdown prompt>
    query: <multi-line SQL>
---
```

Small models struggle with multi-line YAML composition (same
class of problem as TCF emit args).  Symptoms: bad indentation,
wrong field names, missing required keys.

### Phase E design

Replace the "write YAML by hand + call save_profile" pattern
with a structured tool:

```python
@tool
def append_audit_job(
    profile_name: str,           # which profile to extend
    job_name: str,
    job_type: Literal["sql", "anomaly", "incident", "baseline"],
    severity: Literal["Critical", "Warning", "Info"],
    sql_query: str,              # multi-line OK; LLM strength is prose
    section_prompt: str,         # FREE-FORM markdown
    threshold_condition: str = "",
) -> dict:
    """Append a Job to a profile.  Returns {profile_path, job_count}."""
```

And for new profiles:

```python
@tool
def submit_profile_draft(
    name: str,
    version: str = "4.0",
    jobs: list[dict],            # list of Job models
    correlation_pass_prompt: str = "",  # Markdown body
) -> dict:
    """Create a new profile YAML from structured Job specs."""
```

The `jobs: list[dict]` arg uses Pydantic nested model — each
Job has its own schema with severity enum, type enum, etc.
LangChain handles this nesting correctly in the tool definition.

### Phase E scope

Tracked separately as **R-AUDIT-STRUCTURED-OUTPUT** in
`02. todo.md`.  Defer until Phase D ships and is validated;
re-evaluate based on small-model audit Designer test results.

### Phase E NON-targets

* **Run mode** (map_engine + render_report) is already
  deterministic; no LLM-authored args.  No change.
* **Curator schema discovery** is already deterministic.  No change.
* **Curator trace analysis** outputs are naturally prose;
  schema constraints offer little benefit.  Defer indefinitely.

## Phase F — Schema-in-config framework (post-validation refinement)

**Trigger** (2026-05-09): Phase D nothink E2E PASS proved the
structured-output approach works.  Next limitation: the schema
(intent enum, devices arity) is **hardcoded in Python** via
`Literal[...]` type hints + `_INTENT_RENDERERS` dict.  Adding a
new intent type (e.g. `static_route_add`) requires:
1. Edit Python tool signature + Literal enum
2. Edit `tcf_writer._INTENT_RENDERERS`
3. Write new `_render_<intent>` function
4. `uv build` + `pip install --force-reinstall` + `olav skill install`

This violates the dev_docs/94 business model goal: **"users
inject their own experience"**.  Users adding new change types
should not need to rebuild wheels.

### Phase F design — schema YAML + intent handlers

```
olav-netops/.olav/workspace/netops/sim/
├── SKILL.md                         (references schemas dir)
├── schemas/
│   └── change_plan.schema.yaml      (declares args, enums, dispatch)
├── handlers/
│   ├── ebgp_direct.py               (one per intent)
│   ├── ibgp_direct.py
│   └── vlan_add.py
└── prompts/system.md
```

`change_plan.schema.yaml`:
```yaml
name: submit_change_plan
description: "Submit your change plan ..."
args:
  intent:
    type: enum
    values: [ebgp_direct, ibgp_direct, vlan_add]
    required: true
  devices:
    type: list
    items: string
    min: 1
    max: 4
  summary: { type: string, required: true }
  rationale: { type: string, multiline: true }
  steps: { type: string, multiline: true }
  feasibility:
    type: enum
    values: [OK, BLOCKED]
    default: OK
  feasibility_reason: { type: string }
dispatch:
  field: intent
  handler_dir: ../handlers
  output:
    plan_md_dir: exports/change_plans
    spec_yaml_dir: exports/cab
```

Each handler defines:
```python
# handlers/ebgp_direct.py
def render(args: dict, db_facts: dict, lab_subnet: str) -> dict:
    """Build TCF blocks for ebgp_direct intent. Returns
    {implementation, rollback, post_check, tvt}."""
```

### Phase F runtime — `src/olav/core/skills/structured_output.py`

* Reads `<skill>/schemas/*.schema.yaml`
* Builds Pydantic model dynamically (`pydantic.create_model`)
* Wraps as a `langchain.tools.StructuredTool.from_function`
* Tool body: parse args → dispatch by `dispatch.field` →
  load `<handler_dir>/<value>.py` → call its `render()` → write
  artifacts → return envelope

Same framework reusable by:
- `audit/designer/schemas/audit_job.schema.yaml`
  + `audit/designer/handlers/{sql,anomaly,incident,baseline}.py`
- Any future skill needing structured-output deliverable

### Phase F adding-new-intent workflow (the user-facing benefit)

Old (hardcoded):
1. Edit `submit_change_plan.py` Literal enum
2. Edit `tcf_writer._INTENT_RENDERERS`
3. Write `_render_<new_intent>`
4. `uv build` + `pip install --force-reinstall`
5. `olav skill install`

New (schema-in-config):
1. Edit `change_plan.schema.yaml` enum values
2. Add `handlers/<new_intent>.py`
3. `olav skill install` (no wheel rebuild)

### Phase F NON-targets

* Multi-language renderer DSL — keep handlers Python (Python is
  the right tool for CLI generation; YAML/Jinja templates would
  add dependency without removing Python need).
* User-supplied schema validators — Pydantic dynamic generation
  + JSON-schema standard is enough; no custom DSL.

### Phase F verification gate

* New intent end-to-end (e.g. write `static_route_add` schema +
  handler, install via `olav skill install`, gemma4 nothink
  picks the new intent and writes valid TCF).
* All Phase D unit tests still pass under the new framework
  (backwards compat).

## Empirical lesson 2: original Markdown sim design hangs on small models (2026-05-09)

**Failed experiment**: reverted sim to the original
``ops-routing-simulator`` design (3b1a928 2026-03-01) — six-section
Markdown report from a NetworkX-based What-If sandbox, no
``submit_change_plan`` tool, no TCF in agent vocabulary.  Used the
new ``model.graph`` + ``model.facts`` helpers (also added this
session) to keep sandbox code minimal.

**Result**: gemma4:31b nothink hung at 12 min timeout.  Only 2
visible tool calls: ``task`` (orchestrator delegate) + ``write_todos``.

**Diagnosis**: the original design (commit 3b1a928 2026-03-01)

## Empirical lesson: sim sub-agent has value beyond routing (2026-05-09)

**Failed experiment**: removed sim sub-agent, moved
`submit_change_plan` tool to `analyze`.  Theory: with structured
output enforcing schema, the agent split is redundant.

**Result**: gemma4:31b nothink regressed.  Without sim:
* 11 `run_python_simulation` investigation calls
* 2 `write_todos` re-planning rounds
* `submit_change_plan` reached but tcf_writer dir missing
  (likely killed mid-render at 8min timeout)
* vs Phase D with sim: 2 tool calls, 5min, clean

**Diagnosis**: structured output (Pydantic schema enforced via
LangChain tool-calling channel) is necessary but not sufficient
for small models.  The sub-agent boundary provides an
additional contextual constraint:

| Constraint layer | What it does |
|---|---|
| Structured tool schema (Phase D) | LLM can't author free-form fields outside the enum/types |
| **Sub-agent boundary (sim)** | LLM has a NARROW tool list (3 tools) + a FOCUSED prompt ("ONE sandbox call max, then submit") |
| Deterministic Python (tcf_writer) | LLM-supplied facts ignored; DB grounding overrides |

Removing the middle layer makes analyze inherit BOTH
`run_python_simulation` AND `submit_change_plan` — the LLM
defaults to investigation mode (`run_python_simulation` is the
"more powerful" tool, attractive to a model with broad context).

**Conclusion**: sim is not redundant.  Its focused 3-tool list +
"submit-now" prompt are a behavioural lever the structured tool
channel alone does not replace.  Keep the split.

The wider principle: for small models, **narrow sub-agents
biased toward a single deliverable outperform broad agents
even with strong output schemas**.  Phase A's workspace
consolidation rule (3 user-facing orchestrators) and Phase B's
sim/analyze split are both expressions of this same insight at
different levels.

## Honest production-readiness assessment (2026-05-09)

After the inspector pattern shipped (`157fb5d`), the user asked:

> "Did sim use real data?  Real NetworkX computation?  Cover network
> scenarios?  Output usable?  Production-grade?"

### Real data: YES ✓

All 4 inspectors hit DuckDB via ``model.graph`` / ``model.facts``.
TCF YAML carries DB-grounded ``prod_asn`` / ``prod_loopback`` /
``platform`` per device.  ``tcf_writer`` queries
``netops.v_show_ip_bgp_summary_auto`` directly — LLM never authors
these fields.

### Real NetworkX: YES ✓ — but the agent can misuse it silently

``inspect_blast_radius`` runs ``nx.weakly_connected_components`` on
the live ``model.graph``.  Real computation.

**Silent failure observed in the gemma4 inspector E2E test (2026-05-09)**:
LLM called ``inspect_blast_radius(remove_links=[["R2", "R3"]])``.
But R2-R3 have no direct L2 link in the current topology — they
transit via R4.  ``g.remove_edge("R2", "R3")`` was a no-op; tool
returned "fully connected" (vacuously true).  LLM took this as
validation: *"Blast radius analysis confirmed network remains
fully connected"*.  The check was **theatrical** — it looked
analytical but proved nothing.

Production-grade fix: ``inspect_blast_radius`` must return a
``warnings`` field when ``remove_links`` references non-existent
edges, so the LLM can correct course.

## Cross-domain pattern (post-Phase D + E)

The **structured-tool-output for LLM-authored artifacts**
pattern applies anywhere the LLM today composes structured
text by hand:

| Domain | Today | After |
|---|---|---|
| CAB (sim) | Markdown + YAML block | `submit_change_plan` tool |
| Audit Designer | YAML profile + `save_profile` | `append_audit_job` / `submit_profile_draft` tool |
| Curator scaffolding | Already structured (no change) | n/a |
| Lab post_checks | Already in TCF schema (no change) | n/a |

Each instance: schema-constrained metadata + free-form prose
fields.  The pattern is a generalised application of ADR-0007
Python-first: deterministic Python handles structure;
free-form prose channels handle semantics.
