# 108. Presales Design Profile — Profile-First Architecture + Constraint-Driven Lifecycle

**Status:** design (2026-07-24). **Supersedes the generation model of** dev_docs/107
(§7 "LLM authors chapters") **with the audit-style profile-first pattern**; keeps
107's renderers, gates, decisions, constraints, and grounding. **Extends** dev_docs/98,
100, 104, 106, 107.

---

## 1. The reframe: profile-first, the document is a rendering (like audit)

OLAV's audit domain already proves the right pattern: **author a structured
`map profile`, approve it, then `render_report` renders the document
deterministically from it.** The document is a *view* of an approved, structured
spec — not something the LLM writes free-hand.

dev_docs/107 had the LLM author narrative chapters directly. That works (campus
N=3 → 3/3 after a step machine + gates) but is LLM-variable and needs machinery to
force completeness. The audit pattern is better and more OLAV-idiomatic:

> **The reviewable, approvable artifact is the `design profile` (structured). The
> HLD and LLD are deterministic renderings of the approved profile.**

Mapping:

| audit | presales (this doc) |
|---|---|
| `map profile` (structured analysis spec) | **`design profile`** (structured design spec) |
| human approves the profile | human approves the **profile** (not the prose) |
| `render_report` → report | **render** → HLD / LLD |

The LLM's job shifts from *"write 14 prose chapters"* to *"populate the profile"*
(extract constraints, record decisions with rationale, select devices, design the
topology) — small, structured, reliable tasks. Rendering is deterministic, so the
chapter-authoring variance disappears; editing the profile re-renders instantly;
the document is always faithful to what was approved.

## 2. The design profile has TWO dimensions — bone AND flesh

A complete HLD/LLD needs both **structure (骨/bone)** and **substance (肉/flesh)**.
The design profile captures both:

- **骨 — document architecture:** the sections, in order, AND *what each section
  must contain* (a structured content-element checklist, not just a title). This
  is the existing doc-structure profile, **upgraded from a one-line `scope` to a
  per-section content specification** (§4).
- **肉 — design content:** the actual design data that fills the sections —
  **constraints** (§5), **decisions** (with rationale + source), **device
  selection**, **topology**, **addressing**. Mostly already modelled
  (`requirement_items`, `design_decisions`, `topology_*`, `requirement_responses`);
  this doc adds **constraints** and binds it all under one profile.

Rendering (§6) weaves the flesh into the bone per each section's content spec; the
completeness gate (§7) checks *every required content element is present* — so a
section is "done" only when it has its substance, not merely a heading.

## 3. Why this fixes "flesh-and-bone completeness"

The dev_docs/107 completeness gate checked *chapter non-empty*. That is bone-only:
a one-sentence chapter passed. The content specification makes completeness mean
**"this section contains the tier model AND the protocol choice+why AND the
diagram AND the scaling rationale"** — the gate fails a section missing any
required element. The document cannot be structurally complete but substantively
thin.

## 4. Section content specification (the 骨, made precise)

Each doc-structure profile section gains a `content:` list — the elements it must
contain, each declaring where it comes from (`decision` / `constraint` /
`computed:<renderer>` / `narrative`) and whether it is `required`. Example
(HLD Logical Topology):

```yaml
- id: logical-topology
  title: "Logical Topology"
  content:
    - {element: tier_model,       from: decision,   topic: "layering (spine-leaf / 3-tier) + why", required: true}
    - {element: routing_protocol, from: decision,   topic: "underlay/IGP choice + why",            required: true}
    - {element: topology_diagram, from: computed:topology_mermaid,                                  required: true}
    - {element: segmentation_ref, from: constraint, topic: "VLAN/VRF boundaries honoured",          required: false}
    - {element: scaling,          from: computed:capacity,                                          required: true}
    - {element: traffic_flow,     from: narrative,  topic: "east-west vs north-south",              required: false}
```

- `from: decision` → the renderer pulls the confirmed `design_decisions` matching
  this element's topic (with their rationale + `[D:]` citation) — the "why".
- `from: constraint` → pulls the relevant approved constraint (§5), cited.
- `from: computed:<name>` → runs the deterministic renderer (topology diagram,
  capacity, failure-domain, BOM, compliance-matrix — dev_docs/107 §7).
- `from: narrative` → an optional short LLM slot for connective prose, still
  grounded/cited; NOT the primary substance.

The content spec is git-tracked YAML — **the user edits it to define what a
section must contain**, which is itself part of what they approve (the bone).

## 5. Constraints — the hard bounds that drive generation

Distinct from requirements (what the client asks → responded to in the compliance
matrix), **constraints are hard bounds the design must honour**, extracted and
approved, that **drive the generators**.

### 5.1 Two tiers
- **HLD-tier** (extracted at preliminary info, approved before HLD): vendor
  preference/lock, technology route (EVPN-VXLAN / SD-WAN / 3-tier), scale bounds,
  redundancy targets, compliance mandates, **product/route inferred from tender
  parameters** (e.g. "DNA Center" → cisco+controller route; "VXLAN EVPN" → overlay).
- **LLD-tier** (extracted after HLD discussion, approved before LLD): IP
  supernets/ranges, VLAN ID plan, **management address range**, ASN range, naming
  convention, routing policy, OOB/DNS/NTP.

### 5.2 Extraction (three sources)
1. **Parameter inference** — a `param → constraint` mapping (keywords/specs in the
   tender imply vendor/route/product tier).
2. **Documents** — Docling chunks: extract explicit IP/VLAN/mgmt tables.
3. **Meetings** — ingested meeting notes: same extraction path.
All land as `constraints` rows with a `source` (`param`/`document`/`meeting`) +
`status` (`extracted` → `approved`), HITL-reviewed.

### 5.3 They DRIVE generation (the point)
- HLD-tier → `select_devices` filters by vendor/route constraint; approach
  selection is *locked* to the constrained route; the skeleton honours it.
- LLD-tier → the IP allocator uses the **constrained supernet/ranges** (not an
  arbitrary 10.0.0.0/8); VLANs from the constrained plan; mgmt addressing from the
  mgmt range; ASN from the ASN range. `generate_lld` becomes constraint-driven.

### 5.4 Data model
`presales.constraints`: `constraint_id, project_id, tier(hld|lld), kind
(vendor|route|ip_range|vlan_plan|mgmt_range|asn_range|naming|...), value(JSON),
source(param|document|meeting), evidence_id, status(extracted|approved|waived),
approved_at`. New table (created via ensure_schema — no ALTER). Generalises the
existing `design_runs.hld_constraints_json` into an extractable, approvable,
generation-driving store.

## 6. Rendering (deterministic, from the approved profile)

`render_document(project, run, doc_type, network_type)`:
1. Load the doc-structure profile (bone) + the design content (flesh: constraints,
   decisions, selection, topology, addressing) for the run.
2. For each section, for each `content` element: resolve it from its `from:` source
   (decision rationale / constraint / computed renderer / narrative slot), each
   carrying a resolvable citation.
3. Assemble in section order; append declared diagrams; embed BOM + compliance
   matrix appendices. Grade (§7).

Narrative substance = **the decision rationales** (human-approved, in the profile)
woven per section — not free per-chapter LLM prose. `narrative` slots remain for
thin connective text only.

## 7. Completeness gate — of SUBSTANCE, not just structure

Extends the dev_docs/107 gates. A document passes only when, in addition to
(citations resolve · no placeholders · rationale present · coverage · diagrams
embedded):

- **content-completeness**: every `required` content element of every section is
  present (the decision/constraint/computed/narrative it names resolved to real
  content). A section missing its tier-model decision, or its topology diagram, or
  its scaling calc, FAILS — reported as `missing_content: [{section, element}]`.
- **constraint-honoured**: the design does not violate an approved constraint
  (e.g. an IP allocated outside the constrained supernet; a vendor outside the
  lock) — reported as `constraint_violations`.

Both zero-LLM, deterministic.

## 8. Lifecycle — profile-first, double approval gate

```
立项 project new
 → intake + preliminary extraction (documents + tender params + meetings)
 → build HLD design profile  (requirements + HLD-tier constraints + decisions
                              + selection + topology, structured)
 → ①  HUMAN APPROVES THE PROFILE  (edits constraints / decisions / content spec)
 → render HLD  (deterministic; substance-complete or the gate blocks)
 → HLD ↔ client, multi-round discussion → new materials ingested
 → re-extract → add LLD-tier constraints (IP / VLAN / mgmt ranges) to the profile
 → ②  HUMAN APPROVES THE (LLD) PROFILE
 → render LLD  (deterministic; IP/VLAN/mgmt from the approved constraints)
```

The two gates are the real-world checkpoints the user described. Between them the
profile is the single evolving source of truth; every render is faithful to it.

## 9. Evolution from dev_docs/107 (kept vs changed)

| Kept | Changed |
|---|---|
| doc-structure profiles (outline) | + per-section `content:` spec (§4) |
| computed renderers (failure-domain / capacity / BOM / matrix / topology diagram) | become the `computed:` content sources |
| `design_decisions` (+ rationale/source coercion) | become the narrative substance (rendered), not chapter prose |
| requirement register + compliance matrix + coverage gate | unchanged |
| grader (citations / placeholders / rationale / coverage / diagrams) | + content-completeness + constraint-honoured |
| chapter accumulation / per-chapter loop | subsumed — the loop can still populate `narrative` slots, but sections are render-first |

Not wasted: everything built in 107 (renderers, decisions, constraints seed,
gates, accumulation) is the profile's content or its renderer.

## 10. Phased plan

**Phase 1 — constraints (extract → approve → drive):** `constraints` table;
`extract_constraints` (param-inference + doc/meeting); `approve_constraints` (HITL);
wire LLD IP/VLAN/mgmt constraints into the allocator + vendor/route into
`select_devices`. Highest real-world value (IP/VLAN/mgmt are what LLDs live on).

**Phase 2 — section content spec + render-from-profile:** add `content:` to the
doc-structure profiles; `render_document` resolving each element; content-completeness
+ constraint-honoured gates. HLD/LLD become render-from-profile.

**Phase 3 — lifecycle orchestration:** the two approval gates as verbs/state on
`design_runs` (profile_status: draft→approved per tier); the orchestrator flow
kickoff→extract→approve→render→discuss→extract→approve→render. Re-run Pershing +
campus end-to-end.

## 11. Definition of Done / testing

- Deterministic: constraint extraction (fixture params/docs → constraints),
  constraint-driven allocation (LLD uses the constrained supernet — assert the
  allocated IPs fall in range), content-completeness gate (a section missing a
  required element FAILS), constraint-honoured gate (an out-of-range IP FAILS).
- Wiring: every new script reachable via `execute_skill_script`; approval gates
  fire from a real invocation.
- Behavioural: campus/DC render-from-profile at N≥3; the gate blocks any
  substance-incomplete or constraint-violating document.
