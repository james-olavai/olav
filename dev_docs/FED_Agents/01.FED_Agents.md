# 🚀 OLAV Federated Agents Architecture (v2)

This document details the redesigned 4-Agent architecture for OLAV, shifting from a single Orchestrator to a decoupled, intent-driven Multi-Agent structure. This design aligns natively with LangGraph's Multi-Graph philosophy, providing targeted context, blazing-fast response times for simple queries, and deep reasoning capabilities for complex troubleshooting.

## 🌟 The 4 Main Agents (Folder-Isolated)

Users invoke specific agents via the CLI (e.g., `olav --agent ops`). Each agent lives in its own subdirectory under `.olav/workspace/` and is governed by a localized `AGENT.md` configuration file.

1.  **Quick Query Agent (`quick`)**: Default. Blazing fast, zero-shot SQL and CLI lookup.
2.  **Operations Agent (`ops`)**: Deep-dive troubleshooting and complex network analysis.
3.  **Config & System Agent (`config`)**: Lifecycle management, data syncing, and system health.
4.  **Audit & Compliance Agent (`audit`)**: Rule generation and compliance checking.

---

## ⚡ 1. Quick Query Agent (`quick`)
**Design Philosophy:** Speed with reliability. This agent is optimized for sub-5-second responses but allows a limited **Self-Healing Loop (max_iterations=3)**. It prioritizes direct SQL generation from a static reference but can correct its own syntax errors. It acts purely as a translator from Natural Language to SQL/CLI.
**Context Isolation:** It only knows the database schema and basic CLI execution paths. It does NOT load troubleshooting prompts or complex analysis tools.
**Memory & Knowledge Integration:** Native integration with the Semantic Cache (Tier 0). If a query is a direct hit on the cache, it returns in <0.5s. If not, it can optionally use `search_knowledge` to quickly retrieve past troubleshooting playbooks before returning a response.

### Subagents
- **Main Agent Only:** No subagents needed to achieve sub-5-second latency.

### Tools
- `execute_sql` (Existing): Fast DuckDB querying using `snapshot_id = MAX(snapshot_id)`. **Note:** This tool *internally* acts as a schema search (its `explain_only=True` mode or caching mechanism allows the agent to discover schema dynamically before writing SQL).
- `execute_cli` (Existing): Live device query for real-time state.
- `search_commands` (Existing): Look up valid CLI commands.
- `search_knowledge` (Existing): Semantic search against `.olav/knowledge/` to find past cases or SOPs.
- `format_and_export` (Existing): To support user requests like "Export this table to CSV or Markdown".

*Tools to Move/Develop:*
- Ensure `execute_sql`'s internal schema auto-discovery is robust enough that the agent doesn't need a separate, explicit `search_schema` tool taking up a reasoning step.

## 🕵️‍♂️ 2. Operations Agent (`ops`)
**Design Philosophy:** Deep reasoning. Full ReAct loop enabled. This agent orchestrates a team of specialized subagents to diagnose complex network faults.

### The Ops Orchestrator (主 Agent)
**Role**: The Senior Network Architect.
**Memory & Knowledge Integration**: Before allocating tasks to subagents, the Orchestrator **MUST query the KB (`search_knowledge`)** to see if this fault pattern has been documented. If the KB says "When OSPF drops on interface Gi0/0, check MTU first", it immediately directs the relevant subagent to check MTU, saving valuable ReAct cycles.
**Tools**:
- Needs `search_commands`, `search_knowledge`, and *Schema Discovery* tools natively. Why? The Orchestrator must understand *what operations are possible* and *what past solutions exist* to correctly formulate a plan and delegate.
- `format_and_export` for finalizing the global report.
**Subagent Delegation**: Once the plan is made, it delegates *execution* to subagents.

### Subagents (Execution Experts)
1.  **L2 / Topology Expert**
    - **Focus:** MAC tables, ARP, physical links, loop detection (STP), CDP/LLDP.
    - **Tools:** `analyze_network_topology`, `execute_sql` (restricted to topology tables).
2.  **L3 / Routing Expert**
    - **Focus:** BGP, OSPF, static routes, routing blackholes, optimal path analysis.
    - **Tools:** `execute_sql` (restricted to routing tables), `execute_cli`.
3.  **Probe Expert (勘探专家)**
    - **Focus:** Active liveness and latency testing, exploring unknown network segments.
    - **Tools:** `ping_device`, `traceroute`, `port_scan`, `execute_cli_parallel`.
4.  **Diff Expert (变更专家)**
    - **Focus:** Time-series drift detection. Compares two `snapshot_id`s to find exactly what broke in the network, drawing inspiration from advanced tools like `pyATS` (multi-dimensional state comparison).
    - **Tools to Develop:**
      - `diff_sql_state`: A high-level tool that takes two `snapshot_id`s and a table name (e.g., `routes`, `ospf_neighbors`), executing a SQL `EXCEPT/MINUS` query to return a structured JSON of missing or new entries.
      - `diff_topology_drift`: A specialized tool that compares the `topology_links` between two snapshots to instantly highlight links that went DOWN or came UP.
      - `diff_routing_drift`: Specifically checks for BGP prefix loss or OSPF adjacency changes between $T1$ and $T2$.
      - `diff_raw_configs`: Similar to the existing `diff_configs`, but guaranteed to use the new `snapshot_id` architecture for pure CLI text comparison.

## ⚙️ 3. Config & System Agent (`config`)
**Design Philosophy:** The administrative workhorse. Handles data ingestion, schema normalization, self-healing, and framework maintenance.

### The Init Workflow (Day 0 & Scheduled)
When a user runs `olav --init` or a scheduled Cron job triggers, this Agent executes a strict pipeline:
1. **Sync Commands:** Download the latest parsing templates (TextFSM).
2. **Take Snapshot:** SSH to all devices and pull raw logs + parse them into `parsed_outputs`.
3. **Fuzzy Mapping (Schema Alignment):** Normalize multi-vendor output to the Cisco baseline.
4. **Topology Generation:** Extract LLDP/CDP and BGP/OSPF adjacencies from normalized tables and build the visual `topology_links` mapping.

### Subagents
1.  **Snapshot & Sync Subagent**
    - **Focus:** Executes Steps 1 & 2 of the Init workflow. Connects to devices, pulls data, and maintains the basic DB schema.
    - **Tools:** `sync_commands`, `take_snapshot`, `sync_schemas`.
2.  **Topology & Schema Alignment Subagent**
    - **Focus:** Executes Steps 3 & 4 of the Init workflow. First, it "washes" non-Cisco data using LLM Fuzzy Mapping. Then, it sweeps the parsed routing and neighbor tables to mathematically generate the `topology_links` and `interfaces` tables.
    - **Tools:** `fuzzy_map_schema`, `generate_topology`.
3.  **Knowledge & Cache Manager Subagent**
    - **Focus:** OLAV uses a "File as Source of Truth" design for Knowledge (in `.olav/knowledge/`). This subagent parses new markdown PDFs or user input, updates the vector database (LanceDB or DuckDB vectors), and manages cache invalidation.
    - **Tools:** `index_knowledge`, `manage_cache`.
4.  **Skill Creator & Integration Subagent (NEW)**
    - **Focus:** Automating the onboarding of new external systems (e.g., NetBox, ServiceNow) using Schema-Aware deployment. By providing an `openapi.yaml` or WSDL, this agent writes the Python integration script, places it in `.olav/scripts/`, and generates the `SKILL.md`.
    - **Tools:** `read_api_schema`, `write_skill_code`.
5.  **Command Learner Subagent**
    - **Focus:** Teaching OLAV how to parse new CLI commands via TextFSM.
6.  **Doctor / System Subagent**
    - **Focus:** Diagnosing OLAV itself (DuckDB locks, missing skills, cron status).

## 📋 4. Audit Agent (`audit`)
**Design Philosophy:** Read-only governance. Ensures the network complies with defined intents. Decouples rule definition from rule execution.

### Subagents
1.  **Rule Writer Subagent**
    - **Focus:** Translating user intent ("Ensure all edge ports have BPDU guard", "Identify unused ports with no traffic for 30 days") into YAML configurations.
    - **Tools:** Native DeepAgents `FileSystem` middleware.
2.  **Rule Executor Subagent**
    - **Focus:** Running the audits (including Policy, Compliance, and **Resource Optimization** scans) and formatting markdown reports.
    - **Tools:** `run_audit`.

## 🔄 Migration Path

1.  **Directory Initialization:**
    - Create `.olav/workspace/{quick,ops,config,audit}` folders.
    - *Note*: There is no global `common/` directory; each agent/subagent folder is a self-contained unit.
2.  **CLI Entrypoint Update (`cli_main.py`):**
    - Add `--agent [quick|ops|config|audit]` argument.
    - Map default execution to `quick` agent with forced `max_iterations=1`.
3.  **Skill Repackaging:**
    - Migrate existing tools from `olav-ops`, `olav-config`, and `olav-audit` into the new isolated folder structure.
    - Create localized `AGENT.md` files in each agent's root to define subagent experts.
4.  **Tool Relocation:**
    - Shared utilities like `execute_sql` and `search_knowledge` are consolidated within the `quick` agent or specifically duplicated/linked into specialized skills that require them to maintain **Independent Portability**.
    - Move domain-specific tools (like `take_snapshot`) to localized `config/sync` sub-skills.
5.  **Configuration Migration:**
    - Deprecate the monolithic `OLAV.md`. Move its logic into fragmented `AGENT.md` and `SKILL.md` files within each expert directory.
