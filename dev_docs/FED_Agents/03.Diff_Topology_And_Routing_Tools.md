# 🛤️ Diff Expert Tools: diff_topology_drift & diff_routing_drift

This document details the specialized domain-specific comparison tools for the `ops` agent's Diff Subagent. Unlike generic SQL state comparisons, these tools understand network protocols and relationships.

## 1. `diff_topology_drift` (Topology Drift Detection)

### Purpose
To tell the LLM exactly how the physical or logical network map has changed between two snapshots, focusing on `topology_links`.

### Implementation Strategy
This tool goes beyond a simple row-by-row SQL `EXCEPT`. It needs to handle the fact that a link $A \rightarrow B$ might be represented differently or have its status change without the row disappearing.

#### Core Logic
1. **Fetch State**: Query `topology_links` for both `snapshot_id_1` and `snapshot_id_2`.
2. **Normalize Links**: Treat links as bidirectional edges $(A, B)$ or $(B, A)$ if they are physical.
3. **Analyze Drift**:
   - **Link Down (Removed)**: Existing in $T1$ but not in $T2$.
   - **Link Up (Added)**: Existing in $T2$ but not in $T1$.
   - **Status Change**: Exists in both, but `link_status` transitioned (e.g., from `up` to `down` or protocol from `LLDP` to `CDP`).

### Output Format
Provides a highly readable summary highlighting topological impacts:
```json
{
  "topology_changes": {
    "links_down": [
      {"source": "Core-SW1", "src_int": "Gi1/0/1", "dest": "Dist-SW2", "dst_int": "Te0/1"}
    ],
    "links_up": [
      {"source": "Core-SW1", "src_int": "Gi1/0/2", "dest": "Dist-SW2", "dst_int": "Te0/2", "note": "Backup link became active"}
    ],
    "status_changes": []
  }
}
```

## 2. `diff_routing_drift` (Routing Drift Detection)

### Purpose
To identify loss of reachability, changes in routing paths (metrics/next-hops), and BGP prefix shifts between snapshots.

### Implementation Strategy
Routing tables (`routes` and `bgp_routes`) are massive. The LLM cannot look at everything. This tool must filter for actual *drift*.

#### Core Logic
It compares the routing state focusing on key indicators of network stability:
1. **Lost Prefixes**: A specific subnet was reachable in $T1$ but is completely missing in $T2$ across a specific device. (Potential routing blackhole).
2. **Next-Hop Shifts**: The prefix exists in both, but the `next_hop` IP changed. This indicates a topology reconvergence.
3. **BGP Attribute Shifts**: For BGP specifically, compare `as_path` length or `local_pref`. A longer `as_path` in $T2$ explains why traffic is suddenly taking a slower backup route.

### Processing Pipeline
1. Run specialized SQL joins contrasting $T1$ and $T2$ tables.
   ```sql
   SELECT t1.network, t1.next_hop as old_hop, t2.next_hop as new_hop
   FROM routes t1
   LEFT JOIN routes t2 ON t1.device_name = t2.device_name AND t1.network = t2.network
   WHERE t1.snapshot_id = 'T1' AND (t2.snapshot_id = 'T2' OR t2.snapshot_id IS NULL)
   AND t1.next_hop != COALESCE(t2.next_hop, '')
   ```
2. Limit output to a maximum of ~20 significant changes to prevent context overflow, summarizing the rest (e.g., "And 340 other prefixes experienced next-hop changes").

### Output Format
```json
{
  "device_name": "R1",
  "routing_drift": {
    "lost_destinations": ["10.50.1.0/24", "10.50.2.0/24"],
    "path_shifts": [
      {"network": "0.0.0.0/0", "old_next_hop": "192.168.1.1", "new_next_hop": "192.168.2.1"}
    ],
    "bgp_as_path_changes": [
      {"network": "172.16.0.0/16", "old_path": "65001 65002", "new_path": "65001 65003 65002"}
    ]
  }
}
```
