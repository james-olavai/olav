# 🛠️ Config Agent: Pipeline Upgrades

This document outlines the required engineering tasks to upgrade the `config` agent's "Init Workflow," ensuring a robust data pipeline from raw device logs to normalized mathematical topologies.

## 1. Fix: Historical Snapshot Cleanup Bug

### The Problem
During Phase 0, we refactored the database schema from using a single `snapshot_date` (which implicitly overwrote identical dates) to using a unique `snapshot_id` for every run, making all tables append-only. 
However, the system currently lacks a retention policy manager. Running `take_snapshot` repeatedly will cause the DuckDB file and the `exports/snapshots/` directory to grow infinitely. 

### Implementation Requirements
**Tool:** `clean_historical_snapshots` (To be added to the `Snapshot & Sync Subagent`)

1. **Retention Policy:** Implement a configuration-driven retention policy (e.g., retain the last 7 days or the last 30 snapshots via `olav.yaml`).
2. **Database Cleanup:** Write a SQL sequence that identifies stale `snapshot_id`s based on timestamp (derived from the ID suffix or `sync_metadata` table) and executes `DELETE FROM <table> WHERE snapshot_id IN (...)` across all operational tables.
3. **Filesystem Cleanup:** Ensure that when a `snapshot_id` is purged from the database, the corresponding `exports/snapshots/<date>_<id>/` folder containing the raw text logs is also deleted from disk to reclaim space.

## 2. Feature: LLM Fuzzy Schema Mapping

### The Problem
Network automation has historically failed because every vendor (Cisco, Huawei, Juniper, Arista) names their JSON parsed keys differently. For instance, an interface status might be `up` (Cisco), `est` (Huawei), or `Established` (Juniper). Building rigid `if/else` parsers is a never-ending, unmaintainable task.

### Implementation Requirements
**Tool:** `fuzzy_map_schema` (To be added to the `Topology & Schema Alignment Subagent`)

This tool sits between the raw `parsed_outputs` table and the extraction of specific domain tables (like `interfaces` or `routes`).

1. **Cisco as the Baseline:** We define standard Pydantic models (or JSON schemas) for our target tables (`interfaces`, `bgp_neighbors`, etc.) based strictly on Cisco IOS/NXOS expected keys.
2. **LLM Translation Layer:** When the Sync subagent encounters data from `vendor: huawei`, the Fuzzy Mapping tool analyzes a sample JSON output from that vendor and the desired Cisco baseline schema. It asks the LLM: *"Map these Huawei keys to the Cisco standard keys."*
3. **The `schema_mappings` Cache:** 
   - Once the LLM successfully translates a schema, it saves the mapping logic into a new DuckDB table: `schema_mappings` (e.g., `{"vendor": "huawei", "command": "display bgp peer", "raw_key": "est", "cisco_key": "up"}`).
   - **Crucial Optimization:** In all future snapshot runs, the system queries this mapping table *first*. The expensive ReAct LLM loop is bypassed; the Python code simply renames the JSON keys according to the cached mapping rule in milliseconds.

## 3. Refactoring: Topology Link Generation Algorithm

### The Problem
Currently, physical topology relationships are somewhat brittle, relying heavily on LLDP/CDP parsed keys that vary wildly depending on the OS. With the introduction of the Fuzzy Mapping layer, we now have a guaranteed, uniform data structure to work with, allowing us to build a much more mathematically rigorous and deterministic topology generator.

### Implementation Requirements
**Tool:** `generate_topology` (To be rewritten for the `Topology & Schema Alignment Subagent`)

1. **Dependency on Purity:** This algorithm must *only* execute after `fuzzy_map_schema` has guaranteed that the underlying `interfaces`, `cdp_neighbors`, and `lldp_neighbors` tables strictly adhere to the Cisco baseline schema.
2. **Edge Normalization:** The algorithm must iterate over all neighbor tables to construct bidirectional graph edges `(Device A, Port X) <--> (Device B, Port Y)`.
   - It must ensure no duplicate edges are created (i.e., treating `A->B` and `B->A` as a single `topology_link` entry).
3. **Logical Overlay:** After physical links are established, the algorithm should execute a secondary pass over the `bgp_neighbors` and `ospf_neighbors` tables to draw logical edges (e.g., eBGP peerings over loopbacks).
4. **Persistence:** The final, cleaned, bidirectional graph is bulk-inserted into the `topology_links` table under the current `snapshot_id`.
