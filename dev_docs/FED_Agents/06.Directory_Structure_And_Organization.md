# 📂 Directory Structure & Agent Organization

This document defines the physical organization of the OLAV `.olav/workspace` directory. We adopt a **Folder-based Agent Isolation** strategy to ensure context purity, tool security, and horizontal scalability.

## 1. Core Principles
- **Directory as Context**: An agent only loads tools and prompts from its specific sub-directory. There is NO global `common/` directory.
- **Independent Portability**: Every skill folder is a self-contained unit. It contains all the tools (`.py`) and prompts (`.md`) it needs to function. This allows a skill to be zipped and moved to another OLAV instance seamlessly.
- **Physical Isolation**: Tools for "Config" (writing data) are physically separated from tools for "Ops" (reading data), preventing unauthorized cross-domain tool execution.
- **Micro-Skill Pattern**: Each subagent's logic is encapsulated in a sub-folder with its own `SKILL.md`.

## 2. The `.olav/workspace` Map

.olav/
└── workspace/
    ├── quick/                  # 1. Quick Query Agent (Default)
    │   └── AGENT.md            # Entry point. Loads localized query skills.
    │
    ├── ops/                    # 2. Operations Agent (Orchestrator)
    │   ├── AGENT.md            # Senior Architect Prompt. Delegates to sub-folders.
    │   ├── routing/            # Specialist Routing Subagent
    │   │   └── SKILL.md        # DB Schema: routes, bgp_routes
    │   ├── topology/           # Specialist Topology Subagent
    │   │   └── SKILL.md        # DB Schema: topology_links, interfaces
    │   ├── probe/              # Specialist Probe Subagent (Active testing)
    │   │   └── SKILL.md        # Tools: ping_device, traceroute
    │   └── diff/               # Specialist Diff Subagent (Time-series)
    │       └── SKILL.md        # Tools: diff_sql_state, diff_routing_drift
    │
    ├── config/                 # 3. Config & System Agent (Orchestrator)
    │   ├── AGENT.md            # Admin Prompt.
    │   ├── sync/               # Snapshot & Sync Subagent
    │   │   └── SKILL.md        # Tools: take_snapshot
    │   ├── discovery/          # Schema Alignment Subagent
    │   │   └── SKILL.md        # Tools: fuzzy_map_schema, generate_topology
    │   ├── creator/            # Skill Creator Subagent (New Skill Deployment)
    │   │   └── SKILL.md        # Tools: read_api_schema, write_skill_code
    │   ├── learner/            # Command Learner Subagent
    │   │   └── SKILL.md        # Tools: learn_textfsm
    │   ├── knowledge/          # Knowledge & Cache Manager
    │   │   └── SKILL.md        # Tools: index_knowledge
    │   └── system/             # Doctor / Self-Healing Subagent
    │       └── SKILL.md        # Tools: check_health
    │
    └── audit/                  # 4. Audit Agent (Orchestrator)
        ├── AGENT.md            # Compliance Prompt.
        ├── writer/             # Rule Writer Subagent
        │   └── SKILL.md        # Permission: FileSystem Write Access
        └── auditor/            # Rule Executor Subagent
            └── SKILL.md        # Tools: run_audit
```

## 3. Configuration Management (`AGENT.md`)

Each Agent directory contains an `AGENT.md` file (replacing the previous monolithic `OLAV.md` sections).

### Example: `.olav/workspace/ops/AGENT.md`
```yaml
name: ops-orchestrator
description: "Expert senior network architect for troubleshooting."
system_prompt_file: prompts/orchestrator.md
subagents:
  - path: ./routing/SKILL.md
  - path: ./topology/SKILL.md
  - path: ./diff/SKILL.md
```

## 4. Key Benefits for Developers
- **Context Management**: By passing the local path to the agent loader, we automatically restrict the "World View" of the LLM.
- **TDD Focus**: Developers can write tests that target a specific agent sub-directory (e.g., `pytest tests/agents/ops/`).
- **Scalability**: Adding a new "Expert" (e.g., an `ipsec-expert`) simply involves creating a new folder under `ops/` and registering it in `ops/AGENT.md`.
