# 113. Pre-sales architecture validation — render the design, validate it layer by layer

**Status:** Design / gap analysis. Nothing built. Supersedes nothing.
**Depends on:** dev_docs/112 (twin builder — the back half is reused verbatim),
dev_docs/106 (deterministic IP allocation), dev_docs/110 (profile→render, the
reliability lesson), dev_docs/107 (bid-grade provenance contract).
**Date:** 2026-08-02. All numbers in §3-§5 are measured against the live
`main.duckdb` presales schema and the live clab host, not estimated.

---

## 0. Scope — what this line is, and what it is not

Pre-sales produces a design. The question this line answers is **"does the
proposed architecture actually work"** — does the addressing plan hold, does
the underlay converge, does the fabric survive a link failure.

It is **not price validation**, and that is not a phasing decision — it is
structurally impossible:

* There is **no price data in the system**. A repo-wide grep across
  `olav-presales/src` finds no `price` / `cost` / `currency` field; the BOM is
  a device list, not a quote. The only match is the string
  `"(no priced devices in the design)"`.
* **Sizing is arithmetic, and a lab cannot improve arithmetic.**
  `compute_sizing` returns `oversubscription = downlink_bw / uplink_bw`,
  `device_count = ceil(endpoint_ports / ports_per_device)`,
  `endpoint_capacity = ports × speed`. Running these through containers a
  hundred times does not change `ceil(480/48) = 10`.
* **Virtual images have no dataplane fidelity.** `throughput_gbps`, table
  scale, TCAM, queueing — every vrnetlab/SRL number is artificially capped.
  A measured figure here would be worse than no figure, because it would look
  authoritative.

The one price-*adjacent* thing a lab could touch is the `features:` list in
`device_catalog.yaml` (`[bgp, ospf, evpn, vxlan, mlag]`), which are datasheet
assertions that drive `device_select` scoring → model choice → price. But the
direction is wrong: **a virtual image lacking a feature does not imply the
hardware lacks it** (dev_docs/112 §12.2 — `cisco_iol:17.12` refuses
`access-session` that a real Catalyst 9300 accepts). It can falsify, not
confirm, and selection needs confirmation. Do not build on this.

### 0.1 The scope constraint that drives every decision below

> **In pre-sales, clab buys architectural validation at minimum cost. It is
> not functional validation, and must never be scoped as if it were.**

This is the governing constraint, not a preference, and it settles most of the
design questions before they are asked:

* **One image for everything: SR Linux.** Public, no vendor licence, no
  per-vendor packaging. Vendor-native images (`arista_ceos`, `cisco_n9kv`,
  `paloalto_panos`) are functional-validation tools; buying config fidelity
  means buying image supply, licensing and per-vendor breakage, and the
  deliverable does not need it.
* **Render only what the architecture rests on**: interfaces, addressing,
  routing. **No** ACLs, NAT, policy, QoS, 802.1X or feature config — and
  therefore no per-vendor feature grammar. This is why the renderer (G1) stays
  small: `build_interface_spec` + `generate_bgp_sessions` already hold
  essentially the whole input.
* **Three layers, not four.** L1 links, L3 addressing, L4 routing convergence.
  L2 is vacuous in a routed fabric and out of scope in an access design (G6) —
  assert "not applicable", never pad it into evidence.
* **Node count is the only real cost driver**, so the scale gate (G9) matters
  more than any fidelity question. Labs are always destroyed (§112 runner
  behaviour), never kept warm.
* **Whatever a role's product is actually bought for is out of scope by
  definition** — firewall policy, campus access control, WAN optimisation.
  Batfish (T0) answers those, or nothing does (§6).

Everything below is scoped to this constraint. Where an option would buy
functional fidelity, it is recorded as out-of-scope **with its reason**, not as
a future phase.

## 1. This is not the SRL translation that was killed twice

dev_docs/73 and dev_docs/96 §8 killed "SR Linux as a universal translation
target", and dev_docs/112's governing principle is "the LLM never authors
config". Both still hold. This line does a **different operation**:

| | killed (dev_docs/96 §8) | this line |
|---|---|---|
| input | **existing production running-config** (Cisco/Juniper syntax) | **structured design parameters** (role / ASN / IP / links) |
| operation | **translate** across grammars — semantics lost at every hop | **render** greenfield, natively in the target's own grammar |
| better deterministic alternative? | **yes** — run the native image; translation was never worth it | **no** — greenfield has to generate config from something |
| fidelity requirement | config-level (the config *is* the thing under test) | shape-level (the config will never be deployed) |

SRL collapsed originally because "translate to SRL" fused all three orthogonal
compatibility axes (§112 §1) into one action. Greenfield rendering has no
translation step, so the axes stay separate. This is also **not** the TS
stand-in of §112 §9.2 — TS carries facts across from a source config; here
there is no source config at all, only design parameters.

## 2. Governing principle

> **The design is the source of truth. Render it to targets. The LLM declares
> the architecture (WHAT); Python renders the config (HOW); the lab confirms
> layer by layer.**

The LLM must not author config lines, for a reason pre-sales has already paid
for: dev_docs/110 took HLD reliability from ~1/3 to N=3 3/3 by replacing
per-chapter LLM authoring with nine deterministic renderers. The root cause was
**call count**, not model capability — ~15-58 LLM calls made four consecutive
`loop_breaker` failures near-certain. A bid exhibit additionally must be
**reproducible**: the same design rendered twice must produce byte-identical
config, which LLM authoring cannot guarantee.

The WHAT/HOW boundary is the same as §112 §2.4, with "render from design"
substituted for "slice from production".

## 3. What already exists (measured)

### 3.1 Pre-sales side — the design pipeline is further along than it looks

| component | file | output shape |

`build_interface_spec` is the important one: it is already, almost exactly, the

## 4. Gaps

### G1 — No design→CLI renderer *(the main build item; small)*

Nothing renders `interface_spec` + `bgp_sessions` into device config. Needed:
one renderer per target grammar, driven by the existing per-family profile
mechanism, emitting **already-layered** config
(`{device: {L1: [...], L2: [...], L3: [...], L4: [...]}}`) so the bucketer is
bypassed rather than round-tripped.

### G2 — CLOSED: the addressing→DB handoff works *(verified 2026-08-02)*

This was the blocking gate. It holds.

Driven end to end with a complete 2-spine/4-leaf skeleton
(`plan_ip_allocation` → `generate_bgp_sessions` → `build_interface_spec` →
`_persist_to_be`) against a scratch DB: **6 nodes and 8 links persisted with
zero NULLs** across `loopback_ip`, `bgp_asn`, `source_ip`, `destination_ip`.
The dev_docs/106 promise ("the LLD's addressing/routing is QUERYABLE") is real.

The production NULLs that raised the alarm are explained, not a defect:

| project | written by | node `loopback_ip`/`bgp_asn` | link p2p IPs |
|---|---|---|---|
| `proposal-request` | **`lld_generator`** | 0/5 | **6/6 present** |
| `designer-dc`, `meridian-dc`, `campus-metro` | not `lld_generator` | 0 | 0 |

Only one project has ever been through the LLD path, and **its link addressing
is complete**. Its nodes carry no loopback because `loopback_scheme` is
optional and was omitted, and no ASN because it is a campus L2 design —
`generate_bgp_sessions` returns empty for exactly that case by contract. The
other three projects never ran the LLD, so their NULLs are not evidence.

Two contracts worth recording, both enforced by clear errors rather than silent
degradation: `p2p_scheme.pool` is **required** (`plan_ip_allocation` raises,
`generate_lld` returns `status: error`), and `loopback_scheme` is **optional**
(omit → no loopbacks at all, which a design without loopbacks legitimately
wants).

### G10 — Interface names are absent from real design data *(found by the G2 probe)*

`proposal-request`'s six links have full p2p addressing and
`source_interface = destination_interface = NULL`. The skeleton's
`a_iface`/`b_iface` are optional, and the one real LLD run did not supply them.

The renderer needs interface names for two things the lab cannot do without:
the clab link endpoints (L1) and the per-interface address config (L3). Asking
the LLM to name ports is the wrong fix — it is HOW, not WHAT (§2), and it is
exactly the class of detail a small model invents (`Eth1/49` on a device whose
model has 48 ports).

Needs a **deterministic interface allocator**: assign ports from the device
model's own layout (`device_catalog.yaml` already carries `port_count` and
`port_speeds`), in a canonical order, uplinks from the top of the range. This
is the same shape as `remap.lab_interface_pool()` in the twin (§112 §6.2) —
allocate over a declared pool, record the bijection — with the design's model
supplying the pool instead of the clab kind.

### G3 — `build_twin` assumes slice-from-running-config *(small)*

`build_twin(intent, configs)` runs seed derivation → slice → bucket → remap.
For a rendered design all of that is redundant and the slicer would actively
*drop* lines not reachable from the intent's base refs. Needs a
`build_twin_from_design()` that constructs `DeviceTwin`s directly, with an
empty `SliceResult`.

### G4 — Batfish cannot parse SR Linux *(architectural, not a defect)*

`nokia_srl / nokia_srlinux | NONE — no Batfish parser as of 2025.7`
(`batfish_capability_catalog.guide.yaml`). You cannot feed one rendered config
to both tiers. This forces — and justifies — **two render targets from one
design**:

```
        design (topology_nodes / topology_links / interface_spec / bgp_sessions)
                              │
              ┌───────────────┴───────────────┐
        render: nxos|ios                render: srl
              │                               │
        Batfish (T0)                    clab SRL (TS)
        "is the design correct"    "does it come up, and can we show it"
```

### G5 — Interface-name mapping from design names to SRL *(small)*

Designs use NX-OS style (`Eth1/1`, `Eth1/49`). SRL wants `ethernet-1/1`, and
clab link endpoints want `e1-1`. `remap.py` already does prod→lab bijection and
`rulesets/srl.yaml` already has the pool and the endpoint-name rule; this is a
new *entry point* into existing machinery, not new machinery.

### G6 — Labelling rule, not an exclusion rule *(revised under §0.1)*

An earlier draft of this gap excluded firewalls and campus access as "roles SRL
cannot represent". Under the §0.1 scope that framing is wrong: **every role is
representable at the architecture level, and no role is representable at the
functional level — including the ones SRL nominally "supports".** SRL running a
spine's config still proves nothing about the N9K's buffers. So the gate is not
*which roles may enter the lab*; it is *what the report is permitted to claim*.

What is validated for every role, uniformly: is it in the path, does it hold
the addresses the design assigns it, does routing converge through it, does
traffic reroute when its peer link fails.

What is never claimed, per role class:

| role class | out of scope, name it explicitly |
|---|---|
| firewall | policy, stateful inspection, NAT, App-ID / User-ID, IPS |
| campus access | 802.1X, device-tracking, QoS, PoE |
| any switch/router | throughput, table scale, buffers, hardware behaviour |

So `campus-metro` (23 nodes, 21 campus + 2 PaloAlto) **is** a valid subject —
its L3 boundary placement, redundancy and reconvergence are exactly what the
lab is for. What it must not carry is an access-feature verdict.

Needs: a per-role `not_claimed: [...]` list on the artifact, emitted into the
report, same mechanism as `config_faithful` / `caveat` (§112 §9.2 — warnings
travel as data, not as prose).

**Out of scope under §0.1 (recorded so it is not re-litigated):** a firewall
*can* be given real policy — Batfish parses PAN-OS at FULL, and the
`kind_map.yaml` rationale for PAN being T0-only ("hier_config has no PAN-OS
parser, so slice/bucket/round-trip do not apply") is specific to the
change-validation path: pre-sales does not slice, renders its own layers, and
round-trip is line-based rather than hier_config-based, so a real
`paloalto_panos` node would in principle be buildable here. It is still not
built, because policy is functional validation. Approximating policy with an
SRL ACL is likewise rejected: a stateless ACL standing in for a stateful
firewall yields verdicts that are wrong in both directions, which is worse than
declining to answer.

### G7 — Layer semantics differ from the change-validation case

In a routed DC fabric L2 is largely vacuous (p2p /31s, no switching). The
predicate library is keyed on `(layer, family)` and §112 §8.1 already scopes
defaults to "layers the twin actually built" — but a design path needs an
explicit **"layer not applicable"** verdict so the bid narrative does not pad
an empty L2 section into evidence.

### G8 — No evidence class for a lab run in the provenance contract

dev_docs/107 requires every rendered sentence to carry a parseable
`[R/D/E/Doc/Spec/Calc:]` citation. A lab run has no class. Needs
`[Lab:<run_id>]` (or an `[E:]` sub-form) resolvable to the twin_id, image
digest, per-layer verdicts and the destroy receipt.

### G9 — Scale gate

`campus-metro` at 23 nodes against 8 cores is near the ceiling (§3.3). Needs a
node-count/core check up front that degrades to T0-only rather than attempting
a deploy that will thrash.

## 5. Applicability — say this in every report

Under §0.1 the axis is not *which designs qualify* but *what the lab is worth
for each*. Every design enters; the claim differs.

| design class | what the lab is worth |
|---|---|
| Routed DC fabric (underlay/overlay, eBGP, EVPN/VXLAN) | **highest** — the architecture *is* the routing design, so the lab validates the deliverable itself |
| WAN / routed core | high — path, redundancy, reconvergence |
| Campus (core/distribution/access) | **moderate** — L3 boundary, redundancy and reconvergence are validated; access features are not (G6) |
| Security architecture | **low** — path and segmentation shape only; policy belongs to T0 |
| Above ~25 nodes on the current host | T0 only (G9) |

Every artifact carries `config_faithful: False` plus the caveat (§112 §9.2) and
the per-role `not_claimed` list (G6). The customer is being shown a fabric
built from SR Linux, not from the product on the BOM — and that is sufficient,
because the claim is about the architecture, not the product.

## 6. T0 / T1 split for pre-sales

Different from the change-validation split (§112 §12.4), because the deliverable
is a sales artifact, not an engineering answer.

| question | Batfish (T0) | SRL lab (TS) |
|---|---|---|
| routing correctness, loops, ECMP | ✅ symbolic, all flows | ⚠️ only the packets you send |
| reachability matrix, policy plane | ✅ | ❌ |
| candidate A vs candidate B | ✅ differential snapshots | ❌ two full runs |
| does it actually converge | ⚠️ model fixpoint | ✅ real protocol implementation |
| reconvergence after a link failure | ❌ no time dimension | ✅ |
| **can it be demonstrated to a customer** | ❌ tables | ✅ **a running fabric** |
| cost | seconds, no images | minutes, host resources |

**Batfish is the gate; the SRL lab is the exhibit.** For correctness T0 is both
better and cheaper. T1's unique contribution is demonstrability plus the L1→L4
confirm sequence, which gives the bid document an evidence-backed narrative
spine ("L1 all links up / L3 addressing conflict-free / L4 underlay converged,
N sessions established / overlay routes exchanged").

## 8. Open questions

1. **Where does the renderer live** — `olav-presales` (owns the design) or
   `olav-ent/.../lab/twin` (owns the rendering profiles)? Leaning presales,
   consuming the twin as a library, so the twin stays domain-neutral.
2. ~~Per-vendor render targets (EOS + `ceos`) to remove the
   `config_faithful: False` caveat?~~ **CLOSED by §0.1 — no.** That buys
   functional fidelity at the price of per-vendor image supply, licensing and
   breakage. The caveat is acceptable because the claim is architectural.
3. ~~Should the customer-facing exhibit keep the lab running?~~ **CLOSED by
   §0.1 — no.** Always destroy, as `runner` already does. A kept lab is an
   owned asset with a TTL, an access path and a cost; a demo re-deploys, which
   at these node counts costs minutes.
4. **EVPN/VXLAN predicates.** Genuinely open, and the one place where more
   depth is still in scope: for an overlay design the architecture *is* the
   overlay, so "type-2/type-5 routes exchanged" is an architectural claim, not
   a functional one. `rulesets/srl.yaml` has L1-L4; this is a new predicate
   class.
5. **Is a link-failure drill (step 5) architectural or functional?** Ruling it
   architectural: reconvergence behaviour is a property of the topology and
   routing design, not of the product. Recorded here because it is the one
   step where the §0.1 line is genuinely close.
