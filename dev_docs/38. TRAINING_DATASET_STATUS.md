## 2. 可用的导出格式

```bash

```

### SFT（Supervised Fine-Tuning）

**格式：** OpenAI chat JSONL

```jsonl
{"messages": [
  {"role": "user", "content": "How many devices in NetBox?"},
  {"role": "assistant", "content": null, "tool_calls": [{"function": {"name": "api_request", "arguments": "{...}"}}]},
  {"role": "tool", "content": "[{\"name\": \"R1\", ...}]"},
  {"role": "assistant", "content": "6 devices in NetBox..."}
]}
```

**数据源：** `audit_messages`（7,650 条）
**质量：** ✅ 完整对话轮次（user → system → assistant → tool → assistant）
**缺口：** reasoning_block 事件为零 — thinking 内容未捕获

### Trajectory（Tool-Use 序列）

**格式：** JSONL，每行一个 step

```jsonl
{"run_id": "...", "step": 1, "tool": "execute_sql", "input": "SELECT ...", "output": "{...}", "status": "completed"}
{"run_id": "...", "step": 2, "tool": "api_request", "input": "{service: netbox, ...}", "output": "[...]", "status": "completed"}
```

**数据源：** `audit_tool_calls`（4,329 条）
**质量：** ✅ 工具名 + 输入 + 输出 + 状态
**缺口：** `tool_call_completed` events 为零（不影响导出 — tool_calls 表已有完整数据）

### ATIF（完整 Trace）

**数据源：** `audit_events`（15,187 条）
**质量：** ⚠️ 部分 — 有 routing_decision + llm_usage，缺 tool_call 时序事件
**缺口：** 同上

## 3. 已知缺口

### 3.1 reasoning_block 未捕获

**现象：** `audit_events` 中 `event_type='reasoning_block'` 为 0 条。

**原因：** 检测逻辑在 `on_llm_end` 中查找 `type="thinking"` 块，但当前 LLM 配置可能未启用 extended thinking，或返回格式不匹配。

**影响：** 无法导出 LLM 推理过程（thinking chain）。对标准 SFT 无影响（只需 input/output），但对 **thinking 模型微调**（如 Claude 3.5 extended thinking）有影响 — 缺少 reasoning 作为训练信号。

**修复：** 需要启用 Anthropic extended thinking 并验证 callback 检测逻辑。P3 优化。

### 3.2 tool_call_completed events 为零

**现象：** `audit_events` 中无 `tool_call_started` / `tool_call_completed` 事件。

**原因：** LangChain callback 的 `on_tool_start` / `on_tool_end` 写入了 `audit_tool_calls` 表（独立表），但没有同时写入 `audit_events` 表。

**影响：** 对 SFT/Trajectory 无影响（tool_calls 表完整）。对 ATIF 有影响（event 流缺少工具时序）。

**修复：** 在 callback 中同时写入 events 表。P3 优化。

### 3.3 HITL 事件稀少

**现象：** `hitl_requested` / `hitl_decision` 事件极少。

**原因：** 大部分测试使用 `--dangerously-skip-permissions` 跳过审批。

**影响：** 缺少人工批准/拒绝标签，无法构建 preference learning 数据集（RLHF/DPO）。

**修复：** 在正式使用（非测试）场景中不使用 `--dangerously-skip-permissions`，自然积累 HITL 数据。

### 3.4 stuck runs

**现象：** 13 个 runs 状态为 "running"（实际已终止）。

**影响：** 导出时被跳过（无 end_time）。可能包含有效的部分对话。

**修复：** `UPDATE audit_runs SET status='interrupted' WHERE status='running' AND start_time < now() - interval 1 hour`

## 4. Thinking 模型微调策略

### 4.1 正向训练数据（agent 做对了）

```jsonl
{"type": "positive",
 "think": "用户问 NetBox 设备 → 应用 api_request 而非 execute_sql",
 "action": {"tool": "api_request", "args": {"service": "netbox", "path": "/api/dcim/devices/"}},
 "result": "6 devices returned",
 "source": "run 6cb1177e (infra, completed)"}
```

**来源：** 460 个 completed runs — 每个都是一个"agent 做对了"的案例。

### 4.2 反向训练数据（agent 做错了 → 被纠正/拦截）

```jsonl
{"type": "negative",
 "think": "查 NetBox → execute_sql 查本地库",
 "action": {"tool": "execute_sql", "args": {"sql": "SELECT * FROM netops.devices"}},
 "result": "返回本地数据而非 NetBox 数据",
 "correction": "用户说 'in NetBox' → 应该用 api_request",
 "source": "run before quick routing fix"}
```

**来源：**
- 108 个 error runs — agent 推理错误导致失败
- hard_block 拦截记录 — agent 尝试写操作被阻止
- lab retry loops — 33 次重试链（长推理 + 修正）
- infra `run_shell` → `api_request` 修正（prompt 更新前后的 run 对比）

### 4.3 Preference Pairs（正负对比）

同一个任务，修复前后的 run 形成天然 preference pair：

| Claim | Rejected (before fix) | Chosen (after fix) |
|-------|----------------------|-------------------|
| C-NE-37 | quick 用 execute_sql 查 "NetBox devices" | quick 用 api_request |
| infra CLAB | infra 用 run_shell("containerlab list") | infra 用 api_request |
| devops 导出 | 脚本在 chat 输出 | 脚本写入 exports/scripts/ |

### 4.4 构造方法

```python
# 从审计数据构造 preference pairs
def build_preference_pairs():
    pairs = []

    # 找同一 agent + 相似 query 的 before/after runs
    for claim_id in ["C-NE-37", ...]:
        rejected_runs = get_runs(agent="quick", before_fix_date, status="completed")
        chosen_runs = get_runs(agent="quick", after_fix_date, status="completed")

        for r, c in zip(rejected_runs, chosen_runs):
            pairs.append({
                "chosen": extract_messages(c),
                "rejected": extract_messages(r),
                "reason": f"Fix for {claim_id}: correct tool routing"
            })

    return pairs
```
