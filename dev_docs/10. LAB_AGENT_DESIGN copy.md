## 0. Revision Context

v0.2/v0.3 drifted from the original intent.

The original design (`old_10. CLAB_CAB_AGENT_DESIGN.md`) specified:
- **Two tools only**: `clab_import_schema` + `clab_sandbox`
- Agent **discovers** endpoints by querying `clab_api_schema` table
- Agent **generates** HTTP calls dynamically — no hardcoded API adapters

What was built instead:
- `clab_client.py` with hardcoded `_OPS` dict (7 fixed methods)
- `api_registry` used only for sanity-checking hardcoded paths (not discovery)
- `run_e2e.py` — 10-step deterministic pipeline orchestrator
- Scenarios pre-written in YAML; assertions predefined before any lab exists

This document reasserts the original intent and extends it with the correct digital twin data path.

---

## 1. Core Design Principle

The lab agent is a **network engineer with a sandbox**, not a test runner.

A network engineer who wants to validate a change:
1. Looks at the current network state
2. Builds a small lab that approximates the relevant part
3. Pushes the configuration
4. Observes what happens
5. Adjusts if something breaks
6. Decides whether the change is safe

This means the agent needs **autonomy and tools**, not a scripted pipeline.

---

## 2. Agent Mental Model

```
change_intent (from operator or Ops sandbox)
        ↓
Lab Agent (autonomous ReAct loop)
        │
        ├─ Query production state (DuckDB semantic views)
        │
        ├─ Decide: which devices are in blast radius?
        │
        ├─ Discover ContainerLab capabilities (api_registry → schema query)
        │
        ├─ Deploy lab topology
        │
        ├─ Export OC snapshot → push via gNMI (digital twin baseline)
        │
        ├─ Apply proposed change
        │
        ├─ Observe convergence, collect state
        │
        ├─ Run assertions (agent decides what to check)
        │
        ├─ If something fails → debug, adjust, retry
        │
        └─ Emit CAB evidence artifact + verdict
```

The agent decides the topology, the assertions, and what to fix. Nothing is pre-scripted.

## 3. Tool Layer Design

### 3.1 Principle: No Hardcoded API Methods

The agent tool layer must NOT hardcode ContainerLab API endpoints.

Instead, three generic tools expose the `api_registry` infrastructure:

```
query_api_schema(api_name, filter?)      → list available operations + schemas
call_api(api_name, method, path, body?, path_params?)  → execute HTTP call
get_definition_schema(api_name, def_name)              → request body fields
```

When the agent needs to deploy a lab:
1. `query_api_schema("clab")` → discovers `POST /api/v1/labs`, sees `DeployRequest` schema
2. `get_definition_schema("clab", "DeployRequest")` → knows `topologyContent`, `reconfigure` are the fields
3. `call_api("clab", "POST", "/api/v1/labs", body={"topologyContent": ...})` → executes

**No Python code changes when ContainerLab upgrades its API.** The agent re-queries the schema.

### 3.2 Schema Bootstrap

`api_registry` is already built. Bootstrap is a one-time operation:

```python
# Load CLAB OpenAPI spec into DuckDB
python -m olav.core.api_registry load clab \
    http://192.168.100.12:8080/swagger/doc.json \
    --base-url http://192.168.100.12:8080
```

After this, `~/.olav/olav_registry.duckdb` contains:
- `api_registry.operations` — all endpoints (method, path, summary, request/response refs)
- `api_registry.definitions` — all schema definitions (field names + types)
- `api_registry.schemas` — raw spec + metadata

### 3.3 Tool Signatures

```python
# tools/query_api_schema.py
def query_api_schema(
    api_name: str,
    filter: str | None = None,   # keyword filter on summary/path
) -> list[dict]:
    """
    Returns list of available operations for api_name.
    Each entry: {method, path, summary, request_body_def, response_200_def}
    Use this before calling an API to discover what endpoints exist.
    """

# tools/get_definition_schema.py
def get_definition_schema(
    api_name: str,
    def_name: str,
) -> dict[str, str]:
    """
    Returns field_name → type mapping for a schema definition.
    Use this to understand what fields to include in a request body.
    """

# tools/call_api.py
def call_api(
    api_name: str,
    method: str,
    path: str,
    body: dict | None = None,
    path_params: dict | None = None,   # e.g., {"labName": "cab-r1-xyz"}
    timeout: int = 300,
) -> dict:
    """
    Execute an HTTP call against api_name using base_url from api_registry.
    Handles auth token injection from config.
    Returns parsed JSON response or raises on non-2xx.
    """
```

## 4. Digital Twin Data Path

### 4.1 Design

SR Linux is the universal digital twin target.

The data path from production snapshot to lab baseline:

```
schema_catalog
    (所有命令 → OC path 映射，platform-aware)
        ↓ 发现该设备有哪些OC数据
parsed_outputs
    (device × command 的原始JSON)
        ↓ apply_oc_mapping_cached()
完整OC JSON per device
    (openconfig-interfaces, openconfig-bgp, openconfig-network-instance, ...)
        ↓ 按OC模块分组
gNMI Set → SRL nodes in ContainerLab
        ↓
baseline state established in lab
```

**关键原则：** 导出哪些协议由 `schema_catalog` 动态决定，不硬编码协议列表。凡是数据库里有OC路径映射的数据，全部导出。

### 4.2 OC数据发现机制 — schema_catalog驱动

`schema_catalog` 是主注册表，记录每个 `(platform, command)` 下每个字段的OC路径映射：

```sql
-- 1. 发现目标设备有哪些命令已采集
SELECT DISTINCT command, platform
FROM parsed_outputs
WHERE device_name = ?

-- 2. 查哪些命令有OC路径映射
SELECT source_name, fields
FROM schema_catalog
WHERE platform = ? AND source_name IN (采集到的命令列表)

-- 3. fields是JSON数组，每项含 {name, openconfig_path}
-- openconfig_path 非空 = 有OC映射
-- _unmapped / olav: 前缀 = 私有字段，跳过
```

`apply_oc_mapping_cached()` 接收 `parsed_data` + `field_map`，输出按OC模块命名空间分组的嵌套结构：

```python
{
  "openconfig-interfaces": {"interfaces": {"interface": [...]}},
  "openconfig-bgp":        {"bgp": {"global": {...}, "neighbors": {...}}},
  "openconfig-network-instance": {"network-instances": {...}},
  # ...按数据库实际收录内容，不预设协议列表
  "_unmapped": {"vendor_field": "value"}   # 无OC映射字段，记录但不推送
}
```

覆盖范围由现网采集了什么决定，不由代码硬编码决定：

| OC模块 | semantic view | 典型命令 |
|--------|--------------|---------|
| openconfig-interfaces | v_interfaces | show interfaces, show ip interface |
| openconfig-bgp | v_bgp_neighbors | show bgp summary, show ip bgp |
| openconfig-network-instance (OSPF) | v_ospf_neighbors | show ospf neighbor |
| openconfig-network-instance (ISIS) | v_isis_adjacencies | show isis neighbors |
| openconfig-vlan / EVPN | v_evpn_instances | show evpn instance |
| openconfig-lldp | (from LLDP collect) | show lldp neighbors |
| … | 按schema_catalog扩展 | 无需改代码 |

### 4.3 配置推送机制 — 唯一选择：gNMI Set per path

SRL支持三种配置方式：startup-config文件注入、gNMI Set、exec API + sr_cli命令。

**只使用gNMI Set**，原因：

| 需求 | startup-config | gNMI Set | exec + sr_cli |
|------|---------------|----------|---------------|
| agent逐步观察每一步结果 | 否（整体启动） | **是** | 是（文本） |
| 精确定位哪个字段失败 | 否 | **是（per-path structured error）** | 需要解析文本 |
| 只修复失败字段，不影响其他 | 否 | **是** | 粒度粗 |
| baseline和change delta用同一机制 | 否 | **是** | 是 |
| OC JSON直推无需格式转换 | 否（需SRL native JSON） | **是（json_ietf）** | 否（需CLI翻译） |

agent需要在推baseline、推change delta、调试错误这整个过程中有一致的结构化反馈，gNMI Set是唯一满足所有要求的机制。startup-config是一次性烧录，不适合需要自主修复的agent。

### 4.4 非标准字段处理

`_unmapped` 字段无OC路径，无法通过gNMI Set推送。

`references/srl-cli-syntax.md` 告诉agent：
- 哪些SRL-native路径可以接受非OC配置
- 已知值格式差异（如 `admin-status: UP` → `enabled: true`）
- 哪些字段在数字孪生中可以安全忽略

当gNMI push失败：
1. Agent读取错误（path + reason）
2. 查 `srl-cli-syntax.md` 找对应语法
3. 修正字段重试 — 不是pipeline failure

### 4.5 OC导出工具


## 5. gNMI网络连通性

### 5.1 网络拓扑

```
Agent主机 (OLAV运行处，如 10.0.1.20)
    │
    │  静态路由: ip route add <docker_bridge_subnet> via <clab_server_ip>
    ↓
CLAB服务器 (如 10.0.1.50)
    │
    │  Docker bridge (内部，如 172.20.20.0/24 或 192.168.100.0/24)
    ↓
Lab节点管理IP (如 172.20.20.2, 172.20.20.3, ...)
    port 57400 → SRL gNMI
```

Docker bridge子网由CLAB创建，只在CLAB服务器本机可见。Agent主机需要一条静态路由才能直达lab节点的gNMI端口。

### 5.2 Config中的必填字段

`~/.olav/config/skills/clab.yaml`（或项目级config）中需要声明：

```yaml
clab:
  # CLAB REST API
  api_server: "http://10.0.1.50:8080"

  # gNMI连通性
  gnmi:
    port: 57400                        # SRL默认gNMI端口
    encoding: "json_ietf"
    credentials:
      username: "admin"
      password: "NokiaSrl1!"           # SRL容器默认密码

  # Docker bridge网络（用于生成静态路由命令）
  network:
    clab_server_ip: "10.0.1.50"       # CLAB服务器在agent主机可达的IP
    docker_bridge_subnet: "172.20.20.0/24"  # 从CLAB服务器获取，见用户指南
    agent_outbound_iface: "eth0"       # Agent主机发往CLAB的出口网卡

  # 节点管理IP分配（CLAB分配，与docker_bridge_subnet一致）
  mgmt:
    subnet: "172.20.20.0/24"
    start_offset: 2                    # 第一个lab节点的主机位
```

`docker_bridge_subnet` 是唯一需要从CLAB服务器手动获取的值，获取方法见用户指南 `docs/netops/07_LAB_SETUP.md`。

### 5.3 路由验证工具

```python
# tools/check_lab_connectivity.py
def check_lab_connectivity(
    node_mgmt_ips: list[str],
    gnmi_port: int = 57400,
) -> dict[str, bool]:
    """
    gNMI操作前验证每个节点端口可达。
    不可达时从config读取docker_bridge_subnet和clab_server_ip，
    输出具体的ip route add命令供操作员执行。
    """
```

Agent在每次lab session开始时调用此工具作为前置检查。不可达不报错退出，而是输出路由命令让操作员确认后继续。

## 5. Agent Autonomy — What "Sandbox" Means

The ContainerLab lab is the sandbox. The agent is free to:

- Deploy any topology it decides is appropriate for the change
- Push configuration in any order
- Re-run gNMI pushes if errors occur
- Execute diagnostic commands in the lab (`call_api` exec endpoint)
- Destroy and redeploy if the lab state becomes unrecoverable
- Decide what assertions to run based on what it observes
- Keep the lab running longer if it needs to investigate an anomaly

What the agent must NOT do:
- Write configuration to production devices
- Use the production DuckDB as a write target
- Leave labs running after the validation is complete (always destroy, even on failure)

## 6. Error Recovery — Agent, Not Pipeline

Current v0.2 behavior: any step failure → pipeline stops.

Correct behavior: agent observes the error and decides what to do.

**Example: gNMI push failure**
```
Agent pushes OC payload to r1.
gNMI returns error on path openconfig-interfaces:interfaces/interface[name=GigabitEthernet0/1]/config/name
Agent reads error: "interface name format invalid for SRL"
Agent looks up srl-cli-syntax.md: interface names must be ethernet-1/N format
Agent corrects iface_map: GigabitEthernet0/1 → ethernet-1/1
Agent retries gNMI push with corrected path
Success.
```

**Example: BGP not converging**
```
Agent pushes BGP config, waits 60s, BGP session still not Established.
Agent runs: call_api("clab", "POST", "/api/v1/labs/{labName}/exec",
                      body={"command": "show network-instance default protocols bgp neighbor"})
Agent sees: neighbor IP is wrong (10.0.0.2 vs actual 10.0.0.6)
Agent traces: OC payload had wrong peer-ip from v_bgp_neighbors
Agent re-queries: execute_sql("SELECT * FROM v_bgp_neighbors WHERE device='r1'")
Agent finds correct IP, pushes corrected BGP config
BGP converges.
```

This is how a network engineer works. Not: `step_7_bgp_converge() → FAILED → exit(1)`.

## 7. Reference Documents as Agent Context

The `references/` directory is the agent's domain knowledge, not Python configuration.

| File | Purpose |
|------|---------|
| `srl-cli-syntax.md` | SRL gNMI paths + equivalent CLI syntax for non-OC fields |
| `api-behaviors.md` | Documented ContainerLab API quirks (NodeFilter bug, exec format, cEOS issues) |

These files are passed as static context to the agent system prompt. The agent reads them like documentation, not like config files parsed by Python.

When a new protocol needs to be supported, the operator updates `srl-cli-syntax.md`. No code changes required.

## 8. Scenario / Assertion Design

v0.2 pre-defines assertions in YAML before the lab exists.

The correct model: **agent defines assertions based on what it observes**.

The agent receives a `change_intent`:
```
"Validate that moving R1's BGP policy to reject prefixes longer than /24
 does not drop any currently-active prefixes toward AS65002."
```

The agent then:
1. Queries current state to understand what prefixes are active toward AS65002
2. Builds the lab baseline with those prefixes present
3. Applies the policy change
4. Checks: are the same prefixes still present? Any that were previously accepted now dropped?

The assertions emerge from the agent's understanding of the change intent and the observed baseline. They are not written in a YAML file before the lab exists.

## 9. Relationship to Ops Sandbox

The lab agent is downstream of the Ops NetworkX sandbox.

```
Ops sandbox (fast, graph-based):
    - Investigates production state
    - Proposes candidate change plan
    - Estimates blast radius
    - Flags: requires_lab_validation = true

Lab Agent (slow, emulation-based):
    - Receives change intent + blast radius estimate from sandbox
    - Builds lab using production snapshot data
    - Validates in isolation
    - Returns CAB evidence artifact
```

The lab agent does not replace sandbox reasoning. It is the evidence layer that makes CAB approval defensible.

## 10. Implementation Transition

Current `scripts/` in `.olav/workspace/ops/lab/` are the v0.2 implementation.

The transition path:

### Phase A — Tools Layer (highest priority)

Replace `clab_client.py` hardcoded methods with three generic tools:
- `query_api_schema.py`
- `call_api.py`
- `get_definition_schema.py`

These wrap `api_registry` read queries + httpx calls. ~150 lines total.

### Phase B — gNMI Push Tool

Add `push_gnmi_config.py` tool using `pygnmi` or `grpc` directly against SRL port 57400.

Replace exec-API-based config push in `configure_device.py`.

### Phase C — Agent System Prompt

Rewrite `prompts/system.md` to:
- Give the agent the three API tools + gNMI tool
- Provide `srl-cli-syntax.md` + `api-behaviors.md` as static context
- Remove the 10-step pipeline description
- Replace with the network-engineer mental model: intent → discover → build → push → observe → fix → conclude

### Phase D — Remove Pipeline Orchestrator

`run_e2e.py` is a pipeline orchestrator that belongs in a CI/CD tool, not in an agent skill.

Once the agent has proper tools, `run_e2e.py` is replaced by the agent's own ReAct loop.

The YAML scenario files can remain as examples of how to invoke the agent, not as execution scripts.

## 14. What This Design Is Not

The lab agent is not:
- A test runner (no YAML scenario scripts)
- A production change executor (never writes to production)
- A general troubleshooting assistant (use Ops sandbox for that)
- A replacement for human judgment (verdict is a recommendation)

The correct OLAV workflow:
1. Ops sandbox: investigate + propose
2. Lab agent: validate in isolation + emit evidence
3. Human network engineer: review evidence + execute
