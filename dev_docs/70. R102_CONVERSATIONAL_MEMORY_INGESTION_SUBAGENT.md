## Why now

OLAV's memory architecture has three load paths today:

1. **L1 implicit growth** — `OperationalEventCapturePlugin` writes successful tool calls automatically.  Free, but limited to "what already happened."
2. **L2 distillation** — `pattern_extractor` summarises L1 into expert_knowledge.  On-demand LLM step.
3. **Declarative YAML** — user authors `*.guide.yaml`, runs `olav kb import-guides`.  Powerful but requires learning the schema.

What's missing is the **conversational ingestion path** — the user telling OLAV in natural language "remember this rule for our team", uploading a runbook, or pointing at a topology file, and having OLAV figure out the structure.

R102 closes that gap.  It's the third leg of the user-experience triangle:

```
implicit growth (L1) ── observation-driven, automatic
declarative YAML    ── version-controlled, team-shared, schema-bound
NL ingestion (R102) ── conversational, exploratory, immediate
```

## Why a sub-agent (not another CLI command)

The first design instinct was `olav kb add "<natural language>"`.  Rejected in favour of a sub-agent for six reasons:

| dimension | CLI command | sub-agent |
|---|---|---|
| Discoverability | requires `--help` | natural delegation; user just talks |
| Multi-step refinement | re-run command | continue chat: "no, tenant should be X, retry" |
| HITL confirmation | `--confirm` flag | natural "OK save it" reply |
| Multi-input mixing | multiple commands | "add this rule + this runbook + this diagram" in one sentence |
| Consistency with OLAV's agentic UX | command-line | agentic chat (matches Ch3-Ch7) |
| Future R100/Tier 2 + L3 extensibility | flag accumulation | sub-agent internals route freely |

A sub-agent is the natural completion of OLAV's pattern.  CLI commands stay for power users + scripting; conversational ingestion becomes the demo / customer-onboarding path.

### Tool inheritance

Per the existing loader pattern, `memory_curator` automatically inherits core platform tools (`recall_memory`, `read_file`, `format_and_export`, `search_logs`) via `_load_orchestrator_tools` step ①.  The new tool `commit_to_memory` lives in the sub-agent's own `tools/` dir.

### `commit_to_memory` tool signature

```python
@tool
def commit_to_memory(
    intent: str,                           # short identifier, snake_case
    keywords: list[str],                   # AutoRecall match hints (en + zh)
    body: str,                             # the actual rule / wisdom in prose
    *,
    agent: str = "core",                   # who owns this guide
    scope: str = "global",                 # "global" | agent name | "shared:<domain>"
    category: str = "usage_guide",         # usage_guide | document | topology
    chunks: list[str] | None = None,       # for long-doc dual-track ingestion
    confirm: bool = True,                  # if False, skip HITL — debug only
) -> dict:
    """Write a memory guide to disk + prime into LanceDB in one transaction.
    
    Returns:
        {
          "file": "<absolute path of guide.yaml>",
          "memory_ids": ["guide_<intent>", "doc_<chunk_hash_1>", ...],
          "primed": true,
          "agent_visibility": ["core", "ops", ...]   # who AutoRecall surfaces it to
        }
    """
```

Internally calls `prime_guides_from_dir` (existing infra) plus, for `category=document`, the existing `LanceDBStore.kb_import` chunking path.

### Sub-agent behaviour decision tree

System prompt (`memory_curator/prompts/system.md`):

```
You are the OLAV memory curator.  When the user wants to teach OLAV
something — a rule, a runbook section, a topology, a convention —
you guide it into the right memory category.

Decision tree (apply in order):

1. SHORT NATURAL LANGUAGE (≤ 500 tokens):
   → synthesise a single `usage_guide` entry
   → extract intent (snake_case), keywords (en + zh), body
   → call commit_to_memory(category="usage_guide", ...)

2. FILE PATH MENTIONED:
   → read_file first
   → measure length:
     - short (≤ 500 tokens) → handle as case 1
     - long (> 1500 tokens) → propose dual-track:
       a. summarise → 1× usage_guide (executive overview + section index)
       b. chunk → N× document entries (~500 tokens each)
   → confirm dual-track approach with user before commit

3. MERMAID / DOT / SVG-XML TEXT (recognise by header):
   → category="topology"; body = full source text
   → metadata.media_path = original file path if any

4. IMAGE / PNG / BINARY:
   → R100 Tier 2 — NOT YET SUPPORTED.  Tell user:
     "Image memory is on the roadmap.  For now, describe the
     image in words and we'll store the description."

ALWAYS BEFORE COMMIT:

  a. recall_memory(query=<extracted intent>, scope=<target>):
     check whether a similar entry already exists.  If yes →
     OFFER to update vs add a new sibling.

  b. Show the user the EXACT yaml that will be written.

  c. Wait for explicit confirmation ("OK", "yes", "save", "好",
     "可以", "入库") before calling commit_to_memory.

AFTER COMMIT:

  * Tell the user the file path written.
  * Tell the user which agents AutoRecall will surface it to.
  * Suggest a test query: "Verify with: olav --agent <agent>
    '<sample query that should hit this memory>'"
```

### Long-doc dual-track ingestion

For docs > ~1500 tokens (a typical SOP or runbook section):

```
> User: 把 /home/me/runbooks/netbox_sop.md 加进记忆

memory_curator:
🔧 read_file(path='/home/me/runbooks/netbox_sop.md')
  → 14,200 tokens, 38 sections

  This document is too long for a single guide.  I'll propose
  dual-track ingestion:

    a. ONE summary guide (intent='runbook_netbox_sop'):
       - executive overview (~300 tokens)
       - section index with key takeaway per section
       - AutoRecall surfaces this on netbox / sop / runbook
         keywords (high-precision recall)

    b. THIRTY-EIGHT document chunks:
       - one per section, full text
       - searchable via deep semantic similarity (low-precision
         recall when user wants exact text)

  Both committed in one transaction.  Total ~12 KB stored, ~50 KB
  vector index.  Continue?  [y / N]

> User: y

memory_curator:
🔧 commit_to_memory(category='usage_guide', intent='runbook_netbox_sop',
                    body=<summary>, ...)
🔧 commit_to_memory(category='document', chunks=[...38 chunks...])

  ✓ Summary guide + 38 document chunks committed.

  Test recall:
    "what does our SOP say about NetBox cable assignments?"
    → AutoRecall should surface section 14 chunk + summary index.
```

## Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| LLM hallucinates rules during synthesis → poisons team memory | High | HARD requirement: HITL confirmation before commit.  Show exact YAML, wait for explicit "yes".  Never bypass except in `confirm=False` debug. |
| Local 27B can't reliably extract intent / keywords | Medium | Stable prompt with strict structured output (R100/S2 strict-schema lessons apply here too).  Cloud LLM fallback for synthesis step (similar to L2 pattern_extractor pattern). |
| Long-doc summarisation drops critical constraints | Medium | Two-stage prompt: first extract "constraints / must-do / must-not-do", second extract "narrative summary".  Constraints get higher AutoRecall weight via dedicated keywords. |
| Dedup logic misses near-duplicates with different keywords | Medium | recall_memory uses both vector (semantic) + keyword.  Show top-3 nearest entries to user; let them decide. |
| Sub-agent ReAct loop hits ctx limit on long docs | Low | Read file once, summarise in chunks, store before re-reading.  Same `OLAV_EMBED_MAX_CHARS=6000` truncation applies to recall too. |
| User doesn't realise `agent` field affects who sees the memory | Medium | Sub-agent ALWAYS shows "AutoRecall will surface this to: <agent list>" before commit.  Suggest test query that should hit it. |

## What this DOESN'T solve

* **Image memory (R100 Tier 2)** — the sub-agent gracefully tells the user "describe in words instead" until Tier 2 ships.  No new schema work in R102.
* **L3 cross-team aggregation** — when a user adds a rule, it's local to their workspace.  Team-wide diffusion is a separate enterprise concern (see olav-ent roadmap).
* **Automatic forgetting / TTL** — memories persist forever unless manually removed.  R103 candidate.
* **Native multilingual translation** — sub-agent passes through whatever language the user uses; doesn't auto-translate to a canonical form.  Acceptable trade-off for first cut.

## Decision log

* **Sub-agent over CLI command** — full reasoning above; UX win > maintenance cost.
* **HARD HITL requirement** — memory becomes team ground truth; LLM hallucination at this layer is worse than agent runtime errors.
* **Dual-track for long docs** — summary guide for high-precision recall + chunks for deep search.  Single-mode (one or the other) is insufficient: pure chunks give low recall on "what's the high-level rule"; pure summary loses retrievable detail.
* **Defer image ingestion** — Tier 2 schema migration is its own design; R102 ships text + topology only, with clear "this is roadmap" message for image.
* **Reuse `prime_guides_from_dir` + `LanceDBStore.kb_import`** — don't build new ingest paths.  The sub-agent is a UX wrapper; the storage path is shared with `olav kb import-guides`.
