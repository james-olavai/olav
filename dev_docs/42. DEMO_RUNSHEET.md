## LLM Backends — Cloud vs Local Ollama vs Local llama.cpp (recommended)

OLAV runs against any OpenAI-compatible endpoint via
`.olav/config/api.json`. Three tested configurations:

| | Cloud (OpenRouter) | Local Ollama | **Local llama.cpp (recommended)** |
|---|---|---|---|
| LLM | `x-ai/grok-4.1-fast` | `qwen3.6:27b` | `qwen3.6-27b-dense` (Q5_K_M, dense not MoE) |
| Embedding | `openai/text-embedding-3-small` (1536 dim) | `nomic-embed-text-v2-moe:latest` (768 dim) | `qwen3-vl-embedding-2b` (2048 dim) |
| Reranker | n/a | n/a (Ollama can't serve cross-encoder) | `qwen3-reranker-0.6b` via `--reranking` |
| api_key | `sk-or-v1-...` (real) | `"ollama"` (sentinel) | `"any"` (no auth) |
| base_url | `https://openrouter.ai/api/v1` | `http://<gpu>:11434/v1` | `http://<gpu>:11433/v1` |
| Per-call latency | 5-15 s | 30-50 s for 27B | 8-12 s for 27B (q8_0 KV + flash-attn) |
| End-to-end Ch8 demo | ✅ | ⚠️ partial | ✅ verified (R100 fixes required) |

**Local llama.cpp prereqs (verified end-to-end on demo7, 2026-04-29)**:
* docker-compose stack with three llama-server containers (router on
  :11433 with `--models-max 3 --models-autoload`, or three explicit
  ports 11433/11435/11436 for LLM/embed/rerank)
* LLM container: `--ctx-size 65536 --parallel 1 --cache-type-k q8_0
  --cache-type-v q8_0 --flash-attn on -ngl 99`
* Embed container: `--embedding --pooling mean --batch-size 4096
  --ubatch-size 1024 --ctx-size 8192 -ngl 99`
* Reranker container: `--reranking --ctx-size 2048 -ngl 99`
* OLAV ≥ commit `42ff7db` (R100/S2-S4 — strict tool schema, quote-strip
  defense, FilesystemPermission deny on virtual-FS writes, embed input
  truncation).  These are NOT optional for adherence on local 27B
  models — without them, write-class prompts fail silently.
* `.olav/config/api.json` `reranker` block: `kind="llama_cpp"`,
  `enabled=true`, `base_url=http://<gpu>:11433`

For interactive multi-step agent flows the local-llama.cpp path lands
production-quality outputs (3.9 KB vendor-aware bash backup script
written by qwen3.6-27b-dense in ~5 turns end-to-end).

Cloud (OpenRouter) is the simplest path for first-time evaluation —
no GPU box, no docker-compose tuning.  Local llama.cpp is the
production deploy story — open-source, on-prem, full audit trail,
and the only path that supports cross-encoder rerank (Ollama's
`/api/embeddings` doesn't preserve the rerank head; see dev_docs/67).

### Step 4: Configure LLM API key

**方法 A：从开发环境拷贝配置**（推荐，保留所有设置）

```bash
# 从开发环境拷贝完整 api.json（含 LLM key、model、embedding 等）
cp /path/to/dev-env/.olav/config/api.json .olav/config/api.json
```

**方法 B：手动编辑**

```bash
nano .olav/config/api.json
```

必填字段：
```json
{
  "shared": {
    "api_key": "sk-or-v1-your-openrouter-key"
  },
  "llm": {
    "model": "x-ai/grok-4.1-fast",
    "base_url": "https://openrouter.ai/api/v1"
  },
  "embedding": {
    "mode": "local"
  },
  "auth": {
    "mode": "token"
  },
  "security": {
    "allowed_cidrs": ["192.168.100.0/24", "127.0.0.1/32"]
  }
}
```

> **配置说明：**
>
> | 字段 | 说明 | 默认值 |
> |---|---|---|
> | `shared.api_key` | LLM API key（OpenRouter/OpenAI/Anthropic） | 空（必填） |
> | `llm.model` | 模型名 | `gpt-4o` |
> | `llm.base_url` | API 端点（OpenRouter 用 `https://openrouter.ai/api/v1`） | OpenAI 默认 |
> | `embedding.mode` | `"local"`（本地 HuggingFace）或 `"api"`（OpenAI/OpenRouter embedding） | `"local"` |
> | `auth.mode` | `"none"`（无认证）或 `"token"`（token 登录） | `"none"` |
> | `security.allowed_cidrs` | 允许访问 Web API 的 IP 段（空=放行所有） | 空（全放行） |
>
> **注意：**
> - `embedding.mode=api` 通过 OpenRouter 使用时，`embedding.api.model` 需加 `openai/` 前缀（如 `openai/text-embedding-3-small`），`embedding.api.base_url` 设为 `https://openrouter.ai/api/v1`。`mode=local` 则用本地 HuggingFace 模型（默认 `BAAI/bge-small-zh-v1.5`），无需外部依赖
> - `security.allowed_cidrs` 不配则所有 IP 可访问；`127.0.0.1` 和 `::1` 始终放行；`/health` 端点不受限制
> - `auth.mode=token` 时浏览器访问需要 token（`cat ~/.olav/token`）；`auth.mode=none` 无需登录

## Chapter 5: Lab — Validate the CAB Spec from Chapter 4

**Goal:** Take the CAB Implementation Spec produced in Chapter 4
(``exports/reports/cab_r1_r4_ebgp.md``) and run it in a digital
twin lab to validate convergence before production deployment.

**Architectural rule (encoded in `ops/lab/SKILL.md`):**

> The change plan is the contract — implement exactly what it says.
> SKIP DB query — change plan provides all needed IPs/ASNs directly.
> CAB is a validation gate, NOT a fix-it loop.

ops-lab does NOT re-discover topology from the snapshot DB; if the
spec is missing fields, the right answer is "FAIL: spec incomplete",
not "fall back to DB query".

### Pre-flight: CLAB API 必须可达

```bash
curl -s http://192.168.100.12:8080/login \
  -d '{"username":"olav","password":"olav123"}' \
  -H 'Content-Type: application/json' | head -3
# Expected: {"token":"eyJ..."}
```

> **如果端口 8080 连接被拒 / `clab-api-server` 容器 Exited:**
>
> CLAB API 容器靠 `/tmp/shadow_clab` 绑定挂载 `/etc/shadow` 做 PAM 认证。`/tmp` 在主机重启后清空，若 systemd-tmpfiles 没重建该文件，容器启动会报 `mount "/tmp/shadow_clab" to rootfs at "/etc/shadow": not a directory`。
>
> ```bash
> # 在 CLAB 主机（192.168.100.12）上执行:
> ssh olav@192.168.100.12
> rmdir /tmp/shadow_clab 2>/dev/null
> sudo cp /etc/shadow /tmp/shadow_clab && sudo chmod 644 /tmp/shadow_clab
> docker start clab-api-server
> # 固化（防止下次重启丢失）:
> echo 'C /tmp/shadow_clab 0644 root root - /etc/shadow' | sudo tee /etc/tmpfiles.d/clab-api.conf
> ```

### Demo

```bash
# Single command — feeds the spec from Chapter 4 to ops-lab.
olav --agent ops \
    "Validate the CAB Implementation Spec at exports/reports/cab_r1_r4_ebgp.md
     in a digital twin lab.  Deploy SRL containers for R1 and R4, push the
     spec's config_lines verbatim, exec_on_node to verify BGP Established +
     prefix exchange, render the CAB report (PASS/FAIL with evidence),
     then destroy_lab."
```

Expected tool sequence (deterministic, ~5-8 min):

```

save_lab_config(lab='r1-r4-ebgp', node='r1', lines=[...]) # spec.r1.config
save_lab_config(lab='r1-r4-ebgp', node='r4', lines=[...]) # spec.r4.config
deploy_and_push_lab(lab='r1-r4-ebgp', yaml_content=...)   # deploy + push
exec_on_node(node='clab-r1-r4-ebgp-r1',
             command="bash -c 'sr_cli show network-instance default protocols bgp neighbor 2>&1'")
exec_on_node(node='clab-r1-r4-ebgp-r4', command="...")    # verify both sides
format_and_export(data=<cab_md>, format='md',
                  subdir='cab', filename='cab_r1_r4_ebgp')
destroy_lab(lab_name='r1-r4-ebgp')                        # always cleanup
```

Expected: SRL deploy → config push → BGP ESTABLISHED → CAB PASS →
`exports/cab/cab_r1_r4_ebgp.md` saved → containers torn down.

**⏱** ~5-8min total.

### What "good" looks like

* The first tool call is `read_file` on the Chapter 4 spec — NOT
  `execute_sql`.  If you see `execute_sql` calls, the agent is
  ignoring the spec and re-discovering data; treat as test failure.
* `exec_on_node` is called at least once per side of the BGP session.
  Without that, "PASS" is a hallucination.
* `destroy_lab` runs even on failure — leaked containers indicate a
  control-flow bug.

## Chapter 5b: TCF — Structured Change Contract + LLM-Rendered CAB Report (R94)

**Goal:** Run the structured TCF (Test Case File) pipeline end-to-end:
sim emits a Pydantic-validated YAML contract with real Junos+IOS prod
CLI, lab pushes SRL twin config to CLAB, deterministic + LLM cross-
verification produces step verdicts, and a writer-style LLM call
renders the final CAB markdown report — all from one self-contained
artifact.

**Why this exists alongside Chapter 5:** the free-form markdown spec
in Chapter 5 is brittle (lab can't reliably translate vendor CLI). The
TCF contract is the structured replacement: one YAML file is the
canonical record from sim → lab → prod-deploy → archive. See
`dev_docs/65` for design.

### Pre-flight

* CLAB API reachable (same as Chapter 5)
* **Netops DB populated** — `generate_clab_topology` (R88-A, called in
  stage 3) reads L2 link data from `.olav/databases/main.duckdb`.
  Chapter 2 (`/netops_init`) must have run first.  On a fresh demo
  without device access, copy a known-good DB from a populated
  install: `cp /path/to/dev/.olav/databases/main.duckdb .olav/databases/`
* Run from a working dir that has `.olav/config/api.json` (LLM key for
  stage 11c) and `.olav/workspace/ops/lab/config/config.json` (CLAB
  PAM creds).  The `tests/integration/e2e_tcf_in_vivo.py` script is
  cwd-relative — it writes to `<cwd>/exports/cab/tcf_e2e_r1r4/`.

### Demo (automated, ~95s)

```bash
# Single command runs all 12 stages: sim → lab → diff → LLM review → destroy
.venv/bin/python tests/integration/e2e_tcf_in_vivo.py

# Expected stage sequence:
#   ① derive_prod_cli_from_tcf — generates real Junos R1 (12 lines) + IOS R4 (13 lines)
#   ② tcf_emit_from_sim         — writes spec.tcf.yaml
#   ③ tcf_load_for_lab          — derives r88/r89 args
#   ④ generate_clab_topology    — CLAB YAML with links
#   ⑤ generate_srl_lab_config   — 22-line SRL skeleton per node
#   ⑥ save_lab_config           — write dropbox
#   ⑦ deploy_and_push_lab       — REAL CLAB DEPLOY (~40s)
#   ⑧ exec_on_node              — BGP Established
#   ⑨ generate_srl_rollback_config
#   ⑩ push_node_config (rollback) + verify
#   ⑪a tcf_record_lab_run round 1 — atomic lab-side write
#   ⑪b tcf_diff_spec_vs_lab       — deterministic structural verdicts (3)
#   ⑪c review_paired_blocks      — LLM semantic verdicts (4)
#   ⑫ destroy_lab               — cleanup (always)

# Artefact: exports/cab/tcf_e2e_r1r4/spec.tcf.yaml — 9.5 KB, contains:
#   - Sim's prod-form CLI (R1 Junos 12 lines, R4 IOS 13 lines, zero ellipses)
#   - Sim's prod-form rollback (3 lines + 3 lines)
#   - Lab's SRL twin CLI (22+22 implementation_lab, 7+7 rollback_lab)
#   - 7 step_verdicts: 3 deterministic (post_check + 2 tvt) + 4 LLM-semantic
#     (each with field-level reason citing AS / neighbor IP / policy)
```

### Render the TCF as a CAB markdown report (writer pattern)

```bash
# Pure LLM rendering — no SQL, no DB query. Writer reads the YAML and
# writes prose with embedded mermaid for the change subgraph.
.venv/bin/python -c "
from pathlib import Path
from olav.core.llm import get_chat_model
spec = Path('exports/cab/tcf_e2e_r1r4/spec.tcf.yaml')
out_md = spec.with_suffix('.md')
prompt = f'''You are a CAB change-document writer. Render this TCF YAML as a
markdown CAB report with sections: Change Summary / Topology Sketch (mermaid) /
Implementation Plan / Rollback Plan / Verification (TVT) / Lab Evidence /
Cross-Verification (Step Verdicts) / CAB Decision Brief. Use ONLY YAML facts;
mark missing fields as (not specified). Highlight info/rejected verdicts.

\`\`\`yaml
{spec.read_text()}
\`\`\`'''
md = get_chat_model(temperature=0.1).invoke(prompt).content
out_md.write_text(md)
print(f'wrote {len(md)} chars → {out_md}')
"

# Expected: ~3.9 KB markdown with:
#   - Change Summary (change_id, intent, devices)
#   - mermaid graph LR R1[R1 AS65000] -->|eBGP 172.16.99.0/30| R4[R4 AS65001]
#   - Per-vendor fenced code blocks (juniper_junos / cisco_ios)
#   - TVT table (test_id / expected / actual_lab / status)
#   - Step Verdicts table with **bold** on info verdicts
#   - CAB Decision Brief flagging open items for approver
```

### What "good" looks like

* `exports/cab/tcf_e2e_r1r4/spec.tcf.yaml` contains zero `...` ellipses
  in `implementation[*].cli` — sim wrote real deployable Junos+IOS CLI
* `lab.step_verdicts` has 7 entries; agent verdicts include field-level
  comparisons ("AS 65000/65001, neighbor 172.16.99.2, eBGP match"), not
  just device-name pairing platitudes
* The rendered markdown is readable end-to-end without referring back to
  the YAML — that's the writer pattern proving its worth
* Topology mermaid in the md is derived from `tcf.devices` alone — no
  SQL was issued by the writer

### Architectural rules encoded by R94

* **sim writes prod CLI, lab writes SRL twin CLI** — two parallel
  artefacts, never a "translate-then-deploy" path.  Production runs sim's
  commands; lab provides per-command twin evidence
* **Deterministic step_verdicts** only emit structural facts (missing /
  extra / tvt-pattern / post_check-form-diff).  Faking semantic
  approval from device-name match was banned in R94.2
* **Agent layer** (LLM) is responsible for semantic verdicts on paired
  blocks, via `olav.core.cab.semantic_review.review_paired_blocks(tcf)`.
  Each verdict carries a real reason; one bad LLM call yields `info`
  not silent failure
* **Writer** (this section) stays a pure polishing tool — no SQL, no
  DB.  Diagrams beyond TCF.devices come from upstream `db_query`
  agents emitting separate `.mmd` files

## Chapter 9: Write Security — Multi-Layer Enforcement

**Goal:** 7 层独立安全防线。

```bash
# Layer 1: readonly service — permanently blocked
olav --agent services "Write to InfluxDB"
# → hard_block: readonly_only=true

# Layer 2: API write — blocked by default
olav --agent services "Update R1 in NetBox"
# → blocked: pass --enable-api-write

# Layer 3: HITL approval

# → Approve? [y/N]

# Layer 4: SSH write — hard block
olav --agent ops "Push BGP config to R1"

# Layer 5: Sandbox network isolation
olav --agent ops "Use run_python_simulation to POST to http://192.168.100.101"

```
