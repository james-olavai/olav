## Chapter 1: Fresh Install — Zero to Query in 5 Minutes

**Goal:** Demonstrate installation and first query from scratch.

```bash
# 1. Create clean environment (~5s)
mkdir ~/olav-demo && cd ~/olav-demo
python3 -m venv .venv && source .venv/bin/activate

# NOTE: Python 3.11/3.12/3.13 recommended. Python 3.14 works but may show
#       Pydantic V1 compatibility warnings from LangChain.

# 2. Install OLAV (~150s on first install — downloads ~300MB of dependencies)
pip install olav==0.13.1
# deepagents-cli is a required runtime dependency (~1s)
pip install deepagents-cli --no-deps

# 3. Initialize (~8s)
olav init
# Expected output:
#   platform ready: created .olav scaffolding
#   llm: ⚠ unavailable (check api.json llm settings)  ← until API key is set
#   db: ✓ domain.duckdb + audit.duckdb ready
#   workspace: ✓ core workspace deployed

# 4. Configure LLM API key
# NOTE: olav init creates .olav/config/api.json directly — no .example to copy
nano .olav/config/api.json
# Edit: set "shared.api_key" to your LLM provider key (e.g. "sk-...")

# 5. Install NetOps skill (~0.3s)
# For local dev / demo without public GitHub access:
olav skill install /path/to/olav-netops/
# For production (requires public GitHub repo):
# olav skill install https://github.com/james-olavai/olav-netops
# Expected: installed ops v0.13.x → .olav/workspace/ops/
#           ⚠ missing packages: nornir>=3.3.0, nornir-netmiko>=1.0.0
#           (install only if using SSH collection: pip install nornir nornir-netmiko)

# 6. Verify (~1s)
olav list
# Expected: core, ops, quick visible
```

**Talking point:** One `skill install` command gives you network operations. No pip dependencies to manage — OLAV handles the workspace structure.

## Chapter 5: Sim → Lab — Change Plan to CAB Validation

**Goal:** Show the full pre-deployment workflow: deterministic simulation first, then digital twin validation of the resulting change plan.

> **Note:** Both `analysis` (sim) and `lab` are subagents of `ops`. Two invocation methods:
> - `olav --agent ops "deploy digital twin"` → orchestrator auto-routes to lab subagent
> - `olav --agent ops-lab "deploy digital twin"` → direct invocation (skips orchestrator routing)

> **Prerequisites:**
> 1. ContainerLab REST API running at `192.168.100.12:8080`
> 2. Credentials stored in `.olav/workspace/ops-lab/config/config.json`:
>    ```json
>    {"base_url": "http://192.168.100.12:8080", "username": "olav", "password": "olav123", "mgmt_subnet": "172.20.50.0/24"}
>    ```
> 3. Env vars (or stored in `.olav/services/containerlab/env/containerlab.env`):
>    ```bash
>    CLAB_USERNAME=olav
>    CLAB_PASSWORD=olav123
>    ```
>
> ⏱ Prerequisites setup ≈ 1 min

### Step 1: Simulation — Generate Change Plan

Ask the analysis subagent to compute what changes are needed and what the blast radius is before touching anything.

```bash
olav --agent ops "I want to decommission R3 and make R1 and R4 directly connected. Give me a change plan."
# Expected (analysis subagent):
#   1. Query topology from DuckDB — loads current link graph
#   2. Run Python sandbox: remove R3 node, add R1↔R4 direct link
#   3. Re-run Dijkstra — verify all paths still converge
#   4. Identify affected sessions: R1→R3 eBGP (AS65001↔AS65003), R3→R4 iBGP
#   5. Output phased change plan with rollback steps:
#      Phase 1: Drain R3 traffic (BGP prepend/community drain)
#      Phase 2: Remove R3 (delete OSPF/BGP neighbors, decommission)
#      Phase 3: Cable R1 ge-0/0/2 ↔ R4 Eth0/2, assign 10.1.14.0/24
#      Phase 4: Validate convergence (OSPF FULL, no R3 prefixes)
#   Blast radius: R3 isolated, R1↔R4 direct -2ms latency improvement
#
# Actual result (2026-04-10): ✅ Full 4-phase change plan with rollback generated
```

⏱ Step 1 ≈ 30s

### Step 2: Lab Validation — CAB Gate

Feed the change plan into the lab subagent to validate it in a real container network before raising a CAB ticket.

```bash
olav --agent ops-lab "Deploy a 2-node digital twin lab with R1 and R4. Use a simple direct eBGP connection between them (R1 AS65001, R4 AS65004, subnet 10.1.14.0/24). Run CAB validation to verify BGP becomes ESTABLISHED."
# Expected (lab subagent):
#   1. save_lab_config — build SR Linux node configs for R1 and R4
#   2. deploy_lab — POST CLAB YAML to ContainerLab REST API
#   3. push_node_config — push eBGP config to both nodes
#   4. exec_on_node (×N) — wait for BGP convergence, assert ESTABLISHED
#   5. CAB report: PASS ✓
#      - R1 10.1.14.2 → ESTABLISHED (~4min, TCP :179)
#      - R4 10.1.14.1 → ESTABLISHED (~4min, TCP :179)
#   6. destroy_lab — cleanup (NOTE: agent may skip this step, see ISSUE-P2 below)
#
# Actual result (2026-04-10):
#   ✅ Lab deployed: r1-r4-ebgp-direct (2x nokia_srlinux:24-10)
#   ✅ BGP ESTABLISHED on both nodes (session age ~4min)
#   ⚠️  destroy_lab NOT called by agent — manual cleanup needed:
#       curl -X DELETE http://192.168.100.12:8080/api/v1/labs/r1-r4-ebgp-direct \
#            -H "Authorization: Bearer <token>"
#   See ISSUE-P2-LAB-AGENT-SKIPS-DESTROY-LAB
```

> **⚠️ Always verify lab cleanup after demo:**
> ```bash
> TOKEN=$(curl -s -X POST http://192.168.100.12:8080/login \
>   -H "Content-Type: application/json" \
>   -d '{"username":"olav","password":"olav123"}' | python3 -c "import json,sys; print(json.load(sys.stdin)['token'])")
> curl -s http://192.168.100.12:8080/api/v1/labs -H "Authorization: Bearer $TOKEN"
> # If r1-r4-ebgp-direct is still listed, destroy it manually:
> curl -X DELETE http://192.168.100.12:8080/api/v1/labs/r1-r4-ebgp-direct -H "Authorization: Bearer $TOKEN"
> ```

⏱ Step 2 ≈ 5–8 min (SR Linux boot ~3min + BGP convergence ~1min + exec checks ~1–3min)

**Talking point:** The sim step is mathematically computed — Dijkstra on real OSPF costs, not LLM inference. The lab step deploys real SR Linux containers and verifies actual BGP convergence. If either step fails, the change is blocked before it ever reaches a CAB ticket. The two subagents (`analysis` and `lab`) are both orchestrated by a single `--agent ops` call.

## Chapter 7: Infra Agent — Full Service Onboarding (InfluxDB)

**Goal:** Show the complete lifecycle of onboarding a new service: declare in `services.yaml`, set credentials, load API schema, generate reference tools, and query via agent.

We use **InfluxDB** (time-series metrics, API-key auth) as the demo service to show a different auth pattern from NetBox.

> **Prerequisites — NetBox v5 Token:**
> NetBox 5.x uses peppered HMAC v2 tokens. The `services.yaml` uses `auth.type: bearer`, so the token must be provided as the full `nbt_<key>.<plaintext>` value. If you see `403 Invalid v1 token`, regenerate via Django shell:
> ```bash
> docker exec netbox-netbox-1 python3 /opt/netbox/netbox/manage.py shell -c "
> from users.models import Token
> from django.contrib.auth import get_user_model
> User = get_user_model()
> admin = User.objects.get(username='admin')
> Token.objects.filter(user=admin).delete()
> t = Token(user=admin); t.save()
> print('NETBOX_TOKEN=nbt_' + t.key + '.' + str(t._token))
> "
> # Then update .olav/services/netbox/env/netbox.env with the printed NETBOX_TOKEN value
> ```
> See ISSUE-P2-NETBOX-V2-TOKEN-AUTH-FORMAT.
>
> ⏱ Token regeneration ≈ 5s

## Chapter 9: Write Security — Multi-Layer Enforcement

**Goal:** Demonstrate that write operations are blocked at multiple independent enforcement points — API writes, SSH device access, file system, and sandbox network isolation.

### Layer 1: Read-Only Service — Permanently Blocked

```bash
# InfluxDB is declared readonly_only: true — cannot be unlocked at runtime
olav --agent infra "Write a new data point to the network_metrics bucket in InfluxDB"
# Expected: {"status": "blocked",
#            "reason": "Service influxdb_netops is read-only. readonly_only=true cannot be overridden.",
#            "layer": "service_readonly_guard"}
```

### Layer 2: Writeable API — Blocked by Default

```bash
# NetBox allows writes, but the flag is not set
olav --agent infra "Update device R1 status to staged in NetBox"
# Expected: {"status": "blocked", "reason": "API write mode not enabled. Pass --enable-api-write to unlock."}
```

### Layer 3: Writeable API — HITL Approval Required

```bash
olav --agent infra "Update device R1 status to staged in NetBox" --enable-api-write
# Expected: Warning banner
#   ⚠ API write mode ENABLED
#   Reading current state of R1...
#   Proposed change: status "active" → "staged"
#   Approve this change? [y/N]:
#   Agent cannot proceed without user typing 'y'
```

### Layer 4: SSH Write to Network Device — Hard Block

```bash
# Attempt to push config changes via SSH
olav --agent ops "Push this BGP config to R1: neighbor 10.0.0.2 remote-as 65002"
# Expected: {"status": "hard_block",
#            "reason": "SSH write access is not supported. OLAV is read-only for live network devices.",
#            "layer": "ssh_write_guard"}

# Attempt to delete device config via SSH
olav --agent devops "Use SSH to erase the startup-config on R2"
# Expected: hard_block — there is no --enable-ssh-write flag, by design
```

### Layer 5: Destructive File Operations — Approval Gate

```bash
# Attempt to delete a single config backup
olav --agent devops "Delete the BGP config backup for R1 from exports/"
# Expected: approval gate triggered
#   ⚠ Destructive file operation requested
#   Target: exports/backup/r1_bgp_20260410.cfg
#   Delete this file? [y/N]:

# Attempt bulk deletion
olav --agent devops "Remove all config backups from exports/backup/"
# Expected: hard_block — bulk destructive file operations are blocked unconditionally
#   {"status": "hard_block", "reason": "Bulk file deletion requires explicit user confirmation per file."}
```

### Layer 6: Sandbox Network Isolation — Hard Block

```bash
# Even inside the Python simulation sandbox, outbound network writes are blocked
olav --agent ops "Use run_python_simulation to POST config to http://192.168.100.101"
# Expected: sandbox_guard returns hard_block before code executes
#   {"status": "hard_block", "reason": "Outbound network access is blocked in simulation sandbox."}

olav --agent ops "Use run_python_simulation to write to http://192.168.100.50:8087/api/v2/write"
# Expected: same hard_block — InfluxDB write endpoint, still blocked in sandbox
```

### Layer 7: Bypass Scope Boundary

```bash
# --dangerously-skip-permissions only bypasses tool approval UI
# It CANNOT unlock SSH write, API write, sandbox isolation, or readonly services
olav --agent infra "Update R1 in NetBox" --dangerously-skip-permissions
# Expected: STILL blocked at API write layer
#   approval UI skipped, but write guard remains active

olav --agent infra "Write to InfluxDB" --dangerously-skip-permissions
# Expected: hard_block — readonly_only is a service-level constraint, not a permission
```

**Talking point:** Seven independent enforcement points — not a single flag. `readonly_only: true` is permanent at the service level. SSH writes don't exist — there is no `--enable-ssh-write`. Bulk file deletion is unconditionally blocked. The sandbox cannot open outbound sockets regardless of any flag. `--dangerously-skip-permissions` only affects the tool approval UI; it cannot escalate to write access.

□ pip install olav==0.13.1                             # ~150s (first install)
□ pip install deepagents-cli --no-deps                 # ~1s
□ olav init                                            # ~8s — creates .olav/ + api.json
□ nano .olav/config/api.json  (set shared.api_key)    # no .example copy needed
□ olav skill install /path/to/olav-netops/             # ~0.3s (local path)
# Public repo (when available): olav skill install https://github.com/james-olavai/olav-netops
□ pip install nornir nornir-netmiko                    # only needed for SSH collection
□ cp .olav/workspace/ops/probe/config/nornir/hosts.yaml.example \
     .olav/workspace/ops/probe/config/nornir/hosts.yaml  (fill inventory)
□ Configure lab/config/config.json (CLAB credentials)
□ Start NetBox: docker compose up -d (in .olav/services/netbox/)
□ Set NETBOX_TOKEN environment variable
□ Set INFLUXDB_NETOPS_TOKEN environment variable
□ olav registry register netbox
□ olav registry register influxdb_netops
□ olav --agent ops "/netops_init" (collect device data)
□ Import devices to NetBox (run devops-generated script)

□ olav registry list → shows netbox, influxdb_netops
