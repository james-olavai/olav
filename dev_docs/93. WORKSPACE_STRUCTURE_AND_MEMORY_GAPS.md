# Workspace Structure Debt & Memory Layer Gaps

**发现时间**: 2026-06-05  
**状态**: Open — 待设计决策后修复  
**影响范围**: 所有 agent workspace 目录结构 + LanceDB memory 三层架构

---

## 问题一：workspace 目录命名不统一

### 现象

当前 workspace 下存在三种目录命名，表达同一语义（"注入到 agent 的参考内容"）：

| 目录 | 位置 | 实际用途 |
|---|---|---|
| `prompts/` | services, admin, devops, netops, audit, core, core/writer, core/memory-curator | agent 系统提示文件 |
| `guides/` | `core/guides/`, `netops/guides/` | `*.guide.yaml`，通过 `olav kb import-guides` 注入 LanceDB |
| `references/` | netops 各 sub-agent, audit/explorer, core/db-query | 同样是 `*.guide.yaml` + `.md` 参考文档 |

**`guides/` 和 `references/` 功能完全相同，命名不同是历史遗留。**

### 根因

平台代码 `agent.py:1412` 对 root agent 的 system prompt 硬编码了默认路径：

```python
# agent.py:1412
_prompt_file_rel = olav_config.get("system_prompt_file", "prompts/system.md")
```

而 sub-agent 路径（SKILL.md body）已是正确做法：

```python
# agent.py:1218 — sub-agent，已正确
prompt = (post.content or "").strip()   # SKILL.md body 直读，无需 prompts/
```

两条路径导致 root agent 和 sub-agent 的目录结构不同。

### 目标标准

```
<agent>/
  AGENT.md          ← 路由配置，不含 system_prompt_file
  SKILL.md          ← 系统提示内容直接写在 frontmatter 之后的 body
  scripts/          ← 可调用脚本
  references/       ← *.guide.yaml + *.md 参考文档（统一命名）
```

### 需要改动

**平台层（agent.py）**：
- `_prompt_file_rel` 默认值改为回落 SKILL.md body（而非 `prompts/system.md`）
- 加 legacy fallback：若 `prompts/system.md` 存在则继续读，向后兼容

**文件迁移（各 agent）**：

| 操作 | 涉及文件 |
|---|---|
| `prompts/*.md` 内容合并入 SKILL.md body | services, admin, devops, netops, audit, core（共 8个 prompt 文件） |
| `guides/` → `references/` 重命名 | `core/guides/`（6文件）、`netops/guides/`（11文件） |
| 删除空 `prompts/` 目录 | 迁移完成后 |

**特殊情况 — audit-runner `prompts/`**：
`audit-runner/prompts/` 含 3 个文件（`system_envelope.md`, `correlation_pass.md`,
`postcheck_prompts.md`），系动态拼装使用，需单独确认迁移方式再处理。

## 问题二：LanceDB memory 三层架构中 `expertise/` 层从未建立

### 架构设计（三层）

```
Layer 1 — usage_guide       *.guide.yaml → olav kb import-guides
          38 条，正常运作

Layer 2 — expert_knowledge  expertise/*.expert.yaml → olav kb import-experts
          设计存在，但 0 个 .expert.yaml 文件被创建
          当前 18 条 expert_knowledge 均来自 agent 运行时 olav_store_memory 写入

Layer 3 — reflection        AutoCaptureMiddleware 对话后提取 → fact/decision/preference
          13 条（7 fact + 5 decision + 1 preference），正常运作
```

### 现状

```
find workspace/ -name "*.expert.yaml"   → 0 results
ls ~/.olav/expertise/                   → 目录不存在
ls .olav/expertise/                     → 目录不存在
```

`expert_kb.py` 的 `discover_experts()` 扫描路径：
- `<workspace>/<agent>/expertise/*.expert.yaml`（shipped，随 wheel 发布）
- `~/.olav/expertise/*.expert.yaml`（用户注入，org scope）
- `<project>/.olav/expertise/*.expert.yaml`（项目级注入）

以上三个路径均为空。

### 问题

`usage_guide`（guide KB）和 `expert_knowledge`（expert KB）在功能上有重叠：

| | usage_guide | expert_knowledge |
|---|---|---|
| 文件格式 | `*.guide.yaml` | `*.expert.yaml` |
| scope | agent-scoped（由文件路径推断） | agent / shared:\<domain\> / org |
| 语义 | "agent 应该 **做什么**（workflow）" | "agent 应该 **知道什么**（corrective knowledge）" |
| 当前状态 | ✅ 38 条，正常 | ⚠️ shipped 层 0 条，全靠 agent 运行时写入 |

当前大量本应是 `expert_knowledge` 的内容（SQL schema、BGP 参考、fault analysis workflow）被放进了 `usage_guide`，导致两层边界模糊。

### 待决策

1. **expertise 层是否需要建立**？哪些现有 `*.guide.yaml` 应该迁移为 `*.expert.yaml`？
2. **scope 策略**：网络拓扑 SQL schema 应该是 `shared:netops` 还是特定 sub-agent scope？
3. **user injection 路径**：是否需要给用户提供一个初始化流程（`olav init --with-expertise`）？
4. **`usage_guide` 和 `expert_knowledge` 的边界**：是否合并，还是保持两层并明确分工？

## 问题三：`user (legacy)` tier 标记

### 现象

`olav kb list-guides` 输出中，约 27/40 条 usage_guide 显示为 `user (legacy)` tier：

```
core  bgp_path_selection_and_state_machine  user (legacy)  core/guides/bgp_path_and_state_reference.guide.yaml
```

### 根因

`source_tier` 字段是后期（Phase 1.5）加入的。早期导入的 guide entry 在 LanceDB row
中没有 `source_tier` 字段，`list-guides` 命令回落显示 `user (legacy)`：

```python
# kb.py:628
tier = data.get("source_tier") or "user (legacy)"
```

### 影响

纯展示问题，不影响 recall 功能。需要重新 import-guides 才能补上 `source_tier`。
