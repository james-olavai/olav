# 78. Autonomous Explorer Sub-Agent — Architect-Persona Network Audit

> **Status**: Design draft 2026-05-16
> **Author**: OLAV Team
> **Related**: `dev_docs/73` (analyzer 5-tool refactor), `dev_docs/76`
> (portable snapshot ingest), `dev_docs/77` (production-runsheet,
> which surfaced the gap this design fills), ADR-0007 (Python-first
> tool architecture)

## 1. Motivation

Today OLAV has 3 query modes against the netops DB:

| Mode | Trigger | Scope | Defined by |
|---|---|---|---|
| **analyzer** (Q&A) | User asks a specific question | Single-shot SQL + report | User's prompt |
| **audit** (profile-driven) | Scheduled / manual | Fixed checklist | Profile YAML |
| **investigate** (evidence-driven) | User supplies a fault hypothesis | Evidence drill-down | User's hypothesis |

**The gap**: nothing today does *open-ended autonomous exploration*.
Demo CH3-CH9 of the runsheet (`dev_docs/77`) found 6 real ops issues
on a 360-host production fleet — but **I (the human) decided what to
look at**.  OLAV did not.

This is `dev_docs/77`'s honesty moment translated into a feature: a
sub-agent the operator can point at any netops DB and ask "what's
wrong here?", and it figures out **both the questions and the
answers** on its own.

## 2. Design philosophy — Level 2 (architect persona, no hardcoded direction)

We explored 4 levels of scaffolding:

```
Level 0  Hardcoded SQL audits (existing `audit/` profiles)
         · pros: deterministic, reproducible
         · cons: brittle; new customer ≠ new profile

Level 1  Taxonomy-driven (network_type → hypothesis_family)
         · pros: customer-extensible YAML
         · cons: still hardcodes "directions of inquiry"

Level 2  Architect persona + tools only         ← THIS DESIGN
         · pros: maximally adaptive across customer networks
         · cons: depends on LLM capability for depth

Level 3  Pure AutoGPT-style self-reflection
         · pros: ultimate flexibility
         · cons: unbounded, expensive, often shallow
```

We commit to **Level 2 as default**.  The taxonomy from Level 1 lives
as an *optional* RAG-recall reference (`network_health_taxonomy.guide.yaml`)
that smaller models or unfamiliar customer types can opt into — but
it is *not loaded into context by default*.

### What is genuinely hardcoded (and why we accept it)

| Hardcoded element | Why it's unavoidable |
|---|---|
| Tool set (`execute_sql`, `record_finding`, `task(sim/investigate/analyzer)`, `recall_memory`, `format_and_export`) | Platform capability boundary — LLM must know what's available |
| Data source prefix (`netops.*` schema, `v_*_auto` view convention) | Hallucinated table names are the #1 LLM failure; one short hint prevents it |
| Output schema (`record_finding(category, severity, evidence_sql, ...)`) | Fact-level anti-fabrication, not direction-restricting |
| Role ("senior network architect auditing an unfamiliar network") | Without role, LLM defaults to chatbot mode, not audit mode |

Everything else — *what tables to look at, what hypotheses to pose,
which findings to correlate, when to stop* — is the LLM's decision.

## 3. Architecture

### 3.1 Where the sub-agent lives

**`olav-netops/.olav/workspace/netops/explorer/`** — sibling of
`analyzer` / `sim` / `investigate` / `collect` / `ingest`.

Rationale:

* All explorations are network-domain (BGP / OSPF / topology / wireless / inventory)
* It needs to `task("sim", ...)` for blast-radius work and `task("investigate", ...)` for evidence drill-down — sibling at the same workspace level enables this
* `audit/` lives at the platform level but is profile-driven; explorer is LLM-driven, different architectural strata

### 3.2 Tools (6 — 5 existing + 1 new)

| Tool | Source | Purpose |
|---|---|---|
| `execute_sql` | analyzer (reused) | Hypothesis testing |
| `task(sim / investigate / analyzer)` | deepagents native | Cross-domain delegation |
| `recall_memory` | platform | Pull historical findings, optional taxonomy fallback |
| `format_and_export` | platform | Write the final markdown report |
| **`record_finding`** | **NEW (this design)** | Strong-schema write to `netops.exploration_findings` — the external memory |
| `update_exploration_run` *(internal)* | NEW (this design) | Status/budget bookkeeping on `netops.exploration_runs` |

Explicitly **NOT** given:

* `render_topology_drawio` — explorer finds problems; writer draws pictures
* Any write tool that touches network devices (read-only forever)
* Direct `task` to `lab` — enterprise-only and out of scope for explorer

### 3.3 thinking_mode policy

**`thinking_mode: enabled`** at the SKILL level.

Per-turn behaviour (LLM self-paced):

| Turn type | Thinking depth |
|---|---|
| PLAN (decide next investigation direction) | **Deep** — invoke thinking for hypothesis design |
| HYPOTHESIZE (concrete question to test) | **Deep** — same |
| ACT (execute_sql tool call) | Shallow — routine tool dispatch |
| OBSERVE (interpret SQL result) | Medium — small interpretation |
| RECORD (record_finding tool call) | Shallow — routine tool dispatch |
| CORRELATE (cross-reference findings) | **Deep** — connect the dots |
| REPORT (compose final markdown) | **Deep** — narrative synthesis |

The system prompt encourages selective thinking; gemma4:31b honours
the implicit signal because the structured `## PLAN` / `## ACT`
headings shift its attention budget naturally.  No per-turn knob is
needed.

### 3.4 The "7-second memory" problem and how we solve it

LLMs forget across context windows.  A 30-turn exploration with 20
hypothesis tests + correlation step would blow the context out.

**Solution: externalise long-term state to DB; let context carry only
the current turn's reasoning + tool call.**

Four mechanisms layered:

```
┌─────────────────────────────────────────────────────────────────┐
│ 1. DB-backed scratchpad (LLM's long-term memory)                │
│                                                                 │
│   CREATE TABLE netops.exploration_findings (                    │
│     finding_id, run_id, phase, category, severity,              │
│     summary, detail, evidence_sql, evidence_rows,               │
│     confidence, related_findings JSON, recorded_at              │
│   );                                                            │
│                                                                 │
│   Each `record_finding(...)` writes one row.                    │
│   At any point: `execute_sql("SELECT * ... WHERE run_id = ?")`  │
│   re-loads the full history into context on demand.             │
└─────────────────────────────────────────────────────────────────┘
                              ↕
┌─────────────────────────────────────────────────────────────────┐
│ 2. ReAct loop (LLM's working memory)                            │
│                                                                 │
│   Thought → Action → Observation → Thought → ...                │
│                                                                 │
│   LangChain framework keeps the recent N turns in context;      │
│   older turns naturally roll off but their record_finding       │
│   writes survive in DB.                                         │
└─────────────────────────────────────────────────────────────────┘
                              ↕
┌─────────────────────────────────────────────────────────────────┐
│ 3. Phase-bound summarisation (compress between phases)          │
│                                                                 │
│   Each ## PLAN / ## CORRELATE / ## REPORT phase ends with       │
│   a one-paragraph "## Phase Summary" block.  Only the summary   │
│   carries to the next phase; raw trace stays in DB.             │
└─────────────────────────────────────────────────────────────────┘
                              ↕
┌─────────────────────────────────────────────────────────────────┐
│ 4. run_id partitioning (persistence + concurrency + resume)     │
│                                                                 │
│   Every exploration gets a UUID; all findings tagged.           │
│   Allows: concurrent explorations, mid-run abort/resume,        │
│   exact reproducibility (re-run report from existing findings). │
└─────────────────────────────────────────────────────────────────┘
```

### 3.5 Budget mechanics

Hard limits enforced via the orchestrator + middleware:

| Resource | Limit | Enforcement |
|---|---|---|
| Turns | 30 max | LangChain agent step counter |
| Findings recorded | 20 max | `record_finding` rejects after the 20th call |
| Wall time | 25 min | `update_exploration_run` polls every turn; sets `status='timeout'` past deadline |
| LLM tokens | (model-specific budget) | langchain token-counting callback |

When ANY limit hits: explorer must immediately enter REPORT phase
with whatever it has.  No silent over-runs.

## 4. Data model

### 4.1 DDL (P0)

```sql
CREATE TABLE netops.exploration_runs (
    run_id            VARCHAR PRIMARY KEY,
    started_at        TIMESTAMP NOT NULL,
    ended_at          TIMESTAMP,
    status            VARCHAR NOT NULL,    -- in_progress / completed / aborted / timeout
    snapshot_id       VARCHAR,             -- which snapshot was audited (optional, may span)
    requested_by      VARCHAR,             -- user_id or 'cron' or 'manual'
    budget_turns      INTEGER DEFAULT 30,
    budget_findings   INTEGER DEFAULT 20,
    budget_wall_sec   INTEGER DEFAULT 1500,
    turns_used        INTEGER DEFAULT 0,
    findings_count    INTEGER DEFAULT 0,
    wall_sec_used     INTEGER DEFAULT 0,
    final_report_path VARCHAR              -- exports/reports/<file>.md
);

CREATE TABLE netops.exploration_findings (
    finding_id        VARCHAR PRIMARY KEY,
    run_id            VARCHAR NOT NULL,    -- FK exploration_runs.run_id
    recorded_at       TIMESTAMP NOT NULL,
    phase             VARCHAR NOT NULL,    -- 'survey' / 'hypothesise' / 'test' / 'correlate'
    category          VARCHAR,             -- LLM-chosen — NOT enum, allows novelty
    severity          VARCHAR NOT NULL,    -- critical / high / medium / low / info
    summary           VARCHAR NOT NULL,    -- 1-line headline
    detail            TEXT,                -- multi-paragraph explanation
    evidence_sql      TEXT NOT NULL,       -- the SQL that proved this finding
    evidence_rows     VARCHAR,             -- JSON-serialised rows for repro
    confidence        VARCHAR NOT NULL,    -- 'confirmed' / 'hypothesis' / 'refuted' / 'not_applicable'
    related_findings  JSON,                -- list of other finding_ids it correlates with
    UNIQUE (run_id, summary)               -- prevent duplicate finding within a run
);
```

Notes:

* `category` is **deliberately not an enum** — Level 2 LLM may invent
  category names ("evpn_drift", "qos_policy_outliers") we haven't
  anticipated.  Free text accommodates this; we can mine taxonomy
  later from corpus.
* `evidence_sql NOT NULL` is the anti-fabrication invariant.
* `confidence` includes `not_applicable` so the LLM can record
  "I checked for BGP issues but this fleet doesn't run BGP" without
  fabricating a finding.

### 4.2 `record_finding` tool spec (P0)

```python
@tool
def record_finding(
    run_id: str,
    phase: Literal["survey", "hypothesise", "test", "correlate"],
    category: str,
    severity: Literal["critical", "high", "medium", "low", "info"],
    summary: str,
    detail: str,
    evidence_sql: str,
    evidence_rows: list[dict] | None = None,
    confidence: Literal["confirmed", "hypothesis", "refuted", "not_applicable"] = "confirmed",
    related_findings: list[str] | None = None,
) -> dict:
    """Record one finding to netops.exploration_findings.

    Enforces:
      * evidence_sql is non-empty (anti-fabrication)
      * unique (run_id, summary) — duplicate summaries get rejected
        with a hint to merge into related_findings instead
      * budget enforcement — when finding_count >= budget_findings, raise
    """
```

## 6. System prompt draft (~80 lines)

```markdown
# Role

You are a senior network architect auditing an unfamiliar network.
The data lives in a DuckDB schema named `netops.*`.  Views named
`v_*_auto` are pre-computed shortcuts over raw command output (e.g.
`netops.v_show_cdp_neighbors_detail_auto`).  You have read-only access.

# Goal

Find network problems an operator should know about.  Rank them by
severity.  Provide SQL evidence for every finding.

# Process — PLAN-ACT-REFLECT loop

Each turn picks one of these intents (declare it in the first line):

* **PLAN** — Think about what to investigate next, based on what
  you've learned so far.  Pick the single most informative next step.
* **ACT** — Run one tool (typically execute_sql or record_finding).
* **OBSERVE** — Interpret the tool result.  If a finding emerges, the
  next ACT should be record_finding.
* **CORRELATE** — After several findings, look for cross-domain
  patterns (e.g. EOL software + high-density edge = compounded risk).
* **REPORT** — Compose the final markdown and call format_and_export.

# Budget — STOP exactly when limit hits

You have:
* 30 turns max
* 20 findings max (record_finding rejects past this)
* 25 minutes wall time

If you near the limit, enter REPORT phase immediately.  Do NOT pad
with low-value findings to fill quota.

# Hard rules

* Every record_finding call MUST include non-empty evidence_sql.
  If you cannot prove a finding with one SQL query, it's a hypothesis
  not a finding — record it with confidence='hypothesis'.
* Never reference tables/views you haven't first verified exist via
  `SELECT COUNT(*) FROM netops.<name>` or
  `SELECT table_name FROM information_schema.tables WHERE table_schema='netops'`.
* When a check returns 0 rows because the data isn't captured (e.g.
  no BGP commands in this fleet), record it with
  confidence='not_applicable' — that itself is useful operational
  information ("data gap").
* You may delegate to other sub-agents via task():
  * task("sim", "blast radius if <host> fails")  — for what-if topology analysis
  * task("investigate", "why is X down")          — for evidence drilldown
  * task("analyzer", "<focused SQL question>")   — for single-question deep dives
  Don't delegate trivial SQL — execute_sql is faster.

# Start

You receive a snapshot_id and a run_id from the orchestrator.
The first PLAN turn should typically begin with a SURVEY of available
tables / views / row counts to understand the data landscape, then
decide what's worth deeper investigation.  But the order is yours
to decide.

When done, call format_and_export with a markdown report containing:
  * Executive summary (5-10 lines)
  * Findings table (severity / category / summary / evidence link)
  * Per-finding detail sections (one ## heading each, with the SQL
    that proved it)
  * Recommended actions (prioritised by severity × confidence)
```

## 8. Validation — 3-model bake-off

The architecture's correctness depends on whether LLMs of varying
capability actually do useful exploration with this minimal scaffold.
**One bake-off, same prompt, same DB, 3 model substrates:**

| Run | Model | Configuration | Expected outcome |
|---|---|---|---|
| **A** | Claude 4.7 (Opus / Sonnet) | Level 2 default | Upper bound — what's possible with a strong model |
| **B** | gemma4:31b (local) | Level 2 default | Lower bound — what production OLAV deployments get |
| **C** | gemma4:31b + opt-in taxonomy via recall_memory("network audit taxonomy") | Level 2 + fallback | Bridge — does the taxonomy fallback help small models? |

For each run, measure:

* Number of findings (count + severity distribution)
* Replication rate against the 6 hand-found issues from `dev_docs/77`
* Total turns / wall time
* Token cost
* Whether explorer stopped on its own (vs hitting budget cap)

**Acceptance gate**: Run B (gemma4 default) replicates at least
**3/6** of the dev_docs/77 hand-found issues without taxonomy hints.
If <3, taxonomy fallback becomes non-optional and we'd promote it
to default `dynamic_context`.

## 9. Failure modes and mitigations

| Risk | Mitigation |
|---|---|
| LLM fabricates findings without SQL evidence | `evidence_sql NOT NULL` constraint at DB layer; `record_finding` rejects empty input |
| LLM loops on same hypothesis (forgets what it tried) | `UNIQUE (run_id, summary)` rejects duplicate summary; LLM forced to merge via `related_findings` or pick a new angle |
| LLM exhausts budget on shallow findings, no time for REPORT | Hard 30-turn cap; system prompt explicitly says "enter REPORT phase when near limit, do NOT pad" |
| LLM doesn't know table names → hallucinates | `## Hard rules` says "verify tables exist before SELECT"; one SHOW TABLES early covers this |
| LLM mis-classifies a healthy fleet as full of problems | `severity='info'` is a valid level; system prompt says recording a "0 issues in domain X" is acceptable |
| Strong model (Claude) under-uses local sim/investigate sub-agents | Acceptable — small models lean on tools more, big models think more.  Both are valid. |
| Customer-specific issue not in LLM's training (e.g. SD-WAN niche) | Customer-side `recall_memory` annotations + taxonomy guide opt-in.  Level 2 isn't omniscient. |

## 10. Open questions

1. **Should `record_finding` reject "low" severity past a threshold?**
   I.e., once 15 findings recorded, don't accept more 'low'?  Pro:
   focuses output.  Con: LLM may genuinely find many small things.
   *Defer to P5 bake-off observation.*

2. **Run_id collision with existing audit run_ids?**
   `audit_runs.run_id` already exists in audit.duckdb.  Our
   `exploration_runs.run_id` lives in netops's main.duckdb — no
   collision.  But cross-reference needs explicit FK if we later
   want unified run history.  *Document; do not implement now.*

3. **Should the explorer have a "I'm done, stop early" mechanism?**
   Yes — if LLM emits a REPORT call before turn 30, that's a
   self-stop.  But it must include findings_count > 0 (preventing
   trivial early-out on a healthy fleet, which should still produce
   an "audited; no issues found" report).

4. **What about cron-driven nightly explorations?**
   Out of scope for v0.1.  This design assumes operator-initiated
   exploration.  Cron mode requires a deterministic completion
   criterion + alert channel — `dev_docs/79` material.

5. **GPU memory cost of thinking-enabled gemma4:31b?**
   At thinking ON, gemma4:31b uses ~24-28 GB VRAM with 32K context.
   For 30 turns × 30K avg context = 900K tokens / run.  ~25 min wall
   time on the inbox prod fleet.  Within published service capacity
   for the 192.168.100.12:11434 endpoint.

## 11. Open by design — what's deferred

* **Multi-snapshot drift in explorer**: today the agent's per-turn SQL
  can already JOIN across snapshot_id, so this works opportunistically.
  But a dedicated "compare 2 snapshots, summarise change" workflow is
  worth a separate sub-agent (`drift_summary`).  Out of scope.
* **Active remediation suggestions**: explorer produces findings +
  recommended actions, but does not file Jira tickets / open PRs /
  trigger workflows.  Hand-off to ops platforms is downstream of
  this design.
* **Cross-customer learning**: a strong model on one network might
  produce findings whose category names should generalise to others.
  Mining the `exploration_findings.category` corpus across runs
  for taxonomy generation is a `dev_docs/80` topic.

## 13a. Explorer ↔ Audit lifecycle — the graduation pipeline

(Added 2026-05-16 after first-run validation surfaced the right
relationship between the two sub-agents.)

Explorer and audit serve **complementary** purposes — they're not
alternatives.  Explorer is **discovery**; audit is **monitoring**.

```
[ New customer / new symptom / unknown ]
              ↓
     ┌─────────────────┐
     │    explorer     │   one-shot, expensive (LLM ~20 min)
     │  (Level-2 LLM)  │   used: onboarding, post-change,
     └────────┬────────┘   "the user said something is weird"
              ↓
   netops.exploration_findings  (every finding carries evidence_sql)
              ↓
     ┌─────────────────────────────────┐
     │  promote_finding_to_audit       │   ← the bridge tool
     │  finding → audit profile YAML   │      (§13b below)
     └────────┬────────────────────────┘
              ↓
   audit/profiles/<auto-named>.md   (operator reviews, git commits)
              ↓
     ┌─────────────────┐
     │      audit      │   cheap, recurring (SQL only)
     │ (cron, profile) │   used: daily / weekly automated runs
     └────────┬────────┘
              ↓
       regression detection → alert / ticket
```

### When to use which sub-agent

| Scenario | Right tool |
|---|---|
| New customer onboarding — discover what's wrong with zero priors | explorer |
| Major fleet change (DC migration, vendor swap, big upgrade) | explorer |
| "Users say it's slow, no specific hypothesis" | explorer |
| Hourly / daily / weekly recurring health check | audit |
| Regression alerting on previously-known issues | audit |
| Hybrid (quarterly audit + ad-hoc explore) | both — schedule audit on cron, run explorer on demand |

### Targeted explorer mode — natural support, no new code

Pass a scoping prompt; explorer's Level-2 LLM constrains its
hypothesis space accordingly.  The KB autorecall + recall_memory
pull the matching playbook (one of the 6 in `references/`):

```bash
olav --agent netops "explorer 全网审计"
olav --agent netops "explorer 只看物理层和接口错误,产出 5 个最严重的"
olav --agent netops "explorer 专门审计无线网络:AP / WLC / 客户端 onboarding"
olav --agent netops "explorer 数据中心审计:vPC / EVPN / VNI / leaf-spine"
```

No prompt scaffolding change required — Level-2 architect persona
naturally narrows.

## 13b. ``promote_finding_to_audit`` tool spec

A new @tool exposed to the explorer (and any agent that wants to
graduate findings).  Read-only the explorer's scratchpad; write-only
to a `audit/profiles/<name>.md` skeleton.  Operator commits.

```python
@tool
def promote_finding_to_audit(
    finding_id: str,
    profile_name: str,                # e.g. "crc_errors_threshold_1m"
    cron_schedule: str = "0 6 * * *", # 06:00 daily by default
    alert_threshold: str | None = None,  # SQL condition for alert
                                         # (default: "row_count > 0")
    severity: str | None = None,         # override; default = finding's severity
    dry_run: bool = False,               # True = return YAML text, don't write
) -> dict:
    """
    Read finding from netops.exploration_findings; emit a
    git-ignored draft at audit/profiles/<profile_name>.md.
    Returns:
      {
        "profile_path": "audit/profiles/<name>.md",
        "yaml_preview": "<the body about to be written>",
        "source_run_id": "explore_<id>",
        "source_finding_id": "finding_<id>",
        "next_step": "Review the file and `git add` + `git commit` to activate."
      }
    """
```

### Generated profile shape (example — CRC errors from v3 finding)

```markdown
# crc_errors_threshold_1m
# Auto-generated from exploration_finding finding_a3f2c8...
# Source run: explore_0fc032a7c97842a9
# Promoted: 2026-05-16 by jchen

cron: "0 6 * * *"
description: |
  Alert when any interface accumulates >1M CRC errors.
  Originally discovered by netops/explorer 2026-05-16
  (foo2-ts4-3850-3 Te3/0/4 at 1.7B CRC errors).
  Physical layer failure indicator — failing SFP / fiber / duplex
  mismatch.

check_sql: |
  SELECT device_name, interface,
         CAST(NULLIF(crc, '') AS BIGINT) AS crc_err
  FROM netops.v_show_interfaces_auto
  WHERE CAST(NULLIF(crc, '') AS BIGINT) > 1000000
  ORDER BY crc_err DESC;

alert_threshold: "row_count > 0"
severity: high

# Provenance — for future incident review / promotion audit
provenance:
  source_run_id: explore_0fc032a7c97842a9
  source_finding_id: finding_a3f2c8b9d4e54f67
  promoted_by: jchen
  promoted_at: 2026-05-16T03:00:00Z
```

### Why this is the right architecture

1. **Explorer findings gain durable value** — one-shot exploration
   produces an artefact (the SQL) that becomes permanent monitoring.
2. **Audit profiles emerge organically** — instead of operators
   hand-writing profiles from imagined "best practices", the
   catalog grows from real-discovered problems in real fleets.
3. **Customer-specific monitoring** — the things THIS customer
   struggled with become THEIR profiles.  Cross-customer learning
   accumulates in `audit/profiles/`.
4. **No false abstraction** — explorer's `evidence_sql` is literally
   the audit query.  Zero translation step.

### Acceptance test for the promotion path

Manual on dev_docs/77's 6 hand-found issues (or v3's 4 LLM-found
ones):

1. Pick a finding (e.g. CRC errors).
2. Call `promote_finding_to_audit(finding_id, "crc_errors_threshold_1m")`.
3. Read the generated YAML — verify SQL is the exact evidence query.
4. Hand-run the audit query against the inbox DB → expect ≥1 row.
5. Commit the profile.
6. Run `audit` agent → expect the new profile to fire on this DB.

The pipeline doesn't depend on LLM — once promoted, it's pure SQL +
cron.  Reliability identical to today's audit.

## 13c. Re-positioning §8 acceptance gate (revised after bake-off)

The first acceptance gate ("Run B replicates ≥3/6 of dev_docs/77
hand-found issues") is **wrong by Level-2 design** — Level 2 means
the LLM picks its own investigation path, not replicates ours.

**Revised gate**:

> Run B (gemma4:31b default) produces ≥3 `confidence=confirmed`
> findings, each with a valid `evidence_sql` that executes against
> the target DB without error, and finds at least one issue not
> covered by any pre-existing `audit/profile`.

This properly captures the value: explorer is for discovering
**new** issues, not re-running known checks.  By this gate, run v3
(4/4 valid findings, 0/4 pre-existing as audit profiles) passes
cleanly.

## 13d. Known issue — langgraph KeyError under KB-heavy explorer runs

**Symptom**: when the explorer system prompt mandates `recall_memory`
calls (CLASSIFY phase pulling L1-L4 playbooks), runs occasionally
crash mid-flight with:

```
File "langgraph/graph/_branch.py", line 203, in _finish
    r if isinstance(r, Send) else self.ends[r] for r in result
                                  ~~~~~~~~~^^^
KeyError: 'model'
During task with name 'model' and id 'b1c8bf3c-...'
During task with name 'tools' and id '801050cc-...'
```

**When it happens**: bake-off v4 (with `recall_memory` mandated in
the CLASSIFY phase) crashed mid-run with this KeyError.  v3 (without
`recall_memory` mandated) ran cleanly to REPORT and 4 confirmed
findings.

**Root cause**: not fully traced.  Hypotheses:

1. `_TASK_RETURN_DIRECT` ContextVar (agent.py:86) propagates to
   sub-agents that ALSO have a `task` tool — sub-agent's task tool
   inherits `return_direct=True`.  Langgraph compiles the sub-agent's
   branch from `tools → END` (skipping `model`) for return_direct
   tools.  If middleware injection (`AutoRecallMiddleware`) modifies
   the post-tool state such that langgraph's routing function
   returns `'model'`, the branch's `ends` dict is missing that key.
2. Heavy context from KB playbook injection (~1500-2000 tokens
   added per recall_memory call) pushes gemma4:31b into a path
   where it emits tool calls in a sequence langgraph's branch
   compilation didn't anticipate.

**Workaround (v0.1 release)**: system prompt makes `recall_memory`
**opt-in** rather than mandatory.  v3-style runs (zero
`recall_memory` calls, pure first-principles) are stable.  The 6

them on-demand when first-principles exploration runs dry.

   - Likely involves changes to `_patched_build_task_tool` to

   - Reproduce against a minimal explorer config to isolate

## 13e. Audit-side conventions for promoted profiles

After ``promote_finding_to_audit`` lands a profile, the **audit
sub-agent** is responsible for executing the check on cron and
surfacing the provenance back to operators.  Two conventions:

### Convention #4 — ``audit_runs.collection_source``

When the audit runner kicks off a profile evaluation, the run
should be recorded in ``audit_runs`` with:

```python
recorder.record_run_start(
    run_id=run_id,
    agent_id="audit",
    source_channel=f"audit:{profile_name}",
    # Note: ``audit_runs.collection_source`` (added by
    # ``migrations/v0_22_audit_collection_source.py``) is reserved
    # for *data acquisition* lineage (live SSH / bundle / etc.) — the
    # audit run *consumes* whatever data the latest bundle / live
    # snapshot already landed.  Use ``source_channel`` for the
    # audit-specific dimension.
)
```

This lets downstream queries distinguish:
* `source_channel = 'cli'`               — user-typed interactive query
* `source_channel = 'audit:<profile>'`   — scheduled audit check
* `collection_source = 'live_ssh'`       — data was acquired via live SSH
* `collection_source = 'bundle:...'`     — data was acquired via offline ingest

### Convention #2 — surface provenance in alerts

When ``audit/profiles/<name>.md`` was auto-generated by
``promote_finding_to_audit``, it contains a ``provenance:`` block.
The audit runner should call:

```python
from olav.core.explorer import read_audit_profile_provenance

prov = read_audit_profile_provenance("audit/profiles/<name>.md")
if prov:
    # Embed into the alert / report:
    alert_body += (
        f"\nOriginally discovered by netops/explorer "
        f"on {prov['promoted_at']} (run {prov['source_run_id']}, "
        f"finding {prov['source_finding_id']}).\n"
    )
```

This closes the loop: an alert that fires today can be traced back
to the exploration that first observed the issue — giving on-call
the discovery context without leaving the report.

### Optional CLI helper

```bash
# Dry-run preview of all auto-generated profiles' provenance:
olav --agent audit "list all profiles + show their explorer provenance"
```

Implementation lives in ``olav.core.explorer.read_audit_profile_provenance``
(no LLM, pure Python text parsing; ~30 LOC; 3 unit tests).
