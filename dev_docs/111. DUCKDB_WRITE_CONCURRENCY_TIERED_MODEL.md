## 0. TL;DR

OLAV 的 DuckDB 写入并发问题**按部署形态分层解决**，不做"一刀切"：

| Tier | 部署形态 | 并发画像 | 写入并发策略 |
|---|---|---|---|
| **OSS**（olav / olav-netops） | 个人使用，单用户 | 偶发子进程并发（一个 AIMessage 批量 tool_call） | **保持现状：短连接 + 文件锁 + full-jitter 重试**。够用，不引入排队。 |
| **Enterprise**（olav-ent） | 团队使用，多用户 | 多进程/多用户持续争抢同一 DB | **daemon 排队 + web**，作为 `olav.enterprise.*` 功能。真串行化写者。 |

共同基座：先把散落的 ~40 个写站点收敛到一个统一的 `open_write_connection()` seam（平台核心 `src/olav`）。OSS 版这个 seam 内部就是"锁+重试"；Enterprise 版在同一个 seam 里注入"排队/broker"层。**收敛是两版共同的前提，排队只在企业版启用。**

## 1. 背景：当前写入并发模型

OLAV 当前对 DuckDB 的写入是**乐观并发**模型，没有任何中心化排队：

1. **短命连接** —— 写操作用 `with duckdb.connect(path, read_only=False)`，写完立即释放文件锁（`database.py:73-79` 明确警告不要用长持有的 `get_database()` 单例来写）。
2. **DuckDB 自身文件级写锁** 做跨进程"串行化"—— 但它**不排队**。失败者在 `connect()` 阶段直接拿到 `IOException: ... Could not set lock on file`，写从未发生（锁在跑任何 SQL 之前就失败，所以重试整个操作是安全的，无部分状态）。
3. **重试 + 退避**，两套独立实现：
   - 进程内 audit 写：`audit_recorder.py:250` `_run_with_retry`（模块级 `threading.Lock` + 指数退避，DDL 12 次 / DML 8 次）。
   - 跨子进程 skill 脚本写：`skill_runner.py:336`（full-jitter 退避重试 10 次，覆盖 presales/netops 所有经 `execute_skill_script` 的写）。

争用的**根因**（`skill_runner.py:30-43` 记录的实测）：deepagents/langgraph 一个 AIMessage 会并发派发多个 tool_call，每个 `execute_skill_script` 是独立子进程，N 个子进程竞争打开同一个 DuckDB 文件写。这是**跨进程**争用，不在任何单一进程内。

### 1.1 为什么"daemon 内 asyncio.Queue worker"不成立（对 OSS 而言）

一个直觉方案是：在 daemon（`daemon.py`，单进程 asyncio）里放一个 `asyncio.Queue` 写 worker，把所有写串行化。**这解决不了问题**，因为：

- 写入发生在 `execute_skill_script` 派生的**子进程**里，不在 daemon 事件循环内。asyncio.Queue 只能串行化"同一进程内投递的写"。
- daemon 是 **opt-in** 的（用户要显式 `olav daemon start`）。cron job、独立 CLI、presales 脚本单跑都没有 daemon。把写入依赖 daemon = 让可选组件变硬启动依赖，违背当前"短连接、无长驻持锁"设计。
- 有**多个独立 .duckdb 文件**（main / audit / users / registry …），一个全局队列会把本不冲突的写也串起来。

要让排队真正生效，daemon 必须变成**跨进程写 broker**（子进程的写走 IPC 投递给 daemon，daemon 用它独占的写连接串行落库）——这是大得多的架构改动。**这个改动只对"团队并发"有 ROI，因此归入企业版**（见 §3）。

## 2. 核心洞察：并发画像随部署形态分层

写入争用的严重程度**由部署形态决定**，不是一个固定属性：

- **个人使用（OSS 定位）**：一个用户、一个 agent 会话。并发只来自"一个 AIMessage 批量派发的 tool_call"这种**偶发、短窗口**的子进程 burst。实测（`skill_runner.py:75-87`）full-jitter 重试 + 更多次数已经可靠关闭 5+ 路碰撞，presales live e2e N=3 全绿。**对个人使用，重试就是正确的工程点** —— 简单、无常驻依赖、已验证收敛。

- **团队使用（Enterprise 定位）**：多个用户、多个 agent 会话、可能有共享服务端，**持续**争抢同一 DB。此时 burst 不再是偶发的，而是稳态的，重试的尾延迟和失败率会随并发度非线性恶化。团队场景才真正需要"排队/串行化写者"来给出可预测的写入延迟和零失败。

**结论**：给个人版套排队是过度工程（成本高、违背 opt-in 设计、收益低）；给团队版只留重试是欠工程（尾延迟不可控）。所以**分层**。

## 3. 决策（详见 ADR-0018）

### 3.1 OSS 版：保持重试，不引入排队

`olav` / `olav-netops` wheel **不包含**任何 daemon 写 broker、flock 门、中心化 worker。写入并发继续靠"短连接 + 文件锁 + full-jitter 重试"。理由见 §2（个人使用已被验证够用）。

### 3.2 Enterprise 版：daemon 排队 + web

以下作为 `olav.enterprise.*` 命名空间扩展功能，随 `olav-ent` 分发：

1. **daemon 写排队（write broker）** —— 团队部署下，daemon 升级为跨进程写代理：所有写者（含 `execute_skill_script` 子进程）把写请求经 IPC 投递给 daemon，daemon 用**单一独占写连接**串行落库（真 FIFO，无 failed-and-retry）。按 db_path 分片队列，避免过度串行化独立 DB。
2. **web** —— 团队协作的 web 前端/API 也归企业版（与 daemon 服务形态天然耦合：团队通过 web 共享一个后台服务）。

### 3.3 共同基座：写连接收敛到统一 seam

无论哪一版，先把散落写站点收敛到平台核心 `src/olav` 的一个 `open_write_connection(db_path, *, read_only=False, conn=None)`：

- **OSS**：seam 内部 = 复用 `audit_recorder` 的"按 db_path 分桶 threading.Lock + 短连接 + retryable 退避"（把该逻辑从 audit_recorder 私有方法提取为公共 helper，audit_recorder 反向复用它，消除两套互不感知的锁）。
- **Enterprise**：在**同一个 seam** 处注入 broker/flock 层——写者调用不变，只是 helper 在企业版加载时把"直接落库"换成"投递到 daemon 队列"。这让排队成为一个可插拔的 seam，而非侵入每个写站点。

> 关键设计原则：**收敛出一个写入 seam，让"个人=重试 / 团队=排队"变成同一个 seam 的两种实现**，而不是两套并行的写路径。

## 4. 企业版 daemon 排队的设计张力（诚实记录，待 §7 决议）

把 daemon 做成跨进程写 broker，有几个必须正视的张力：

1. **子进程如何投递写** —— `execute_skill_script` 的子进程当前直连 DuckDB。改成投递，需要子进程侧一个轻客户端（连 daemon 的 Unix socket，发写请求，收结果）。但 presales/netops 的写函数本体（`requirement_register.py` 等）执行的是任意 SQL/DDL，不是简单 KV，broker 协议要能承载"任意写事务"——这实际上接近一个 mini SQL-over-IPC 网关。
2. **DuckDB 本质上不是团队并发数据库** —— 单写者文件锁的设计前提就是"低并发"。给它套 broker 能串行化写，但读写混合、多用户、长事务下，团队规模一大，DuckDB 单文件仍是瓶颈。**可能的替代**：企业版直接把后端换成服务端 DB（Postgres / MotherDuck / DuckDB-over-HTTP），排队问题由数据库自身的 MVCC 解决，daemon 只做连接池。这条路避开了自建 broker 的复杂度，但引入后端迁移成本。
3. **flock 作为中间态** —— 不搭 broker 进程，改为写前对 per-db lockfile 做 `fcntl.flock(LOCK_EX)` 阻塞获取。flock **本身就排队**、天然跨进程（对子进程/CLI 都有效）、无常驻依赖。代价：写者从"失败即退避"变"阻塞等待"，需配获取超时防卡死。flock 可以作为企业版 broker 的"轻量版"，甚至 OSS 版将来若并发上升也能用。

**这三条是 §7 的未决问题**，本文档不锁定 broker 的具体形态，只锁定"排队是企业版功能、收敛 seam 是共同前提"这个方向。

## 5. 写站点盘点结果（收敛清单）

全仓库穷尽盘点结论（两个 Explore agent 交叉验证，2026-07-26）。**presales 与 netops 写同一个 `main.duckdb`（MAIN_DB_PATH）**——这正是收敛 seam 覆盖两域的依据。

### 5.1 规模

| 域 | 写站点 | 关键特征 |
|---|---|---|
| 平台核心 `src/olav` | ~18 | `audit_recorder` 是**唯一**已有锁+重试的（私有、仅 audit.duckdb） |
| presales `olav_presales/core/` | 23 | 全在 core 单一源；三份 skill 镜像不含 connect（脚本只 import core）→ 改 core 一处惠及全部 |
| netops | 20 逻辑 | skillpack 脚本裸连 MAIN_DB_PATH；**×3 镜像树 = 39 物理副本** |

### 5.2 "获取写连接"现有模式（3 类）

1. **直连 + context-manager**（`with duckdb.connect(path) as conn:`）—— 最多，改造最易。
2. **直连 + 持有型裸连接**（返回/赋值 conn，`finally: close()`，事务跨多次 execute）—— `config_evolve`、`audit_agent`、`fix_topology`、netops `landing.py`、`map_engine.py`（嵌套写连接）、`database.OlavDatabase`。
3. **经局部工厂**（`api_registry._open` / `registry_sync._open_main_db` / presales `projects._connect`）—— 改工厂内部一处惠及所有下游。

### 5.3 现成可复用 helper

**没有通用的**。最接近正确形态的是 `audit_recorder._run_with_retry`（短连接 + `_WRITE_LOCK` + 退避），但是私有、仅 audit.duckdb。`database.get_database()` 是**反面教材**（长持有独占锁单例，注释即警告不要拿它写）。→ 需新建 `open_write_connection`，把 audit_recorder 的锁+重试逻辑提取为公共实现。

### 5.4 收敛 helper 必须支持的语义（否则改不动）

- **连接注入**：`constraints.py:51`、`requirement_register.py:67` 是 `conn = conn or duckdb.connect(...)`。helper 必须"传入则复用且不关闭，否则新建并托管"。
- **持有型长事务**：`config_evolve`/`audit_agent`/`fix_topology`/`landing.py`/`map_engine.py` 事务跨多次 execute。需要 helper 的"返回可长期持有 conn"变体，或首批不纳入。
- **read_only 动态开关**：`migrate_add_platform_column.py`(`read_only=args.dry_run`)、`projects._connect`。helper 必须保留 `read_only` 形参。
- **必须排除**：`:memory:` 沙箱（`query_evidence.py` 两处，不碰 main.duckdb）；`database.get_database()` 单例。

### 5.5 镜像同步注意

- **presales 无镜像问题**：三份 workspace 镜像里的 presales 脚本只 import core，不含 connect。改 core 自动惠及三镜像。
- **netops 有三镜像**：skillpack 脚本（save_recipe/rebuild_views/netops_init/take_snapshot/map_engine）×3 棵树逐字节相同。收敛须改**打包源** `olav-netops/src/olav_netops/data/skillpack/.olav/workspace/` 再同步，或改成 `from olav_netops import open_write_connection`（presales 模式为范本，但引入脚本→包 import 依赖，需评估沙箱）。

## 6. 收敛落地路线（分批，可增量验证）

- **批 1（最高 ROI，低风险）**：新建 `open_write_connection`（OSS 内部=锁+重试）→ 切两个工厂 `api_registry._open` / `registry_sync._open_main_db`（下游自动受益）+ 所有 presales `with` 型站点（改 core 一处=三镜像全惠及）→ 跑 presales N=3 e2e 验证锁争用消失。
- **批 2**：netops skillpack `with` 型站点，处理三镜像同步。
- **批 3（需 helper 变体）**：持有型长事务 + 注入型 + 嵌套写（config_evolve/audit_agent/landing/map_engine/constraints/requirement_register injection 分支）。
- **收尾**：audit_recorder 反向复用公共 helper，统一两套锁。
- **企业版（独立轨道，收敛完成后）**：在 seam 处注入 daemon 排队 / flock 门，落 `olav.enterprise.*`。

**工作量重心不在写 helper，而在批 3 长事务站点 + netops 三镜像同步。**

## 7. 企业版排队形态：对比与分阶段决定（收敛自原未决问题 1）

**决策记录：ADR-0019（flock 优先、Postgres 兜底、broker 基本不选）。** 此处保留权衡摘要。

### 7.1 决定性前提：写负载画像不是 OLTP

OLAV 的写是"一次 agent 会话突发写一批"（presales 出一份 HLD/LLD、netops 存一次快照/拓扑）——**低频、突发、批量**。团队痛点是偶发 burst 撞锁，不是稳态高吞吐。因此"全局串行写单文件"的上限远未到瓶颈，这直接拉低了对高并发后端的真实需求，是下面推荐的基石。

### 7.2 三方对比

| 维度 | flock 阻塞门 | daemon write-broker | 换服务端后端 |
|---|---|---|---|
| 并发上限 | 中低（全局串行写单文件） | 中（串行+常驻连接省 open 开销） | **高**（MVCC，读不阻塞写） |
| 改造工作量 | **最小**（seam 里 +十几行） | **最大**（自建 SQL-over-IPC 网关+改子进程） | 大（SQL 方言抽象层） |
| 常驻/单点故障 | **无**（flock 是内核对象） | 有（daemon 崩=全团队写瘫） | 有（客户通常已有 DBA） |
| 进程崩溃恢复 | **内核自动放锁** | 需自建重启/恢复 | DB 自管 |
| 读被写阻塞 | 不解决（DuckDB 层仍互斥） | 可做但要额外实现 | **原生解决** |
| 沙箱影响 | 无（不碰子进程模型） | **削弱**（子进程要连 socket） | 无 |
| 数据主权（不出域） | **保留** | 保留 | Postgres 自托管保留；**MotherDuck 上云=可能 dealbreaker** |
| DuckDB 列存/快照优势 | **保留** | 保留 | **丢失**（Postgres）；MotherDuck 保留 |
| 治理插入点（审计/限流/配额） | 弱（seam 里可补） | **强**（天然集中点） | 中（DB 层做） |

### 7.3 分阶段决定

1. **企业版 v1 = flock 门**：装在收敛 seam 里，把"锁失败重试"升级成"跨进程真排队、零写失败"。改动最小、无常驻依赖、保留全部 DuckDB 优势和数据主权，匹配低频突发写画像，覆盖绝大多数团队。
2. **按需 v2 = Postgres 后端**：仅当实测超出 flock 单文件串行上限、或"读被写阻塞"成痛点时才上；数据主权优先自托管 Postgres，MotherDuck 仅当客户明确接受上云。
3. **broker 基本不选**：投入最大、上限中等、引入单点故障+削弱沙箱。唯一独特价值是"所有写过一个点"的治理能力，但这大部分可在 seam helper 内实现，无需独立进程。仅当出现强治理需求且无法在 seam 内满足时才重新评估。

收敛 seam 让三者都是"同一注入点的不同实现"，故 v1 选 flock **不锁死** v2 换后端的路。

## 7bis. 其余未决问题（Open Questions）

1. **flock 在生产文件系统的可靠性**：NFS/某些容器 overlay 上 `flock` 语义是否可靠？现代 NFSv4+Linux 可用，本地/单机容器无问题，但企业部署环境需逐一确认（ADR-0019 的 v1 前置验证项）。
2. **read/write 分离**：团队并发下读也会被写锁阻塞（DuckDB），是 v1→v2 升级的触发信号之一；v1(flock) 不解决，v2(Postgres) 原生解决。
3. **子进程投递协议**（仅当将来重启 broker 方向才相关）：`execute_skill_script` 子进程如何在保持沙箱隔离（`skill_runner.py:14-23`）的前提下投递任意写事务？
4. **收敛 seam 的 OSS↔Enterprise 注入机制**：用 entry-point 插件发现（符合 ADR-0002 允许的动态耦合方向），还是 helper 内 guarded optional import `olav.enterprise.*`？

## 8. 企业边界合规（ADR-0002 / feedback_presales_enterprise_boundary）

- daemon 写排队 + web 属 **ENTERPRISE tier**，落 `olav-ent/src/olav/enterprise/`，随 olav-ent 分发。
- `olav` / `olav-netops` wheel **零企业排队代码**（`packages = ["src/olav"]`，`enterprise/` 天然在包外）。
- 公开 GitHub 镜像：`publish_github_mirrors.py` 的 strip 清单已覆盖 `olav-ent/`；新增的企业排队模块在 `olav.enterprise.*` 下，自动被 strip，无需额外配置。
- 收敛 seam 本体（`open_write_connection` + OSS 锁+重试实现）属**平台核心 `src/olav`**，是公开的（OSS 也用它），只有"排队实现"进企业版。依赖方向 `olav-ent → olav` 合规。
