# 04. Ownership Manifest Design

**创建日期：** 2026-04-04  
**状态：** Proposed  
**依赖：** `99. REPO_BOUNDARY_AND_OWNERSHIP.md`

---

## 1. Purpose

本文定义一个**独立的 ownership manifest**，用于机器可读地描述 repo / package / path 的归属边界。

它的目标不是替代 runtime `MANIFEST.yaml`，而是补足以下能力：

1. 判定某个路径归谁负责
2. 区分 authoritative / transitional / misplaced
3. 指出过渡资产的迁移目标
4. 为脚本审计提供唯一输入

---

## 2. Non-Goals

ownership manifest **不负责**：

1. agent / skill 路由注册
2. workspace 运行时发现
3. tool 注入
4. dependency availability check
5. CLI 生命周期接线

这些职责继续由 `.olav/workspace/**/MANIFEST.yaml` 承担。

---

## 3. Why Not Reuse Existing `MANIFEST.yaml`

现有 `.olav/workspace/**/MANIFEST.yaml` 的语义是 runtime control-plane descriptor。

它当前表达的是：

- `kind`
- `name`
- `version`
- `route_keywords`
- `tools_dir`
- `requires`
- `provider_package`
- `config_namespace`

这些字段适合回答“如何运行和发现”，不适合回答“归谁拥有、是否临时、最终迁去哪里”。

因此必须分层：

- runtime manifest: `.olav/workspace/**/MANIFEST.yaml`
- ownership manifest: repo-level 单独文件

---

## 4. Design Decision

采用**单一 repo-level 清单文件**作为边界判定唯一输入。

推荐文件名：

- `ownership_manifest.yaml`

推荐放置位置：

- repo root

原因：

1. 路径匹配天然以 repo root 为基准
2. 方便脚本一次加载
3. 不和 `.olav/workspace/` 的 runtime descriptor 混层

---

## 5. Core Model

ownership manifest 采用**规则列表**模型，而不是按文件逐项枚举。

每条规则至少描述：

1. `pattern`: 路径匹配规则
2. `owner`: 归属单元
3. `class`: 资产类别
4. `status`: 当前状态

可选描述：

1. `target_repo`: 未来迁移目标
2. `notes`: 备注
3. `reason`: 为什么仍是过渡态
4. `enforced`: 是否作为 CI 强校验

---

## 6. Schema

```yaml
version: 1
default_owner: unknown

owners:
  - olav
  - olav-netops
  - olav-ent
  - olav-doc

classes:
  - platform
  - netops
  - enterprise
  - docs
  - website
  - runtime-workspace
  - transitional
  - generated

statuses:
  - authoritative
  - transitional
  - externalized
  - misplaced
  - generated

rules:
  - pattern: src/olav/**
    owner: olav
    class: platform
    status: authoritative
    enforced: true

  - pattern: olav-netops/src/**
    owner: olav-netops
    class: netops
    status: authoritative
    enforced: true

  - pattern: olav-ent/src/**
    owner: olav-ent
    class: enterprise
    status: authoritative
    enforced: true

  - pattern: docs/**
    owner: olav-doc
    class: docs
    status: transitional
    target_repo: olav-doc
    reason: root-and-olav-doc-dual-source-must-collapse
    enforced: false

  - pattern: mkdocs.yml
    owner: olav-doc
    class: docs
    status: transitional
    target_repo: olav-doc
    enforced: false

  - pattern: web/**
    owner: olav-doc
    class: website
    status: transitional
    target_repo: olav-doc
    enforced: false

  - pattern: .olav/workspace/**
    owner: olav
    class: runtime-workspace
    status: authoritative
    notes: workspace control plane and vendored assets are evaluated separately
    enforced: true
```

---

## 7. Field Semantics

### 7.1 `pattern`

使用 repo-root 相对路径 glob。

约束：

1. 不允许绝对路径
2. 规则按顺序匹配
3. 后续规则只用于更具体覆盖，不能无意中放大范围

### 7.2 `owner`

允许值必须来自顶层 `owners`。

当前允许：

- `olav`
- `olav-netops`
- `olav-ent`
- `olav-doc`

### 7.3 `class`

`class` 表示资产类别，不表示发布状态。

例如：

- `platform`
- `netops`
- `enterprise`
- `docs`
- `website`
- `runtime-workspace`

### 7.4 `status`

`status` 是最关键字段。

含义如下：

| 状态 | 含义 |
|---|---|
| `authoritative` | 该路径是当前权威源 |
| `transitional` | 当前仍存在，但不应长期保留在此处 |
| `externalized` | 该能力已迁出，root 只保留引用或兼容层 |
| `misplaced` | 路径不应存在于当前位置 |
| `generated` | 构建或运行时生成，不做 ownership 真值判断 |

### 7.5 `target_repo`

仅在 `status: transitional` 或 `status: misplaced` 时使用。

作用：

- 为脚本输出迁移目标
- 防止“知道有问题，但不知道该迁去哪”

### 7.6 `enforced`

是否作为 CI / 脚本强约束：

- `true`: 违规则报错
- `false`: 仅警告

推荐策略：

- `authoritative` 默认 `true`
- `transitional` 初期默认 `false`
- 稳定后再把关键规则提升为 `true`

---

## 8. Matching Rules

匹配顺序必须固定：

1. 从上到下
2. 最后一个匹配项覆盖前面的泛规则
3. 更具体的规则必须写在更后面

例如：

```yaml
rules:
  - pattern: .olav/workspace/**
    owner: olav
    class: runtime-workspace
    status: authoritative

  - pattern: .olav/workspace/ops/**
    owner: olav-netops
    class: netops
    status: transitional
    target_repo: olav-netops
```

这样脚本才能正确识别：

- `.olav/workspace/` 默认属于 `olav`
- 但 vendored `ops` 是 netops 过渡资产

---

## 9. Recommended Initial Rules for This Repo

建议第一版不要把所有路径都纳入，只覆盖边界敏感区域：

1. `src/olav/**`
2. `olav-netops/src/**`
3. `olav-ent/src/**`
4. `docs/**`
5. `mkdocs.yml`
6. `web/**`
7. `.olav/workspace/**`
8. `dev_docs/**`

推荐初始判断：

- `dev_docs/**` → `olav`, `class: platform`, `status: authoritative`
- `docs/**`, `mkdocs.yml`, `web/**` → `olav-doc`, `status: transitional`
- `.olav/workspace/ops/**` → `olav-netops`, `status: transitional`

---

## 10. Validation Model

ownership manifest 脚本应输出三类结果：

1. **OK**
   路径归属与 manifest 一致

2. **WARN**
   路径属于 `transitional`

3. **ERROR**
   未命中规则、命中 `misplaced`、或规则冲突

第一阶段不需要深入 AST 或 import graph，只做路径级审计。

第二阶段可增加：

1. 检查 `olav-doc` 规则路径是否被 root 同时维护
2. 检查 `olav -> olav-netops` 的硬 import 是否违反 99 号文档约束
3. 检查过渡资产是否超过设定期限

---

## 12. Initial Adoption Plan

建议分三步落地：

### Step 1

仅创建 `ownership_manifest.yaml`，覆盖最关键路径。

### Step 2

增加一个只读校验脚本，输出 OK / WARN / ERROR。

### Step 3

在 root docs / web 与 vendored netops 资产收敛后，再把部分规则提升为 CI 强校验。

---

## 13. Final Position

最终结论如下：

1. 只用 manifest 是可行的。
2. 但必须使用**独立 ownership manifest**，而不是复用现有 runtime `MANIFEST.yaml`。
3. ownership manifest 的主职责是路径归属和过渡状态治理。
4. runtime `MANIFEST.yaml` 的主职责仍然是 workspace discovery 和 router/runtime 接线。
5. 两者不能混为一个 schema，否则会把 runtime 与 governance 两套语义缠在一起。
