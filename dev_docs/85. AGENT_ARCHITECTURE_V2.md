## 1. 背景与问题诊断

### 1.1 现状清单

|---|---|---|---|
| audit | `audit-orchestrator` | `audit` | 内外名不一致 |

### 1.2 根因

- **R70（2026-04-23，commit `14d41cab`）** 清理了 `config/system` 整体（含 `check_health.py`、`audit_workspace.py`、`analyze_logs.py`）和 `devops/references/`，但未完整清理 devops AGENT.md 本体，导致两份并存。
- topology 顶层 agent 是 R-AGENT-HIERARCHY Phase A（dev_docs/73）后的遗留物，当时 netops/topology 子 agent 已接管其全部功能，顶层只是忘记删除。
- `investigate` 是早期 fault localization 的单工具 wrapper，analyzer 获得 `query_evidence` 后已经冗余。
- `services` 与 `devops/infra` 在 API 调用层完全重叠；生命周期管理（register/deploy/stop）属于平台管理职责，不是 DevOps 脚本工作。
- `explorer` 的设计动机（dev_docs/83）是弥补 audit 模式的空白（自主探索 vs 固定 Profile），本质是 audit 域的一种模式。

## 3. 关键决策说明

### 3.1 investigate 删除

`investigate` 只有 `query_evidence` + `format_and_export` 两个工具。  
`analyzer` 已包含 `query_evidence`，且 analyzer 的 Workflow D（深度调查报告）完全覆盖 investigate 的使用场景。

**结论**：删除 `investigate` 子 agent，orchestrator 将"why/log/syslog/fault"路由改为 `task("analyzer", ...)`。

**边界说明**：analyzer 的 `query_evidence` 用于日志/config 的文本搜索，与 analyzer 的 SQL 查询互补，不需要专门的子 agent 中转。

### 3.2 explorer 归属 audit

explorer 的定位（dev_docs/83）："弥补 audit 两种模式之间的空白——结构化 Profile 和假设驱动的 investigate——之外的第三种：自主探索。"

| 模式 | 子 agent | 触发条件 |
|---|---|---|
| 结构化 Profile | runner | 定时 / 手动执行固定检查项 |
| 开放探索 | **explorer**（迁入） | "找问题" / 无具体方向 |
| 变更计划 / 报告 | 委托给 netops/analyzer | 有明确目标 |

explorer 迁入 audit 后，netops orchestrator 对 explorer 的路由改为：
```
"自主巡检 / 找问题 / 无目标审计" → olav --agent audit "开始自主探索"
```
或 audit orchestrator 内部 `task("explorer", ...)`。

**注意**：explorer 工具集使用 `netops.*` 视图，迁移后需在 SKILL.md 的 `allowed_tables` 中显式声明，并在 audit AGENT.md 中说明其网络数据依赖。

### 3.3 services 合并到 devops

`services`（生命周期）和 `devops/infra`（API 集成查询）的边界：

| 工具 | 当前位置 | 迁移后 |
|---|---|---|
| `register_service` | services | devops/services |
| `deploy_service` | services | devops/services |
| `stop_service` | services | devops/services |
| `api_request`（生命周期用） | services | devops/services |
| `api_request`（集成查询用） | devops/infra | devops/infra（不变）|
| `service_health` | devops/infra | devops/infra（不变）|

`services` agent 路由关键词（deploy/register/stop）并入 devops 的 `route_keywords`。  
用户侧：`olav --agent devops "部署 NetBox"` 替代 `olav --agent services "部署 NetBox"`。

**不合并的理由**（反驳）：`register_service` 和 `deploy_service` 是有审计要求的操作（每次必须写 audit_tool_calls 行），工具本身已经满足 CLAUDE.md 的 MCP 条件，放在 devops 下不改变这一点。

### 3.4 admin 主 agent 定位 — 自运维 + 自开发

`core/admin` 子 agent 当前职责已超出"通用查询入口"。更重要的是，R70 删掉的 `config/system` agent 原本已经包含了完整的平台自开发能力（`write_skill_code`、`generate_skill_config`、`read_api_schema`、`audit_workspace`）——这些功能需要独立的主 agent 承载，而非挂在 core 下。

**admin 的两个关切：**

| 子 agent | 问题 | 代表工具 |
|---|---|---|
| `ops` | 系统现在运行得怎么样？ | check_health、export_logs、manage_cron |
| `developer` | 如何扩展 / 修复平台？ | skill install、audit_workspace、scaffold_skill、read_api_schema |

**设计动机：**
1. **独立路由**：`olav --agent admin "导出最近 24 小时日志"` / `"帮我安装 olav-netops"` 不经过 core
2. **权限隔离**：admin 的写操作（文件写入、进程探针）风险高于 core 查询，单独 agent 便于 HITL 门控
3. **自开发闭环**：OLAV 用户可以通过 admin/developer 让 OLAV 帮自己写新的 tool、生成 SKILL.md、安装 skill pack，实现平台能力的自我扩展

**git 历史根据**：`config/system` agent（删于 `14d41cab`）已包含 `read_api_schema`、`write_skill_code`、`generate_skill_config`，说明早期设计已有此意图，R70 清理时因重组而误删。

### 3.5 admin/developer 子 agent 设计

```yaml
name: developer
description: "OLAV self-development — install/manage skill packs, scaffold new tools and agents,
  audit workspace consistency, parse external API schemas to generate integrations"
tools:
  - skill_install       # wrap: olav skill install <path|url>
  - skill_list          # wrap: olav skill list
  - skill_status        # wrap: olav skill status <name>
  - audit_workspace     # 从 git 历史恢复：检查 SKILL.md 语法、@tool 冲突、broken refs
  - write_workspace_file # 创建/编辑 SKILL.md、guide.yaml、tool .py 骨架
  - read_api_schema     # 从 git 历史恢复：解析 OpenAPI/WSDL → 生成集成方案
  - scaffold_skill      # 新建：从 API schema 自动生成 SKILL.md + tool 骨架
```

skill_install/list/status 是 Python wrapper，调用 `src/olav/cli/commands/skill.py`。  
满足 CLAUDE.md 的 MCP 条件：skill install 是 sandbox-external write（写入 `.olav/workspace/`），需要审计行。

## 5. 产品化命名规范

### 5.1 命名原则

面向网络运维团队的产品，agent 命名需满足：

1. **主 agent 用领域术语**：运维工程师直接在 CLI 输入，须一眼明白用途
2. **子 agent 用行为者名词**：统一 `-er`/`-or` 后缀（actor noun），表达"这个 agent 是做 X 的角色"
3. **无父级前缀**：`audit-author` → `author`，前缀是目录结构，不应进入名字
4. **无下划线**：`api_query` → `api`，用于 `task("api", ...)` 时更自然
5. **无缩写歧义**：`sim` 在英文中有 "similar"/"simulated" 等多义，须展开

### 5.2 主 Agent 命名

| 当前 | 产品名 | 说明 |
|---|---|---|
| `core` | **`core`** | 保留。默认入口，用户极少直接输入 |
| `netops` | **`netops`** | 保留。网络运维领域标准术语，目标用户熟悉 |
| `devops` | **`devops`** | 保留。行业通用术语，涵盖脚本+服务集成 |
| `audit` | **`audit`** | 修正（当前 AGENT.md 内部名是 `audit-orchestrator`） |
| `admin` | **`admin`** | 新建。IT 运维场景下 `admin` 语义明确 |
| `topology`（顶层） | 删除 | 冗余，功能由 netops/topology 覆盖 |
| `services` | 合并 → devops/services | 不再作为主 agent |

CLI 使用体验：
```bash
olav "..."                        # → core（默认）
olav --agent netops "..."         # 网络运维
olav --agent devops "..."         # 脚本生成 + 服务集成
olav --agent audit "..."          # 审计报告
olav --agent admin "..."          # 平台管理
```

### 5.4 命名决策说明

**为什么 `sim` → `simulator` 而非保留短名？**  
`sim` 在英文中有 SIM 卡、similar、simulation 等含义，在 LLM prompt 上下文中容易造成解析歧义。`simulator` 多 2 个 token，换来零歧义，值得。

**为什么 `ingest` → `importer` 而非 `ingester`？**  
`ingester` 是 ETL 行话，运维工程师不熟悉。`importer` 对应 "我把离线数据导入系统" 这个操作，更直观。

**为什么 `scripts` 不改成 `scripter`？**  
`scripts` 是产出物名词（这个 agent 生成脚本），而不是角色名词。`scripter` 反而有歧义（剧本作者）。保持 `scripts` 作为"产出集合"的命名是合理的。

**为什么 `platform` 改成 `health`？**  
`admin/platform` 的实际工作是检查系统健康和导出日志，`health` 直接描述职责。`platform` 太宽泛，可能与整个 OLAV Platform 概念混淆。

**为什么主 agent 不用中文或全拼？**  
目标用户是英文语境下的网络工程师，CLI 参数使用英文是行业惯例。内部提示词可以是中文。

## 6. 实施顺序

按风险从低到高，分 4 步：

**Step 1 — 纯改名（无功能影响）**
- 按 §5.3 改名表执行：audit 系列去前缀、`sim`→`simulator`、`collect`→`collector`、`ingest`→`importer`、`api_query`→`api`、`db_query`→`db`
- 同步更新所有 orchestrator prompt 和 dispatch guide 里的 `task("旧名", ...)` 引用

**Step 2 — 删除冗余（无功能损失）**
- 删顶层 topology
- 删 investigate（确认 orchestrator 改路由后）
- 删 olav-netops 中的 devops 副本

**Step 3 — 迁移重组（有路由变更）**
- services → devops/services
- explorer → audit/explorer
- core/admin 职责迁移至 admin 主 agent

**Step 4 — 新建 admin（净增功能）**
- platform 子 agent：恢复 check_health + 新建 export_logs
- skills 子 agent：包装 skill install/list/status
- `olav health` CLI 命令

## 6. export_logs 工具设计

```python
def export_logs(
    since: str | None = None,   # "24h" / "7d" / ISO 8601 datetime
    until: str | None = None,   # ISO 8601 datetime，默认 now
    include: list[str] = None,  # ["all"] 或 ["web","olav","nornir","alerts","audit"]
    dest_dir: str | None = None,  # 默认 exports/logs/

```

打包内容：
```
olav_logs_<since>_<until>.tar.gz
├── web.log
├── olav.log
├── nornir.log
├── alerts.json
└── audit/
    ├── runs.csv          # audit_runs WHERE start_time BETWEEN since AND until
    ├── tool_calls.csv    # audit_tool_calls（关联 run_id）
    └── events.csv        # audit_events（关联 run_id）
```
