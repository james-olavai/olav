# 109. Presales Minimal-Tool Profile Model — read profile · query docs · append · compute · render

**Status:** design + staged migration (2026-07-24). **Culminates** dev_docs/107
(bid-grade docs) + 108 (profile-first + constraints + lifecycle). **Simplifies** the
authoring machinery of 107/108 into a minimal tool set once the profile is the
medium.

---

## 1. The insight

With the profile as the single structured artifact and the document a deterministic
rendering of it (dev_docs/108), most of the authoring machinery built in 107/108
is redundant — it existed to compensate for the LLM writing free-form chapters.
The LLM's real job collapses to:

> **read the profile · query the documents · append to the profile (ReAct) ·
> invoke a hard-core tool when a value must be computed · render.**

The LLM never hand-writes an IP, a matrix, or a per-chapter loop. Everything the LLM
cannot do reliably (allocation, sizing, graph validation, aggregation, rendering,
grading) is a deterministic tool; everything else is "read/append the profile."

## 2. The loop

```
loop (ReAct):
  read the profile view          (current structured design)
  → query_documents              (chunk recall / read_file over ingested materials)
  → profile_add(kind=…, …)       (append a requirement / constraint / decision /
                                  response / chapter body — typed, validated)
  → OR a hard-core tool          (allocate_addressing / compute_sizing /
                                  validate_topology / generate_bom — results are
                                  written back into the profile)
until render_document reports the deterministic gates pass
  → render_document(doc_type)    (profile → HLD/LLD markdown + run all gates)
```

The completeness / coverage / constraint / citation gates run on render and tell
the LLM exactly what is still missing; the LLM appends it and re-renders. No
bespoke per-chapter step machine — the gate result IS the loop's control signal.

## 3. Minimal tool set

**Hard-core (deterministic — the LLM cannot do these reliably):**
- `allocate_addressing` — exact IP/subnet allocation within the approved ranges.
- `compute_sizing` — oversubscription / device counts / capacity, each sourced.
- `validate_topology` — networkx connectivity / redundancy / SPOF over to_be.
- `generate_bom` — aggregate to_be topology × catalog datasheet specs.
- `render_document(doc_type)` — profile → HLD/LLD markdown; runs ALL gates
  (content-completeness, coverage, constraint-honoured, citation, placeholders);
  returns pass/fail + what's missing.
- (analyst) recency-weighted extraction — newer materials win on conflict (§108-addendum).

**Profile read/write + evidence:**
- `profile_view` — the readable assembled profile (requirements + constraints +
  decisions + selection + topology + per-section status). What the LLM reads.
- `query_documents` — semantic recall over ingested materials.
- `profile_add(kind, …)` — the ONE typed append (kind ∈ requirement | constraint |
  decision | response | chapter). Validates arg shape at the boundary.

**Lifecycle (light):** `lifecycle_status`, `approve_profile` (the ①/② gates).

That is ~8 uniform tools, versus the ~15 bespoke scripts of 107/108 — a large
reduction in the small-model tool-selection surface.

## 4. Profile read/write contract

- **Write** — `profile_add(kind, …)` is the single append. It dispatches to the
  existing typed stores (they survive as the implementation):
  requirement → `requirement_register.add_requirement_item`; constraint →
  `constraints.add_constraint`; decision → `record_design(kind=decision)` (with the
  rationale+source coercion guard); response → `set_requirement_response`; chapter →
  `_persist_and_merge_chapters`. One tool, typed dispatch, shape validated.
- **Read** — `profile_view` assembles the current structured design into a readable
  summary (the LLM reads it instead of calling build_chapter_brief per chapter).
- **Render** — `render_document(doc_type)` is generate_hld/generate_lld behind one
  verb; it assembles from the accumulated profile + computed sections and grades.

## 5. What collapses vs survives

| Collapses (into profile_add / render_document / profile_view) | Survives (hard-core / renderers / gates / stores) |
|---|---|
| extract_requirements, record_constraint, record_design, respond_requirement | → `profile_add(kind=…)` — the typed stores stay as impl |
| build_chapter_brief | → `profile_view` (LLM reads the profile) |
| author_hld_chapter (step machine), generate_hld chapter orchestration | → `profile_add(kind=chapter)` + `render_document`; gate result drives the loop |
| generate_hld / generate_lld (as separate verbs) | → `render_document(doc_type)` |
| — | allocate_addressing, compute_sizing, validate_topology, generate_bom |
| — | the renderers (topology/failure-domain/capacity/BOM/matrix) + all gates |
| — | constraints/decisions/requirements/chapters DB stores; lifecycle gates |

Nothing hard is thrown away — the collapse is of *orchestration scripts*, not of
the deterministic core.

## 6. Single `designer` agent

With the tool set this small and uniform, the architect/engineer split is no longer
warranted (their only difference was the doc they authored). Merge them into one
**`designer`** sub-agent; HLD vs LLD is `render_document(doc_type=…)` + the lifecycle
stage. Presales sub-agents become: **surveyor** (ingest) · **analyst** (research /
selection / recency-weighted extraction) · **designer** (HLD+LLD via the minimal
tools) · **publisher** — 4 sub-agents, each a small focused menu.

## 7. Migration path (staged, each validated green)

**Stage A — unified tool facade (low risk, no behaviour change):** add `profile_add`,
`render_document`, `profile_view` (core + scripts) dispatching to the existing
functions; keep the old scripts working. Prove parity.

**Stage B — designer agent:** create `designer/` (tools: execute_skill_script,
olav_recall_memory, read_file; scripts: profile_view, query_documents, profile_add,
render_document, allocate_addressing, compute_sizing, validate_topology,
generate_bom, + lifecycle recall). Point the orchestrator's subagents at
surveyor/analyst/designer/publisher. Migrate the architect+engineer guides/profiles.

**Stage C — retire the collapsed scripts:** remove extract_requirements /
record_constraint / record_design / respond_requirement / build_chapter_brief /
author_hld_chapter / generate_hld / generate_lld from the workspace once
profile_add/render_document cover them; update tests + governance (subagent set:
architect/engineer → designer). Keep the CORE modules (they are the impl behind the
unified tools).

## 8. Definition of Done / testing

- Parity: `profile_add(kind=X)` produces the same rows as the old typed script;
  `render_document(doc_type=X)` produces the same document + gates as
  generate_hld/generate_lld. Integration via execute_skill_script.
- Reachability: the `designer` agent routed + declared; its scripts carry the
  `execute_skill_script(skill_name="designer")` recipe; the retired scripts gone.
- Governance: subagent set updated (v018), reachability, drift, ownership 0 ERROR.
- Behavioural: the campus HLD/LLD via the designer at N≥3 still reaches graded-pass.

## 9. Open questions

1. `profile_view` format — markdown summary vs a structured JSON the LLM parses?
   Start with a compact markdown summary (small-model-friendly) + section status.
2. Does `render_document` auto-run the hard-core (allocate/size/validate) if the
   profile lacks them, or must the LLM call them first? Start explicit (the LLM
   calls them; render reports if missing) — keeps the loop legible.
3. analyst vs designer boundary — analyst stays research/selection + recency
   extraction; designer consumes the analyst's selection from the profile.
