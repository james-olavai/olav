## Ch1 — Fresh install (5 min)

**Goal**: zero to web UI in 5 minutes.

```bash
mkdir ~/olav-demo && cd ~/olav-demo
python3 -m venv .venv && source .venv/bin/activate
```

**Talking point**: one-command skill install — `pip install` + workspace
deploy + agent registration in a single step (no manual venv juggling).

### Ch2b — Offline import from OLAV canonical bundle archive (no live devices)

**Goal**: ingest historical/offline data without SSH — same downstream
path as live collection. Use this when demo hardware is unavailable or
to show the scale of a real campus network.

> **Demo data**: `tmp/anon/` contains 15 anonymized weekly OLAV canonical
> bundle archives (2025-11-02 → 2026-02-15) from a 13-site campus network.
> Format: `home/admin.demo/network_data/<command>/<device_fqdn>` (NOT RANCID format).
> **Always pass absolute path**: use `$(pwd)/tmp/anon/...` or full path.
> Hostnames anonymized to site prefixes: `delta-`, `gamma-`, `beta-`,
> `alpha-`, `epsilon-`, `eta-`, `zeta-`, `kappa-`, `iota-`, `theta-`,
> `lambda-`, `mu-`, `nu-`. IPs SHA-256 mapped to `10.x.x.x` (topology
> preserved). Domain: `net.demo.internal`.

```bash
# Import the most recent weekly backup (→ netops/importer sub-agent)
# NOTE: Always use absolute path — relative paths fail in script subprocess context
BUNDLE_DIR=$(pwd)/tmp/anon
olav --agent netops \
  "Import the network backup at $BUNDLE_DIR/network_data_backup_2026-02-15.tar.gz"
# Sub-agent pipeline:
#   1. survey_bundle(path)   → format=olav_canonical, 13+ sites, 100+ hosts
#   2. validate_bundle(path) → sha256 + manifest ok
#   3. ingest_snapshot(path) → lands in raw_output_store + structured views

# Import a second week for drift comparison
olav --agent netops \
  "Import the network backup at $BUNDLE_DIR/network_data_backup_2026-02-08.tar.gz"

# Verify scale of imported data
olav "How many devices were imported? Show the site distribution."
# → 100+ devices across 13 anonymized campus sites
```

**Verification**:

**Talking point**: `importer` sub-agent handles OLAV canonical bundles,

## Ch4 — Knowledge Base (declarative memory, 5 min)

**Goal**: hand-author team rules in YAML and have AutoRecall surface
them.

```bash
# 1. Author a rule — drop anywhere under .olav/workspace; the importer
#    rglob's *.guide.yaml (no fixed `guides/` directory required).
#    Recommended locations:
#      .olav/workspace/<agent>/guides/    — agent-scoped
#      .olav/workspace/<agent>/<skill>/references/  — per-skill (portable
#                                                    via SKILL.md
#                                                    `dynamic_context`)
cat > .olav/workspace/netops/guides/netbox_naming.guide.yaml <<'EOF'
schema_version: 2
intent: netbox_naming_convention
agent: netops
source_tier: team        # vendor | platform | team | user (dev_docs/75).
                          # Team-tier (priority 6 → weight 1.33) beats
                          # user-tier R102 commits (priority 3 → 0.83).
keywords: [netbox, naming, hostname, 命名, 规范]
body: |
  Device hostnames in NetBox follow <site>-<role>-<n> pattern.
  Example: us-west-border-01.  Status defaults to active.
EOF

# 2. Prime into LanceDB
olav kb import-guides .olav/workspace
# → "✓ guides primed: N (K skipped, P orphan(s) pruned)"
#   The orphan-prune phase deletes memory entries whose source YAML
#   was removed — keeps AutoRecall in sync with disk truth.

# 3. Inspect the live KB (new in dev_docs/75)
olav kb list-guides --tier team
# → table of team-tier guides; --tier user surfaces R102 commits
olav kb show netbox_naming_convention
# → prints the YAML; copy/paste for git PR promotion to platform tier

# 4. Verify recall
olav --agent netops "What's our NetBox naming convention?"

# 5. Decommission a guide (audit-trail mandatory) — dev_docs/75
olav kb remove netbox_naming_convention --reason "moved to org-wide repo"
# → tombstone YAML (<intent>.guide.yaml.removed) + LanceDB row deleted
#   + kb_audit/<ts>_remove_<intent>.yaml row written (actor + body_sha256
#   + reason + timestamp).  Reprime will not resurrect.
```

**Verification**:
```bash
python -c "
import lancedb
db = lancedb.connect('.olav/databases/memory.lance')
df = db.open_table('memory').to_pandas()
print(df[df['id']=='guide_netops_netbox_naming_convention'].iloc[0]['text'][:120])
"
# → echoes the body
```

**Talking point**: declarative `*.guide.yaml` is the **version-controlled,
schema-bound, team-shareable** memory path — pairs with R102
conversational ingestion (Ch5) and L1 implicit capture. Per-skill
`references/` (2026-05-13) keeps guides portable across agent
frameworks while OLAV's rglob importer still finds them.

## Ch6 — Ops deep analysis + writer pipeline (8 min)

**Goal**: netops agent does multi-step BGP / OSPF / topology analysis,
delegates config-layer eval to `sim` (Batfish-backed) and report
polish + topology Mermaid embedding to `writer`.

> **Sub-agent routing (rev ~306, 2026-05-26)**: `analyzer` and `reporter`
> are now two separate sub-agents — both were previously merged in `analyzer`.
> The orchestrator routes by intent keyword:
> - "plan / add / change / modify / 变更" → **analyzer** (Mode A: change-plan drafter)
> - "investigate / why / drift / blast-radius / audit" → **reporter** (Mode B+C)

```bash
# Mode B: investigation (→ reporter sub-agent)
olav --agent netops "Investigate BGP convergence — which sessions are unstable?"

# Mode A: change planning (→ analyzer sub-agent)
olav --agent netops "Plan a change: add R5 to area 0, peer with R3+R4. \
  Emit a change plan markdown under exports/reports/."

# Drift detection (→ reporter, uses diff_snapshots)
olav --agent netops "Snapshot the network for change comparison"
# (make a config change on R2)
olav --agent netops "Detect any drift on R2 since last snapshot"
```

**Verification**:
* `execute_sql` against `v_bgp_neighbors_auto` returns rows
* Analyzer emits a structured topology table inside the change plan
  (so downstream renderers can transform it without re-querying)
* Writer subagent polishes the markdown and embeds a Mermaid block
  under `### Diagram` via `render_topology_mermaid` (pure transformer
  — no SQL access from writer, by design)
* `olav --agent netops "list snapshots"` shows new snapshot id
* `diff_snapshots` in `reporter` handles snapshot-vs-snapshot deltas

### Parser learning (learner sub-agent)

```bash
# After netops_init or bundle import, if parse coverage < 100%:
cat .olav/config/unsupported.json  # shows unparseable (platform, command) pairs

# Teach OLAV a missing parser
olav --agent netops "/learn_cmd cisco_ios 'show spanning-tree'"
# → learner: captures raw output → drafts TextFSM template →
#   freezes to .olav/templates/cisco_ios/show_spanning_tree.textfsm
#   Next netops_init auto-picks it up via standard parse chain.

# Verify frozen parser
ls .olav/templates/cisco_ios/
```

**Verification**: `cat .olav/templates/cisco_ios/show_spanning_tree.textfsm`
shows a valid TextFSM template. Next collection run: `show spanning-tree`
no longer appears in `unsupported.json`.

**Talking point**: parse coverage is never 100% out of the box — vendors
drift, OS versions change. `/learn_cmd` learns once (LLM drafts TextFSM,
freeze to disk), every subsequent pipeline run inherits the template with
zero additional LLM cost. This is the self-healing parser layer.

### Topology subagent (dedicated topological queries)

```bash
olav --agent netops "Show the full L2+L3 topology as a Mermaid diagram"
# → topology subagent: multi-hop graph traversal, color-coded by tier
olav --agent netops "Which devices are single-points-of-failure in the campus topology?"
# → topology: graph analysis → reports nodes with no redundant path
```

### Simulator subagent (Batfish config-layer evaluation)

```bash
# Analyzer delegates to simulator automatically during change planning.
# Direct invocation when you need a pure config-layer question:
olav --agent netops "Does R1's route-map outbound to R4 permit the 10.0.0.0/8 summary?"
# → orchestrator → simulator: batfish_q(question='reachability', ...)
#   No SQL, no live device — pure config analysis against frozen snapshot.
```

**Talking point**: netops has 8 sub-agents (collector / analyzer /
reporter / simulator / importer / topology / learner / writer); analyzer
and reporter are intentionally split to keep per-sub-agent context budget
under control on small models (FINDING-21: each sub-agent ≤ 7 tools).
Sim is Batfish-backed config-layer eval; writer is a pure-transformer
polish stage with no DB access. Lab/CAB lives in `olav-ent`.

## Ch9 — Audit (5 min)

**Goal**: show all 4 audit sub-agents — runner, author, explorer, curator.

> Audit orchestrator routes to 4 sub-agents (rev ~306):
> - **runner** — run a Profile → Markdown report
> - **author** — create / extend / retune profiles; list profiles
> - **explorer** — open-ended "find issues" investigation (migrated from netops 2026-05-19)
> - **curator** — schema discovery, TextFSM learning, trace analysis

```bash
# author: list available profiles
olav --agent audit "List available audit profiles"
# → calls list_profiles.py (terminal: one call, present table, stop)

# runner: execute a profile
olav --agent audit "Run the bgp_health profile for the last 24 hours"
# → run_map_engine → render_report → returns path + executive summary

# author: create a new profile
olav --agent audit "Create a CPU utilization check profile for all routers"
# → execute_sql(get_schema_context=True) → test_map_query → create_profile_atomic

# explorer: open-ended investigation (no specific question)
olav --agent audit "What problems does this network have? Find any anomalies."
# → explorer sub-agent: queries SQL + syslog freely, writes findings
#   incrementally to exports/reports/<name>.md (mode='append')
# With anon campus data (Ch2b): 13-site campus, 100+ devices — real findings

# curator: schema discovery and TextFSM field mapping
olav --agent audit "What columns are available for BGP session analysis?"
# → curator: discover_view_schemas() + sync_schema_reference()
#   → maps v_show_ip_bgp_summary_auto fields to standard BGP concepts

olav --agent audit "Analyze recent audit failures to improve the bgp_health profile"
# → curator: trace_learner(hours=168) → mines audit.duckdb for failure
```

## Ch10 — Services (CSV-intermediate sync to NetBox)

**Goal**: demo the canonical netops ↔ services handoff via CSV
intermediate.  netops (read side) shapes the data; services (write
side) handles NetBox API quirks.  The CSV is the audit-friendly
contract between them — git-diff-able, replayable across
environments, human-reviewable before any push.

**Two phases**:
* **Ch10a (default, no external dep, ~5 min)** — netops exports
  NetBox-shaped CSV.  Validates the read pipeline + column mapping
  without needing a real NetBox.
* **Ch10b (full path, ~30-40 min, optional)** — `olav --agent
  services "deploy netbox"` starts the official netbox-docker
  stack; services agent imports the CSV via NetBox REST API.
  Skip unless you're validating the write side end-to-end.

### Ch10a — netops → CSV (no external services)

```bash
# 1. netops exports devices via the deterministic slash command
#    (no LLM in the loop — the script wraps the SQL + CSV write atomically
#    so gemma4 nothink doesn't have to chain execute_sql + format_and_export,
#    which it does unreliably).
olav --agent netops "/export_netbox_csv"
# → writes exports/netbox_devices.csv in <1s
# Optional: --filename my_export, --tenant team-xxx

# 2. Inspect the CSV — operator's HITL gate
head -5 exports/netbox_devices.csv
wc -l exports/netbox_devices.csv     # 1 header + N device rows
```

The slash command is a thin Python wrapper (`netops/export_netbox_csv/run.py`);
the canonical column mapping + SQL + tenant resolution lives in the
`netbox_csv_export.guide.yaml` platform-tier guide (source-of-truth for
operators who want to edit the export shape).

**Verification**:
* `exports/netbox_devices.csv` exists, ≥ 7 lines (header + 6 devices)
* Header includes `name, device_role, manufacturer, device_type,
  primary_ip4, platform, site, status, tenant, snapshot_id,
  exported_at` (exact column set determined by `netbox_csv_export`
  guide)
* `tenant` column = `acme-network-ops` on every row (sourced from
  the team-tier `netbox_tenant_default` guide written in Ch4)
* `snapshot_id` matches the latest `netops.v_snapshots_auto` row

**Talking point**: CSV-as-contract decouples the two agents.
netops only knows OLAV's `netops.devices` schema + the column
mapping (lives in `netbox_csv_export.guide.yaml`, source_tier:
platform).  services only knows NetBox's API + foreign-key order
(site → device_type → device).  Neither sees the other's quirks;
a single CSV change-set is the unit of review + git audit.

### Ch10b — services → NetBox import dry-run (validates CSV; no HTTP)

```bash
# After Ch10a produced exports/netbox_devices.csv, validate it
# against NetBox's import contract WITHOUT touching any service.
olav --agent devops "/import_netbox_csv"
# → writes exports/reports/netbox_import_dry_run.md
# → exit 0  if all rows would create cleanly
# → exit 1  if any row fails validation (operator's HITL gate)
# → exit 2  on accidental --write (stub guard)

# Optional: custom CSV path / report path
olav --agent devops "/import_netbox_csv --csv exports/my.csv --report exports/reports/my_dryrun.md"
```

**Verification**:
* Report `exports/reports/netbox_import_dry_run.md` is written with:
  - header column-check (✓ matches contract, or `Header mismatch`
    listing missing/extra columns + order drift)
  - per-row verdict table — `would_create` or `skip` with reason
  - top-line summary (`Total / Would create / Skipped / Verdict`)
* Validation catches: empty required field, non-IPv4 `primary_ip4`,
  unknown `status`, non-ISO `exported_at`, column drift
* `--write` errors out (NotImplemented stub — real POST awaits the
  next iteration once the services agent has `netbox_dcim_create_*`
  per-tier write tools)

**Talking point**: dry-run = audit-friendly gate.  The same CSV can
be reviewed in git diff, dry-run validated for shape, and (later)
pushed by `--write`.  No accidental writes; no validation-by-failure
at NetBox's REST layer.

### Ch10c — real NetBox container (full sync, live)

Brings up a real NetBox stack, pushes the Ch10a CSV through the
Ch10b validator, then issues the actual POSTs.

```bash
# 1. Start NetBox stack (~30s cold-start on cached images; ~5 min on
#    first pull).  Uses .olav/services/netbox/docker-compose.yml.
cd .olav/services/netbox && docker compose up -d

# 2. Bootstrap admin + grab API token
docker compose exec netbox /opt/netbox/venv/bin/python \
  /opt/netbox/netbox/manage.py shell <<'PY'
from users.models import User, Token
u = User.objects.filter(is_superuser=True).first() or \
    User.objects.create_superuser('admin','admin@example.com','admin')
tok, _ = Token.objects.get_or_create(user=u)
print(tok.key)
PY

# 3. Real-write the CSV (idempotent — re-run = no-op)
export NETBOX_TOKEN=<token from step 2 — actually the full nbt_... form>
olav --agent devops "/import_netbox_csv --write \
  --endpoint http://localhost:8000 --token $NETBOX_TOKEN"

# 4. Tear down
cd .olav/services/netbox && docker compose down
```

**Verification** (against a live NetBox at `http://localhost:8000`):

```bash
curl -s -H "Authorization: Token $NETBOX_TOKEN" \
  http://localhost:8000/api/dcim/devices/ | jq '.count'
# → ≥ 2 (the rows that passed validation in Ch10b)

# Idempotency
olav --agent devops "/import_netbox_csv --write ..."
# → "0 created | N existed | 0 failed"
```

**The lookup-or-create chain** (per CSV row, in this exact order):

1. site         — GET ?name=<site>; POST if missing
2. manufacturer — GET ?name=<vendor>; POST if missing
3. device_type  — GET ?model=<m>&manufacturer_id=<mid>; POST if missing
4. device_role  — GET ?name=<role>; POST if missing
5. device       — GET ?name=<n>&site_id=<sid>; POST with resolved FKs if missing

Idempotency is on (name, site) — re-running the same CSV after a
successful import returns `exists` for every row without re-POSTing.

**In-vivo verified 2026-05-15** on a fresh NetBox v4.5 docker stack:
6-row Ch10a CSV produced 2 created devices (R1 + R2 — the rows that
passed Ch10b validation) and 4 skipped (R3/R4/SW1/SW2 — empty
device_type column, validator caught it).  Re-run: 0 created / 2
existed / 0 failed.

## Ch14 — Multi-user (Linux-uid-aligned, encrypted tokens)

**Design**: OLAV users **track Linux system users** — no separate
"OLAV account" concept.  `olav user create alice` requires
`pwd.getpwnam('alice')` to succeed first (the Linux user must
exist).  What OLAV does manage is **per-user encrypted tokens** for
API access:

* `users.duckdb` stores `token_hash` (sha256, 64 chars) + `token_salt`
  (32 chars) — never the plaintext token
* Plaintext token is shown ONCE at `olav user create` time; lost
  thereafter → rotate via `olav user token <name>`
* Bearer-token auth to the web API (`http://localhost:2280/`) checks
  the hash against `token_hash` on every request

```bash
# Multi-user: token-auth aligned to Linux uid
# Prereq: target Linux user must exist
sudo useradd alice                              # platform: real Linux user

olav user create alice                          # OLAV issues + stores token hash
                                                # → prints plaintext token ONCE
ALICE_TOKEN=$(olav user token alice)            # rotate + reveal new token

# Bearer-auth against web API
curl -H "Authorization: Bearer $ALICE_TOKEN" http://localhost:2280/threads
```

**Verification**:

```bash
# Confirm hash + salt stored, plaintext is not
duckdb .olav/databases/users.duckdb -c "
  SELECT username, role, length(token_hash) AS hash_len,
         length(token_salt) AS salt_len, is_active
  FROM users;
"
# → hash_len=64, salt_len=32, plaintext absent

# Linux-user check enforced by default (override = --no-verify)
olav user create nonexistent_user
# → "error: Linux user 'nonexistent_user' not found. Create with:
#    sudo useradd nonexistent_user (use --no-verify to skip)"
```

**Talking point**: per-Linux-user token isolation gives platform
auth aligned to OS auth (no parallel identity to drift); token
hash+salt at rest is enterprise-friendly without paying for a
secrets-manager dependency.
