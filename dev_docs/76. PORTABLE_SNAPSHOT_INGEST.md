# 76. PORTABLE SNAPSHOT INGEST — offline data acquisition + drop-folder ingest

> **Status**: Design draft 2026-05-15
> **Author**: OLAV Team
> **Supersedes**: nothing
> **Related**: ADR-0008 (collection-time redaction), `dev_docs/73` (sim/analyzer
> split), `dev_docs/66` (R102 ingest-via-sub-agent pattern)

## 1. Motivation

Today OLAV's network data acquisition path is **live SSH only**: `netops_init`
opens scrapli/netmiko sessions, runs the per-platform command catalogue,
scrubs raw output via netconan, lands it in `raw_output_store`, then
runs parsers to materialise the structured tables (`netops.bgp_sessions`,
`netops.ospf_neighbors`, `netops.interfaces`, `netops.routes`, etc.).

Three classes of customer can't use that path:

1. **Air-gapped / compliance-gated environments** — SSH from a Linux box
   running OLAV into production routers is denied by policy. The operator
   has to log in from a jump host or via a vendor-blessed terminal.
2. **Sites that already have backups** — rancid / Oxidized / SolarWinds NCM
   / vendor-native commit-archives are running nightly. The text is sitting
   in a git repo or NFS share. Re-SSH'ing duplicates effort and risks
   inconsistency.
3. **Vendor support handoffs** — a customer ships us a `show tech-support`
   bundle for diagnostics; today we have no path to parse it through the
   same downstream as a live snapshot.

The fix: **decouple acquisition from interpretation**. Acquisition becomes
either (a) live SSH, (b) a separate packaged collector that produces a
portable bundle, or (c) raw text the operator already has. All three feed
the same downstream — same scrub, same `raw_output_store`, same parsers,
same structured tables.

## 2. Architecture overview

```
┌─────────────────────┐                              ┌──────────────────────┐
│  Acquisition side   │    Bundle  (zip/tar/dir)     │   Interpretation     │
│  (privileged)       │ ───────────────────────────► │   (LLM + parsers)    │
└─────────────────────┘                              └──────────────────────┘
  Three sources:                                       One destination:
  (a) live SSH        ──────►  netops_init (today)   ─►  raw_output_store
  (b) olav-collector  ──────►  ~/.olav/inbox/*.zip   ─►  ingest sub-agent
  (c) rancid / dump   ──────►  ~/.olav/inbox/path/    ─►  ingest sub-agent
```

Two new artefacts:

- **`olav-collector` wheel** — standalone packaged collector. Ships per-vendor
  command lists + scrapli + netmiko + netconan. NO langchain / duckdb / LLM
  deps. Operators install on a jump host with SSH reachability to the
  network, run `olav-collect run`, get a `snapshot_<ts>.zip` back.
- **`ingest` sub-agent** — workspace sub-agent that watches a drop folder
  (`~/.olav/inbox/`), uses deepagents-native file primitives (`ls`,
  `read_file`, `glob`, `grep`) to discover what was dropped, classifies the
  format (our bundle / rancid layout / loose vendor dumps / show-tech), then
  invokes a Python ingest tool that does scrub + DB write + parser fan-out.

Both feed the same `raw_output_store` and the same parser fan-out as today's
live path. `audit_runs` gains a `collection_source` field so we can tell
"live SSH at 14:32" apart from "ingested bundle from R1 collected at 11:08".

## 3. Bundle format (the contract between acquisition and ingest)

The bundle is the only thing the collector and the ingest agent must agree
on. It is intentionally **lax** — the ingest agent's LLM does fuzzy
classification, the Python tools do strict validation only at the final
DB-write step.

### 3.1 Canonical layout

```
snapshot_<workspace-id>_<utc-ts>.zip
├── manifest.yaml                # required
├── devices/
│   ├── R1/
│   │   ├── _meta.yaml           # required (per-device)
│   │   ├── show_version.txt
│   │   ├── show_running-config.txt
│   │   ├── show_ip_bgp_summary.txt
│   │   └── ...
│   └── R2/
│       └── ...
└── audit.log                    # collector audit trail (optional)
```

### 3.2 `manifest.yaml`

```yaml
schema_version: 1
collector:
  name: olav-collector
  version: 0.1.0
  invocation: "olav-collect run --inventory hosts.yml --out snapshot_xyz.zip"
collected_at: 2026-05-15T11:08:42Z
collected_by: jchen@jumphost-tor1     # OS user @ host
workspace_id: site-tor1               # operator-chosen; goes into snapshot_id
hosts_collected: 6
hosts_failed: 0
redaction:
  pre_scrubbed: true                  # bundle is already netconan-scrubbed
  salt_fingerprint: a3f2c891           # first 8 hex of sha256(salt); for audit cross-ref
  netconan_version: 0.13.0
content_sha256: 9f3a...               # over devices/ tree
signature: null                       # optional GPG sig for chain-of-custody
```

### 3.3 `devices/<host>/_meta.yaml`

```yaml
hostname: R1
mgmt_ip: 10.10.0.1                    # what scrapli/nornir would have hit
vendor: Cisco
platform: cisco_ios                   # nornir-canonical platform key
scrapli_platform: cisco_iosxe         # populated from platform_profiles.yaml
os_version: "15.6(3)M5"
model: "Cisco 2911"
commands_attempted: 14
commands_succeeded: 14
commands_failed: 0
collected_at: 2026-05-15T11:08:42Z    # per-host timestamp (drift on slow hosts)
```

### 3.4 Per-command files

Each file is the raw stdout of one CLI command, optionally pre-scrubbed.
Filename = command with `[ \/]` → `_`. E.g. `show ip bgp summary` becomes
`show_ip_bgp_summary.txt`. The original command string is recorded in the
file's header comment for parser routing:

```
# command: show ip bgp summary
# collected_at: 2026-05-15T11:08:42Z
# pre_scrubbed: true
# scrub_replacements: 3

BGP router identifier 1.1.1.1, local AS number 65001
BGP table version is 142...
Neighbor        V   AS MsgRcvd MsgSent...
10.1.12.2       4 65000     142     138...
netconanRemoved0 ...
```

A two-line header gives ingest enough metadata to route to the right
parser without re-parsing the filename.

### 3.5 Alternative layouts (ingest agent recognises)

Operators won't always send our format. The ingest agent recognises:

- **olav-collector bundle** — described above, the happy path.
- **rancid layout** — `<group>/configs/<hostname>` files, each a
  concatenation of multi-command output separated by `!`-banners.
  Ingest splits on banners, infers per-command boundaries.
- **Loose vendor dumps** — `R1.txt`, `R2.txt`, ... single-file-per-device.
  Ingest LLM identifies platform from content heuristics
  (`Cisco IOS Software` line, `Junos:` prefix, `*A:` SR OS prompt, etc.),
  then attempts to split into commands by prompt-regex.
- **show tech-support bundles** — vendor-native diagnostic archives.
  Vendor-specific extractors (Cisco `.tar`, Juniper `.tgz`, etc).

When in doubt → HITL: ingest agent reports "I see 3 hosts, 2 look like
rancid format and 1 looks like a Junos tech bundle — proceed?" and waits.

## 4. The `ingest` sub-agent

### 4.1 Q1: Where does this sub-agent live?

**Decision: `olav-netops/.olav/workspace/netops/ingest/` — sibling of `collect`.**

Rationale (considered candidates):

| Candidate location | Pros | Cons | Verdict |
|---|---|---|---|
| `netops/ingest/` (sibling of `collect`) | Same domain knowledge (vendor formats, parser routing, command catalog). `collect` = live SSH, `ingest` = offline files — clean symmetry. Inherits netops orchestrator routing keywords. | None — netops/ already owns the full data model. | **CHOSEN** |
| `services/ingest/` (write-side platform agent) | Logical home for things that write to DB. | services/ is cross-domain (NetBox push, syslog daemons) — adding netops-specific format detection muddles its scope. The ingest agent's *job* is overwhelmingly network-specific. | Rejected. |
| New top-level `ingest/` workspace | Maximum independence; could grow into a generic data-onboarding agent (CSV imports, log dumps, etc.). | Premature abstraction. Today's only user is network snapshots. ADR-0004 discourages new top-level agents until justified. | Rejected — revisit only if non-network ingest emerges. |
| Inside existing `netops_init/` skill | Smallest delta; netops_init is already the "first-time setup" agent. | netops_init is a one-shot setup CLI (`/netops_init`), not a sub-agent with LLM reasoning. The format-detection step *needs* LLM judgment (rancid vs loose vs bundle is fuzzy). Wrong tool. | Rejected. |

The `collect` / `ingest` pair becomes the canonical "two faces of acquisition":

```
netops/
├── collect/          # live SSH gather (existing)
│   └── SKILL.md      # tools: execute_cli_parallel
├── ingest/           # offline file gather (NEW)
│   └── SKILL.md      # tools: ls/read_file/glob/grep (deepagents native)
│                     #        + ingest_snapshot (Python, audited)
├── netops_init/      # first-time bootstrap (existing, can dispatch to either)
│   └── run.py
└── ...
```

### 4.2 `SKILL.md` shape

```yaml
---
name: ingest
agent_type: api               # tool-execution, not plan-and-iterate
thinking_mode: enabled        # format classification benefits from reasoning
description: "Offline snapshot ingest — parses dropped bundles / rancid backups / vendor dumps into raw_output_store + structured tables."
metadata:
  version: 0.1.0
  type: agent
  agent_type: api
  category: network-data-ingest
  intent: offline_snapshot_ingestion
tools:
  # deepagents native — format discovery
  - ls
  - read_file
  - glob
  - grep
  # Python first-party — final landing
  - ingest_snapshot           # @tool — runs scrub + DB writes (audited)
  - validate_bundle           # @tool — manifest + content sha256 check
dynamic_context:
  - path: ./references/bundle_schema.guide.yaml
  - path: ./references/rancid_format.guide.yaml
  - path: ./references/vendor_dump_heuristics.guide.yaml
system: $ref:./prompts/system.md
---
```

### 4.3 Workflow

```
USER: /ingest_bundle ~/.olav/inbox/snapshot_xyz.zip

[ingest sub-agent]
1. ls ~/.olav/inbox/snapshot_xyz.zip → confirms exists
2. unzip via run_python_simulation → /tmp/ingest_xyz/
3. ls /tmp/ingest_xyz/ → sees manifest.yaml + devices/
4. read_file manifest.yaml → "olav-collector v0.1.0, 6 hosts, pre_scrubbed=true"
5. validate_bundle(/tmp/ingest_xyz/) → content sha256 OK, all _meta.yaml present
6. ingest_snapshot(
     path=/tmp/ingest_xyz/,
     snapshot_id="snap_20260515_110842_<workspace-id>",
     pre_scrubbed=true,
     collection_source="bundle:olav-collector:0.1.0",
   )
   → returns {raw_rows_written: 84, parser_fills: {bgp: 12, ospf: 8, ...},
              failures: []}
7. Markdown report back to user with delta vs previous snapshot.
```

For non-bundle layouts (rancid / loose dumps), step 4 fails the manifest
check, so the LLM falls through to format heuristics (its `prompts/system.md`
contains a decision tree mirroring §3.5).

When ambiguous → HITL via standard `request_user_input` middleware.

## 5. The `olav-collector` wheel

### 5.1 Q2: Command candidate pool, config file, blacklist

The collector wheel needs to know **what to run** without any LLM in the
loop, on every platform OLAV supports. The design must:

1. Reuse OLAV's existing command knowledge (don't fork the catalog).
2. Stay safe by default — never run mutating or interactive commands.
3. Be operator-overrideable per environment (some sites need MPLS commands;
   most don't).

#### 5.1.1 The three tiers + the wall

```
                          ▲
        Tier 4: BLACKLIST │  hard regex deny — collector refuses to run
        (always wins)     │  examples: ^write, ^reload, ^configure,
                          │            ^show tech-support, ^debug
                          ▼
              ─── wall ─────────────────────────────────
                          ▲
        Tier 3: USER      │  operator-added per-platform commands
                          │  (~/.olav-collector/user_commands.yaml)
                          ▼
                          ▲
        Tier 2: BACKUP    │  heavy commands run only during full snapshots
                          │  (show running-config, show logging, etc.)
                          ▼
                          ▲
        Tier 1: DEFAULTS  │  textfsm-parseable per-platform commands
                          │  (frozen at wheel build time from
                          │   ntc-templates → netops.commands SSOT)
                          ▼
```

The candidate pool = `(Tier 1 ∪ Tier 2 ∪ Tier 3) − Tier 4`. Tier 4 is the
final filter and **cannot be turned off** — only extended.

#### 5.1.2 Wheel layout

```
olav-collector/
├── pyproject.toml
├── src/olav_collector/
│   ├── __init__.py
│   ├── cli.py              # click entrypoints: dry-run / run / validate
│   ├── inventory.py        # parse hosts.yml (nornir-compatible)
│   ├── runner.py           # scrapli/netmiko fan-out
│   ├── bundle.py           # produce snapshot_*.zip in §3 format
│   └── data/
│       ├── platform_profiles.yaml      # frozen copy from netops_init/config
│       ├── commands.yaml               # generated from netops.commands at build
│       ├── backup_only_commands.yaml   # frozen copy
│       └── blacklisted_commands.yaml   # frozen copy — Tier 4 wall
└── tests/
```

The four YAML files in `data/` are **single-sourced from olav-netops**:
a build-time hook (`scripts/freeze_command_catalog.py`) reads from a fresh
`olav init`'s `netops.commands` table and emits `commands.yaml`. This keeps
the collector and the platform in lockstep without runtime DB dependency.

#### 5.1.3 `commands.yaml` (Tier 1) — generated, never hand-edited

```yaml
# AUTO-GENERATED — do not edit.
# Source: olav-netops netops.commands at build time.
# Regenerate: scripts/freeze_command_catalog.py

schema_version: 1
generated_at: 2026-05-15T10:00:00Z
generated_from: olav-netops==0.21.1

platforms:
  cisco_ios:
    - command: show version
      parser: cisco_ios_show_version
      parser_type: textfsm
    - command: show ip interface brief
      parser: cisco_ios_show_ip_interface_brief
      parser_type: textfsm
    - command: show ip bgp summary
      parser: cisco_ios_show_ip_bgp_summary
      parser_type: textfsm
    # ... ~30 commands per platform

  cisco_xr:
    - command: show version
      ...
  juniper_junos:
    ...
  arista_eos:
    ...
  # 10+ vendors total
```

#### 5.1.4 `user_commands.yaml` (Tier 3) — operator extension

Operator drops this in `~/.olav-collector/user_commands.yaml`. Schema
identical to the YAML in `olav-netops/.../netops_init/config/user_commands.yaml`
so operators can copy-paste between platform and collector configs.

```yaml
# Per-platform additions specific to this site.
# Loaded after defaults; output stored as raw_only (no parser).

commands:
  cisco_ios:
    - show mpls ldp neighbor      # operator's site is MPLS-heavy
    - show mpls forwarding-table
  cisco_xr:
    - show mpls ldp neighbor

# Operators can also REMOVE Tier 1 / Tier 2 commands here:
exclude:
  cisco_ios:
    - show processes cpu          # we collect via SNMP instead
```

#### 5.1.5 `blacklisted_commands.yaml` (Tier 4) — the wall

Same regex schema as `olav-netops/.olav/workspace/netops/config/blacklisted_commands.yaml`.
Operators can **add** patterns (`overrides.yaml` is merged on top); they
**cannot remove** shipped patterns. The CLI prints which patterns would
block a candidate during `dry-run`:

```
$ olav-collect dry-run --inventory hosts.yml
[R1 cisco_ios]
  ✓ show version
  ✓ show ip bgp summary
  ✗ show running-config            [Tier 2 — included only with --backup]
  ⊘ show tech-support              [Tier 4 — BLACKLISTED: ^show tech-support]
  ⊘ clear counters                 [Tier 4 — BLACKLISTED: ^clear\b]

42 commands planned across 6 hosts.
2 blocked by blacklist (printed above).
```

#### 5.1.6 Inventory file (operator-provided)

Nornir-compatible YAML so the collector can reuse the existing
`olav-netops/inventory/hosts.yaml` verbatim:

```yaml
hosts:
  R1:
    hostname: 10.10.0.1
    platform: cisco_ios
    username: admin
    password: !env CISCO_PASSWORD
  R2:
    hostname: 10.10.0.2
    platform: juniper_junos
    username: admin
    password: !env JUNOS_PASSWORD
```

#### 5.1.7 CLI commands

```
olav-collect dry-run --inventory hosts.yml
  → print candidate matrix per host, highlight blacklist hits, no SSH

olav-collect run --inventory hosts.yml --out snapshot.zip
  → fan-out, scrub locally (default --scrub=true), bundle as §3 format

olav-collect run --inventory hosts.yml --no-scrub --out snapshot.zip
  → emit raw; ingest agent will scrub at landing. Use only if collector host
    cannot install netconan.

olav-collect run --inventory hosts.yml --backup --out snapshot.zip
  → include Tier 2 (heavy commands like running-config).

olav-collect validate snapshot.zip
  → local sanity check: manifest schema, content sha256, command coverage
    matrix per platform. No DB touch.
```

### 5.2 Dependencies (tight)

```toml
[project]
name = "olav-collector"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "scrapli>=2024.1",
    "scrapli-community>=2024.1",      # vendor platforms beyond core
    "netmiko>=4.2",                    # fallback for non-scrapli vendors
    "nornir>=3.4",
    "netconan>=0.13",                  # local scrub before bundling
    "click>=8.1",
    "pyyaml>=6.0",
    "rich>=13.0",                      # CLI table output

# NO langchain, NO duckdb, NO lancedb, NO sentence-transformers.
# Wheel size target: <2MB.
```

### 5.3 Repo location

Per ADR-0004 (new top-level agent extension policy), this is a **sub-package
under `olav-netops`**, not a new top-level repo:

```
olav-netops/
├── olav-collector/          # NEW sub-package
│   ├── pyproject.toml       # independently installable
│   └── src/olav_collector/
├── src/olav_netops/         # existing
├── .olav/workspace/         # existing
└── pyproject.toml           # existing
```

Independent versioning, independent PyPI release (`pip install olav-collector`),
but lives in the netops monorepo so the command catalog stays single-sourced.

## 6. Audit & provenance

### 6.1 `audit_runs` extension

Add column:

```sql
ALTER TABLE audit_runs ADD COLUMN collection_source VARCHAR;
-- Values: 'live_ssh' | 'bundle:olav-collector:0.1.0' | 'ingest:rancid' | 'ingest:dump'
```

Backfill: existing rows are all `live_ssh`.

### 6.2 `raw_output_store` extension

Existing columns: `device_id, command, output, scrub_marker_count, collected_at`.

Add:

```sql
ALTER TABLE raw_output_store ADD COLUMN ingested_via VARCHAR;
-- For live_ssh rows: NULL
-- For bundle rows: 'bundle' + nullable bundle_id pointer
ALTER TABLE raw_output_store ADD COLUMN bundle_id VARCHAR;
ALTER TABLE raw_output_store ADD COLUMN bundle_sha256 VARCHAR;
```

### 6.3 New `bundle_ingests` table

```sql
CREATE TABLE netops.bundle_ingests (
    bundle_id           VARCHAR PRIMARY KEY,    -- uuid
    snapshot_id         VARCHAR,
    bundle_sha256       VARCHAR NOT NULL,       -- content hash from manifest
    collector_name      VARCHAR,
    collector_version   VARCHAR,
    collected_at        TIMESTAMP,
    ingested_at         TIMESTAMP,
    ingested_by         VARCHAR,                -- OS user
    pre_scrubbed        BOOLEAN,
    salt_fingerprint    VARCHAR,
    hosts_count         INTEGER,
    commands_count      INTEGER,
    parser_fill_summary VARCHAR                 -- JSON: {bgp: 12, ospf: 8, ...}
);
```

One row per ingest event. Joins to `raw_output_store.bundle_id` give full
provenance for any downstream query.

### 6.4 Chain of custody

For compliance-sensitive deployments, the bundle's `manifest.yaml` can
carry a GPG signature. The ingest agent verifies the signature against
a keyring at `~/.olav/trusted-collectors.gpg` before proceeding. Failed
sig verification → HITL ("bundle signed by unknown key — accept?").

## 8. Open questions

1. **Bundle signature default** — opt-in or required? Lean opt-in for MVP;
   required is an enterprise tier.
2. **Pre-scrub vs landing-time scrub** — default in `olav-collect run` is
   `--scrub=true`. But re-scrubbing on landing is cheap (netconan is fast).
   Do we always re-scrub for defense-in-depth, even if `pre_scrubbed=true`
   in the manifest? Probably yes; the only cost is one extra
   `salt_fingerprint` entry in `Findings` for telemetry.
3. **Auto-discovery of inbox** — does the ingest agent get a file-watcher
   (inotify) so dropping a file triggers ingest automatically, or always
   user-triggered via `/ingest_bundle <path>`? Lean user-triggered for
   MVP; the auto path raises permission/concurrency concerns better
   solved after we see real usage patterns.
4. **rancid CVS support** — modern rancid uses git, but legacy
   deployments still use CVS. Do we support CVS adapter, or document
   "git mirror first"? Lean document-only; CVS in 2026 is rare enough.
5. **Vendor tech-support bundles** — Cisco `.tar`, Juniper `.tgz`, Arista
   `tech-support` outputs are large + heterogeneous. Defer to a Phase 6
   add-on. MVP supports the three formats listed in §3.5.
