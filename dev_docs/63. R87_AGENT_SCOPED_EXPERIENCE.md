## Context

R84-R86 built three layers of memory-driven knowledge that all live
in a **single global LanceDB store**, surfaced uniformly to every
agent:

| category | purpose | scope today |
|---|---|---|
| `schema_knowledge` | DB views auto-discovered at ingest | global |
| `value_distribution` | per-column value frequencies | global |
| `query_pattern` | captured-from-success SQLs | global |
| `usage_guide` | curated workflow imperatives | global |
| `format_guide` | curated save-call shapes | global |

All agents see the same pool.  This is a **start**, but Chapter 5
testing exposed three structural limits:

### Limit 1 — vendor-bias of the LLM

When ops-lab validated the SRL eBGP CAB spec, the agent saw `bgp
neighbor` state = `active` and reported PASS.  In SR Linux,
`active` means **TCP is failing** (hard fault).  The LLM applied
its **Cisco-flavored prior** (where `active` is "trying").
Generic memory entries can't fix this — the model's training data
is overwhelmingly Cisco-shaped, so vendor-specific
counter-knowledge is the only fix.  But that knowledge would only
be relevant when the active workflow involves SRL containers — for
core-agent / writer-agent it's noise.

### Limit 2 — partial-success poisoning

`query_pattern_capture` writes successful execute_sql calls
directly to memory.  But "successful" only means "tool didn't
error".  In R84 CC-1c, Q3's captured SQL was single-view (queries
one of 5 interface views), which the diversifier surfaced for
later runs — agent then "answered fast" but with **incomplete
data**.  Predicate failed.  We saw partial-success poison the
recall.

### Limit 3 — agentic learning is currently a hope, not a system

The vision in `dev_docs/200` is "users inject experience".  But
right now, the only auto-learning mechanism is `query_pattern_capture`,
which has the poisoning problem above.  There's no review,
no confidence model, no rollback, no per-agent isolation.

R87 addresses all three.

## Architecture: scoped + tiered + curated

### The full design (4-tier confidence)

```
┌──────────────────────────────────────────────────────────────┐
│  GLOBAL CURATED CONTENT (R84/R85/R86, already shipped)       │
│  scope='global', confidence=1.0                              │
│  ├── schema_knowledge   (auto from ingest)                   │
│  ├── value_distribution (auto from ingest)                   │
│  ├── usage_guide        (curated *.guide.yaml)               │
│  └── format_guide       (curated *.format.yaml)              │
├──────────────────────────────────────────────────────────────┤
│  AGENT-SCOPED CURATED EXPERTISE  (R87 Phase 1, this doc)     │
│  scope='<agent_name>', confidence=1.0                        │
│  └── expert_knowledge   (curated *.expert.yaml)              │
│      ↑ vendor / platform-specific corrective knowledge       │
│        — fixes the LLM's training-data bias.                 │
│        Examples: SRL eBGP gotchas, IOS-XR EVPN quirks,       │
│        Junos commit-confirmed semantics.                     │
├──────────────────────────────────────────────────────────────┤
│  AGENT-SCOPED LEARNED EXPERIENCES (R87 Phase 2-4, FUTURE,    │
│                                     ENTERPRISE EDITION)      │
│  scope='<agent_name>', confidence=0.0~1.0 progressive        │
│  ├── pending          (auto-capture, conf=0.3)               │
│  │   recall middleware FILTERS OUT (conf < 0.5 default)      │
│  ├── approved         (curator review pass, conf=0.5-0.7)    │
│  ├── seasoned         (N reuses w/o user override, conf=0.8) │
│  └── authoritative    (cross-agent validated, conf=1.0)      │
└──────────────────────────────────────────────────────────────┘
```

### Phase 1 (open source, this doc) — per-agent curated expertise

**Goal**: scoped curated knowledge that fixes vendor-bias.  No
auto-learning yet.

* New memory category: `expert_knowledge`
* New file schema: `*.expert.yaml`
* Scope semantics: `scope='global'` OR `scope='<agent_name>'`
  - Recall middleware filter: `scope IN ('global', current_agent)`
  - Per-agent expertise stays out of other agents' recall
* New CLI: `olav kb import-experts <dir> --agent <name>`
* New `_CATEGORY_QUOTAS["expert_knowledge"] = 1` (borrow 1 slot
  from schema_knowledge: 3→2; total stays 13)
* First curated content: `bgp_validation_srl.expert.yaml`
  (scope='ops-lab') — corrects the Cisco-flavored BGP state
  decoder

**Validation gate**: Chapter 5 retest after Phase 1.  Expected:
agent recognizes `active` as TCP failure (per SRL knowledge),
reports CAB FAIL with specific diagnosis ("missing
ebgp-default-policy" / "no IGP route to peer loopback").
Without Phase 1 (R86 baseline): agent reports CAB PASS or
incorrect FAIL with no actionable diagnosis.

**Why this is open source**: vendor-specific quirks are community
knowledge — TAC engineers, network architects, certification
holders all contribute.  OLAV provides the schema + import path;
the value flow goes through customers/community, not vendor.

### Phase 2-4 (enterprise edition, FUTURE)

**Phase 2 — pending pool + manual curator CLI** (~2 days work):
* `AutoCaptureMiddleware` writes to `scope='pending'`,
  `confidence=0.3`
* Recall middleware default filter: `confidence >= 0.5` (pending
  invisible)
* `olav curator list/inspect/approve/reject/merge` CLIs (manual
  human review)

**Phase 3 — automated curator agent** (~3-5 days work):
* New subagent `core/curator` (or extend `audit/curator`)
* Curator's static_context: `principles.expert.yaml` shipping with
  the platform — what makes a capture worth approving
* Curator runs on a schedule (cron) or threshold (>N pending)
* Decisions: approve+promote / reject / hold-for-evidence /
  cluster+merge / GC stale

**Phase 4 — cross-agent validation propagation** (~1 week):
* ops-lab CAB PASS/FAIL retroactively boosts/demotes ops-analyze's
  spec-generation captures
* Reward signal flows backward through delegation chain
* Time-window + debounce to prevent oscillation

**Phase 2-4 are deferred to enterprise edition** for these
reasons:

1. **Curator quality is the moat**.  An OLAV deployment with a
   well-tuned curator gets smarter over time; one without
   stagnates.  This is exactly the high-touch "knowledge
   distillation" service `dev_docs/200` describes.
2. **Operational complexity**.  Pending pool + curator agent +
   audit logging + rollback is enterprise-grade ops.  Open source
   users get curated content (Phase 1); enterprise gets the
   self-improving loop.
3. **Privacy / multi-tenancy**.  Per-deployment learned content
   needs isolation tooling (PII sanitization, opt-in community
   contribution).  That's an enterprise feature.
4. **Time to validate Phase 1 first**.  Before committing to a
   curator agent, we need bench data showing per-agent expertise
   actually moves the needle.  If Phase 1 doesn't pay off,
   Phase 2-4 are dead.

## Phase 1 detailed design (open source, current work)

### `*.expert.yaml` schema

```yaml
schema_version: 1
topic: bgp_state_decoder_srl     # human-readable identifier
scope: ops-lab                   # which agent surfaces this
vendor: srl                      # OPTIONAL — for filter / display
platform_family: nokia           # OPTIONAL
keywords:
  - srl
  - sr-linux
  - bgp
  - established
  - active
  - cab
body: |
  # SRL-specific BGP State Decoder (NOT Cisco)
  ...
```

Required: `topic`, `scope`, `keywords`, `body`.
Optional: `vendor`, `platform_family`, `schema_version` (defaults to 1).

`memory_id` = `expert_<scope>_<topic>` — idempotent upsert.

### Module: `src/olav/core/memory/expert_kb.py`

Mirrors the structure of `guide_kb.py` and `format_kb.py`.
Discovery glob: `<workspace_root>/<agent>/expertise/*.expert.yaml`
(sibling to `guides/`, `formats/`).

### CLI: `olav kb import-experts <dir>`

Sibling to `import-guides` / `import-formats`.  Scans for
`*.expert.yaml`, primes each with category=`expert_knowledge`,
scope from YAML's `scope` field.

### Recall middleware change (small but semantic)

In `_gather_candidates`:
* Was: `scope='global'` (or omitted)
* Becomes: `scope IN ('global', current_agent_name)`

This requires the recall middleware to know which agent is
currently running.  The orchestrator passes `current_agent` when
constructing AutoRecallMiddleware (already happens in
`_build_subagents`).

### Quota update

```python
_CATEGORY_QUOTAS = {
    "schema_knowledge": 2,      # was 3 (R86); -1 for expert_knowledge
    "value_distribution": 4,    # unchanged
    "query_pattern": 2,         # unchanged
    "usage_guide": 3,           # unchanged
    "format_guide": 1,          # unchanged
    "expert_knowledge": 1,      # NEW
}
# Total: 13 (recall_top_k for large tier; budget unchanged)
```

Borrowing the slot from `schema_knowledge` (currently
under-utilised since most queries don't need 3 schema entries —
the matched one is usually clear from the query verb).

### First curated content

`olav-netops/.olav/workspace/ops/lab/expertise/bgp_validation_srl.expert.yaml`:

```yaml
schema_version: 1
```

## Risks & open questions

### Risk 1: scope=ops-lab but agent uses execute_sql for general queries
ops-lab uses `execute_sql` to gather generic info (not just lab).
The `bgp_validation_srl` expertise would also surface for those
queries (because keywords match).  Whether that's good or bad —
needs bench observation.

Mitigation: tighten keywords to lab-specific phrases (`sr_cli`,
`clab-`, `digital twin`).

### Risk 2: who writes the first curated YAML
The user (us, in this session) has to write it.  Quality depends
on human-driven SRL expertise.  Long-term, OLAV team / community /
vendor partnerships supply the content; for now, hand-rolled.

### Risk 3: prompt adherence still required
Even with SRL knowledge in recall, the small model has to
**actually apply** it.  We've seen agents skip recall content
(R84 CC-1c).  The bench is the only way to know.

If Phase 1's bench shows recall surfaces but agent ignores → need
prompt-level reinforcement (`usage_guide` for ops-lab saying
"when SRL platform involved, consult `expert_knowledge`").

### Open question 1: should other vendor knowledge be added before bench?
Or just the SRL one for now (smallest test surface)?

Recommendation: **just SRL** — focus the Chapter 5 gate.  Other
vendors come after the architecture validates.

### Open question 2: scope inheritance
ops-lab is a subagent of ops-orchestrator.  Should
`scope='ops-orchestrator'` be visible to ops-lab too?  Hierarchy?

Recommendation: **flat scope, no inheritance** for Phase 1.  Each
agent sees `('global', '<own_name>')`.  Cleaner mental model.
Hierarchy can be Phase 1.5 if needed.

### Open question 3: when agent has no expertise files, anything bad?
Recall just returns 0 expert_knowledge entries.  Quota slot is
filled from global ranking (existing fallback path).  No
regression — recall_top_k still saturates at 13 from the other
categories.

## Phase 1.5 design — scope vocabulary + user injection

**Status**: Designed 2026-04-27 — not yet implemented. Trigger:
during R87 Phase 1 closed-loop validation we hit two structural
gaps that Phase 1 doesn't address:

1. **No "shared" tier** — `srl_spec_generation_rules` is needed by
   ops-analyze (writes spec) AND ops-lab (validates spec). Phase 1
   forces a choice (one scope) → either duplication or wrong-agent
   recall.
2. **No user-injection path** — `dev_docs/200` business model
   requires "users inject experience" but Phase 1 only ships
   platform-authored YAMLs. There's no recall slot reserved for
   user content, no on-disk path the user can write to, no
   provenance tracking.

Phase 1.5 closes both gaps without touching the Phase 2-4 curator
machinery (which stays enterprise).

### Three-tier scope vocabulary

| scope value | meaning | who can write | recall visibility |
|---|---|---|---|
| `<agent_name>` | agent-specific | platform/extension authors | only that agent |
| `shared:<domain>` | cross-agent within a domain | platform/extension authors | all agents in that domain |
| `org` | universal organizational | **users only** | all agents, all domains |

`<domain>` is the skill name (`ops`, `audit`, `ent`). `shared:ops`
is visible to all `ops-*` subagents; `shared:audit` to audit
subagents; etc.

**Why no multi-value scope (`scope: [ops-lab, ops-analyze]`)?**
Multi-value devolves into copy-pasted lists with no abstraction.
Forcing the author to choose between `<agent>` / `shared:<domain>`
/ `org` is a cleaner mental model.

### Two-axis source provenance

`source` field — auto-populated at import time, not authored:

| source | meaning | provenance |
|---|---|---|
| `shipped` | came with the package | author = OLAV team / extension maintainers |
| `user` | locally injected | author = end user / org |

Used for:
* Audit (`olav kb list-experts --source=user` shows my customizations)
* Conflict signaling (when shipped + user knowledge collide)
* Bench testing (compare model behavior with/without user injections)

### Directory layout

```
# Shipped — versioned with the code
<plugin>/.olav/workspace/<agent>/expertise/             → scope: <agent>
<plugin>/.olav/workspace/shared/<domain>/expertise/     → scope: shared:<domain>

# User-injected — NOT versioned with the code
~/.olav/expertise/                                       → scope: org (cross-project)
<project>/.olav/expertise/                               → scope: org (per-project)
```

`shared/<domain>/expertise/` is a NEW directory pattern (sibling
to per-agent dirs). `discover_experts` recursively scans both
patterns and infers scope from path:

```python
# discover_experts(workspace_root) returns list of (path, inferred_scope)
# path matches "<root>/<agent>/expertise/*.expert.yaml" → scope=<agent>
# path matches "<root>/shared/<domain>/expertise/*.expert.yaml" → scope=shared:<domain>
```

YAML's `scope` field (if present) overrides the inferred default —
useful when YAML is symlinked / copied across paths.

### Recall filter (replaces Phase 1's vector-only approach)

When agent `X` in domain `D` runs:

```sql
-- Phase 1 (current): vector relevance only, no scope filter
WHERE category = 'expert_knowledge'

-- Phase 1.5: hard scope isolation
WHERE category = 'expert_knowledge'
  AND scope IN ('X', 'shared:D', 'org')
```

This solves the "vector-relevance occasionally surfaces wrong-agent
expertise" issue we observed in R87 closed-loop validation.

### Quota allocation — split the expert_knowledge slot

Currently `_CATEGORY_QUOTAS["expert_knowledge"] = 1`. Phase 1.5
splits into 3 sub-slots inside the recall block:

```python
_CATEGORY_QUOTAS["expert_knowledge"] = {
    "agent":  1,   # at least 1 own-agent entry
    "shared": 1,   # at least 1 cross-agent entry
    "org":    1,   # at least 1 user-injected entry
}
# Total: 3 (was 1) — borrow 2 slots from value_distribution
# (currently 4, dropping to 2 — diminishing returns past 2 entries)
```

User-injected (`org`) ALWAYS gets 1 slot when present — concrete
implementation of "users own their workflow". Empty slots fall
through to vector ranking (no waste).

### Conflict handling — surface, don't auto-resolve

When user `org` knowledge contradicts shipped `shared` knowledge
(example: user says "we use BGP md5", shipped says "SRL doesn't
support md5, use TCP-AO"), DON'T programmatically resolve. Instead:

1. **Surface both** in the recall block
2. **Sort `source=user` first** (user's content visible first)
3. **Optional explicit override**: YAML field `precedence: override`
   tells recall to put it ahead of shipped on tied vector scores

LLM gets both viewpoints in context and reasons about the conflict
— more rigorous than if-else resolution in code, and the user can
see what's clashing.
