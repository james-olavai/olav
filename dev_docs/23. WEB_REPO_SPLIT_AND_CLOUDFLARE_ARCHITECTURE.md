# 23. Web Repo Split and Cloudflare Architecture

**创建日期：** 2026-04-04  
**状态：** Proposed  
**目标：** 明确文档站与主站的仓库边界，确定主站在 Cloudflare 上的推荐部署架构，并给出从当前 `olav-doc/web/` 迁移到独立 `olav-web` 的决策标准。

---

## 1. 背景

当前 `olav-doc/` 同时承载两类公开站点：

- `docs/` + `mkdocs.yml`：文档站（MkDocs Material）
- `web/`：主站 / 官网（Astro + Tailwind）

这种组织在早期是合理的，因为：

- 两者都属于公开发布内容
- 两者都不依赖 `src/olav` 运行时代码
- 单仓维护可以降低初期治理成本

但主站的目标形态已经不再是“纯静态营销页”，而是逐步演进为：

- Cloudflare Worker 承载边缘逻辑
- Workers Static Assets 托管静态资源
- R2 承载大对象与版本化媒体资源
- Mermaid 预渲染流水线

因此需要单独回答两个问题：

1. 是否还应该让 `olav-doc` 同时拥有文档站与主站源码
2. Cloudflare 上主站的目标架构应该如何分层

---

## 2. 问题定义

核心问题不是“Cloudflare 能不能从同一个 repo 部署两个域名”。

Cloudflare 本身支持同一个 Git 仓库创建多个项目，并分别指定：

- Root directory
- Build command
- Output directory
- Production domain

因此，**仅从多域名映射能力看，不拆 repo 完全可行。**

真正需要决策的是：

- 文档站与主站是否仍属于同一种发布系统
- 两者的构建链、缓存策略、边缘逻辑、资源治理是否已经显著分化
- 是否值得为长期演进而拆出独立 repo 和独立 ownership

---

## 3. 当前状态

### 3.1 当前仓库职责

`olav-doc` 已成为文档与官网的**唯一权威源**（root `docs/`、`web/`、`mkdocs.yml` 已于 2026-04-04 删除并收敛）。

当前 `olav-doc` 的实际内容是：

- `docs/`：文档内容（含 enterprise 文档）
- `mkdocs.yml`：文档站配置
- `web/`：Astro 主站源码

也就是说，今天的 `olav-doc` 本质上仍是”文档站 + 官网发布仓库”。

### 3.2 当前 Cloudflare 映射方式

在不拆 repo 的情况下，可以直接在 Cloudflare 上配置两个项目：

1. 文档项目
	- Repo: `olav-doc`
	- Root: 仓库根目录
	- Build: `mkdocs build`
	- Output: `site`
	- Domain: `docs.olavai.com`

2. 主站项目
	- Repo: `olav-doc`
	- Root: `web`
	- Build: `npm run build`
	- Output: `dist`
	- Domain: `olavai.com`

结论：**短期交付不需要为了域名映射而立即拆 repo。**

---

## 4. 决策驱动因素

### 4.1 倾向继续单 repo 的条件

- 目标只是让两个域名在 Cloudflare 上更容易映射
- 主站仍然是纯静态 Astro 站点
- 文档站与主站由同一维护者负责
- 发布节奏基本一致
- 不希望立刻引入新的仓库治理成本

### 4.2 倾向拆分为 `olav-web` 的条件

- 主站将长期采用 `Worker + R2 + Mermaid + Static Assets`
- 主站需要独立的缓存策略、安全头、边缘重写和 API 入口
- 主站会有自己的发布节奏、活动页、埋点、A/B 或媒体资源治理
- 希望 Cloudflare 上一个域名对应一个 repo，职责更清晰
- 希望避免 `olav-doc` 同时承载两种明显不同的系统复杂度

---

## 5. 决策

### 5.1 短期决策

短期内允许继续保持单 repo。

原因：

- `olav-doc/web/` 已经存在并可直接演进
- Cloudflare 已支持一仓多项目
- 可以先验证主站 Worker 架构，再决定是否拆分

### 5.2 中长期决策

中长期建议拆为两个 repo：

#### `olav-doc`

只负责：

- `docs/`
- `mkdocs.yml`
- 文档站部署配置

目标域名：`docs.olavai.com`

#### `olav-web`

只负责：

- Astro 主站源码
- Worker 入口与边缘逻辑
- R2 资源治理
- Mermaid 预渲染流水线
- 主站部署配置

目标域名：`olavai.com`

### 5.3 原因

因为主站的目标能力已经超出“静态网页集合”，而接近一个边缘应用发布系统：

- 页面构建
- 边缘路由
- 下载控制
- 资源签名
- 对象存储
- 图形预渲染

这和文档站的关注点已经显著不同。

---

## 6. 推荐的 Cloudflare 主站架构

主站推荐采用：

**Static-first Astro + Workers Static Assets + Thin Worker + R2 + build-time Mermaid**

### 6.1 分层

#### Layer 1: Site Generation

使用 Astro 生成：

- 首页
- 产品页
- 定价页
- 更新页 / 博客页
- 中英文双语页面
- SEO 导向 landing pages

原则：**静态优先，不做 SSR-first。**

当前范围约束：

- 产品页暂时不做
- 定价页暂时不做
- 公司页暂时不做
- 主站默认按中英文双语设计，而不是单语站

#### Layer 2: Static Delivery

使用 Workers Static Assets 托管：

- HTML
- CSS
- JS
- 字体
- 小型图片
- 预生成 Mermaid SVG

#### Layer 3: Edge Logic

Worker 只做薄逻辑：

- redirects / rewrites
- 安全头注入
- locale / campaign routing
- feature flags
- 轻量表单 API
- 签名下载 URL
- abuse / bot 控制

#### Layer 4: Object Storage

R2 负责：

- PDF
- 视频
- 下载包
- 大图
- 版本化媒体资源
- 独立缓存策略的 Mermaid 产物

---

## 7. Mermaid 策略

### 7.1 基本原则

主站中的 Mermaid 图默认应在**构建期预渲染为 SVG**，而不是在请求时动态生成。

### 7.2 原因

这样可以：

- 降低首屏运行时负担
- 避免浏览器端 Mermaid JS 成为关键依赖
- 提高 SEO、截图和静态预览稳定性
- 避免 Worker 承担图渲染计算
- 让图产物直接进入缓存链路

### 7.3 三类图的处理方式

1. 固定图
	- build 阶段生成 SVG
	- 随站点静态产物发布

2. 版本化图
	- build 阶段生成 SVG
	- 上传到 R2
	- 页面按版本引用

3. 用户输入图
	- 不属于主站默认能力
	- 如未来需要，再单独设计异步渲染链路

## 8. 主站语言策略

主站建议直接采用**中英文双语站**，而不是先做英文单语、后续再补中文。

### 8.1 推荐模式

- 默认英文：`/`
- 中文版本：`/zh/`

页面示例：

- `/` ↔ `/zh/`
- `/product` ↔ `/zh/product`
- `/pricing` ↔ `/zh/pricing`
- `/blog/<slug>` ↔ `/zh/blog/<slug>`

### 8.2 当前页面范围

首批建议只做这些页面类型：

- 首页
- 产品页
- 定价页
- 更新页 / 博客页

暂不进入首批范围：

- 公司页
- Careers
- Press
- 法务以外的扩展品牌页

### 8.3 实现原则

- 路由层面直接保留语言前缀
- 内容层面使用独立中英文内容源
- SEO 层面补齐 canonical 与 hreflang
- Worker 只负责 locale 判断和跳转，不负责动态翻译

---

## 9. URL 职责划分

建议按路径职责明确拆分：

- `/`、`/product`、`/pricing`、`/blog/*` → Astro 英文静态页面
- `/zh/`、`/zh/product`、`/zh/pricing`、`/zh/blog/*` → Astro 中文静态页面
- `/assets/*` → Workers Static Assets
- `/media/*` → R2 公共资源
- `/downloads/*` → R2 下载资源
- `/api/*` → Worker API
- `/diagrams/*` → 预渲染 Mermaid 图
- `docs.olavai.com/*` → 独立文档站

---

## 10. 缓存策略

### 10.1 HTML

建议：

```text
Cache-Control: public, max-age=0, s-maxage=300, stale-while-revalidate=86400
```

### 10.2 指纹化静态资源

建议：

```text
Cache-Control: public, max-age=31536000, immutable
```

### 10.3 R2 大对象

按资源类型设置长期缓存，并尽量使用版本化路径，而不是原地覆写对象。

建议：

```text
Cache-Control: public, max-age=604800, stale-while-revalidate=86400
```

版本化路径（如 `/media/v2/hero.mp4`）可以使用更激进的缓存：

```text
Cache-Control: public, max-age=31536000, immutable
```

### 10.4 预渲染 Mermaid 图（`/diagrams/*`）

Mermaid SVG 在 build 时生成，内容随部署变更，与指纹化静态资源同等对待：

```text
Cache-Control: public, max-age=31536000, immutable
```

前提是路径包含构建哈希或版本号。如果使用固定路径，则退回到 HTML 策略。

### 10.5 Worker API（`/api/*`）

API 响应不缓存：

```text
Cache-Control: no-store
```

如果存在只读查询类端点（如 feature flags 配置），可以放宽为：

```text
Cache-Control: private, max-age=0, s-maxage=60
```

## 12. 迁移规则

如果正式拆分，必须遵守以下规则：

1. `olav-doc` 只能保留唯一权威文档源码
2. `olav-web` 只能保留唯一权威主站源码
3. 不允许长期并行维护：
	- `olav-doc/web/`
	- `olav-web/...`
4. 拆分完成后必须同步更新：
	- `dev_docs/03. REPO_BOUNDARY_AND_OWNERSHIP.md`（Delivery Units 表增加 `olav-web`）
	- `ownership_manifest.yaml`（`owners` 列表增加 `olav-web`，添加对应路径规则）
	- `CLAUDE.md`（仓库结构表增加 `olav-web`）
	- `olav-doc/README.md`
	- `olav-web/README.md`
5. `olav-web` 将成为第五个 delivery unit，依赖方向为 `olav-web -> none`（与 `olav-doc` 一样不依赖 runtime）

否则会重新出现双源漂移。

---

## 13. 最终建议

### 13.1 如果目标只是更快完成 Cloudflare 多域名映射

保持单 repo 即可，不需要立即拆分。

### 13.2 如果目标是让主站以独立边缘应用长期演进

应拆出 `olav-web`。

### 13.3 本文建议

推荐采用三阶段策略：

1. 先在 `olav-doc/web/` 内验证主站目标架构
2. 一旦正式进入 Worker + R2 + Mermaid 实施阶段，拆出 `olav-web`
3. 再同步更新边界治理和 ownership 文档

这样可以避免过早拆分，也不会把长期边界继续拖模糊。

---

## 14. 结论

最终结论如下：

- **仅为了 Cloudflare 多域名映射，不需要拆 repo**
- **为了主站长期独立演进，建议拆出 `olav-web`**
- **首批主站范围为：首页、产品页、定价页、更新页，暂不做公司页**
- **主站直接采用中英文双语站：默认英文 `/`，中文 `/zh/`**
- **主站推荐架构是：Static-first Astro + Workers Static Assets + Thin Worker + R2 + build-time Mermaid**
