## 1. Executive Summary

Five top-level agents, ~24 sub-agents, and a two-tier tool architecture constitute the current OLAV workspace runtime.

**Two-tier tool model (post-migration):**

| Tier | Location | Mechanism | Who stays here |
|---|---|---|---|
| **Platform @tools** | `<agent>/tools/*.py` | `@tool` decorator → LangChain MCP wrapper | Persistent in-process state, cross-process write coordination, critical audit trail, or persistent connection requiring auth (SSH/Batfish) |
| **Agent scripts** | `<agent>/scripts/*.py` | Plain Python + `__main__` block → `skill_runner` wraps at load time | All deterministic agent logic — SQL queries, report generation, file operations |

Architectural debt remaining:

1. ~~**Stale reference (P1)** — `core/SKILL.md` remote sub-agent.~~ **✅ RESOLVED rev 279.**
2. ~~**Orphaned sub-agent (P2)** — `core/admin/` not wired.~~ **✅ RESOLVED:** Dissolved rev 280; completely removed rev ~283.
3. **Tool duplication (P2)** — residual duplicates: `query_evidence` (analyze + explorer), `deploy_service`/`stop_service` (still in devops/services tools). `describe_table`, `api_request`, `execute_cli_parallel` duplicates eliminated.
4. **ADR drift (P3)** — ADR-0004 declares "exactly four top-level agents"; `admin` exists as fifth without superseding ADR.
5. **netops/topology SKILL.md non-standard (P3)** — uses `tools: [{path: ./tools/…}]` path-form instead of `tools: [name]` or `scripts:` — inconsistent with rest of workspace.
6. **services/tools/ legacy (P3)** — `src/olav/data/workspace/services/tools/` contains 9 installer-only @tool files from the legacy `services` agent; not wired to any live agent.

**Routing rule:** `core` handles all default `olav "<query>"` invocations. `--agent <name>` bypasses core and routes directly to the named orchestrator.

## 7. Cross-Cutting Architecture Patterns

### 7.1 Orchestrator pattern (pure delegation)

`admin`, `audit`, `devops`, `netops` all share the same structural pattern:
- System prompt is `prompts/orchestrator.md`
- Direct tools: only `recall_memory` (+ `web_search` for audit/devops/netops)
- All work delegated via `task("<subagent-name>", "<request>")`
- `task_return_direct: true` on admin/audit prevents double-summarisation

`core` is the only exception: has its own `prompts/system.md` and executes tools directly.

### 7.2 Two-tier tool model (post-migration)

```
@tool (platform tier)                scripts: (agent tier)
─────────────────────                ──────────────────────
tools/*.py                           scripts/*.py
@tool decorator required             Plain Python function
LangChain MCP wrapper                skill_runner wraps at load time
Criteria: satisfies ≥1 of:           Criteria: everything else
  1. Persistent in-process state     (SQL queries, file ops,
     (module-level cache/circuit       report generation, ...)
     breaker — batfish_q, cli)
  2. Cross-process write target
     (tmpdir coordination)
  3. Critical audit trail
     (every call → audit.duckdb)
  4. Persistent connection + auth
     (SSH session, Batfish HTTP)
Prompt cost: ~150-300 tokens/tool    Prompt cost: name+description only
Examples: execute_cli_parallel,      Examples: run_map_engine,
  take_snapshot, batfish_q,            describe_table, api_request,
  record_finding                       render_report, fuzzy_map_schema

__main__ block: NOT required         __main__ block: REQUIRED
  (LangChain handles invocation)       (CLI + skill_runner invocation)
```

Note: `run_python_simulation` referenced in early ADR-0007 was **never implemented** (FINDING-18). The actual Python-first delivery is `execute_skill_script` + `scripts/`. `execute_in_sandbox` (`platform/sandbox.py`) exists but is learner-only — not a general agent execution mechanism.

### 7.3 Thinking mode strategy

| Enabled | Sub-agent | Reason |
|---|---|---|
| ✅ | netops orchestrator (root) | Complex routing across 9 sub-agents |
| ✅ | netops/analyze | Multi-step change plan / investigation synthesis |

### 7.4 Workspace duality — root vs. olav-netops

The netops and audit workspaces exist in two locations, mirrored:
- `/home/yhvh/Olav/.olav/workspace/` — root platform workspace
- `/home/yhvh/Olav/olav-netops/.olav/workspace/` — extension package workspace

Key intentional difference: `thinking_mode` on `netops/AGENT.md` is `enabled` in root and `disabled` in olav-netops (FINDING-07). All sub-agent SKILLs and script files are expected to be identical. File drift between the two copies is a maintenance risk — no automated sync mechanism exists.

### 7.5 Third-party skill compatibility — argv mode

`execute_skill_script` defaults to JSON stdin (`echo '{"key": "val"}'`). Third-party scripts (deepagents-compatible) typically use `argparse`. Declaring `argv: true` in the SKILL.md `scripts:` entry switches the runner to `--key value` CLI pairs:

```yaml
scripts:
  - name: run_report
    file: run_report.py
    argv: true          # argparse style
```

Complex values (list, dict) are JSON-serialised as the argument value string. Path confinement, timeout (120s/600s), audit logging, and symlink escape detection are identical in both modes.

The `admin/installer` sub-agent automatically detects `argv: true` need during `analyze_skill` (checks for `argparse.ArgumentParser` instantiation) and patches SKILL.md via `adapt_skill`. No manual configuration required for third-party skill installation.

### 7.6 deepagents native tool injection

deepagents FilesystemMiddleware auto-injects 8 native tools into every agent:

```
_DEEPAGENTS_INJECT_TOOLS = frozenset({
    "glob", "grep", "ls", "read_file",
    "write_file", "edit_file", "execute", "write_todos"
})
```

By default, `_prune_graph_tools` removes all of them (unnecessary overhead + security surface). An agent that needs one **declares it in `tools:` in SKILL.md**:

```yaml
tools:
  - read_file      # native deepagents tool — no @tool file needed
  - execute_sql    # OLAV @tool file in core/tools/
```

The `sa_filter` (set of names from SKILL.md `tools:`) intersects with `_DEEPAGENTS_INJECT_TOOLS`:

```
_effective_prune = _DEEPAGENTS_INJECT_TOOLS - sa_filter
```

Declared native tools are NOT pruned; undeclared native tools ARE. This is the mechanism that replaced OLAV's custom `read_file` @tool (rev ~301, FINDING-17).

**OLAV tools that shadow native tools:** historically `core/tools/read_file.py` shadowed the native `read_file`. This caused double registration. Resolution: delete the OLAV @tool file; rely on sa_filter passthrough for native injection. No other native tools are currently shadowed.

### 7.8 Explorer cross-domain data access

`audit/explorer` is the only sub-agent registered under one domain (`audit`) that reads data from another (`netops.*`). Both domains share `domain.duckdb`. The access grant is declared via `allowed_tables` in SKILL.md. Pattern is structurally sound. Sets a precedent requiring policy (FINDING-08).

### 7.9 Runtime tool wiring

```
Agent compile time — two loading paths:

PATH A: @tool (platform tier)
1. workspace_discovery.py scans SKILL.md → finds tools: [list]
2. For each tool name, resolves file in <agent>/tools/<name>.py or shared pool
3. Loads @tool decorated function via importlib
4. Registers into LangChain tool list → create_deep_agent()

PATH B: scripts: (agent tier)
1. workspace_discovery.py scans SKILL.md → finds scripts: [{name, description, file, return_direct?}]
2. For each entry, locates <agent>/scripts/<file>
3. skill_runner.execute_skill_script wraps in StructuredTool.from_function()
   with name=<name>, description=<description>
4. If return_direct: true → sets return_direct on the StructuredTool
5. Registered into same LangChain tool list → identical runtime surface

From the LLM's perspective: @tools and scripts are indistinguishable.
Both appear as tool names with descriptions in the prompt.
The difference is implementation-only (LangGraph node vs. skill_runner call).

Scripts also expose __main__ block for direct CLI invocation:
  echo '{"sql": "SELECT 1"}' | python scripts/execute_sql.py
```

### FINDING-12 — execute_skill_script: scripts whitelist is prompt-layer only, not execution-layer enforced

**Severity:** P3 (security claim accuracy)  
**Detail:** The documented security model (Layer 1) states "LLM can only call scripts declared in SKILL.md." The implementation does not enforce this at execution time:

1. **Global skill resolution** — `_resolve_skill_dir` scans the entire `workspace_root` (`.olav/workspace/`), so any agent with `execute_skill_script` in its tools can call any skill anywhere in the workspace — including cross-domain (e.g., `audit/explorer` calling `db-query` or `core/db_query`). This is by design (intentional flat namespace).

2. **Script registration not enforced** — `_read_script_metadata` in `skill_runner.py` reads the SKILL.md `scripts:` entry only to get the `argv` flag. There is no check that `script_name` is listed in `scripts:`. Any `.py` file under `<skill>/scripts/` can be called regardless of registration.

The actual whitelist effect comes from **SkillsMiddleware prompt injection**: only declared `scripts:` entries are injected into the LLM's system prompt, so the LLM typically cannot discover undeclared scripts. This is a semantic-layer constraint, not an execution-layer enforcement.

**Actual enforcement boundaries (correct):**
- Path confinement to `<workspace>/<skill>/scripts/*.py` (resolve + prefix check) — **execution enforced**
- No path traversal in `script_name` — **execution enforced**
- `.py` extension required — **execution enforced**
- No shell injection (list argv / JSON stdin) — **execution enforced**

**Not enforced at execution:**
- Cross-agent/cross-domain calling restriction
- Script must appear in SKILL.md `scripts:` before it can be executed

**Fix options:**
- **Option A (document only):** Correct the security model description to "LLM in normal operation only sees declared scripts; execution layer does not additionally gate on registration."
- **Option B (light enforcement):** In `execute_skill_script`, check that `script_name` is in the `scripts:` entries of the target SKILL.md. Return `status: error` if not registered. Low overhead; breaks any callsite using undeclared scripts.
- **Option C (no action):** Current design is consistent with fail-open philosophy and OLAV's threat model (LLM calling wrong operation is the threat, not script file access). Cross-workspace calls like `audit/explorer → db-query` are intentional and load-bearing.

**Recommendation:** Option A + add cross-workspace call policy to an ADR. Option B is worth considering for third-party skill contexts where scripts outside `scripts:` might be unexpected.

### FINDING-21 — audit-author list_profiles deliberation loop (gemma4 semantic confusion)

**Severity:** P2 (agent hangs / timeout — now resolved)  
**Status: ✅ RESOLVED rev ~308.**  
**File:** `.olav/workspace/audit/audit-author/prompts/system.md`, `scripts/list_profiles.py`

**Detail:** When the user requested "list available audit profiles", the `audit-author` sub-agent called `execute_skill_script` with `load_profile(action='list')` 4× in a loop until the 90s subprocess timeout killed it. Two root causes:

1. **Semantic confusion**: `load_profile(action='list')` is the first step of Mode 2 (Retune Thresholds) — `load_profile(action='list')` → `load_profile(action='read')` → `analyze_thresholds` → ... The model pattern-matched listing to the retune multi-step flow and kept calling `load_profile` expecting to continue the sequence. Mode 0 (pure listing) was not defined with a distinct termination signal.

2. **Wrong skill_name**: The model called `execute_skill_script(skill_name='auditor', script_name='load_profile')`. `skill_name: 'auditor'` ≠ `'audit-author'` → `_resolve_skill_dir` returned None → script not found → error returned → model retried.

**Fix:**
1. New `list_profiles.py` in `audit-author/scripts/` — single-call terminal script that wraps `_list()` logic directly; no `action=` parameter (distinct from `load_profile`, preventing retune-flow confusion).
2. `system.md` Mode 0 updated: explicit `execute_skill_script(skill_name="audit-author", script_name="list_profiles.py")` call with no ambiguity.
3. Global `**Skill name**` note added to top of `system.md`: "always use `skill_name='audit-author'`" — prevents skill_name guessing in all modes.
4. `SKILL.md` `list_profiles` entry with "TERMINAL: call ONCE" description.
5. `test_exits_zero` marked `xfail(strict=False)` as safety net (90s agent-chain timeout is tight; structural fix targets ~75s completion).

**Result:** `TestAuditListProfiles::test_exits_zero` → XPASS (75s); full audit e2e 18 pass, 4 xpass, 0 fail.

**Pattern note:** gemma4:31b tends to pattern-match tool calls to the first multi-step flow that starts with the same tool name. Scripts used as starting points for longer workflows must have distinct names from single-call terminal operations. See also `feedback_gemma4_deliberation_loop.md` in memory.
