# 48. Cross-Workspace Tool Architecture

**Date:** 2026-04-15
**Status:** Design rationale — guides v0.19+ implementation

---

## Three Layers

```
┌─────────────────────────────────────────────────────────┐
│ Layer 1: Implementation (Python packages)                │
│   olav.tools.sql, olav_netops.tools.ssh, etc.           │
│   Any code can import any package. No workspace needed.  │
├─────────────────────────────────────────────────────────┤
│ Layer 2: Registration (workspace @tool wrappers)         │
│   core/tools/execute_sql.py → @tool → olav.tools.sql    │
│   ops/tools/execute_cli.py → @tool → olav_netops.ssh    │
│   Determines what the LLM sees as available tools.       │
├─────────────────────────────────────────────────────────┤
│ Layer 3: Composition (AGENT.md + runtime loading)        │
│   Which tools load for which agent at runtime.           │
│   core tools inherited by all. Domain tools scoped.      │
└─────────────────────────────────────────────────────────┘
```

## Tool Inheritance Rules

```
                    ┌──────────┐
                    │   core   │  ← platform tools (execute_sql, api_request, ...)
                    └────┬─────┘
                    inherits ↓ (automatic, all agents get core tools)
             ┌──────────┴──────────┐
             │                      │
        ┌────┴────┐           ┌────┴────┐
        │   ops   │           │  audit  │
        └────┬────┘           └────┬────┘
    ┌────┬───┴───┬────┐      ┌────┼────┐
    │    │       │    │      │    │    │
  anal probe  diff  lab   design audit learn
```

**Rule 1:** Core tools → inherited by ALL agents and subagents (automatic).
**Rule 2:** Domain tools → scoped to their workspace only.
**Rule 3:** No upward inheritance — core never loads domain tools.
**Rule 4:** No lateral inheritance — ops tools not available in audit (at @tool level).

## Cross-Workspace Invocation Patterns

### Pattern 1: Downward (core → domain) — Semantic Routing

User asks a domain question → core's semantic router delegates to the right agent.

```
User: "check R1 BGP status"
  → core semantic router: confidence(ops) > 0.85
  → delegate to ops agent
  → ops uses execute_cli (its own tool) to SSH
  → returns result
```

No cross-workspace tool loading. Fully decoupled.

### Pattern 2: Upward (domain → core) — Automatic Inheritance

Domain agents need platform capabilities → they inherit core tools.

```
ops agent loading:
  1. Load core tools: execute_sql, api_request, recall_memory, ...
  2. Load ops tools: execute_cli, take_snapshot, ...
  3. LLM sees all tools combined
```

Already implemented. No code change needed.

### Pattern 3: Lateral (audit → ops tool) — Package Import

Audit's /learn_cmd needs SSH → import from package, not from workspace.

```python
# audit/learner/tools/learn_cmd.py (workspace @tool wrapper)
@tool
def learn_cmd(device: str, command: str) -> str:
    # Direct Python import — NOT loading ops workspace tools
    from olav_netops.tools.ssh import execute_on_device
    from olav_netops.tools.textfsm_parse import parse_output
    
    raw = execute_on_device(device, command)
    template = _generate_textfsm_template(raw["raw_output"])
    return template
```

At the **@tool level**, audit agent doesn't "see" execute_cli.
At the **Python level**, audit code can import any function.
The LLM doesn't know about the cross-workspace dependency.

### Pattern 4: Agent Delegation (core → ops for complex tasks)

Core can't SSH, but can delegate to ops agent.

```python
# Used by LLM when it decides core can't handle a request:
olav_delegate(agent="ops", task="Take a snapshot of R1 with show version")
```

Already implemented via `olav_delegate` tool.

## What Goes Where

### Tool Registration (which workspace owns the @tool)

| @tool | Workspace | Why |
|---|---|---|
| execute_sql | core | Any data source, not just netops |
| api_request | core | Any registered service |
| recall_memory | core | Platform knowledge store |
| web_search | core | General purpose |
| run_python_code | core | General purpose |
| workspace_health | core | Platform maintenance |
| execute_cli | ops | Network SSH — domain specific |
| take_snapshot | ops | Network collection — domain specific |
| diff_* | ops | Network drift — domain specific |
| deploy_lab | ops | ContainerLab — domain specific |
| analyze_thresholds | audit | Compliance — domain specific |
| learn_cmd | audit | Learning — but CALLS ssh via package import |

### Implementation (which package owns the code)

| Function | Package | Can be imported by |
|---|---|---|
| `query_duckdb()` | `olav.tools.sql` | Anyone |
| `service_request()` | `olav.tools.api` | Anyone |
| `search_memory()` | `olav.tools.memory` | Anyone |
| `execute_on_device()` | `olav_netops.tools.ssh` | Anyone (if olav-netops installed) |
| `parse_output()` | `olav_netops.tools.textfsm_parse` | Anyone |
| `collect_snapshot()` | `olav_netops.tools.snapshot` | Anyone |

### Context (what enriches the agent's understanding)

| Context | Location | Loaded by |
|---|---|---|
| DB schema hints | Dynamic from information_schema | execute_sql at runtime |
| Service API references | `core/references/services/` | core agent static_context |
| Network domain prompts | `ops/prompts/` | ops agent only |
| Audit profiles | `audit/profiles/` | audit agent only |

## The Decoupling Test

**Can olav work without olav-netops?**

| Capability | Without netops | With netops |
|---|---|---|
| `olav "query"` → execute_sql | ✅ (DB may be empty) | ✅ (DB has device data) |
| `olav registry register X` | ✅ | ✅ |
| `olav "query X API"` | ✅ (if X registered) | ✅ |
| `olav "SSH to R1"` | ❌ (no execute_cli) | ✅ |
| `olav kb import/search` | ✅ | ✅ |
| Schema hints | ✅ (dynamic, shows actual tables) | ✅ (includes netops tables) |

**Can olav-netops tools be used without OLAV workspace?**

```python
# Yes — direct Python import
from olav_netops.tools.ssh import execute_on_device
from olav_netops.tools.textfsm_parse import parse_output

raw = execute_on_device("R1", "show version")
parsed = parse_output("cisco_ios", "show version", raw["raw_output"])
```

## Core Subagent Architecture

Core has 15 tools — too many for reliable LLM tool selection. Split into subagents with strict tool isolation:

```
core orchestrator
  │ (sees only subagent descriptions, routes by intent)
  │
  ├── db_query/           ← "查数据/列出/多少/BGP状态"
  │   execute_sql           DuckDB queries (devices, topology, parsed data)
  │   recall_memory         Knowledge base search
  │   web_search            External web search
  │   format_and_export     Output formatting
  │
  ├── api_query/          ← "查 API/NetBox/InfluxDB"
  │   api_request           HTTP request to registered services
  │   service_health        Service health check
  │   web_search            External web search (API docs, troubleshooting)
  │   format_and_export     Output formatting
  │
  ├── remote/             ← "SSH/远程执行/shell"
  │   remote_execute        SSH to remote hosts
  │   run_shell             Local shell commands
  │
  └── admin/              ← "平台管理/健康检查/部署"
      workspace_health      Platform audit
      bulk_ingest           Staging → DuckDB
      analyze_logs          Audit log analysis
      manage_cron           Cron management
      deploy_service        Docker Compose up
      stop_service          Docker Compose stop
      write_workspace_file  Write workspace files
```

**Key isolation rule:** `execute_sql` and `api_request` are in DIFFERENT subagents.
LLM cannot accidentally use `api_request` when it should use `execute_sql`.
  
  ── Output ──
  format_and_export   → (existing)
  
  ── Platform Management ──
  workspace_health    → (merged check_health + audit_workspace)
  bulk_ingest         → olav.core.ingest_manager
  analyze_logs        → (existing)
  manage_cron         → (existing)
  write_workspace_file → (existing)
  sync_tools          → (existing)
```

## Summary

| Question | Answer |
|---|---|
| Tool 归属 | @tool 在 workspace（定义 LLM 可见范围），实现在 package（任何人可 import） |
| 跨 workspace 调用 | Python import（Layer 1）— 不经过 @tool 层 |
| core 调域工具 | 不直接调——通过 semantic routing 委托给域 agent |
| 域 agent 调 core 工具 | 自动继承——所有 agent 加载时先加载 core tools |
| 域 agent 互调 | Package import（如 audit 的 learn_cmd import ssh）|
| 能否完全解耦 | Implementation 层完全解耦；Registration 层 workspace 隔离；Composition 层 core 单向继承 |
| SSH 归属 | 通用 SSH → core (`remote_execute`)；网络设备 SSH → ops (`execute_cli`) |
| 平台已有能力未暴露 | SSHBackend + LifecycleManager 应加 @tool wrapper |
| 避免重复造轮子 | 12 个平台模块审计完毕，2 个需新增 tool，其余正确保持 internal |
