# 20. 安全模型 — Olav 内网可信平台

**Date:** 2026-03-31
**Status:** 当前实现状态记录
**定位:** 内网部署、可信用户、不对外暴露

---

## 1. 平台安全定位

Olav 是一个**内网只读 AIOps 平台**，部署在受控内网环境中，使用者为可信内部用户。

**不在威胁模型内:**
- 外部攻击者直接访问
- 多租户隔离（不同组织间）
- 公网 API 暴露
- 消息网关（Slack/Telegram/webhook）对外暴露操作入口

**在威胁模型内:**
- agent 幻觉或误操作导致的意外破坏性操作
- prompt injection（来自采集的网络设备数据、KB 文档）
- 内部用户误配置
- skill 包含恶意代码（跨 skill 包冲突或注入）

---

## 2. 安全层总览

```
请求路径                    安全机制                        强度
────────────────────────   ─────────────────────────────   ──────
execute_cli                check_approval() 危险命令检测     硬约束
execute_sql                DuckDB read_only=True 连接       硬约束
API 工具生成               readonly_only=True 只生成 GET     硬约束
sandbox HTTP 写操作        sandbox_guard.py 预执行扫描       软约束
sandbox DB 写操作          sandbox_guard.py 预执行扫描       软约束
memory/KB 写入             injection_scanner.py             软约束
skill 安装                 MANIFEST.yaml 签名验证（计划）    —
```

硬约束 = 执行层强制，无法被代码绕过。
软约束 = 正则/模式扫描，有已知旁路（见 §5）。

## 3. 各层详细设计

### 3.1 execute_cli — 危险命令审批

**文件:** `src/olav/platform/safety/approval.py`

在 Nornir 执行网络设备 CLI 命令前调用 `check_approval(command, device)`。

覆盖的危险类别:

| 类别 | 示例命令 | 严重度 |
|------|---------|--------|
| 设备重载 | `reload`, `reload in 5` | high |
| 配置清除 | `write erase`, `erase startup-config` | high |
| 路由协议删除 | `no router bgp 65000`, `no router ospf 1` | high |
| 接口关闭 | `interface Gi0/0` + `shutdown` | high |
| AAA 禁用 | `no aaa new-model` | high |
| SRL 网络实例删除 | `delete network-instance default` | high |
| SSH 禁用 | `no ip ssh` | medium |
| 文件系统格式化 | `format flash:` | high |

只读命令（`show`, `display`, `ping`, `traceroute` 等）直接放行，不触发检测。

**HITL 机制:** 返回 `{"status": "requires_approval", "reason": ..., "suggested_action": ...}`，agent 必须通过 `record_hitl_requested()` 上报并等待人工确认。

### 3.2 execute_sql — 数据库只读约束

**文件:** `.olav/workspace/ops/tools/execute_sql.py`

```python
# 所有查询连接强制 read_only=True
with duckdb.connect(str(MAIN_DB_PATH), read_only=True) as conn:
    ...
```

DuckDB 驱动层面拒绝任何写操作（DELETE/DROP/UPDATE/INSERT）。这是**不可绕过的硬约束** — 即使 agent 写出 `DELETE FROM netops.devices`，连接本身会报错拒绝。

UPDATE/DELETE/DDL 语句走单独审批路径（`requires_approval: True`）。

### 3.3 API 工具生成 — readonly_only 过滤

**文件:** `src/olav/platform/services/registry.py`, `tool_generator.py`

```yaml
# .olav/config/services.yaml
netbox:
  readonly_only: true       # 默认 — 只生成 GET 工具

containerlab:
  readonly_only: false      # 模拟系统 — 需要 POST/DELETE（部署/销毁 lab）
```

`tool_generator` 在生成工具文件时过滤掉非 GET/HEAD/OPTIONS 操作。生成的工具集中根本不存在 `netbox_delete_device()`，agent 无法调用不存在的工具。

**设计原则:** 写工具的缺席比运行时拦截更可靠。

**例外:** ContainerLab 作为模拟/实验室系统，需要部署和销毁能力，显式设 `readonly_only: false`。新增服务时默认只读，需要写权限时显式声明。

### 3.4 sandbox 外部写操作 — sandbox_guard

**文件:** `src/olav/platform/safety/sandbox_guard.py`

`execute_in_sandbox()` 在执行任何代码前调用 `scan_sandbox_code(code)`，检测外部写操作。

**拦截模式:**

```
httpx.delete(...)          → "HTTP mutation via httpx"
httpx.post(...)            → "HTTP mutation via httpx"
requests.put(...)          → "HTTP mutation via requests"
client.request("DELETE",..)→ "HTTP mutation via client.request"
service_call("x","DELETE") → "External API mutation via service_call"
curl -X DELETE ...         → "HTTP mutation via subprocess curl"
.execute("DELETE FROM ..") → "Database mutation in .execute()"
.execute("DROP TABLE ..")  → "Database mutation in .execute()"
```

**明确允许（本地文件系统操作不受限）:**
```python
open('/tmp/out.csv', 'w')      # 本地文件写 ✅
os.remove('/tmp/old.txt')      # 本地文件删 ✅
shutil.rmtree('/tmp/workdir')  # 本地目录删 ✅
duckdb.connect(..., read_only=True)  # 只读DB连接 ✅
httpx.get('http://...')        # HTTP 读 ✅
```

**触发时:** 返回 `{"status": "requires_approval", "reason": ..., "suggested_action": ...}`，代码不执行。

### 3.5 prompt 注入扫描

**文件:** `src/olav/platform/safety/injection_scanner.py`

在以下写入路径调用 `scan_content(text)`:
- `recall_memory` 工具的内容写入
- workspace SKILL.md / AGENT.md 加载路径
- KB 文档导入

检测模式覆盖: 角色劫持、指令覆盖、数据外泄 payload、不可见 Unicode。

## 4. 各路径安全状态矩阵

| 操作 | 路径 | 是否被保护 | 机制 |
|------|------|-----------|------|
| 查询设备列表 | `execute_sql(SELECT ...)` | ✅ 允许 | read_only 连接 |
| 删除设备记录 | `execute_sql(DELETE ...)` | ✅ 拦截 | read_only 拒绝 |
| 推送危险 CLI | `execute_cli("write erase")` | ✅ 拦截 | check_approval |
| 推送安全 CLI | `execute_cli("show ip bgp")` | ✅ 允许 | 白名单前缀 |
| 调用 netbox 写 API | 工具不存在 | ✅ 无法调用 | readonly_only |
| 调用 clab 销毁 lab | `service_call("clab","DELETE",...)` @tool | ✅ 拦截 | service_call 写方法审批 |
| 调用 clab 销毁 lab | `service_call(...)` via sandbox | ✅ 拦截 | sandbox_guard（正则） |
| sandbox httpx.delete | `run_python_code` | ✅ 拦截 | sandbox_guard（正则） |
| sandbox httpx.get | `run_python_code` | ✅ 允许 | 不触发 guard |
| sandbox 写本地文件 | `run_python_code` | ✅ 允许 | 本地 FS 豁免 |
| sandbox duckdb 写（直接） | `run_python_code(.execute("DELETE..."))` | ✅ 拦截 | sandbox_guard（正则） |
| sandbox duckdb 写（变量拼接） | `con.execute(f"{op} FROM ...")` | ✅ 拦截 | DuckDB monkey-patch（硬约束） |

## 5. 已知局限性（软约束旁路）

`sandbox_guard` 基于静态正则扫描，存在以下已知绕过方式。这些场景在**内网可信用户**的威胁模型下可接受，但在多租户或外部用户场景下不够。

**① import 别名**
```python
import httpx as h
h.delete("http://clab/labs/prod")   # "httpx" 不在代码中
```

**② 动态方法调用**
```python
getattr(httpx, "delete")("http://...")
method = "DEL" + "ETE"
httpx.request(method, "http://...")
```

**③ subprocess 二次执行**
```python
# 写本地文件是允许的，然后通过 subprocess 执行
with open('/tmp/x.py', 'w') as f:
    f.write("import httpx; httpx.delete('http://...')")
subprocess.run(['python3', '/tmp/x.py'])
```

**④ 未覆盖的 HTTP 库**
```python
import urllib.request, aiohttp   # 不在扫描规则中
```

**⑤ raw socket**
```python
import socket
s = socket.socket()
s.connect(("192.168.100.12", 8080))
s.send(b"DELETE /api/v1/labs/prod HTTP/1.1\r\n...")
```

**⑥ SQL 变量拼接**
```python
import duckdb
con = duckdb.connect(".olav/databases/olav.duckdb")
op = "DELETE"; con.execute(f"{op} FROM netops.devices")
```

## 6. 已实施加固项

以下三项已通过 TDD 实施（2026-03-31，17 unit tests green）。

### 6.1 ✅ DuckDB sandbox monkey-patch

**文件:** `src/olav/platform/sandbox.py` — `_DUCKDB_READONLY_PROLOGUE`

每个 sandbox 脚本的开头注入：

```python
try:
    import duckdb as _olav_ddb
    _olav_ddb_orig_connect = _olav_ddb.connect
    def _olav_ddb_safe_connect(database=':memory:', read_only=False, **_kw):
        return _olav_ddb_orig_connect(database, read_only=True, **_kw)
    _olav_ddb.connect = _olav_ddb_safe_connect
except ImportError:
    pass
```

封死所有 sandbox 内的 DuckDB 写操作，包括变量拼接的 SQL（§5 旁路⑥）。
子进程层面强制，Python 内部无法绕过。读操作（SELECT）不受影响。

### 6.2 ✅ 网络命名空间隔离（per-call opt-in）

**文件:** `src/olav/platform/sandbox.py` — `_build_sandbox_cmd()`, `execute_in_sandbox()`

隔离通过 `network_isolation` 参数按调用控制，而非全局 env var：

```python
# 纯计算类 sandbox（simulation、diff、topology）— 强制隔离
execute_in_sandbox(code, network_isolation=True)

# 需要外部网络的 sandbox（lab agent httpx → clab API）— 允许网络
execute_in_sandbox(code, network_isolation=False)
```

优先级：调用参数 > 环境变量 `OLAV_SANDBOX_NETNS=1`（全局默认，兼容旧配置）。

启用后，sandbox 子进程使用 `unshare --net` 隔离，`httpx`/`socket`/`urllib`/`aiohttp`/raw socket 全部 `Connection refused`（§5 旁路④⑤）。`unshare` 不可用时静默回退为普通执行。

**各 agent 隔离策略:**

| Agent | network_isolation | 原因 |
|-------|------------------|------|
| sim | `True` | 纯本地计算（networkx、DuckDB 内存克隆） |
| diff | `True` | 纯本地配置比对 |
| topology | `True` | 纯本地图分析 |
| lab | `False` | 需要 httpx 推送配置到 ContainerLab exec API |
| probe | N/A | 无 sandbox，直接 execute_cli |

新建 skill 时默认 `network_isolation=True`，只有明确需要外部 API 的工具才设为 `False`。

### 6.3 ✅ `service_call` 写方法审批

**文件:** `src/olav/platform/services/client.py`

```python
_WRITE_METHODS = frozenset({"DELETE", "POST", "PUT", "PATCH"})

if method.upper() in _WRITE_METHODS:
    return {"status": "requires_approval", "method": method, "path": path, ...}
```

所有写方法在到达 httpx 之前被拦截，返回 `requires_approval`。
封住通过 `service_call` @tool 直接调用写 API 的场景（不依赖 sandbox_guard）。

## 7. 审计与追责

即使某些操作绕过了预防性控制，审计层提供事后追责能力：

- **`audit.duckdb`:** 记录所有工具调用（工具名、参数、user_id、时间戳）
- **`record_network_event`:** append-only，agent 主动记录的变更事件
- **DuckDB WAL:** 数据库层面的写操作日志

对于内网可信用户场景，审计追责与预防性控制共同构成完整的安全闭环。

## 8. 不实施项说明

以下功能被明确排除，不在规划内：

| 功能 | 排除原因 |
|------|---------|
| 消息平台网关（Slack/Telegram/Discord） | 扩大外部攻击面，与内网定位矛盾 |
| Webhook 接收器 | 引入外部可触发的执行路径 |
| 公网 API 端点 | 不在部署场景内 |
| 外部存储导出（S3/GCS） | 超出内网边界，数据合规风险 |
| 旁路安全 LLM（guard LLM） | 对 sandbox 代码无效（见 §5），增加延迟和成本，收益有限 |

**旁路安全 LLM 的局限性说明:**
Guard LLM 对固定接口（execute_cli、execute_sql）有补充价值，但对 `run_python_code` 这种图灵完备执行环境基本无效 — 代码混淆、间接执行、变量拼接都能绕过语义理解。执行层的硬约束（§3.1-3.3）比 LLM 审查可靠得多。
