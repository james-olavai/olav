## 0. Why this exists

### The fundamental problem

Same concept, different vendor strings:

| Concept | Cisco IOS | Junos | Arista |
|---|---|---|---|
| BGP up | `Established` | `Estab` | `Established` |
| Interface up (L2 status) | `connected` | n/a | `connected` |
| Interface up (oper) | `up` | `up` | `up` |
| Interface admin-down | `administratively down` | `down` | `disabled` |

Every prior architecture failed at the same wall:

* **Cisco-as-canonical**: ethnocentric, every new vendor needs reverse-mapping.
* **OpenConfig YANG** (R67-R70 ARCH-24): rigid schema, hand-curated `(vendor.field, oc.path)` map → exploded into ~1240 LOC of lookup tables, deleted in R70.
* **Observed canonical** (R67 续): "argmax frequency wins" → bootstrap problem (first run has no observation), wrong dominant form sticks.
* **Field-normalizer rules** (R72/R83.2): tiny dict like `{"Estab": "Established"}` → still a hand-curated table; missing entries break next vendor.

All four required a maintenance table.  None scale to a heterogeneous fleet without recurring edits.

### The data-science textbook answer

```
1. INGEST   — raw values, no normalisation
2. PROFILE  — auto-summarise distinct values + frequency
3. CLUSTER  — group similar values via algorithm (no rules)
4. ANNOTATE — optionally LLM-classify clusters once, cache result
5. QUERY    — agent reads profile + clusters, writes SQL with confidence
```

OLAV today implements 1 only.  This doc adds 2-4.

### Architectural goal

Agent's NL-query loop drops from **4-6 SQL round-trips** (each round-trip costs LLM context + latency) to **2** (introspection then data).  Small models gain a single-shot view of "what data exists, in what shape, with what value variants".

## 1. The three caches

### Layer 1 — Schema cache (per-init refresh)

Already mostly in place via R83 per-command auto-views.  Each `/netops_init` rebuilds:

* `netops.v_show_<safe_command>_auto` — typed columns from `json_structure(parsed_data)`
* `netops.v_l2_links_auto` — column-rename projection of `topology_links`

**Gap to close (this doc)**: the agent currently has to call `information_schema.views` + `DESCRIBE <view>` per query to see what's available.  We pre-compute both into `netops.introspection_cache`.

### Layer 2 — Value cache (per-init refresh)

**New** `netops.value_profile`:

| view_name | column_name | value | freq | fingerprint | cluster_id |
|---|---|---|---|---|---|
| v_show_bgp_summary_auto | state | Established | 4 | established | 1 |
| v_show_bgp_summary_auto | state | Estab | 2 | estab | 2 |
| v_show_bgp_summary_auto | state | Idle | 1 | idle | 3 |
| v_show_ip_interface_brief_auto | status | up | 5 | up | 4 |
| v_show_ip_interface_brief_auto | status | administratively down | 1 | administratively down | 5 |

Built by:
1. Iterate every `v_show_*_auto` view; iterate every VARCHAR column with cardinality ≤ 30.
2. For each (view, column), `SELECT DISTINCT value, COUNT(*) FROM ... GROUP BY 1`.
3. Apply **OpenRefine fingerprint** in pure DuckDB SQL: `array_to_string(list_distinct(list_sort(regexp_split_to_array(lower(regexp_replace(value, '[^a-z0-9 ]', '', 'g')), '\s+'))), ' ')`.
4. Optional second pass: Levenshtein-merge fingerprints with edit-distance < 3 → same `cluster_id`.

**Open-source pedigree**: OpenRefine clustering (BSD, Google → community) is the gold-standard algorithm for categorical de-duplication.  We reimplement its fingerprint pass in 1 SQL expression — no PyPI dependency.

### Layer 3 — Pattern memory (cross-session, append-only)

Already implemented via `query_pattern_capture` + `AutoRecallMiddleware` (R83.2).  Stores ``(intent, working SQL)`` tuples; AutoRecall surfaces relevant ones as `<relevant-memories>` on the next similar question.

This layer learns **across sessions** what worked; the other two layers reset every `/netops_init`.

## 2. The unifying view: `netops.introspection_cache`

Single-row table, one JSON-bag column per concept:

```sql
CREATE OR REPLACE TABLE netops.introspection_cache AS
SELECT
    -- Fleet diversity
    (SELECT json_group_array(json_object(
                'hostname', hostname,
                'platform', platform,
                'role',     role,
                'site',     site,
                'ip',       ip_address))
     FROM netops.devices)                                                 AS fleet,

    -- Available views with their typed columns
    (SELECT json_group_array(json_object('view', view_name, 'cols', cols))
     FROM (
         SELECT v.table_name AS view_name,
                json_group_array(json_object('name', c.column_name, 'type', c.data_type)
                                  ORDER BY c.ordinal_position) AS cols
         FROM information_schema.views v
         JOIN information_schema.columns c
              ON c.table_schema = v.table_schema AND c.table_name = v.table_name
         WHERE v.table_schema = 'netops' AND v.table_name LIKE 'v_%_auto'
         GROUP BY v.table_name
     ))                                                                   AS views,

    -- Categorical value distributions + clusters
    (SELECT json_group_array(json_object(
                'view', view_name, 'col', column_name,
                'value', value, 'freq', freq,
                'cluster', cluster_id))
     FROM netops.value_profile)                                            AS value_distributions,

    -- Refresh timestamp
    NOW() AS refreshed_at;
```

Agent's NL-query workflow becomes:

```
1.  SELECT * FROM netops.introspection_cache;
    → JSON: { fleet: [...], views: [...], value_distributions: [...] }
2.  agent reasons over JSON  (LLM step, no SQL)
3.  SELECT ... FROM netops.v_show_<x>_auto WHERE col IN (...);
```

**Two SQL round-trips for any data question.**  Down from 4-6.

### Phase B — fingerprint clustering (target: next round)

OpenRefine fingerprint already in scope above.  Add Levenshtein second pass:

```sql
-- After fingerprint, merge clusters whose fingerprints differ but
-- levenshtein distance < 3 (handles 'establ' vs 'established').
WITH near AS (
    SELECT a.cluster_id AS a_id, b.cluster_id AS b_id
    FROM value_profile a, value_profile b
    WHERE a.view_name = b.view_name AND a.column_name = b.column_name
      AND a.cluster_id < b.cluster_id
      AND levenshtein(a.fingerprint, b.fingerprint) <= 3
)
-- union-find to merge cluster ids
```

### Phase C — semantic dimension tables (later)

Only if Phase A+B insufficient.  LLM-classify each cluster once:

```
cluster_id 1 (values: Established, Estab) → bucket: 'up'
cluster_id 2 (values: Idle)               → bucket: 'down'
```

Stored in `netops.dim_<concept>` with `(cluster_id, canonical, bucket)`.  Agent can JOIN for explicit semantic queries.

## 4. Cost / benefit

### `/netops_init` cost
* +1 SQL pass over per-command views (≤ 30 columns × ≤ 30 rows of distinct values)
* +1 row insert into introspection_cache
* **Estimated**: +1-2 seconds on a 6-device fleet, +5s on 100 devices.

### Per-query benefit
* Q1 (simple list): 4 → 2 round-trips (-50%)
* Q2 (BGP existence): 5 → 2 (-60%)
* Q3 (cross-platform interfaces): 17 → **3-4** (-80%) — agent sees Junos `terse` view + cisco `brief` view + the equivalence of `connected`/`up` in one read.
* Q4 (ops simulation): unchanged (uses run_python_simulation, not introspection-heavy).

### Memory pressure
* `introspection_cache` is a single row — JSON column ~10-50KB on a small fleet.  Negligible.
* `value_profile` is bounded by Σ(low-card columns × distinct values per column) — ~500 rows on a 6-device fleet.

### Scaling concern
On a 1000-device fleet:
* `fleet` JSON ~200KB — agents truncate at ~5KB context anyway, would need `LIMIT` or partitioning.
* `value_distributions` likely under 5000 rows — fine.
* Trigger: when fleet > 100 devices, switch from "single-row cache" to "per-platform partitions" — out of scope this round.

## 5. Trade-offs explicitly considered

### Keeping value_recipes-style L1 semantic views?

**No.**  Already deleted in R83.2 P1 — moving back would re-introduce the maintenance table.  The introspection cache + clustering replaces that role data-driven.

### Could we just rely on memory (P0) for everything?

**No.**  Memory is reactive — it captures what already worked.  An agent's *first* query for a new concept has no memory hit, so it must introspect.  A profile cache makes that first query work without LLM-knowledge of vendor variants.

### Should clustering be LLM-driven instead of fingerprint?

**Algorithmic first, LLM only as fallback.**  Fingerprint + Levenshtein covers ~80% of value variance (BGP/OSPF/interface state) deterministically and free.  Reserve LLM for the 20% where strings are semantically related but not lexically (`connected` vs `up`).  This becomes Phase C if needed.

### Materialised TABLE vs lazy VIEW?

**TABLE** for `introspection_cache` and `value_profile`.  Lazy views would re-scan parsed_outputs on every query (16 calls per Q3 → 16 full scans).  Materialised at /netops_init time is one scan, queried thousands of times until next snapshot.

## 8. Implementation notes

### Why single connection

Each `duckdb.connect()` opens a transaction.  Closing/reopening between steps doesn't share the in-memory query cache and adds ~100ms × 6 = 600ms.  More importantly, view definitions don't propagate across connections immediately on some DuckDB versions; a single-connection `finalise_ingest` is also less surprising.

`populate_devices` currently opens its own connection — refactor to accept `con` parameter (default to opening if not given, for back-compat with tests).

### How `build_value_profile` enumerates views

```python
def build_value_profile(con):
    # 1. Enumerate per-command auto-views
    views = con.execute("""
        SELECT table_name FROM information_schema.views
         WHERE table_schema='netops' AND table_name LIKE 'v_show_%_auto'
    """).fetchall()

    # 2. For each view, find low-cardinality VARCHAR columns
    rows = []
    for (view_name,) in views:
        cols = con.execute(f"""
            SELECT column_name FROM information_schema.columns
             WHERE table_schema='netops' AND table_name = '{view_name}'
               AND data_type IN ('VARCHAR', 'TEXT')
        """).fetchall()
        for (col,) in cols:
            # cardinality probe
            n = con.execute(
                f"SELECT COUNT(DISTINCT \"{col}\") FROM netops.\"{view_name}\""
            ).fetchone()[0]
            if n > 30:                # not categorical, skip
                continue
            con.execute(f"""
                INSERT INTO netops.value_profile (view_name, column_name, value, freq, fingerprint)
                SELECT '{view_name}', '{col}', "{col}",
                       COUNT(*),
                       array_to_string(
                           list_distinct(list_sort(
                               regexp_split_to_array(
                                   lower(regexp_replace(CAST("{col}" AS VARCHAR), '[^a-z0-9 ]', '', 'g')),
                                   '\\s+'))),
                           ' ') AS fingerprint
                FROM netops.\"{view_name}\"
                WHERE "{col}" IS NOT NULL
                GROUP BY "{col}"
            """)
    return {"value_profile_rows": con.execute("SELECT COUNT(*) FROM netops.value_profile").fetchone()[0]}
```

(The literal SQL with `f"`-string quoting is OK because view/col names come from `information_schema`, not user input.)

## 10. Open questions

1. **Cardinality threshold** for "categorical" — 30 is a guess.  Profile real fleets and adjust.
2. **Cluster algorithm** — fingerprint alone, or fingerprint + Levenshtein?  Phase B decides based on observed misses.
3. **Cross-view value sharing** — `state='Established'` appears in BGP and OSPF views.  Should they share a cluster_id?  Probably no (different concepts) — keep cluster scope per (view, column).
4. **Refresh granularity** — do we rebuild `value_profile` after every `take_snapshot` (current plan), or only at full `/netops_init`?  Current plan = rebuild always; cheap enough.
