# Memory-Driven Usage Guides

**Status**: Design proposal — Phase 1 ready to prototype
**Owner**: R84 (post-Chapter 4 architecture)
**Related**: dev_docs/60 (three-layer introspection cache), R83.4 follow-up
(diversifier + SaveAssertion)

## Problem

Every OLAV agent loads a static_context bundle at startup that's
inlined into the system prompt for every model call:

```
ops/AGENT.md → static_context: [
  references/DB_SCHEMA.md      (~500 lines)
  references/TOOL_PARTITIONING.md
  references/SERVICE_DEPLOYMENT.md
  references/OUTPUT_EXPORT_RULES.md
]
ops/analyze/SKILL.md → static_context: [
  references/SIMULATION_WORKFLOW.md  (~200 lines)
  references/TOPOLOGY_VIZ.md         (~150 lines)
  references/CAB_SPEC_FORMAT.md
  references/DRIFT_MODE.md
  references/ROUTING_EXPERT_GUIDE.md
  references/DESIGN_FEASIBILITY_CHECK.md
]
audit/auditor/SKILL.md → static_context: [
  references/PROFILE_AUTHORING.md
]
core/AGENT.md → static_context: [
  references/SKILL_DEVELOPMENT.md
]
```

Total ~2000 lines of reference text per system prompt, **regardless of
what the user asked**.

Symptoms in Chapter 4 verification:

* Long prompts dilute small-model attention — grok-4.1-fast ignored
  HARD RULE #0 (delegate to writer for save).
* Cross-agent reuse is broken: core can't see ops's
  `OUTPUT_EXPORT_RULES.md`; ops can't see core's
  `SKILL_DEVELOPMENT.md`.
* Per-call token cost is paid for every reference even when irrelevant
  (an "is BGP up?" query loads `TOPOLOGY_VIZ.md`).
* Updating a reference requires a wheel release.

The R83.4 memory primer already proved a related pattern works:
schema/value knowledge moved from static `DB_SCHEMA.md` examples into
LanceDB `schema_knowledge` / `value_distribution` entries, retrieved
on-demand via `AutoRecallMiddleware`.  Q3 cross-platform tool calls
dropped from 17 to 3 because the agent gets exactly the schema rows
it needs, not the entire `DB_SCHEMA.md`.

This proposal extends the same pattern to **procedural references**:
"how do I do X?" guides like `TOPOLOGY_VIZ.md`, `SIMULATION_WORKFLOW.md`,
`OUTPUT_EXPORT_RULES.md`.  Source-of-truth stays as files (auditable,
git-tracked); memory becomes the runtime view.

## Architecture

```
┌──────────────────────────────────────────────────────────┐
│ source-of-truth: YAML files (git tracked)                │
│ .olav/workspace/<agent>/guides/                          │
│   topology_viz.guide.yaml                                │
│   simulation_workflow.guide.yaml                         │
│   output_export_rules.guide.yaml                         │
│   ...                                                    │
└──────────────────────────────────────────────────────────┘
                          │
                          ↓ olav refresh / olav init / netops_init
┌──────────────────────────────────────────────────────────┐
│ prime_usage_guides()  (extends prime_memory_at_ingest)   │
│   for guide in glob(".olav/workspace/*/guides/*.yaml"):  │
│     for entry in guide.entries:                          │
│       store.add_memory(                                  │
│         id=f"guide_{agent}_{intent}",  # deterministic   │
│         category="usage_guide",                          │
│         text=entry.body,                                 │
│         tags=[intent, agent, *keywords],                 │
│         scope="global",                                  │
│         origin="config",                                 │
│         confidence=1.0,                                  │
│       )                                                  │
└──────────────────────────────────────────────────────────┘
                          │
                          ↓ each NL query
┌──────────────────────────────────────────────────────────┐
│ AutoRecallMiddleware._gather_candidates                  │
│   _CATEGORY_FETCH = {                                    │
│     "schema_knowledge": 6,                               │
│     "value_distribution": 6,                             │
│     "query_pattern": 3,                                  │
│     "usage_guide": 4,        ← NEW                       │
│   }                                                      │
│   ↓                                                      │
│   diversify → inject as <relevant-memories>              │
└──────────────────────────────────────────────────────────┘
```

### YAML schema (proposed)

```yaml
# .olav/workspace/ops/guides/topology_viz.guide.yaml
schema_version: 1
intent: topology_visualization
agent: ops
keywords:
  - topology
  - mermaid
  - diagram
  - graph
  - visualize
  - 拓扑
  - 网络图
body: |
  When user asks for network topology Mermaid diagram:

  1. Get latest data:
     SELECT * FROM netops.v_l2_links_auto;
     (latest snapshot is built into the view; no MAX(snapshot_id) needed)

  2. Build Mermaid graph TD with one node per device, one edge per
     link.  Annotate edges with interface names + protocol.

  3. Persist via writer subagent:
     olav_delegate("writer",
                   "report_type: topology_diagram\n<json data>")
     Writer auto-saves to exports/diagrams/.

  4. Cite the path that writer returned, verbatim.

  ⚠️ Do NOT inline Mermaid in chat without delegating to writer —
  the file won't exist on disk.  SaveAssertionMiddleware will warn,
  but native delegation is preferred.
related:
  - intent: simulation_what_if
    note: "for what-if questions, prefer ops-analyze with run_python_simulation"
```

### Why YAML, not Markdown

* Structured `keywords` field feeds directly into vector embedding tags
  → improves recall hit rate.
* Multiple guides per file (one entry per intent) keep related
  knowledge together.
* Schema version field allows iteration without breaking older installs.
* Body still supports Markdown formatting for the LLM to read.

## Implementation phases

### Phase 1 — additive prototype (1-2 days)

* Create `prime_usage_guides()` in `olav-netops/src/olav_netops/core/memory_primer.py`.
* Wire into `view_builder.finalise_ingest()` after `prime_memory_at_ingest`.
* Add 1 demo guide: `ops/guides/topology_viz.guide.yaml`.
* Extend `AutoRecallMiddleware._CATEGORY_FETCH` with
  `"usage_guide": 4`.
* **Keep all current static_context loads** — double-write phase.

**Validation**: Q1-Q4 + Chapter 4 topology — measure tool-call deltas.
If `topology` query drops from 12 → 8 (or similar), the new memory
entries are demonstrably helping.  If unchanged, recall isn't surfacing
the guide.

### Phase 2 — selective static→memory migration (1 week)

* Migrate non-critical references to YAML guides, one at a time:
  * `OUTPUT_EXPORT_RULES.md` (50 lines, table-shaped — easy)
  * `TOPOLOGY_VIZ.md` (150 lines, single-intent)
  * `DRIFT_MODE.md` (100 lines, single-intent)
* For each: write YAML guide → remove from static_context → run
  regression tests (Q1-Q4 + Chapter 4 + drift query).
* If any regression, revert that one migration; static fallback
  remains as the safety net.

### Phase 3 — slim base prompts (2-3 weeks)

* Migrate procedural references (`SIMULATION_WORKFLOW.md`,
  `CAB_SPEC_FORMAT.md`, etc.).
* Remove static_context entirely from agents that have full guide
  coverage.
* Goal: base prompt drops from ~5K tokens to ~1.5K; per-query
  `<relevant-memories>` adds ~1K of *just relevant* context.
* Cold-start guard: if `usage_guide` count is 0 (memory not yet
  primed), `_gather_candidates` falls back to loading the YAML files
  directly into the prompt.

## Trade-offs and risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Cold start (memory empty) | High | Phase 1 keeps static fallback; Phase 3 adds runtime fallback that reads YAML if `usage_guide` count is 0 |
| Recall misses (guide not surfaced) | Medium | R83.4 diversifier already provides per-category quotas; usage_guide reserves 4 slots like schema_knowledge |
| Source-of-truth drift | Medium | YAML is the only authoritative source; memory is derived.  Re-prime on `olav refresh`. Memory entries use deterministic ID for idempotent upsert |
| Cross-agent confusion | Low | `tags=[agent]` allows scope-filtered recall when agent identity matters; otherwise global recall lets any agent benefit from any guide |
| Maintenance asymmetry | Low | Single editing target (YAML).  No double-writes.  CI test asserts every guide YAML primes successfully |
| Prompt-fidelity assumption | Medium | Even with smaller prompts, LLM may ignore guide content. SaveAssertion + R1 reflection rules remain the safety net for behavior issues |

## Comparison to current state

| Dimension | Static context (today) | Memory-driven (Phase 3) |
|---|---|---|
| Default prompt size | ~5K tokens | ~1.5K tokens |
| Per-call relevant context | All loaded references | Top-4 relevant guides |
| Cross-agent reuse | None (per-agent isolation) | Global recall |
| Update flow | Edit file → wheel release | Edit YAML → `olav refresh` |
| Cold-start UX | Works (files always present) | Falls back to YAML reading |
| Auditability | High (git tracked .md) | High (git tracked YAML) |
| Cost per query | Fixed (large) | Variable (small base + relevant adds) |

## Open questions

1. **Trigger for re-prime**: every `olav refresh`, every
   `olav agent install <pkg>`, or auto on guide YAML mtime change?
2. **Granularity**: one guide per intent, or one guide per reference
   file (with multiple intents per guide)?
3. **Failure mode**: what does the agent do when a critical guide
   doesn't surface in recall (e.g. Mermaid query without TOPOLOGY_VIZ
   guide)?  Hard fail (warn user) vs soft fall back to YAML?
4. **Versioning**: when guide content materially changes (breaking),
   how do we invalidate cached query patterns that rely on the old
   content?

These resolve during Phase 1 prototype.

## LanceDB recall optimisation

Recall accuracy is the key risk for Phase 2/3.  Phase 1 will ship with
the current `hybrid_search` (vec + BM25 RRF fusion + post-filter +
diversifier) — already validated on `schema_knowledge` /
`value_distribution` for the R83.4 cross-platform Q3 fix.  But
`usage_guide` has a different shape than schema entries (longer body,
keyword-rich, intent-anchored), and we should harden recall before
betting Phase 2/3 on it.

### What LanceDB 0.30+ already gives us

| Feature | OLAV today | Notes |
|---|---|---|
| Vector search (HNSW) | ✅ used | `search_by_vector(query_vector, limit, category, scope)` |
| BM25 / FTS index on `text` | ✅ used | Created at table init via `create_fts_index("text", replace=True)` |
| Hybrid search (RRF fusion) | ✅ used | `hybrid_search()` over-fetches 2× then fuses |
| Tier-0 semantic cache | ✅ used | `SemanticCache` short-circuits ≥98% similar queries |
| Post-filter on `category`, `scope` | ✅ used | WHERE clauses applied after vector search |
| **FTS on `tags` column** | ❌ not built | Tags are stored as JSON string; not searchable via BM25 |
| **Scalar index on `category` / `scope`** | ❌ not built | `create_scalar_index` would speed up filter pre-pass |
| **Pre-filter (filter-then-search)** | ❌ post-filter only | Reduces ANN search space when filter is selective |
| **`with_row_id`-based reranking** | ❌ not used | Top-N candidates → LLM/cross-encoder rerank |
| **Multi-vector search** | ❌ not used | Could embed `intent`, `body`, `keywords` separately and weight |
| **Score thresholds** | ❌ not used | All top-K returned regardless of relevance |
| **FTS boolean / phrase queries** | ❌ basic | `query_type="fts"` uses default tokenizer; no AND/OR/`"phrase"` parsing |

### Target improvements (in priority order)

#### 1. **Tags FTS index** (highest leverage for usage_guide)

The `usage_guide.tags` array contains the most discriminative tokens —
intent name (`topology_visualization`), agent (`ops`), keywords
(`mermaid`, `diagram`, `拓扑`).  Right now `tags` is stored as a JSON
string and BM25 only indexes `text`.

Fix: at table init, also build FTS on `tags`:

```python
tbl.create_fts_index(["text", "tags"], replace=True)
# or build separately and search both
tbl.create_fts_index("tags", replace=True, name="tags_fts")
```

Or: store `tags` as a tokenised text field instead of JSON, so the
default `text` FTS picks them up.

**Expected impact**: a query "show topology mermaid" should hit the
guide whose tags include `topology` and `mermaid` with high BM25
score, even when the guide body doesn't mention those exact words.
Tag-keyword match → strong signal that vector embedding alone may
miss (especially for vendor jargon).

#### 2. **Score thresholds** (avoid noise injection)

Currently `_gather_candidates` returns top-K regardless of similarity.
If the top match has cosine distance 0.85 (very weak), injecting it
adds noise — the agent gets misleading "relevant" context that
doesn't actually match.

Fix: add a `min_score` parameter; drop candidates below it.

```python
# In _gather_candidates
results = store.search_by_vector(query_vector=vec, limit=n,
                                  category="usage_guide")
results = [r for r in results if r["_distance"] < 0.7]  # 0.7 = 30% similar
```

Threshold tuning: instrument 30+ real queries, plot
distance-of-top-hit, set threshold at the natural valley between
"hit" and "miss" populations.

#### 3. **Pre-filter via scalar index** (latency + recall)

`category="usage_guide"` filtering currently happens after vector ANN
finds the top-K * 2 candidates.  For a 2K-row memory table, the ANN
expands the search to ~16 candidates and then post-filters down to
maybe 4 of category usage_guide.

Better: build a **scalar index** on `category`, then **pre-filter**
during ANN traversal:

```python
# At table init
tbl.create_scalar_index("category", index_type="BTREE")

# At search time — LanceDB's "prefiltering" mode
results = (
    tbl.search(query_vector)
       .where("category = 'usage_guide'", prefilter=True)
       .limit(limit)
       .to_list()
)
```

Pre-filter narrows the search space first, so the ANN can return
exactly K matches from the right category — no padding needed.
Higher recall AND faster.

#### 4. **Re-ranking top-N** (precision boost)

Hybrid search returns top-K with RRF-fused scores.  RRF is
robust-but-blunt: it doesn't capture semantic specificity.

Fix: over-fetch top-20 from hybrid → re-rank with either:

* **Cross-encoder** (e.g. `ms-marco-MiniLM-L-6-v2`, ~80MB ONNX) —
  produces a query-doc relevance score per candidate, more accurate
  than dot product.  Adds ~50ms for 20 candidates on CPU.
* **LLM rerank** — small prompt asking "which 3 of these 20 best
  match the query?".  Higher quality but adds API call cost; only
  worth it for high-stakes queries.

For Phase 2 we'd only use cross-encoder when token budget tight;
default off, opt-in via config flag.

#### 5. **Multi-vector / aspect embeddings** (advanced)

A usage_guide has multiple "aspects":
* **intent name** ("topology_visualization") — short, exact
* **body** — long, narrative
* **keywords** — list

Embedding each as a separate vector and combining at query time gives
finer control:

```python
# Schema with multiple vector columns
schema = pa.schema([
    ("vector_intent", pa.list_(pa.float32(), 1536)),
    ("vector_body", pa.list_(pa.float32(), 1536)),
    ...
])
# At query time
intent_score = cosine(query_vec, vector_intent) * 1.5  # boost intent matches
body_score = cosine(query_vec, vector_body) * 1.0
combined = intent_score + body_score
```

Defer to Phase 3 — adds storage cost and requires schema migration.

#### 6. **FTS phrase / boolean queries** (nice-to-have)

LanceDB FTS supports phrase queries (`"exact phrase"`) and AND/OR
operators.  We currently pass raw user queries unmodified, which means
"show topology mermaid" becomes a bag-of-words match.  A targeted
query like `"topology" AND ("mermaid" OR "diagram")` would be more
precise — but requires NL→FTS query translation.  Probably not worth
it; vector search handles synonyms better.

### Recommended sequencing

| Phase | LanceDB enhancement | Effort | Recall impact |
|---|---|---|---|
| **Phase 1** | (none — use current hybrid_search) | 0 | baseline |
| **Phase 1.5** | Tags FTS index (#1) + score threshold (#2) | 0.5 day | +20-30% on guide queries |
| **Phase 2** | Scalar index + prefilter (#3) | 0.5 day | +10% recall, 2-5× faster |
| **Phase 3** | Cross-encoder rerank for top-N (#4) | 1-2 days (ONNX integration) | +15% precision, no recall loss |
| **Future** | Multi-vector (#5) | 3-5 days + migration | +10% on ambiguous intent matches |

### Measurement: how do we know recall improved?

Cannot trust LLM "felt better" — need quantitative signal.  Build a
golden test set during Phase 1:

```python
# tests/integration/test_guide_recall.py
GOLDEN = [
    ("show network topology mermaid", "topology_visualization"),
    ("simulate R3 losing all links", "simulation_what_if"),
    ("compare last two snapshots", "drift_detection"),
    ("save the diagram to exports/", "topology_visualization"),
    ...  # 30+ pairs
]

def test_top1_hit_rate():
    hits = 0
    for query, expected_intent in GOLDEN:
        results = recall.gather_candidates(query, ...)
        top_intents = [r.metadata["intent"] for r in results[:1]]
        if expected_intent in top_intents:
            hits += 1
    assert hits / len(GOLDEN) >= 0.9  # 90% top-1 hit rate
```

Run this after each LanceDB enhancement; promote to CI gate.

### Why not just use a bigger model?

Tempting answer: stop fighting recall, run gpt-4o or sonnet-4.6 with
all references inline; instruction-following is good enough.  Real,
but:

1. **Cost**: gpt-4o input tokens at scale is 10× grok-4.1-fast.  Most
   of the 5K base prompt is wasted on every query.
2. **Latency**: bigger prompts = bigger TTFT, especially through
   OpenRouter.
3. **Architectural drift**: even sonnet-4.6 benefits from focused
   prompts.  "Just use bigger model" is a config change, not an
   architecture improvement; doesn't help when next-gen models change
   prompt-handling characteristics.
4. **Long-term thinking**: small-model first remains OLAV's design
   stance (per `dev_docs/51 SMALL_MODEL_GOVERNANCE_ROADMAP.md`).
   Memory-driven recall serves all model tiers.

The recall investment is durable; the model upgrade isn't.

## Decision (updated)

**Phase 1 prototype** — just `prime_usage_guides()` + 1 demo guide +
quota in diversifier.  Use current hybrid_search.  Measure.

**Phase 1.5** — if Phase 1 looks promising but recall is shaky, add
tags FTS + score threshold (the two cheapest wins).

**Phase 2/3** — gated on Phase 1.5 demonstrating ≥85% top-3 hit rate
on golden set.

**No** big-bang rewrite.  Each step ships independently and is
measurable.

## Decision

**Recommended**: implement Phase 1 as a feasibility test.  ~1 day
work, low risk (purely additive), measurable signal (tool-call count
delta on Chapter 3+4).  Hold Phase 2/3 until Phase 1 demonstrates
positive recall hit rate.

If Phase 1 shows the diversifier surfaces guides reliably, Phase 2/3
unlock significant prompt reduction.  If recall is unreliable even
with quotas, the memory system has a deeper retrieval issue that
needs solving before further migration.
