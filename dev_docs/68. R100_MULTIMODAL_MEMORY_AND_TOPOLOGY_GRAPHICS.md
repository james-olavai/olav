## Why now

When user pulled `qwen3-vl-embedding-2b-q5_k_m.gguf` for embedding (replacing `nomic-embed-text-v2-moe`), the implicit motivation was: **OLAV generates topology diagrams (mermaid / SVG / PNG); we want users to be able to retrieve those diagrams by semantic similarity, including image-based search.**

But OLAV's `LanceDBStore.memory` schema currently has **only one content column (`text VARCHAR`)**. There is no `media_path`, no `content_kind`, no image blob support.  Even though the VL embedder *can* embed images, there is no place to store the source image alongside the embedding — vector goes in, "what was embedded" is lost.

Net effect today: VL embedder is doing pure text embedding work.  Its image capability is loaded into VRAM but unreachable.

This is a real but contained gap.  Topology is the most acute case (network engineers think in diagrams), but it generalizes to any visual artifact OLAV produces — diff visualizations, BGP convergence sparklines, audit-report charts, screenshots in user uploads.

---

## Goals

1. Allow OLAV memory to store image-typed entries (PNG / SVG / rendered mermaid / user-uploaded screenshots) with embeddings produced from the actual image content.
2. Allow AutoRecall to surface those entries to agents in a form the (likely text-only) LLM can use.
3. Stay incremental — no schema-shocking migration unless the use-case demands it.

Non-goals (out of R100 scope):
* Replacing the chat LLM with a multimodal one (deferred to R101+ if needed)
* Building an image generation tool (OLAV is a retrieval/analysis platform, not Stable Diffusion)
* OCR support (orthogonal — separate document-ingest concern)

---

## Three-tier design

### Tier 1 — text-anchored topology capture (cheap, ~30 LOC)

Most of OLAV's "graphics" output today is **mermaid source code** written by `format_and_export(format='mmd', ...)`.  Mermaid is text — it has structure (nodes, edges, attributes) — so a competent embedder picks up topology semantics directly from the source code.

```python
# Hook into format_and_export's mermaid output
async def capture_topology_artifact(
    *, mermaid_src: str, render_path: Path | None,
    snapshot_id: str, store: LanceDBStore,
) -> None:
    """Capture topology as memory; mermaid source IS the embedding signal."""
    text_for_embed = (
        f"Network topology diagram (mermaid format):\n"
        f"{mermaid_src}"
    )
    vec = await embed_text_async(text_for_embed)
    store.add_memory(
        id=f"topo_{snapshot_id}",
        text=text_for_embed,
        vector=vec,
        category="topology",
        scope="global",
        metadata={
            "media_path": str(render_path) if render_path else None,
            "format": "mermaid",
            "snapshot_id": snapshot_id,
        },
    )
```

* Schema unchanged
* AutoRecall unchanged (mermaid source as `text` is human-readable to the LLM)
* Future query "show me the DC1 topology" matches on mermaid structure
* If `media_path` points to a rendered SVG/PNG, agent can re-render or surface the path

**This covers ~95% of "topology graphics" use cases** because OLAV's own pipeline produces mermaid source as the canonical representation.  PNG/SVG are downstream renders.

### Tier 2 — true image memory (moderate, ~200 LOC + schema migration)

For use cases not covered by Tier 1: user-uploaded screenshots, third-party diagrams, raster-only artifacts.

Schema extension:
```sql
ALTER TABLE memory ADD COLUMN content_kind VARCHAR DEFAULT 'text';
                  -- enum: 'text' | 'image' | 'multimodal'
ALTER TABLE memory ADD COLUMN media_path  VARCHAR NULL;
                  -- relative path under .olav/blobs/ or exports/
ALTER TABLE memory ADD COLUMN media_thumb VARCHAR NULL;
                  -- optional 64×64 base64 PNG for web UI preview
```

Storage layout:
```
.olav/blobs/
├── sha256-<hex>.png        ← deduped by content hash
├── sha256-<hex>.svg
└── manifest.duckdb         ← optional: blob-id → memory-ids index
```

API changes:
```python
def add_memory(
    self, id: str, *,
    text: str = "",
    media: bytes | Path | None = None,
    content_kind: str = "text",  # 'text' | 'image' | 'multimodal'
    vector: list[float],
    ...
):
    if media is not None and content_kind in ("image", "multimodal"):
        # Hash + write blob, embed via VL endpoint
        blob_path = self._write_blob(media)
        # vector should already be the VL embedding of the image (or
        # multimodal pair) — caller is responsible for using the right
        # embedder
```

AutoRecall surfacing:
* For `content_kind='text'`: behaviour unchanged
* For `content_kind='image'`:
    * If LLM is multimodal → inject as `<image src='${media_path}' />` block in `<relevant-memories>`
    * If LLM is text-only → call `image_describer` tool to generate caption, inject caption + path

New tool:
```python
@tool
def image_describer(media_path: str) -> str:
    """Generate a short text description of an image via the VL model.
    Caption is cached by content hash so repeat retrievals are free."""
```

Workload estimate:
| component | LOC |
|---|---|
| `LanceDBStore.add_memory` multimodal dispatch | +60 |
| Schema migration (`alter_memory_add_media_columns`) | +40 |
| `AutoRecallMiddleware._format_relevant_memories` content-kind split | +40 |
| `image_describer` tool + caption cache | +50 |
| `format_and_export` PNG/SVG hook → embed + store | +20 |
| Tests | +80 |
| **Total** | **~290** |

### Tier 3 — end-to-end multimodal LLM (heavy, ~600 LOC + model swap)

If users want the agent to *reason about* image content (not just retrieve), the chat LLM itself must be multimodal.  This means:
* Replace `qwen3.6:27b` chat with `qwen3.6-VL-72B` or `GPT-4o-class` model
* AutoRecall injects images as multimodal payload (not text caption)
* Prompt token budget grows ~300 tokens per surfaced image (vision-encoder output)
* OLAV's tool-call pipeline + LangGraph nodes need to handle `content: list[dict]` vs `content: str`

Triggered only by a concrete user story like:
> "Here's a screenshot of an alert dashboard, find similar past incidents."

Defer until that story shows up.

---

## Recommendation

**Do Tier 1 now, defer Tier 2/3 until concrete user-driven need.**

Rationale:
1. OLAV's actual graphics pipeline (`format_and_export`) emits text-format mermaid as the canonical artifact. PNG/SVG are downstream renders, not the source of truth.
2. The VL embedder, fed mermaid source, performs as well as (probably better than) a pure-text embedder — it has seen "image-caption" pairs in training, including diagram captions.
3. Tier 2 is a 290-LOC change that buys image-blob storage but the LLM still can't *use* the image without Tier 3 or an `image_describer` caption pipeline. The caption pipeline ends up being "VL embedding to retrieve, then text caption to inject" — at which point Tier 1 (skip the image entirely, embed the text caption directly) is equivalent for less code.
4. If future user reports "I need to retrieve uploaded screenshots", that's the trigger for Tier 2.

## Risks / open questions

* **VL embedder correctness on text-only input** — assumed equal-or-better than pure-text embedder. Verify with an A/B benchmark on the demo7 corpus before committing.  If VL underperforms text on text inputs, Tier 1 is still useful but value drops.
* **Mermaid embedding quality** — VL models trained on (caption, image) pairs may not have strong representations for raw mermaid syntax.  An ablation: embed both `"DC1 has 4 routers in a hub-and-spoke"` (caption-style) and `graph LR\n  R1 --- ...` (raw source). Expect raw source to underperform caption.  Mitigation: prefix the embed text with a short caption before storing.
* **Schema migration risk (Tier 2 only)** — destructive `ALTER TABLE` on a populated `memory.lance` is fragile in LanceDB.  The R99/S1 dim-migration churn already drops rows on backend swap (see `ISSUE-CH8-DEMO-DIRECTIVE-VANISHES-ON-DIM-MIGRATION`).  Tier 2 must add `media_path` as a nullable column and never re-embed existing rows.

---

## Decision log

* **Tier 1 first** — leverages OLAV's text-format topology output (mermaid is the canonical source); zero schema risk; zero LLM compatibility risk; ~110 LOC delivers the 95% case.
* **Reject "VL embed PNG, store base64 in text"** — bloats text column, kills LanceDB perf, loses readability when AutoRecall surfaces it.
* **Reject "embed images, no schema change, lookup-only"** — produces orphan vectors with no way to surface the source image to agent or user.
* **Defer Tier 2** — until concrete user story (likely "search uploaded screenshots") arrives.
* **Defer Tier 3** — multimodal chat LLM is a 5-10× cost increase (per token) for a feature that helps a minority of OLAV use cases.  Wait for user demand.

---

## What this does NOT replace

* Existing memory categories (fact, decision, query_pattern, expert_knowledge, usage_guide, etc.) — Tier 1 just adds `topology` as a new category.
* `format_and_export` — same tool, gains a side-effect hook.
* AutoRecall middleware logic — unchanged (mermaid as text, surfacing as text).

R100 is purely a **memory-content-modality** extension, optionally followed by surfacing-format extensions if a Tier 2/3 use case materializes.
