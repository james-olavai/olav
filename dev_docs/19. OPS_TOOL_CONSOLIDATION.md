# 19. Ops Tool Consolidation — 统一工具布局

**Date:** 2026-04-06
**Status:** Design — Pending Implementation
**Scope:** `.olav/workspace/` 全部工具目录
**Driver:** analysis agent 精简 + 跨 workspace 工具调用已就绪

---

## 1. 问题

### 1.1 工具重复泛滥

当前 4 个工具存在多份物理拷贝（非 symlink），版本漂移风险高：

| 工具 | 物理拷贝数 | 位置 |
|------|-----------|------|
| `execute_cli.py` | 4 | ops, analysis, config, quick |
| `diff_configs.py` | 4 | ops, diff, config, quick |
| `search_commands.py` | 3 | ops, config, quick |
| `read_api_schema.py` | 2 | config/system, config/creator |

修改 `execute_cli.py` 的白名单逻辑需要同步 4 个文件——实际上从未同步过。

### 1.2 analysis agent 工具冗余

`ops/analysis` 持有 3 个工具，其中 2 个不应存在：

| 工具 | 问题 |
|------|------|
| `execute_cli` | analysis 声明 `network_isolation=True`，却持有设备访问工具——矛盾 |
| `topology` | DuckPGQ 图分析，被 sandbox 的 networkx 完全覆盖 |
| `run_python_simulation` | **唯一必要工具** — db + sim + nx + netutils 已覆盖全部分析需求 |

### 1.3 discovery 里的冗余 sandbox

`config/discovery/tools/run_topology_sandbox.py` 与 `analysis/tools/run_python_simulation.py` 功能重叠——都是 networkx 图分析 + Mermaid 导出。

## 2. 设计原则

1. **单一真相源（Single Source of Truth）** — 每个工具只有一份物理文件，其它位置一律 symlink
2. **按职责分层** — 工具归属于其"能力所有者"，不归属于"调用者"
3. **跨 workspace 调用** — 平台已支持 `olav_delegate()`，agent 不需要本地持有他人的工具
4. **最小工具集** — 每个 agent 只持有其核心能力所需的工具，通用工具通过 core 继承

---

## 3. 工具分层模型

```
Layer 0: core/tools/          ← 平台级（所有 agent 自动继承）
Layer 1: ops/tools/           ← NetOps 共享工具（canonical source）
Layer 2: ops/<subagent>/tools/ ← subagent 专属工具（不可替代的）
```

### Layer 0 — 平台工具（core/tools/）

所有 agent 通过 `_build_subagents()` 自动注入，无需 symlink。

```

format_and_export    — 数据导出
recall_memory        — 长期记忆
run_python_code      — 纯计算沙箱
run_shell            — Shell 命令
web_search           — 网络搜索
search_knowledge_lancedb — KB 搜索
deploy_service       — 服务部署
stop_service         — 服务停止
write_workspace_file — 文件写入
```

**不变。**

### Layer 1 — NetOps 共享工具（ops/tools/）

这些工具的**唯一物理文件**存放在 `ops/tools/`，所有需要的 workspace 通过 symlink 引用。

| 工具 | 能力 | 当前物理拷贝 → 改为 |
|------|------|---------------------|

## 4. analysis agent 精简

### Before（3 工具）

```yaml
tools:
  - execute_cli              # 矛盾：network_isolation=True 却访问设备
  - run_python_simulation    # 核心能力
  - topology                 # 冗余：被 sandbox networkx 覆盖
```

### After（1 工具）

```yaml
tools:
  - run_python_simulation    # db + sim + nx + netutils = 全部分析能力
```

**删除理由：**

| 工具 | 理由 |
|------|------|
| `execute_cli` | analysis 是纯计算 agent（`network_isolation=True`）。需要实时数据时 → orchestrator 委托 probe → 结果入 DB → analysis 查 DB |
| `topology` | DuckPGQ 图分析的全部能力（shortest_path, cycle_detection, connectivity）在 sandbox 内用 networkx 均可实现，且更灵活（支持 mutation + 加权） |

**analysis agent 角色定义变为：**

> 纯计算分析引擎。只读生产 DB，在内存中模拟变更，用 networkx 做图分析。
> 不访问实时设备，不调用外部 API。需要新鲜数据时告知 orchestrator。

## 11. 风险与回退

| 风险 | 缓解 |
|------|------|
| symlink 在 Windows/WSL 下行为不同 | 开发环境为 Linux，不影响 |
| analysis 删除 execute_cli 后丢失实时验证能力 | orchestrator 委托 probe → 结果入 DB → analysis 查 DB |
| analysis 删除 topology 后丢失 DuckPGQ 能力 | sandbox networkx 覆盖全部图分析；DuckPGQ 仍可通过 execute_sql (core) 访问 |
| quick agent 行为变化 | symlink 指向同一代码，行为完全一致 |
