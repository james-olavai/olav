# OLAV Agent Architecture Audit

**Date:** 2026-05-20 (rev 281 state)  
**Scope:** All workspace agents, sub-agents, and tool files under `.olav/workspace/`  
**Trigger:** post-`core/remote` deletion + `docker_compose` migration; full structural review  
**Rev 280 delta:** core/admin dissolved — tools inlined into admin/ops (6 tools) and admin/developer (9 tools); wrapper pattern removed; manage_service merges deploy+stop; workspace_health removed.  
**Rev 281 delta:** `execute_cli` retired; `execute_cli_parallel` upgraded to full replacement (5 new safety layers: check_approval gate, environment per-device filter, full/compact output, upgraded docstring ≤17 lines). Both workspace copies (root + olav-netops) updated; collector copies byte-identical to canonical.

## 1. Executive Summary

Five top-level agents, 22 sub-agents (SKILLs), and ~84 tool `.py` files constitute the current OLAV workspace runtime. The system is functionally sound and the core delegation pattern is consistent. Four categories of architectural debt are documented:

1. ~~**Stale reference (P1)** — `core/SKILL.md` still documents a `remote` sub-agent.~~ **✅ RESOLVED rev 279.**
2. ~~**Orphaned sub-agent (P2)** — `core/admin/` was not wired in `core/AGENT.md`.~~ **✅ RESOLVED rev 280:** Dissolved — 11 tools redistributed to `admin/ops/` (6 tools incl. new `manage_service`) and `admin/developer/` (9 tools); wrapper pattern removed.
3. **Tool duplication (P2)** — remaining duplicates: `execute_cli_parallel` (2 copies), `describe_table` (3 copies), `query_evidence` (2 copies), `api_request` (2 copies), `deploy_service`/`stop_service` (still in devops/services). Rev 280 eliminated 6 duplicates from core/admin layer.
4. **ADR drift (P3)** — ADR-0004 declares "exactly four top-level agents"; `admin` was added as a fifth without a superseding ADR. Three additional documentation gaps.

## 6. Calling Flow Architecture

### 6.1 Default invocation — core routes directly

```
User: olav "show BGP neighbors for R1"
  ↓
CLI → agent "core" (default)
  ↓
core/AGENT.md → OLAVAgent.__init__()
  ├─ _build_subagents()         compile writer, db_query, api_query runnables
  ├─ create_deep_agent()        LangGraph factory; deepagents middleware injected
  ├─ _prune_deepagents_tools()  strip auto-injected FS tools (glob, grep, ls…)
  └─ _apply_custom_middleware() TodoListMiddleware / SubAgentMiddleware
  ↓
core/prompts/system.md (routing heuristics):
  "BGP neighbors" → execute_sql directly
  ↓
execute_sql("SELECT * FROM netops.v_show_ip_bgp_summary_auto
             WHERE device_name = 'R1'")
  ↓
DuckDB read-only → result → formatted response → user
```

### 6.2 Orchestrator delegation — audit

```
User: olav --agent audit "run bgp_health profile"
  ↓
CLI → agent "audit"; task_return_direct: true
  ↓
audit/prompts/orchestrator.md:
  intent "run profile" → task("audit-runner", "run bgp_health")
  ↓
audit/runner sub-agent:
  1. run_map_engine(profile, window="24h", output_dir)
       → each Job's SQL executed against DuckDB
       → findings JSON written
  2. render_report(json_path, profile_path, output_dir)
       → per-Job LLM render + global correlation pass
       → Markdown written to exports/reports/
  → returns "Report saved: …" + Markdown preview
  ↓
orchestrator (task_return_direct=true):
  receives runner result → forwards verbatim → exits
  (no second LLM pass; no double-summary)
```

### 6.3 Multi-level delegation — netops analyzer → simulator

```
User: olav --agent netops "what happens to BGP if we change AS on R1?"
  ↓
netops orchestrator (thinking_mode: enabled)
  → reasoning: change plan + BGP config analysis = analyzer task
  → task("analyzer", "draft change plan + validate BGP AS change")
  ↓
netops/analyzer (thinking_mode: enabled):
  1. execute_sql() → current BGP config
  2. decides Batfish validation needed
  3. task("simulator", "evaluate BGP AS change")
  ↓
netops/simulator (thinking_mode: disabled, temperature: 0.0):
  1. batfish_capability() → check what Batfish can answer
  2. batfish_q(question="bgpSessionStatus") → Batfish HTTP API
  3. format_and_export(format='md') → saves simulation result
  → returns to analyzer
  ↓
analyzer:
  synthesises change plan from SQL + simulation results
  format_and_export(format='md', subdir='exports/change_plans/')
  → returns to netops orchestrator → user
```

## 7. Cross-Cutting Architecture Patterns

### 7.1 Orchestrator pattern (pure delegation)

`admin`, `audit`, `devops`, `netops` all share the same structural pattern:
- System prompt is `prompts/orchestrator.md` (not `system.md`)
- Direct tools: only `recall_memory` (+ `web_search` for audit/devops/netops)
- All work delegated via `task("<subagent-name>", "<request>")` — deepagents task tool
- `task_return_direct: true` on admin/audit prevents double-summarisation

`core` is the only exception: it has its own `prompts/system.md` and executes tools directly, without always delegating.

### 7.2 Thinking mode strategy

| Enabled | Sub-agent | Reason |
|---|---|---|
| ✅ | netops orchestrator (root) | Complex routing across 7 sub-agents |
| ✅ | netops/analyzer | Multi-step change plan / investigation synthesis |
| ✅ | netops/importer | Fuzzy format detection (rancid vs. bundle vs. vendor dump) |
| ✅ | admin/developer | Self-modification reasoning (scaffold, install, audit) |
| ✅ | audit/explorer | Open-ended autonomous investigation |
| ❌ | simulator, collector, learner, runner, db_query, api_query | Deterministic / low-complexity tool selection; temperature 0.0 for sim/learner |
| ❌ | netops orchestrator (olav-netops) | gemma4:31b full-stack tuning — see dev_docs/77 |

### 7.3 Workspace duality — root vs. olav-netops

The netops workspace exists in two locations, mirrored:
- `/home/yhvh/Olav/.olav/workspace/netops/` — root platform workspace
- `/home/yhvh/Olav/olav-netops/.olav/workspace/netops/` — extension package workspace

Key intentional difference: `thinking_mode` on `netops/AGENT.md` is `enabled` in root and `disabled` in olav-netops. All sub-agent SKILLs and tool files are expected to be identical. File drift between the two copies is a maintenance risk — no automated sync mechanism exists.

### 7.4 Explorer cross-domain data access

`audit/explorer` is the only sub-agent registered under one domain (`audit`) that reads data from another (`netops.*`). This works because both domains share `domain.duckdb`. The access grant is declared via `allowed_tables` in SKILL.md:

```yaml
# audit/explorer/SKILL.md
allowed_tables:
  - netops.devices
  - netops.topology_links
  - netops.parsed_outputs
  - netops.raw_output_store
  - netops.commands
  - netops.v_show_logging_auto
  - ...
```

Pattern is structurally sound. It sets a precedent requiring policy (FINDING-08).

### 7.5 Runtime tool wiring (how @tool reaches the agent)

```
Agent compile time:

1. workspace_discovery.py scans SKILL.md → finds tools: [list]
2. For each tool name, resolves file in <agent>/tools/<name>.py (or shared pool)
3. Loads @tool decorated function via importlib
4. Registers into LangChain tool list passed to create_deep_agent()
5. deepagents compiles LangGraph state machine with tool nodes

deepagents auto-injected FS tools (glob, grep, ls, read_file, write_file,
edit_file, execute, write_todos) are pruned post-compile via
_prune_deepagents_tools() — these are framework internals, not OLAV tools.
```

### FINDING-04 — ADR-0004 declares 4 top-level agents; 5 now exist
**Severity:** P3 (documentation gap)

### FINDING-06 — netops/learner: 4 helper tool files not declared in SKILL.md
**Severity:** P3 (convention violation)  
**Path:** `.olav/workspace/netops/learner/tools/`  
**Detail:** SKILL.md declares `learn_commands` and `cmd_learn`. The `tools/` directory also contains `analyze_structure.py`, `draft_parser.py`, `freeze_parser.py`, `validate_parser.py`.
