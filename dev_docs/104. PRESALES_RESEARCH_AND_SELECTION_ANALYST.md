# PRESALES Research & Selection — the `analyst` sub-agent

**Status**: Proposal (pre-implementation)
**Date**: 2026-07-22
**Builds on**: [100. PRESALES_DOMAIN_DESIGN](100.%20PRESALES_DOMAIN_DESIGN.md)
(which builds on [98. ARCHITECT_AGENT_HLD_LLD_DESIGN](98.%20ARCHITECT_AGENT_HLD_LLD_DESIGN.md))

Doc 100 designed presales as *ingest → design (HLD/LLD) → deliverables*, but it
**assumed the requirements and the technical approach were already decided**:
`surveyor` extracts structured facts, `architect` drafts HLD chapters that
*state* decisions ("spine-leaf, eBGP") without a comparative justification, and
`engineer` computes the LLD from those decisions. The single largest presales
activity is missing: the **research + selection** that produces those decisions
in the first place — technology selection, device/product selection, and
requirement analysis of a customer/tender document. This document adds that
phase as a fifth (and final) presales sub-agent, `analyst`.

This is a **scope expansion** of doc 100; doc 100 stays authoritative for the
ingest/storage/design/deliverable layers. This doc changes nothing in those; it
adds a pre-design research phase and one sub-agent.

Decisions locked before writing (2026-07-22, with the user):
- The research role is a **fifth sub-agent** (`analyst`), not folded into
  surveyor/architect — filling the last per-domain sub-agent slot (≤5).
- **`web_search` is deferred** — this phase does catalog-based selection and
  analysis of *already-ingested* documents only. The tender/datasheet web
  channel is a later increment (§8, §12).
- Role name: **`analyst`** (house-style occupational noun; distinct from the
  netops `analyzer` change-plan agent).

---

## 1. Scope and positioning

### 1.1 What the analyst does

Between `surveyor` (raw extraction) and `architect` (HLD authoring), the
`analyst` performs the **comparative research + decision** work:

| Task | Input | Output |
|---|---|---|
| **Requirement analysis** | ingested customer/tender docs + `presales.requirements` | a normalised requirement matrix + compliance gaps (for tenders) |
| **Technology selection** | requirements + design-pattern guides | a scored **approach comparison** (spine-leaf vs 3-tier; eBGP vs OSPF; SD-WAN vs MPLS) with rationale, tied to requirements |
| **Device/product selection** | requirements + product-catalog content pack | a scored **candidate matrix** (throughput / ports / features / role) with alternatives + rationale, feeding `generate_bom` |
| **Selection report** | the above | a human-readable, git-committed report for HITL review |

The analyst answers *"which approach and which boxes, and why"* — the input to
`architect`'s HLD, not the HLD itself.

### 1.2 Non-goals (this phase)

- **No `web_search`** — no fetching tenders/datasheets from the internet yet.
  Works over ingested documents (surveyor's Docling output) + the local
  catalog. Web is §8/§12.
- **No pricing/quoting** — same boundary as `generate_bom` (§100 §5.3):
  materials + selection, not commercial quoting.
- **No design authoring** — the analyst decides; `architect` writes the HLD.

### 1.3 The tender workflow (a first-class case)

"上网找招标文件→分析需求→做技术和设备选型" splits cleanly across existing +
new pieces, with the web step deferred:

```
(future: web fetch tender)                      ← §8, deferred
   ↓
surveyor.convert_documents  (Docling ingest the tender PDF)   ← exists (§100 §2.2)
   ↓
analyst.analyze_tender      (tender text → requirement matrix + compliance gaps)
   ↓
analyst.compare_approaches + select_devices  (tech + device selection)
   ↓
analyst.generate_selection_report  → [HITL] → design_decisions
   ↓
architect  (HLD citing the approved selections)
```

Until the web channel lands, the user drops the tender file into the project
`input/` and surveyor ingests it — the rest is unchanged.

## 2. Where it sits: flow + design-run lifecycle

```
surveyor (ingest, incl. tender)
   → analyst (analyse reqs → compare approaches → select devices → report)
        → [HITL: approve → design_decisions / reject → revise]
   → architect (HLD, cites approved selections)
   → engineer (LLD + networkx/Batfish validation)
   → publisher (dossier, BOM, docx/PDF)
```

The analyst runs **before** `architect.create_design_run`. Its approved
selections are recorded against the **project** (not a specific run), so any
subsequent HLD run consumes them. Concretely: `design_runs.phase` is unchanged;
the analyst writes `presales.design_decisions` with `status='confirmed'` +
`source_type='selection'`, which `architect`'s Phase-1 `inspect_requirements` /
Phase-3 `query_project_docs` already surface. No new lifecycle state is required;
if a `research` phase label proves useful later it can be added to `design_runs`
without migration.

## 3. Inputs

- **Requirements matrix** — `presales.requirements` (+ `requirement_dimensions.yaml`
  taxonomy, §100 §3.2), reused as-is.
- **Ingested documents** — surveyor's `extracted/*.md` (+ §2.6 LanceDB chunks),
  recalled via `query_project_docs`. Tenders included.
- **Product-catalog content pack** — the device universe the analyst selects
  *from* (model → attributes: role, throughput, port count/speeds, features,
  vendor, part number). Grounding source: the analyst never invents a SKU.
- **Design-pattern guide library** — approach-selection heuristics
  (`*.guide.yaml`, AutoRecall) — when spine-leaf vs 3-tier, eBGP vs OSPF, etc.

The catalog + pattern library are **content**, not mechanism — see §9.

## 4. The selection mechanism — deterministic fat tools over content packs

**Load-bearing constraint**: comparative selection over many options is exactly
the open-ended reasoning where small/medium models loop (the gemma4 deliberation
trap; V2 §M3). So selection is **deterministic scoring driven by a content
pack**, not free-form LLM reasoning. The LLM's job is to route, to set the
requirement filters, and to narrate the already-scored matrix — never to
enumerate/compare options in prose.

Proposed scripts (all self-contained, deterministic cores; flat args — the
`plan_fabric`/`generate_lld` call-construction lesson from the LLD e2e):

- **`analyze_tender`** — tender/requirements markdown → normalised requirement
  matrix mapped onto `requirement_dimensions.yaml` + a compliance list
  (met / partial / missing). Deterministic mapping + LLM only for free-text
  dimension extraction (Tier-2-style), gated by the review step.
- **`compare_approaches`** — requirements + a design-pattern guide → a scored
  approach matrix (options × criteria → weighted score + rationale rows).
  Python scores; the guide supplies the criteria/weights.
- **`select_devices`** — requirements (role, throughput, ports, features) +
  product catalog → filtered, scored candidate matrix per role, with alternates.
  Mirrors `generate_bom` (§100 §5.3) but selection-forward; flags roles with no
  catalog match (never fabricates). **Applies the region-aware vendor
  eligibility policy (§8.2) first**: candidates excluded by the project's
  jurisdiction (regulatory ban or no channel/support) are dropped from scoring
  but **surfaced with the reason** — never silently — so the compliance
  reasoning is auditable in the report.
- **`generate_selection_report`** — **self-authoring + self-writing** (the
  netops `generate_change_plan` / presales `generate_lld` pattern, dev_docs/98
  §4.3): Python assembles the full report (requirement summary, approach
  comparison, device matrix, compliance, open questions) and **writes the file**
  → returns the path. The LLM does not author the doc or call
  `format_and_export` (the LLD-e2e hallucination point we already fixed).

The deterministic-core + `@tool`/script split follows the CLAUDE.md tool
architecture: scripts under `analyst/scripts/`, logic in `olav_presales.core.*`.

## 5. The HITL loop — approve → knowledge base → HLD / reject → revise

This is the user's proposed loop, realised by **reusing existing machinery** (no
new subsystem):

1. **Report** — `generate_selection_report` writes `wiki/selection_report.md`
   (or `output/`) — a projection like the dossier (§100 §5.1), marker-blocked.
2. **Approve** → the analyst persists each accepted selection with
   `record_design(kind="decision", decision=…, rationale=…, source_type="selection",
   source_ref=<evidence_id>)` and the supporting excerpts with
   `record_design(kind="evidence", …)`. These become **recallable knowledge**:
   `architect`'s `inspect_requirements` sees the confirmed dimensions and its
   `query_project_docs` (§100 §2.6) recalls the rationale/evidence when drafting
   chapters. That is exactly "认可就加入知识库写 HLD".
3. **Reject / feedback** → the user's objections become `record_design(kind=
   "question", …)` entries in `questions_backlog`; the analyst re-runs
   `compare_approaches` / `select_devices` with the added constraints and
   regenerates the report. Iterate until approved. That is "不认可就给它提需求
   再改" — the same Plan-Act-Reflect loop the architect uses per chapter.

So the analyst introduces **no new storage or recall path** — it feeds the
design-decision / evidence / questions tables and the §2.6 recall that
`architect` already consumes.

## 6. Storage

- **Selections + rationale** → `presales.design_decisions`
  (`source_type='selection'`), reusing the existing table. No schema change.
- **Supporting excerpts** → `presales.design_evidence` (+ §2.6 LanceDB chunks).
- **Product catalog** → a content pack, NOT operational data. Options:
  (a) `references/device_catalog.yaml` (guide-adjacent, git-tracked,
  curator-reviewable — preferred for the open baseline), or (b) a
  `presales.device_catalog` table if it grows large / needs SQL joins. Start
  with (a); promote to (b) only if a real catalog outgrows YAML. The BOM
  part-number map (`bom_part_numbers.yaml`, already shipped) is the seam this
  catalog extends.
- **Compliance matrix** (tender) → derived at report time from
  `presales.requirements.status`; no new table.
- **Project jurisdiction** → `presales.projects` gains a `region` / `country`
  attribute (e.g. `US`, `AU`, `CN`, `EU`). It drives the vendor eligibility
  policy (§8.2). A single scalar on the project is enough for the common case;
  a per-segment override can live as a requirement dimension later. This is the
  one small schema add this phase (nullable column, no migration risk).

### 6.1 Config vs content — where each artifact lives (OLAV convention)

Three distinct artifact kinds, three homes — do **not** conflate them:

| Artifact | Kind | Home | Why |
|---|---|---|---|
| trusted-source allowlist; vendor eligibility policy (blocklist) | **deployment policy** (org/environment-specific, user-tunable) | `.olav/config/presales.yaml` (+ a shipped `presales.yaml.example`) | Same home as `vision_model` already uses; siblings `approval_rules.yaml` / `services.yaml`. Read directly by the tools; **NOT** AutoRecall-injected. |
| product catalog | **shipped content** (baseline open, extended commercially) | `references/device_catalog.yaml` (or a `presales.device_catalog` table if it outgrows YAML) | Data `select_devices` scores over; ships in the wheel skillpack. |
| design-pattern selection heuristics | **AutoRecall steering** | `references/design_pattern_selection.guide.yaml` | Injected into `compare_approaches` reasoning via `dynamic_context`. |

The allowlist/blocklist are **hard rules the deterministic tools read**, not
guidance to inject on every LLM call — putting them in `dynamic_context` would
burn context budget and misclassify policy as steering. They belong in
`.olav/config/presales.yaml`, following the existing `vision_model` precedent,
with a `.example` template so a fresh install has sane, editable defaults.

## 7. Agent structure

`analyst` is presales sub-agent **5 of 5** (surveyor / analyst / architect /
engineer / publisher). This **fills the per-domain sub-agent ceiling** (≤5,
ADR-0003/0005/0006); ADR-0004's top-level agent set is unaffected (still one
`presales` top-level agent). Any future presales capability must extend an
existing sub-agent or restructure — a deliberate constraint.

```yaml
# analyst/SKILL.md (sketch)
name: analyst
tools:                       # ≤5; NO web_search this phase
  - execute_skill_script
  - olav_recall_memory       # recall requirements + prior evidence
  - read_file                # read extracted/*.md (tenders, customer docs)
  - format_and_export        # (report is self-written by the script; this is fallback)
scripts:                     # ≤5, name-form, execute_skill_script recipe injected
  - analyze_tender
  - compare_approaches
  - select_devices
  - generate_selection_report
  - record_design            # (identical copy — reuse the architect writer)
dynamic_context:
  - references/design_pattern_selection.guide.yaml   # steering (AutoRecall)
  # device_catalog.yaml is read by select_devices directly — NOT dynamic_context
  # allowlist/blocklist live in .olav/config/presales.yaml — read by the tools
metadata:
  deterministic_synthesis_grader: true
```

Orchestrator routing gains one row:

| User intent | Route |
|---|---|
| "选型 / 技术方案 / 设备选型 / 分析这份招标文件 / research the options" | `task("analyst", req)` |

`architect`'s dispatch is unchanged; it now *finds* approved selections in the
decision/evidence tables rather than inventing them.

## 8. Trust, eligibility, confidentiality

Three separate guardrails, all read from `.olav/config/presales.yaml` (§6.1),
enforced by the deterministic tools — not prose:

### 8.1 Trusted-source allowlist (deferred web channel, §12) — NOT blind search

Device specs must be **authoritative and current**, so blind `web_search`
(blogs, forums, SEO spam, stale cached pages) is the wrong primitive. When the
web channel lands it is built on a curated **trusted-source allowlist**
(`.olav/config/presales.yaml` → `trusted_sources:`): official vendor domains +
datasheet/product-page URL patterns (cisco.com, arista.com, juniper.net,
huawei.com, arubanetworks.com, fortinet.com, paloaltonetworks.com, …). Rules,
enforced **structurally** (a guardrail, not prose):

1. **Allowlist-only network access** — a constrained fetch tool that *refuses*
   any non-allowlisted domain. Prefer **targeted fetch** of known official
   datasheet URLs over search; if search is needed, it is **site-scoped**
   (`site:<allowlisted-domain>`) so results never leave trusted domains.
2. **Catalog-first, web-fills-gaps, write-back** — the local
   `device_catalog.yaml` is the authoritative, HITL-vetted source. Web is only
   invoked for a role with **no catalog match**; the fetched spec is
   HITL-verified and then **written back to the catalog**, which becomes the
   accumulating trusted knowledge (not a per-query web dependency).
3. **Provenance + freshness** — every spec (catalog or web-sourced) carries
   `source_url` + `retrieved_date` + `confidence`. This makes "trustworthy +
   current" auditable; entries older than a freshness threshold are flagged
   `needs_reverify`. We do **not** claim "always latest" (vendors EOL/revise
   pages) — we claim authoritative source + dated provenance + a re-verify gate.
4. **Confidentiality (§4.5) still applies** — queries use **generic
   requirement terms only**, never customer-identifying strings (a query
   sanitiser). Access is a constrained `@tool` (network + allowlist state =
   the "process-external privilege" @tool criterion), not a script.

Until this lands, no outbound network access occurs; selection is catalog-only.

### 8.2 Vendor eligibility policy (blocklist) — region/jurisdiction-aware

A device can be *technically* the best fit and still be **ineligible** for the
deployment. Two independent reasons, both jurisdiction-dependent and
**bidirectional** (they cut both ways, not "Chinese vendors only"):

- **Regulatory ban** — e.g. the US (NDAA §889) and Australia (and other
  Five-Eyes / allied markets) bar Huawei / ZTE from many deployments. This is a
  **hard** exclusion.
- **No sales channel / support** — e.g. some Chinese products have no
  distribution or local support overseas; conversely some Western products are
  unavailable in certain markets. This is a **soft** exclusion (warn + allow
  override).

Design:

1. **Policy file** — `.olav/config/presales.yaml` → `vendor_policy:`, keyed by
   region → `{vendor, type: regulatory|no-channel|no-support|org-policy,
   reason, source_ref}`. Deployment/org-tunable; ships with a `.example`
   carrying well-known baseline bans.
2. **Project jurisdiction** — the project's `region` (§6) selects the applicable
   rules. `select_devices` filters the catalog against them **before** scoring.
3. **Explained, never silent** — excluded candidates appear in the selection
   report with `excluded: <reason>` (e.g. "Huawei — US NDAA §889"; "vendor X —
   no channel in AU"). The reviewer sees *what would have been chosen and why it
   was ruled out* — auditable compliance, the grounding discipline of §8.1.
4. **Hard vs soft** — `regulatory` cannot be overridden without an explicit,
   **recorded waiver** (`record_design(kind="decision", …, waiver=…)`) and even
   then may stay blocked by org policy; `no-channel`/`no-support` are warnings
   the user can override with a rationale.
5. **Gates the web allowlist too** — no point fetching a regulatorily-banned
   vendor's datasheets for that project; §8.1 fetch skips vendors ineligible
   under the project's jurisdiction. (Separate mechanisms, composed: trust of
   *source* vs eligibility of *vendor*.)

### 8.3 Grounding (recap)

`select_devices` chooses only from the catalog (never a fabricated SKU); roles
with no *eligible* match are flagged (like `generate_bom`'s `unmapped`).
Approach comparisons cite the pattern guide. The selection report is
HITL-reviewed before it becomes `design_decisions` (same gate as the extraction
HITL, §100 §2.5).

## 9. Content packs: open baseline vs commercial

Consistent with dev_docs/94 + §100 §1.3 ("mechanism open; curated content
commercial"):

- **Open (olav-presales)**: the analyst + its scripts (mechanism), the
  scoring/compare/select fat tools, the report generator, and a **baseline
  catalog + generic pattern guide** sufficient to run + demo (a small
  DC-switch catalog across 2-3 vendors; spine-leaf/campus/wan pattern
  heuristics).
- **Commercial (olav-ent / services)**: deep curated device catalogs with
  current SKUs/features, industry-specific tender-requirement taxonomies,
  vetted design-pattern libraries, **and current jurisdiction-specific vendor
  eligibility policy** (regulatory bans + channel/support maps by region) — a
  decade of selection experience, not copyable in a week. The open baseline
  ships only well-known bans (Huawei/ZTE in US/AU/Five-Eyes) as a `.example`;
  the accurate, current, per-market policy is the curated layer.

## 11. Governance

- **Sub-agent cap**: presales goes to 5/5 — update the per-domain cap assertion
  and note the ceiling is now full (a design constraint, not a target).
- **Reachability** (`test_subagent_reachability.py`): analyst declared by the
  orchestrator; its `execute_skill_script` recipe carries `skill_name="analyst"`.
- **DoD**: every module lands with an integration test through `execute_skill_script`;
  the report generator is self-writing (verified by asserting the file is written,
  not that the LLM claimed it — the LLD-e2e lesson).
- **Behavioural e2e** with `assert_success_rate(n≥3)` on a real model: selection
  determinism should make this reliable (the scoring is Python, not LLM).
- **Content boundary**: baseline catalog/guide ship open; no customer data in
  either. The `vendor_policy:`/`trusted_sources:` blocks ship as a
  `presales.yaml.example` (never a live `.olav/config/presales.yaml` in git —
  same rule as `api.json.example`).
- **Schema add**: `presales.projects.region` is a nullable column — verify it
  via `IngestManager` auto-`CREATE`/idempotency (the §100 step-1 table pattern),
  no destructive migration.

## 12. Open questions

1. **Web channel timing** — deferred now (§8). When added: query sanitiser +
   HITL spec verification are prerequisites, not options.
2. **Catalog store** — start `device_catalog.yaml` (content pack); promote to a
   `presales.device_catalog` table only if a real catalog needs SQL-scale joins.
3. **Same-customer reuse** — should approved selections/rationale be reusable
   across a customer's projects (with §4.5 project-dimension care)? Ties to
   §100 §10 Q3 (customer→projects grouping). Deferred.
4. **`analyst` vs `architect` boundary on "approach"** — the analyst picks the
   approach (spine-leaf/eBGP); the architect must not silently re-decide it in a
   chapter. Enforce via: architect grounds the "Logical Topology" chapter in the
   analyst's recorded decision (cite-or-question, never override).
5. **Eligibility policy currency** — the baseline `vendor_policy:` ships
   well-known bans, but regulatory lists + channel maps change. Same problem as
   §8.1 freshness: dated entries + a re-verify gate; the current per-market
   policy is the commercial layer (§9). Should a stale `vendor_policy` block the
   run or only warn? (Lean: warn + require HITL acknowledgement.)
6. **Region granularity** — a single `projects.region` scalar covers the common
   case; multi-region / per-segment deployments may need the region on the
   requirement or a project→sites split (ties to Q3). Deferred until a real
   multi-region project appears.
