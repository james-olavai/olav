## ISSUE-NO-SYNTHESIS

**状态**: Open  
**严重程度**: P1 — 功能预期未达成（agent 拿到数据但不输出自然语言回答）  
**发现时间**: 2026-05-30  
**影响章节**: CH3, CH4, CH5, CH6, CH8, CH12, CH13, CH14, CH15（共 15 个内容断言测试）

### 症状

`olav --agent <X> "<prompt>"` 执行后，终端输出只有工具调用回显：

```
  🔧[orch] execute_sql(SELECT device_name, platform...)
  🔧[orch] execute_sql(SELECT COUNT(*)...)
📁 execute_sql → [{"device_name": "R1", "platform": "cisco_ios"}, ...]
```

没有任何自然语言综合段落。用户看到的是原始 JSON 行，而非"根据查询结果，全网共有 XX 台设备…"。

### 根因（已确认）

**触发路径**：`src/olav/cli/main.py:1324` — `NL-CLI-SILENT-FINAL` fallback

```
LLM 发起工具调用
  → execute_sql 返回 JSON rows
  → LLM 应进入"综合答复"轮次 (ReAct 的最后一步)
  → gemma4 (小模型) 认为"工具跑完 = 任务完成"，不再发出 AIMessage
  → LangGraph 图退出，_chunks 为空
  → CLI fallback (main.py:1330): final_content 为空 → 将 tool_results 格式化为
    "📁 execute_sql → [...]" 行输出
  → 用户看到原始数据，没有综合
```

代码位置：`src/olav/cli/main.py:1324-1353`

```python
# NL-CLI-SILENT-FINAL (R82): some models (small ones especially)
# finish a run with only tool calls — they consider the work
# "delegated and done" and emit no final assistant text.
if not final_content and _tool_results:
    ...
    _fallback_lines.append(f"📁 {name} → {preview[:200]}")
```

**这个 fallback 解决了"CLI 完全无声"的问题，但没有解决"用户需要自然语言答复"的问题。**

### 受影响的测试

|---|---|---|

### 为什么 CH7 / CH9 不受影响

CH7（drift detection）和 CH9（migration plan）的内容断言无 `_is_no_synthesis` bypass，
且这两个 prompt 已被验证**总能触发 gemma4 的综合输出**：

- CH7 prompt 含明确的双时间戳对比指令 → 模型需要生成对比句子
- CH9 prompt 含"按建筑分组 / 每批最多5台"的约束 → 模型需要输出表格和批次数

这两个章节的 prompt 结构强制了模型的综合输出。其余章节的开放式 prompt（如"统计全网设备清单"）
更容易让小模型认为"工具结果即答案"而跳过最终答复轮次。

### 修复方向

**方案 A（推荐）— Forced synthesis 节点**

在 `_is_no_synthesis` 的路径上，CLI fallback 检测到 `final_content` 为空时，
追加一次 LLM 调用，传入工具结果并要求综合：

```python
# main.py NL-CLI-SILENT-FINAL 之后
if not final_content and _tool_results:
    synthesis_prompt = (
        "Based on the following tool results, provide a concise natural-language summary:\n"
        + json.dumps([tr["content"][:800] for tr in _tool_results[:3]])
    )
    synthesis_result = await llm.ainvoke([HumanMessage(content=synthesis_prompt)])
    final_content = synthesis_result.content
    console.print(final_content)
```

缺点：额外一次 LLM 调用，增加 latency（~5-10s）。

**方案 B — Prompt 工程**

在各 agent 的 `system.md` 末尾加强制综合指令：

```markdown
IMPORTANT: After completing all tool calls, you MUST write a natural-language
summary of your findings. Do NOT exit without a final text response.
```

缺点：对 gemma4 效果不稳定，已有类似指令但被忽略。

**方案 C（根本）— 换模型**

gemma4 的 "tool-done=task-done" 行为是小模型固有特征。
换用更大的模型（如 grok-4.1 / llama-3.3-70b）可从根本上消除此问题。
受 memory `feedback_pinned_llm_model.md` 约束：当前 LLM 锁定为 gemma4，
修复应走方案 A（architectural fix），而非切换模型。

### 修复实现

**2026-05-30** — `src/olav/cli/main.py:1329`（FORCED-SYNTHESIS 块）

在 `NL-CLI-SILENT-FINAL` 的现有 `📁` 原始数据 fallback 之前，
插入一次强制综合 LLM 调用：

```
检测到 final_content 为空 AND 存在 substantive tool results
  → 构造 synthesis prompt: "User asked X. Tool results: [JSON]. Summarize."
  → await agent.llm.ainvoke([HumanMessage(synthesis_prompt)])
  → 如果返回非空文字 → 输出到 console，作为 final_content
  → 如果 LLM 调用失败或返回空 → fall through 到原有 📁 fallback
```

不影响正常路径（agent 正常输出文字时，`final_content` 非空，完全不进入此块）。

**适用范围**：仅 `execute_sql` / `execute_skill_script` / `diff_configs` 等数据查询工具；
文件写入工具（`format_and_export` / `render_report` 等）已由 terminal-tool 路径处理，不触发此逻辑。

**测试行为变更**：
- 15 个 `_is_no_synthesis` bypass 从 `return`（静默通过）改为 `pytest.fail()`
- 修复生效后，这些测试不再进入 no_synthesis 路径，正常通过
- 修复未生效时（LLM 再次静默），测试 FAIL 并附上输出尾部，便于调试

## ISSUE-FORCED-SYNTHESIS-IS-PATCH

**状态**: ✅ Fixed (2026-06-01, v0.20) — 重构为两层 fallback（Tier 1: LLM synthesis call via `agent.llm.ainvoke`；Tier 2: raw path preview）；12 个 unit tests 覆盖候选过滤和 prompt 结构  
**严重程度**: P2 — 补丁掩盖根因，生产可靠性风险  
**发现时间**: 2026-05-30  
**影响范围**: 所有调用小模型（gemma4-31b）的 agent 章节

### 症状

ISSUE-NO-SYNTHESIS 的修复（`main.py:1329` FORCED-SYNTHESIS 块）是在 CLI 层事后注入一次额外 LLM 调用来补出综合文字。它解决了测试断言问题，但：

- 每次触发增加 **30-60s 额外延迟**（本地 gemma4 调用）
- 使用 `_synth_prompt` 传入的是截断后的工具结果（最多 1200 字符/工具），综合质量受限
- 根因（模型跳过最终 answer turn）完全未解决——每次查询都默默触发 fallback
- 如果 forced synthesis LLM 调用失败（网络抖动、模型加载中），用户仍然看到原始 `📁` 行

### 根因

gemma4-31b 在完成工具调用后认为"任务已完成"，不再发出 AIMessage。这是小模型的 ReAct 训练特征，不是 OLAV 代码 bug。补丁在 CLI 层感知到空 `final_content` 后才介入，已经脱离了图执行的正常流程。

### 修复方向

**方案 A（推荐）— LangGraph 层 synthesis 节点**

在图编译前加一个 `post_tool_synthesis` 条件边：若工具执行节点退出后 `final_content` 为空，则路由到专用 synthesis 节点而非直接到 END。

```
tool_executor → (has_output?) → agent  [正常路径]
             → (empty output?) → synthesis_node → END
```

优势：发生在图内，synthesis 节点拿到完整消息历史，质量更高；不需要在 CLI 里单独维护工具过滤逻辑（`_SILENT_DELEGATE` / `_WRITE_TOOLS`）。

**方案 B — 系统提示强制综合**

在 `core/prompts/system.md` 和各子 agent system prompt 末尾加约束块：

```
## OUTPUT CONTRACT
After all tool calls complete, you MUST write a prose summary paragraph.
Format: "Based on the query results, [findings]."
Exiting without a prose paragraph is a protocol violation.
```

风险：gemma4 已有类似指令但不稳定；prompt 工程对小模型效果难以保证。

**方案 C（辅助）— 测试侧 retry**

`_run()` 检测到 `_is_no_synthesis()` 后自动重跑一次（不同于 503 retry），给模型第二次机会。代价是测试时间翻倍。

**推荐路径**：先实现方案 B 观察稳定性，同时设计方案 A 作为长期架构修复。

## ISSUE-PLANNING-ONLY-ACCEPTANCE

**状态**: ✅ Fixed (2026-05-30)  
**严重程度**: P2 — 测试通过但功能未执行，误导性绿灯  
**发现时间**: 2026-05-30  
**影响章节**: CH3（主要）；多跳委派的其他章节潜在受影响

### 症状

在 fresh demo env 下，CH3 netops orchestrator 有时产生如下输出：

```
## SESSION INTENT
用户想统计全网设备清单...
## NEXT STEPS
1. 执行 SQL 查询，按厂商和平台统计设备数量
2. 向用户展示结果
```

然后超时。测试 `test_mentions_cisco` 因为更新了断言（接受 `"vendor" in out AND "## next steps" in out`）而 **PASS**。

但 **agent 实际上没有执行任何 SQL 查询**，用户得到的是规划文字而非真实数据。

### 根因

多跳委派链耗时叠加：

```
netops orchestrator（LLM call #1: ~45s）
  → olav_delegate 或 task → core agent（LLM call #2: ~45s）
    → execute_sql（SQL: ~2s）
    → core 综合（LLM call #3: ~45s）
  → netops 综合（LLM call #4: ~45s 或跳过）
```

总耗时 ~135-180s（正常），加上 forced synthesis ~200-240s。CH3 timeout=480s 应该足够，但在 LLM 服务器负载高时容易压线。

### 修复方向

**方案 A — 测试断言收紧**

要求 `execute_sql` 字符串出现在输出中（代表查询实际被调用），而非只检查规划关键词：

```python
def test_mentions_cisco(self):
    ...
    has_execution = "execute_sql" in out or "execute_skill_script" in out
    if not has_execution and "## next steps" in out_lower:
        pytest.skip("planning-only: agent understood but timed out before execution")
    assert "cisco" in out_lower
```

将规划文字场景从 PASS 改为 SKIP（带原因），而非硬通过。

**方案 B — 减少委派跳数**

给 netops orchestrator 直接配置 `execute_sql` 工具，让常见查询（设备清单、版本统计）无需二次委派给 core。

**方案 C — 强制 checkpoint**

在 netops orchestrator 的 system prompt 加约束：如果任务可以通过直接 SQL 完成，必须先调用工具再规划，而非先规划后委派。

## ISSUE-LOOSE-KEYWORD-ASSERTIONS

**状态**: ✅ Fixed (2026-05-30) — 新增 test_demo_data_integrity.py 作为 DB 完整性前置门控  
**严重程度**: P2 — 测试通过不等于功能正确，无法发现数据错误  
**发现时间**: 2026-05-30  
**影响章节**: CH3, CH4, CH5, CH6, CH7, CH8 等所有关键词断言章节

### 症状

当前测试断言形如：

```python
assert "cisco" in out.lower()
assert any(m in out_lower for m in ("3850", "c9300", "c9500", "ws-c"))
```

以下场景都能让断言通过，但都不代表功能正确：

- "cisco" 出现在规划文字的举例里（"例如 Cisco 设备..."）
- 型号字符串出现在错误消息里（"Table 'cisco.devices' not found"）
- 数量来自不相关的 COUNT 查询
- 合成文字重复了 prompt 中的关键词（LLM 回复 "如您所问，Cisco 设备的情况是..."）

### 根因

LLM 输出的非确定性导致断言设计偏向宽松。但当数据库是确定性的（静态快照），预期结果应该是精确可知的。

已知 fresh demo env 数据集的确定性事实：
- Cisco 设备：282 台
- Unknown 设备：58 台  
- C9300 系列：主力型号（具体数量需查 DB）
- AP 型号：AIR-AP3802I-Z-K9, C9130AXI-Z (440), CW9166I-Z (100)

### 修复方向

**方案 A — 数值范围断言**

对关键数量加范围检查（LLM 输出中通常包含完整数字）：

```python
import re
numbers = [int(n) for n in re.findall(r"\b(\d{2,})\b", out)]
# 应包含至少一个在 250-320 范围内的数（Cisco 设备总数 ~282）
assert any(250 <= n <= 320 for n in numbers), f"Cisco count expected ~282, found {numbers}"
```

**方案 B — DB 地面真值对照**

在测试 class setup 时直接查 DuckDB 取到期望值，然后在断言里对照：

```python
@classmethod
def setUpClass(cls):
    con = duckdb.connect(str(_DB), read_only=True)
    cls._expected_cisco = con.execute(
        "SELECT COUNT(*) FROM netops.parsed_outputs WHERE vendor='cisco'"
    ).fetchone()[0]
```

**方案 C（推荐）— 独立 DB 完整性测试**

新增 `test_demo_data_integrity.py`：完全不调用 LLM，直接查 DuckDB 验证期望的行数、型号、版本分布。这类测试运行快（<1s）、100% 确定性，且能独立于 E2E 测试运行。

## ISSUE-TIMEOUT-SENSITIVITY

**状态**: ✅ Fixed (2026-05-30) — 新增 OLAV_E2E_TIMEOUT_FACTOR 乘数，pytest timeout 同步缩放  
**严重程度**: P2 — 环境依赖，CI 中容易随机失败  
**发现时间**: 2026-05-30  
**影响章节**: CH3 (480s), CH4 (360s), CH8 (480s), CH11 (480s), CH13 (480s)

### 症状

E2E 测试超时值硬编码在各 `_run()` 调用中：

| 章节 | 超时 | 触发条件 |
|---|---|---|
| CH3 | 480s | 多跳委派 + 大结果集综合 |
| CH4 | 360s | AP 固件分布查询 |
| CH8 | 480s | 拓扑连通性分析（batfish/NetworkX） |
| CH11 | 480s | 变更计划文件写入 |

本轮在本机（gemma4 @ 192.168.100.12:11433）测试通过。但如果：

- LLM 服务器负载高（响应从 30s → 60s），480s 的章节从 2 次调用变为 0 个容错空间
- 网络抖动导致某次工具调用重试
- 新的 LLM 参数（temperature、上下文长度）影响响应速度

则同样的代码会产生随机失败，不代表功能退化。

### 根因

超时值是针对当前硬件（11433 端口的本地 LLM）在正常负载下实测出来的，没有余量系数，不能适应不同环境。

### 修复方向

**方案 A — 环境变量乘数**

```python
_TIMEOUT_FACTOR = float(os.environ.get("OLAV_E2E_TIMEOUT_FACTOR", "1.0"))

def _run(agent, prompt, timeout=180):
    effective_timeout = int(timeout * _TIMEOUT_FACTOR)
    ...
```

在慢机器上设 `OLAV_E2E_TIMEOUT_FACTOR=2`。

**方案 B — LLM benchmark 预热**

测试 session 开始时发一个简单 prompt，测量 p50 延迟，动态计算 `TIMEOUT_FACTOR`：

```python
@pytest.fixture(scope="session", autouse=True)
def calibrate_llm_latency():
    t = time.time()
    _run("core", "hello", timeout=30)
    latency = time.time() - t
    if latency > 15:  # baseline 5s; >15s = slow environment
        os.environ["OLAV_E2E_TIMEOUT_FACTOR"] = str(latency / 5)
```

**方案 C — 减少 LLM 调用次数**

根本上减少每章节需要的 LLM hop 数（见 ISSUE-PLANNING-ONLY-ACCEPTANCE 方案 B），使在相同超时内有更多完成空间。

## ISSUE-NO-DATA-ACCURACY-VALIDATION

**状态**: ✅ Fixed (2026-05-30) — 同 ISSUE-LOOSE-KEYWORD-ASSERTIONS，由 test_demo_data_integrity.py 覆盖  
**严重程度**: P3 — 覆盖范围缺口，不影响当前测试通过率  
**发现时间**: 2026-05-30  
**影响范围**: 整个 E2E 测试套件

### 症状

当前所有内容断言只验证关键词是否出现（见 ISSUE-LOOSE-KEYWORD-ASSERTIONS），没有一个测试验证：

- 查询返回的设备数是否与 DB 实际数据一致
- AP 型号分布比例是否正确
- 版本字符串是否来自真实设备而非 LLM 编造
- 变更计划文件是否包含真实设备名（而非 placeholder）

### 影响

如果 DuckDB 数据导入损坏（例如某次 ingest 写入了错误数据），E2E 测试仍然会通过（只要 LLM 能输出任意符合格式的文字）。

### 修复方向

**最高优先级**：新建 `tests/e2e/test_demo_data_integrity.py`

该测试文件不调用 LLM，仅：

1. 直接查询 fresh demo DuckDB
2. 验证关键统计量（设备数、型号、快照数）在期望范围内
3. 验证 `bundle_ingests.collected_at` 包含 5 个正确日期

```python
class TestDemoDataIntegrity:
    """验证 fresh demo DB 的数据完整性（无 LLM 调用）。"""
    
    def test_cisco_device_count(self):
        n = _con.execute("SELECT COUNT(*) FROM netops.parsed_outputs WHERE vendor='cisco'").fetchone()[0]
        assert 260 <= n <= 310, f"Expected ~282 Cisco devices, got {n}"
    
    def test_snapshot_count(self):
        n = len(_snaps)
        assert n >= 5, f"Expected ≥5 snapshots, got {n}"
    
    def test_bundle_dates(self):
        dates = {r[0] for r in _con.execute("SELECT DISTINCT collected_at FROM bundle_ingests").fetchall()}
        assert len(dates) >= 5, f"Expected 5 bundle dates, got {dates}"
```

这类测试运行 <1s，完全确定性，是 LLM E2E 测试的可靠前置门控。

## ISSUE-IN-PROCESS-AGENT-BYPASS-SERVER

**状态**: Open  
**严重程度**: P2 — 功能退化（audit 写入失败、资源竞争、双实例开销）  
**发现时间**: 2026-05-31  
**影响范围**: CLI 单查询、TUI overlay 模式、admin NL 任务、/config 斜杠命令

### 症状

当 OLAV API server（`uvicorn olav.api.app:app --port 2280`）已作为后台进程运行时，以下调用路径仍在 CLI 进程内直接实例化 `OLAVAgent`，而不是通过 HTTP 转发给 server：

```
WARNING: audit.duckdb unavailable (write) — audit disabled:
  Connection Error: Can't open a connection to same database file
  with a different configuration than existing connections
```

### 受影响的调用路径

| 路径 | 文件:行号 | 描述 | 优先级 |
|---|---|---|---|
| **CLI 单查询** | `cli/main.py:1129 run_single_query()` | `create_olav_agent_with_backend()` → `OLAVAgent()` → `astream_events()` | P1 |
| **TUI overlay 模式** | `cli/main.py:1023 run_interactive()` | overlay 模式直接传本地 graph 给 deepagents-cli TUI | P2 |
| **Admin NL 任务** | `cli/admin.py:72 admin_handler()` | 复杂 admin 任务 `create_olav_agent()` + `agent.invoke()` | P2 |
| **/config 斜杠命令** | `cli/commands/builtin.py:342 cmd_config()` | TUI 内缓存 agent 单例 + `agent.ainvoke()` | P3 |

**不受影响的路径**（有意在本地运行）：
- `cli/daemon.py`：daemon 本身就是独立后台进程，无冲突
- `server/graph_factory.py`：server 端 graph 工厂，正确路径

### 根因

`run_single_query` 没有"检测到 server 正在运行时转发给 server"的逻辑。所有路径直接调用 `create_olav_agent_with_backend()`，在 CLI 进程内启动完整 agent 实例。

共享 `audit.duckdb` 的冲突链：
1. CLI 进程内 `trace_learner` 后台任务（`asyncio.create_task`）以线程池并发打开 `audit.duckdb`
2. 同时 `audit_recorder` 尝试写入同一文件
3. DuckDB 1.5.1 拒绝同进程内 read_only / write 混合模式连接

**临时修复（已落地）**：`trace_learner._analyze_failures` 去掉 `read_only=True`，改为普通 write 连接，消除混合模式冲突。

### 正确修复方向

**`run_single_query` 加 server 探测逻辑：**

```python
async def run_single_query(query, assistant_id, ...):
    if await _api_server_is_available():          # probe GET /ok → 200
        return await _forward_to_api_server(query, assistant_id, ...)
    # 降级：本地 agent（server 未运行时的兜底）
    agent, backend = create_olav_agent_with_backend(assistant_id, ...)
    ...
```

实现要点：
1. `_api_server_is_available()`：向 `http://localhost:2280/ok` 发 HEAD/GET，超时 200ms，失败视为 server 未就绪
2. `_forward_to_api_server()`：用 `langgraph_sdk.get_sync_client()` 或 `httpx` 调用 `/threads/{thread_id}/runs/stream`，流式输出到 console
3. TUI overlay 模式：同样探测，有 server 则切换为 native 模式（强制走 subprocess server 路径）
4. Admin / `/config`：转为向 server 发请求，或直接废弃 in-process invoke

### 关联副作用

- **双倍初始化开销**：CLI 进程每次重建完整 graph（含 warmup、plugin registry、checkpointer），而 server 已缓存了相同的 graph——浪费 2–4s
- **audit 写入丢失**：CLI 进程的 audit 事件与 server 进程的 audit 事件可能相互干扰，导致 `audit.duckdb` 写入部分失败
- **双内存空间**：CLI 进程和 server 进程各有一套 LanceDB / expert_kb 内存实例，recall_memory 结果不一致

## ISSUE-HARNESS-PROMPT-CACHING-PROVIDER-BLIND

**状态**: ✅ Fixed (2026-06-01) — `should_use_prompt_caching()` 函数已实现并在注入点被调用；`test_prompt_caching_middleware_absent_for_non_anthropic` 覆盖  
**严重程度**: P1 — 无声 bug（middleware 注入逻辑与实际 provider 不匹配）  
**发现时间**: 2026-05-31  
**影响范围**: 所有 compiled sub-agents（`_build_subagents()` 路径）

### 症状

`AnthropicPromptCachingMiddleware` 被注入到**每一个** compiled sub-agent，即使当前 LLM provider 不是 Anthropic：

```python
# _deepagents_bridge.py
HAS_PROMPT_CACHING: bool = True  # 硬编码，不感知 provider

# agent.py _build_subagents()
if HAS_PROMPT_CACHING and AnthropicPromptCachingMiddleware is not None:
    _middleware.append(AnthropicPromptCachingMiddleware(unsupported_model_behavior="ignore"))
```

当前配置：`provider=custom`（OpenRouter / deepseek-v4-flash）。middleware 以 `"ignore"` 模式运行（不报错），但：

1. 每次 model 调用都走一遍 Anthropic 专属的 cache_control 注入逻辑，随后被静默丢弃
2. 若未来 deepagents 修改 `"ignore"` 语义，将无声地产生 prompt 污染（多余的 cache_control 标记发给非 Anthropic 后端）
3. 没有任何 governance test 防止此情形

### 根因

`HAS_PROMPT_CACHING` 的 gate 条件是"langchain_anthropic 包是否可导入"，而非"当前 LLM provider 是否为 Anthropic"。只要 `langchain_anthropic` 在环境中存在（deepagents 依赖链会带进来），flag 永远为 True。

### 修复方向

```python
# _deepagents_bridge.py
def _is_anthropic_provider() -> bool:
    try:
        from olav.core.config import get_llm_config
        return get_llm_config().provider in ("anthropic",)
    except Exception:
        return False

HAS_PROMPT_CACHING: bool = _is_anthropic_provider()
```

或者在 `_build_subagents()` 注入点加 provider guard：

```python
if HAS_PROMPT_CACHING and AnthropicPromptCachingMiddleware is not None:
    from olav.core.config import get_llm_config
    if get_llm_config().provider == "anthropic":
        _middleware.append(AnthropicPromptCachingMiddleware(unsupported_model_behavior="ignore"))
```

### Governance 补丁

新增测试：当 provider 非 Anthropic 时，`_middleware` 列表不包含 `AnthropicPromptCachingMiddleware` 实例。

## ISSUE-HARNESS-SUMMARIZATION-TRIGGER-MISCALIBRATED

**状态**: ✅ Fixed (2026-05-31) — `api.json context_budget=120000`，trigger 降至 96K，低于模型 128K 上限  
**严重程度**: P1 — SummarizationMiddleware 对当前模型实际上永远不触发  
**发现时间**: 2026-05-31  
**影响范围**: 长流程 agent（explorer、analyzer 长对话）

### 症状

```
tier=large → trigger=("tokens", 160000)
deepseek-v4-flash context window ≈ 128K tokens
config.context_budget = None（用户未设置，回退到 TIER_DEFAULTS）
```

Trigger 设在 160K，但 deepseek-v4-flash 在约 128K 处会开始报 context length exceeded 错误。SummarizationMiddleware **从未有机会触发**——模型先挂，压缩逻辑才有机会介入。

对于 explorer 这类长流程 sub-agent，长对话没有任何 token 压缩保护，迟早会命中模型 context 上限后失败。

### 根因

`compute_summarization_trigger()` 的计算链：

```
config.context_budget → None（未设置）
    ↓ 回退
TIER_DEFAULTS["large"]["context_budget"] = 200_000
    × summarization_trigger_pct = 0.8
    = 160_000 tokens  ← 超出 deepseek-v4-flash 实际上限
```

TIER_DEFAULTS 的 context_budget 是按"大模型通用"设定的，不感知具体部署的模型规格。

### 修复方向

**方案 A（推荐）— 在 `api.json` 中设置 `context_budget`：**

```json
"llm": {
    "model": "deepseek/deepseek-v4-flash",
    "context_budget": 120000
}
```

`compute_summarization_trigger` 优先读取此值（代码已支持），trigger 变为 `120000 × 0.8 = 96000`，在模型报错前能正常触发。

**方案 B — TIER_DEFAULTS 按模型系列分档：**

为 `deepseek-*` 模型系列在 TIER_DEFAULTS 中增加专项配置，但这需要维护更细粒度的 tier 映射。

**验证方式：**

```python
from olav.agents._deepagents_bridge import compute_summarization_trigger
from olav.core.config import get_llm_config
trigger = compute_summarization_trigger(get_llm_config().model_tier)
assert trigger[1] < 130_000, f"trigger {trigger} exceeds deepseek context window"
```

## ISSUE-HARNESS-SUBAGENT-PLUGIN-MIDDLEWARE-GAP

**状态**: Open  
**严重程度**: P2 — 架构盲区（sub-agent 层无 OLAV 安全/记忆中间件覆盖）  
**发现时间**: 2026-05-31  
**影响范围**: 所有 compiled sub-agents（analyzer、reporter、collector、explorer 等）

### 症状

通过 events 流对比，orchestrator 与 compiled sub-agent 的中间件栈存在显著差异：

**Orchestrator（netops）：**
```
guardrails.before_model      ← 拒绝有害请求
memory_recall.before_model   ← 注入长期记忆
safety.after_model           ← 安全扫描
save_assertion.after_agent   ← 幻觉检测（声称写文件但未实际写）
query_pattern_capture        ← SQL 模式学习
memory_capture               ← 提炼 insights 写入 long-term memory
```

**Compiled sub-agent（analyzer）：**
```
PatchToolCallsMiddleware      ← deepagents 内置
TodoListMiddleware            ← OLAV 手动注入
SummarizationMiddleware       ← OLAV 手动注入（见 ISSUE-SUMMARIZATION-TRIGGER）
```

**关键空缺：**

| 缺失中间件 | 实际后果 |
|---|---|
| `save_assertion` | sub-agent 幻觉（声称"Profile saved: X"但未写入磁盘）不被捕获，静默传给 orchestrator |
| `memory_capture` | explorer/analyzer 在深度调查中产生的洞察不进入长期 memory，下次运行从零开始 |
| `guardrails` | sub-agent 收到的注入式 tool result 不经安全过滤 |
| `memory_recall` | sub-agent 不能主动检索历史 memory（当前靠 recall_memory @tool 间接实现） |

### 设计权衡

此空缺是**有意的信任边界设计**（sub-agents 被视为 orchestrator 的可信组件），但缺乏显式文档，存在以下隐患：

- `save_assertion` 空缺：sub-agent 幻觉会"成功"传递给 orchestrator，orchestrator 的 `save_assertion` 无法二次拦截（它检测的是自身输出，不是 sub-agent 传来的 tool result）
- `memory_capture` 空缺：explorer 是当前最需要跨 session 积累洞察的 agent，但它的 memory 只能靠手动 `format_and_export` + 人工 recall 链路

### 修复方向

**近期（低成本）：**
- 在 explorer/analyzer 的 SKILL.md body（系统提示）里显式要求："发现重要洞察时，主动调用 `recall_memory` 存储"（依赖 LLM 自主行为，不可靠）
- 在 `_build_subagents()` 中对特定 sub-agent 类型（`category: autonomous-audit`）选择性注入 `memory_capture`

**中期（架构级）：**
- 在 compiled sub-agent 外层（task 工具返回后、orchestrator 处理前）加一个 sub-agent 结果审计节点，运行 `save_assertion` 逻辑

## ISSUE-HARNESS-DEEPAGENTS-INJECT-TOOL-PRUNE-FRAGILE

**状态**: Open  
**严重程度**: P2 — 防御机制脆弱（依赖静态白名单，upgrades 可能悄悄失效）  
**发现时间**: 2026-05-31  
**影响范围**: 所有 compiled sub-agents，deepagents 升级时

### 症状

```python
# agent.py
_DEEPAGENTS_INJECT_TOOLS = frozenset({
    "glob", "grep", "ls",
    "read_file", "write_file", "edit_file",
    "execute", "write_todos",
})
```

OLAV 使用 `_prune_graph_tools` + `_prune_model_node_bind_tools` 在 graph 编译**后**剪掉 deepagents 注入的 filesystem 工具。这是"先污染后清理"的补丁逻辑。

**脆弱点：**
1. deepagents 在某次升级中新增注入工具（如 `shell_exec`、`code_eval`）→ OLAV 的白名单未更新 → sub-agent 悄悄多出危险工具
2. `_DEEPAGENTS_INJECT_TOOLS` 是静态 frozenset，与 deepagents 版本无关联，升级时没有自动失效提示
3. 没有 governance test 验证"实际运行时 sub-agent 的工具集"，只测 SKILL.md 声明

### 对比正确的防御：

- `filesystem_middleware=False` 参数（已用于 orchestrator）是编译前的**白名单控制**，deepagents 内部不注入 FilesystemMiddleware → 干净
- 但 `SubAgentMiddleware` 注入的工具（`write_todos` 等）没有对应的 `subagent_middleware=False` 参数——因此才需要后置 prune

### 修复方向

**短期：** 在 deepagents 升级 checklist（`dev_docs/17. RELEASE_PLAN.md`）中加一条：执行 `_DEEPAGENTS_INJECT_TOOLS` 对账——列出当前版本实际注入的工具，与白名单比对。

**中期：** 新增 governance test，实际实例化一个 compiled sub-agent（mock LLM），断言其 bound tools 集合等于 SKILL.md 的 `tools:` 声明，不多也不少。

```python
def test_subagent_runtime_tools_match_skill_md(tmp_path, monkeypatch):
    # 实例化 analyzer sub-agent，检查 bound tools
    bound = {t.name for t in get_compiled_subagent_tools("analyzer")}
    declared = _parse_front_matter(ANALYZER_SKILL_MD)["tools"]
    assert bound == set(declared), f"runtime tool leak: {bound - set(declared)}"
```

## ISSUE-AGENT-SCRATCHPAD-NOT-WIRED

**状态**: ✅ Fixed (2026-05-31)  
**严重程度**: P1 — 架构断路（Plan-React 持久化层实现完整但从未接入任何 agent）  
**发现时间**: 2026-05-31  
**影响范围**: explorer sub-agent；Plan-React 工作流的跨步骤结构化持久化

### 症状

`audit/explorer` sub-agent 在 SKILL.md 描述中声称"writes findings incrementally"，但实际写入目标是 `format_and_export(mode="append")` 产生的 markdown 文件（`exports/reports/*.md`），而非 DuckDB。下一个 sub-agent 无法通过 SQL 查询这些发现，必须由 orchestrator 在上下文中携带，导致 orchestrator 上下文随任务链线性膨胀。

### 根因

`src/olav/core/explorer/scratchpad.py` 完整实现了结构化落盘机制：

```python
start_exploration(db_path, snapshot_id, ...) → run_id
    # 写入 netops.exploration_runs

record_finding(db_path, run_id, phase, severity, summary, evidence_sql, ...) → finding_id
    # 写入 netops.exploration_findings
    # 强制约束：evidence_sql 必填（防幻觉），severity/confidence 枚举验证，
    #           budget_findings 上限，同一 run_id 内 summary 不可重复

update_exploration_run(db_path, run_id, status, ...)
    # 更新运行状态、turns_used、final_report_path
```

但这三个函数**从未被注册为任何 agent 的 script**：

| 检查项 | 状态 |
|---|---|
| Python 实现 | ✅ 完整（scratchpad.py + 强约束） |
| DB 表（migration v0_23） | ✅ netops.exploration_findings / exploration_runs |
| `audit/explorer/scripts/` 包装脚本 | ❌ 不存在 |
| 任何 SKILL.md `scripts:` 注册 | ❌ 无 |
| 任何 agent prompt 中的调用指令 | ❌ 无 |

Explorer 当前的 `scripts/`：只有 `describe_table.py` 和 `query_evidence.py`（均只读）。

### 架构影响

Plan-React 模式在落盘环节断路：

```
正确路径（设计意图）:
  Step N: explorer 调查 → record_finding() → netops.exploration_findings
  Step N+1: analyzer 调用 execute_sql 查 exploration_findings → 基于结构化发现推进

实际路径（当前）:
  Step N: explorer 调查 → format_and_export(append) → exports/reports/*.md
  Step N+1: analyzer 无法读取该文件 → orchestrator 只能在上下文中带结果
            → orchestrator ctx 随任务链线性增长
```

对 64K 本地模型场景，这意味着即使每步子代理上下文独立且充裕，orchestrator 仍会在 3–5 步后被历史挤满。

### 修复方向

1. **创建包装脚本**（3 个文件）：
   - `audit/explorer/scripts/start_exploration.py` — 调用 `scratchpad.start_exploration()`
   - `audit/explorer/scripts/record_finding.py` — 调用 `scratchpad.record_finding()`
   - `audit/explorer/scripts/finish_exploration.py` — 调用 `scratchpad.update_exploration_run(status="completed")`

2. **更新 explorer SKILL.md**：
   - `scripts:` 中注册三个新脚本
   - Prompt 更新工作流：`start_exploration` → 调查循环（`execute_sql` + `record_finding`）→ `finish_exploration` → `format_and_export`（从 DB 查询发现后生成报告）

3. **讨论 analyzer/reporter 是否有写权限**：
   - 方案 A：explorer 是唯一写入点，analyzer 只读 `exploration_findings`
   - 方案 B：analyzer 也有 `record_finding`，用于记录变更分析结论

## ISSUE-ZERO-TOKEN-FALSE-POSITIVE

**状态**: ✅ Fixed (2026-05-31)  
**严重程度**: P2 — 每次工具调用触发 3 次不必要重试，增加约 4s 延迟  
**发现时间**: 2026-05-31  
**影响范围**: 所有通过 OpenRouter 调用 deepseek-v4-flash 的 agent

### 症状

日志中看到如下警告，但实际上工具调用成功执行：

```
WARNING  OpenRouter 0-token (attempt 1/3, msgs=4, llm_output={'token_usage': {'completion_tokens': 0, ...}}) — retrying
WARNING  OpenRouter 0-token (attempt 2/3, msgs=4) — retrying
WARNING  OpenRouter 0-token (attempt 3/3, msgs=4) — retrying
ERROR    OpenRouter returned 0-token after 3 retries (msgs=4) — giving up
```

"giving up" 之后 LangGraph 仍能正确执行工具调用。

### 根因

deepseek-v4-flash（和多数 DeepSeek 系列模型）对只含工具调用（无文字）的响应报告 `completion_tokens=0`，因为 tool call JSON 不计入 completion tokens。

`src/olav/core/llm.py` 的 `_is_zero_token()` 函数：

```python
def _is_zero_token(result) -> bool:
    comp = usage.get("completion_tokens")
    if comp != 0:
        return False
    # 检查 text 内容
    for gen in generations:
        if getattr(gen, "text", None):
            return False
        msg = getattr(gen, "message", None)
        if msg and getattr(msg, "content", None):
            return False
    return True   # ← 漏检了 tool_calls！
```

当响应含 `tool_calls` 但 `content=""` 时，该函数误返回 `True`（判定为空响应），触发不必要重试。

### 修复方向

在 `_is_zero_token` 检查中加入 `tool_calls` 判断：

```python
def _is_zero_token(result) -> bool:
    ...
    for gen in generations:
        msg = getattr(gen, "message", None)
        if msg:
            if getattr(msg, "content", None):
                return False
            # tool_calls 存在 = 有效响应，不算 0-token
            if getattr(msg, "tool_calls", None) or getattr(msg, "additional_kwargs", {}).get("tool_calls"):
                return False
    return True
```

### 修复

`src/olav/core/llm.py` `_is_zero_token()` 函数增加 `tool_calls` 检查（与 ISSUE-ASTREAM-NO-RETRY 同批落地 2026-05-31）：

```python
tc = getattr(msg, "tool_calls", None) or \
     (getattr(msg, "additional_kwargs", {}) or {}).get("tool_calls")
if tc:
    return False   # tool_calls 存在 = 有效响应，不算 0-token
```

### 影响

- 修复后：tool call 响应立即通过，无重试
- 日志噪声：大量误导性 WARNING/ERROR 被清除

## ISSUE-ASTREAM-NO-RETRY

**状态**: ✅ Fixed (2026-05-31)  
**严重程度**: P1 — 合成步骤失败时静默无输出，无重试保护  
**发现时间**: 2026-05-31  
**影响范围**: LangGraph server 模式下所有 OpenRouter 调用（langgraph dev / langgraph_api）

### 症状

合成步骤（tool execution 之后的最终 AI 回答）返回空，无任何 WARNING 日志：

```python
[3] ai: text='', tool_calls=[]   # 无日志，静默失败
```

同时 `_agenerate_with_seed` 的 3 次重试日志出现在工具调用之前（误报）。

### 根因

`src/olav/core/llm.py` OpenRouter monkey-patch 的两条执行路径不对称：

| 路径 | 触发条件 | 重试逻辑 |
|---|---|---|
| `_agenerate_with_seed` | 无 streaming callback handler | ✅ 3 次重试 + `user`/`seed` 注入 |
| `_astream_with_seed` | 有 streaming callback handler | ❌ 无重试，仅注入 seed |

LangGraph server（`langgraph dev`）为每次 run 安装 `_StreamingCallbackHandler`。`BaseChatModel._should_stream` 检测到此 handler 返回 True，路由至 `_astream` 路径。

合成步骤走 `_astream_with_seed`，返回空流时无重试、无日志，静默失败。

### 修复方向

为 `_astream_with_seed` 增加重试逻辑：

```python
async def _astream_with_seed(self, messages, stop=None, run_manager=None, **kwargs):
    for attempt in range(3):
        kwargs["seed"] = _random.randint(1, 2 ** 31)
        kwargs["user"] = f"olav-{_uuid.uuid4().hex[:12]}"
        chunks = []
        has_content = False
        async for chunk in _orig_astream(messages, stop=stop, run_manager=run_manager, **kwargs):
            chunks.append(chunk)
            if chunk.content or getattr(chunk, "tool_calls", None):
                has_content = True
        if has_content or attempt == 2:
            for c in chunks:
                yield c
            return
        logger.warning("OpenRouter _astream 0-content (attempt %d/3) — retrying", attempt + 1)
```

注意：streaming generator 的重试需要缓冲所有 chunks 再 re-yield，会牺牲流式输出的即时性。

### 修复

`src/olav/core/llm.py` `_astream_with_seed` 改为带 3 次重试的缓冲流式实现（2026-05-31）：

```python
async def _astream_with_seed(self, messages, stop=None, run_manager=None, **kwargs):
    for attempt in range(3):
        kwargs["seed"] = _random.randint(1, 2 ** 31)
        kwargs["user"] = f"olav-{_uuid.uuid4().hex[:12]}"
        chunks: list = []
        has_content = False
        async for chunk in _orig_astream(messages, stop=stop, run_manager=run_manager, **kwargs):
            chunks.append(chunk)
            if chunk.content or getattr(chunk, "tool_calls", None):
                has_content = True
        if has_content or attempt == 2:
            for c in chunks: yield c
            return
        logger.warning("OpenRouter _astream 0-content (attempt %d/3) — retrying", attempt + 1)
```

注意：streaming 路径缓冲所有 chunk 后再 yield，会牺牲即时性但保证合成完整。

### 关联

- 与 ISSUE-ZERO-TOKEN-FALSE-POSITIVE 共同导致用户看到空输出
- 两个修复同批于 2026-05-31 落地

## ISSUE-DEEPAGENTS-UPGRADE-EVAL

**状态**: Open（架构决策，待 P2 验证）

| `ContextHubBackend` | ❌ | ✅ | Git 式版本化 memory，跨 session 持久化 |

### OLAV 复杂流程逐一评估

#### 1. Explorer 多层调查（L1-L4 + 写文件）

**当前问题**：靠 SKILL.md 文字规则约束 agent 行为，fragile。`read_file` 每层写前读一次磁盘，4 层 = 4 次额外 round-trip。

**0.6.0 CodeInterpreterMiddleware**：LLM 写 QuickJS 代码批量执行 `read_file + check + format_and_export`，结果留在 JS runtime，单次 LLM 调用完成。减少 4 次 → 0 次磁盘读往返。

**0.6.5 RubricMiddleware**：预定义 rubric = "报告包含 L1/L2/L3/L4/Summary 各节且无重复 header"，agent 完成后自评，未达标自动重试（max_iterations=2），替代所有 Rule 7 文字约束。

#### 2. Orchestrator 上下文膨胀（ISSUE-ORCHESTRATOR-CONTEXT-BLOAT）

**当前**：SummarizationMiddleware 在 96K token 触发压缩，但 explorer 长调查还是会线性增长 orchestrator 上下文。

**0.6.0 DeltaChannel**：checkpoint 只存 diff，200 turn 会话从 5.27 GB → 129 MB。对 explorer 这类长 session 有显著内存节省，但不直接解决上下文 token 问题。

**正确解法**（架构级）：explorer 调查结果落到 `netops.exploration_findings`（scratchpad，已修复），orchestrator 只看 SQL 查询结果，不在上下文携带完整报告文本。deepagents 升级不直接改变这一数据流设计。

#### 3. Memory 跨 session 积累（ISSUE-HARNESS-SUBAGENT-PLUGIN-MIDDLEWARE-GAP）

**当前**：explorer 的调查洞察靠 `format_and_export` 写 markdown，不进入 LanceDB long-term memory，下次运行从零开始。

**0.6.6 ContextHubBackend + state_schema**：explorer 可在 session 结束时将发现写入 `/memories/` 目录（ContextHub Git 历史），下次 session 的 `MemoryRecallPlugin` 自动检索。不需要手动 recall_memory 调用链。

**替代方案（当前版本即可）**：在 `_build_subagents()` 对 `category: network-autonomous-audit` 的 agent 选择性注入 `memory_capture` OLAV middleware。

#### 4. Sub-agent 工具泄漏防护（ISSUE-HARNESS-DEEPAGENTS-INJECT-TOOL-PRUNE-FRAGILE）

**当前**：静态 `_DEEPAGENTS_INJECT_TOOLS` frozenset，deepagents 新版注入新工具时 OLAV 无法感知。

**0.6.7 `DeepAgentState` 公开导出**：可在 governance test 中直接断言 sub-agent 实际 bound tools，不再依赖对比名称白名单。
