## ISSUE-NO-SYNTHESIS

**状态**: Open  
**严重程度**: P1 — 功能预期未达成（agent 拿到数据但不输出自然语言回答）  
**发现时间**: 2026-05-30  
**影响章节**: CH3, CH4, CH5, CH6, CH8, CH12, CH13, CH14, CH15（共 15 个内容断言测试）

### 症状

`olav --agent <X> "<prompt>"` 执行后，终端输出只有工具调用回显：

```
  🔧[orch] execute_sql(SELECT device_name, platform...)
  🔧[orch] execute_sql(SELECT COUNT(*)...)
📁 execute_sql → [{"device_name": "R1", "platform": "cisco_ios"}, ...]
```

没有任何自然语言综合段落。用户看到的是原始 JSON 行，而非"根据查询结果，全网共有 XX 台设备…"。

### 根因（已确认）

**触发路径**：`src/olav/cli/main.py:1324` — `NL-CLI-SILENT-FINAL` fallback

```
LLM 发起工具调用
  → execute_sql 返回 JSON rows
  → LLM 应进入"综合答复"轮次 (ReAct 的最后一步)
  → gemma4 (小模型) 认为"工具跑完 = 任务完成"，不再发出 AIMessage
  → LangGraph 图退出，_chunks 为空
  → CLI fallback (main.py:1330): final_content 为空 → 将 tool_results 格式化为
    "📁 execute_sql → [...]" 行输出
  → 用户看到原始数据，没有综合
```

代码位置：`src/olav/cli/main.py:1324-1353`

```python
# NL-CLI-SILENT-FINAL (R82): some models (small ones especially)
# finish a run with only tool calls — they consider the work
# "delegated and done" and emit no final assistant text.
if not final_content and _tool_results:
    ...
    _fallback_lines.append(f"📁 {name} → {preview[:200]}")
```

**这个 fallback 解决了"CLI 完全无声"的问题，但没有解决"用户需要自然语言答复"的问题。**

### 受影响的测试

|---|---|---|

### 为什么 CH7 / CH9 不受影响

CH7（drift detection）和 CH9（migration plan）的内容断言无 `_is_no_synthesis` bypass，
且这两个 prompt 已被验证**总能触发 gemma4 的综合输出**：

- CH7 prompt 含明确的双时间戳对比指令 → 模型需要生成对比句子
- CH9 prompt 含"按建筑分组 / 每批最多5台"的约束 → 模型需要输出表格和批次数

这两个章节的 prompt 结构强制了模型的综合输出。其余章节的开放式 prompt（如"统计全网设备清单"）
更容易让小模型认为"工具结果即答案"而跳过最终答复轮次。

### 修复方向

**方案 A（推荐）— Forced synthesis 节点**

在 `_is_no_synthesis` 的路径上，CLI fallback 检测到 `final_content` 为空时，
追加一次 LLM 调用，传入工具结果并要求综合：

```python
# main.py NL-CLI-SILENT-FINAL 之后
if not final_content and _tool_results:
    synthesis_prompt = (
        "Based on the following tool results, provide a concise natural-language summary:\n"
        + json.dumps([tr["content"][:800] for tr in _tool_results[:3]])
    )
    synthesis_result = await llm.ainvoke([HumanMessage(content=synthesis_prompt)])
    final_content = synthesis_result.content
    console.print(final_content)
```

缺点：额外一次 LLM 调用，增加 latency（~5-10s）。

**方案 B — Prompt 工程**

在各 agent 的 `system.md` 末尾加强制综合指令：

```markdown
IMPORTANT: After completing all tool calls, you MUST write a natural-language
summary of your findings. Do NOT exit without a final text response.
```

缺点：对 gemma4 效果不稳定，已有类似指令但被忽略。

**方案 C（根本）— 换模型**

gemma4 的 "tool-done=task-done" 行为是小模型固有特征。
换用更大的模型（如 grok-4.1 / llama-3.3-70b）可从根本上消除此问题。
受 memory `feedback_pinned_llm_model.md` 约束：当前 LLM 锁定为 gemma4，
修复应走方案 A（architectural fix），而非切换模型。

### 修复实现

**2026-05-30** — `src/olav/cli/main.py:1329`（FORCED-SYNTHESIS 块）

在 `NL-CLI-SILENT-FINAL` 的现有 `📁` 原始数据 fallback 之前，
插入一次强制综合 LLM 调用：

```
检测到 final_content 为空 AND 存在 substantive tool results
  → 构造 synthesis prompt: "User asked X. Tool results: [JSON]. Summarize."
  → await agent.llm.ainvoke([HumanMessage(synthesis_prompt)])
  → 如果返回非空文字 → 输出到 console，作为 final_content
  → 如果 LLM 调用失败或返回空 → fall through 到原有 📁 fallback
```

不影响正常路径（agent 正常输出文字时，`final_content` 非空，完全不进入此块）。

**适用范围**：仅 `execute_sql` / `execute_skill_script` / `diff_configs` 等数据查询工具；
文件写入工具（`format_and_export` / `render_report` 等）已由 terminal-tool 路径处理，不触发此逻辑。

**测试行为变更**：
- 15 个 `_is_no_synthesis` bypass 从 `return`（静默通过）改为 `pytest.fail()`
- 修复生效后，这些测试不再进入 no_synthesis 路径，正常通过
- 修复未生效时（LLM 再次静默），测试 FAIL 并附上输出尾部，便于调试

## ISSUE-FORCED-SYNTHESIS-IS-PATCH

**状态**: Open  
**严重程度**: P2 — 补丁掩盖根因，生产可靠性风险  
**发现时间**: 2026-05-30  
**影响范围**: 所有调用小模型（gemma4-31b）的 agent 章节

### 症状

ISSUE-NO-SYNTHESIS 的修复（`main.py:1329` FORCED-SYNTHESIS 块）是在 CLI 层事后注入一次额外 LLM 调用来补出综合文字。它解决了测试断言问题，但：

- 每次触发增加 **30-60s 额外延迟**（本地 gemma4 调用）
- 使用 `_synth_prompt` 传入的是截断后的工具结果（最多 1200 字符/工具），综合质量受限
- 根因（模型跳过最终 answer turn）完全未解决——每次查询都默默触发 fallback
- 如果 forced synthesis LLM 调用失败（网络抖动、模型加载中），用户仍然看到原始 `📁` 行

### 根因

gemma4-31b 在完成工具调用后认为"任务已完成"，不再发出 AIMessage。这是小模型的 ReAct 训练特征，不是 OLAV 代码 bug。补丁在 CLI 层感知到空 `final_content` 后才介入，已经脱离了图执行的正常流程。

### 修复方向

**方案 A（推荐）— LangGraph 层 synthesis 节点**

在图编译前加一个 `post_tool_synthesis` 条件边：若工具执行节点退出后 `final_content` 为空，则路由到专用 synthesis 节点而非直接到 END。

```
tool_executor → (has_output?) → agent  [正常路径]
             → (empty output?) → synthesis_node → END
```

优势：发生在图内，synthesis 节点拿到完整消息历史，质量更高；不需要在 CLI 里单独维护工具过滤逻辑（`_SILENT_DELEGATE` / `_WRITE_TOOLS`）。

**方案 B — 系统提示强制综合**

在 `core/prompts/system.md` 和各子 agent system prompt 末尾加约束块：

```
## OUTPUT CONTRACT
After all tool calls complete, you MUST write a prose summary paragraph.
Format: "Based on the query results, [findings]."
Exiting without a prose paragraph is a protocol violation.
```

风险：gemma4 已有类似指令但不稳定；prompt 工程对小模型效果难以保证。

**方案 C（辅助）— 测试侧 retry**

`_run()` 检测到 `_is_no_synthesis()` 后自动重跑一次（不同于 503 retry），给模型第二次机会。代价是测试时间翻倍。

**推荐路径**：先实现方案 B 观察稳定性，同时设计方案 A 作为长期架构修复。

## ISSUE-PLANNING-ONLY-ACCEPTANCE

**状态**: ✅ Fixed (2026-05-30)  
**严重程度**: P2 — 测试通过但功能未执行，误导性绿灯  
**发现时间**: 2026-05-30  
**影响章节**: CH3（主要）；多跳委派的其他章节潜在受影响

### 症状

在 fresh demo env 下，CH3 netops orchestrator 有时产生如下输出：

```
## SESSION INTENT
用户想统计全网设备清单...
## NEXT STEPS
1. 执行 SQL 查询，按厂商和平台统计设备数量
2. 向用户展示结果
```

然后超时。测试 `test_mentions_cisco` 因为更新了断言（接受 `"vendor" in out AND "## next steps" in out`）而 **PASS**。

但 **agent 实际上没有执行任何 SQL 查询**，用户得到的是规划文字而非真实数据。

### 根因

多跳委派链耗时叠加：

```
netops orchestrator（LLM call #1: ~45s）
  → olav_delegate 或 task → core agent（LLM call #2: ~45s）
    → execute_sql（SQL: ~2s）
    → core 综合（LLM call #3: ~45s）
  → netops 综合（LLM call #4: ~45s 或跳过）
```

总耗时 ~135-180s（正常），加上 forced synthesis ~200-240s。CH3 timeout=480s 应该足够，但在 LLM 服务器负载高时容易压线。

### 修复方向

**方案 A — 测试断言收紧**

要求 `execute_sql` 字符串出现在输出中（代表查询实际被调用），而非只检查规划关键词：

```python
def test_mentions_cisco(self):
    ...
    has_execution = "execute_sql" in out or "execute_skill_script" in out
    if not has_execution and "## next steps" in out_lower:
        pytest.skip("planning-only: agent understood but timed out before execution")
    assert "cisco" in out_lower
```

将规划文字场景从 PASS 改为 SKIP（带原因），而非硬通过。

**方案 B — 减少委派跳数**

给 netops orchestrator 直接配置 `execute_sql` 工具，让常见查询（设备清单、版本统计）无需二次委派给 core。

**方案 C — 强制 checkpoint**

在 netops orchestrator 的 system prompt 加约束：如果任务可以通过直接 SQL 完成，必须先调用工具再规划，而非先规划后委派。

## ISSUE-LOOSE-KEYWORD-ASSERTIONS

**状态**: Open  
**严重程度**: P2 — 测试通过不等于功能正确，无法发现数据错误  
**发现时间**: 2026-05-30  
**影响章节**: CH3, CH4, CH5, CH6, CH7, CH8 等所有关键词断言章节

### 症状

当前测试断言形如：

```python
assert "cisco" in out.lower()
assert any(m in out_lower for m in ("3850", "c9300", "c9500", "ws-c"))
```

以下场景都能让断言通过，但都不代表功能正确：

- "cisco" 出现在规划文字的举例里（"例如 Cisco 设备..."）
- 型号字符串出现在错误消息里（"Table 'cisco.devices' not found"）
- 数量来自不相关的 COUNT 查询
- 合成文字重复了 prompt 中的关键词（LLM 回复 "如您所问，Cisco 设备的情况是..."）

### 根因

LLM 输出的非确定性导致断言设计偏向宽松。但当数据库是确定性的（静态快照），预期结果应该是精确可知的。

已知 fresh demo env 数据集的确定性事实：
- Cisco 设备：282 台
- Unknown 设备：58 台  
- C9300 系列：主力型号（具体数量需查 DB）
- AP 型号：AIR-AP3802I-Z-K9, C9130AXI-Z (440), CW9166I-Z (100)

### 修复方向

**方案 A — 数值范围断言**

对关键数量加范围检查（LLM 输出中通常包含完整数字）：

```python
import re
numbers = [int(n) for n in re.findall(r"\b(\d{2,})\b", out)]
# 应包含至少一个在 250-320 范围内的数（Cisco 设备总数 ~282）
assert any(250 <= n <= 320 for n in numbers), f"Cisco count expected ~282, found {numbers}"
```

**方案 B — DB 地面真值对照**

在测试 class setup 时直接查 DuckDB 取到期望值，然后在断言里对照：

```python
@classmethod
def setUpClass(cls):
    con = duckdb.connect(str(_DB), read_only=True)
    cls._expected_cisco = con.execute(
        "SELECT COUNT(*) FROM netops.parsed_outputs WHERE vendor='cisco'"
    ).fetchone()[0]
```

**方案 C（推荐）— 独立 DB 完整性测试**

新增 `test_demo_data_integrity.py`：完全不调用 LLM，直接查 DuckDB 验证期望的行数、型号、版本分布。这类测试运行快（<1s）、100% 确定性，且能独立于 E2E 测试运行。

## ISSUE-TIMEOUT-SENSITIVITY

**状态**: Open  
**严重程度**: P2 — 环境依赖，CI 中容易随机失败  
**发现时间**: 2026-05-30  
**影响章节**: CH3 (480s), CH4 (360s), CH8 (480s), CH11 (480s), CH13 (480s)

### 症状

E2E 测试超时值硬编码在各 `_run()` 调用中：

| 章节 | 超时 | 触发条件 |
|---|---|---|
| CH3 | 480s | 多跳委派 + 大结果集综合 |
| CH4 | 360s | AP 固件分布查询 |
| CH8 | 480s | 拓扑连通性分析（batfish/NetworkX） |
| CH11 | 480s | 变更计划文件写入 |

本轮在本机（gemma4 @ 192.168.100.12:11433）测试通过。但如果：

- LLM 服务器负载高（响应从 30s → 60s），480s 的章节从 2 次调用变为 0 个容错空间
- 网络抖动导致某次工具调用重试
- 新的 LLM 参数（temperature、上下文长度）影响响应速度

则同样的代码会产生随机失败，不代表功能退化。

### 根因

超时值是针对当前硬件（11433 端口的本地 LLM）在正常负载下实测出来的，没有余量系数，不能适应不同环境。

### 修复方向

**方案 A — 环境变量乘数**

```python
_TIMEOUT_FACTOR = float(os.environ.get("OLAV_E2E_TIMEOUT_FACTOR", "1.0"))

def _run(agent, prompt, timeout=180):
    effective_timeout = int(timeout * _TIMEOUT_FACTOR)
    ...
```

在慢机器上设 `OLAV_E2E_TIMEOUT_FACTOR=2`。

**方案 B — LLM benchmark 预热**

测试 session 开始时发一个简单 prompt，测量 p50 延迟，动态计算 `TIMEOUT_FACTOR`：

```python
@pytest.fixture(scope="session", autouse=True)
def calibrate_llm_latency():
    t = time.time()
    _run("core", "hello", timeout=30)
    latency = time.time() - t
    if latency > 15:  # baseline 5s; >15s = slow environment
        os.environ["OLAV_E2E_TIMEOUT_FACTOR"] = str(latency / 5)
```

**方案 C — 减少 LLM 调用次数**

根本上减少每章节需要的 LLM hop 数（见 ISSUE-PLANNING-ONLY-ACCEPTANCE 方案 B），使在相同超时内有更多完成空间。

## ISSUE-NO-DATA-ACCURACY-VALIDATION

**状态**: Open  
**严重程度**: P3 — 覆盖范围缺口，不影响当前测试通过率  
**发现时间**: 2026-05-30  
**影响范围**: 整个 E2E 测试套件

### 症状

当前所有内容断言只验证关键词是否出现（见 ISSUE-LOOSE-KEYWORD-ASSERTIONS），没有一个测试验证：

- 查询返回的设备数是否与 DB 实际数据一致
- AP 型号分布比例是否正确
- 版本字符串是否来自真实设备而非 LLM 编造
- 变更计划文件是否包含真实设备名（而非 placeholder）

### 影响

如果 DuckDB 数据导入损坏（例如某次 ingest 写入了错误数据），E2E 测试仍然会通过（只要 LLM 能输出任意符合格式的文字）。

### 修复方向

**最高优先级**：新建 `tests/e2e/test_demo_data_integrity.py`

该测试文件不调用 LLM，仅：

1. 直接查询 fresh demo DuckDB
2. 验证关键统计量（设备数、型号、快照数）在期望范围内
3. 验证 `bundle_ingests.collected_at` 包含 5 个正确日期

```python
class TestDemoDataIntegrity:
    """验证 fresh demo DB 的数据完整性（无 LLM 调用）。"""
    
    def test_cisco_device_count(self):
        n = _con.execute("SELECT COUNT(*) FROM netops.parsed_outputs WHERE vendor='cisco'").fetchone()[0]
        assert 260 <= n <= 310, f"Expected ~282 Cisco devices, got {n}"
    
    def test_snapshot_count(self):
        n = len(_snaps)
        assert n >= 5, f"Expected ≥5 snapshots, got {n}"
    
    def test_bundle_dates(self):
        dates = {r[0] for r in _con.execute("SELECT DISTINCT collected_at FROM bundle_ingests").fetchall()}
        assert len(dates) >= 5, f"Expected 5 bundle dates, got {dates}"
```

这类测试运行 <1s，完全确定性，是 LLM E2E 测试的可靠前置门控。
