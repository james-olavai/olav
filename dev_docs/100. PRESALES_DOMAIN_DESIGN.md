# PRESALES Domain Design — Ingest, Storage, Multi-Project, Deliverables

**Status**: Proposal (pre-implementation)
**Date**: 2026-07-20
**Builds on**: [98. ARCHITECT_AGENT_HLD_LLD_DESIGN](98.%20ARCHITECT_AGENT_HLD_LLD_DESIGN.md)
**Extended by**: [104. PRESALES_RESEARCH_AND_SELECTION_ANALYST](104.%20PRESALES_RESEARCH_AND_SELECTION_ANALYST.md) —
adds the pre-design research/selection phase (technology + device selection,
tender analysis) as the fifth sub-agent `analyst`.

Doc 98 designed the **reasoning core** of design generation: the dialogue-driven
HLD sub-agent and the reason→specify→validate LLD sub-agent. This document
designs the **surrounding presales domain** that doc 98 assumed but did not
specify:

1. Document ingest — how unstructured customer inputs (meeting notes, docs,
   topology diagrams) become queryable data (98 §10 Open Question 1)
2. Fact storage — where structured facts (topology, requirements) live,
   as opposed to semantic chunks
3. Multi-project partitioning — one presales engineer, N concurrent
   engagements (98 §10 Open Question 3)
4. Deliverable projection — the git-committed, human-readable project dossier

The HLD/LLD workflow itself is **not** re-designed here; doc 98 remains
authoritative for it. This doc changes doc 98 in exactly two ways: the domain
is named `presales` (§1.2), and all `architect.*` tables gain a `project_id`
column (§4.3).

## 1. Scope and Positioning

### 1.1 What presales is

| Domain | Time horizon | Input | Output |
|---|---|---|---|
| `netops` | Present | Live snapshots | Change plan CLI |
| `audit` | Present | DB snapshots | Health report |
| `presales` | **Future** | Customer docs + dialogue | HLD → LLD → validated design |

Presales is the customer-facing engagement lifecycle: intake of unstructured
customer material, structured extraction, collaborative design (doc 98's
HLD/LLD core), design validation (networkx → Batfish → CLAB), and deliverable
production — partitioned per engagement.

**Confirmed vs to-be-designed**: `netops` is a known, shipped domain. Presales
is partially confirmed (HLD/LLD core designed in 98) with the ingest/storage/
project layers designed here for the first time.

### 1.2 Naming: `presales` subsumes `architect`

Doc 98 named the domain `architect` because its scope was design generation
only. The scope has grown (ingest, multi-project, dossier), and the business
role it serves is presales engineering. **Decision: the domain is `presales`;
doc 98's `architect` orchestrator + `hld` + `lld` sub-agents move under it
unchanged.** The `architect.*` DB schema name is likewise renamed
`presales.*` before first implementation (nothing is shipped yet, so this is
a doc-level rename, not a migration).

### 1.3 Delivery model: separate package, netops precedent

`olav-presales` is delivered as an **independent pip package** following the
`olav-netops` model, not as an in-tree platform agent:

- Workspace source: `olav-presales/.olav/workspace/presales/**`, deployed via
  `olav skill install olav-presales`
- Table registration: `[project.entry-points."olav.ingest_tables"]`
  (same mechanism as `olav_netops.core.tables`)
- Dependency direction: `olav-presales -> olav` (platform contract) and
  `olav-presales -> olav-netops` (read `netops.*` topology, delegate to
  `simulator`/`analyzer`). Never the reverse.

Rationale: presales has its own release cadence, its own greenfield
dependencies (Docling, potentially a vision client) that must not enter
the platform wheel, and an enterprise-adjacent audience. ADR-0004 governs
changes to the *top-level workspace agent set*; the required governance work
(ADR + `_EXPECTED_TOP_LEVEL_DIRS` update + per-artifact governance tests, all
atomic) applies to the workspace-agent registration and is listed in §9.

**Open-core boundary (decided 2026-07-21)** — consistent with dev_docs/94's
"no Pro tier with extra features; monetise content + services" stance, and
resolving the tension with dev_docs/31's feature-tier framing:

- **Open (`olav-presales`)**: all *mechanism* — the four sub-agents and
  scripts, ingest pipeline, profile mechanism itself, and the §4.5/§4.2
  confidentiality machinery (security code must be auditable to be
  trusted), plus baseline profiles/taxonomies per network type (enough to
  run and demo).
- **Commercial (olav-ent / services delivery)**: the *deep content packs* —
  curated doc profiles, industry requirement taxonomies, design-pattern
  guide libraries, BOM part-number mappings, corporate docx templates
  (the presales-domain instance of 94's "guide library + golden tests"
  service model: the mechanism is copyable in a week, a decade of presales
  experience distilled into profiles is not); compliance attestation
  reporting; and the CLAB validation rung, which already lives in olav-ent.

This split requires **no new dependency edge** (whole-domain placement in
olav-ent would have created `olav-ent -> olav-netops` for the
simulator/analyzer delegation, which the boundary rules do not allow today).

## 2. Inputs and the Ingest Pipeline

### 2.1 Input contract

Per project, the user drops everything into one directory (see §4.1 layout):

```
.olav/presales/projects/<slug>/input/
    meeting_2026-07-12.docx        ← meeting minutes
    requirements_v2.pdf            ← customer requirement docs
    current_topology.drawio        ← diagram (XML)
    legacy_diagram.png             ← diagram (raster)
    port_matrix.xlsx               ← structured tables
    old_core_config.txt            ← existing device configs (optional)
    kickoff_call.mp4               ← meeting recordings (audio/video, §2.8)
```

No naming convention is required from the user. The `surveyor` sub-agent
classifies files by extension + content sniffing.

### 2.2 Conversion layer: Docling

All office/PDF formats are converted via
[Docling](https://github.com/docling-project/docling) (IBM → LF AI, MIT) as
a dependency of `olav-presales` **only** — the platform pyproject explicitly
keeps PDF libraries out (`pyproject.toml` "pdf — 0 importers" note), and
that stays true.

**Decision (2026-07-21): Docling over markitdown.** Three load-bearing
reasons, in order:

1. **Provenance is a hard requirement, not nice-to-have** — doc 98's HLD
   workflow requires a source citation on every design decision
   (`design_evidence.source_file`). Docling preserves page + bbox
   provenance ("requirements_v2.pdf p.14"); markitdown emits a flat
   markdown stream (file-level citation only). On 100-page customer docs,
   page-level evidence decides HITL review efficiency.
2. **Tables are load-bearing presales data** — port matrices, BOMs,
   requirement tables live in PDFs. Docling's TableFormer restores
   row/column structure (→ deterministic Tier-1 ingest into DuckDB);
   markitdown's pdfminer-based PDF table output is unusable, silently
   downgrading Tier-1 data to Tier-2 LLM guessing.
3. **Confidentiality** — customer docs must not leave the intranet.
   Docling OCR (scanned PDFs) is fully local; markitdown's quality OCR
   path is Azure Document Intelligence (cloud).

Costs accepted: heavy deps (torch + ~500 MB layout/table models — pin a
models dir for offline/air-gapped deploys) and per-page-seconds CPU speed
(ingest is offline batch via `execute_skill_script`, not interactive).
~~markitdown reserved for a future audio channel~~ — superseded 2026-07-21:
audio/video goes through ffmpeg + whisper.cpp (§2.8); markitdown's audio
path uses cloud speech APIs, which the confidentiality constraint rules
out. markitdown is fully out of the dependency set. LangChain
document loaders (and `langchain-docling`) are deliberately not used —
scripts call the Docling API directly; the `Document` abstraction only adds
framework coupling.

Per source file, `extracted/` receives: **DoclingDocument JSON**
(authoritative artifact, carries provenance) + **markdown export** (feeds
LanceDB chunking), alongside a `manifest.json` (source file, sha256,
converted paths, page-provenance map, mtime) so re-ingest is incremental.

### 2.3 Topology extraction: three tiers, vision last

The central question of this design: how to extract topology from customer
material. Answer: **deterministically wherever the source format allows;
vision LLM is a fallback for raster images only.**

| Tier | Source | Method | LLM cost |
|---|---|---|---|
| 1 | draw.io / Visio (`.drawio`, `.vsdx` — both XML), port-matrix `.xlsx`, PDF tables (Docling TableFormer structure) | Pure-Python parser scripts | zero |
| 2 | Text descriptions in docs/minutes ("two cores, dual uplinks per access switch") | Main LLM structured extraction over converted markdown | normal |
| 3 | Raster images (PNG/JPG, PDF-embedded screenshots, whiteboard photos) | Vision LLM → structured JSON | separate model |

Tier ordering is a hard rule: a `.drawio` file must never be screenshotted
and sent to a vision model — the XML has exact node/edge/label data.

**Tier 3 platform constraint**: the platform LLM stack has **no multimodal
support** (`src/olav/core/llm.py` exposes no image params; the pinned
`deepseek-chat` has no vision). Vision extraction therefore requires a
**separate, optional model config** — it lives in `olav-presales`' own
config file (e.g. `.olav/config/presales.yaml`: `vision_model:
{base_url, model, api_key}`), **not** in the platform `api.json`; only the
ingest scripts read it. The whole Tier-3 path degrades gracefully: if no
vision model is configured, raster diagrams are flagged `needs_manual_entry`
instead of failing ingest.

**Tier 3 model — validated 2026-07-20**: `gemma4-31b-it-qat` +
`gemma-4-31B-it-qat-mmproj-BF16.gguf` at `http://192.168.100.12:11433/v1`
(llama-swap + llama.cpp).

*Method*: synthetic campus diagram (PNG, generated with PIL) — 7 nodes
(1 WAN router, 2 cores, 4 dual-homed access), 11 links, per-end interface
labels (`Eth1/x`, `Gi0/0/x`), link speeds (10G/25G/100G), deliberately
crossing lines in the core→access region; prompt asks for JSON per the §2.4
intermediate schema with a "use null, do NOT guess" rule for unreadable
labels; scored against ground truth on node recall, undirected link-pair
recall, per-endpoint interface accuracy, and hallucinated nodes/links.
N=3 runs per the behavioural-testing rule (`assert_success_rate` ethos).

*Results* — 3/3 perfect, zero hallucination:

| Run | Time | Nodes | Links | Iface labels | Hallucinated |
|---|---|---|---|---|---|
| 1 | 71 s | 7/7 | 11/11 | 22/22 | 0 |
| 2 | 72 s | 7/7 | 11/11 | 22/22 | 0 |
| 3 | 78 s | 7/7 | 11/11 | 22/22 | 0 |

Spot-check confirmed link speeds and crossing-line interface attribution
were also correct (not scored formally).

*Validity caveat*: this is a **clean synthetic diagram** (crisp fonts,
regular layout). It establishes the capability floor and the deployment
envelope, not a production accuracy figure — real customer Visio
screenshots and whiteboard photos are far noisier. Before relying on
Tier-3 output quality targets, re-benchmark on real project diagrams
(N≥3); the §2.5 HITL gate stays mandatory regardless.

Deployment constraints the extraction script must encode:

1. **Resize to ≤896 px width before sending** — ≥1120 px crashes the
   llama.cpp backend (`proxy error: Failed to read connection`; suspected
   image-tiling VRAM spike on top of the draft model). 896 px is stable.
2. **`max_tokens ≥ 6000`** — gemma4 reasoning consumes ~2–3 K completion
   tokens before the JSON lands in `content`; 3000 truncated the answer.
3. mmproj must match the base weights — this box briefly served a config
   pairing 31B weights with the 26B projector, which failed to load.
   Modality support is a *deployment* property, not a model property:
   verify with an actual image call, not the model card.

### 2.4 Unified intermediate schema

All three tiers emit the same Pydantic-validated intermediate document:

```json
{
  "nodes": [
    {"name": "CORE-SW-01", "role": "core", "vendor": "cisco",
     "model": "N9K-C9336C", "site": "SH-DC1"}
  ],
  "links": [
    {"a": "CORE-SW-01", "a_iface": "Eth1/1",
     "b": "CORE-SW-02", "b_iface": "Eth1/1",
     "link_speed": "100G"}
  ],
  "source": "current_topology.drawio",
  "extraction_tier": 1,
  "confidence": 1.0
}
```

- `extraction_tier` + `confidence`: Tier 1 = 1.0; Tier 2/3 = model-estimated,
  surfaced at review time.
- Call-construction errors are fixed at the **Pydantic coercion layer**, not
  with prompt imperatives (CLAUDE.md tool-I/O rule).

### 2.5 HITL gate before DB write

Tier 2/3 extractions **must** be human-confirmed before insertion into
`presales.*` tables — a wrong link poisons every downstream artifact (HLD
diagram, clab lab, Batfish check). The ingest agent presents a per-file diff
("12 nodes, 18 links extracted from legacy_diagram.png — 2 low-confidence
links flagged") and the human approves/edits. Tier 1 results auto-commit
(deterministic parse, `confidence` 1.0) but appear in the same review summary.

### 2.6 Text/semantic ingest

Converted markdown chunks flow into LanceDB via the existing
`memory-curator` / `kb_import` path (`origin="document"`), tagged with the
project dimension (§4.4). This is doc 98's hard prerequisite ("memory-curator
must run first") — **resolved here as: ingest is a presales sub-agent step,
not a manual pre-step.** The `architect` agent's Phase-0 refusal rule stays: it
checks `presales.documents` for the project and refuses to proceed if empty.

### 2.7 Document evolution, contradictions, staleness propagation

Presales is a running engagement: `requirements_v3.docx` supersedes v2, this
week's meeting overrides last month's document. Three mechanisms (gap
identified 2026-07-21):

1. **Supersede chain** — `presales.documents` carries `supersedes_doc_id`.
   When a new version is ingested, the old version's LanceDB chunks are
   down-weighted/expired (`expires_at`) and its `design_evidence` rows are
   marked `superseded`, never silently deleted (traceability).
2. **Contradiction ruling** — default precedence: *newer conversation >
   newer document > older document*; any contradiction touching a
   `blocks_topology` dimension is never auto-ruled — it becomes a
   `questions_backlog` entry for the human. The precedence rule lives in a
   guide.yaml, not code, so it is steerable per engagement.
3. **Reverse staleness propagation** — `design_decisions.source_ref` already
   links decisions to evidence. A deterministic script
   (`propagate_staleness.py`) walks decisions whose evidence became
   superseded and flips their status to `stale`, which surfaces in the
   dossier and blocks HLD sign-off until re-confirmed. Approved chapters
   citing stale decisions are listed for re-review; re-ingest of a new
   document version triggers this automatically.

### 2.8 Audio/video ingest: ffmpeg + whisper.cpp (decided 2026-07-21)

Meeting recordings (Webex/Teams mp4/m4a) are a first-class input — in
practice "会议记录" often exists only as a recording. Transcription must be
local (customer call audio is *more* sensitive than documents — the same
constraint that ruled out Azure OCR): **ffmpeg ≥ 8.0 with the whisper.cpp
audio filter** (`af_whisper`, FFmpeg 8.0 "Huffman", 2025-08). One system
binary does both format conversion and transcription; zero Python-dependency
growth.

**Pipeline** — `convert_media.py` (surveyor):
audio extraction/normalisation (16 kHz mono) → whisper filter with segment
timestamps → transcript markdown into `extracted/` + manifest → the same
LanceDB chunk path as documents. **Timestamp provenance mirrors Docling's
page/bbox**: evidence cites `meeting_2026-07-12.mp4 @00:14:32` exactly as
documents cite `requirements_v2.pdf p.14` — `design_evidence` needs no
schema change.

**Deployment gates** (encode in the script + deploy docs):

1. FFmpeg must be ≥ 8.0 **built with `--enable-whisper`** — distro packages
   mostly are not (Ubuntu 24.04 ships 6.x); provision a static build.
   Runtime capability check: `ffmpeg -filters | grep whisper`; missing →
   media files flagged `needs_manual_entry` (same graceful-degradation
   pattern as Tier-3 vision).
2. Whisper GGML model file provisioned in the local models dir (same policy
   as Docling/vision models); Chinese-heavy meetings need medium/large-v3 —
   transcription quality on zh/en mixed audio must be benchmarked on real
   recordings before quality claims (N≥3, same discipline as §2.3).

**Known limitation — no speaker diarization**: whisper.cpp transcribes but
does not attribute speakers, yet §2.7 gives conversation evidence the
highest precedence — "预算可以放宽" carries entirely different evidential
weight from customer vs vendor mouths. Mitigation: transcript-sourced
evidence gets reduced default confidence, and the HITL review step is where
key attributions are manually tagged. Diarization stacks (pyannote) are out
of scope initially (Open Question 6).

**Optional extension**: ffmpeg scene-detect keyframe extraction from video
walkthroughs (whiteboards, rack photos) feeding the Tier-3 vision path —
two existing pipelines meeting naturally; experiment later, not MVP.

## 3. Storage: DuckDB Facts + LanceDB Semantics

**Anti-pattern to avoid**: topology in LanceDB. LanceDB is the semantic
recall layer — no joins, no path queries, no exact filters. Graph data in a
vector store loses every downstream capability. Likewise **no graph database**
(Neo4j/Kùzu): presales topologies are tens-to-hundreds of nodes; the shipped
netops pattern (edge table in DuckDB + networkx in-memory projection, never
persisted) is exactly right at this scale.

| Store | Holds | Examples |
|---|---|---|
| DuckDB `presales.*` | Structured facts | topology nodes/links, requirements matrix, design runs/decisions/evidence/questions (from 98 §5), documents manifest |
| LanceDB | Semantic layer | document chunks (`origin=document`), presales `expert_knowledge` / `usage_guide` (design patterns, vendor selection heuristics) |

### 3.1 Topology tables: field-aligned with netops

`presales.topology_nodes` mirrors `netops.devices` fields (hostname, platform,
site, role, vendor, model) and `presales.topology_links` mirrors
`netops.topology_links` (same `link_id` = md5 of sorted `device:intf` pair,
same column names), plus:

```sql
project_id       VARCHAR NOT NULL,   -- §4
source           VARCHAR,            -- drawio / vision / text / xlsx / manual
extraction_tier  SMALLINT,           -- 1/2/3
confidence       FLOAT,
design_state     VARCHAR             -- as_is / to_be  (customer current vs proposed)
```

**Field alignment is the highest-leverage decision in this doc** — the entire
downstream chain works on `topology_links`-shaped data and is reused as-is:

| Existing capability | Location | Presales use |
|---|---|---|
| `draw_topology` (draw.io/Mermaid render) | `src/olav/core/topology/` + core writer scripts | HLD topology figures |
| networkx analysis (`inspect_path`, blast radius, critical nodes) | netops skillpack scripts | design structural checks |
| `generate_clab_topology_from_links` | `olav-ent/.../lab/topology.py:486` | future lab validation of proposed design |
| Batfish export / synthetic snapshots | `olav-netops/export/batfish.py`, 98 §4.5 | LLD config-layer validation |

The reuse mechanism is view-level: a `netops.topology_links`-shaped view over
`presales.topology_links WHERE project_id = ? AND design_state = ?` feeds any
consumer that expects the netops shape.

### 3.2 Design-run tables

Doc 98 §5's four tables (`design_runs`, `design_evidence`, `design_decisions`,
`questions_backlog`) are adopted verbatim under the `presales` schema, each
gaining `project_id` (a `design_run` belongs to exactly one project; one
project may have several runs, e.g. option-A/option-B designs).

Two additions (gap identified 2026-07-21):

- **`presales.requirements`** — the requirements matrix gets its own table
  (project_id, dimension, value, status confirmed/partial/missing,
  evidence_id FK, blocks_topology), not a JSON blob inside `design_runs`.
  `inspect_requirements.py` reads/writes it deterministically.
- **`requirement_dimensions.yaml`** — the dimension taxonomy is config, not
  code, parameterised by network type (dc-fabric / campus / wan), resolving
  doc 98 §10 Q4. Each dimension declares `blocks_topology` and elicitation
  question templates. Adding a dimension = YAML edit only (same pattern as
  netops `discovery_protocols.yaml`).

### 3.3 Validation ladder

```
networkx structural checks   (always: connectivity, redundancy, single points)
    → Batfish synthetic snapshot  (when LLD emits config-layer specs — 98 §4.5)
        → CLAB lab                (future: generate_clab_topology_from_links)
```

Each rung reuses shipped machinery; presales adds no new validation engine.

## 4. Multi-Project Partitioning

### 4.1 The problem and the decision

The platform has a **single project-root** concept (`_resolve_project_root`:
`OLAV_HOME` → nearest `.olav/` ancestor → CWD) and no engagement switching.
Two options considered:

- **A — directory-per-engagement** (separate `.olav/` each): zero platform
  change, but LanceDB memory is siloed too. Presales *needs* cross-project
  reuse of design experience — unacceptable cost. Rejected.
- **B — single root + `project_id` dimension** (chosen): structured isolation
  where it matters, shared experience where it matters.

### 4.2 Filesystem layout

```
.olav/presales/projects/<slug>/
    input/        ← user drop zone (§2.1)
    extracted/    ← Docling output (JSON + md) + manifest.json
    wiki/         ← project dossier (§5)
    output/       ← HLD/LLD exports (replaces 98's exports/designs/ flat dir)
```

Project lifecycle: `presales project new|use|list|archive <slug>`.

**Archive/purge must be three-way** (compliance gap identified 2026-07-21 —
"customer data deleted" is a contract-level claim):

1. DuckDB: `DELETE FROM presales.* WHERE project_id = ?`
2. **LanceDB: delete all records with `metadata.project = <slug>`** —
   including any captured/distilled memories carrying the project tag, not
   just document chunks
3. Filesystem: `input/`, `extracted/`, `wiki/`, `output/` moved to
   `archive/` (or shredded on request)

The purge script reports counts per store so the operator can attest
completeness. A lost deal disappears cleanly.

### 4.3 DuckDB

Every `presales.*` table carries `project_id` (netops precedent:
`snapshot_id`). All presales scripts take `project_id` as their first
argument; the "current project" is session state (CLI flag or
`presales project use`), stored in `presales.projects`
(`project_id, slug, customer, status, created_at`).

### 4.4 LanceDB: project facts isolated, expertise shared

Two-track design matching the presales reality (project data must not leak
across customers; design skill must):

- **Project-scoped records** (document chunks, project facts): `metadata`
  JSON (already free-form in the schema, `memory/__init__.py:301`) gains a
  `project` key. AutoRecall's Python-side IN-set filter
  (`middleware.py::_gather_candidates`) — the same place expert-scope tiers
  are applied — gains a project predicate: when a session has an active
  project, project-tagged records from *other* projects are excluded;
  untagged records pass.
- **Cross-project expertise** (`expert_knowledge`, `usage_guide`,
  `reflection`): untagged, shared via the existing scope tiers
  (`agent / shared:presales / org`). No change needed.

**This is the only platform-side change in the whole design.** It ships as
its own PR with a short ADR (first multi-tenancy dimension in the memory
layer — worth the paper trail), an integration test through AutoRecall with
production-default config (DoD wiring rule), and is a no-op for every
existing caller (no active project → no predicate).

### 4.5 Confidentiality: capture policy for the self-improving loop

**Highest-severity gap found in the 2026-07-21 review.** The L1/L2 capture
loop distills session experience into `expert_knowledge`, and
`shared:presales` scope is cross-project by design. Without a rule, a fact
distilled in customer A's session ("their core is dual-active N9K on
10.8.0.0/16") gets injected into customer B's session — a confidentiality
breach, not merely a quality issue. Policy:

1. **Capture from presales sessions defaults to project-tagged**
   (`metadata.project = <active project>`), never directly to
   `shared:presales` or `org`.
2. **Promotion to a shared scope is HITL-only** — through the existing L4
   trace-review/curator flow, with an explicit review criterion: *does this
   memory contain customer-identifiable information* (names, IP plans,
   topology specifics, commercial terms)? Only pattern-level knowledge
   ("dual-active designs need RTO confirmed before topology chapters") may
   be promoted.
3. Recall-side enforcement is §4.4's project predicate; this section is the
   **write-side** counterpart. Both are needed — the predicate alone does
   not stop a mis-scoped write from leaking later.
4. In-session cross-contamination is handled by the project-switch rules
   (§4.6).

### 4.6 Active project: resolution, visibility, switching

**Resolution order** (deterministic, three levels — every presales script
resolves the project this way):

1. Explicit `project_id` argument to the script (highest)
2. `OLAV_PRESALES_PROJECT` env var — set by `olav -a presales --project
   <slug>` at launch; session-scoped, lets two terminals work two projects
   without fighting over global state
3. `presales.projects.is_active` flag in DuckDB (persistent default; exactly
   one row; flipped by `project use <slug>`)

No active project and none given → the agent lists projects and asks (or
offers `project new`). **Empty/omitted project arg = active project**, never
an error (ADR-0009 empty-arg semantics: unspecified means "the obvious
default", not "none").

**Visibility (small-model critical)**: the active project is injected into
the system prompt as a single dynamic-context banner — `ACTIVE PROJECT:
acme-dc (customer: ACME) — all scripts operate on this project` — the same
single-control-point pattern as the global output-language directive. The
LLM never types project slugs from memory; scripts default to the resolved
active project.

**Startup = welcome-back**: on session start the agent surfaces the active
project, its design-run phase (`design_runs.phase`), and open-question count
— doc 98's "structured state survives context resets" makes resumption
free, so a session restart costs nothing.

**Mid-session switching is a session-boundary event, not a state flip.**
The conversation window still holds project A's topology and requirements
when the user switches to B — that is both a §4.5 confidentiality risk
(capture middleware would tag A-facts with B's project) and a small-model
confusion source. Rules:

1. "切到项目 B" routes to `project_admin.py use B` — it flips the DB flag,
   then **instructs the user to start a fresh session** (`/clear` /
   relaunch). SKILL.md forbids continuing design work for the new project
   in the same conversation.
2. Deterministic backstop (not just a prompt rule): presales scripts record
   the session-start project; on mismatch with the resolved active project
   they refuse with "project changed mid-session — restart", and the capture
   path suppresses memory writes for the remainder of the session.
3. Fast rejoin is the compensation: welcome-back + DB-held design state
   mean the "switch cost" is one relaunch, a few seconds.

## 5. Deliverables: the Project Dossier

HLD/LLD generation follows doc 98 unchanged. This section adds the
**projection layer**, borrowing the output shape of LangChain's OpenWiki
(git-committed markdown wiki; marker-block incremental updates) without
importing the tool (TypeScript/JS-deepagents stack — a second runtime; and
its prose-only model cannot carry structured facts).

### 5.1 Dossier = git-ized markdown projection

`wiki/` holds a human-readable engagement dossier generated by the writer
from DuckDB + LanceDB state:

```
wiki/
    index.md            ← project summary, status, links
    requirements.md     ← requirements matrix (from presales tables)
    topology_as_is.md   ← rendered current-state (draw_topology output embedded)
    topology_to_be.md   ← rendered proposed design
    decisions.md        ← design_decisions with rationale + sources
    open_questions.md   ← questions_backlog
HLD/LLD live in output/ and are linked from index.md.
```

Update semantics (OpenWiki-inspired): generated files carry
`<!-- OLAV:START/END -->` marker blocks; regeneration rewrites only its own
blocks, preserving human edits outside them. **DuckDB/LanceDB remain the
source of truth; the wiki is a projection** — never edited as input.

### 5.2 Memory export/import bridge (not migration)

Related but separate from presales: an export of `expert_knowledge`/guides to
frontmatter-markdown bundles (the reverse of the existing `kb_import`) gives
the L4 HITL trace-review loop a git-diff review surface — curator reviews a
PR instead of raw LanceDB records, then re-imports. LanceDB stays the source
of truth. Tracked as an independent platform enhancement, not a presales
deliverable.

### 5.3 Deliverable formats and scope (decided 2026-07-21)

- **md → docx/PDF rendering is in scope** — customers receive HLD/LLD as
  corporate-template documents, not markdown. One script
  (`render_deliverable.py`: pandoc + reference-doc template) at the end of
  the pipeline; markdown stays the authoritative editable form.
- **BOM is in scope** — the LLD already determines every device/module;
  emitting a bill of materials is one fat-tool call over the LLD spec
  (`generate_bom.py`), joined against a vendor part-number mapping guide.
  Pricing/quoting stays out (commercial systems own it).
- **Presentation decks (PPT) are out of scope** — the dossier (§5.1) and
  rendered HLD serve as source material; deck authoring is a human task.

### 5.4 Document-structure profiles: the skeleton as a steerable artifact

Doc 98's Phase 2 proposes a chapter skeleton conversationally and its §10 Q4
asked how to vary it per network type. Answer: **the skeleton is
instantiated from a document-structure profile** — a YAML artifact in the
steering layer (author guides, don't edit prompts), reusable across
projects, editable by the user. Same philosophy as audit's profile concept
(a saved, dialogue-authored, reusable definition).

**Profile artifact** — `references/doc_profiles/<doc_type>_<network_type>.profile.yaml`
(git-tracked, curator-reviewable):

```yaml
doc_type: hld                  # hld | lld
network_type: dc-fabric        # dc-fabric | campus | wan
chapters:
  - id: logical-topology
    title: "Logical Topology"
    scope: "layered architecture, protocol selection"
    requires_dimensions: [sites, redundancy]     # gates: must be confirmed
                                                 #   in presales.requirements
    diagrams:
      - {kind: topology_to_be, format: drawio}   # §5.5
      - {kind: traffic_flow,  format: mermaid}
    done:                                        # feeds the deterministic grader
      - every_decision_cited
      - no_pending_markers
      - required_diagrams_embedded
  # ...
```

**Workflow** (refines 98 Phase 2/3, no new phases):

1. **Propose** — `propose_structure.py propose` (deterministic): picks the
   profile matching `doc_type` + the project's network type (from
   `presales.requirements`), cross-checks each chapter's
   `requires_dimensions` against the requirements matrix, and returns the
   skeleton + per-chapter readiness. The LLM then *tailors* it to the
   project (add/remove/reorder suggestions with reasons) and presents it.
2. **Approve/modify (HITL)** — the human edits at the gate. Two persistence
   levels: per-run (approved skeleton → `design_runs.skeleton_json`, this
   project only) and durable ("以后都用这个结构" → `propose_structure.py save`
   writes a new/updated profile YAML — the edit outlives the project).
3. **Chapter loop (Plan-Act-Reflect per 98 Phase 3)** — for each chapter,
   `propose_structure.py` returns **only the current chapter's spec** (scope,
   required dimensions, diagram list, done-criteria). The full profile
   never enters the prompt — the script slices it (context budget).
4. **Done-criteria are grader input** — the chapter's `done:` list maps to
   `DeterministicSynthesisMiddleware` checks (citations present, no
   `[PENDING]`, required diagrams embedded). Zero-LLM verification, per the
   dev_docs/97 rule.

LLD uses the same mechanism (`doc_type: lld`); 98 §4.3's fixed section list
becomes the default `lld_*.profile.yaml` rather than hardcoded structure.
This resolves doc 98 §10 Q4.

### 5.5 Diagrams: Mermaid + draw.io, maximum reuse

HLD/LLD chapters and the dossier require architecture and topology figures.
Two formats, one hard authorship rule:

| Format | Author | Use |
|---|---|---|
| Mermaid | LLM-emitted (text) OR generated | conceptual/flow/layered-architecture figures; renders natively in wiki/markdown |
| draw.io XML | **Python-generated only, never LLM-emitted** | topology figures; editable customer handoff artifact |

The authorship rule is a small-model constraint: draw.io XML is verbose and
brittle — a small model *will* corrupt it (same failure class as the R88
JSON-envelope lesson). LLMs may write Mermaid (compact, line-oriented,
syntax-checkable); all draw.io output comes from code.

**Reuse — the render pipeline already exists** (§3.1's field alignment pays
off again): core's `draw_topology` + `render_topology_drawio.py` (writer
scripts, `src/olav/core/topology/`) render Mermaid and draw.io from
`topology_links`-shaped rows. `render_diagram.py` is a thin wrapper: resolve
project → select `design_state` (as_is/to_be) + scope filter → call the
core renderer → write `wiki/figures/<kind>.{mmd,drawio}` → return the
markdown embed snippet. New code is glue, not renderers.

`render_diagram.py` kinds:
- `topology_as_is` / `topology_to_be` — from `presales.topology_links`
  (drawio + mermaid twins: drawio for handoff, mermaid for inline render)
- `traffic_flow`, `layered_arch`, `zoning` — Mermaid; skeleton generated
  from DB facts where possible (zones from requirements, layers from device
  roles), LLM fills labels only; output syntax-validated before embed
- LLM-authored Mermaid in chapter prose is allowed but passes the same
  syntax validation in the Reflect step

**Raster export for docx/PDF** (§5.3): pandoc cannot render Mermaid fences —
`render_deliverable.py` must convert embedded Mermaid to SVG/PNG at render
time. Toolchain candidate: `mermaid-cli` (node) run locally; must work
air-gapped. draw.io files are attached as-is (editable source), with the
Mermaid twin providing the in-document figure. Toolchain choice is Open
Question 5.

## 6. Agent Structure

**Entry point**: `olav -a presales` — presales is its own top-level agent
(the 7th workspace domain alongside core/audit/netops/admin/devops/services),
not a sub-agent routed from another domain's orchestrator. The ADR required
by §9 covers the top-level-set change; per-domain sub-agent caps are
unaffected (presales brings its own orchestrator with 4 sub-agents).

Small-model caps apply: ≤5 sub-agents, ≤5 @tools each, thin orchestrator,
scripts-first (`execute_skill_script` in every script-bearing `tools:` list;
name-form `scripts:` entries; recipe injection per the sub-agent
`skill_name` gotcha). Every script resolves the project via §4.6 — the LLM
never passes slugs. Scripts duplicated across sub-agents follow the netops
canonical-copy pattern (canonical in `presales/scripts/`, copies must be
byte-identical, `scan_ownership.py` verifies).

### 6.1 Orchestrator `presales` — thin router + project admin

Project management is a session-level concern that fits no sub-agent; the
orchestrator owns its one script.

```yaml

    description: "new/use/list/status/archive a project; status returns the
      welcome-back bundle (active project, design-run phase, open questions);
      archive runs the §4.2 three-way purge and reports per-store counts"
    file: project_admin.py
```

Routing: intake intents → `surveyor`; design intents → `architect`/`engineer`
(98 §7 rules); deliverable intents ("出文档/更新档案/BOM") → `publisher`;
project admin handled locally.

**Sub-agent naming (decided 2026-07-21)** — platform house style is agentive
role nouns (netops: analyzer/collector/importer/learner/reporter/simulator;
audit: runner/author; core: explorer/curator/writer). Verbs and acronyms
