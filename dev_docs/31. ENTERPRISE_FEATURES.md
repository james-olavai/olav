# 企业版功能清单（BSL Commercial Tier）

**Updated:** 2026-04-17  
**对应设计文档：** `olav_aaa.md`、`log_rector.md`、`plugin_rector.md`、`audit_dataset_export.md`、`encrypted_dataset_control.md`、`dev_docs/00. issues.md` ARCH-06/14（开源 fallback 路径）

> **分界原则**：安全基线（基础认证、凭据脱敏、安全 Cookie）属于**开源版，必须实现**；  
> 合规增强（SSO、审计哈希链、长期保留、训练数据导出、高级速率限制）属于**企业插件**。  
> 企业插件通过 Python entry points 发现，不在开源目录中（见 `plugin_rector.md`）。  
> 参照：HashiCorp Vault / Teleport / GitLab 同一切割模式。

> **RBAC 分界补充**：
> - **默认内置 / 开源基线**：固定三角色（admin/user/readonly）+ 默认 skill 权限矩阵 + admin-only workspace lifecycle
> - **企业增强**：可编辑 RBAC 策略、用户组、审批流、策略版本化、UI/CLI 管理工具
> - 因此，企业版卖点不是“有没有 RBAC”，而是“能否灵活管理和审计 RBAC”

> **命名规则**：从本版开始，所有企业功能统一使用 `ent_` 前缀作为功能标识；旧的 `E-A1`、`E-4.5` 等编号仅作为历史别名保留在注释中，不再作为新设计主标识。

### 诊断与分析企业层（高级 sim / lab 能力）

#### ent_batfish_analyzer 配置层确定性分析引擎（pybatfish 集成）

**定位:** 开源版 OLAV 提供 live-state 查询（`execute_sql` + NoM 范式）；企业版加入 **Batfish 配置层确定性求值**，覆盖 policy / reachability / what-if 场景。

**与开源版能力的边界:**

| 问题类型 | 开源版（NoM / recipe） | 企业版（+ ent_batfish_analyzer） |
|---|---|---|
| Live state 查询（BGP 邻居状态、接口流量） | ✅ | ✅ |
| 拓扑 / ECMP / OSPF 路径 | ✅ | ✅ |
| Policy 解释（route-map 链路） | LLM-as-interpreter（不确定） | **确定性求值** |
| ACL reachability（"X 能否 ping Y:port"） | — | ✅ |
| Config what-if（"改这条 ACL 后通吗"） | — | ✅ |
| 跨 snapshot differential reachability | — | ✅ |
| Lab pre-push gate（变更预演） | — | ✅ |

**触发洞察（数据复用）:** `IngestManager._backup_commands()` 已持久化 `type: configuration` 的 raw running-config 到 `exports/backup/{snap_id}/`，覆盖 Cisco IOS/NXOS/IOSXR/ASA、Huawei VRP、Juniper Junos、Palo Alto、Arista EOS —— 完全对应 pybatfish vendor 支持范围。**企业版插件零额外采集开销。**

**实施清单（更新 2026-05-09，对接 R-AGENT-HIERARCHY Phase D 后 inspector 模式）:**

- [ ] `olav-ent[batfish]` extra：声明 `pybatfish` 依赖；不污染开源 base 安装
- [ ] Batfish 容器服务模板（注册到 `services/`，复用现有 `deploy_service`）
- [ ] Backup → Batfish adapter（< 50 行）：扫 `exports/backup/{snap_id}/`，按 `backup_only_commands.yaml` 中 `type: configuration` 过滤 + 重命名 + 软链到 `batfish_input/{snap_id}/configs/{device}.cfg`
- [ ] **4 个 inspector @tool**（与 Phase D inspector 模式一致——typed args + typed return，agent 用 ReAct 选 tool 调用）：
  - `inspect_batfish_traceroute(src_device, src_ip, dst_ip, protocol, dst_port)` →
    `{nodes_traversed, accepted, rules_matched, denied_at}`
  - `inspect_batfish_route_lookup(device, prefix, vrf)` →
    `{protocol, next_hop, as_path, metric, admin_distance}`
  - `inspect_batfish_policy_test(device, policy_name, test_prefix, direction)` →
    `{matched, action, matched_clauses}`
  - `inspect_batfish_compare_snapshots(baseline_snap, candidate_snap, dimension)` →
    `{routes_added, routes_removed, policies_changed, reachability_diff}`
- [ ] sim SKILL.md 加 Batfish 决策表行：检测 policy / reachability / what-if 类问题自动 dispatch 到 `inspect_batfish_*`；解析失败 / 不支持 vendor 时 fallback 到现有 inspector（model.graph）
- [ ] Snapshot 级缓存（每 `snap_id` 只 init 一次，常驻 batfish 服务）
- [ ] 输出附带 evidence token `[src: batfish#snap_id query=...]`（对接 ARCH-11 引用链规范）
- [ ] **tcf_writer 内建 Batfish validate**（确定性 deterministic 安全网，LLM 不感知）：
  - 在 `render_tcf_from_change_plan` 渲染完 candidate CLI 后，自动调
    `bfq.differentialReachability(baseline, candidate)`
  - 如 Batfish 预测 BGP convergence 失败 / 现有 reachability 损坏 →
    返回 `{status: "error", blockers: [...]}`，spec.tcf.yaml 不写盘
  - 与现有 `_db_facts` 的 ASN cross-check 并列——第二层确定性验证
- [ ] Lab pre-push gate：变更前 Batfish 推演，预测合理才推 lab 实跑（lab 资源更贵）
- [ ] CLI：`olav --agent netops --batfish "..."` 强制 batfish 路径（绕过 LLM 路由）
- [ ] CI：跑 batfish 相关测试需 batfish 容器健康；不可用时 SKIP 而非 FAIL

**为什么是 4 个 inspector 而不是 1 个 generic `bfq_query`（设计决策）:**

R-AGENT-HIERARCHY 实证（`dev_docs/69`）：小模型对**多个窄工具选择**（1/N picker）比**一个大工具填多种 args**（多 mode 复杂 schema）友好得多。Phase D inspector 模式（4 个网络 inspector + submit_change_plan）在 gemma4:31b nothink 上跑通 6-call ReAct workflow；早期实验中 generic `run_python_simulation` + 30 行 NetworkX 模板让 gemma4 12 分钟卡死。

Batfish 集成沿用同款模式。每个 inspector 一个语义明确的查询，typed 入参 + typed 出参——LLM 不需要懂 pybatfish API，只需要"选工具填 args"。

**典型用例:**
- `olav --agent ops "R1 ACL 是否允许 10.1.2.3:any → 10.2.3.4:443？"` → batfish 返回 permit/deny + 命中 ACL 行号
- `olav "R1 学不到 10.2/16？"` → NoM 显示当前 RIB（无 10.2/16）+ batfish 显示"在 R3 出向 prefix-list BLOCK 第 5 条拒绝"
- 准备 route-map 变更 → `olav diff_change <file>` → batfish 输出"R1→R2 方向 prefix 10.1/16 将不再 advertise" → 用户确认后才推 lab

**风险与缓解:**

| 风险 | 缓解 |
|---|---|
| Java/JVM 依赖重 (~300MB) | 标记 optional extra；CI 未启用时 skip 相关测试 |
| Batfish 解析某些 vendor config 失败 | warning + fallback 到 NoM/LLM |
| 初始化 latency（10s-2min/snapshot） | snapshot 级缓存 + 常驻 batfish 服务 |
| 与开源版"轻量诊断"定位冲突 | 严格 enterprise-only；默认安装不含 |

**与其他企业能力联动:**
- `ent_audit_hash_chain`：batfish 输出的 evidence token 进入哈希链审计
- `ent_field_redaction`：batfish 处理的 raw config 含 community/password → 必须经脱敏引擎

**前置依赖:**
- 开源版完成 ARCH-06（recipe）+ ARCH-14 P1/P2（NoM L1+L2+L3+policy 只读）作为 fallback 路径
- 开源版 ARCH-11（引用链规范）为 batfish 输出对接预留 evidence 字段

## 许可与分发（`ent_license_*`）—— 设计草案

**Added:** 2026-08-04 ｜ **状态：设计草案，未实现，末尾待决问题定稿后再动代码**

### 立场与硬约束

**现有法律立场已经决定了保护模型。** core 与 olav-netops 是 **BSL-1.1**（源码可见 +
使用限制 + change date），olav-ent 的 `LICENSE` 是 **OLAV Enterprise Commercial
License v1.0**。也就是说这套产品从一开始就选择了「靠许可条款保护，不靠保密保护」
——与 HashiCorp Vault / Teleport / GitLab 同一模式（本文开头的分界原则已经引用了
它们）。后文关于代码混淆的结论与这个既有立场一致，不是新的取舍。

> 附带缺口：`olav-ent/pyproject.toml` **没有 `license` 字段**（core 与 netops 都有
> `license = {text = "BSL-1.1"}`）。因为 ent 不上 PyPI，影响仅限于 wheel 元数据缺
> 少商业许可声明，但交付给客户的 wheel 里应当能自证许可归属。

**离线可验证是硬约束，不是偏好。** 气隙部署是旗舰场景——`[local-embed]` extra
整个存在的理由就是 offline / air-gapped。任何以 phone-home 为运行前提的方案会直接
砍掉最有价值的那类客户。因此：**签名令牌离线校验为主，联网仅作可选增值**
（自动续期、自动 true-up、用量遥测），永不作为启动条件。

### `ent_license_token` — 许可令牌

离线可验证的签名令牌，公钥随 olav-ent 分发，`olav license install <file>` 落地，
全程不联网。

**加密原语无需新依赖**：olav-ent 已声明 `tink>=1.14.1`（原为加密数据集导出引入）
与 `PyJWT>=2.8.0`。建议 Ed25519 + JWS —— 选 JWS 而非私有二进制格式，是因为客户能
自行解开查看内容，对企业采购是透明度加分项。

令牌字段（草案）：

| 字段 | 说明 |
|---|---|
| `lic_id` | 许可证唯一 ID，用于审计与吊销名单 |
| `customer` | 客户标识 |
| `tier` | 层级（决定 `ent_*` 功能开关位） |
| `features` | 显式功能开关，允许按项售卖而非只按层级 |
| `device_quota` | 设备额度（见 `ent_license_device_scale`） |
| `not_before` / `not_after` | 有效期 |
| `binding` | 绑定策略与参数（见 `ent_license_node_lock`） |
| `rebind_quota` | 允许的自助重绑定次数 |

### `ent_license_device_scale` — 设备规模授权

**计数口径不能取库存表。** `netops.devices` 是客户自己可写的 DuckDB，改一行就绕过。
正确的计量点是**设备被实际操作的出口**，而这套代码里这些出口已经很窄：SSH 采集
（`execute_cli_parallel` / `take_snapshot`）、配置推送（node_cli push）、快照。

**口径建议**：滚动窗口（默认 30 天）内**实际发生过采集或推送的不同设备身份数**。
身份优先取序列号 / chassis ID，退化到 `hostname + mgmt IP`。落库存**加盐哈希**而非
明文——计数可核对，但即使启用遥测也不泄露客户网络清单。

这个口径对客户也更公平：库存 500 台、实际只管 80 台就按 80 计，销售侧更好谈。

**超额处置：只告警，不阻断。**

| 用量 | 行为 |
|---|---|
| ≥90% | 告警 |
| ≥100% | 每次运行显示超额 + 写审计 |
| ≥150% | 仅限制**新增**设备，不限制已在管设备的操作，且给足宽限期 |

理由不是宽容，是风险：网络运维工具在变更窗口里因许可超额拒绝执行，会直接导致投诉
升级甚至丢单。超额事件写入 `audit.duckdb`——既是续约时的真实证据，也是客户可自查
的透明记录，与本仓 @tool 判据 #3「关键审计必须落审计表」一致。

### `ent_license_node_lock` — 一机一码

**这套架构下硬绑定会失控**：运行环境包含容器与 VM（仓库内即有 docker overlayfs 与
containerlab）。容器里的 `/etc/machine-id` 每容器一份、重建即变——硬绑它等于每次
重新部署都要客户重新申请授权，支持成本不可接受。

**方案 A（推荐）：模糊指纹 + 自助重绑定。**

指纹取多源元组：`/etc/machine-id`、DMI product UUID
（`/sys/class/dmi/id/product_uuid`，注意需 root）、主网卡 MAC、根盘序列号、
CPU 型号 + 核数、主机名。匹配用 **N-of-M**（如 6 取 4）：换网卡、迁移 VM、扩容 CPU
都不误伤，整机更换则失配。再叠**重绑定配额**（如许可期内 3 次自助重绑），能消掉
绝大多数支持工单。

**方案 B（更省事，值得认真考虑）：绑部署实例而非机器。** 首次运行生成实例 ID 写入
客户自己的 DuckDB，令牌约定「同时活跃实例数 ≤ N」。对 HA / 蓝绿 / 容器编排友好得多，
代价是防复制弱一些。若客户以直签企业为主，这个折中通常更划算——企业客户不会为省一份
授权去做批量克隆，风险收益不成比例。

**必须设计的两个失效模式**：

- **时钟篡改**：调回系统时间可绕过到期。对策是本地记录「观察到的最大时间戳」高水位，
  发现时钟大幅倒退则拒绝运行并要求人工确认。
- **气隙续期**：必须有纯文件投放的续期路径，不能只有联网续期。

这套代码已有的钩子，不需要新开侵入式检查：

| 钩子 | 位置 | 用途 |
|---|---|---|
| `db_write_gate` | `core/db_write.py:125`（try/except 引入 `olav.enterprise.db_write_gate`） | 写入闸门，天然收口点 |
| 认证分派 | `core/auth/provider.py` → `olav.enterprise.auth.*` | 已有的 enterprise 挂载点 |
| `olav.enterprise_commands` entry point | 已存在（`log_export` 走它） | 加 `olav license` 系列命令 |
| `olav doctor` | 已报 15~19 项检查并带 `fix` | **展示**许可状态：到期 / 超额 / 指纹失配 |

**强制逻辑放在 olav-ent 内部**，挂在 enterprise 功能入口上，不进 core。理由：core 是
BSL 源码可见单元，把许可检查写进去既违反边界（CLAUDE.md 禁止 core 硬编码 enterprise
语义），又等于白送一份可 patch 的检查代码。没装 olav-ent 就没有 enterprise 功能可
授权，逻辑自洽。

> **来自本仓血泪史的强提醒**：CLAUDE.md 记录了四个「TDD 全绿但从未被任何入口触达」
> 的功能，其中两个躺了几个月。许可检查若只有单测、没有从真实 CLI / middleware 路径
> 走通的集成测试，它极可能成为第五个——而这个功能一旦是死的，**不会有任何报错**，
> 只会在某天发现所有客户都在免费使用。按 CLAUDE.md「Definition of Done: wiring must
> be verified from a real entry point」，这是必须项而非加分项。

### 代码保护：真实威胁模型

**结论：不要编译成 `.pyc`。** 三层理由，第三层是这套架构特有的、也是决定性的。

**（1）保护力接近零。** `.pyc` 是字节码，`decompyle3` / `pycdc` 可还原为可读
Python。它拦住的是不会写代码的人，而不会写代码的人本来也不会去逆许可检查。

**（2）成本很实：版本锁死。** pyc 带 magic number，绑定具体 CPython 小版本。
`requires-python = ">=3.11"` 而实测环境已在 3.14——意味着 3.11/3.12/3.13/3.14 各需
一份 wheel，客户升级 Python 即失效；同时 traceback 失去源码行，远程支持难度陡增。

**（3）它会直接打断产品机制**：

- **docstring 就是 LLM 的工具契约。** `@tool` 的 docstring 是喂给模型的 API 描述
  （CLAUDE.md：每个 tool schema 每次调用花 150~300 token，且有
  `test_docstring_budget` 守卫）。要真正剥离字符串需 `-OO`，而 `-OO` **删除所有
  docstring** —— 等于撕掉 agent 的工具说明书。不用 `-OO` 则 docstring 原样留在 pyc
  里，混淆价值更低。
- **workspace 脚本是当源码执行、当文档阅读的。** `execute_skill_script` 起子进程跑
  `<skill>/scripts/*.py` 纯文件；SKILL.md 的 `scripts:` 描述注入系统提示。
  `services/lab/scripts/*.py` 正是这一类。编译后要么跑不了，要么运维再也读不懂
  agent 在做什么——而「运维能读懂脚本」是本设计刻意保留的性质。

**最关键的一点：真正值钱的资产根本无法编译。** 这是个 LLM 产品，核心资产是
**skill / prompt / guide**——`SKILL.md`、`prompts/*.md`、`references/*.guide.yaml`、
tier 默认值、WHAT-not-HOW 的提示工程结论。这些**必须是明文**，因为消费方是模型本身。
`.pyc` 保护的是最不值钱的 Python 管道，对最值钱的提示资产**零作用**。所以「做不做
pyc」这个问题本身就问错了层次。

### 真正提高门槛的手段（按性价比排序）

| 手段 | 挡住什么 | 代价 | 建议 |
|---|---|---|---|
| 许可令牌 + 绑定 + 审计（前述 `ent_license_*`） | 内部超量部署、随手复用——**占实际风险的绝大多数** | 中 | **做** |
| **按客户水印 skill / prompt 资产** | 让泄露可归因，威慢作用强 | 低 | **做**（仓库里已有 `demo_watermark.py` 先例） |
| 仅把许可/指纹/计量模块 Cython 化 | 阻止对检查本身的轻易 patch | 低（模块小、无 docstring 职责、运维不需读） | **值得**——这是编译唯一挣回成本的地方 |
| 高价值 guide 加密 + 内存解密 | 抬高门槛 | 中高；且破坏「运维可读」性质 | 谨慎，注意可内存 dump |
| 皇冠功能移到托管侧 | **唯一真正的保护** | 放弃该功能的气隙能力 | 仅对确定不需气隙的功能考虑 |

**威胁分层要诚实**：内部超量部署（最常见）→ 许可 + 审计足够；竞争对手决心克隆 →
进程内没有任何手段能阻止，靠法律 + 迭代速度；客户员工好奇心 → 无关。**最典型的
错误是把工程投入花在第二层（不可能赢），而第一层（便宜有效）还没实现。**

**对本产品最强的实际护城河是自我改进闭环**：guide / memory 随部署持续积累
（L1/L2 capture、reflection），被窃取的快照是**贬值资产**，而持续更新与支持偷不走。

### 待决问题（定稿后才动代码）

1. **绑定粒度**：方案 A（一机一码，N-of-M 指纹 + 重绑定配额）还是方案 B（绑部署实例，
   活跃实例数上限）？B 的支持成本低一个数量级。
2. **设备计量口径**：接受「滚动 30 天内实际操作过的设备数」，还是坚持按库存计？
3. **超额策略**：确认「只告警不阻断」为底线，还是需要硬上限？
4. **遥测通道**：是否需要可选联网上报用量以支持自动 true-up；气隙客户如何 true-up。
5. **是否 Cython 化许可模块**：若客户群存在转售风险则值得；若均为直签企业客户，
   建议省下这份复杂度。
6. **水印方案**：水印落在 guide / prompt 的哪一层，如何做到不影响模型行为。
