> **Date**: 2026-05-16

## Why this runsheet

Earlier runsheets (`dev_docs/71`) walked OLAV against a small synthetic CLAB
lab (6 nodes).  This one drives OLAV against **production-scale real data**
to validate:

1. **Ingest scales** — 360 hosts × 24 commands × 2 snapshots in one DB.
2. **Cross-snapshot drift analysis** is correct on real change patterns.
3. **Fault analyses** surface real operational issues
   (AireOS migration debt, WLC coverage gaps, AP-density imbalance) on
   data we did *not* curate.
4. **Change simulations** (topology blast-radius, migration sequencing)
   produce useful plans without invented data.

The "fault" findings here are **real ops issues** that exist in this
university's network — re-discovering them from raw CDP/inventory data
is the point.

## CH8 — Change simulation #1: foo-dist-4500xv-d chassis failure

```bash
cd ~/olav-demo-inbox-prod
olav --agent netops "foo-dist-4500xv-d 故障后，网络会断成几个部分？"
```

OLAV routes to `analyzer` → calls `inspect_blast_radius` (NetworkX weakly-connected
components on the DB topology graph).

> **Metric note**: `inspect_blast_radius` counts nodes that become **completely
> disconnected** (zero-degree, all edges severed). An earlier Python BFS approach
> counted nodes that lose their **path to the WAN core** (`foo-wan-6880v`) — a
> larger set (~332) because it includes nodes still connected to local peers but
> cut off from the uplink. The two metrics answer different questions;
> `inspect_blast_radius` is the OLAV-native definition.

**Acceptance**: OLAV response includes:
- `73 → 99 connected components` (delta: +26 partitions)
- `55 completely isolated nodes` (zero-degree after failure)
- Named example fragments: a 248-node cluster, multiple 20-60 node mid-tier clusters

## CH11 — Change Plan: Catalyst 4500X Distribution IOS-XE Upgrade

**触发依据**: CH7 发现接入层已从 17.9.6 升至 17.12.5，但全部 WS-C4500X-32
distribution/wifi/server 层仍停留在 03.11.10.E（2021 年发布，距当前 latest stable
03.11.12.E 差两个 maintenance release）。版本割裂导致 VSS/LACP 报文格式不一致，
存在 CDP capability mismatch 和 QoS policy 解释差异风险。

### 分阶段升级计划（OLAV 自主生成）

```bash
cd ~/olav-demo-inbox-prod
olav --agent netops "制作 WS-C4500X-32 6阶段 BFS 升级变更计划，目标设备 foo-dist-4500xv-a 至 foo-dist-4500xv-n（14台），叶节点优先，保存到 exports/change_plans/WS-C4500X_BFS_staged_upgrade_plan.md"
```

OLAV routes to `analyzer` → SQL topology queries → `inspect_blast_radius` per stage
→ `format_and_export(mode='append')` × 6.

**验收**: `exports/change_plans/WS-C4500X_BFS_staged_upgrade_plan.md` 存在，包含：

| 阶段 | 设备 | blast radius 等级 |
|---|---|---|
| Stage 1 | foo-dist-4500xv-b, c | Low |
| Stage 2 | foo-dist-4500xv-e, f | Low |
| Stage 3 | foo-dist-4500xv-g, h | Low |
| Stage 4 | foo-dist-4500xv-i, j, k | Low |
| Stage 5 | foo-dist-4500xv-l, n, d | High（d: 35 接入交换机） |
| Stage 6 | foo-dist-4500xv-a, m | Critical（核心汇聚，影响 16+25 接入交换机）|

### 升级前验证

```bash
cd ~/olav-demo-inbox-prod
olav --agent netops "列出所有 WS-C4500X-32 设备当前的 IOS 版本、CDP 邻居数量和上行接口状态，作为升级前 baseline"
```

**验收**: 返回 14 台设备的版本（应为 03.11.10.E）、邻居数和接口状态；数字存档用于升级后对比。

### 升级后验证

```bash
cd ~/olav-demo-inbox-prod
olav --agent netops "对比升级前快照和升级后快照，确认所有 WS-C4500X-32 已升至 03.11.12.E，CDP 邻居无丢失"
```

**验收**: 所有 14 台返回 ✓ OK；任何 ✗ FAILED 触发回滚流程。

### 回滚标准

满足以下任一条件立即回滚至 03.11.10.E：
1. 升级后 CDP 邻居数量减少 >1（邻居丢失）
2. 任意 uplink 接口 `link_status != 'up'`（拓扑中断）
3. 升级后 5 分钟内发生 BGP/OSPF flap（路由不稳定）
4. AP 关联数在 WLC 侧下降 >10%（Stage 5 专用指标）
