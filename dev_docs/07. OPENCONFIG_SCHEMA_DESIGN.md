## 0.1 Package Ownership Boundary

本文件虽然以 NetOps 场景为主要例子，但其核心内容属于 **platform-facing data contracts**，不是纯 NetOps 运行手册。

归属划分如下：

- **属于 `olav-platform` 的机制**：raw snapshot contract、inventory abstraction、schema-on-read、semantic view contract、`schema_catalog` 作为 authoritative semantic metadata 的规则
- **属于 `olav-netops` 的领域语义**：OpenConfig vocabulary、network domains、topology relationship taxonomy、SR Linux / CAB render 语义
- **当前仓库中的混合现实**：文档仍以 NetOps 为主叙事，但后续拆包时应保持“平台提供机制，NetOps 注入标准库与领域模型”的边界

详细归属总表见 `12. PLATFORM_NETOPS_OWNERSHIP_MAP.md`。

## 0. 文档目的

这份文档只回答四个问题：

1. **当前运行时的真实 SSOT 是什么**
2. **目标架构中哪些数据应该保持原样，哪些数据可以派生**
3. **标准字段名从哪里来**
4. **LLM / sandbox / YANG / inventory 各自负责什么**

本稿明确区分：

- **Current State**：仓库里今天已经存在、可验证的实现
- **Target State**：后续要收敛到的目标设计
- **Migration**：从 Current State 走到 Target State 的步骤

这三部分不得混写。

## 1. 核心结论

1. **Raw Snapshot SSOT**：`parsed_outputs.parsed_data` 是采集结果快照，保存厂商原始 TextFSM 字段，不做写时字段名重写
2. **Inventory SSOT**：设备 `platform` 的权威来源是运行态 inventory provider；当前默认实现是 `.olav/config/nornir/hosts.yaml`，但设计上不得绑定单一 inventory 后端
3. **Canonical Namespace SSOT**：标准字段名优先来自 OpenConfig / YANG 叶子语义；无覆盖时才落到 OLAV 扩展命名空间
4. **Value Normalization Only**：写入前只做值级规范化，如接口名、MAC、IP/CIDR；不在写入时把厂商字段名改成 canonical 字段名
5. **Schema-On-Read**：跨厂商统一查询通过 Semantic Views 完成，而不是修改原始快照
6. **LLM Is Mapper, Not Lawgiver**：LLM / sandbox 负责字段对齐、歧义消解、DDL / ETL 生成，不负责发明标准字段体系
7. **OC Is Canonical Vocabulary + Export Protocol**：OpenConfig 一方面提供 canonical 语义命名，另一方面用于 SR-Linux / CAB 的导出协议；它不是内部存储格式
8. **Bundled Reference, Explicit Refresh**：安装产物内自带固定版本 OpenConfig reference 作为 bootstrap 基线；如需更新版本，必须走显式刷新流程，而不是每次 init 联网拉最新

## 2. 当前运行现实

### 2.1 已存在的运行时事实

当前仓库已存在以下可验证组件：

- **Inventory**：当前默认运行态是 `.olav/config/nornir/hosts.yaml`，保存设备、平台、分组、别名
- **Raw Snapshot Store**：DuckDB `parsed_outputs` 保存设备名、命令、`parsed_data`、快照 ID 等
- **Write-time Value Normalization**：`src/olav/core/normalization.py` 中存在 `normalize_record()`
- **OC/YANG Assets**：`bootstrap_yang.py`、`yang_leaves`、`OPENCONFIG_YANG_REFERENCE`
- **Bundled Reference Asset**：包内资源 `olav.data.yang/openconfig_reference.txt` 随 wheel 安装，用于无网络环境下初始化 `yang_leaves`
- **Schema Engine**：`schema_engine.py` 当前仍支持 `schema_catalog × yang_leaves -> mapping_rules`

这意味着：

- 运行时 inventory 不是某个独立 CSV 文件
- YANG 不是“可有可无的背景资料”，而是当前体系里的真实资产
- 当前实际可复现的 bootstrap 基线应来自包内固定 reference，而不是依赖 init 时在线拉取上游仓库
- 现有系统还处于 OC-first 残留和 Schema-On-Read 目标并存的过渡期

### 2.2 当前实现中的主要矛盾

当前代码和此前草稿存在四类混淆：

1. **把 inventory 写成 `devices.csv`**，但实际运行态是 Nornir inventory
2. **把字段名重写放到入库前**，这与 `parsed_outputs` 作为 raw snapshot 的原则冲突
3. **把 YANG 降级为可选辅助**，但当前代码实际上仍然依赖 `yang_leaves` 和 YANG 参考路径
4. **把目标架构、过渡步骤、当前状态写在同一层**，导致文档不可执行

本次重写的目标就是消除这四类冲突。

## 3. 三个 SSOT

### 3.1 Inventory SSOT

**定义**：决定设备身份、平台、站点、角色、别名的权威源。

**当前默认实现**：`.olav/config/nornir/hosts.yaml`

**目标抽象**：`InventoryProvider`

Inventory SSOT 在设计上不能等同于某一个文件路径。它应该是一个稳定接口，允许不同运行环境替换底层 inventory 来源，例如：

- Nornir `hosts.yaml`
- 第三方 CMDB / Source of Truth
- 用户自定义 inventory 插件
- 临时实验环境注入的 session inventory

**设计要求**：

- Stage 2 解析流程中使用 `InventoryProvider.get_platform(device_name)` 给出的 `platform`
- 不信任 Scrapli / Netmiko 的自动探测结果作为最终平台判定
- 自动探测只可作为 fallback 或 warning source，不可覆盖 inventory SSOT
- 允许第三方 inventory provider 替换 Nornir 文件实现，但上层调用接口不变

**建议接口**：

```python
class InventoryProvider(Protocol):
  def get_platform(self, device_name: str) -> str | None: ...
  def get_device(self, device_name: str) -> dict[str, Any] | None: ...
  def list_devices(self) -> list[str]: ...
```

**建议扩展接口**：

```python
class InventoryProvider(Protocol):
  def get_platform(self, device_name: str) -> str | None: ...
  def get_device(self, device_name: str) -> dict[str, Any] | None: ...
  def list_devices(self) -> list[str]: ...
  def resolve_identity(self, query: str) -> str | None: ...
  def get_aliases(self, device_name: str) -> list[str]: ...
```

### 3.1.1 Device Identity Contract

为了避免 query、collect、topology 三条链路对同一设备使用不同名字，设备身份归一规则必须前置定义。

**Canonical device identity**：`device_name`

`device_name` 是全系统唯一稳定键，要求：

- 在一个 workspace 内唯一
- 不因 hostname 变化而变化
- topology / query / collect / render 共用同一个 identity

**推荐解析优先级**：

```text
1. Exact inventory key match
2. Alias match
3. Hostname match
4. Management IP match
5. Reject as ambiguous / unresolved
```

**约束**：

- `topology_links.source_device` / `destination_device` 只能写 `device_name`
- semantic views 中的 `device_name` 只能写 `device_name`
- Query Agent 接收自然语言时，可命中 alias / hostname / 管理 IP，但在执行前必须归一到 `device_name`
- 如果一个查询词命中多个设备，必须返回歧义错误，不能隐式选一个

**理由**：

- auto-detect 在边界平台上可能误判
- schema 映射、命令注册、模板选择都依赖 `platform`
- 如果平台源不稳定，整个语义映射链路就会静默漂移
- 如果把 SSOT 写死为 `.olav/config/nornir/hosts.yaml`，一旦用户切到外部 inventory，设计立即失效

### 3.2 Raw Snapshot SSOT

**定义**：设备命令原始解析结果的唯一事实来源。

**当前实现**：`parsed_outputs.parsed_data`

**设计要求**：

- 保存厂商原始字段名
- 保存 TextFSM 原始结构
- 不在入库时改成 canonical 字段名
- 允许做值级清洗，但不允许做语义字段改名

**允许的写时处理**：

- 接口名值规范化：`Gi0/0` -> `GigabitEthernet0/0`
- MAC 值规范化：`0050.7966.6800` -> `00:50:79:66:68:00`
- IP / netmask 转前缀
- 空值统一成 `None`

**不允许的写时处理**：

- `link_status` -> `oper_status`
- `name` -> `interface`
- `peer` -> `neighbor_address`

这些都属于 **read-time projection**，不属于 snapshot。

### 3.3 Canonical Namespace SSOT

**定义**：跨厂商统一查询时使用的标准字段命名空间。

**优先级**：

1. **OpenConfig / YANG canonical leaf**
2. **OLAV semantic extension namespace**（仅当 OC 无覆盖）

**例子**：

- `oper-status` / `oper_status` 来源于 OpenConfig interfaces 语义
- `peer-as` / `peer_as` 来源于 OpenConfig BGP 语义
- `admin_distance` 若无直接 YANG 叶子，可归入 OLAV 扩展语义命名

**关键点**：

- canonical namespace 不等于存储格式
- canonical namespace 主要体现在 Views、Query contract、Topology contract、OC render contract 中

### 3.4 YANG Bootstrap Asset

**定义**：用于初始化 `yang_leaves` 的固定版本 OpenConfig reference 资产。

**当前实现**：包内资源 `olav.data.yang/openconfig_reference.txt`

**原则**：

- 默认 bootstrap 使用随包安装的固定 reference
- bootstrap 必须支持离线执行
- `init` 只负责确保本地基线存在，不负责在线刷新上游 OpenConfig 仓库
- 如需升级 YANG 版本，必须走显式 refresh/revendor 流程

这保证了安装结果可复现，也避免把“init”变成一个依赖外网和上游状态的非确定性动作。

## 4. 标准字段名从哪里来

### 4.1 结论

标准字段名的来源不是 LLM 主观命名，而是：

1. **先从 OpenConfig / YANG 抽取 canonical 叶子语义**
2. **再让 LLM 将厂商字段映射到这些既有 canonical names**
3. **只有在 OC 无覆盖时，才允许产生 OLAV 扩展语义字段**

### 4.2 YANG 的角色

YANG 在目标架构中不是“存储目标”，而是“命名空间来源”。

它负责提供：

- 规范字段名
- 语义路径
- domain 边界
- 高置信度映射候选

它不负责：

- 决定内部存储格式
- 强迫所有命令都变成 OC JSON
- 在写入阶段构建树形结构

**补充约束**：

- 安装产物中应至少带有一份固定版本的 OpenConfig reference 作为 bootstrap 基线
- `yang_leaves` 的默认初始化应来自该包内 reference，而不是依赖每次 init 时联网下载 `.yang` 文件
- 如果未来需要完整 `.yang` 模块集，也应采用 vendored snapshot 随版本发布，而不是 runtime pull latest

### 4.3 LLM / Sandbox 的角色

LLM / sandbox 负责：

- 从 `parsed_outputs` 中抽取厂商字段清单
- 将厂商字段映射到 YANG / canonical namespace
- 对低置信字段做语义补全
- 生成 Semantic View DDL
- 生成 topology ETL 模板

LLM / sandbox 不负责：

- 发明新的标准体系替代 YANG
- 直接写共享数据库
- 在写入时修改 raw snapshot

### 4.4 推荐映射优先级

```text
Priority 1: Exact or near-exact OpenConfig / YANG leaf match
Priority 2: Same-domain canonical alias derived from YANG semantics
Priority 3: OLAV extension field for uncovered concepts
Priority 4: Human review for unresolved mappings
```

## 5. 目标架构

### 5.1 总体图

```text
Inventory SSOT (InventoryProvider)
        |
        v
CLI Collect (Scrapli -> Netmiko fallback)
        |
        v
TextFSM raw records
        |
        v
Value normalization only
        |
        v
parsed_outputs.parsed_data   <-- Raw Snapshot SSOT
        |
        +--> schema discovery sandbox (Phase A / B)
        |        |
        |        v
        |   field inventory + examples
        |        |
        |        v
        |   YANG-first semantic mapping
        |        |
        |        v
        |   schema_catalog / generated view metadata
        |
        +--> Semantic Views (read-time projection)
        |
        +--> topology_links ETL (derived truth for graph / CLAB)
        |
        +--> render_oc (export-time OC JSON)
```

### 5.2 Collection Layer

采集链路保持 CLI-first：

- Scrapli 为首选 SSH 驱动
- Netmiko 为稳定 fallback
- 失败写入 repair queue
- 不再把 gNMI / NETCONF 作为常规读取路径主轴

### 5.3 Write-time Normalization

写入阶段只保留 **value normalization**：

- `normalize_record()` 这一类逻辑保留
- 可扩展为更强的值清洗器
- 但不做 canonical field rename

因此，正确的写入顺序应该是：

```python
records = [normalize_record(r) for r in records]
parsed_data = json.dumps(records)
```

而不是：

```python
records = [catalog_driven_normalize(r, command, platform) for r in records]
```

后者会破坏 raw snapshot 的定义。

### 5.4 Semantic View Layer

Semantic Views 才是 canonical field contract 的主要载体。

职责：

- 跨厂商字段统一
- query agent 的主查询入口
- topology ETL 的一致输入
- SR-Linux render 的规范字段来源

Views 的列名原则：

- 有 OC 覆盖的 domain：采用 OC 语义名
- 无 OC 覆盖的 domain：采用 OLAV 扩展语义名

### 5.4.1 Query Contract

Query Agent 只允许消费两层 contract：

1. **Level 1: Semantic View Contract**
2. **Level 2: Raw Fallback Contract**

**Level 1: Semantic View Contract**

- 返回 canonical 列名
- 适用于跨厂商聚合、筛选、JOIN、排序
- 是默认查询路径

示例：

- `v_interfaces.oper_status`
- `v_bgp.peer_as`
- `v_l2_neighbors.remote_system`

**Level 2: Raw Fallback Contract**

- 仅在某命令尚无 semantic view 时使用
- 返回厂商原始字段 + 命令上下文
- 不伪装成 canonical schema

设计要求：

- fallback 结果必须明确标注 `command`、`platform`、`raw_fields`
- Query Agent 不得把 raw fallback 返回值伪装为 canonical view contract
- 一旦某类查询进入稳定高频路径，应回补 semantic view，而不是长期依赖 fallback

### 5.5 Topology Layer

`topology_links` 不是 raw snapshot，而是 **derived operational truth**。

它的输入来源应统一为：

- Semantic neighbor views
- 必要时的 relationship-specific ETL

它的用途：

- NetworkX 图分析
- ContainerLab topology render
- CAB 审核证据

### 5.5.1 Relationship Taxonomy

为避免 topology、graph、simulation 三层接口继续发散，relationship 类型在设计上先固定为以下五类：

| relationship_type | link_type | 定义 | 是否进入 `topology_links` |
|---|---|---|---|
| `l2_neighbor` | `L2` | CDP / LLDP 发现到的二层设备邻接 | 是 |
| `l3_adjacency` | `L3` | OSPF 等 IGP 邻接关系 | 是 |
| `logical_peering` | `logical` | BGP、隧道、overlay 等逻辑对等关系 | 是 |
| `route_dependency` | `derived` | 路由下一跳对接口、邻居、前缀的依赖 | 否，单独派生 |
| `interface_attachment` | `attachment` | 接口与子网、VRF、VLAN 等附着关系 | 否，单独派生 |

约束：

- `topology_links` 只承载 **device-to-device** 关系
- `route_dependency` 和 `interface_attachment` 不直接写入 `topology_links`
- 这两类关系应进入后续单独的依赖表或派生视图，避免污染核心拓扑边模型

### 5.5.2 Graph Contract

图数据的 canonical 输入不是 raw snapshot，而是 `topology_links`。

**Canonical graph representation**：`nx.MultiDiGraph`

原因：

- 同一对设备可能同时存在 L2、L3、logical 多条异构边
- 部分关系是有方向的
- 需要保留 `discovery_protocol`、`relationship_type`、`snapshot_id` 等边属性

**边属性最小集合**：

```python
{
  "source_device": str,
  "source_interface": str | None,
  "destination_device": str,
  "destination_interface": str | None,
  "relationship_type": str,
  "link_type": str,
  "discovery_protocol": str,
  "snapshot_id": str,
  "confidence": float | None,
  "status": str,
}
```

**派生图规则**：

- `G_canonical`: `nx.MultiDiGraph`，完整保留全部边
- `G_l2`: 从 `relationship_type = l2_neighbor` 投影为无向图
- `G_l3`: 从 `relationship_type = l3_adjacency` 投影为无向或弱有向图
- `G_logical`: 从 `relationship_type = logical_peering` 投影为有向多重图

结论：

- canonical graph 只保留一个：`MultiDiGraph`
- 其它图都是针对具体分析任务的 projection

### 5.6 OC Render Layer

`render_oc()` 是 **export-time translation**，不是存储层。

它读取：

- raw snapshot
- semantic views
- schema catalog / canonical mapping metadata

它输出：

- OpenConfig JSON
- 交给 `gnmi_push.py` 推送到 SR-Linux

它不应该依赖写时字段改名后的 `parsed_data`，因为目标设计里并不存在这种数据结构。

### 5.6.1 Render Contract

`render_oc()` 的输入 contract 必须固定为：

1. semantic view rows 或等价 canonical projection
2. `schema_catalog` 中的 canonical-to-OC path metadata
3. 必要时对 raw snapshot 的只读补充访问

约束：

- render_oc 不得直接消费 Query Agent 的 raw fallback 输出
- render_oc 必须把 canonical 字段映射视为唯一稳定输入语义
- 对于没有 semantic view 的命令，必须先形成明确 projection contract，才能进入 render

这样才能保证 query contract 和 render contract 使用同一套 canonical vocabulary。

## 6. schema_catalog 的正确定位

### 6.1 它是什么

`schema_catalog` 是 **semantic mapping metadata**，不是 raw data，也不是最终 view 本身。

它至少要描述：

- 命令属于哪个 domain
- 记录是 entity 还是 relationship
- 每个厂商字段映射到哪个 canonical 字段
- canonical 字段背后的 OC path 或 OLAV semantic path
- 该命令是否需要 topology ETL

### 6.2 它不应该是什么

`schema_catalog` 不应该承担：

- 写时字段改名逻辑容器
- Pydantic 源码仓库
- 运行时 snapshot 替代品

如果后续确实需要 schema validation model，也应该是：

- **validation model**
- 或 **projection contract**

而不是修改 raw snapshot 的工具。

### 6.3 推荐结构

```json
{
  "juniper_junos::show bgp summary": {
    "domain": "bgp",
    "record_type": "entity",
    "canonical_source": "openconfig",
    "field_mappings": {
      "peer": {
        "canonical": "neighbor_address",
        "oc_path": "openconfig-bgp:bgp/neighbors/neighbor/state/neighbor-address",
        "confidence": 0.96
      },
      "as": {
        "canonical": "peer_as",
        "oc_path": "openconfig-bgp:bgp/neighbors/neighbor/state/peer-as",
        "confidence": 0.95
      }
    }
  }
}
```

这里的 `canonical` 是 **view-time contract**，不是 write-time storage key。

### 6.4 `schema_catalog` 与 `mapping_rules` 的过渡关系

当前实现中两者同时存在，因此必须明确过渡期职责，避免双重真相源。

| 组件 | 过渡期职责 | 长期目标 |
|---|---|---|
| `schema_catalog` | canonical mapping metadata、view generation 输入、render contract 输入 | 长期保留 |
| `mapping_rules` | 兼容旧 OC-first 路径、旧 topology engine / legacy query path 的桥接层 | 最终退出或降级为缓存 |

**过渡原则**：

1. 新设计中的 **authoritative mapping source** 是 `schema_catalog`
2. `mapping_rules` 只作为 legacy compatibility layer 使用
3. 不允许先修改 `mapping_rules` 再反写 `schema_catalog`
4. 如需保留 `mapping_rules`，应由 `schema_catalog` 单向派生生成

**推荐过渡顺序**：

```text
schema_catalog  -->  generate semantic views
schema_catalog  -->  generate render contract
schema_catalog  -->  optionally derive mapping_rules for legacy paths

NOT ALLOWED:
mapping_rules   -->  reverse-build schema_catalog
```

这条规则保证未来删除 `mapping_rules` 时不会破坏设计主轴。

## 7. YANG-first Auto Discovery

### 7.1 自动发现的正确顺序

```text
Step 1: 从 parsed_outputs 抽取字段清单和示例值
Step 2: 从 YANG / OpenConfig 索引加载 canonical leaf inventory
Step 3: LLM 对字段进行 YANG-first 映射
Step 4: 将无法匹配的字段归入 OLAV semantic extension
Step 5: 生成 view metadata / DDL / ETL 模板
```

### 7.2 Sandbox 应分阶段执行

自动发现不应在一次 sandbox 执行里同时完成“字段映射、关联发现、拓扑建模、图构建”。建议明确拆成四个阶段：

#### Phase A：平台基线映射

目标：每个平台选择一个代表性命令样本，先建立 **platform-specific field mapping baseline**。

输入：

- InventoryProvider 提供的平台列表
- 每个平台的代表设备
- 每个平台的代表命令与样本记录

输出：

- 平台级别映射表
- 高置信 canonical 字段映射
- 低置信待审项

目的：先解决“这个平台上的字段怎么理解”，而不是一开始就用全量数据混在一起做映射。

#### Phase B：全量命令归档与领域视图生成

目标：在已有平台映射基线之上，收集完整数据并归档到 domain 级 schema metadata。

输入：

- 全部 `parsed_outputs`
- Phase A 的平台映射表
- YANG / OC canonical inventory

输出：

- domain 级 `schema_catalog`
- entity / relationship 分类
- Semantic View DDL

目的：把“单个平台字段理解”提升为“跨平台统一查询契约”。

#### Phase C：关联发现、topology 映射与图构建

目标：在已有 domain metadata 之上识别所有可能的关联数据，建立 topology ETL 和 graph contract。

输入：

- neighbor / route / BGP / OSPF / ARP 等 relationship 候选数据
- Phase B 的 domain metadata

输出：

- topology relationship mapping table
- `topology_links` ETL 模板
- graph build contract（L2 / L3 / logical edge typing）

目的：把字段映射问题和拓扑关系问题解耦，避免在映射阶段就过早做图建模。

#### Phase D：图数据生成与仿真消费

目标：将 `topology_links` 派生成 NetworkX / CLAB / simulation 可消费的数据结构。

输出：

- NetworkX graph
- CLAB render input
- Simulation engine input

结论：

- **平台映射表建立** 是第一阶段
- **全量数据归档** 是第二阶段
- **关系发现 + topology 映射** 是第三阶段
- **图数据生成** 是第四阶段

这样才能保证每一步都有明确输入输出和可验证 Gate。

### 7.3 为什么不是“LLM 先命名”

因为如果让 LLM 先命名，会产生三个问题：

1. 同义字段容易出现多个 canonical name
2. Query Agent contract 会漂移
3. render_oc 无法稳定绑定到 OC path

### 7.4 Sandbox 的职责边界

沙箱可以做：

- 数据调查
- 映射候选生成
- DDL / ETL 模板生成
- 在内存 DuckDB 中验证 SQL

沙箱不应做：

- 直接修改共享 DuckDB
- 决定 raw snapshot 结构
- 绕开 inventory / YANG SSOT

## 9. 关键设计决策

### 9.1 为什么 inventory 应以 InventoryProvider 为准

因为设计级 SSOT 不能绑定某个具体后端文件。当前默认实现虽然是 Nornir runtime inventory，但架构层真正稳定的对象应该是 `InventoryProvider` 接口。这样既能兼容当前实现，也能支持第三方 inventory。

### 9.2 为什么 raw snapshot 不能在写时改字段名

一旦把 `name` 改成 `interface`、把 `link_status` 改成 `oper_status`，`parsed_outputs` 就不再是 snapshot，而变成 projection。这样会丢掉对模板升级、映射修订、重建视图的可逆性。

### 9.3 为什么标准字段名必须 YANG-first

因为 canonical namespace 必须稳定、可审查、可解释。YANG / OC 提供的是既有标准；LLM 负责把厂商字段贴到标准上，而不是再发明一套标准。

### 9.4 为什么 render_oc 不能依赖“已改名 parsed_data”

因为目标设计中这种数据不存在。render_oc 应该依赖 canonical mapping metadata，而不是依赖被修改过的 snapshot。

### 9.5 为什么 topology_links 仍然保留

因为 topology graph、CLAB render、CAB evidence 都需要一个统一且扁平的派生事实表。它是共享下游契约，保留是合理的；但它应该从 read-time projection 生成，而不是从写时字段改名生成。

## 10. 迁移路径

### Phase 1：文档与现实对齐

- 删除文档中的 `devices.csv` SSOT 表述
- 删除文档中的写时字段名重写表述
- 明确 inventory SSOT = `InventoryProvider`，当前默认实现为 Nornir runtime inventory
- 明确 canonical namespace = YANG-first

**Gate**：设计文档内部不再出现上述自相矛盾表述。

### Phase 2：收敛 write path

- 保留并强化 `normalize_record()` 作为 value normalization
- 明确禁止 write-time canonical field rename
- 评估当前 `apply_oc_mapping()` 在主链路中的位置，逐步退出 raw snapshot 路径

**Gate**：`parsed_outputs` 保持厂商字段名；值级规范化仍然生效。

### Phase 3：收敛 canonical mapping path

- 以 `yang_leaves` / OpenConfig path inventory 作为 canonical source
- 让 schema discovery sandbox 改为 YANG-first pipeline
- 重定义 `schema_catalog` 为 projection metadata，而不是 rename recipe

**Gate**：新增 NTC 模板时，可以自动生成映射候选，但不会改写历史 snapshot。

### Phase 4：收敛 query / topology / render path

- Query Agent 优先走 Semantic Views
- topology_links 从 Semantic Views / relationship ETL 派生
- render_oc 从 canonical metadata + raw snapshot / semantic views 生成 OC JSON

**Gate**：

- 跨厂商查询返回统一列名
- topology graph 与 CLAB render 使用同一派生表
- render_oc 不再依赖被重写字段名的 snapshot

### 10.1 分阶段验证 Gate

为避免“阶段完成”只停留在文字描述，每个 sandbox / migration 阶段至少满足以下量化要求：

| 阶段 | 最低 Gate |
|---|---|
| Phase A 平台基线映射 | 每个平台至少选 1 台代表设备、3 条代表命令；高置信映射覆盖率 >= 80% |
| Phase B 全量命令归档 | 每条命令至少生成 `domain`、`record_type`、`field_mappings`、`canonical_source` |
| Phase C topology 映射 | `topology_links` 中 L2 / L3 / logical 边均有明确 `relationship_type`；空接口字段仅允许出现在 `logical_peering` |
| Phase D 图生成 | `G_canonical` 节点数与 `topology_links` 设备集合一致；边类型投影总数与源表统计一致 |

这些 Gate 不是最终测试全集，但必须作为最小通过线。

### Phase 5：删除过时 OC-first 组件

- 在完成 read-time canonical projection 收敛后，再评估 `mapping_rules`、部分 legacy schema engine 路径的退出
- 删除条件是“替代链路可运行”，不是“设计文档里觉得应该删除”

**Gate**：测试通过，且运行态不再依赖已删除路径。

### 10.2 迁移执行细则

为了避免迁移阶段再次混淆“值规范化”和“字段投影”，执行步骤固定如下：

1. **冻结当前 snapshot 语义**
  - 明确 `parsed_outputs.parsed_data` 不再发生字段级重写

2. **补齐 value normalization**
  - 对历史数据执行可回放的值级清洗
  - 仅影响接口名、MAC、IP、空值等 value-level 处理

3. **生成 canonical metadata**
  - 以 `schema_catalog` 作为 authoritative source
  - 从 YANG-first pipeline 生成 field mappings、domain、record type

4. **重建 read-time projections**
  - 重建 semantic views
  - 重建 topology_links
  - 重建 graph projections

5. **切换 query/render consumer**
  - Query Agent 默认改走 semantic view contract
  - render_oc 改走 canonical projection contract

6. **下线 legacy compatibility path**
  - 确认无 consumer 依赖 `mapping_rules` / `apply_oc_mapping()` 后再移除

7. **固定 bootstrap 资产来源**
  - 将 OpenConfig reference 作为包内资源纳入安装产物
  - `init` / `netops_init` 只负责 ensure `yang_leaves` 已初始化
  - 上游 YANG 版本升级通过显式 revendor 流程完成，不在 init 中自动联网执行

**绝对禁止的迁移动作**：

- 直接批量把历史 `parsed_data` 的字段名改写成 canonical names
- 在未定义 cut line 前同时让新旧两套 canonical contract 长期并行
- 用 render/export 逻辑反向定义 query contract

## 11. 最终原则

可以用一句话概括新架构：

> **Inventory 用 `InventoryProvider` 作为唯一抽象来源，snapshot 保持厂商原样，canonical 字段体系来自 YANG / OpenConfig，LLM 只负责把两者连接起来。**

这条原则同时约束：

- 平台判定
- snapshot 写入
- schema 自动发现
- semantic view 生成
- topology 派生
- OC export

只要未来变更不违反这条原则，这份设计就仍然自洽。
