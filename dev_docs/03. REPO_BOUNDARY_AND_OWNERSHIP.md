# 03. Repo Boundary and Ownership

**创建日期：** 2026-04-04  
**状态：** Active  
**目标：** 为 `olav`、`olav-doc`、`olav-netops`、`olav-ent` 定义权威边界，并明确当前过渡期允许保留的耦合。

---

## 1. Purpose

这份文档不是“拆分已经完成”的宣言。

这份文档的作用是定义四类边界：

1. 哪个仓库 / 包拥有什么能力
2. 哪些能力当前仍必须在 `olav` 根仓库内继续开发
3. 哪些内容已经可以独立拆出
4. 过渡期允许哪些临时实现位置和依赖方向

因此，本文必须同时区分：

- **当前态（Current State）**
- **目标态（Target State）**
- **过渡例外（Transitional Exceptions）**

---

## 2. Terminology

### 2.1 Delivery Units

本文约束以下五个交付单元：

| 名称 | 类型 | 角色 |
|---|---|---|
| `olav` | 核心 Python 包 / 主运行时仓库 | 平台控制面、运行时、CLI、插件契约、共享基础设施 |
| `olav-netops` | 领域扩展包 | 网络运维领域能力 |
| `olav-ent` | 企业扩展包 | 企业特性、企业集成、企业治理能力 |
| `olav-doc` | 文档发布仓库 | 文档站源码（MkDocs）— `docs.olavai.com` |
| `olav-web` | 网站 / 边缘应用仓库 | 主站源码（Astro + Cloudflare Worker + R2）— `olavai.com` |

### 2.2 Ownership vs Implementation Location

必须明确区分两个概念：

- **Ownership**：某能力从架构上归谁负责
- **Implementation Location**：该能力当前代码暂时放在哪个路径

当前代码路径不能自动代表最终归属。

如果某能力今天仍位于 `src/olav/...`，但它本质上是网络领域专属能力，那么该路径应视为**过渡实现位置**，而不是最终 ownership 结论。

---

## 3. Decision Summary

当前边界决策如下：

1. `olav` 继续作为**平台基座**和**运行时控制面**维护。
2. `olav-netops` 作为网络领域扩展持续拆出，但允许暂时依赖 `olav` 的稳定平台契约。
3. `olav-ent` 作为企业扩展持续拆出，但允许暂时依赖 `olav` 的稳定平台契约。
4. `olav-doc` 只负责文档站（MkDocs），不依赖运行时。
5. `olav-web` 只负责主站与边缘逻辑（Astro + Worker + R2），不依赖运行时。与 `olav-doc` 类似，但关注点不同。
6. 文档站点与主站的拆分，不等于平台代码已经可以粗暴地从 `olav` 根仓库移除。

---

## 4. Current State

### 4.1 Root `olav` 仍是平台基座

当前 `olav` 根仓库仍承载以下平台级职责：

- 平台 CLI 入口
- runtime bootstrap
- workspace 生命周期管理
- agent / tool / service 发现与装配
- audit、auth、database、memory 等平台共性能力
- platform-level plugin contract

这意味着：**部分功能现在仍必须先在 `olav` 内开发，再向扩展仓库下沉。**

这不是边界失败，而是过渡期事实。

### 4.2 `olav-netops` 已经是独立包，但尚未完全脱耦

`olav-netops` 已具备独立包形态，但仍依赖 `olav` 提供的平台入口和基础契约。

因此：

- 可以独立发布
- 不能假定已经完全脱离 `olav`
- 新的 platform contract 仍可能首先在 `olav` 中设计和实现

### 4.3 `olav-ent` 已经独立打包，但边界更不干净

`olav-ent` 当前同样依赖 `olav`，且企业能力与 root CLI / root namespace 的关系尚未完全清理。

因此：

- 可以独立发布
- 不能声称已经完全独立运行
- 与 `olav` 的 enterprise hook 边界仍需继续规范化

### 4.4 Docs / Web 更容易先拆出

文档站与官网的构建链、部署链和运行时链都与 `olav` 核心运行时弱耦合。

因此，`olav-doc` 是当前最适合优先独立维护的部分。

但这里有一个前提：**只能有一个权威源码源头。**

不能长期同时维护：

- root `docs/` + `mkdocs.yml` + `web/`
- `olav-doc/docs/` + `olav-doc/mkdocs.yml` + `olav-doc/web/`

双源并存会直接导致漂移。

---

## 5. Target State

### 5.1 `olav` Owns Platform-Generic Capabilities

`olav` 的最终稳定职责应包括：

- agent orchestration
- runtime bootstrap
- workspace lifecycle
- plugin discovery and entry-point contracts
- audit / trace pipeline
- auth / RBAC
- shared database and memory infrastructure
- generic service registry mechanisms
- generic schema / ingest / tool discovery contracts
- platform sandbox and safety primitives

`olav` **不默认拥有**网络协议语义、网络拓扑语义、OpenConfig / YANG 词汇本体、CLAB 工作流或企业专属业务能力。

### 5.2 `olav-netops` Owns Network Domain Capabilities

`olav-netops` 的目标稳定职责应包括：

- OpenConfig / YANG vocabulary bootstrap
- network inventory semantics
- topology ETL and topology reasoning
- graph-based network investigation helpers
- network policy IR and control-plane reasoning
- network-specific validation
- network-specific collectors / exporters / services
- lab / ContainerLab specific workflows

### 5.3 `olav-ent` Owns Enterprise-Only Capabilities

`olav-ent` 的目标稳定职责应包括：

- enterprise-only auth / governance integrations
- enterprise audit export workflows
- encrypted dataset control and policy
- enterprise compliance features
- enterprise deployment integrations

任何只对企业版有意义、且不属于平台通用机制的能力，最终都不应留在 root `olav` 中。

### 5.4 `olav-doc` Owns Public Documentation and Website

`olav-doc` 的目标稳定职责应包括：

- `docs/` 文档内容
- `mkdocs.yml` 文档站配置
- `web/` 官网源码
- Cloudflare Pages 或等价静态站部署配置

`olav-doc` **不拥有** Python runtime、platform bootstrap、agent runtime 或任何生产运行时服务逻辑。

---

## 6. Boundary Rules

### 6.1 Allowed Dependency Directions

允许的依赖方向：

1. `olav-netops -> olav`
2. `olav-ent -> olav`
3. `olav-doc -> none`（不依赖 runtime internals）

理由：`olav` 是平台基座，领域包与企业包建立在平台契约之上。

### 6.2 Conditionally Allowed Reverse Coupling

`olav -> olav-netops` 与 `olav -> olav-ent` 只有在以下条件满足时才允许：

- 通过 entry point / plugin discovery 动态发现
- 通过 guarded optional import 实现
- 不把扩展包设为核心启动链路的硬前置依赖

也就是说，`olav` 可以“发现扩展”，但不应“绑死扩展”。

### 6.3 Forbidden Dependency Directions

以下情况视为违反边界：

1. `olav-doc` 直接依赖 `src/olav` 运行时代码
2. `olav` 核心基础设施默认硬编码网络领域语义
3. `olav` 核心基础设施默认硬编码企业版特性
4. 文档站源码在 root 与 `olav-doc` 两边长期并行演进

---

## 7. Repo Content Boundaries

### 7.1 What Belongs in `olav`

应该保留在 `olav` 的内容：

- `src/olav/` 中的平台通用代码
- root `pyproject.toml`
- 平台 CLI 与 runtime lifecycle
- `.olav/workspace/` 中平台级控制面定义
- 平台插件契约和 extension hooks

不应长期保留在 `olav` 的内容：

- 仅用于公开文档站发布的源码
- 网络领域专属协议语义实现
- 企业专属业务逻辑

### 7.2 What Belongs in `olav-netops`

应该归入 `olav-netops` 的内容：

- network domain models
- topology / simulation / OpenConfig / YANG
- network-specific service implementations
- network slash commands and domain prompts
- network-specific schema and collectors

### 7.3 What Belongs in `olav-ent`

应该归入 `olav-ent` 的内容：

- enterprise commands
- enterprise-only authz / policy extensions
- enterprise export / encryption / compliance flows

### 7.4 What Belongs in `olav-doc`

应该归入 `olav-doc` 的内容：

- public docs site content
- MkDocs configuration
- Astro website source
- docs-site / web-site deployment config

---

## 8. Transitional Exceptions

以下例外在当前阶段允许存在，但必须被明确标记为过渡状态，而不是长期边界。

### 8.1 Platform Contract First, Extraction Later

如果某能力同时满足以下条件，则允许先在 `olav` 中开发：

1. 它本质上是平台契约、平台生命周期或平台扩展点
2. `olav-netops` 或 `olav-ent` 需要依赖它，但它尚未稳定

例如：

- workspace lifecycle contract
- plugin discovery contract
- service registry mechanism
- platform extension hooks

这些能力可以先在 `olav` 中实现，再让扩展包接入。

### 8.2 Vendored Domain Assets During Split

如果某些 domain asset 当前仍以 vendored 方式存在于 root runtime 中，允许暂时保留，但必须满足：

- 文档中声明它是过渡资产
- 不把其路径误写为最终 ownership
- 存在明确的迁出目标和退出条件

### 8.3 Enterprise Namespace Leakage

如果 `olav-ent` 当前仍与 root namespace 或 root CLI 存在遗留耦合，这属于过渡问题，不代表 enterprise 应继续常驻 root。

解决方向应是：

- 收敛为稳定 hook
- 去除 root 对 enterprise 的硬编码路径依赖

### 8.4 Docs Split Can Happen Earlier

文档与官网仓库可以先于代码完全拆分而独立。

因此允许：

- 先将 docs / web 的 authoritative source 收敛到 `olav-doc`
- 平台代码仍继续在 `olav` 中迭代

禁止把这一步误读成：

- `olav` 已经不再需要作为主开发仓库

---

## 9. Publish and Release Policy

### 9.1 Publish Order

推荐发布顺序：

1. `olav`
2. `olav-netops`
3. `olav-ent`
4. `olav-doc`

说明：

- `olav-netops` 与 `olav-ent` 依赖 `olav` 的兼容版本
- `olav-doc` 发布节奏可以独立于 Python 包版本

### 9.2 Version Compatibility

版本策略应满足：

- `olav-netops` 明确声明与 `olav` 的兼容范围
- `olav-ent` 明确声明与 `olav` 的兼容范围
- `olav-doc` 不以 Python import compatibility 为约束，而以内容准确性和发布时点为约束

## 10. Ownership Matrix

| Capability | Owning Unit | Runtime Host | Current Reality | Transitional Note |
|---|---|---|---|---|
| CLI bootstrap | `olav` | `olav` | root 已承载 | 平台核心能力，继续保留 |
| workspace lifecycle | `olav` | `olav` | root 已承载 | 扩展包依赖该契约 |
| plugin discovery | `olav` | `olav` | root 已承载 | 扩展包通过该机制接入 |
| audit / auth / DB / memory | `olav` | `olav` | root 已承载 | 平台通用基础设施 |
| network vocabulary | `olav-netops` | `olav-netops` + `olav` runtime | 仍有部分遗留在 root | 应逐步迁出 root |
| topology / graph reasoning | `olav-netops` | `olav-netops` + `olav` runtime | 仍有部分遗留在 root | 视为过渡实现位置 |
| network collectors / services | `olav-netops` | `olav-netops` + `olav` runtime | 部分仍与 root 耦合 | 通过 plugin/service contract 下沉 |
| enterprise-only features | `olav-ent` | `olav-ent` + `olav` runtime | 仍存在 root 耦合 | 应改为 enterprise hook |
| public docs content | `olav-doc` | static site | root 与 `olav-doc` 双源并存 | 必须收敛为单一权威源 |
| public website | `olav-doc` | static site | root 与 `olav-doc` 双源并存 | 必须收敛为单一权威源 |

## 11. Immediate Policy Consequences

从本文件生效起，以下规则成立：

1. 任何新文档若描述 repo split，必须引用本文作为边界总则。
2. 任何新代码若准备迁出 `olav`，必须先判断它是平台契约还是领域实现。
3. 任何新文档站或官网修改，都必须避免继续制造 root 与 `olav-doc` 双源编辑。
4. 不得再以“路径当前在 root”作为 ownership 的唯一依据。
5. 不得再以“文档站可拆”推导出“平台代码可整体搬离 root”。

---

## 12. Open Questions

本文确认了边界原则，但以下问题仍需后续决议：

1. `olav-doc` 何时成为唯一 authoritative docs / web source
2. root 中现有 docs / web 资产如何迁移或归档
3. `olav-ent` 与 root namespace 的最终清理路径
4. `.olav/workspace/ops/` 是过渡 vendored asset 还是长期内置资产
5. `olav` 与扩展包之间哪些 hook 应被正式冻结为稳定 API

这些问题应在后续迁移执行文档中处理，而不是在本文中假设已经解决。

---

## 13. Final Position

最终立场如下：

1. `olav` 继续作为平台基座开发与发布。
2. `olav-netops` 与 `olav-ent` 独立发布，但仍基于 `olav` 平台契约运行。
3. `olav-doc` 可以更早独立，并成为文档站与官网的唯一权威源码位置。
4. 文档站点可先分离，平台功能不能粗暴拆走。
5. 边界治理的关键不是“立即物理拆分一切”，而是“清楚定义 ownership、依赖方向与过渡例外”。
