# 116. 导入不能是静默的：损失账本与导入报告

**Date**: 2026-08-05
**Trigger**: dev_docs/115 §8.4 —— Ch2 第一 beat 答「317 台设备」而真实是 339。
我最初把它记成「agent 口径错」。用户反驳：**这不算 agent 的错，真正该修的是导入
过程静默**——应该说清导入了多少、哪些设备没进来、哪些数据没导出、原因是什么。
**这个判断是对的，而且指向一个比 317 大得多的问题。**

---

## 1. 先把事实澄清（用户表述里有一处需要修正，但结论不变）

用户说「db 只能查解析后的数据」。**这一点不准确**：

| 表 | 内容 | 设备数 |
|---|---|---|
| `netops.devices` | 每台设备一行（hostname/platform/model/role…）| **339** |
| `netops.raw_output_store` | 每个 (设备,命令) 的**原始文本** | **339** 台 / 8761 条 |
| `netops.parsed_outputs` | 结构化解析结果 | **317** 台 / **2278** 条 |

所以 339 台全部可查，原始文本也全部可查；只有**结构化视图**（`parsed_outputs`
与 `v_*_auto`）受解析能力限制。因此对「刚导入了多少台设备」这个问法，**339 才是
正确答案**，317 是「有结构化数据的设备数」。

**但用户的结论完全成立，而且更重要**：317 这个数字之所以会被当成答案，正是因为
**导入过程从不报告自己丢了什么**。agent 只能看到「有解析结果的东西」，于是把
「能解析的」当成了「导入的」。修 agent 的口径只是打补丁；根因是导入静默。

## 2. 静默的真实规模：8761 → 2278，**74% 无声丢失**

导入完成时 agent 收到的摘要是：

> Devices Processed: 339 · Total Commands Ingested: 8,761 ·
> Structured Data: **9 command types** were successfully parsed

只报成功项。实测缺口：

| 指标 | 数量 |
|---|---|
| 落地的 (设备,命令) 对 | 8761 |
| 进入 `parsed_outputs` 的 | **2278**（26%）|
| **未解析** | **6483**（74%）|
| 一条都没解析出来的设备 | **22 台**（每台只有 1 条 raw 命令）|
| 存在未解析输出的命令种类 | 29 |

未解析量最大的命令（按 (设备,命令) 对计）：

| 命令 | raw | 未解析 |
|---|---|---|
| `show running-config` | 338 | 338 |
| `show interfaces status` | 315 | 315 |
| `show interfaces description` | 315 | 315 |
| `show ip igmp snooping group` | 281 | 281 |
| `show environment power all` | 281 | 281 |
| `show switch detail` | 281 | 281 |

**其中 `show running-config` 的 338 条是完全正常的**——它在 `netops.commands` 里
登记为 `parser_type='raw_only'`，本来就不该解析（Ch4 的 Batfish 导出正是用它的
原始文本）。而其余的原因各不相同，却被同一个 `None` 抹平了。

## 3. 根因：一个 `None` 承载了三种完全不同的结局

`olav_netops/core/ingest/landing.py` 原来的实现：

```python
def _parse_one(platform, command, body) -> str | None:
    try:
        parsed = parse_output(platform, command, body)
    except Exception:      # ← ① 解析器抛异常，被吞掉
        return None
    if not parsed:         # ← ② 模板匹配到 0 行；③ 根本没有模板
        return None
    return json.dumps(parsed)
```

调用方：

```python
parsed_json = _parse_one(...)
if parsed_json:
    parser_fills[rec.command] += 1      # 只统计成功
# else: 什么都不做 —— 损失就在这一行的“不存在”里
```

**流程在丢弃的那一刻是知道原因的**（异常类型就在手上，命令是否登记解析器
`netops.commands` 也查得到），却把原因扔了。这是「静默」的确切位置。

## 4. 修法：损失账本 + 一份真实的导入报告

### 4.1 `_parse_one` 返回原因

```python
def _parse_one(...) -> tuple[str | None, str]:
    ...
    except Exception as exc:
        return None, f"parser_error:{type(exc).__name__}"
    if not parsed:
        return None, "no_rows"
    return json.dumps(parsed), "ok"
```

`no_rows` 仍然合并了「模板不匹配」与「没有模板」——因为 `parse_output` 把三层
tier 折叠成一个 `None`。这两者在**入库之后**用 `netops.commands` SSOT 分开，那张
表知道每个 platform+command 的 `parser_type`。不去改 tier 级联，是为了把改动限制在
一处。

### 4.2 循环里记账

按 `(platform, command)` 累计未解析数、记录首个异常类型，同时记录「产出过解析行的
设备集合」——后者一减就是「无结构化数据的设备」。

### 4.3 入库后归类

| 判据 | reason | 含义 |
|---|---|---|
| 记录到异常 | `parser_error:<Type>` | 解析器抛了，日志里有 traceback |
| SSOT 中 `parser_type='raw_only'` | `raw_only` | **设计如此**，不该解析 |
| SSOT 中无该 platform+command | `no_parser_registered` | 没有登记解析器 |
| 其余 | `parser_no_match` | 有解析器但匹配到 0 行（模板/输出不符）|
| SSOT 读不到 | `unclassified` | 明说读不到，并提示跑 `olav init` 同步 SSOT——**不猜** |

### 4.4 产出

- `IngestResult.parse_report` —— 结构化字典（设备总数 / 有结构化数据的设备数 /
  无结构化数据的设备及样例 / 落地与解析的 (设备,命令) 对数 / 按 reason 汇总 /
  按命令 top-20），wrapper 脚本一并透出，agent 因此能如实叙述。
- `exports/import_reports/<snapshot_id>.md` —— 人可读的完整报告：头部数字、
  **点名**无结构化数据的设备、按 reason 的表、按命令的表、以及成功解析的清单。
  报告里明确写一句：**没解析 ≠ 没导入**，原始文本在 `raw_output_store`，
  设备行在 `netops.devices`，受限的只是 `v_*_auto` 这类结构化视图。

报告写失败**绝不影响导入**（`_write_import_report` 返回 None）。这一条有测试守护，
而且它当场抓到一个真 bug：`landing.py` 里没有 `logger`，我在 except 块里调用它会
抛 `NameError`——本来是「报告失败」的地方会变成「导入失败」。

## 4.5 真实数据上的实测输出（339 台 bundle，真实入口）

重装后的 demo 主机上，通过 `importer/scripts/ingest_snapshot.py` 这个真实 wrapper
重跑导入，得到：

```
Devices landed: 339 | Command outputs landed: 8761
Parsed into structured rows: 2278 (26%) | Not parsed: 6483 (74%)

unparsed_by_reason:
  no_parser_registered  3421
  parser_no_match       2724
  raw_only               338
```

**这个三项分解是修改前拿不到的信息**——原来只有一句「9 command types parsed」。
报告同时点名了 22 台无结构化数据的设备（`alpha-ag-224-*`、`beta-ag-224-*`、
`epsilon-ag-224-*`、`nu-wan-3850`、`theta-ag-204-*`、`zeta-ag-224-2`、
`alpha-br-3560`、`alpha-ls4-3560`），落盘于
`exports/import_reports/snap_20260805_091113_imported.md`。

注意 `no_parser_registered` 是最大的一类（3421，53%）——**白名单缺项比模板不匹配
更严重**，这是修改前完全看不见的事实。

## 4.6 工具返回还不够 —— 叙述模板才是那个静默的地方

把 `parse_report` / `report_path` 加进工具返回值之后重跑 Ch1，**agent 的叙述一字
未变**，仍是「9 command types were successfully parsed」。

原因在 `importer/SKILL.md` 的「### 5. Report」：它给了一个**只列成功项**的摘要
模板，agent 是**忠实照做**的。数据可得 ≠ 会被说出来——这正是 CLAUDE.md 反复讲的
「转向靠 prompt/guide，不靠工具多返回一个字段」。

改掉模板（要求逐项引用 `parse_report`，并明写「只列成功项的导入摘要是错的」）后
重跑，叙述变成：

> - **Devices Imported:** 339
> - **Command Outputs:** 8,761 (2,278 parsed into structured views;
>   **6,483 stored as raw text**)
> All devices and raw outputs are now available in `netops.devices` and
> `netops.raw_output_store`.
> Full report available at: `exports/import_reports/snap_….md`

**如实记录一点**：它把 by-reason 分解与 22 台设备清单压缩掉了（模板要求列出），
但给出了完整报告路径，两者都在那份文件里。所以是**部分遵循**——对 demo 而言这个
简洁形式够用，但不能说模板被完全执行了。

三份副本都要改：`olav-netops/.olav/workspace/`、
`olav-netops/src/olav_netops/data/skillpack/.olav/workspace/`、以及根仓库的
`.olav/workspace/` 运行时镜像。前两份我手动同步，第三份由治理门抓出来
（`test_workspace_netops_ssot` + `test_skill_md_structure` + 漂移门同时报警），
再用 `scripts/workspace_drift.py --apply` 补齐。

## 5. 这份报告怎么改变 Ch2

修好之后，「刚导入了多少台设备」这类问题有了可引用的事实来源：**339 台落地、317
台有结构化数据、22 台没有，且每台的原因写在报告里**。agent 不必在两个口径之间猜，
观众也不再看到一个来历不明的 317。

Ch2 第一 beat 的另一个问题（编排器丢掉子 agent 的最终答案，同一 prompt 2/2 可复现）
与本节无关，仍未修，见 dev_docs/115 §1c / §8.4。

## 6. 遗留

- `no_parser_registered` 数量最大的那些命令（`show ip igmp snooping group`、
  `show interfaces counters` 等）说明白名单缺项。报告会把它们按量排序列出来，
  正好是「下一个该补哪个解析器」的排期依据——这是本次修改的附带收益。
- `parse_output` 的三层 tier 仍把「无模板」与「无匹配」折叠成同一个 `None`。在
  landing 层用 SSOT 反推是够用的，但把 tier 结果直接带出来会更准。
- `olav-netops/tests/` 另有 3 个文件在收集期就报错（与 dev_docs/115 §6.1 修掉的
  `test_populate_devices.py` 同类的失效路径）。本次未动，但同一类问题。
