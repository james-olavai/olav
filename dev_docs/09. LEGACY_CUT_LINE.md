## 0.1 Package Ownership Boundary

本文件定义的是 **platform-facing migration governance**，但服务的第一目标域是 NetOps。

归属划分如下：

- **属于 `olav-platform` 的职责**：authoritative source cut line、compatibility layer 退场规则、query/render/topology contract 的治理原则
- **属于 `olav-netops` 的职责**：具体网络语义视图、网络 topology ETL、OpenConfig export path、网络协议相关 compatibility 清理
- **当前仓库中的混合现实**：由于实现仍在根仓库过渡态，本文会引用现有 `src/olav/*` 路径；这些引用不代表最终包归属

详细归属总表见 `12. PLATFORM_NETOPS_OWNERSHIP_MAP.md`。

## 0. 文档目的

这份文档只回答一个问题：

> **从当前仓库的 OC-first / mapping_rules 过渡实现，如何切到 07 文档定义的新架构，而且不留下双重真相源？**

本稿是 **Legacy Cut Line** 文档，不重复解释新架构本身。
新架构定义以 `07. OPENCONFIG_SCHEMA_DESIGN.md` 为准；本稿只定义：

1. 哪些组件属于 legacy path
2. 每个 legacy path 的替代物是什么
3. 哪些路径可以短期保留，哪些必须尽快切断
4. 切断顺序、Gate、禁止事项

## 1. Cut Line 总结

### 1.1 最终目标

重构完成后，运行时只保留以下主链路：

```text
InventoryProvider
    -> raw collection
    -> value normalization only
    -> parsed_outputs.parsed_data   (raw snapshot)
    -> schema_catalog               (authoritative semantic metadata)
    -> semantic views               (query contract)
    -> topology ETL                 (relationship contract)
    -> topology_links               (graph / simulation contract)
    -> render_oc                    (export contract)
```

### 1.2 本次 Cut Line 的核心判断

以下路径属于 **必须退出主链路** 的 legacy 实现：

1. `apply_oc_mapping()` 这种写时或近写时 OC 结构投影路径
2. `mapping_rules` 作为 query / topology / render 的 authoritative source
3. `topology_engine` 直接依赖 `parsed_outputs × mapping_rules`
4. 任何把 raw snapshot 当成 canonical storage 的实现

以下组件允许作为 **短期 compatibility layer** 保留：

1. `mapping_rules` 作为由 `schema_catalog` 单向派生的缓存/桥接层
2. 仍读取 `topology_links` 的 graph / simulation 消费端
3. 仍依赖老表结构的 prompt / query 文本，但只能作为提示层，不得再反向决定 schema

## 2. 新架构的唯一真相源

为了避免长期双轨并存，先固定重构后的 authoritative source。

### 2.1 Inventory

- **Authoritative**: `InventoryProvider`
- **当前默认后端**: `.olav/config/nornir/hosts.yaml`
- **Legacy to remove**: 将 inventory 视为 `devices.csv` 或其它临时静态文件

### 2.2 Raw Data

- **Authoritative**: `parsed_outputs.parsed_data`
- **要求**: 厂商原始字段名保留，允许 value normalization，不允许 canonical rename
- **Legacy to remove**: 把 `parsed_data` 当作 OpenConfig-shaped storage

### 2.3 Semantic Mapping

- **Authoritative**: `schema_catalog`
- **Allowed compatibility**: `mapping_rules`
- **Legacy to remove**: 任何 “先写 `mapping_rules`，再反推 schema” 的流程

### 2.4 Query Contract

- **Authoritative**: semantic views
- **Allowed fallback**: raw fallback contract
- **Legacy to remove**: agent 直接把 `mapping_rules` 当查询 schema

### 2.5 Topology / Graph Contract

- **Authoritative upstream**: semantic relationship ETL
- **Shared downstream table**: `topology_links`
- **Legacy to remove**: `parsed_outputs × mapping_rules -> topology_links`

### 2.6 Render Contract

- **Authoritative input**: semantic views + `schema_catalog` metadata + raw snapshot 补充读取
- **Legacy to remove**: 依赖“已改名 parsed_data”的 render 路径

## 4. Hard Cut Line

以下四条是硬切线，不能模糊处理。

### 4.1 `parsed_outputs` 不再接受字段级改名

自 cut line 开始：

- 允许 `normalize_record()` 一类 value normalization
- 禁止任何 canonical field rename 写回 `parsed_outputs`
- 禁止把 OC-shaped dict 当成 snapshot 标准格式

### 4.2 `schema_catalog` 成为唯一 authoritative mapping source

自 cut line 开始：

- 新映射只能先写 `schema_catalog`
- `mapping_rules` 若存在，只能由 `schema_catalog` 单向派生
- 禁止 `mapping_rules -> schema_catalog` 逆向构建

### 4.3 semantic views 成为默认 query contract

自 cut line 开始：

- Query Agent 默认查询 semantic views
- raw fallback 必须显式标注 `platform`、`command`、`raw_fields`
- 禁止 raw fallback 伪装成 canonical contract

### 4.4 topology_links 的上游必须切到 semantic relationship ETL

自 cut line 开始：

- `topology_links` 继续保留
- 但上游必须来自 semantic views / relationship ETL
- 禁止继续把 `mapping_rules` 当 topology relationship 的长期真相源

## 5. 分阶段重构计划

### Phase 0: Freeze 现状边界

**目的**：先冻结哪些路径是 legacy，避免新代码继续加在旧链路上。

**动作**：

1. 在设计层声明 `mapping_rules` 为 compatibility layer
2. 在设计层声明 `apply_oc_mapping()` 不再进入主链路
3. 停止新增任何依赖 `mapping_rules` 的 query / topology / render 逻辑

**Gate**：

- 新提交不再把 `mapping_rules` 描述成 authoritative source
- 新功能不再把 OC-shaped `parsed_data` 当作输入前提

### Phase 1: 收敛 Write Path

**目的**：先把 raw snapshot 保住。

**动作**：

1. 只保留 `normalize_record()` 这类 value normalization
2. 把 `apply_oc_mapping()` 从 ingest / near-ingest 路径移出
3. 明确 `parsed_outputs.parsed_data` 保持厂商字段名

**Gate**：

- 新采集写入的数据不再依赖 OC 字段名
- 测试不再断言 snapshot 已 canonicalized

### Phase 2: 收敛 Mapping Authority

**目的**：把 “谁定义 canonical mapping” 固定下来。

**动作**：

1. `schema_mutation_service` 改为写 `schema_catalog`
2. `schema_cache` 改为从 `schema_catalog` / semantic metadata hydrate
3. `build_mapping_rules()` 降级为 compatibility generator，而不是最终目标

**Gate**：

- 新增映射规则时，authoritative store 是 `schema_catalog`
- `mapping_rules` 可清空后由 `schema_catalog` 再生

### Phase 3: 收敛 Query Contract

**目的**：让 agent 联查真正切到新架构。

**动作**：

1. 建立 semantic views 作为默认 query entrypoint
2. 修改 query prompt / schema context，不再把 `mapping_rules` 当主 schema 暴露
3. raw fallback contract 显式化

**Gate**：

- 高频跨厂商查询默认走 semantic views
- agent 回答中区分 canonical result 与 raw fallback

### Phase 4: 收敛 Topology Contract

**目的**：把 topology 从 legacy mapping 解耦。

**动作**：

1. 重写 `topology_engine`，输入改为 semantic relationship ETL
2. 固定 `relationship_type` / `link_type` taxonomy
3. 保持 `topology_links` 作为共享派生事实表

**Gate**：

- `topology_links` 的生成不再依赖 `mapping_rules`
- graph / simulation 继续消费 `topology_links`，但上游来源已切换

### Phase 5: 收敛 Render Contract

**目的**：把 SR-Linux / CAB export 路径对齐到同一 canonical vocabulary。

**动作**：

1. `render_oc()` 只消费 semantic views + `schema_catalog` metadata + raw snapshot 补充
2. 删除对“已改名 snapshot”的隐含依赖
3. 让 render 与 query 使用同一套 canonical field naming

**Gate**：

- render 不再依赖 OC-shaped `parsed_data`
- semantic query 与 OC export 的字段语义一致

### Phase 6: 退出 Compatibility Layer

**目的**：彻底切断双轨。

**动作**：

1. 删除主链路对 `mapping_rules` 的依赖
2. 删除主链路对 `apply_oc_mapping()` 的依赖
3. 保留 `mapping_rules` 仅在明确需要的导出/兼容场景，或彻底下线

**Gate**：

- 查询、拓扑、render、graph、simulation 均不再依赖 `mapping_rules`
- 删除 compatibility layer 后主流程测试仍通过

## 6. 组件级 Cut Line

### 6.1 `apply_oc_mapping()`

**判定**：退出主链路。

**原因**：

- 它把 `mapping_rules` 直接应用到 raw records
- 它输出的是 OC-shaped projection，而不是 snapshot

**允许的剩余位置**：

- 可临时保留为 export helper
- 不得再用于 ingest、query schema、topology 提取前置步骤

### 6.2 `mapping_rules`

**判定**：短期保留，长期退出 authoritative role。

**原因**：

- 当前仓库仍有多个组件依赖它
- 立即删除风险高

**硬约束**：

- 只允许 `schema_catalog -> mapping_rules`
- 禁止 `mapping_rules` 反向驱动新设计中的 schema truth

### 6.3 `schema_cache`

**判定**：~~必须改造。~~ → **Phase 2 实况：已完成迁移。**

> ⚠️ **Type A 修正 (2026-03-21)**：代码审查发现 `schema_cache.py:77-79` 的 hydrate source **已经是 `schema_catalog`**，而非本文原述的 `mapping_rules`。原"目标"已在此前版本中实现，无需 Phase 3 额外改造。

**原目标（已达成）**：

- ~~cache 的 hydrate source 改为 `schema_catalog`~~ ✅ 已实现 (`schema_cache.py:77-79`)
- 如果需要 compatibility projection，再单独派生 legacy cache 结构 — 待 Phase 3 评估是否仍需要

### 6.4 `schema_mutation_service`

**判定**：必须改造。

**目标**：

- 不再直接 upsert `mapping_rules`
- mutation target 改为 `schema_catalog` 或同级 semantic metadata store

### 6.5 `topology_engine`

**判定**：~~必须重写上游，不必删除下游表。~~ → **Phase 2 实况：上游已部分迁移。**

**保留**：

**已替换**：

- ~~`parsed_outputs × mapping_rules` 输入链路~~ → 已改为 `parsed_outputs` 直读 + vendor key 硬编码解析

## 8. 禁止事项

以下动作一律禁止：

1. 直接批量改写历史 `parsed_outputs.parsed_data` 字段名
2. 在未定义 authoritative source 前，让 `schema_catalog` 和 `mapping_rules` 长期双写
3. 让 topology、query、render 分别使用三套不同 canonical vocabulary
4. 让 raw fallback 长期替代 semantic views 成为默认查询路径
5. 用 export/render 逻辑反向定义 query contract

---

## 9. 推荐执行顺序

如果只按收益/风险排序，推荐顺序如下：

1. **先切 Write Path**
2. **再切 Mapping Authority**
3. **再切 Query Contract**
4. **再切 Topology Contract**
5. **最后切 Render Contract 与 compatibility layer**

原因很简单：

- 先保住 raw snapshot，才不会继续制造新债
- 再固定 mapping truth，才能避免 query/topology/render 各自演化
- Query contract 先切，agent 联查收益最大
- topology / render 最后切，风险更可控

---

## 10. 最终定义

可以把这份 cut line 压缩成一句话：

> **允许保留 compatibility layer，但不允许 compatibility layer 决定新架构中的事实。**

因此，真正的重构完成标准不是“旧代码还在不在”，而是：

1. old path 不再决定事实
2. new path 能独立运行
3. compatibility path 被删除后，主链路不回退
