## The architectural claim

OLAV runs on **local small models** (qwen3.6:27b on demo hardware,
7-30B in general). Such models have **strong conversational reflexes**
from RLHF training that override system-prompt rules in some
scenarios. Specifically: when asked to write/save/create an artefact,
they often respond with "Now I'll write..." text and stop, without
emitting the actual write tool_call.

The wrong reaction is to build new push-style middleware
(`IntentCompilerMiddleware`, prompt rewriters, etc.). OLAV already
has the right machinery: **memory + AutoRecall**. Memory is OLAV's
prompt programming language.

This doc records the experimental proof (Ch8, six runs) and the
operating principles that fall out of it.

## The 6-experiment matrix (Demo7 Ch8, 2026-04-28)

Same vague user prompt in every run:

```
Write a bash script to backup running-config from all routers.
Use real device names/IPs from the database. Save to exports/scripts/.
Include --dry-run + error handling.
```

| # | Backend | max_tokens | SKILL.md | Memory state | Outcome | Wall-clock |
|---|---|---|---|---|---|---|
| 1 | qwen3.6:27b | 2048 | original | clean | ❌ narrate-only | 2:51 |
| 2 | qwen3.6:27b | 2048 | original | clean (DIRECTIVE PROMPT) | ✅ 118 lines | 2:26 |
| 3 | qwen3.6:27b | **16000** | original | clean | ❌ narrate-only | 2:44 |
| 4 | qwen3.6:27b | 16000 | **strengthened** | clean | ❌ narrate-only | 1:52 |
| 5 | deepseek-v4-flash | 16000 | strengthened | clean | ✅ 126 lines | 2:52 |
| **6** | **qwen3.6:27b** | 16000 | strengthened | **directive memory + L1 precedent** | ✅ **150 lines** | 3:40 |

**Variable analysis**:

* `max_tokens` 2048→16000 (#1 vs #3): no effect. Output tokens for
  "Now I'll write..." are ~16 tokens — the cap was never hit.
  Hypothesis ruled out.
* `SKILL.md` original→strengthened "MUST emit tool_call" (#3 vs #4):
  no effect. Local 27B doesn't re-read system prompt on every turn
  with strong attention; rules buried in static context get ignored.
  Hypothesis ruled out.
* prompt vague→directive (#1 vs #2): big effect. Concrete tool name
  + key args lands. Workable workaround but pushes burden to user.
* model 27B→deepseek-v4-flash (#4 vs #5): big effect. Cloud model
  doesn't have the "narrate then stop" reflex.
* Memory state clean→**directive guide + L1 precedent** (#4 vs #6):
  **big effect on the SAME 27B**. Memory-injected via AutoRecall
  surfaces the directive AT decision time, not as background system
  context. Plus L1 captured one of #5's successful tool call —
  AutoRecall surfaces it as a concrete example.

**Conclusion**: same 27B, same prompt, same SKILL.md — only memory
state differs between #4 and #6. Memory injection is the variable
that flips the outcome.

## Why memory beats system prompt for steering small models

System prompt is **background context** — loaded once, attended to
weakly across long turns. AutoRecall-injected memories live in a
`<relevant-memories>` block **adjacent to the user query**, with
high attention weight. For local small models where attention is
the budget, **proximity to the query matters more than the strength
of the rule**.

This is why repeating "MUST emit tool_call" in SKILL.md does
nothing (#4) but the same rule injected as memory works (#6).

It also explains why the L1 capture from #5 was so impactful: a
concrete `format_and_export(data='#!/usr/bin/env bash\\n...')`
example surfaced via AutoRecall is **more imitable** than a
prose rule. Small models follow precedent better than they
follow abstract instructions.

## Operating principles

### 1. Steer behaviour via memory, not middleware

Wrong impulse: see a model fail at X → write a middleware that
intercepts and rewrites. This locks behaviour in code.

Right impulse: see a model fail at X → write a memory that says
how to do X correctly. AutoRecall takes care of injecting it
when relevant. **No new code, no new latency, customisable per
team / scope**.

### 2. L1 + L2 already do this for free

After L1 captures a successful pattern (e.g., a real `format_and_export`
call), AutoRecall surfaces it on similar future queries. Eventually
L2 generalises N samples into a higher-quality pattern. Operators
get a self-improving system without any code changes.

### 3. Directive guides are first-class artefacts

`<agent>/guides/*.guide.yaml` files ship with the wheel and are
primed into memory at `olav init` time. This is the appropriate
place for behaviour rules that aren't yet captured organically by
L1+L2 — kickstart a fresh install with the patterns you already
know matter.

The first such directive shipped 2026-04-28:
`src/olav/data/workspace/core/guides/write_class_tool_call.guide.yaml`
codifies the "must emit tool_call for write requests" rule.

### 4. SKILL.md remains the agent's API doc, not the rulebook

SKILL.md is for stable, declarative agent shape: tools, sub-agents,
delegation map. Behaviour rules — especially context-sensitive ones
that should fire only when relevant — belong in memory.

Avoid the urge to bury behaviour rules deep in SKILL.md. They will
not get attention they need at decision time on local models.

## Implications for the OLAV → enterprise path

The "memory is the programming language" claim has real product
implications:

* **Per-team customisation** = adding directive memories. No
  source code fork needed. Customer A says "always validate
  IP plan before save_profile" → write a guide, ship it, done.
* **Compliance / governance** = memory-level allow/deny
  guidance. Customer B requires "all writes go through a 4-eye
  review" → directive memory + retry middleware (lightweight
  enforcement layer).
* **Cross-team learning** (the L3 layer of agentic memory growth) =
  aggregating L1 captures across deployments. The data
  infrastructure (LanceDB scopes + memory categories) is in place;
  what's missing is the federation layer — a real enterprise
  differentiator.

The pattern: **OLAV core stays open, memory ecosystem becomes the
business**. Small open source platform + paid memory bundles for
verticals (telco, fintech, healthcare).

## What this does NOT solve

Memory injection works because AutoRecall surfaces relevant entries.
For this to work, the user's query must embed close enough to the
directive's keywords. Edge cases:

* Brand-new tasks with no precedent and no directive — still fail.
* Highly specific domain language that doesn't match general keywords
  — directive may not be retrieved.
* Queries that L1 has captured many similar prior queries for —
  the prior captures may out-rank the directive (saw this in Ch8
  setup).

These are real limits, but they shrink as L1 keeps capturing and
the operator keeps adding directives. **Tail behaviour, not common
behaviour**.

## Implementation summary (2026-04-28)

* `src/olav/data/workspace/core/guides/write_class_tool_call.guide.yaml` —
  directive guide, ships with wheel, primed at olav init
* L1 + L2 (already shipped) provide self-reinforcing precedent
  capture — every successful tool call becomes future training data
  via memory
* No new middleware required. No new agent. No new tool.

This is the leanest possible architectural fix for the "local small
model conversational reflex" problem. Cost: 1 YAML file (84 lines).
Effect: same 27B succeeds on Ch8 vague prompt (150-line bash output).

## Decision log

* **Reject** new `IntentCompilerMiddleware` / prompt-rewriter middleware:
  duplicates AutoRecall's job, adds engineering surface, lacks
  per-team customisation.
* **Reject** retry-on-no-tool-call middleware (B path): adds latency,
  reactive not proactive, doesn't compose with team customisation.
* **Reject** model routing (C path): not needed if memory works for
  local models.
* **Accept** memory-as-prompt-language: 1 YAML, 0 new code, same
  pattern as existing L1+L2 + usage_guide system.
