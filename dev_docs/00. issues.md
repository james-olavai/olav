### ISSUE-T3-01-RELOAD-CONFIGLOADER-SINGLETON

**状态**: ✅ Fixed in `src/olav/api/server.py`
**发现日期**: 2026-04-14
**修复日期**: 2026-04-14
**类型**: P2 — 平台 bug

`POST /reload` 只重置了 `_agent_instance`，未重置 `ConfigLoader` 单例。`ConfigLoader._loaded = True` 导致后续请求始终读取首次加载的配置快照。写入 `api.json`（例如修改 `auth.mode`）后调用 `/reload` 不会生效，必须重启服务才能应用更改。

**影响**：`/reload` 的 config 热重载功能完全失效，包括 auth.mode、llm、embedding 等所有配置项。

**Fix**: 在 `reload_agent()` 中加入 `ConfigLoader._loaded = False; ConfigLoader._instance = None`，使下次请求重新从磁盘读取 `api.json`。

### ISSUE-T1-01-PID-REUSE-RACE


**状态**: ✅ Fixed in `src/olav/cli/commands/services/web.py`
**发现日期**: 2026-04-14
**修复日期**: 2026-04-14
**类型**: P2 — 平台 bug

`WebService._is_running()` used `os.kill(pid, 0)` which only confirms a PID exists in the process table — not that it is our uvicorn process. When killed externally, the stale PID file was left behind. If the old PID was reused by another OS process before the next `start()` call, `_is_running()` returned `True` → uvicorn never spawned → port 2280 empty.

**Fix**: Added `_is_our_process(pid)` module-level helper that reads `/proc/<pid>/cmdline` (Linux) or `ps -p` (macOS) and checks for `"uvicorn"` or `"olav.api.server"`. Updated `_is_running()` to call it after `os.kill(pid, 0)` succeeds — if the process identity check fails, the stale PID file is deleted and `False` is returned. Returns `True` conservatively when identity cannot be determined (e.g. PermissionError) to avoid accidental double-starts.

### ISSUE-A9-SAFETENSORS-SHARD-NOISE — Gitea #2

**状态**: ✅ Fixed (v0.18.0-post) — noise 来自 fd2 (stderr)，全部三处均改为同时重定向 fd1+fd2
**发现日期**: 2026-04-13 / **修复日期**: 2026-04-16
**Gitea**: http://192.168.100.50:3000/admin/olav/issues/2

`safetensors` 库在模型加载时通过 C-level **stderr (fd2)** 打印 "The following layers were not sharded"。之前所有修复仅重定向 fd1，噪音仍从 fd2 漏出。Tier 0 `INIT_LOG=$($OLAV init 2>&1)` 捕获 stderr，导致 A9 WARN。

**根因:** 需在 `init.py`、`router.py`、`embedder.py` 三处同时 dup2 fd1 **和** fd2：
```python
_saved1 = os.dup(1); _saved2 = os.dup(2)
_null = os.open(os.devnull, os.O_WRONLY)
os.dup2(_null, 1); os.dup2(_null, 2)
try:
    SentenceTransformer(model, ...)  # or HuggingFaceEmbeddings(...)
finally:
    os.dup2(_saved1, 1); os.dup2(_saved2, 2)
    os.close(_null); os.close(_saved1); os.close(_saved2)
```
**CI 影响:** Tier 0 A9 WARN → PASS；Tier 0 32/32 clean。

### ISSUE-P2-LLM-OUTPUT-TRUNCATION — Gitea #4

**状态**: ✅ Fixed (v0.18.0-post) — `db_query/SKILL.md` Output Rules 节已添加；LLM 遵从度取决于模型，待 T2-11 LLM 环境验证
**发现日期**: 2026-04-16 / **修复日期**: 2026-04-16
**Gitea**: http://192.168.100.50:3000/admin/olav/issues/4

**普遍性分析:** 这不仅仅是 "列出所有设备" 的问题。LLM 对所有 `execute_sql` 多行结果都倾向于摘要而非完整展示：

| 查询 | 工具返回 | LLM 实际输出 |
|---|---|---|
| 列出所有设备 | 6 行完整数据 | 只列出 ~3 个设备名 |
| 所有接口状态 | 30+ 行接口数据 | 可能只列 "down" 的几个 |
| BGP 邻居列表 | N 行邻居状态 | 可能只列 "not established" 的 |
| 拓扑链接 | 11 行链接 | 可能只列代表性的几条 |

**根因:** `execute_sql` 已返回完整数据到 LLM context（6 行 < `MAX_ROWS_TO_CONTEXT=20`，无截断）。问题在 LLM 输出行为层——它选择摘要而非逐行列出。

**修复方案（prompt 层）:** 在 `src/olav/data/workspace/core/db_query/SKILL.md` body 添加 Output Rules：
```markdown
## Output Rules

1. When user asks to **list/enumerate/列出**, display **ALL rows** — do not summarize or truncate.
2. Format tabular data as Markdown tables with column headers.
3. If result >50 rows, show first 20 and note total count + exported CSV path.
4. Always include row count: "共 N 条记录".
```

同时在 `core/prompts/system.md` Tool Selection 段添加全局规则：
> When execute_sql returns data, present ALL rows unless the user explicitly asks for a summary.

**风险:** LLM 模型遵从度不同。grok-4.1-fast 对 prompt 指令遵从度低，Claude/GPT-4o 可能更好。这是平台级问题，需要持续跟踪。
**CI 影响:** Tier 2 T2-11 WARN → PASS（取决于 LLM 遵从度）。
