# R-AGENT-VERTICAL-SLICE — 把分析能力按意图切成窄 sub-agent

**Status:** proposed (2026-05-09)
**Predecessor:** dev_docs/69. AGENT_HIERARCHY_REFACTOR.md (Phase A-D 已完成)
**Driver:** gemma4:31b nothink 工具选择幻觉 / analyze 工具数量 vs 可靠性 tradeoff

## 起因

R-AGENT-HIERARCHY Phase D 落地后，analyze 走 inspector 模式（5 个 inspect_*
@tool + format_and_export），drift 测试 E2E PASS。但生产级审计暴露问题：

1. `inspect_blast_radius` 静默 false positive（不存在的 link 返回 "fully connected"）
2. drift 报告 root cause 段是 LLM 自由发挥，无 evidence 链接
3. 完全缺失日志/syslog/SQL 钻取能力 —— 故障分析 50% 工作量在日志里
4. 复杂场景（路径仿真 / 路由策略 / ECMP）完全空白

把缺口工具加回去会把 analyze 推到 8-10 工具 —— gemma4 nothink 经验值
> 9 工具进入"中危区"，工具选择错误率 10-20%。

## 核心 insight

**orchestrator 已经是路由模型**（Patch D' Step 2.5 之后只有
`recall_memory` + `web_search` + `task` 三个工具）。它本来就该承担
"问什么 → 找谁"决策。**让 orchestrator 在意图层路由，sub-agent 只
专注一件事**，每个 sub-agent 工具数 ≤ 6 永远不进危险区。

设计原则：
- orchestrator 知道 sub-agent **能力描述**（capability），**不知道**
  sub-agent 内部用哪些工具
- 每个 sub-agent SKILL.md 写清能力边界 + 单一 workflow
- 跨域查询（drift + 日志查变化设备）由 orchestrator 串
  `task("diff", ...) → task("investigate", ...)`

## 提议架构

```
netops/                    orchestrator（intent 层路由）
├── inspect/               能力：状态/拓扑/路由 Q&A          3 工具
│   inspect_devices, inspect_topology, inspect_routing
├── whatif/                能力：故障 what-if reachability  1 工具
│   inspect_blast_radius (with 存在性校验)
├── diff/                  能力：snapshot 对比               1 工具
│   analyze_drift (thick analyzer, 跨源验证)
├── investigate/           能力：日志/证据钻取               1 工具
│   query_evidence (syslog/command_output/config 三合一)
├── sim/                   能力：变更规划                    5 工具（不变）
│   4 inspector + submit_change_plan
├── lab/                   不变
├── collect/               不变
├── topology/              不变
└── learner/               不变
```

每个新 sub-agent 工具数：1-3，远低于 9 工具危险区。

## orchestrator 决策表

netops/prompts/orchestrator.md 加 dispatch table，配合 intent-keyed
memory（Patch J 验证有效）：

| 用户意图 | 路由到 |
|---|---|
| 设备/拓扑/状态查询 | inspect |
| 故障影响 / what-if | whatif |
| 快照对比 / drift report | diff |
| 故障定位 / 日志 / 为什么 | investigate |
| 变更方案 / CAB | sim |
| 拓扑发现 / LLDP/CDP | topology |
| 命令解析学习 | learner |
| 实验环境 | lab |
| CLI 采集 | collect |

orchestrator 只看用户问题的 intent 词，不需要知道
"inspect_drift_topology vs inspect_drift_routing 怎么选"。

## 与 dev_docs/69 Phase A 的关系

dev_docs/69 把 7 个顶层 agent 折成 3 个 orchestrator + sub-agents

sub-agent（**纵向切分继续**）。同一原则：每 agent 一件事。

**Step 1（试点 — 这周做）**：拆 `investigate` 出来

- 报告类输出（drift-*.md / fault-*.md）frontmatter 必须含

## 实现细节

### investigate sub-agent（Step 1）

```
netops/investigate/
├── SKILL.md
├── prompts/system.md       — 一个 workflow：根据问题选 source 调 query_evidence
└── tools/
    └── query_evidence.py   — Literal["syslog","command_output","config"]
```

`query_evidence` 内部分发：
- `source=syslog` → 查 syslog 表，按 device + time_range + pattern 过滤
- `source=command_output` → 查 `parsed_outputs` / `raw_output_store`，按 device + command
- `source=config` → 查 raw running-config 文本，按 pattern grep

返回 `{matches: [{timestamp, device, source_table, content}], total, truncated}`。

### orchestrator capability description（关键设计点）

netops/prompts/orchestrator.md 描述 sub-agent 时**只写能力边界**：

```
## Sub-agents

### investigate
Use when user asks: 为什么/why/故障定位/log/syslog/查看输出/具体内容
Investigate questions about *what's recorded* (events, errors, command
outputs, config snippets). Returns matched lines with timestamps.

### diff
Use when user asks: 对比/drift/什么变了/差异/between snapshots
Compares two snapshots and returns structured findings with evidence.

### inspect
Use when user asks: 拓扑/邻居/状态/BGP up/OSPF/AS号/loopback
Returns current state of devices/links/sessions.

### whatif
Use when user asks: 故障/down/挂了/影响/blast radius
Simulates failure and returns reachability impact.

### sim
Use when user asks: 计划变更/添加 BGP/CAB/change plan
Designs change implementation, emits TCF spec.
```

**不出现工具名。** orchestrator 只看意图分类。

### 跨域多步查询

orchestrator system.md 加一条 workflow：

```
## Multi-hop workflows

If user asks something that spans capabilities, chain task() calls:
- "drift + 给我看变化的设备的日志":
  1. task("diff", ...) → 拿 findings
  2. 从 findings 提变化的 device names
  3. task("investigate", ...) for each device
- "故障设备 + 影响范围":
  1. task("investigate", ...) → 找出 down 的设备
  2. task("whatif", remove_devices=[...])
```

## Risks

| Risk | 应对 |
|---|---|
| orchestrator 拿不准 intent，路由错 | dispatch table 用关键词清晰分割；intent-keyed memory guide 兜底 |
| 跨域查询信息丢失（task() 间） | orchestrator system.md 显式教 multi-hop workflow |
| sub-agent 数量膨胀维护成本 | 每个 sub-agent ≤ 200 行 SKILL.md + 1 个工具，单点维护 |
| 与现有 analyze 共存期路由冲突 | Step 1 期 analyze 维持现状，investigate 仅承接 *新增* 日志意图 |

### 16 条架构原则确立

详见 ADR-0009。摘要：

1. Tool data quality > tool count > prompt eng
2. Surface every silent drop
3. Decode every overloaded field
4. Uniform error envelope
5. Hard constraint > soft template
6. Capability-level routing
7. Hybrid thinking (orch on, sub-agent off)
8. Vendor 兼容性在 view 层
9. Reparse without recollect
10. Circuit breaker on transient failures
11. Write-time denormalisation of known dimensions
12. Empty input = discovery mode
13. Prompt-only adherence breaks at long contexts on small models
14. Memory-driven workflows + auto-generated environment context
15. Empty results carry steering hints
16. Per-tool dedup at the source

### 仍未解决（accept as known limits）

1. **Long context rule decay** — gemma4:31b 在 30+ tool 调用后
   prompt 规则遵守率下降。已通过工具层的硬约束（dedup budget）
   + 记忆层的 intent-keyed guide 缓解，但根本上是模型容量限制。
2. **R1/R2 的 interface IP peers** — `10.1.12.1`/`10.1.12.2`
   仍 resolved=false（point-to-point eBGP 用接口 IP 而非 loopback）。
   需要在 build_device_facts 加 interface→hostname 反查。
3. **Sub-agent 嵌套 orchestration** — 子 agent 内部不能 task()
   到其他子 agent。CAB sim→lab 仍依赖用户手动切。HITL 设计有意
   如此，不是 bug。

### 关键洞察（为何这次 session 工作量超预期）

R-VERTICAL-SLICE 原计划只是把 analyze 拆成 4 个窄 sub-agent。
但 Phase 0 hybrid-thinking 金丝雀触发的连锁发现：

- inspect_routing silent drop → 揭露 R1 facts gap
- 修 facts → 揭露 Junos textfsm bug
- 修 textfsm → 揭露 reparse 缺失
- 加 reparse → 揭露 cross-vendor view 缺失
- 加 view → 揭露 nornir 配置路径错误
- 修配置 → 揭露 diff_configs 走 filesystem 而非 DB
- 修 diff_configs → 揭露 platform 反范式化机会
- 加 platform 列 → 揭露 LLM 鬼打墙模式
- 加 budget → 揭露 scope guard 缺失
- 加 scope guard → 整套质量管道闭环

每个发现都是上一个修复的副产物。这印证了 16 条原则中的第 1 条：
**Tool data quality is the highest-ROI investment** — 修一个数据
质量 bug 揭露下一个，连锁改进比独立特性开发收益高 10×。

## Empirical findings

### Phase 0 canary (2026-05-09)

ChatOllama 0.4 + gemma4:31b：thinking 模式产出干净 tool call，无
`<think>` 污染 content。延迟代价 ~9× (1.1s vs 9.6s)。task #277
的旧 bug 已被上游修复。

### Hybrid thinking E2E test (2026-05-09)

setup：netops orchestrator `thinking_mode: enabled`，所有 sub-agent
`thinking_mode: disabled`。

prompt：「R3 看起来 BGP 有问题，帮我诊断 — 检查现状并查日志中相关事件」。

**机制验证 PASS：**
- ✓ 两种 mode 在同一 graph 中共存，无 LangChain 报错
- ✓ orchestrator 用 think，sub-agent 用 no-think
- ✓ `task("investigate", ...)` 正确路由
- ✓ investigate sub-agent 4 次 `query_evidence` 智能 pattern 变体
- ✓ 输出真实发现（R3 与 1.1.1.1 peering 但 0 prefixes，物理连 R1 但没 BGP）

**架构合规 FAIL：**
- ✗ orchestrator 跳过 `write_todos`，没按模板规划
- ✗ orchestrator 直接 `execute_sql` 15 次，绕过 `task("analyze", ...)`
- ✗ 多次重复查询（R3 BGP 查 4 次，R1 BGP 查 2 次）— 小模型 thinking
  的"过度推理"失败模式
- ✗ 总耗时 ~7 分钟（15 次 execute_sql × ~10s thinking + 4 次 query_evidence）

**关键洞察：**

thinking-on 让 orchestrator **同时获得规划能力和过度推理倾向**。它能
做出"用 execute_sql 比 task('analyze') 更便宜"的合理判断，但也会
重复查询同一个东西多次。

模板"如果是简单 Q&A 跳过 write_todos"被 orchestrator 当成绕过 todos
的借口 —— 它把"诊断 BGP 故障"判定为"简单"。

### 后续调整方向

1. **强制 write_todos 触发** — 检测 multi-capability 意图（"诊断/为什么
   /分析"等触发词），中间件强制第一步写 todos
2. **限制 execute_sql 在 orchestrator 中的使用** — 改成"仅设备名查询"
   单一场景（已在 prompts/orchestrator.md 注明，但 thinking-on 时 LLM
   忽略）。考虑工具白名单移除 execute_sql，强制走 task("analyze")
3. **dispatch table 严格化** — 当前"BGP/routing 读侧 → task('analyze')"
   在 orchestrator 选择直接 SQL 时未触发；可在 orchestrator system.md
   加 "MUST delegate state queries to task(), DO NOT execute_sql for
   any field other than `hostname`"

|---|---|---|---|
| 总 tool 调用 | 18 | 27（kill at 8min） | 20 |

进行。这是 thinking-on 把"我应该再确认下"的倾向放大到病态。

### 硬约束 #1 验证（移除 orchestrator execute_sql）

更改：netops/AGENT.md `tools:` 删 `execute_sql`，
prompts/orchestrator.md 的 "Schema cheatsheet" / "Required-info
check" 段落删除，dispatch 表 "Device info → execute_sql" 改为
"task('analyze')"。

效果：
- ✓ orchestrator 0 次 execute_sql 调用
- ✓ 4 次 `task()` 全部正确路由（analyze + investigate + 2 重试）
- ✓ 找到真问题（BGP 控制面完全不活动 + 物理连接正常）
- ◯ 仍有过度推理（4 次 task() 中后 2 次是确认重试），但已大幅降低
- ✗ 仍未触发 write_todos（template 软约束被 thinking-on 绕过）

**约束 #1 PASS。** 工具白名单是抑制鬼打墙最有效的硬约束 ——
小模型不会对不存在的工具产生幻觉。
