# 102. Declarative Cross-Subagent Workflows — Design & Rollout Plan

**Status:** change_plan workflow LIVE (2026-07-19, demo-verified 2/2);
rollout phases below in progress.
**Owner:** platform (`src/olav/agents/workflows.py`) + each domain's
`workflows/*.workflow.yaml`.

---

## 1. What this is

Known-shape multi-step tasks (draft → verify → formally validate) are
declared as **YAML data** under `<agent_dir>/workflows/*.workflow.yaml` and
rendered deterministically into the domain orchestrator's system prompt.
The orchestrator (LLM) executes the declared `task()` sequence; artifacts
travel between steps **by file path / snapshot ID only** — never by pasting
content (R88: small models lose payload round-trips).

This deliberately extends the thin-router doctrine (ADR-0003/0005/0006)
rather than repealing it: free-form intents still single-route; only
declared, schema-validated sequences orchestrate. Control flow is
prompt-level (the one LLM-trusting part); everything that made it reliable
is code:

| Layer | Mechanism | Kind |
|---|---|---|
| Sequence declaration | `*.workflow.yaml` → `render_workflows_section()` | data + deterministic render |
| Delegation | deepagents `task` | code |
| Artifact passing | file paths + real-FS scripts (`read_change_plan`) | code (subprocess; deepagents `read_file` sees only the virtual FS!) |
| Runaway protection | `ToolLoopBreakerMiddleware` (3× short-circuit / 6× hard stop) | code |
| Arg-shape hygiene | coercion layers (batfish_q FQDN→short retry, headers Pydantic) | code |
| Verification | reporter Mode V (light) + simulator/Batfish (formal) + deterministic graders | code + prompt |

Schema, loader semantics (never-raise, skip-on-invalid, undeclared-step-agent
→ skip), and renderer live in `src/olav/agents/workflows.py`; injection at
`OLAVAgent._get_orchestrator_prompt` step ④. Tests:
`tests/unit/test_agent_workflows.py`.

## 2. Selection criteria (from the 2026-07-18/19 experiment series)

A task qualifies iff:
1. **Known shape** — fixed 2-4 step sequence; no LLM planning required.
2. **Artifact by reference** — steps exchange a path / snapshot_id / profile
   name, each step's deliverable lands on disk.
3. **Per-step boundedness** — every step is an existing sub-agent's bounded
   job (its own budget rules apply).
4. **Real-ops meaning** — the sequence mirrors an actual operational process
   (change management, audit lifecycle, onboarding).
5. **Explicit per-step output contract** (Phase 2 lesson) — every step agent
   must emit a machine-extractable artifact reference (analyzer names the
   plan path natively; audit-author needed an explicit `PROFILE_PATH:`
   final-line rule). Verify BEFORE writing the YAML, not after the first
   broken run.
6. **Orchestrator hard-rule audit** (Phase 2 lesson) — a mature
   orchestrator's existing terminating rules (e.g. "sub-agent reply IS the
   final answer" passthrough) will WIN against an injected workflow. If the
   domain orchestrator has such rules, either the composition isn't worth
   the conflict, or the rules must be restructured — a bolt-on exception
   clause was measured insufficient (0/3).

Anti-patterns (stay single-route): open-ended exploration (explorer),
self-contained loops (learner's parser sandbox), cross-domain compositions
(task() cannot reach another domain's sub-agents — that would be a top-level
orchestration feature, a separate ADR-sized decision).

Evidence base for "why not free-form LLM orchestration": 8-run Ch4 series —
prose/guide steering peaked at ~33% tool-adoption with arg corruption
(V2 §M3 confirmed); the deterministic scaffolding above took the same model
to 2/2 end-to-end.

### Phase 2 — `audit_profile_lifecycle` — VALIDATED THEN WITHDRAWN (2026-07-19)
audit-author → audit-runner (artifact: profile path). Ran 3 exploratory
rounds; **workflow behavior 0/3** — the orchestrator always stopped after
step 1, even after (a) the `PROFILE_PATH:` output contract landed and was
honored by the author, and (b) a passthrough-exception clause was added.
Root causes and outcome:
- **Platform generality: PROVEN.** Injection rendered correctly for the
  audit agent dir (verified directly); all failures were domain-content,
  not platform.
- **The audit orchestrator's mature "sub-agent reply IS the final answer"
  passthrough hard-rule wins** over injected workflow prose (criterion 6
  above was written from this).
- **Operational value was low anyway**: authoring a profile is a setup-time
  act, running it is recurring — the two are naturally separate; the
  composition saved one command, rarely.
- **Withdrawn**: workflow YAML removed; passthrough rule restored to its
  pure form. **Kept** (independent wins): audit orchestrator
  `deterministic_synthesis_grader` (top-level flag — nested `metadata:`
  placement is the dev_docs/97 trap and was hit again here) and the
  author's `PROFILE_PATH:` output contract (composability groundwork).
Regression pin: `test_audit_domain_ships_no_workflows`.

## 4. Constraints & future work

- **Prompt tax**: each rendered workflow ≈ 30-40 lines in the domain
  orchestrator's prompt. Cap: **≤2-3 per domain**. Beyond that, implement
  intent-lazy injection (render only the trigger-matched workflow — the
  loader already parses `trigger`; match at prompt-build or before_model).
- **Python pipeline runner** (option B fallback): the same YAML is designed
  to be executable by a deterministic runner if LLM sequencing proves
  unstable for some domain/model tier. Do not write a second declaration
  format.
- **Per-workflow test protocol** (from CLAUDE.md N≥3 rule): 1 exploratory
  run reading the full trace (audit `run_id` grouping), then ≥3 runs judged
  by audit-log criteria, then done. A single green run is not signal.
- Related open issue: ISSUE-CAPTURE-TRANSIENT-FACTS (dev_docs/00) — repeated
  workflow runs amplify transient-fact memory pollution until capture
  filtering lands; purge `cap-*` path/interface facts between test batches.
