# 107. Presales Bid-Grade HLD/LLD — Requirement-Traceable, Provenance-Cited Documents

**Status:** design (2026-07-23). **Extends** dev_docs/98 (architect HLD/LLD),
dev_docs/100 (presales domain), dev_docs/104 (analyst), dev_docs/106
(validation-driven LLD). **Does not reopen** the retire-runbook decision
(dev_docs/106 Option A) — see §11.

---

## 1. Problem: the current output is a parameter dump, not a bid response

The LLD the pipeline emits today (`exports/designs/*/LLD_*.md`) is, verbatim, an
**addressing worksheet**:

```
## IP Allocation … | spine-01 | 10.0.255.1/32 |
## Routing Design  … | spine-01 | 65000 | 10.0.0.0 | leaf-01 | 65001 | 10.0.0.1 |
## Interface Specification …
## Risks — AS/IP overlap; cabling must match.
```

Held against a real bid submission, every load-bearing element is missing:

| Missing | Consequence |
|---|---|
| Any mention of the tender / customer | **Zero response** — the document answers no clause of the RFP. |
| Real product models (it says `spine-01`, not `Nexus 9336C-FX2`) | No BOM; the bidder cannot even price it. |
| "Why 2 spine / 4 leaf" | No capacity justification, no sizing defence. |
| Design rationale / trade-offs | Reads as a config export, not an engineering argument. |
| Security / segmentation / QoS / migration / assumptions | Only two boilerplate risk bullets. |
| Provenance on any statement | Nothing is defensible in a bid-defence meeting. |

The HLD side is better — `propose_structure` (dev_docs/100 §5.4) gives a
profile-driven chapter skeleton with a readiness gate — but it stops at
**dimension level**: it checks whether the tender *mentioned* ~8 coarse topics
(sites / transport / routing / qos / …), not whether the document *responds to
each clause* of the RFP. There is no first-class **compliance response matrix**,
and chapter prose is written free-hand with no grounding or coverage check.

### 1.1 Root cause — only Level-1 of a three-level requirement model exists

```
Level 1  Dimensions          ~8 coarse topics; readiness gate.        ← HAVE (requirements table)
         (sites, transport…)  "Did the customer tell us enough to design?"

Level 2  Requirement register Every RFP clause = one row               ← MISSING
         (clause 3.2.1 …)      (verbatim text, category, mandatory, page). 50–200 rows.

Level 3  Response matrix       Per clause: compliance verdict +         ← MISSING
                               response narrative + evidence + §ref.
                               THIS is the artifact evaluators score.
```

A bid is won or lost on the Level-3 matrix. The whole of this design is: **build
Levels 2 and 3, ground every statement in provenance, and let a deterministic
grader guarantee coverage — then organise the HLD/LLD around the response, not
around a generic template.**

## 2. What "bid-grade" requires

A submittable HLD/LLD carries these first-class artifacts (all currently absent):

1. **Requirement-response / compliance matrix** — the spine. One row per RFP
   clause: `clause text | compliance (Comply / Partial / Alternative / Non-comply)
   | how we meet it (narrative) | evidence (model/spec/calc) | HLD/LLD §ref`.
2. **Bill of Materials (BOM)** — model × qty × role, cross-referenced to
   datasheets. Deterministically derived from the selection + topology.
3. **Capacity / sizing justification** — *why* this model, this count, this
   topology — bound to a requirement and a computed number (oversubscription
   calc already grounded, `olav_kb/presales/references/oversubscription_calculation.md`).
4. **Narrative design rationale** — design philosophy, alternatives considered,
   the argument for the chosen approach.
5. **Substantive** security / segmentation / QoS / migration / risk / assumption
   / dependency / exclusion sections — not boilerplate.
6. **Per-statement verifiability** — no placeholders; every assertion cites a
   source (§4).

## 3. Production model: deterministic spine + constrained LLM narrative + deterministic grader

The reconciliation of "we need real prose" with OLAV's deterministic-first,
small-model-first discipline:

- **Python owns the spine, the facts, and the coverage gate.** The requirement
  register (L2), the response-matrix scaffold (L3 — every clause forced to a
  row), the computed numbers (addressing, capacity, oversubscription), the BOM,
  and the cross-references. Python **guarantees every clause has a response and
  every number has a source** — the LLM cannot silently drop a requirement or
  invent a spec.
- **The LLM fills bounded, pre-grounded narrative slots.** For each slot it is
  handed `(clause verbatim + chosen model & its datasheet spec + the computed
  number + the design decision & its rationale)` and asked to write the
  *justification prose*. This is **"explain these established facts", not "design
  from scratch"** — the bounded task small/mid models do reliably (the WHAT-not-
  HOW lesson; the `generate_change_plan` reliability pattern).
- **A deterministic document grader (zero-LLM) verifies the result** — coverage,
  citation resolvability, no placeholders, catalog reality, number traceability,
  required diagrams. Same philosophy as the `selection_report` completeness
  contract and `DeterministicSynthesisMiddleware`: *prose quality is the LLM's
  job; whether we actually responded to every clause and grounded every claim is
  Python's job.*

> One line: **the LLM writes the sentences; Python owns whether they answer the
> tender and whether they are made up.**

## 4. The provenance / citation contract (load-bearing)

> Requirement (2026-07-23): the HLD/LLD narrative must be **factual, never
> hand-waved** — every statement must point at *which tender clause it responds
> to, which document is the design basis, which meeting/decision settled it.*

This is grounding taken to its end state: **every claim-bearing sentence carries
at least one resolvable citation.** The backing infrastructure already exists in
schema (it was designed, never enforced or assembled):

```
documents            source docs, Docling-ingested, page_provenance JSON, sha256,
(RFP, datasheet,     supersede chain, expires_at.            ← "which document"
 standard, minutes)          │
                             ▼  extracted snippet
design_evidence      source_file + source_type + content + relevant_chapters.
                             │
                             ▼  decision that used it
design_decisions     decision + rationale + source_type + source_ref(→evidence_id)
                     + chapter.                              ← "which meeting/decision"
requirement_items    verbatim RFP clause + page + mandatory. ← "which tender clause"  (NEW §5)
```

### 4.1 Citation markers

Narrative slots emit inline markers; Python resolves them against the DB:

| Marker | Resolves to | Answers |
|---|---|---|
| `[R:item-…]` | `requirement_items` row | which tender clause this responds to |
| `[D:dec-…]` | `design_decisions` row (carries rationale + source_ref) | which decision / meeting settled it |
| `[E:ev-…]` | `design_evidence` row | the extracted evidence |
| `[Doc:document_id#p12]` | `documents` row + page | the source document (datasheet / RFC / standard) |
| `[Spec:model]` | `device_catalog.yaml` entry (`spec_source` datasheet URL) | the datasheet a number came from |
| `[Calc:name]` | a computed result in the run (oversub / allocation) | a computed, not invented, number |

The LLM **never mints an ID** — it is handed the valid IDs for its slot and may
only cite from that set. The grader (§8) fails the document on any **dangling**
citation or any claim-bearing paragraph with **zero** citations.

### 4.2 Consequence: `source_type` becomes an enumerated provenance kind

`design_decisions.source_type` / `design_evidence.source_type` are typed:
`rfp_clause | datasheet | standard(rfc/ieee) | meeting | customer_statement |
site_survey | engineer_judgement`. `engineer_judgement` is *allowed but flagged*
— the grader lists every judgement-only decision so the reviewer sees exactly
which statements rest on the engineer, not on a document.

## 5. Data-model changes (reuse first)

Existing tables carry most of it. Two new tables + a few columns:

### 5.1 NEW `requirement_items` — clause-level register (Level 2)

Keeps `requirements` (dimension readiness gate — already wired into
`propose_structure`) intact; adds the clause register beside it.

```
requirement_items:
  item_id          VARCHAR NOT NULL     # req-<hash12>
  project_id       VARCHAR NOT NULL
  source_document_id VARCHAR            # → documents.document_id
  source_page      INTEGER              # page_provenance
  clause_ref       VARCHAR              # "3.2.1" (as printed in the RFP)
  text             VARCHAR NOT NULL     # verbatim clause
  category         VARCHAR              # maps to the dimension taxonomy
  mandatory        BOOLEAN              # "shall/must" vs "should/may"
  priority         VARCHAR              # critical / important / nice_to_have
  status           VARCHAR              # extracted / confirmed (HITL) / waived
  extracted_by     VARCHAR              # tier / model
  confidence       DOUBLE
  conflict_key = [item_id]
```

### 5.2 NEW `requirement_responses` — the matrix (Level 3), keyed per run

```
requirement_responses:
  response_id      VARCHAR NOT NULL
  item_id          VARCHAR NOT NULL     # → requirement_items
  project_id       VARCHAR NOT NULL
  run_id           VARCHAR              # HLD/LLD run this response belongs to
  compliance       VARCHAR NOT NULL     # comply / partial / alternative / non_comply
  narrative        VARCHAR              # "how we meet it" (LLM, cited)
  decision_ids     VARCHAR[]            # design_decisions backing it
  evidence_ids     VARCHAR[]            # design_evidence backing it
  section_ref      VARCHAR              # HLD/LLD chapter id that details it
  status           VARCHAR              # draft / approved
  conflict_key = [response_id]  # (item_id, run_id) unique in practice
```

### 5.3 BOM — derived, not stored (MVP)

`topology_nodes` already carries `vendor/model/role`; `device_catalog.yaml`
carries datasheet specs + `spec_source`. `generate_bom(project_id)` groups nodes
by `(role, vendor, model)`, counts qty, joins the datasheet spec + source URL —
**no new table**. (Optional `bom` snapshot table deferred until a run needs a
frozen priced BOM.)

### 5.4 No destructive migration

presales is unreleased → new tables/columns land via `ensure_schema`
(CREATE IF NOT EXISTS). Dev DBs predating this need a one-line `ALTER … ADD
COLUMN IF NOT EXISTS` at setup (the Schema-On-Read rule; §106 precedent).

## 6. The three new artifacts

### 6.1 `generate_compliance_matrix(project_id, run_id)` — fat tool, deterministic assembly + coverage gate

Reads `requirement_items` + `requirement_responses`, emits the matrix markdown,
and **returns a coverage report**: every mandatory item **must** have a response
row with a non-empty verdict + narrative + section_ref; unresponded mandatory
clauses are returned as a hard `open` list (and rendered **flagged**, never
silently omitted — the `select_devices` "auditable, not silent" rule). This is
the completeness contract, at document scope.

### 6.2 `generate_bom(project_id)` — deterministic

`topology_nodes` × `device_catalog.yaml` → BOM table with `[Spec:model]`
citations. Zero LLM.

### 6.3 Capacity justification — deterministic calc, LLM explains

`compute_sizing(requirements, skeleton)` (grounded by
`oversubscription_calculation.md`, RFC 7938) produces the numbers (leaf/spine
count, uplink count, oversub ratio, port budget) → a `[Calc:…]`-citable result.
The narrative slot explains *why the number satisfies the clause*, citing the
clause `[R:…]` and the calc `[Calc:…]`.

## 7. HLD/LLD restructure

### 7.1 LLD: addressing tables become an appendix

`lld_doc.py`'s current output (IP/BGP/interface tables) is **demoted to
Appendix A "Addressing & Interface Plan"**. The LLD *body* becomes:

1. Purpose & scope (cites the RFP clauses it fulfils).
2. Design overview + rationale (narrative, cited).
3. Per-subsystem detailed design (routing policy, segmentation, QoS, HA) —
   narrative + the computed facts, cited.
4. BOM (§6.2).
5. Capacity & sizing justification (§6.3).
6. Validation plan (how each requirement will be verified — networkx today,
   Batfish/CLAB in netops).
7. Assumptions / dependencies / risks.
8. Appendix A: addressing & interface plan (today's tables).
9. Appendix B: compliance matrix (§6.1).

### 7.2 HLD: chapters gain a grounding contract

Each profile chapter's `done` list gains `every_claim_cited` and
`requirements_covered`. The chapter-writing loop (`get_chapter` → narrative slot)
injects, for that chapter: the `requirement_items` in its dimensions (verbatim),
the confirmed `design_decisions` for its chapter (decision + rationale +
source_ref), the chosen devices + specs, and the computed numbers. The LLM writes
prose citing only those IDs.

## 8. Deterministic document grader (`DocumentComplianceGrader`, zero-LLM)

Runs on the assembled document before it is declared done. All checks are Python
predicates over the DB + the rendered markdown:

| Check | Fail condition |
|---|---|
| **Coverage** | any `mandatory` requirement_item with no approved response row. |
| **Citation resolvability** | any `[R/D/E/Doc/Spec/Calc:…]` marker that does not resolve to a real row/entry. |
| **Uncited claims** | any claim-bearing paragraph (heuristic: declarative, in a design chapter) with zero citations. |
| **Rationale present** | any cited `design_decisions` row with empty `rationale` or `source_ref`. |
| **Judgement disclosure** | list (not fail) every `source_type = engineer_judgement` decision for reviewer sign-off. |
| **No placeholders** | `TODO`, `TBD`, `<…>`, `lorem`, `XXX`. |
| **Catalog reality** | any device/model named that is not in `device_catalog.yaml`. |
| **Number traceability** | capacity/sizing numbers not backed by a `[Calc:…]` result. |
| **Diagrams embedded** | required diagrams (profile `diagrams`) missing. |

Wiring proof (DoD): the grader must **fire from a real invocation** (log line /
callback), not merely be flagged — the dev_docs/97 nested-flag + no-op traps.
Prefer this deterministic grader over an LLM rubric (an LLM grading an LLM burns
a round-trip per stop).

## 9. Phased plan

**Phase 1 — the spine (highest leverage; "can we even bid?")**
- `requirement_items` + `requirement_responses` tables (§5.1/5.2).
- Clause extraction: `extract_requirements.py` (LLM Tier-2, grounded on Docling
  document chunks + `page_provenance`) → register, HITL-confirmed via
  `review_extraction` pattern.
- `generate_compliance_matrix` (§6.1) + coverage gate.
- `generate_bom` (§6.2).
- Provenance enforcement: typed `source_type` (§4.2); citation resolver used by
  the matrix.

**Phase 2 — narrative HLD/LLD**
- Narrative-slot mechanism: per-chapter brief assembler (§7.2) + the cited-prose
  contract.
- LLD restructure (§7.1) — tables → Appendix A; narrative body.
- `compute_sizing` (§6.3).
- `DocumentComplianceGrader` (§8) wired to fire on document completion.

**Phase 3 — submission polish + end-to-end**
- Executive summary, assumptions/dependencies/exclusions, migration overview,
  validation plan chapters.
- Re-run the Pershing tender end-to-end (dev_docs/105) → one reviewable, fully
  cited bid document; behavioural e2e at N≥3.

### 9.2 Decision: `generate_hld` replaces `format_and_export` for the deliverable

The HLD was previously assembled by the generic platform `format_and_export`,
which appends whatever prose the LLM wrote — **ungraded, provenance-unenforced**:
exactly the "free prose, no gate" failure for the HLD. `generate_hld` (mirroring
`generate_lld`) is now the bid deliverable path — Python assembles the ordered
cited chapters, embeds the compliance-matrix + BOM appendices, persists
`design_runs.hld_file_path`, and runs `grade_document` **with `require_coverage`**.
`format_and_export` is retained only for ad-hoc/interim exports, never the
submittable HLD.

## 10. Testing / Definition of Done

- **Reachability**: every new script routed + carries the
  `execute_skill_script(skill_name=…)` recipe (subagent-reachability gate).
- **Grader fires**: an integration test asserts `DocumentComplianceGrader` runs
  from a real document-generation invocation and its verdict is surfaced (not
  that the flag is present).
- **Coverage gate is real**: a test with an unresponded mandatory clause must
  make the matrix report `open` and the document fail the grader.
- **Provenance gate is real**: a document with a dangling `[D:dec-nonexistent]`
  must fail; a valid citation must resolve.
- **Deterministic first**: the Phase-1 matrix + BOM tests are zero-LLM and
  always-on (the `test_selection_bench_deterministic` pattern).
- **Behavioural**: the full-agent bid-document run is scored at **N≥3**
  (`assert_success_rate`) — LLM variance is not signal.
- **Isolation**: all tests under tmp `OLAV_HOME`; behavioural runs shred their
  project in teardown (the orphaned-DuckDB-lock lesson).

## 11. Consistency with the retire-runbook decision (dev_docs/106)

dev_docs/106 Option A retired the **implementation runbook** (step-by-step deploy
plan): it is netops territory, multi-step, project-specific, a frontier-model
commodity, and not verifiable. **This design does not reopen that.** The HLD/LLD
*design document* is the presales product itself — refusing to produce it would
make the domain pointless. The distinction that keeps us consistent:

| | Retired runbook | Bid-grade HLD/LLD (this doc) |
|---|---|---|
| What it is | *How to deploy* (steps) | *What the design is + why* (the deliverable) |
| Verifiable? | No — free prose | **Yes** — coverage + citation + grader gates |
| Grounded? | No | Every statement cites a resolvable source |
| Owner | netops implementation | presales product |

The LLM prose here is **bounded and gated**; the retired prose was unbounded and
ungoverned. That is the whole difference.

## 12. Open questions

1. **Clause extraction granularity** — how finely to split an RFP (per numbered
   clause vs per sentence). Start per numbered clause; HITL merges/splits.
2. **`requirement_responses` per-run vs latest-wins** — a clause's response may
   evolve across HLD→LLD. Keyed per `run_id` (keeps history); the matrix renders
   the latest approved.
3. **BOM pricing** — out of scope for MVP (no price feed); BOM lists model + qty
   + role + datasheet only. Pricing is a later enterprise entitlement.
4. **Diagram grounding** — should the `to_be` topology diagram itself be
   citation-checked against `topology_nodes`? Deferred to Phase 3.
