## 2. 仓库目录布局（决策：单仓库）

主站和文档站均位于同一仓库，`web/` 与 `docs/` 平行：

```
Olav/                         ← 项目根
├── mkdocs.yml                ← 文档站配置（根目录，Cloudflare 直接读取）
├── docs/                     ← 文档站唯一内容源（MkDocs docs_dir）
│   ├── 01_README.md          ← 文档首页
│   ├── cn/                   ← 顶层中文入口
│   ├── olav/                 ← 平台核心文档（EN）
│   │   └── cn/               ← 平台核心文档（ZH）
│   └── netops/               ← NetOps 扩展文档（EN）
│       └── cn/               ← NetOps 扩展文档（ZH）
├── web/                      ← 商业主站（Astro + Tailwind）
│   ├── package.json
│   ├── astro.config.mjs
│   └── src/
│       ├── pages/            ← 页面路由
│       └── components/       ← UI 组件
├── src/olav/                 ← Python 核心代码
├── dev_docs/                 ← 内部开发文档（永不发布）
└── pyproject.toml
```

**关键约束：**
- `dev_docs/` 永远不进入 MkDocs `docs_dir`，也不进入 `web/`
- `docs/` 和 `web/` 各自对应一个独立的 Cloudflare Pages 项目，独立部署节奏
- Node.js 构建链（`web/`）与 Python 构建链（`mkdocs`）完全隔离，互不干扰

## 4. 文档站技术栈（MkDocs + Material）

### 4.1 技术选型理由

- OLAV 是 Python 项目，MkDocs Python 原生，不引入额外构建链
- Material theme：全文搜索、中英双语（i18n）、暗色主题、Mermaid 渲染、代码复制
- `mkdocs-awesome-pages-plugin` 直接映射现有 `docs/` 目录结构，零改动

**核心依赖：**
```toml
# pyproject.toml [dependency-groups.docs]
mkdocs = ">=1.6"
mkdocs-material = ">=9.5"
mkdocs-awesome-pages-plugin = ">=2.9"
mkdocs-static-i18n = ">=1.2"
```

### 4.2 mkdocs.yml 核心配置

```yaml
site_name: OLAV Platform
site_url: https://docs.olavai.com
docs_dir: docs
theme:
  name: material
  language: zh
  palette:
    - scheme: default
      toggle: { icon: material/brightness-7, name: 切换暗色主题 }
    - scheme: slate
      toggle: { icon: material/brightness-4, name: 切换亮色主题 }
  features:
    - navigation.tabs
    - navigation.sections
    - search.highlight
    - content.code.copy

plugins:
  - search:
      lang: [zh, en]
  - awesome-pages

markdown_extensions:
  - pymdownx.superfences:
      custom_fences:
        - name: mermaid
          class: mermaid
          format: !!python/name:pymdownx.superfences.fence_code_format
  - admonition
  - pymdownx.highlight
  - pymdownx.tabbed
  - toc:
      permalink: true
```

### 4.3 Cloudflare Pages 部署配置（文档站）

```
Build command:      pip install mkdocs mkdocs-material mkdocs-awesome-pages-plugin && mkdocs build

```

## 7. 文档驱动测试（Doc-Driven Testing）

### 7.1 核心理念

```
传统 TDD：  代码 → 测试 → 文档    （文档是结果，容易碎片化、技术化）
本方案：    文档 → 测试 → 代码    （文档是合同，测试是裁判，代码必须匹配）
```

「声称」先于「实现」。这一顺序迫使文档保持用户语言，而非技术实现细节。
参考：Readme-Driven Development（Tom Preston-Werner）+ Specification by Example。

### 7.2 执行流程

```
Step 1  代码审计
        扫描现有实现，理解真实能力边界
        产出：能力候选清单（草稿，不对外）
              ↓
Step 2  撰写 High-Level Claim 文档
        只写「能做什么」，用用户语言
        示例：
          Claim A: "OLAV 能连接任意 OpenAPI 服务并自动生成工具"
          Claim B: "Creator Agent 能在 2 分钟内部署一个新 Skill"
          Claim C: "多用户并发操作互不干扰"
              ↓
Step 2.5  ★ CLI 验证门（MANDATORY）★
        每条 Claim 必须先通过 olav CLI 自然语言指令验证，才能进入 Step 3
        验证方式：
          olav "<自然语言描述 Claim 的操作>"
          或 olav skill / olav service / olav log 等结构化子命令
        判定标准：
          ✅ CLI 执行成功，输出符合预期  → Claim 通过，可写 E2E 测试
          ❌ CLI 执行失败或输出不符     → 功能未落地，先修代码再回 Step 2.5
        记录格式（附在 Claim 旁）：
          CLI: olav skill install <url>
          Output: installed <name> v<ver> → .olav/workspace/<name>/
          Status: ✅ 2026-04-02
              ↓
Step 3  每条已 CLI Verified 的 Claim → 一个 E2E 验证测试
        test_can_connect_any_openapi_service()
        test_creator_deploys_skill_under_2min()
        test_multiuser_sessions_are_isolated()
              ↓
Step 4  运行测试，触发三种结果处理
        ✅ Pass    → Claim 保留，文档标记 Verified
        ❌ Fail    → 决策：
                      该能力有价值？→ 修复代码，重跑
                      代价太高？    → 从文档删除该 Claim
        ⚠️ Partial → 收窄措辞（"在以下条件下..." / "需要配置 X"）
              ↓
Step 5  文档只保留 Verified Claims
        最终文档 = 可信赖的能力声明，零水分
```

**关键原则：没有经过 `olav` CLI 验证的功能，不算功能落地，不允许进入文档。**

### 7.2.1 CLI 验证记录模板

每条 Claim 的 CLI 验证结果写在 `dev_docs/24. CLI_VERIFICATION_LOG.md` 中：

```markdown
## Claim: <功能描述>

**CLI 指令：**
\`\`\`
olav skill install https://github.com/user/my-skill
\`\`\`

**实际输出：**
\`\`\`
installed my-skill v1.0.0 → .olav/workspace/my-skill/
\`\`\`

**状态：** ✅ Verified 2026-04-02
**落地版本：** v0.12.0
```

### 7.3 防止文档碎片化的内置机制

本方案天然防止碎片化，原因在于：

| 阶段 | 约束来源 | 效果 |
|------|----------|------|
| 写 Claim 时 | 必须能转化为 CLI 指令，否则措辞无效 | 强制使用用户语言 |
| **CLI 验证门** | **olav CLI 执行成功才算功能落地** | **防止「纸面功能」进入文档** |
| 测试失败时 | 不是补文档，而是删 Claim 或收窄范围 | 防止「吹牛」文档 |
| Claim 数量 | 每条 Claim 对应一个完整 E2E 场景 | 成本约束颗粒度 |
| 单元测试 | 永远不驱动文档 | 内部实现不泄露到文档 |

### 7.4 OLAV 文档的 Claim 层级

```
Level 1  平台级 Claim（主站 / README）
         "OLAV 是一个 AI-native 网络运维平台"
         每条对应 1 个端到端场景测试

Level 2  功能级 Claim（文档站页面）
         "Creator Agent 支持任意 OpenAPI 服务"
         每条对应 1 个集成测试

Level 3  操作级 Claim（How-to Guide）
         "通过以下步骤部署 NetBox Skill"
         对应可复制运行的命令序列（本身即验证）
```

Level 3 的 How-to Guide 是「自证明的」——读者能跑通 = Claim 为真，无需额外测试。

### 7.5 与现有测试体系的集成

```
tests/
├── 00_e2e_acceptance_test.py   ← Claim 验证层（Level 1/2）
│   每个 TestClass 对应文档中一个功能章节
│   TestClass docstring 写明对应的 Claim 和文档路径
│
└── unit/                       ← 不驱动文档（代码质量层）
```

CI 流程：
```
push → pytest 00_e2e_acceptance_test.py →
  全部通过 → 文档站正常发布
  有失败   → 构建中断 + 标记对应文档 Claim 为 ⚠️ Unverified
```

### 7.6 执行计划（文档站 Phase 1 前置）

```
Step A  代码审计
        审计 src/olav/ + .olav/workspace/，产出能力候选清单

Step B  Claim 审阅（人工）
        删除不想声称 / 当前不支持的 Claim
        确定 Level 1 / Level 2 边界

Step B.5  ★ CLI 验证（每条 Claim 强制）★
        olav <claim 对应的自然语言或子命令>
        通过 → 记录到 dev_docs/24. CLI_VERIFICATION_LOG.md
        失败 → 修代码 → 重验证（不跳过）
        原则：没有 CLI verified = 没有落地 = 不进文档

Step C  文档骨架
        基于已 CLI Verified 的 Claim 写 docs/ 页面骨架（只写标题 + 一句描述）

Step D  测试编写
        每条 Level 1/2 Claim 写对应 E2E 测试

Step E  修复 or 收窄（持续）
        测试驱动代码修复 or 文档删减，直到全绿

Step F  部署
        mkdocs build → Cloudflare Pages 发布
```

## 8. 关键约束

- **`dev_docs/` 永不发布**：内部开发文档与用户文档严格隔离
- **`docs/` 是文档站唯一内容源**：mkdocs.yml `docs_dir: docs`
- **`web/` 与 `docs/` 独立部署**：两个 Cloudflare Pages 项目，各自触发路径互不干扰
- **中文文档与英文文档保持同步**：新功能文档同时写中英两版
- **单元测试永远不驱动文档**：防止内部实现细节渗透到用户文档
- **每条 Claim 必须可测试**：无法写出 E2E 测试的 Claim 不允许出现在文档中
- **★ CLI 验证是功能落地的唯一判定标准 ★**：`olav` CLI（自然语言或子命令）执行成功才算功能落地，代码通过单元测试≠功能落地，必须经 CLI 端到端验证并记录到 `dev_docs/24. CLI_VERIFICATION_LOG.md`
