## 2. 文档站（Phase 1）

### 2.1 技术选型：MkDocs + Material Theme

**理由：**
- OLAV 是 Python 项目，MkDocs 是 Python 原生，不引入 Node.js 构建链
- Material theme 是技术文档领域事实标准
- 开箱即用的功能：全文搜索、中英双语（i18n）、暗色主题、Mermaid 图渲染、代码高亮
- `mkdocs-awesome-pages-plugin` 直接映射现有 `docs/` 目录，零改动

**核心依赖：**
```toml
# pyproject.toml [dependency-groups.docs]
mkdocs = ">=1.6"
mkdocs-material = ">=9.5"
mkdocs-awesome-pages-plugin = ">=2.9"
mkdocs-static-i18n = ">=1.2"   # 中英切换
```

### 2.2 目录映射

现有 `docs/` 结构直接复用：

```
docs/
├── 01_README.md          → 首页
├── olav/                 → 平台核心文档（英文）
│   ├── architecture.md
```

### 2.3 mkdocs.yml 核心配置

```yaml
site_name: OLAV Platform
site_url: https://docs.olavplatform.com
docs_dir: docs
theme:
  name: material
  language: zh
  palette:
    - scheme: default
      toggle:
        icon: material/brightness-7
        name: 切换暗色主题
    - scheme: slate
      toggle:
        icon: material/brightness-4
        name: 切换亮色主题
  features:
    - navigation.tabs          # 顶部导航
    - navigation.sections
    - search.highlight
    - content.code.copy        # 代码块复制按钮

plugins:
  - search:
      lang: [zh, en]
  - awesome-pages              # 自动读取目录结构

markdown_extensions:
  - pymdownx.superfences:
      custom_fences:
        - name: mermaid        # Mermaid 图支持
          class: mermaid
          format: !!python/name:pymdownx.superfences.fence_code_format
  - admonition                 # !!! note / warning / tip
  - pymdownx.highlight
  - pymdownx.tabbed
  - toc:
      permalink: true
```

**DNS 配置（在 Cloudflare Dashboard）：**
```

```

### 2.5 GitHub Actions（可选，替代 Cloudflare 内置构建）

```yaml
# .github/workflows/docs.yml
name: Deploy Docs
on:
  push:
    branches: [main]
    paths: [docs/**, mkdocs.yml]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install mkdocs mkdocs-material mkdocs-awesome-pages-plugin
      - run: mkdocs gh-deploy --force
        # 或: mkdocs build && wrangler pages deploy site
```

> 推荐直接用 Cloudflare Pages 内置 CI，无需额外 workflow，push 即触发。

## 3. 商业主站（Phase 2）

> 文档站上线后再启动

### 3.1 技术选型：Astro + Tailwind CSS

**理由：**
- 输出纯静态 HTML，Cloudflare Pages 直接托管，无服务器成本
- Tailwind CSS 快速构建 Landing Page
- 原生支持 MDX（博客 / 更新日志直接写 Markdown）
- 构建速度远快于 Next.js

**页面结构（规划）：**
```

/features      功能展示（平台 + NetOps 能力）
/pricing       定价（开源 / Enterprise）
/blog          技术博客（MDX）
/changelog     CHANGELOG.md 自动渲染
               → docs.olavplatform.com  （外链）
```

**单独仓库：**`github/<org>/olav-website`，与主仓库解耦。

### 3.2 Cloudflare Pages 部署配置

```

Build command:      npm run build
Output directory:   dist
```

## 5. 文档驱动测试（Doc-Driven Testing）

> 文档是合同，测试是验证器，代码是实现。

### 5.1 核心理念

```
传统 TDD：  代码 → 测试 → 文档    （文档是结果，容易碎片化、技术化）
本方案：    文档 → 测试 → 代码    （文档是合同，测试是裁判，代码必须匹配）
```

「声称」先于「实现」。这一顺序迫使文档保持用户语言，而非技术实现细节。
参考：Readme-Driven Development（Tom Preston-Werner）+ Specification by Example。

### 5.2 执行流程

```
Step 1  代码审计
        扫描现有实现，理解真实能力边界
        产出：能力候选清单（草稿，不对外）
              ↓
Step 2  撰写 High-Level Claim 文档
        只写「能做什么」，用用户语言
        示例：
          Claim A: "OLAV 能连接任意 OpenAPI 服务并自动生成工具"
          Claim B: "Creator Agent 能在 2 分钟内部署一个新 Skill"
          Claim C: "多用户并发操作互不干扰"
              ↓
Step 3  每条 Claim → 一个 E2E 验证测试
        test_can_connect_any_openapi_service()
        test_creator_deploys_skill_under_2min()
        test_multiuser_sessions_are_isolated()
              ↓
Step 4  运行测试，触发三种结果处理
        ✅ Pass    → Claim 保留，文档标记 Verified
        ❌ Fail    → 决策：
                      该能力有价值？→ 修复代码，重跑
                      代价太高？    → 从文档删除该 Claim
        ⚠️ Partial → 收窄措辞（"在以下条件下..." / "需要配置 X"）
              ↓
Step 5  文档只保留 Verified Claims
        最终文档 = 可信赖的能力声明，零水分
```

### 5.3 防止文档碎片化的内置机制

本方案天然防止碎片化，原因在于：

| 阶段 | 约束来源 | 效果 |
|------|----------|------|
| 写 Claim 时 | 必须能转化为 E2E 测试，否则措辞无效 | 强制使用用户语言 |
| 测试失败时 | 不是补文档，而是删 Claim 或收窄范围 | 防止「吹牛」文档 |
| Claim 数量 | 每条 Claim 对应一个完整 E2E 场景 | 成本约束颗粒度 |
| 单元测试 | 永远不驱动文档 | 内部实现不泄露到文档 |

### 5.4 OLAV 文档的 Claim 层级

```
Level 1  平台级 Claim（主站 / README）
         "OLAV 是一个 AI-native 网络运维平台"
         每条对应 1 个端到端场景测试

Level 2  功能级 Claim（文档站页面）
         "Creator Agent 支持任意 OpenAPI 服务"
         每条对应 1 个集成测试

Level 3  操作级 Claim（How-to Guide）
         "通过以下步骤部署 NetBox Skill"
         对应可复制运行的命令序列（本身即验证）
```

Level 3 的 How-to Guide 是「自证明的」——读者能跑通 = Claim 为真，无需额外测试。

### 5.5 与现有测试体系的集成

```
tests/
├── 00_e2e_acceptance_test.py   ← Claim 验证层（Level 1/2）
│   每个 TestClass 对应文档中一个功能章节
│   TestClass docstring 写明对应的 Claim 和文档路径
│
└── unit/                       ← 不驱动文档（代码质量层）
```

CI 流程：
```
push → pytest 00_e2e_acceptance_test.py → 
  全部通过 → 文档站正常发布
  有失败   → 构建中断 + 标记对应文档 Claim 为 ⚠️ Unverified
```

### 5.6 执行计划（文档站 Phase 1 前置）

```
Step A  代码审计（1天）
        审计 src/olav/ + .olav/workspace/，产出能力候选清单

Step B  Claim 审阅（人工，0.5天）
        删除不想声称 / 当前不支持的 Claim
        确定 Level 1 / Level 2 边界

Step C  文档骨架（1天）
        基于确认 Claim 写 docs/ 页面骨架（只写标题 + 一句描述）

Step D  测试编写（2天）
        每条 Level 1/2 Claim 写对应 E2E 测试

Step E  修复 or 收窄（持续）
        测试驱动代码修复 or 文档删减，直到全绿

Step F  部署（0.5天）
        mkdocs build → Cloudflare Pages 发布
```

## 6. 关键约束

- **不在主仓库（Olav）存放主站代码**：主仓库只负责 docs/ → 文档站
- **中文文档与英文文档保持同步**：新功能文档同时写中英两版
- **文档站 URL 固定为 `docs.*`**：便于从主站、README、CLI help 统一外链
- **单元测试永远不驱动文档**：防止内部实现细节渗透到用户文档
- **每条 Claim 必须可测试**：无法写出 E2E 测试的 Claim 不允许出现在文档中
