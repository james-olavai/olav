### Issue #2 deep-dive: does deepagents-cli need upgrading? (checked 2026-06-03)

**Yes — but it is NOT a simple version bump; it needs a code port.**

- **The conflict:** `deepagents-cli==0.0.41` (olav's pinned dep) hard-pins
  `deepagents==0.5.3`; olav's code needs `deepagents>=0.6.7`. pip cannot resolve
  both (`ResolutionImpossible`). They coexist ONLY via the `[tool.uv]
  override-dependencies` (uv forces deepagents 0.6.7 alongside cli 0.0.41,
  effectively `--no-deps` on the cli's pin). **So `pip install olav` is broken
  for any non-uv user.**
- **cli version → deepagents requirement (PyPI):** 0.0.41→`==0.5.3`;
  0.0.52-56→`==0.5.8/0.5.9`; 0.0.59→`==0.6.1` (exact, still conflicts with 0.6.7);
  **0.1.0 / 0.1.2 / 0.2.0 → `>=0.6.1`** (range, ALLOWS 0.6.7 — would fix the conflict).
- **BUT cli 0.1.0+ restructured the internal API olav depends on.** Verified
  against cli 0.2.0: `deepagents_cli.app` and `deepagents_cli.command_registry`
  modules are GONE; `config._UNICODE_BANNER` and `config.SessionState` are GONE.
  A bump to 0.2.0 breaks olav's CLI — even a one-shot query fails with
  `cannot import name 'SessionState' from 'deepagents_cli.config'`.
- **olav's cli-integration surface (5 files to port):** `cli/main.py`
  (`deepagents_cli.execution`, `app.run_textual_app`, `config.SessionState`),
  `cli/tui_overlay.py` (`app.DeepAgentsApp`, `command_registry.COMMANDS`,
  `_UNICODE_BANNER/_ASCII_BANNER`), `cli/commands/builtin.py`,
  `cli/commands/registry.py`, `core/utils.py`.
- **Verdict:** Upgrading the cli (to 0.1.0+) is the correct fix for the
  pip-install breakage, but requires PORTING olav's deepagents-cli integration
  to the new package.

## 2026-06-04 Follow-up: A-class root cause analysis + fixes

**Context:** After fixing B/C/D/E and deploying the new rubric/CLI fixes, re-ran
CH3/4/6/8/11 with gemma4-31b-Q4 on freshly imported demo data (348 devices, 6
bundles from `tmp/anon/`). Revealed three distinct code-layer bugs masquerading as
"LLM quality" failures.

### A1 — CLI `_chunks` depth pollution (CH8) ✅ FIXED `64e8e90c`

**Symptom:** CH8 (`alpha-dist-4500xv-d 故障后网络会断成几个部分`) showed only `🔧`
tool-call lines in CLI output with no natural-language answer — but direct Python
`ainvoke()` returned a complete answer ("67 connected components").

**Root cause:** `main.py:run_single_query` — both `on_chat_model_stream` and
`on_chat_model_end` added LLM text to `_chunks` regardless of `_delegate_depth`.
In a `netops → task("reporter") → reporter runs SQL` chain, the reporter sub-agent's
internal LLM stream filled `_chunks` before the orchestrator produced its final
answer. The `not _chunks` guard in `on_chat_model_end` then silently discarded the
orchestrator's prose.

**Fix:** Guard both handlers with `_delegate_depth == 0`. Sub-agent internal LLM
turns (`_delegate_depth > 0`) are NOT added to `_chunks`. Verified: CH8 retest →
full prose output: "网络碎片化程度显著增加，总组件数从 146 个增加到 163 个，净增 17 个孤立部分".

### A2 — execute_sql per-device loop / context overflow (CH11) ✅ FIXED `c79d536a`

**Symptom:** CH11 (BFS upgrade plan for 14 WS-C4500X-32 devices) triggered 60+
`execute_sql` calls with the same column (`WHERE hostname = 'X'`) querying each
device individually, hitting the 65536-token context limit.

**Root cause:** gemma4 ignored the `≤3 SQL queries` guide and looped per-device.
SKILL.md text rules alone are insufficient for gemma4.

**Fix (two layers):**
1. `execute_sql.py`: `_check_sql_loop()` — per-thread deque of recent SQL structural
   stems (values stripped, column names kept). ≥5 identical stems in a row → hard-stop
   error: "🚫 LOOP DETECTED — use `WHERE model LIKE '%C4500X%'` instead."
   Thread-local so it works inside sub-agent threads independent of orchestrator depth.
2. `analyzer/SKILL.md`: Hard rule #6 + Phase 0 bulk query example.

**Result:** SQL calls 60 → 15; file generated:
`exports/change_plans/WS-C4500X_BFS_staged_upgrade_plan.md` (108 lines, 3-stage
leaf-first plan with CLI/rollback/post-checks for all 14 devices).

### A3 — RubricMiddleware synthesis enforcement ✅ FIXED `83bebd75` + `0f579027`

**Symptom:** Some CH tests fail because gemma4 exits after tool calls without
producing a natural-language answer turn (no-synthesis). The CLI's
`NL-CLI-SILENT-FINAL` fallback emits raw `📁` tool-result lines instead.

**Root cause (two):** (1) RubricMiddleware was added to `_olav_middleware` (storage
ref) but NOT to `effective_middleware` before `create_deep_agent()` compile → grader
never fired. (2) Initial rubric was too strict: grader returned `needs_revision` for
valid Chinese-language prose ("cannot confirm tool usage").

**Fix:** Added `RubricMiddleware` to `effective_middleware` pre-compile when
`rubric_middleware: true` in AGENT.md. Rubric tuned to pass-biased: "PASS if last
message has ANY natural-language sentence in any language; FAIL ONLY if entirely raw
output." Verified: empty AIMessage → `needs_revision` + `jump_to=model`; prose
answer → `satisfied` (1 eval, no unnecessary loop). netops AGENT.md gains
`synthesis_rubric: true`.

### Remaining A-class failures

True gemma4 model-quality gaps (content phrasing, weak reasoning, deliberation
loops) that require a stronger model to pass. Not addressable at the code layer.
Would pass on deepseek-v4-flash, grok-4.1-fast, or Claude Sonnet.

## 2026-06-04 Architectural investigation: small-model root cause + prompt refactoring

### Root cause of A-class failures (re-assessed)

After re-running CH3/4/6/8/11 with gemma4 + demo data (348 devices), the "LLM
quality" classification was wrong for most failures. Three distinct code-layer
causes were found and fixed:

**A1 (CH8): CLI `_chunks` pollution** (`64e8e90c`) — sub-agent internal LLM
stream was added to `_chunks` regardless of `_delegate_depth`, so the
orchestrator's final answer was silently discarded. Fix: guard both stream
handlers with `_delegate_depth == 0`.

**A2 (CH11): per-device SQL loop** (`c79d536a`, `f5faa5e9`, `b4fdeab9`) —
gemma4 interpreted "Phase 2 — DRAFT CLI per device" literally and queried each
device individually (60-80 SQL calls → context overflow). Three-layer fix:
1. `execute_sql` loop detection (same-column repeated queries → hard-stop)
2. `generate_change_plan` fat-tool (bulk model upgrades in 1 Python call)
3. Analyzer SKILL.md refactored from Phase 6-step HOW spec (318 lines) to
   Goal+Constraints WHAT spec (118 lines, 0 Phase mentions)

**A3 (no-synthesis): RubricMiddleware** (`83bebd75`, `0f579027`) — grader was
not in `effective_middleware` (pre-compile). Fixed; rubric tuned to pass-biased.

### Key architectural insight: HOW vs WHAT prompting

Experiment sequence on CH11 (bulk 14-device plan):
```
Attempt A: SKILL.md "NEVER loop" text rule   → 60 SQL (ignored)
Attempt B: TodoListMiddleware enabled        → 40 SQL (write_todos not called)
Attempt C: "MANDATORY write_todos" injected → 80 SQL (harder ignored)
Attempt D: Fat Tool (generate_change_plan)   → 0 SQL, 807-line file ✓
Attempt E: Goal+Constraints SKILL.md        → model self-selected fat tool ✓
```

**Conclusion**: specifying HOW (phases, per-device steps) causes gemma4 to follow
the template mechanically regardless of task type. Specifying WHAT (output spec)
+ Constraints (SQL limit, CLI correctness rules) lets the model choose HOW based
on context. This mirrors deepagents' own system_prompt.md (0 Phase mentions,
213 lines, 4 general principles).

Checked all other agents (reporter/simulator/explorer/devops): none have the
same "per-device Phase" pattern. reporter/simulator use Phase for query-type
iteration (not device iteration), which is correct.

### What actually requires stronger models

After the code fixes, re-validation confirmed:
- CH3/4/6 — gemma4 passes assertion keywords even with test data ✓
- CH8 — fixed (CLI output bug, not model quality)
- CH11 — fixed (prompt over-specification + fat tool)
- F (admin cron) — gemma4 agent-layer non-zero exit; no code fix possible
- Content phrasing edge cases — model-quality, not code
