```
→ olav_delegate (retry, "/tmp/anon/...")

```
→ Timeout at 600s. `ingest_snapshot` was never called.

**Secondary**: First attempt hit HTTP 503 "Loading model" — llama.cpp was cold-starting.

### ISSUE-DEMO-05: Admin sub-agents emit malformed tool-call tokens ✅ FIXED (2026-05-27)
**Severity**: P1 — blocks Ch7 (admin agent) entirely
**Symptom**: `admin/ops` sub-agent outputs raw XML-style tokens instead of JSON tool calls:
```
<|tool_call>call:default_api:check_health{}</tool_call|>
```
LangChain cannot parse these → no tool invoked → agent returns empty.
**Root cause (confirmed)**: `admin/ops/SKILL.md` had `tools: []` — no `execute_skill_script` in the tools list. The LLM sees script descriptions injected by SkillsMiddleware into the system prompt but has no tool to call them with. It falls back to generating tool calls directly by script name in gemma-4's native XML-style format. `thinking_mode: disabled` compounded this (nothink path has weaker tool-call adherence), but the primary cause was the missing tool.
**Fix applied**:
1. `admin/ops/SKILL.md`: `tools: []` → `tools: [execute_skill_script]`
2. `admin/ops/SKILL.md`: `thinking_mode: disabled` → `thinking_mode: enabled`
**Verified**: T2 retest ✅ PASS — `execute_skill_script({'skill_name': 'ops', 'script_name': 'check_health.py'})` called as proper JSON tool call; full health report returned.

### ISSUE-DEMO-06: audit-runner `recall_memory` deliberation loop ❌ P1
**Severity**: P1 — blocks Ch9 runner (run profile)
**Symptom**: After orchestrator delegates to `audit-runner`, the runner calls `recall_memory` 20+ times with queries like `"bgp_health profile path"` without ever calling `run_map_engine`.
**Root cause**: `audit-runner` SKILL.md lists `recall_memory` as a tool. The runner's system prompt says "Given a Profile path + time window, produce a report in exactly two tool calls." But when the user says "Run the bgp_health profile", they haven't specified the full path. The runner then tries to find the path via `recall_memory` instead of using the known profiles directory. gemma-4 treats this as an open-ended research task and loops.
**Fix options**:
- A: Remove `recall_memory` from `audit-runner` tools (runner should never need to search memory — profile path is always in the user message or can be resolved deterministically).
- B: Add to orchestrator routing: resolve profile path before delegating, always pass absolute path `".olav/workspace/audit/profiles/<name>.md"` to runner.
- C: Add to runner system.md: "If profile_path not provided, list `.olav/workspace/audit/profiles/*.md` via `list_profiles` script, present options to user, wait for selection — do NOT call recall_memory."

### ISSUE-DEMO-07: Context overflow in reporter — SQL results accumulate ❌ P2
**Severity**: P2 — blocks Ch6 reporter on real (non-toy) networks
**Symptom**: `netops/reporter` queries 6+ views in sequence → 75,279 tokens prompt → exceeds 65,536 limit → `Error: request exceeds context size`.
**Root cause**: Each `execute_sql` result is appended to the conversation history. On real networks (100+ devices), result sets are large. The summarization middleware should compress history but fails (see ISSUE-DEMO-08).
**Fix options**:
- A: Add row LIMIT to each SQL in reporter's system prompt: "Always add LIMIT 50 to any SELECT without WHERE; increase only if explicitly needed."
- B: Truncate `execute_sql` return value server-side: `result[:2000]` + "... N rows truncated" before injecting into message history.
- C: Fix ISSUE-DEMO-08 first — once summarization works, history compression should prevent overflow.

### ISSUE-DEMO-08: `KeyError: 'files'` in deepagents summarization backend ❌ P1
**Severity**: P1 — root cause for T8/T9/T10/T12 failures; makes context overflow (T10) unrecoverable
**Symptom**: Every multi-turn agent session (3+ LLM calls) hits:
```
Exception offloading conversation history: KeyError: 'files'
```
Conversation history is never summarized → full message history stays in context → context grows until overflow or model behavior degrades.
**Root cause**: The deepagents `SummarizationMiddleware` accesses `config['files']` from the LangGraph checkpoint state. After the langgraph_api + inmem runtime migration (rev 79708c92), the checkpoint schema may have changed and the `files` key no longer exists in the state dictionary.
**Affected**: All agents with multi-turn flows (audit-runner, explorer, reporter, audit-author).
**Fix**: Investigate `deepagents.middleware.summarization` — find where `config['files']` is accessed and update to match the new inmem runtime checkpoint schema. May require `config.get('files', {})` defensively or a different history-access pattern.
**Note**: This is likely a deepagents framework version compatibility issue post-langgraph_api migration. Check deepagents CHANGELOG for `config` schema changes.

---

### ISSUE-DEMO-09: LLM 503 "Loading model" — no retry in OLAV
**Severity**: P2 — sporadic failures, especially between long-running tests
**Symptom**: llama.cpp server returns HTTP 503 `{"error":{"message":"Loading model","type":"server_error"}}` when the model was evicted from VRAM (KV cache eviction or another model loaded). OLAV has no retry logic — the agent fails immediately.
**Context**: With a single GPU shared between LLM (11433) and embedding (11434) models, the LLM model can be evicted if the GPU is used for embedding. Or if the llama.cpp server's context was freed between long test gaps.
**Fix options**:
- A: Add retry with backoff in `olav.core.llm` for 503 responses: retry up to 3× with 5s delay.
- B: Add `--no-mlock` and increase `--parallel` in llama.cpp config to prevent eviction.
- C: Configure llama.cpp `--model-alias` and `--ctx-size` to keep model in VRAM permanently.
