## Why TCF

The 2026-04-27 closed-loop run exposed three orthogonal failures in
the markdown CAB spec interface:

1. **Sim's markdown synthesis is unreliable** — small models drop
   sections, format dicts as ugly headers, mis-name files.
2. **Lab's markdown parsing is unreliable** — small models extract
   structured facts from prose with errors; sometimes silently
   "correct" what they think is a typo.
3. **No diff possible between spec and lab actions** — both sides
   are free-form text; comparing what the spec asked for vs what
   the lab actually did requires more LLM passes that introduce
   their own errors.

R88-A and R89 already proved the pattern: **replace LLM synthesis
with structured contracts**. R88-A turned "synthesise CLAB yaml"
into a deterministic tool over `(nodes, lab_name)`. R89 turned
"translate prod CLI to SRL CLI" into a deterministic tool over
`(nodes, loopbacks, asns, intent_type, lab_subnet)`.

R90 extends this principle to **the sim ↔ lab interface itself**.
Instead of sim writing prose markdown that lab parses, both sides
exchange a single **TCF (Test Case File) artifact**: a YAML file
with a Pydantic-validated schema. Lab consumes it deterministically,
writes results back into the same file, and downstream prod ops
fill another column.

Markdown narrative becomes a **render output**, not the contract.
When a human wants a doc, they invoke the writer agent which uses
its existing LLM-render capability on the YAML file. We do **not**
build a dedicated `tcf_to_markdown` tool — the writer agent's LLM
can render any layout the user asks for, and the YAML is its input.

---

## Core principle: tight structure, loose content

The schema must accommodate *every* CAB change, not just eBGP. So:

* **Tight** on housekeeping shape (change_id, devices list, cli
  blocks, post-checks, TVT rows). Pydantic enforces these.
* **Loose** on domain content (intent type, per-device extras,
  test categorisation). These are open strings / extra dicts —
  Pydantic accepts arbitrary values, downstream tools validate
  at use time.

This means: a new change type (ACL update / MTU bump / route
policy / BFD enable / route reflector reconfig / VLAN add) does
NOT require a schema bump. It just uses different `intent.type`
strings and the natural CLI blocks. Pydantic still catches FK
errors and missing required fields.

## Schema (YAML, Pydantic-validated)

### Single file per change

```
exports/cab/<change_id>.tcf.yaml      # the contract — sim writes, lab fills, prod fills
```

Markdown is on-demand:

```
# user: "render cab_001 as markdown"
# orchestrator → writer subagent
# writer reads cab_001.tcf.yaml + LLM renders to .md
```

No `tcf_to_markdown` tool needed. Writer's LLM picks the layout
(technical detail / executive summary / runbook / whatever the
asker wants). YAML is the source of truth.

### Top-level envelope (tight)

```yaml
schema_version: 1
change_id: cab_r1_r4_ebgp_001
title: Add direct eBGP between R1 and R4
created_by: ops-analyze         # or the user's name for hand-authored
created_at: 2026-04-27T12:00:00Z
risk_class: low                 # low | medium | high | blocker

intent:
  type: ebgp_direct             # FREE-FORM string. Tools that handle
                                # specific change types match on this.
  # ↓ all other intent fields are change-type-specific:
  lab_subnet: 172.16.99.0/30    # only meaningful for connectivity changes
  # acl_name: BLOCK_RFC1918     # would be set for ACL changes
  # vlan_id: 100                # would be set for VLAN changes
```

Pydantic model:

```python
from pydantic import BaseModel, ConfigDict
from typing import Any

class Intent(BaseModel):
    """Open-ended intent. ``type`` is a free-form identifier; tools
    dispatch on it. All other fields are accepted as-is via
    ``model_config["extra"] = "allow"`` so per-change-type payloads
    don't need schema bumps."""

    model_config = ConfigDict(extra="allow")
    type: str
```

### Devices (tight shape, loose extras)

```yaml
devices:
  - name: R1
    platform: juniper_junos       # any string; tools that match on platform validate
    prod_intf: ge-0/0/2
    prod_loopback: 1.1.1.1
    prod_asn: 65000
    # Optional fields — sim adds whatever's relevant:
    prod_intf_ip: 10.1.24.1/30
    role: border
    site: lab
    # Per-change-type extras land in `extras`:
    extras:
      ospf_area: 0.0.0.0          # only when relevant
      mgmt_ip: 192.168.100.101    # for non-default lookups
```

```python
class Device(BaseModel):
    model_config = ConfigDict(extra="allow")
    name: str
    platform: str
    # All other fields optional, sim populates what it has
    prod_intf: str | None = None
    prod_loopback: str | None = None
    prod_asn: int | None = None
    prod_intf_ip: str | None = None
    role: str = ""
    site: str = ""
    extras: dict[str, Any] = Field(default_factory=dict)
```

`extra="allow"` means future fields can be added without Pydantic
rejection. Required fields stay required.

### Implementation + rollback (same shape)

```yaml
implementation:
  - device: R1
    phase: 1
    action: configure
    cli:
      - "set protocols bgp group ebgp-r4 type external"
      - "set protocols bgp group ebgp-r4 neighbor 10.1.24.2 peer-as 65001"
      - "set interfaces ge-0/0/2 unit 0 family inet address 10.1.24.1/30"
  - device: R4
    phase: 1
    action: configure
    cli:
      - "interface Ethernet0/0"
      - " ip address 10.1.24.2 255.255.255.252"
      - "router bgp 65001"
      - " neighbor 10.1.24.1 remote-as 65000"

rollback:
  - device: R1
    phase: rb1
    action: configure
    cli:
      - "delete protocols bgp group ebgp-r4"
      - "delete interfaces ge-0/0/2 unit 0 family inet address 10.1.24.1/30"
  - device: R4
    phase: rb1
    action: configure
    cli:
      - "no router bgp 65001"
      - "interface Ethernet0/0"
      - " no ip address"
```

```python
class CliBlock(BaseModel):
    device: str                 # FK to a Device.name (cross-validated)
    phase: int | str            # 1, "rb1", "0-prereq", etc.
    action: str = "configure"   # "configure" / "verify" / "wait" / etc.
    cli: list[str]              # platform-native lines, in order
```

`phase` is `int | str` because some changes have phased rollouts
(`1`, `2`) and rollback often uses string IDs (`rb1`, `rb2`).

### Post-check (verification commands)

```yaml
post_check:
  - device: R1
    check_id: bgp_up
    description: BGP session ESTABLISHED to R4
    command: "show bgp summary | match 10.1.24.2"
    expected_pattern: "Established"
  - device: R1
    check_id: route_rx
    description: Receive R4 loopback
    command: "show route 4.4.4.4/32"
    expected_pattern: "4.4.4.4/32"
```

```python
class PostCheck(BaseModel):
    device: str                 # FK to Device.name
    check_id: str               # human / machine identifier
    description: str
    command: str                # platform-native verify command
    expected_pattern: str       # default: substring; "re:..." prefix = regex
```

`expected_pattern` is a string. Convention: bare string = substring
match; `re:^Established$` prefix = regex. Tools dispatch.

### TVT — Test Verification Tracker

```yaml
tvt:
  - test_id: T1
    description: BGP r1↔r4 established
    expected: "Established both sides"
    severity: blocker            # blocker | warn | info — open string,
                                  # tools may treat unknown as "info"
    actual_lab: null              # filled by ops-lab
    actual_prod: null             # filled by prod ops post-deploy
    status: PENDING               # PENDING | PASS | FAIL | BLOCKED

required_tests: [T1, T2, T4]      # which test_ids must PASS for green
optional_tests: [T3, T5]
```

```python
class TvtRow(BaseModel):
    test_id: str
    description: str
    expected: str
    severity: str = "info"        # free-form; convention: blocker/warn/info
    actual_lab: str | None = None
    actual_prod: str | None = None
    status: str = "PENDING"       # free-form; convention: PENDING/PASS/FAIL/BLOCKED
```

Severities and statuses are strings (not Literal) — different
domains may want different vocabularies (e.g. some shops want
"P0/P1/P2"). Tools render whatever's there.

### Lab + prod sections (filled post-validation)

```yaml
lab:
  verdict: PENDING                # PENDING/PASS/FAIL/BLOCKED
  ran_at: null                    # ISO datetime
  lab_name: null                  # CLAB lab name used
  snapshot_id: null               # netops snapshot referenced
  journal:                        # per-step record of what lab actually did
    - step: generate_clab_topology
      args: { nodes: [R1, R4], lab_name: cab_001_lab }
      result_summary: { links_found: 1, snapshot_id: 2026-03-30_2210 }
      timestamp: 2026-04-27T12:30:00Z
    - step: generate_srl_lab_config
      args: { nodes: [R1, R4], loopbacks: [1.1.1.1, 4.4.4.4], asns: [65000, 65001], intent_type: ebgp_direct }
      result_summary: { configs_emitted: 2 }
      timestamp: 2026-04-27T12:31:00Z
  diagnosis: ""                   # free-form, present when verdict != PASS
  recommendation: []              # list of action items

prod:
  verdict: PENDING
  ran_at: null
  journal: []
  diagnosis: ""
  recommendation: []
```

```python
class JournalEntry(BaseModel):
    model_config = ConfigDict(extra="allow")
    step: str                   # tool name or workflow phase
    args: dict[str, Any] = Field(default_factory=dict)
    result_summary: dict[str, Any] = Field(default_factory=dict)
    timestamp: datetime | None = None


class ExecutionRecord(BaseModel):
    """Filled by ops-lab (lab-side) or prod runbook (prod-side)."""
    verdict: str = "PENDING"            # PENDING/PASS/FAIL/BLOCKED
    ran_at: datetime | None = None
    lab_name: str | None = None         # only for lab-side
    snapshot_id: str | None = None      # netops snapshot ref (lab-side)
    journal: list[JournalEntry] = Field(default_factory=list)
    diagnosis: str = ""
    recommendation: list[str] = Field(default_factory=list)
```

### Top-level model

```python
class CabTcf(BaseModel):
    schema_version: int = 1
    change_id: str
    title: str
    created_by: str
    created_at: datetime
    risk_class: str = "medium"      # convention: low/medium/high/blocker

    intent: Intent
    devices: list[Device]
    implementation: list[CliBlock] = Field(default_factory=list)
    rollback: list[CliBlock] = Field(default_factory=list)
    post_check: list[PostCheck] = Field(default_factory=list)
    tvt: list[TvtRow] = Field(default_factory=list)

    required_tests: list[str] = Field(default_factory=list)
    optional_tests: list[str] = Field(default_factory=list)

    lab: ExecutionRecord = Field(default_factory=ExecutionRecord)
    prod: ExecutionRecord = Field(default_factory=ExecutionRecord)

    @model_validator(mode="after")
    def _check_device_fks(self) -> "CabTcf":
        """Cross-FK: every CLI block / post-check / referenced device
        must exist in `devices`."""
        names = {d.name for d in self.devices}
        for ref in (
            *self.implementation,
            *self.rollback,
            *self.post_check,
        ):
            if ref.device not in names:
                raise ValueError(
                    f"references unknown device {ref.device!r}; "
                    f"known: {sorted(names)}"
                )
        return self
```

The `model_validator` runs at load + write time. Catches dangling
references early (e.g. sim mistypes a device name).

## Tools (only what sim and lab need)

R90's first cut focuses on **sim and lab consumption**. Markdown
rendering stays with writer's existing LLM capability — not part
of R90.

| Tool | Owner | Purpose |
|---|---|---|
| `tcf_emit(...) -> str` | ops-analyze | Build a CabTcf model + serialize to YAML. Pydantic validates. Returns file path. |
| `tcf_load(path) -> CabTcf` | shared | Read YAML + parse into CabTcf. Errors surface invalid schema clearly. |
| `tcf_to_r88_args(tcf) -> dict` | ops-lab | Derive `generate_clab_topology` input from `devices[*].name + change_id`. |
| `tcf_to_r89_args(tcf) -> dict` | ops-lab | Derive `generate_srl_lab_config` input from `devices[*]` + `intent`. Falls through with explicit error if intent.type not supported by R89. |
| `tcf_to_r90_args(tcf) -> dict` | ops-lab (R90 follow-on) | Derive rollback generator input from `rollback[*]`. |
| `tcf_record_lab_run(path, journal, tvt_results, verdict, diagnosis, recommendation)` | ops-lab | Atomic update of `lab.*` fields + tvt[*].actual_lab/status. Writes back to same .tcf.yaml file. |
| `tcf_diff_spec_vs_lab(tcf) -> str` | ops-lab (Phase 4) | Structured comparison: tvt expected vs lab actual; intent fields vs lab journal args. Returns markdown table. |

Markdown rendering is **NOT** a tool here. The writer agent's LLM
can read the YAML file and produce whatever document the user asks
for — runbook, exec summary, change record, whatever.

## Why we don't build `tcf_to_markdown`

User-facing doc is rendered on demand by the writer agent:

```
user: "render cab_r1_r4_ebgp_001 as a CAB approval doc"
ops-orchestrator → writer subagent
writer:
  - read_file(exports/cab/cab_r1_r4_ebgp_001.tcf.yaml)
  - LLM: "given this YAML, produce a markdown CAB approval doc"
  - format_and_export(...)
```

Why this beats a deterministic jinja template:

* **Layout flexibility** — same TCF can render as runbook / exec
  summary / Slack post / PR description, all via prompt variation
* **No template maintenance** — every new field doesn't need template update
* **Writer agent already exists** — uses LLM rendering daily
* **Audit trail stays clean** — TCF is the source of truth; markdown
  is a transient view

The tradeoff is rendering quality varies with LLM. We're OK with
that because the **structured contract is already lossless** — if
markdown looks weird, regenerate. The TCF doesn't drift.

## Open design questions

1. **Intent vocabulary**: keep open string (current proposal) or
   maintain a registered enum that tools dispatch on?
   Open: more flexible, allows experimental change types
   Enum: catches typos at TCF write time
   **Decision**: open string. Tools that consume specific intent
   types raise clear errors when intent.type is unknown. The cost
   of catching typos at write time is too rigid for the variety of
   real changes.

2. **Phase ordering**: numeric phases sort naturally; string phases
   (`rb1`) require explicit ordering. Worth defining a
   `phase_order: int` separate from `phase_id: str`?
   **Decision**: defer. Single `phase: int | str` field works for
   90% of cases. If we hit ordering issues, add `phase_order` then.

3. **Per-device platform extras**: e.g. `extras.junos_version: 21.4`
   for nuanced platform behavior. Should this live in the device
   record or in a separate `platform_facts` section?
   **Decision**: inside `Device.extras`. Keeps device record
   self-contained.

4. **TCF location**: `exports/cab/<change_id>.tcf.yaml` flat, or
   `exports/cab/<change_id>/spec.tcf.yaml` directory-per-change so
   we can stash supplementary files (renders, lab logs, etc.)?
   **Decision**: directory. Allows on-disk co-location of TCF +
   renders + lab logs without naming collisions.

5. **Backward compat for existing markdown**: write a one-shot
   `markdown_to_tcf` LLM converter, or just ignore?
   **Decision**: ignore. Demo runs forward on TCF; existing markdown
   stays as historical reference, not actively used.

## What this enables (downstream wins)

1. **Real spec ↔ lab diff** (Phase 5): structured comparison, no
   LLM parsing. Discrepancies surface in a column, not a paragraph.
2. **Rollback validation** (R90): `rollback[]` is already in the
   contract; lab can deterministically push the rollback CLI and
   verify reversion. Adds one TVT row, no new design work.
3. **Idempotency check**: re-apply implementation after rollback;
   `tvt[T_idempotent]` confirms convergence.
4. **Cross-deploy audit**: `actual_lab` vs `actual_prod` per TVT
   row creates the chain of custody from sim → lab → prod.
5. **Aggregation**: querying "all CAB specs with risk_class=high
   that failed lab in 2026Q2" becomes a SQL-like operation on a
   collection of YAML files (or a future TCF table).
6. **LLM doesn't write the contract**: Pydantic builds it. Sim's
   LLM just supplies values into a builder pattern, schema is
   guaranteed.
