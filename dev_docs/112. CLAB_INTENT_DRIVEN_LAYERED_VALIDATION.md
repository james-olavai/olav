# 112. CLAB redesign — intent-driven layered validation (minimal scaffold, staged inject, per-layer confirm)

**Status**: 2026-08-01 — **design closed and built; verified on real hardware.**
All §11 questions decided (Q1 hybrid scaffold; Q2 ruleset + `hier_config` §5;
Q3+Q6 predicate library + bounded wait §8; Q4 supported-set discovery §9.1;
Q5 interface remap §6.2; Q7 dependency closure §6.1).

Shipped in olav-ent `feat/clab-twin-builder`: the offline deterministic builder
(parse / bucket / slice / remap / intent / assemble / synth), the runtime
(clab lifecycle client, image scanner + eligibility gate, node CLI, runner with
staged confirm, both Path A and Path B injection), the §9.1 capability
discovery cache, and per-device multi-vendor support (ios + junos rulesets;
PAN-OS/Fortinet/Check Point are deliberately T0-only). Suite 90/90 including
real-hardware integration.

**Verified end to end on real Cisco IOL** via containerlab 0.77.0 /
clab-api-server v0.5.1: intent YAML → slice prod config → layer bucket →
interface remap (`Gi1/0/1`→`Ethernet0/1`) → **synthesize a peer that does not
exist in prod** → deploy a 2-node topology → push config → per-layer confirm →
**BGP established**. No LLM authors any config.

Two real-hardware findings are folded into the design: **§8.0** (there is no
NOS-CLI-over-API for cisco_iol — config/confirm go over SSH from the clab mgmt
net; Path A) and **§8.0 / runner `iol_binds`** (on a user-defined bridge the
container resolv.conf points at docker's embedded DNS `127.0.0.11` and IOL
takes a general-protection fault in libc — the node must get a resolv.conf that
avoids it, alongside the operator's iourc licence).
**Supersedes**: the **full-running-config reproduction** orientation of
dev_docs/96 §5 (whole-config normalization) and §6 (single end-of-run round-trip
diff). The rest of dev_docs/96 — native-image policy, scan-only image firewall,
resolver/gate, honest degrade, "LLM never authors config" — is **kept and built
on**, not replaced.
**Reshapes (not replaces)**: the shipped **TCF** contract
(`olav-ent/.../cab/tcf_schema.py:CabTcf`) becomes the intent spec (§2). The
SRL-translation carriers inside it (`ExecutionRecord.*_lab`, `intent_registry.
TWO_DEVICE_INTENTS` hardcode) are retired.
**Supersedes (already dead)**: SR-Linux-as-universal-target + cross-vendor
translation (dev_docs/73 §3-§4, `cab/postcheck_translate.py`,
`cab/freeform_translator.py`, `lab/srl_render.py`) — already declared wrong by
dev_docs/96 §8; not revived here.
**Builds on**: shipped `sim`/Batfish (`batfish_q`, the T0 primary validator),
shipped clab REST integration (`service_call("containerlab", ...)`), the
shipped **audit author/runner + declarative-profile** pattern
(`.olav/workspace/audit/`), the deterministic-transform principle (R88), and
small-model-first governance.
**Owners**: netops + lab maintainers

## 0. Why the previous model was still the wrong shape

dev_docs/96 correctly killed cross-vendor→SRL translation and moved to native
images with zero translation. But it kept one load-bearing assumption from the
SRL era that is itself the next problem:

> **Both SRL and dev_docs/96 try to reproduce the device's *entire*
> running-config in the lab** — SRL by translating it, dev_docs/96 by
> normalizing it. The unit of work is "the whole config".

Operator-observed reality that breaks this:

1. **Even same-OS-family, simulator ≠ real device.** IOL is not IOS-XE 17.9;
   cEOS is not a 7280R; n9kv is not a real 9500. Some prod commands are simply
   not supported by the lab image, or behave differently. A whole-config push
   therefore *always* produces a non-empty round-trip diff, most of it on lines
   that have nothing to do with what the operator is validating.
2. **~90% of that incompatibility lives in peripheral / hardware config** —
   PoE, stacking, transceiver, breakout, `speed forced`, QoS-hardware, platform
   stanzas. dev_docs/96 §5 already denylists these, but a subtraction approach
   still starts from "everything" and fights every version-drift line the
   denylist didn't anticipate.
3. **That is not how a network engineer uses a lab.** They do not clone a
   device. They stand up the *minimal* base needed to make a change meaningful,
   apply *only the change*, and check *only the thing under test*.

### The governing principle of this redesign

> **The lab validates a change, not a device. Build the minimal L1–L4 scaffold
> the change needs, inject it layer by layer confirming each layer took, then
> apply the change delta and validate only the intended outcome. Compatibility
> is never promised — it is observed at the exact layer and line where it
> breaks, and honestly degraded when it can't be met.**

This shrinks the compatibility surface by an order of magnitude (you stop
pushing the peripheral config where incompatibility concentrates), turns "the
twin is subtly wrong" into "L2 trunk command X is not supported by this image"
(a precise, actionable locus), and asks the *right* question: *does this change
achieve my intent on this vendor's real OS?*

## 1. Compatibility is three orthogonal axes (do not conflate them)

The original failure conflated three independent problems of wildly different
difficulty into one action ("translate the config").

| Axis | Question | Difficulty | Old SRL answer | Correct answer |
|---|---|---|---|---|
| **A. Platform → kind** | Does a lab node type even exist for this device? | Easy (lookup + image present) | force everything to `srl` | resolver table + scan gate (dev_docs/96 §2/§4, **kept**) |
| **B. Config syntax loads** | Will the config actually load into the node? | Depends on same-vendor | cross-vendor semantic translation (**unsolvable**) | **same-vendor ⇒ no translation**; minimal scaffold in the most-portable CLI subset |
| **C. Behavioural fidelity** | Once loaded, does it behave like the real device? | Medium (version drift) | SRL runs a *different* OS (wrong question) | run the device's **own** OS; confirm behaviour per layer |

Axis A is a table. Axis B collapses to "no translation" the moment the target is
the same vendor (dev_docs/96's win). Axis C is where residual same-vendor
incompatibility lives, and is what this doc's **layered confirm** addresses:
incompatibility surfaces at the layer it occurs, not as an opaque whole-twin
gap.

## 2. The intent spec + author/runner architecture

The lab is driven by a single declarative **intent spec** — authored up front,
executed deterministically — following the shipped **audit** pattern
(`.olav/workspace/audit/`): a declarative profile (`profiles/*.md` YAML
frontmatter) written by an **author** sub-agent and executed by a **runner**
sub-agent. The intent spec is the clab equivalent of an audit profile.

### 2.1 Reshape the existing TCF, don't invent a new file

The intent spec already exists at ~80% as the shipped **TCF**
(`olav-ent/.../cab/tcf_schema.py:CabTcf`). We reshape it rather than create a
parallel format:

| Intent field the operator wants | TCF today | Action |
|---|---|---|
| device platform | `Device.platform` | keep |
| device **model** | buried in `Device.extras` | **promote to first-class** (drives the resolver; never trust `platform` — dev_docs/96 §1) |
| count | `len(devices)` + `intent_registry.require_two_devices` | keep count; **drop the `TWO_DEVICE_INTENTS={"ebgp_direct"}` hardcode** (source of the eBGP-only limitation) |
| L1–L4 config | `implementation: [CliBlock{device,phase,cli}]` — **authored config + numeric phase** | **reshape**: `base` declares *object references per layer*, not authored lines (§6); `delta` carries the change verbatim |
| test commands | `pre_check` / `post_check.command` | keep |
| expected results | `post_check.expected_pattern` / `tvt.expected` | keep |
| config to validate | `tvt` + `required_tests` | keep |

**Retired from TCF** (they encode the dead SRL-translation model):
`ExecutionRecord.implementation_lab / rollback_lab / post_check_lab`
(`tcf_schema.py:363-393` — "translate Junos/IOS → SRL"), and the
`intent_registry.TWO_DEVICE_INTENTS` hardcode. This also completes half of
dev_docs/96 §8's "retire the translation path".

### 2.2 The intent spec shape (audit-profile-style)

```yaml
name: bgp-neighbor-add-r1
schema_version: 2
scope:
  devices:
    - {name: R1, platform: cisco_ios, model: C9500-24Y4C, role: scope}
    - {name: R2, platform: cisco_ios, role: synthetic}   # invented peer (§7)
# base = per-layer OBJECT REFERENCES, NOT config lines.
# A deterministic slicer pulls exactly these stanzas from running-config (§6).
base:
  L1: {interfaces: [GigabitEthernet1/0/1]}
  L3: {interfaces: [GigabitEthernet1/0/1], vrfs: [default], igp: ["ospf 1"]}
  L4: {bgp: {local_as: 65001, neighbors: [10.0.0.2]}}
delta:                              # the change under test — the ONLY authored block
  device: R1
  cli: |
    router bgp 65001
     neighbor 10.0.0.3 remote-as 65003
per_layer_confirm:                  # deterministic predicate per layer (§8)
  L1: {command: "show ip interface brief", expect: "GigabitEthernet1/0/1.*up.*up"}
  L3: {command: "show ip ospf neighbor",  expect: "FULL"}
  L4: {command: "show ip bgp summary",     expect: "Estab"}
tests:                              # change validation (= TCF tvt/post_check)
  - {test_id: T1, layer: delta, command: "show ip bgp summary",
     expect: "re:10\\.0\\.0\\.3\\s+4\\s+65003.*Estab", severity: blocker}
```

Load-bearing choices: `base.L*` holds **object references** (interface names,
VRF, IGP process, BGP neighbors), never config lines; `delta` is the only
authored block, pushed same-vendor verbatim; `model` is first-class (feeds the
resolver); `role: synthetic` marks an invented peer (§7).

### 2.3 Author / runner split (maps 1:1 to audit)

| clab role | audit analogue | Responsibility |
|---|---|---|
| **lab-author** sub-agent | `audit-author` | Produce the intent spec — **WHAT**: which devices/platform/model, which per-layer objects, what to test, expected results. LLM allowed here (intent understanding). |
| **lab-runner** sub-agent | `audit-runner` (`map_engine.py`) | Execute deterministically: slice → assemble per-layer files → push via clab REST → confirm layer → next; then push delta → run tests → report. **No config authoring.** |

### 2.4 The deterministic-slice boundary (the stability watershed)

> **Config extraction is a deterministic script driven by the intent's declared
> object references — never the LLM eyeballing running-config and wildcard-
> picking lines.**

The LLM's job ends at declaring scope in the intent spec (`base.L3.interfaces:
[Gig1/0/1]` = WHAT). A deterministic `slice_running_config(device, refs)` parses
the running-config parse tree and extracts exactly those stanzas (HOW), then
assembles the per-layer config files. This is non-negotiable and follows the
governing principle (dev_docs/96 §0): the moment an LLM picks/edits config
lines, cross-turn forgetting, gap-filling, and multi-attempt variance return —
the exact instability that sank the SRL path. "Agent uses a wildcard CLI to
extract" is fine **iff** the extractor is a script the agent merely
parameterizes with the declared scope; it is not fine if the LLM does the
line-picking.

## 3. Pipeline

Four phases. Phases A–B are the **lab-author**'s output (the intent spec);
phases C–D are the **lab-runner**'s deterministic execution. **The LLM appears
only in Phase A (understanding human intent) and in narration/verdict. All
config selection, slicing, bucketing, and transformation is deterministic
Python** (§2.4), consistent with R88 and dev_docs/96 §0.

```
A. Intent & scope        (lab-author; LLM allowed — intent understanding)
   parse change request → intent spec {devices+model, per-layer object refs,
                                        delta, per_layer_confirm, tests}
   resolve model → clab kind + confirm image scanned present (dev_docs/96 resolver/gate)
        │  (ineligible → degrade to T0 Batfish, logged reason; never fake PASS)
        ▼
B. Layer plan            (deterministic, no LLM)
   slice_running_config(device, refs) → per-layer BASE files  (§2.4, §6)
   split BASE (scaffold) vs DELTA (change under test)  (§6)
   synthesize minimal peers required to exercise the change  (§7)
        ▼
C. Deploy + staged confirm   (lab-runner; deterministic — §8.0 Path A)
   render BASE+DELTA → node startup-config; deploy twin (clab REST, image scanned)
   for layer in [L1, L2, L3, L4]:
       wait (bounded) → predicate check  (SSH/scrapli show to node mgmt IP)
           PASS → next layer
           FAIL → STOP AT THIS LAYER, report the exact layer/line  (§8, §9)
        ▼
D. Validate the change + destroy
   run intent `tests` (SSH show + assert) → PASS/FAIL + per-layer receipts → destroy
```

Contrast with dev_docs/96 §7 Experiment Runner: same build/run split, same
native-image + verbatim-same-vendor spine, but the *input* changes from
"normalized whole running-config" to "minimal scaffold + delta", and validation
changes from "one end-of-run round-trip diff" to "incremental per-layer
confirm".

## 4. Why this dissolves the compatibility problem (not just moves it)

- **You stop pushing the config where incompatibility concentrates.** The
  peripheral/hardware stanzas (§0 #2) are simply never part of a minimal
  scaffold — they are not needed to make a routing/switching change testable.
- **The core subset you *do* push (interface / ip / vlan / stp / ospf / bgp /
  route-policy / acl) is the most portable across same-vendor OS trains** — the
  least likely to hit an unsupported command.
- **Layer-by-layer confirm converts a diffuse fidelity gap into a precise
  locus.** "The twin is subtly wrong" becomes "L2: `switchport trunk allowed
  vlan add` not accepted by this image" — recorded, surfaced, actionable.
- **Residual incompatibility has a clean decision rule** (§9): if it's in the
  scaffold, substitute an equivalent that reaches the same layer state; if it's
  in the delta, that *is* the finding — degrade honestly.

## 5. Layer decomposition (deterministic stanza bucketing)

### 5.1 Config source

The slice source is the stored running-config text:
`netops.raw_output_store` (`command='show running-config'`, columns
`device_name / command / raw_output / platform`). **Trap (tables.py:58-70):**
that table's `snapshot_id` is a *last-writer label*, not a partition key —
`WHERE snapshot_id = <latest>` silently returns 0 config rows when the latest
import was state-only. Resolve via `batfish_q._latest_snapshot_with_configs()`
or match on `command` only. (This exact trap caused the Batfish "No valid
configurations" saga.)

### 5.2 Parser

**Decided: `hier_config` (Apache-2.0).** dev_docs/96 §5's "reuse Batfish parse
tree" does **not** hold — Batfish produces a *semantic vendor model*, not
line-preserving CLI you can select-and-reassemble. Slicing needs a hierarchical
CLI parser that (a) selects stanzas by object reference, (b) emits verbatim CLI,
(c) diffs two configs (reused for the §8 round-trip). `hier_config` does all
three and its permissive license is safe for the enterprise wheel. Batfish stays
for T0 *semantic* analysis only. (No hierarchical config parser was in deps
before this — it is a new dependency, netops/lab-scoped.)

### 5.3 Ruleset — home, shape, versioning

The stanza→layer ruleset is **data, not code** (CLAUDE.md "steer via config, not
code"): versioned per-platform-family YAML at
`olav-ent/workspace/netops/lab/rulesets/layer_map.<family>.yaml`
(`family` ∈ {ios, nxos, junos}, selected via `canonicalize_platform()`). Loaded
by a deterministic `bucket_config(parse_tree, ruleset)`.

```yaml
ruleset_version: 1
family: ios
peripheral_denylist:            # → dropped with a receipt, never bucketed
  ["^power inline", "^ *stackwise", "^ *transceiver", "^ *speed forced", "^hw-module"]
layers:                         # ordered, first-match-wins; parent=stanza header, child=in-container subcommand
  L1: {parent: ["^interface "],      child: ["^ *no ?shutdown", "^ *speed ", "^ *duplex "]}
  L2: {parent: ["^vlan ", "^spanning-tree", "^interface Port-channel"],
       child: ["^ *switchport", "^ *channel-group"]}
  L3: {parent: ["^vrf ", "^router ospf", "^router eigrp", "^ip route", "^interface Vlan"],
       child: ["^ *ip address", "^ *ip ospf", "^ *vrf forwarding"]}
  L4: {parent: ["^router bgp", "^route-map", "^ip prefix-list", "^ip access-list"],
       child: ["^ *neighbor", "^ *network ", "^ *redistribute", "^ *address-family"]}
unclassified_action: surface    # never guess
```

| Layer | Owns | Example stanzas / subcommands |
|---|---|---|
| **L1** | physical / link bring-up | `interface … no shutdown`, `speed`/`duplex` (only if under test), breakout **excluded** (hardware) |
| **L2** | switching | `vlan`, `switchport …`, `spanning-tree …`, `channel-group`/`port-channel`, SVI base |
| **L3** | addressing + IGP + VRF | `ip address`, `vrf`, `router ospf`/`eigrp`, `ip route`, SVI `ip address` |
| **L4 / overlay** | services under test | `router bgp`, `route-map`/`policy`, `prefix-list`, `ip access-list`, redistribution |

Version discipline: `ruleset_version` is part of `twin_id` (§6) → any rule change
yields a new, reproducible twin. Additive rule (new stanza → existing layer) =
minor; moving a stanza between layers or editing the denylist = behaviour change
→ version bump + note. Per-family files because `router bgp` (ios) vs
`feature bgp` (nxos) vs `protocols bgp` (junos set-form) diverge; Phase 1 = ios
only.

### 5.4 Bucketing algorithm — container stanzas split per line

The load-bearing subtlety: a container stanza is **split across layers by
child line**, not assigned whole. An `interface Gig1/0/1` block → header +
`no shutdown` to **L1**, `switchport …` children to **L2**, `ip address …`
children to **L3**. The ruleset's `parent`/`child` split expresses this; the
algorithm walks each stanza's children and classifies per line.

Rules:
- Bucketing is a pure function of the parse tree + a versioned ruleset — zero
  LLM, byte-reproducible.
- Hardware/peripheral stanzas (PoE, stacking, transceiver, QoS-hardware) are
  **not bucketed into any layer** — they are dropped with a receipt (dev_docs/96
  §5 denylist, reused). If a change genuinely targets one of these, that device
  is **T1-ineligible** → degrade to T0 with reason.
- A stanza that cannot be classified → `unclassified`, surfaced, never guessed
  (dev_docs/96 §5 constraint #1, reused).

### 5.5 Governance

A governance test runs `bucket_config` over a corpus of real fleet configs and
asserts every stanza lands in **exactly one** of {a layer, denylist,
unclassified} — no silent double-assignment, no crash. The fleet-wide
`unclassified` count is a tracked metric (a rising count means the ruleset is
stale against the fleet). Reachability: the test drives `bucket_config` through
the lab-runner Phase B entry point, not by importing it directly (DoD).

## 6. BASE vs DELTA split

The single most important action in Phase B.

- **DELTA** = the config the change request adds/modifies/removes (the intent
  spec's `delta` block). This is *what we are validating*. Pushed verbatim
  (same-vendor) in Phase D. Never synthesized, never approximated.
- **BASE** = the minimal scaffold across L1–L4 that must exist for the DELTA to
  be meaningful and checkable (the interfaces the change touches, the VRF/VLAN
  it lives in, the IGP that must be up for a BGP session to form, etc.),
  declared as per-layer object references in the intent spec's `base` block and
  **sliced from the running-config by a deterministic script** (§2.4).

The split is derived from the DELTA's dependencies: walk the DELTA's referenced
objects (interfaces, VRFs, neighbors, prefix-lists, route-maps) and pull only
the base context those references need. Everything else in the prod config is
irrelevant to this validation and is excluded.

**Scaffold source (§11 Q1, decided): hybrid.** Scope devices' BASE is
sliced-from-prod (fidelity where it matters); surrounding peers are synthesized
(§7). This keeps prod-faithful config on the devices under test while avoiding
importing the change's entire real neighborhood.

> **`twin_id = hash(scope, delta, base_refs, ruleset_version, refs_map_version)`**
> — idempotent and content-addressed (dev_docs/96 §5 #2, reused). Re-running is
> byte-identical; "multiple attempts / variance" is not a concept because no LLM
> is in the build loop.

### 6.1 Dependency closure — the slice must load clean

`base.L*` names seed objects, but those objects reference others (`router bgp`
neighbor → `route-map` → `prefix-list`; `interface` → `vrf`; SVI → `vlan`). The
slicer pulls the seeds' **transitive dependency closure**, or the sliced base
has dangling references and fails to load.

Algorithm (deterministic, monotone; a visited-set handles reference cycles):

```
seeds   = objects named in base.L* refs ∪ objects referenced by delta
closure = seeds ; frontier = seeds
while frontier:
    deps     = ⋃ extract_refs(obj) for obj in frontier
    frontier = deps − closure ; closure += frontier
emit = verbatim stanzas of closure, layer-bucketed (§5)
```

`extract_refs` is driven by a versioned **reference grammar** (same shape as the
layer ruleset) `lab/rulesets/refs_map.<family>.yaml`, declaring, per stanza
type, which child line names a dependency and of what type:

```yaml
# refs_map.ios.yaml
router bgp:
  "neighbor \\S+ route-map (\\S+) (in|out)": route-map
  "neighbor \\S+ prefix-list (\\S+) (in|out)": ip prefix-list
  "neighbor \\S+ update-source (\\S+)":        interface
route-map:
  "match ip address prefix-list (\\S+)":       ip prefix-list
  "match community (\\S+)":                     ip community-list
interface:
  "vrf forwarding (\\S+)":                      vrf
  "channel-group (\\d+)":                       Port-channel
```

**Two stop rules** (without them the closure drags in the whole config and we
are back to the old whole-config model):

1. **Layer ceiling** — the closure only pulls objects that bucket to L1–L4
   (§5). A dependency that buckets to peripheral/denylist (e.g. a
   `service-policy` → hardware QoS policy-map) **stops**, is marked with a
   receipt, and is not dragged in.
2. **Scope boundary** — the closure walks references *within* a scope device.
   When a reference points *out* of scope (a `neighbor` on a peer device), the
   closure stops and **hands off to synthesis** (§7) — it does not slice another
   prod device. This is where §6.1 meets §7.

Honesty & idempotence: a reference to an object absent from the running-config
(dangling in prod, or a typo) → surfaced as `unresolved_ref`, **never silently
dropped, never invented** (same discipline as `unclassified`, §5). The closure
is a pure function of `(running-config, base_refs, delta, refs_map_version)`;
`refs_map_version` joins `twin_id`, so it is byte-reproducible.

Governance invariant: for a corpus change, the sliced base has **zero dangling
references** — every referenced object is either in the closure, dropped with a
receipt at the layer ceiling, handed to synthesis at the scope boundary, or
surfaced as `unresolved_ref`. "The sliced config loads clean" is the acceptance
assertion.

### 6.2 Interface remap (prod name → lab name; deterministic bijection)

Prod interface names (`GigabitEthernet2/0/1` = stack/slot/port) must become the
lab kind's names (IOL flat-grouped `Ethernet0/1`; n9kv `Ethernet1/1` ≈ identity
for Nexus; cEOS `Ethernet1`). This is the transform dev_docs/96 §5 listed and
§10 Q1 left open. It is load-bearing: the same recorded map drives config
rewrite (push), topology link naming, round-trip normalization, and predicate
scoping.

**Minimal scaffold makes it tractable:** we remap only the few *in-scope*
physical interfaces (slice ∪ delta ∪ topology — typically 2–4/device), never the
whole chassis. So it is a **deterministic allocation**, not a fixed global
table:

```
remap(device, kind):
  prod_intfs = sort(physical intfs in slice ∪ delta ∪ topology)  # canonical (speed,stack,slot,port) sort = determinism anchor
  lab_pool   = interface_pool(kind)                              # IOL: Et0/0,Et0/1,Et0/2,Et0/3,Et1/0,…
  map = {prod: lab_pool[i] for i, prod in enumerate(prod_intfs)}
  # logical interfaces pass through verbatim (NOT allocated from the pool):
  #   Loopback<N> / Vlan<N> / Port-channel<N> — IOL/n9kv/cEOS accept these as-is
  return map    # recorded bijection in the twin manifest
```

The canonical sort is the determinism anchor (same input set ⇒ same
assignment); the map joins `twin_id`. **Only physical interfaces are
remapped** — `update-source Loopback0`, `interface Vlan10` stay verbatim, so the
remap surface is small. Downstream consumers: config-slice rewrite (prod→lab),
clab topology links (lab names), the §8 round-trip (normalize lab
running-config lab→prod before diffing → the diff is "empty modulo the known
interface remap", exactly dev_docs/96 §6), and predicate scoping (resolve a
prod interface name to its lab name to check the right port).

**Honest degrade instead of a blanket stacked-device exclusion.** dev_docs/96
§10 Q1 offered "mark stacked devices ineligible in Phase 1"; the minimal-scaffold
approach makes that unnecessary. The rule:

> Stack/slot identity is **discarded** in the remap **unless the change under
> test depends on it** (StackWise validation, or behaviour that varies by stack
> member — which IOL cannot model anyway) → then the device is **T1-ineligible
> → degrade to T0** with reason, via §9's existing "change targets a
> hardware/peripheral property" hook.

An ordinary routing/switching change that merely lives on `Gi2/0/1` is fine —
the remap flattens the stack member. Pool exhaustion (in-scope physical
interfaces exceed the kind's pool — rare under minimal scaffold) → the same
honest degrade.

Home: the per-kind interface pool is data (folded into the resolver's kind entry
or `lab/rulesets/intf_pool.<kind>.yaml`); the canonical interface-name parser
(prod name → `(family, stack, slot, port)`) is a small per-family deterministic
function. Governance: the map is a **bijection** (injective + every in-scope
prod intf mapped), `prod→lab→prod` is identity, logical interfaces are
unchanged, and a stacking-dependent change is correctly gated ineligible.

## 7. Synthetic peers (new; not in dev_docs/96)

A layered validation of a change on device R1 often needs a counterpart that
exists **only to exercise the change**, not to be reproduced. Validating "add a
BGP neighbor on R1" requires an R2 that will *accept* the session so L4 can
confirm `established`. That R2 is **synthesized** — a minimal peer with just
enough L1–L4 to bring the session up — not sliced from prod. In the intent spec
it carries `role: synthetic` (§2.2).

- Synthetic peers are generated deterministically from the DELTA's requirements
  (peer AS, peer IP, address-families needed) + the topology.
- They are clearly labelled `synthetic` in the manifest and excluded from
  round-trip fidelity accounting (§8) — we do not claim fidelity for a node we
  invented.
- This is the piece that makes "validate a change with 2 devices" possible
  without standing up the change's entire real neighborhood.

## 8. Staged inject + per-layer confirm (the fidelity mechanism)

Replaces dev_docs/96 §6's single end-of-run round-trip diff with an incremental
gate. Each layer has a **deterministic predicate** (the intent spec's
`per_layer_confirm`) — a show command + a Python check — no LLM judging
convergence.

| Layer | Inject | Confirm predicate (deterministic) |
|---|---|---|
| L1 | links / interfaces up | `show interface` → oper up/up for scope ports |
| L2 | vlan / trunk / stp / port-channel | VLAN present; trunk allowed-list correct; PO members up; STP not blocking scope |
| L3 | ip / vrf / igp | IGP adjacency up; expected connected + IGP routes present |
| L4 | bgp / policy / acl (base side + synthetic peer) | BGP session `established`; base prefixes exchanged |
| **Δ** | **the change delta** | **the intent spec's `tests`** (the actual thing under test) |

Loop: `inject → wait (bounded) → predicate`. PASS → next. FAIL → **stop at this
layer**, emit which layer, which command, which predicate failed. This is the
honest, precise replacement for "the twin looks wrong somewhere".

Per-layer confirm also **incrementalizes the round-trip check**: dump the lab
device's running-config, normalize it (via `hier_config`, §5.2) and diff against
intent, so a "line did not take" is attributed to its layer rather than buried
in an end diff.

### 8.0 How config actually reaches a clab node (verified on real .12)

Real-hardware spikes (containerlab 0.77.0 / clab-api-server v0.5.1, cisco_iol
L2) established a hard constraint that shapes the runner:

> **There is no NOS-CLI-over-API for cisco_iol.** The clab REST `exec`
> (`POST /api/v1/labs/{name}/exec`) runs in the container **shell** for every
> kind — `show version` returns *"executable not found in $PATH"*. `fcli` is
> SR-Linux-only (500 for cisco_iol). The IOS CLI is reachable only by **SSH to
> the node management IP** (`172.20.20.x`), which is routable **only from a host
> on the clab management network** (the clab host; a production OLAV must be
> deployed with that reachability — from an off-net sandbox the mgmt IP is "no
> route to host").

This splits the mechanism (Path A, the shipped path; Path B deferred):

- **Inject = startup-config at deploy.** The assembled BASE + DELTA config
  (§6, interface-remapped) is written into each node's **startup-config**; clab
  loads it at boot. This is the containerlab-idiomatic, API-reachable injection
  path — no per-line CLI push required. Base loads in one shot; the layered
  model is preserved as **staged *confirm*** (below), not staged push.
- **Confirm = SSH/scrapli to the node mgmt IP** (creds: clab `cisco_iol`
  default `admin`/`admin`), run from a host on the clab mgmt net. The runner
  polls `show` per layer L1→L4 and stops at the first failing layer.
- **Path B (SHIPPED): true staged *push*** — `run_validation(staged_push=True)`
  pushes one layer, confirms it, then pushes the next. Higher fidelity: a
  refused line is attributed to the layer being built (receipts tagged
  `[L3] …`), and a later layer is never built on an unconfirmed one. Both paths
  are verified on real Cisco IOL; Path A remains the default (cheaper, and what
  the startup-config route does).

### 8.1 Predicate library (data, audit-profile style)

A predicate = show command + parser + assertion over parsed rows +
bounded-wait policy + evidence. Two tiers: **library defaults** per
`(layer, family, check_kind)` (reusable, tested) and **intent overrides** (the
spec's `per_layer_confirm` / `tests` for change-specific checks). Predicates are
**data files** — same spirit as audit's `jobs:` (a declarative check in YAML) —
at `lab/predicates/<family>/<layer>.yaml`:

```yaml
family: ios
layer: L4
checks:
  - id: bgp_sessions_established
    command: "show ip bgp summary"
    parser: ntc:cisco_ios_show_ip_bgp_summary     # reuse netops TextFSM templates
    assert: "all(scope_rows: state == 'Established')"
    wait: {timeout_s: 120, poll_interval_s: 5}     # required for convergence-class (Q6)
    evidence: [bgp_neighbor, neighbor_as, state]
    severity: blocker
```

Assertion DSL stays minimal: `all`/`any`/`exists`/`count` over parsed fields,
scoped to the change's objects; a Python fallback covers the rare check the DSL
can't express.

### 8.2 Execution path (verified reality)

- **Run** the show command over **SSH to the node mgmt IP** (scrapli, driver by
  family — `cisco_iosxe` for IOL), **not** the clab REST `exec` (that is the
  container shell, not the NOS CLI — §8.0). This runs from a host on the clab
  mgmt network. The old SRL `exec_on_node` (base64-`sr_cli` over clab exec,
  `exec_on_node.py:14-32`) is SRL-specific and is **not** the path here.
- **Parse** via the netops TextFSM / ntc-templates pipeline — the same templates
  that build `netops.v_show_ip_bgp_summary_auto` etc. — so lab output parses
  identically to prod (reuse **and** a fidelity win: lab state becomes directly
  comparable to prod). Exact reuse entry point to confirm at build.
- **Assert** → boolean + evidence rows.

### 8.3 Bounded wait (Q6, folded in)

Convergence-class layers (L3 IGP, L4 BGP) cannot be checked once. Predicate
execution polls `exec → parse → assert` until true OR `timeout_s`, at
`poll_interval_s`. Non-convergence checks (L1 link up, L2 VLAN present) use a
short timeout. A confirm predicate without a wait policy is meaningless for a
protocol → `wait` is required on convergence-class checks.

### 8.4 One engine, two roles

- `per_layer_confirm` (staged-build gate): "did the layer come up?" → PASS
  proceeds, FAIL stops at the layer.
- `tests` (post-delta): "did the change achieve intent?" → the verdict.

Same `execute → parse → assert → evidence` engine; they differ only in timing
and whether they gate progression.

### 8.5 Build order & governance

Build order follows the fleet (IOS first; demonstration change = BGP):
L1 (`show ip interface brief`) → L3 (`show ip ospf neighbor`, `show ip route`)
→ L4 (`show ip bgp summary`, `show ip bgp`); L2 (`show vlan brief`,
`show interfaces trunk`, `show spanning-tree`) arrives with the switching line.
Governance: every predicate is exercised through the lab-runner Phase C entry
(not direct import, DoD); and a test asserts every `(layer, family)` the ruleset
can build has ≥1 default predicate — no layer may be buildable yet
unconfirmable.

## 9. Unsupported-command handling & honest degrade

When a push (any layer) hits a command the lab image rejects:

- **In BASE (scaffold)** → substitute a functional equivalent that reaches the
  same layer state (the base is scaffolding; only the *state* matters, not the
  literal line). Record the substitution with a receipt. If no equivalent
  reaches the required state → the layer's predicate will fail → stop and
  report.
- **In DELTA (under test)** → this is a **real finding**: the change/feature
  cannot be behaviourally validated on this image. Do **not** substitute (that
  would validate a different change). Degrade to T0 Batfish for what it can
  answer, or report "behavioural validation unavailable for this feature on
  <image>", with the exact rejecting command. **Never fake a PASS**
  (dev_docs/96 §3 honest-degrade, reused).

Eligibility gate (per device, dev_docs/96 §9, extended): kind resolves + image
scanned present + version close + **the DELTA's commands are in the image's
supported set** (or substitutable at the base layer). Else → T0.

### 9.1 How the gate knows the supported set — discovery, not a maintained table

The governing principle (§0) is "compatibility is observed, not promised", so a
hand-maintained capability table is the wrong default — it drifts silently and
reintroduces the "promise" this design kills. Three layers, discovery over
assertion:

1. **Pre-flight gate (cheap, coarse)** — before paying lab spin-up: kind
   resolves + image scanned present + version-close **only**. No command-level
   check here; command support is too fine to know cheaply/reliably ahead of
   time. (dev_docs/96 §9, unchanged.)
2. **Inject-time accept-and-catch (ground truth, primary)** — the answer to "how
   do we know a command is supported" is *we push it and observe*. Staged inject
   (§8) and the delta push already exec each block; a rejected command surfaces
   immediately with the exact line. Delta rejection → real finding → honest
   degrade (§9). Zero maintenance, always correct.
3. **Discovered capability cache (optimization, never a gate)** — accept/reject
   outcomes from (2) populate a cache keyed by `(image_digest,
   command_signature)`. Later runs *may* consult it to pre-warn and degrade
   before spin-up. Rules: (a) populated by observation only, **never
   hand-authored**; (b) a miss ⇒ proceed to accept-and-catch (the cache only
   accelerates, never falsely gates); (c) digest-keyed, so a new image
   invalidates cleanly. `command_signature` is a normalized command *shape*
   (`neighbor <ip> remote-as <asn>` → `bgp.neighbor.remote-as`, via
   `hier_config` parse), so the cache generalizes across instances of one
   feature.

This deliberately mirrors `batfish_capability`'s two-layer model (static map +
live `fileParseStatus`) but **drops the static map** — the maintained-table trap
— keeping only the observed layer + a self-populating cache. The "fast probe"
option folds in as optional cache warming (push representative feature lines to
a throwaway node on first encounter of an image); the correctness path is always
accept-and-catch.

> **Scanner dependency — RESOLVED in build.** Layer (3) needs the
> `image_digest` of what is present on the clab host. clab-api-server exposes
> `GET /api/v1/images`, so `scanner.scan_images()` reads tags **and digests**
> from there (`ScanResult.digest_for()`) — settling dev_docs/96 §10 Q2 in
> favour of the live-scan option.

**Shipped** (`twin/capability.py`, verified on real hardware). Refusals follow
the §9 split:

- a refused **DELTA** line → `RunResult.rejections`; the run does **not** pass
  (the change cannot be validated on that image);
- a refused **BASE** line → `RunResult.base_substitutions`, a scaffold receipt;
  the base only has to reach the layer *state*, so the layer predicate decides.

This immediately caught a previously-silent incompatibility: the routed IOL
image rejects `no switchport` (it is a router — interfaces are already L3),
while the L1/L3 predicates still confirm the intended state, so it is correctly
a receipt rather than a failure.
