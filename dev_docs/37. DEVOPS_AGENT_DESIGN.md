## 1. 定位

| Agent | 做什么 | 对话对象 |
|-------|--------|---------|
| quick | 快速查询 | 用户 |
| ops | 网络运维（分析/探测/漂移/实验室） | 网络设备 |
| infra | 查询外部管理系统 | API 服务 |
| audit | 合规审计 + 报告 | DB 数据 |
| **devops** | **编写自动化脚本 — 知道用户的设备、服务、拓扑** | **用户环境** |

**devops 不是通用代码助手。** 它和 ChatGPT/Copilot 的区别：它知道你有哪些设备、跑什么服务、用什么 IP、什么拓扑。生成的脚本不是泛化模板，是针对你环境的可直接运行的自动化。

---

## 2. 环境感知能力

devops agent 通过 static_context 和 core 工具获取用户环境信息：

| 数据源 | 内容 | 获取方式 |
|--------|------|---------|
| `netops.devices` | 设备清单（主机名、IP、平台、角色） | `execute_sql` |
| `netops.topology_links` | 网络拓扑（谁连谁、什么接口） | `execute_sql` |
| `services.yaml` | 已注册服务（NetBox、InfluxDB、CLAB 的 URL 和认证） | `execute_sql` 或读文件 |
| `infra/references/*.md` | 各服务 API endpoint 参考 | static_context |
| `v_*_auto` 视图 | BGP/OSPF/接口等实时状态（快照） | `execute_sql` |
| `nornir/hosts.yaml` | SSH 凭证和设备分组 | 读文件 |

**用户说"帮我写个脚本备份所有设备配置"，agent 知道你有 R1-R4(Cisco) + SW1-SW2(Arista)，生成的脚本直接包含正确的设备名、IP、平台特定命令。**

### system.md

```markdown
# DevOps Automation Expert

You write production-quality automation scripts tailored to the user's actual
infrastructure. You are NOT a generic code assistant — you know the user's
devices, services, topology, and credentials configuration.

## Environment Discovery (ALWAYS do first)

Before writing any script, discover the user's environment:

```python
# What devices exist?
execute_sql("SELECT hostname, ip_address, platform, role FROM netops.devices")

# What's the topology?
execute_sql("SELECT source_device, destination_device, discovery_protocol FROM netops.topology_links")

# What services are registered?
execute_sql("SELECT name, endpoint, readonly_only FROM api_registry.services")
```

Use this data to generate scripts with REAL device names, IPs, and service URLs.
NEVER use placeholder values (10.0.0.1, example.com, YOUR_TOKEN).

## Script Standards

Every generated script MUST:

1. **Shebang + strict mode**: `#!/bin/bash\nset -euo pipefail`
2. **Env var validation**: Required vars checked with `${VAR:?message}`
3. **Dependency check**: `command -v <tool> || exit 1`
4. **--dry-run support**: Print what would happen without executing
5. **Error handling**: Per-operation error check with clear messages
6. **Summary**: Count of success/failed/skipped at the end
7. **Idempotent**: Safe to run multiple times (check-before-create)

## Script Types

| Request | Output | Key Tools |
|---------|--------|-----------|
| "备份所有设备配置" | bash + SSH (platform-aware show commands) | execute_sql → run_python_code → format_and_export |
| "把设备导入 NetBox" | bash + curl (NetBox API) | execute_sql → run_python_code → format_and_export |
| "设置 InfluxDB 监控" | bash + curl (InfluxDB API) | execute_sql → run_python_code → format_and_export |
| "写 Ansible playbook" | YAML (Ansible) | execute_sql → run_python_code → format_and_export |
| "迁移脚本：站点 A→B" | bash (multi-step orchestration) | execute_sql → run_python_code → format_and_export |

## Output

ALWAYS export scripts via `format_and_export(subdir="scripts", format="sh")`.
NEVER output scripts as chat text. Scripts must be files the user can review and execute.

## API Write Operations in Scripts

When generating scripts that modify external APIs (NetBox, InfluxDB, etc.):
- Scripts MUST include `--dry-run` flag
- Scripts MUST check HTTP response codes
- Scripts MUST include Authorization header via env var (not hardcoded tokens)
- Scripts SHOULD check if resource exists before creating (idempotent)

You do NOT need --enable-api-write to GENERATE scripts.
--enable-api-write is only for the infra agent executing api_request writes directly.
Your scripts are always exported as files for the user to review and run.
```

## 4. 与其他 Agent 的关系

```
用户: "帮我写个脚本把所有设备配置备份到 Git"

devops agent:
  1. execute_sql → 获取设备清单（R1-R4 Cisco, SW1-SW2 Arista）
  2. run_python_code → 生成 bash 脚本:
     - SSH 到每台设备（IP 从 DB，平台特定命令）
     - 保存 show running-config 输出
     - git add + commit + push
     - --dry-run 模式打印会做什么
  3. format_and_export(subdir="scripts") → exports/scripts/backup-configs-to-git.sh
```

```
用户: "写一个 Python 脚本把 OSPF 邻居数据推到 InfluxDB"

devops agent:
  1. execute_sql → 获取 OSPF 邻居数据 + InfluxDB 服务信息
  2. run_python_code → 生成 Python 脚本:
     - 从 DuckDB 读 v_ospf_neighbors_auto
     - 格式化为 InfluxDB line protocol
     - POST 到 InfluxDB /api/v2/write
     - --dry-run 只打印 line protocol 不发送
  3. format_and_export(subdir="scripts", format="py") → exports/scripts/push-ospf-to-influxdb.py
```

**devops 不直接操作设备或 API。** 它生成脚本，用户自己执行。

## 5. devops vs infra 边界

| | infra | devops |
|---|-------|--------|
| **核心动作** | 查询 API（api_request GET） | 生成脚本（run_python_code → format_and_export） |
| **写操作** | 直接执行（需 --enable-api-write + 三级门控） | 生成脚本文件（用户手动执行） |
| **输出** | 查询结果（表格/JSON） | 可执行脚本文件 (.sh/.py/.yaml) |
| **安全模型** | api_request 三级门控 | 脚本只生成不执行，用户审查后运行 |
| **环境感知** | 知道 API endpoint | 知道设备 + 拓扑 + 服务 + 凭证配置 |

## 8. 统一编码 agent — 核心架构决策

### 8.1 洞察

config/creator、config/system、config/discovery 本质上和 devops 做同一件事：**读上下文 → 写代码**。区别只是 reference 不同。

```
之前（4 个编码角色）：
  config/creator    → 读 OpenAPI → 写 Python @tool       ← 已退役
  config/system     → 读 workspace → 写健康检查           ← 编码职责
  config/discovery  → 读 DB schema → 写 SQL 视图          ← 编码职责
  devops            → 读设备/服务 → 写自动化脚本

之后（1 个编码 agent + N 个 reference）：
  devops + references/netbox_api.md        → 写 API 集成脚本
  devops + references/health_check.md      → 写健康检查脚本
  devops + references/schema_discovery.md  → 写 schema 映射脚本
  devops + references/backup_guide.md      → 写设备备份脚本
```

### 8.2 什么移入 devops

| 原 agent | 编码职责 → devops reference | 确定性 @tool → 保留在 core |
|----------|---------------------------|--------------------------|
| config/creator | ~~Python @tool 生成~~ | — （退役，api_request 替代） |
| config/system | 写健康检查脚本 → reference | `check_health`、`audit_workspace` 保留 |
| config/discovery | 写 schema 视图 → reference | `classify_field`、`create_unified_view` 保留 |

### 8.3 新领域 = 新 reference（不是新 agent）

```bash
# 需要 Prometheus？加 reference
olav registry register http://prometheus:9090
# → infra/references/prometheus_api.md → devops 自动获得 Prometheus 脚本能力

# 需要 Ansible？加 reference
# → devops/references/ansible_patterns.md
```

### 8.4 最终架构

```
OLAV Platform (core)
├── api_request / execute_sql / run_python_code / format_and_export
├── check_health / audit_workspace / classify_field（确定性工具保留）
├── registry register（CLI）
│
├── quick    ← 快速问答
├── infra    ← API 查询 + 写操作（--enable-api-write）
├── devops   ← 统一编码 agent（reference 驱动）
│   └── references/ 决定编码领域
├── ops      ← 网络运维（analysis/probe/diff/lab）
├── audit    ← 合规审计（designer/auditor）
└── config   ← 平台管理（瘦 agent，编码已移入 devops）
```

## 9. 打包与发布

### 9.1 分包决策

| 包 | 包含 agent | 发布渠道 | 版本 |
|----|-----------|---------|------|
| **olav** (pip) | core, quick, config, infra, devops, audit | PyPI | v0.13 |
| **olav-netops** | ops (analysis/probe/diff/lab) + netops 表/采集 | GitHub | v0.13 |

**分界线：** 需要 SSH/Nornir/TextFSM/CLAB → olav-netops。其他 → olav 核心。

### 9.2 为什么 infra + devops + audit 在核心包

| agent | 外部依赖 | 适用范围 | 理由 |
|-------|---------|---------|------|
| infra | 无（api_request = core 工具） | 任何 REST API 服务 | 装 olav 就能 `registry register` + 查询 |
| devops | 无（run_python_code = core 工具） | 任何 DB 数据 | 装 olav 就能写环境感知脚本 |
| audit | 无（DuckDB 查询 = core） | 任何 schema | 装 olav 就能设计/执行审计 profile |
| ops | nornir, netmiko, ntc-templates | 仅网络设备 | 需要额外安装 olav-netops |
