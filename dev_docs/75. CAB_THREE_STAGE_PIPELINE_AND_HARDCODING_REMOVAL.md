# R-CAB-THREE-STAGE — Analyzer / Sim / Lab pipeline + hardcoding removal

**Status:** DESIGN (2026-05-12). Not yet implemented.
**Author:** OLAV Team (J. Chen).
**Successor to:** dev_docs/65 (R90 TCF), 73 (R-AGENT-HIERARCHY), and the
accreted pile of hardcoded patches shipped during the production-readiness
pass (F, A, B, C, D rounds — see `dev_docs/00 § ISSUE-CAB-*`).

**Trigger:** sim+lab E2E demo on 2026-05-12 succeeded as a happy path
but exposed an architectural smell: every gap we close requires another
guardrail bolted onto a monolithic `sim` sub-agent. A 9-gap audit of
the produced TCF (`exports/cab/r2-r3-ebgp/spec.tcf.yaml`) showed 8/9
were code-contract gaps in a single LLM loop carrying too many
responsibilities.

## TL;DR

Split the current `sim` sub-agent (which does investigation + reasoning
+ intent selection + plan emission in one LLM loop) into three sub-agents
with **typed contracts and explicit submit/reject channels**:

```
Analyzer (LLM)  ──draft──▶  Sim (Python)  ──tcf──▶  Lab (Python+infra)
        ◀──reject_with_blockers──     ◀──reject_with_diagnosis──
```

Each stage has ONE responsibility. LLM only runs at the Analyzer stage
(where fuzziness is appropriate). Sim and Lab are deterministic. The
accreted hardcoded patches (F.3 hard-error, F.2 lint, ARCH-40 guards,
narrative_mode flag, etc.) are inventoried and either **promoted to
their natural home** (Sim's invariants) or **removed entirely** if the
new contract eliminates the underlying gap.

**Principle: LLM-first where reasoning helps; Python-strict at
contract boundaries.** No new hardcoded prompt patches — when a gap
appears, fix the contract, not the prompt.

## Why the current `sim` sub-agent doesn't scale

The current `netops/sim` sub-agent owns:

1. **Investigation** — calls `inspect_devices` / `inspect_topology` etc.
2. **Reasoning** — judges feasibility, picks intent
3. **Selection** — chooses intent type + args
4. **Simulation** — supposedly runs `run_python_simulation`, almost never does
5. **Emission** — calls `submit_change_plan`, triggers Python rendering

All five happen inside one LLM chat history. Every constraint we add
(F.3 grounding, F.2 CLI lint, ARCH-40 device guards, the proposed
`require_directly_connected`, capture-into pre_check, deeper TVT) is
a guardrail on this single loop:

| Patch we shipped | What it really compensates for |
|---|---|
| F.3 facts_cited hard-error | No independent Discovery stage |
| F.2 `validate_prod_cli_completeness` | No independent Validation stage |
| `return_direct=True` on render_report | LLM-driven narration in agent's last turn |
| `narrative_mode: jinja` | LLM rendering at all where Python could |
| ARCH-40 `require_two_devices` | No Feasibility stage with invariants |
| Evidence-only correlation prompt | LLM reasoning + narration in same step |
| `task_return_direct: true` | Orchestrator paraphrasing sub-agent output |
| Author auto-selftest | No contract that author-written SQL validates |
| Author `facts_cited` schema rules | Same as F.3 root cause |

Each patch is locally correct but globally a symptom of the same
disease: **stuffing a multi-phase task into a single LLM loop and
fixing the spillover with prompts and lints**. The cost compounds:

- N new intents → N×M lint files
- Each lint = one more place to maintain
- Small models (gemma4:31b) drift in long loops (T15 33%
  non-determinism, T11 compound-instruction loss) — guardrails can't
  fix attention budget
- Failures are hard to localise — was it Discovery, Reasoning,
  Selection, or Emission that erred?

## Proposed three-stage architecture

### Stage 1 — Analyzer (LLM-driven, fuzzy)

**Role:** the researcher. Reads the user prompt, gathers facts, drafts
a proposal explaining *what* and *why*.

**Sub-agent name:** `netops/analyzer` (renamed from `sim`; existing
`netops/analyze` is a different concern — pure read-side investigation;
this analyzer is change-plan-specific and may share inspector tools).

**Tools:** `inspect_devices`, `inspect_topology`, `inspect_routing`,
`inspect_interfaces`, `inspect_blast_radius`, `submit_draft` (new),
`receive_rejection` (new — see §Submit/Reject below).

**LLM mandate:**
* Free-form chain-of-thought across inspector calls.
* Drafts in natural language + a structured envelope.
* Does NOT write CLI. Does NOT compute lab_subnet. Does NOT finalise
  feasibility. (Sim is the truth oracle for all three.)

**Output schema — `DraftChangePlan` (Pydantic):**

```python
class DraftChangePlan(BaseModel):
    user_prompt: str
    devices_in_scope: list[str]
    proposed_intent: Literal["ebgp_direct", "ibgp_direct",
                             "static_route_add", "vlan_add",
                             "ospf_*",  # placeholder
                             "freeform_cli"]
    intent_args: dict[str, Any]  # per-intent fields the LLM picked
    rationale: str                # markdown
    facts_collected: FactsEnvelope  # required, schema-enforced
    revision_round: int = 0       # increments on Sim rejection
    previous_blockers: list[str] = []  # only set when revision_round > 0
```

The `FactsEnvelope` is a typed structure containing the full output of
every inspect_* tool the Analyzer chose to call. **Schema-enforced**
means: Analyzer can't `submit_draft` with empty facts — this replaces
F.3 hard-error which was retrofitted onto an untyped tool.

### Stage 2 — Sim (Python-driven, truth oracle)

**Role:** the truth oracle. Validates the draft against world model,
runs simulation, materialises the TCF.

**Sub-agent name:** `netops/sim` (kept, but completely rewritten — old
"sim" only inspected and emitted; new "sim" actually simulates).

**Tools exposed to LLM:** none. Sim is a **Python pipeline**, not an
LLM agent. It's invoked as a skill script:
`finalize_tcf_from_draft(draft_path) → spec_path | RejectionReport`.

**Pipeline internals (pure Python, deterministic):**

```
draft.yaml
  ↓
(a) Feasibility checks per intent
    ├── ebgp_direct  → require_two_devices + require_different_asn
    │                + require_directly_connected
    ├── ibgp_direct  → require_two_devices + require_same_asn
    │                + require_igp_reachability_for_loopbacks
    ├── static_route_add → require_next_hop_resolves
    ├── vlan_add        → require_vlan_id_unique
    └── freeform_cli    → validate_prod_cli_completeness (existing F.2 lint)
  ↓
(b) NetworkX simulation
    - mutate in-memory graph per intent
    - run invariants:
        * no_routing_loop
        * no_device_isolation
        * existing_sessions_unaffected (or list the ones impacted)
        * convergence_estimate from BFS depth
    - output SimulationReport
  ↓
(c) TCF rendering (existing tcf_writer)
    - implementation: deterministic templates (already exists)
    - rollback:        captured-state-aware (NEW — see §Hardcoding removal)
    - pre_check:       derived from feasibility-required preconds
    - post_check:      derived from SimulationReport.expected_state
    - tvt:             expanded from SimulationReport.risk_flags
  ↓
spec.tcf.yaml (lab block empty)
```

**Reject conditions** (returns `RejectionReport` instead of `spec.tcf.yaml`):
- Any (a) check fails
- (b) detects invariant violation
- Draft `intent_args` insufficient for the rendering template

### Stage 3 — Lab (Python + infra, reality check)

**Role:** the digital twin. Deploys the TCF, runs pre/post checks,
records actual lab evidence into `spec.tcf.yaml.lab`.

**Sub-agent name:** `netops/lab` (unchanged — current implementation
is already a clean atomic skill script).

**Tools:** `validate_tcf_in_lab` (existing).

**Reject conditions** (returns `LabRejectionReport` instead of PASS):
- Pre-check fail (now a hard fail — no more silent downgrade)
- Deploy/push failure
- Post-check pattern miss
- TVT actual_lab evidence missing or contradictory

## Submit / Reject contracts

The three stages communicate via **typed envelopes** persisted to disk
(under `exports/cab/<change_id>/`) so each stage is independently
restartable and the orchestrator can route the next call by reading the
envelope, not from LLM chat history.

### Forward submissions

| From | To | Envelope | Trigger |
|---|---|---|---|
| Analyzer | Sim | `draft.yaml` (DraftChangePlan) | `submit_draft` tool call |
| Sim | Lab | `spec.tcf.yaml` (CabTcf, lab block empty) | finalize_tcf_from_draft success |
| Lab | (terminal) | `spec.tcf.yaml` (lab block populated, verdict=PASS\|FAIL) | validate_tcf_in_lab completion |

### Backward rejections

| From | To | Envelope | Trigger |
|---|---|---|---|
| Sim | Analyzer | `rejection_sim.yaml` (RejectionReport) | feasibility or simulation fail |
| Lab | Sim | `rejection_lab.yaml` (LabRejectionReport) | pre_check / deploy / post_check / TVT fail |
| Lab | Analyzer (escalation) | same `rejection_lab.yaml` | Sim can't auto-revise (intent-level issue) |

### RejectionReport schema (Sim → Analyzer)

```python
class RejectionReport(BaseModel):
    rejected_at: datetime
    rejected_by: Literal["sim", "lab"]
    draft_change_id: str
    revision_round: int

    blockers: list[Blocker]  # at least one
    suggested_alternatives: list[SuggestedAlternative]
    hard_blocked: bool       # True → Analyzer cannot fix, escalate to human

class Blocker(BaseModel):
    code: str                # "not_directly_connected" / "same_asn" / etc.
    message: str             # human-readable
    evidence: dict[str, Any] # facts that prove the blocker

class SuggestedAlternative(BaseModel):
    intent: str              # "ibgp_direct"
    rationale: str           # why this would work
    required_changes: dict[str, Any]  # what Analyzer needs to do differently
```

**Analyzer's behaviour on receiving rejection:**
1. Read `rejection_sim.yaml` via `receive_rejection` tool.
2. Read structured `blockers` + `suggested_alternatives`.
3. Revise the draft (new `revision_round`, copy `previous_blockers`).
4. Re-`submit_draft`.

**Maximum revision rounds:** 3 (configurable via profile). After max
retries, the chain is **hard blocked** and surfaced to the user with
the accumulated blocker history.

### LabRejectionReport schema (Lab → Sim or Analyzer)

```python
class LabRejectionReport(BaseModel):
    failed_at: datetime
    failed_phase: Literal["pre_check", "deploy", "push",
                          "post_check", "tvt"]
    failed_check_id: str | None
    error: str
    captured_evidence: dict[str, str]  # actual lab outputs
    routing_hint: Literal["sim_can_revise", "analyzer_intent_wrong",
                          "infra_problem"]
```

Lab routes back to Sim for revisable issues (e.g. add missing CLI line
via existing `tcf_patch_block`); routes back to Analyzer for
intent-level mistakes; surfaces infra problems to user directly.

## LLM-first principle

Where reasoning is fuzzy and contextual, prefer LLM with strong
contracts over deterministic rules. Where logic is invariant (a
mathematical truth about the network), use Python.

| Decision | Owner | Rationale |
|---|---|---|
| What did the user actually ask for? | LLM (Analyzer) | NL parsing is LLM's strength |
| Which devices are in scope? | LLM (Analyzer) | Cross-references prompt + DB |
| Which inspectors to call? | LLM (Analyzer) | Adaptive based on partial findings |
| Is the proposed intent feasible? | Python (Sim) | Mathematical invariants, not opinions |
| What lab_subnet to allocate? | Python (Sim) | ARCH-36 pool allocator |
| What CLI lines to emit? | Python (Sim) | Templates already exist |
| Will this introduce a routing loop? | Python (Sim) | networkx graph theorem |
| What's the executive summary? | LLM (Analyzer or Lab) | Narrative quality matters |
| Why did the lab post_check fail? | LLM (Lab diagnostic) | Diagnostic reasoning over evidence |

**No more LLM patches.** When a future failure mode appears:
- Is it a contract gap? → tighten the schema between stages.
- Is it a Sim invariant gap? → add a Python check.
- Is it an LLM-decision-too-hard problem? → narrow the Analyzer's
  decision space via better DraftChangePlan schema, do NOT add a
  prompt patch.

### Update steps

1. **Catalog every guide that names `submit_change_plan`, `sim sub-agent`,
   `tcf_emit_from_sim`, or `freeform_cli` slots**.

2. **Rewrite each affected guide** to reference the new
   Analyzer / Sim / Lab split. Specifically:
   - "When user wants a change plan → delegate to `netops/analyzer`"
     (not `sim`)
   - "Analyzer drafts; Sim materialises; never mix the two"
   - Examples updated to call `submit_draft` not `submit_change_plan`

3. **Delete obsolete guides** that purely document old behaviour:
   - any `*_change_plan_emit_tcf.guide.yaml` style guides that teach
     the old single-step flow
   - any guide that documents `_INSPECT_CITE_RE` or `facts_cited` as
     LLM-visible patterns

4. **Re-import** via `olav kb import-guides .olav/workspace` so
   LanceDB reflects the rewritten files. Old memory rows for deleted
   guides are auto-pruned by the importer (R102 ingestor knows
   `guide_<agent>_<intent>` IDs are file-derived).

5. **Verify** with `olav --agent core "How do I plan a network change?"`
   on a fresh memory — the recall should surface the new Analyzer
   routing guide, not stale references to `submit_change_plan`.

### Memory hygiene policy going forward

When a code-side contract changes (schema bump, intent added/removed),
update or delete the corresponding `.guide.yaml` **in the same PR**.
The rule:

> A memory guide that describes obsolete code is worse than no guide —
> it actively misleads the LLM and the user. Delete > rewrite > leave
> stale.

### Cutover strategy

Old `submit_change_plan` API stays compatible for one release cycle,
internally **forwards to `submit_draft` then auto-invokes
`finalize_tcf_from_draft`** behind the scenes (so external callers
keep working). The deprecation warning logs "submit_change_plan is
deprecated; use submit_draft + finalize" on every call.

After two releases without external caller complaints, delete the
shim.

## Acceptance criteria for production-ready

This refactor closes a cluster of L4 / L5 concerns documented under
ARCH-41. A successful landing means:

1. **Zero hand-wave** — every "BLOCKED" outcome cites a structured
   blocker code; every PASS shows a structured SimulationReport.
2. **Zero LLM-authored CLI** for templated intents (ebgp_direct,
   ibgp_direct, static_route_add, vlan_add). Only `freeform_cli`
   intent has LLM CLI, with the existing lint as defense.
3. **Diff-able TCFs** — two runs over the same draft produce
   byte-identical `spec.tcf.yaml` (modulo timestamp). Tests in
   `test_sim_determinism.py`.
4. **Localised failure** — when a run fails, the operator can tell
   which stage (Analyzer / Sim / Lab) without reading a chat log.
5. **Roll-back is real** — pre_check captures original state;
   rollback uses captured values; revert leaves the device in the
   exact pre-state it found.
6. **TVT is deep** — at least 4 test cases per intent type
   (session-up, route-exchange, no-flap-impact-on-existing,
   convergence-time). `actual_lab` populated with real evidence,
   not dashes.
7. **No `# TODO` / `# FIXME` / orphan-comment cruft** introduced by
   this refactor; pre-existing markers reviewed and either fixed or
   deleted.
8. **Memory is current** — every `.guide.yaml` referencing CAB flow
   names Analyzer / Sim / Lab, not the old monolithic sim.
