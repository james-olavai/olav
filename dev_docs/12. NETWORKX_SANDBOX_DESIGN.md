## 0.1 Package Ownership Boundary

本文件定义的是 **NetOps domain capability**，不属于 `olav-platform` core。

归属划分如下：

- **属于 `olav-platform` 的底座**：agent orchestration、sandbox runtime、shared audit/state、通用 query/control-plane framework
- **属于 `olav-netops` 的能力**：topology graph projection、network investigation helpers、protocol-aware troubleshooting logic、blast-radius analysis、CLAB escalation recommendation
- **当前仓库中的混合现实**：文档中引用 `src/olav/core/simulation/*` 等路径，是过渡期实现位置，不代表最终仍应驻留 platform core

## 1. Positioning

OLAV should adopt **Option A + Option C** as the long-term architecture for control-plane safety:

1. **Option A:** build an OLAV-native protocol-semantic layer on top of canonical state
2. **Option C:** use ContainerLab as the strict validation path before CAB approval

Under this architecture, the **NetworkX sandbox is not the final proof engine**.

Its role is:

- assist Ops investigations with graph-anchored reasoning
- reduce LLM hallucination by binding reasoning to real network state
- produce candidate remediation or change plans
- estimate blast radius and likely control-plane impact
- decide whether CLAB validation is required

The NetworkX sandbox is therefore an **Ops troubleshooting and planning assistant**, not a Batfish-equivalent verifier.

OLAV must remain **advisory-only** for production networks:

- it may analyze production state
- it may generate candidate plans and risk assessments
- it may recommend validation steps
- it must not write configuration to production devices
- final execution remains the responsibility of a human network engineer

---

## 2. Why 09 Exists

The old CAB draft mixed two different jobs into one path:

1. exploratory reasoning during incident handling or change planning
2. strict verification for CAB approval

Those jobs must now be separated.

### 2.1 Ops Job

During Ops work, the agent needs a fast environment that can:

- inspect current state
- correlate topology and protocol symptoms
- test multiple hypotheses
- generate a candidate fix sequence
- explain why a plan is likely to work

This job benefits from a flexible sandbox.

### 2.2 CAB Job

Before approval, the system needs a stricter path that can:

- replay the proposed change in an isolated lab
- collect post-change evidence
- validate assertions against observed state
- reject changes whose lab evidence contradicts the prediction

That job belongs to CLAB and is specified in `10. CLAB_CAB_AGENT_DESIGN.md`.

## 3. Core Design Principle

The sandbox must prevent the LLM from drifting away from the actual network state.

So the sandbox must be designed as:

```text
real data anchors
    +
canonical graph builder
    +
lightweight protocol-aware helpers
    +
LLM hypothesis generation and explanation
```

Not as:

```text
LLM imagines protocol behavior from vague prompts
```

The sandbox exists to keep the LLM constrained by evidence.

---

## 4. Responsibility Boundary

### 4.1 What the Sandbox Must Do

The Ops NetworkX sandbox must:

1. read real state from DuckDB using semantic views
2. build a stable `nx.MultiDiGraph` from `topology_links`
3. attach canonical control-plane attributes to nodes and edges
4. support deterministic helper calculations for common protocol questions
5. let the agent run structured investigations over that graph
6. output candidate plans, risks, and required validations

### 4.2 What the Sandbox Must Not Claim

The sandbox must not claim that it has proven:

1. full BGP convergence correctness
2. full OSPF / IS-IS semantic correctness
3. data-plane reachability proof
4. policy correctness across all vendor semantics
5. CAB-grade safety by graph reasoning alone
6. authority to execute production changes

The sandbox may propose. It may prioritize. It may narrow the search space.

It does not replace strict validation.
It also does not replace the human change executor.

---

## 5. Data Contracts

The NetworkX sandbox must align to the new schema strategy.

### 5.1 State Contract

Default reads must come from semantic views such as:

- `v_interfaces`
- `v_bgp_neighbors`
- `ospf_neighbors` or future `v_ospf_*`
- future `v_routes`, `v_policy_*`, `v_prefix_sets`

Raw reads from `parsed_outputs.parsed_data` are allowed only as fallback and must be labeled as raw evidence.

### 5.2 Graph Contract

The sandbox graph must be built from `topology_links`, not from ad hoc joins or prompt-time assumptions.

The graph builder should produce a canonical `nx.MultiDiGraph` with:

- device nodes
- interface-aware edges when present
- relationship types
- discovery source
- confidence and status metadata

### 5.3 Attribute Contract

Protocol state attached to graph objects must come from canonical accessors, not free-form prompt logic.

Examples:

- BGP neighbor session state
- BGP peer AS and prefix counters
- OSPF neighbor state and interface cost
- route-source indicators
- ownership or role metadata from inventory

## 6. Architecture

```text
DuckDB semantic views + raw fallback
        ↓
canonical graph builder
        ↓
Ops NetworkX sandbox
        ├─ graph analytics
        ├─ protocol-aware helper functions
        ├─ hypothesis ranking
        ├─ candidate fix generation
        └─ validation recommendation
        ↓
Ops Agent response
        ├─ probable root cause
        ├─ candidate action plan
        ├─ risk estimate
        └─ whether CLAB CAB validation is required
```

The key point is that the sandbox is an **analysis stage**, not the final decision stage.
It must never be treated as a production change writer.

## 7. Required Internal Layers

The sandbox should be implemented with four internal layers.

### 7.1 Graph Builder Layer

Responsible for:

- loading topology from `topology_links`
- normalizing device and interface identity
- constructing `nx.MultiDiGraph`
- caching or memoizing graph snapshots for one investigation run

### 7.2 Control-Plane Projection Layer

Responsible for projecting semantic state into graph-attached objects.

Examples:

- attach BGP peer state to the edge between two devices
- attach OSPF interface cost to the relevant adjacency edge
- attach loopback or router-id metadata to device nodes

This layer is not yet a full protocol solver. It is a canonical projection layer.

### 7.3 Deterministic Helper Layer

Responsible for bounded, deterministic computations that reduce LLM hallucination.

Examples:

- shortest path on the current adjacency graph
- impacted-neighbor expansion after a device or link failure
- candidate next-hop enumeration
- prefix ownership lookup
- route-policy object lookup and dependency tracing

These helpers should use code, not prompt text, to do the calculation.

### 7.4 Agent Reasoning Layer

Responsible for:

- selecting which helper to call
- combining graph facts with raw evidence
- generating explanations and candidate plans
- deciding whether the answer is strong enough or must be escalated to CLAB

This is where the LLM adds value.

## 8. Relationship to the Future Protocol-Semantic Layer

Option A means OLAV should eventually add a protocol-semantic engine above the canonical graph and canonical state.

That future layer is specified in `11. CONTROL_PLANE_SEMANTIC_ENGINE.md` and should cover at least:

1. BGP propagation and best-path reasoning
2. IGP path computation
3. route-policy semantic evaluation
4. reachability / blackhole / loop checks

The NetworkX sandbox should be designed so that this layer can be called from inside the sandbox when available.

Until then, the sandbox should clearly mark its reasoning as one of:

1. graph heuristic
2. deterministic helper analysis
3. protocol-semantic engine result

This distinction is mandatory to keep evidence honest.

## 9. Output Contract

The sandbox must not return only prose. It should return structured findings.

Recommended output shape:

```json
{
  "reasoning_mode": "graph_assisted_ops",
  "state_inputs": {
    "topology_snapshot_id": "2026-03-20",
    "views_used": ["v_interfaces", "v_bgp_neighbors", "topology_links"],
    "raw_fallback_used": false
  },
  "hypotheses": [
    {
      "name": "R1_to_R3_path_depends_on_R2_bgp_edge",
      "confidence": 0.73,
      "evidence": ["bgp session down on R2", "single alternate path absent"]
    }
  ],
  "candidate_plan": [
    "restore BGP session R2<->R3",
    "verify prefixes from AS65003 are received on R2",
    "re-check downstream next-hop selection"
  ],
  "risk_assessment": {
    "blast_radius": ["R1", "R2", "R3"],
    "risk_level": "high"
  },
  "requires_clab_validation": true
}
```

This gives the user something actionable while making the escalation path explicit.

## 10. When CLAB Validation Is Mandatory

The sandbox should automatically recommend CLAB CAB validation when any of the following is true:

1. the proposed change alters routing policy or path selection
2. the change touches BGP, OSPF, IS-IS, static route preference, or next-hop behavior
3. the blast radius crosses device-role or failure-domain boundaries
4. the result depends on protocol convergence, not just topology adjacency
5. the answer required raw fallback parsing or uncertain mapping
6. the agent produced multiple competing hypotheses

In other words:

- sandbox for diagnosis and planning
- CLAB for strict pre-approval validation

## 11. Required Codebase Changes

### 11.1 Simulation Engine

`src/olav/core/simulation/engine.py` must evolve from adjacency-only impact analysis into a reusable graph analysis backend.

At minimum it should:

1. build a canonical graph object
2. expose stable graph query helpers
3. return structured risk and dependency outputs

### 11.2 Sandbox Runtime

`src/olav/core/simulation/llm_sandbox.py` must expose:

1. canonical graph builders
2. semantic-view access helpers
3. deterministic protocol-aware helper functions
4. explicit reasoning-mode tags in outputs

### 11.3 Query Context

`src/olav/agents/query_runner.py` must stop teaching the agent that `parsed_outputs.parsed_data` is the primary semantic truth.

The sandbox will be more reliable only if the query contract matches the new schema.

### 11.4 Topology Upstream

`src/olav/core/topology_engine.py` must eventually stop treating `parsed_outputs × mapping_rules` as the long-term topology truth.

The sandbox graph is only as good as the contract that feeds it.

---

## 12. Final Position

The Ops NetworkX sandbox should be treated as:

1. a state-anchored reasoning assistant
2. a graph-based troubleshooting environment
3. a candidate-plan generator
4. a hallucination-reduction mechanism for the agent
5. a pre-CAB analysis stage
6. an advisory-only system for production operations

It should not be treated as:

1. a Batfish replacement
2. a full protocol-semantic verifier
3. a substitute for CLAB validation
4. an autonomous production change executor

This separation is the right OLAV design:

- **Option A** provides the future semantic engine
- **NetworkX sandbox** provides grounded Ops reasoning
- **Option C** provides strict validation before CAB

That division of labor is stronger than trying to force a single tool to do all three jobs.
