# 45. Writer Subagent Architecture — Small Model Optimization

**Date:** 2026-04-16
**Status:** Design — guides v0.19+ implementation
**Motivation:** grok-4.1-fast (proxy for internal small models) hits max_tokens / loses Output Rules in multi-step pipelines. Separate "thinking" from "presenting."

---

## Problem

当前每个 agent/subagent 身兼三职：

```
选工具 → 执行 → 格式化输出
```

小模型在第三步失败：
- 执行阶段消耗 context + output tokens
- 格式化规则在 SKILL.md 中，但到输出阶段被 "遗忘"
- 工具越多，选择 + 执行阶段越长，留给输出的 token 越少

**实测证据（grok-4.1-fast, max_tokens=2048）：**

| 测试 | 期望 | 实际 | 根因 |
|---|---|---|---|
| T2-11 列出所有设备 | 6 行完整表格 | 2-4 行摘要 | Output Rules 被忽略 |
| T2-14 工具调用次数 | ≤3 | 5-8 | 先探测 schema 再查询 |
| T2-21 Audit Summary | 提取 Executive Summary | 只输出文件路径 | tokens 耗尽 |
| T2-25 DevOps Export | 写入 exports/ | 只在 chat 中输出脚本 | 忘记调 format_and_export |

---

## 解决方案：MVC 模式

```
Agent = Controller (选择工具 + 执行)
Tools = Model (获取/修改数据)
Writer = View (格式化 + 呈现 + 导出)
```

### Writer Subagent

```
任何 worker agent → 结构化数据（JSON / dict / file path）
     ↓ olav_delegate("writer", "Mode X: {data}")
writer subagent (fresh context window)
     → 完整表格 / Mermaid 图 / 报告 / 脚本导出
```

**Writer 优势：**
- **干净的 context** — 没有工具调用历史，只有待格式化的数据
- **极少的 tool** — 只有 `format_and_export` + `read_file`
- **专注的 prompt** — 只做呈现，规则 100% 被遵守
- **可用更便宜的模型** — 格式化不需要推理能力

---

## Writer SKILL.md

```yaml
name: writer
description: "Report engine — formats data as tables, charts, reports, scripts. Unified output for all agents."
tools:
  - format_and_export
  - read_file
```

### Output Modes

| Mode | 触发条件 | 输入 | 输出 |
|---|---|---|---|
| **1. Data Table** | SQL 结果 / list of dicts | rows + column names | Markdown table, ALL rows, "共 N 条记录" |
| **2. Visualization** | 拓扑/流程/时序数据 | nodes + edges | Mermaid diagram → format_and_export(format="mmd") |
| **3. Report Summary** | 报告文件路径 | file path | 读取文件 → 提取 Executive Summary → 健康判定 |
| **4. Script Export** | bash/python/yaml 脚本 | script content | format_and_export(format="sh", subdir="scripts") + 使用说明 |
| **5. Professional Report** | 分析/审计/drift 结果 | structured JSON | Summary → Data → Visualization → Recommendations → export |

### Output Rules (Writer 内部严格执行)

1. **列表查询**: 展示 ALL rows，永不摘要。>50 行时截断前 20 行并注明总数。
2. **表格格式**: Markdown table，列头匹配查询字段。
3. **行计数**: 每个表格后标注 "共 N 条记录"。
4. **图表**: Mermaid 语法，`graph TD` 用于拓扑，`sequenceDiagram` 用于流程。
5. **报告**: 必须包含 Executive Summary + Data + Conclusion 三段。
6. **脚本**: 必须调用 format_and_export 写入文件，不能只在 chat 中输出。
7. **文件导出**: 报告 → `exports/reports/`，脚本 → `exports/scripts/`，图表 → `exports/`。

## 调用链路

### 简单查询

```
User: "列出所有设备"
Orchestrator: execute_sql(sql="SELECT * FROM netops.devices") → 6 rows
Orchestrator: olav_delegate("writer", "Data Table:\n{json_data}")
Writer (fresh context): 完整 Markdown 表格 + "共 6 条记录"
```

### 复杂分析

```
User: "模拟 R2 断链的影响"
Orchestrator: olav_delegate("ops", "simulate R2 link failure")
  Ops-analysis: run_python_simulation → JSON(paths, blast_radius, topology_edges)
  Ops: olav_delegate("writer", "Professional Report:\n{simulation_json}")
  Writer: Executive Summary + Impact Table + Mermaid Topology + Recommendations
       → format_and_export(format="md", subdir="reports")
```

### Audit 报告

```
Audit-auditor: map_engine → render_report → "Report saved: /path/report.md"
Auditor: olav_delegate("writer", "Report Summary:\n/path/report.md")
Writer: 读取文件 → Executive Summary + Health Verdict (🔴/⚠️/✅)
```

### DevOps 脚本

```
Devops: execute_sql(devices) → 生成 bash 脚本文本
Devops: olav_delegate("writer", "Script Export:\n{script_content}")
Writer: format_and_export(format="sh", subdir="scripts") → exports/scripts/backup.sh
     + 输出使用说明
```

## 小模型优化原则

从 T2 测试和 grok-4.1-fast 的行为总结出的设计原则：

### 1. 工具数限制

| 工具数 | 小模型表现 |
|---|---|
| 1-3 | 稳定选择正确工具 |
| 4-5 | 偶尔选错或多余调用 |
| 6-8 | 频繁选错，多余探测 |
| 9+ | 完全不可靠 |

**规则:** 每个 subagent 工具数 ≤5。超过的拆分。

### 2. Docstring 是指令

小模型把 docstring 当作指令执行。如果 docstring 说 "Use explain_only=True to discover tables first"，模型就会先调 explain_only。

**规则:** Docstring 只描述功能，不给操作建议。操作建议放在 system prompt 中。

### 3. 输出格式和工具执行分离

小模型无法同时执行工具链 + 遵守输出格式规则。context 和 attention 被工具调用消耗后，格式规则被丢弃。

**规则:** Worker 只做工具执行（不需要格式化），Writer 只做格式化（不需要选工具）。

### 4. 结构化中间传递

Worker → Writer 之间传递结构化数据（JSON），不传递自然语言描述。JSON 对小模型来说更容易精确解析。

**规则:** olav_delegate 的 task_description 使用 "Mode X:\n{json}" 格式，不用自然语言叙述。

### 5. explain_only 是反模式

动态 schema 探测消耗额外 tool call + context。预置 schema hints 在 SKILL.md 中让模型直接查询。

**规则:** 常用表/列 hardcode 在 SKILL.md 的 Database Schema 段。explain_only 保留为 fallback，不在 docstring 中推荐。

## 实施路径

### Phase 1: Core Writer (v0.19)
1. 新建 `core/writer/` subagent
2. 移动 `format_and_export` 到 writer
3. 新增 `read_file` 工具（读取报告提取 summary）
4. AGENT.md 注册 writer
5. system.md 添加 delegation 规则

### Phase 2: Ops Writer Integration (v0.19)
1. ops-analysis → JSON output → writer 生成 CAB Spec
2. ops-lab → evidence collection → writer 生成 CAB Report
3. devops → script text → writer export

### Phase 3: Audit Writer Integration (v0.20)
1. audit-auditor → render_report path → writer 提取 Summary
2. audit report 统一输出格式

### Phase 4: OutputFormatterPlugin 退役
1. Writer 完全替代 plugin 的后处理角色
2. Plugin 简化为纯审计日志（不做格式化）

## OutputFormatterPlugin 的过渡角色

在 Writer subagent 实施之前，OutputFormatterPlugin 作为临时解决方案：
- 确定性后处理（零 LLM 成本）
- 处理 render_report summary 提取
- 处理脚本自动导出
- 处理 olav_delegate 包装的子代理输出

Writer 实施后，这些功能迁移到 Writer subagent（LLM 驱动但 context 干净），Plugin 退役。

## 与现有架构的关系

```
v0.18 (当前):
  core (4 direct tools + olav_delegate)
    ├── db_query    (4 tools, 含 format_and_export)
    ├── api_query   (4 tools, 含 format_and_export)
    ├── remote      (2 tools)
    └── admin       (11 tools)

v0.19 (Writer):
  core (3 direct tools + olav_delegate)
    ├── db_query    (3 tools, 无 format_and_export)
    ├── api_query   (3 tools, 无 format_and_export)
    ├── remote      (2 tools)
    ├── admin       (11 tools)
    └── writer      (2 tools: format_and_export + read_file)
```

**核心理念:** Agent 只负责获取数据（Controller），Writer 统一负责呈现（View）。这是 MVC 在 agent 架构中的自然映射，也是小模型优化的关键策略。
