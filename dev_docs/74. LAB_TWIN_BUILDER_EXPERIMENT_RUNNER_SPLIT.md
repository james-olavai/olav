## 0. Why the previous design was wrong

dev_docs/73 §3 modelled `lab` as a single LLM-driven sub-agent that
both (a) translates prod base configs to SRL syntax AND (b) executes
the change experiment on the resulting digital twin. Working through
it surfaced three problems:

1. **Translation is slow and error-prone but cacheable**. Doing it
   inside every experiment wastes minutes and risks new translation
   errors per run. The translated twin is a deterministic function
   of `(scope, snapshot_id)` — it should be built once and reused.

2. **Vendor-faithful images are not the answer either**. They look
   tempting (zero translation) but: simulator interfaces don't match
   physical, some features aren't implemented in VM, vendor coverage
   is limited (no Nokia/Huawei/H3C/Ruijie vrnetlab), and per-VM RAM
   (3-12GB) puts a 6-device lab at 30GB+. SRL on `nokia/srlinux:24.x`
   stays the right unified target.

3. **Base config is required to make any meaningful change**. A change
   like "add iBGP neighbor 3.3.3.3" assumes `router bgp 65000`,
   loopback 1.1.1.1, OSPF carrying that loopback, and interface IPs
   are already configured. Pushing only the delta to an empty SRL
   container always fails. The lab must start from a faithful base.

The right architecture is to **decompose lab into two sub-agents** —
one that compiles snapshots into reusable SRL digital twins (slow,
batch, cacheable), and one that runs experiments on a chosen twin
(fast, on-demand). This document specifies that split.

---

## 1. Top-level architecture

`lab` becomes a **top-level agent** (peer of `netops`), not a sub-agent
under netops. It owns two specialised sub-agents:

```
USER prompt
  ↓
orchestrator routing
  ├─ "build twin for R1,R3,R4" / scheduled idle    → lab.twin_builder
  └─ "run change <plan> against twin <id>" / CAB   → lab.experiment_runner
                                                          ↑
                                                   loads twin artifacts
                                                   built by twin_builder
```

**Why top-level, not netops sub-agent**:
- Two sub-agents need their own dispatch table — putting both under
  netops bloats `netops/AGENT.md` routing.
- Twin Builder runs idle / batch, has different lifecycle than
  netops's interactive sub-agents.
- Clean separation: `lab` agent's job is "physical-emulation
  validation", distinct from `netops`'s "observe + advise".

## 2. Sub-agent A: Twin Builder

### 2.1 Purpose

Take a `(scope=[R1,R3,...], snapshot_id=snap_X)` request, produce a
**reusable, on-disk digital twin** consisting of:
- A clab topology YAML (all nodes use `nokia_srlinux` kind)
- Per-node startup-config translated from prod running-config to SRL syntax
- A topology link map (prod ifname → lab ifname)
- A translation review document (human can edit)
- A manifest (`twin_id`, scope, snapshot_id, built_at, translation
  confidence, known gaps)

Twins live at `data/twins/<twin_id>/` and persist across experiments.

### 2.2 Trigger modes

- **User-triggered**: "build twin for R1,R3" → builds against latest
  snapshot covering all listed devices.
- **Scheduled idle**: nightly cron walks recent snapshots, finds
  scope sets used by recent change-plan activity, pre-builds twins
  so morning experiments hit cache.
- **Re-build**: explicit "rebuild twin <id>" when translation
  manually edited and operator wants to re-render the clab YAML.

### 2.3 Tool list (estimated 6)

```yaml
name: lab.twin_builder
thinking_mode: enabled
tools:
  - execute_sql                # snapshot config + topology_links
  - describe_table             # schema introspection
  - recall_memory              # SR Linux CLI translation guide (RAG, per dev_docs/73 §4)
  - translate_config_chunk     # narrow wrapper: takes a block of prod CLI + vendor + RAG hits, returns SRL equivalent
  - write_twin_artifact        # persist YAML / config / manifest to data/twins/<id>/
  - format_and_export          # the translation_review.md sidecar
```

### 2.4 Workflow T — Build twin

```
Phase 0 COLLECT:
  - execute_sql("SELECT * FROM netops.v_snapshots_auto WHERE snapshot_id = ?")
  - execute_sql("SELECT raw_output FROM netops.raw_output_store
                 WHERE snapshot_id = ? AND device_name IN scope
                 AND command IN ('show running-config', 'show configuration | display set')")
  - execute_sql("SELECT * FROM netops.topology_links
                 WHERE source_device IN scope OR destination_device IN scope")

Phase 0a SCHEMA: confirm v_snapshots_auto / raw_output_store columns

Phase 1 PLAN (per-device):
  for device in scope:
    - parse running-config into logical sections (interfaces, ospf,
      bgp, acl, route-maps, vlan, ...)
    - layer-tag each section (L1/L2/L3/L4)
    - emit per-section translation jobs

Phase 2 ACT — per-device, per-section translation:
  for each section:
    a. translate_config_chunk(prod_cli, vendor, layer) → srl_cli
       (internally: regex fast cache + recall_memory + LLM reasoning)
    b. confidence-tag: high (regex hit) | medium (RAG hit) | low (LLM guess)
    c. record any unsupported feature ("Cisco MPLS LDP — no SRL equiv")

Phase 3 REFLECT:
  - cross-check translated configs reference consistent IPs
  - apply IP substitution: prod IPs (192.168.100.x) → lab subnet (172.20.<id>.x)
  - apply interface name substitution: prod ifname → SRL ifname using build_prod_to_lab_intf_map

Phase 4 SYNTHESISE:
  - assemble per-node startup configs
  - generate clab YAML via generate_clab_topology_from_links()
  - compute twin_id = sha256(scope + snapshot_id)[:16]

Phase 5 EMIT:
  - write_twin_artifact("data/twins/<twin_id>/manifest.yaml", ...)
  - write_twin_artifact("data/twins/<twin_id>/topology.clab.yml", ...)
  - write_twin_artifact("data/twins/<twin_id>/configs/<dev>.srl.startup", ...)
  - format_and_export(translation_review.md, subdir="twins/<twin_id>")
```

### 2.5 Twin artifact layout

```
data/twins/
└── 2c4f7a89_snap20260514101701/    # twin_id (8-char scope-hash + snap_id)
    ├── manifest.yaml
    │     scope: [R1, R3, R4]
    │     snapshot_id: snap_20260514_101701_156d60
    │     built_at: 2026-05-14T10:42:00Z
    │     built_by: twin_builder@gemma4:31b
    │     translation_confidence:
    │       overall: 0.87
    │       per_device:
    │         R1: { high: 0.62, medium: 0.31, low: 0.07 }
    │         R3: { high: 0.91, medium: 0.09, low: 0.00 }
    │     unsupported_features:
    │       - "R1: junos firewall family inet filter (no SRL equiv)"
    │       - "R3: ip nat outside (SRL has limited NAT)"
    │     ip_substitution:
    │       192.168.100.101: 172.20.42.11
    │       192.168.100.103: 172.20.42.13
    │     interface_map:
    │       R1: { ge-0/0/2: ethernet-1/2 }
    │       R3: { Ethernet0/0: ethernet-1/1 }
    │
    ├── topology.clab.yml             # ready for clab deploy
    │
    ├── configs/
    │   ├── R1.srl.startup            # full SRL startup config
    │   └── R3.srl.startup
    │
    └── translation_review.md          # human-readable per-section
                                       # translation log; operator can
                                       # edit configs/*.srl.startup if
                                       # they spot translation errors
                                       # — Runner uses edited version
```

### 2.6 Manual override path

Operator opens `translation_review.md`, sees:
> R3 — L4 BGP section — confidence: medium — LLM mapped `route-map
> RM-IN in` to `import-policy RM-IN` but unsure about apply scope.
> Generated SRL: `set / network-instance default protocols bgp
> neighbor 1.1.1.1 import-policy RM-IN`

If wrong, operator edits `configs/R3.srl.startup` directly. Next time
Runner loads this twin, the corrected version is used. No re-translation
needed unless source snapshot or scope changes.

## 3. Sub-agent B: Experiment Runner

### 3.1 Purpose

Take `(change_plan_markdown, twin_id)`, deploy the twin to clab,
push the change CLI delta, observe per-layer results, emit a markdown
lab report.

### 3.2 Tool list (estimated 7)

```yaml
name: lab.experiment_runner
thinking_mode: enabled
tools:
  - read_change_plan           # parse markdown → {scope, layered_cli, post_checks, topology}
  - load_twin                  # read data/twins/<twin_id>/ → topology YAML + startup configs
  - containerlab_deploy        # clab deploy with --startup-config (per-node)
  - device_push_config         # push change delta (LLM may need to translate CLI per layer)
  - device_show_command        # observation
  - containerlab_destroy       # cleanup
  - format_and_export          # emit exports/lab_reports/<change_id>_lab.md
```

### 3.3 Workflow R — Run experiment

```
Phase 0 COLLECT:
  - read_change_plan(<change_plan.md>) → structured
  - load_twin(<twin_id>) → topology + startup_configs + ip_map + intf_map

Phase 1 PLAN:
  - per-layer execution stages (L1 → L2 → L3 → L4)
  - skip layers with no change CLI

Phase 2 ACT (deploy + per-layer push-observe):
  Stage 1: containerlab_deploy(topology.clab.yml, startup_configs=...)
           → lab boots with twin's base config (R1/R3/R4 all have
             SRL-translated full prod state running)
  For each layer in change.layer_changes:
    Stage L<n>:
      a. for each device, take change.cli_per_device[layer]
         translate via recall_memory + LLM (delta only — base already loaded)
         apply twin's ip_map + intf_map
      b. device_push_config(lab_name, device, translated_cli)
      c. device_show_command(lab_name, device, layer_post_check.command)
         match against expected_pattern (with vendor-pattern catalog)
      d. REFLECT: did this layer succeed? if not, diagnose
                  (translation issue? missing base? config syntax error?)

Phase 3 REFLECT (cross-layer):
  - L4 BGP Established requires L3 OSPF Full requires L1 interface up
  - any layer failure cascades — surface the lowest failure

Phase 4 SYNTHESISE:
  - per-layer verdict (PASS / FAIL / SKIPPED)
  - if FAIL, diagnose root layer + explanation
  - confidence: did the underlying twin look right?

Phase 5 EMIT:
  - format_and_export(<lab_report.md>, subdir="lab_reports")
  - containerlab_destroy(lab_name)   # always cleanup
```

### 3.4 Lab report shape

```markdown
# Lab Report: iBGP R1-R3 (change_id: ibgp_R1_R3_20260514)
_Generated 2026-05-14T11:05; twin: 2c4f7a89_snap20260514101701; lab: ibgp-r1-r3-attempt-3_

## Verdict: PASS / FAIL / PARTIAL

## Twin context
- Twin ID: 2c4f7a89_snap20260514101701
- Built: 2026-05-14T10:42
- Translation confidence: 0.87 (R1: 0.85, R3: 0.91)
- Known gaps in twin: [list from manifest.unsupported_features]

## Per-layer results
| Layer | Action | Result | Evidence |
|---|---|---|---|
| L4 | push iBGP neighbor on R1 + R3 | ✅ PASS | R1: `show bgp summary` → Establ; R3: `show ip bgp summary` → Established |

## Diagnosis (if FAIL)
- Root layer: ...
- Hypothesis: ...
- Suggested investigation: ...

## Cleanup
- lab `ibgp-r1-r3-attempt-3` destroyed
```

## 4. Twin lifecycle + cache strategy

### 4.1 Twin ID

`twin_id = sha256(sorted(scope) + snapshot_id)[:16]`

Same `(scope, snapshot)` → same twin ID → cache hit. The twin is
**immutable** (manifest + configs + clab YAML). To rebuild, change
either scope or snapshot.

### 4.2 Idle build scheduler

Nightly cron (`olav lab twin_build_idle`):
- Find all distinct device scopes used in last 7 days of change plans
  (`exports/change_plans/*.md` → scope field)
- For each scope, check if a twin exists for the latest snapshot
- If not, build it
- Skip if already built or if Twin Builder is currently busy

This means: 95% of operator change-plan submits hit a pre-built twin
and start experimenting in <10s instead of waiting for translation.

### 4.3 Cache invalidation

- New snapshot collected → previous twin still valid for historical
  reproductions; new twin built on demand for "current" experiments.
- Operator edits `configs/<dev>.srl.startup` → twin marked
  `manually_modified: true` in manifest; further Runner runs use
  edited version; rebuilds require explicit confirm to overwrite.
- Translation rules updated (RAG corpus changed) → existing twins
  retain old translation (consistency); new twins use new RAG;
  optional `twin rebuild --all` to refresh.

### 4.4 Garbage collection

Twins older than 90 days with no Runner activity → auto-archive
to `data/twins/_archive/`. Manual delete via `olav lab twin gc`.

## 5. Why this is better than the dev_docs/73 §3 design

| Concern | dev_docs/73 §3 single-lab | This design |
|---|---|---|
| Translation done | Every experiment | Once per `(scope, snap)`, then cached |
| Experiment latency | 5-15 min | <1 min after warm-up |
| Translation errors | Re-happen each run | Caught once, fixed once, reused |
| Multi-operator parallel | Conflicts on shared lab | Each Runner instance gets own clab |
| Idle resource use | None — nothing pre-built | Build twins during off-hours |
| Manual override of bad translation | Not possible | Edit `configs/*.srl.startup` |
| Twin version pinning | Not modelled | First-class via twin_id |
| Failure attribution | Mixed: translation? deploy? push? | Translation = Builder's domain; deploy/push = Runner's |

## 8. Open questions

1. **Cross-twin diffing**: should Runner support "deploy twin A
   AND twin B side by side, compare reachability" for change impact
   analysis? Useful for "would this snapshot's BGP change in twin A
   break twin B"?

2. **Twin storage backend**: filesystem (data/twins/<id>/) is
   simplest. Could move to git for change history, or to S3 for
   shared team access. Decide based on team scale.

3. **vrnetlab hybrid mode**: should Twin Builder optionally produce
   a vrnetlab-targeted twin for change-anchor devices where
   absolute fidelity matters? Adds complexity but covers the
   "SRL-misses-vendor-specific-quirk" edge case. Defer for now.

4. **Translation regression tracking**: when RAG corpus updates,
   should there be a system to detect "twins built before this
   update may now have different translation behavior"? Could be a
   `rag_corpus_version` field in manifest.

5. **Twin per snapshot or per change-window**: snapshot frequency
   may exceed change frequency. Should Twin Builder coalesce
   "snapshots within N hours" into single twin? Trade-off:
   freshness vs cache hit rate.

6. **Resource cap**: how many twins running concurrently? Builder
   is single-threaded but multiple Runners may spawn parallel labs.
   Need clab subnet pool + concurrency limit.
