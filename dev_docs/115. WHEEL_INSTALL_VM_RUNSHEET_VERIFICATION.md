## 1. BUG-1（致命，已修）：`olav init` 让纯开源安装当场变砖

`init.py` 在创建 admin 用户后**无条件**把 `auth.mode` 写成 `token`。而
`get_auth_provider("token")` 在没有 olav-ent 时**故意** fail-fast（把预期的登录
静默降级成 OS 身份是安全意外，见 `provider.py` 的注释）。

于是纯 `olav + olav-netops` 安装的实际表现是：

```
olav init      → ✓ 成功，还打印了 token 和 web 登录链接
olav doctor    → ✓ healthy (9/9 checks passed)
olav "任何问题" → NotImplementedError: auth.mode='token' requires olav-ent
```

**两个绿色健康信号在前，第一个真问题就死。** 这直接堵死 Ch1 及之后所有 beat。

修复：仅当 `olav.enterprise.auth.token` 可导入时才切换 mode；admin 用户和 token
照旧创建（装上 olav-ent 立即可用），并在 init 输出里明说这套安装走 OS 身份。

**为什么本地从未发现**：dev 机上 `olav.enterprise` 在 path 上，`token` 能解析，
那次写入看起来毫无害处。我在 VM 上现场对照过：

| | `olav.enterprise` | `get_auth_provider("token")` |
|---|---|---|
| dev 机（editable） | PRESENT | `TokenAuthProvider` |
| 测试 VM（wheel） | absent | `NotImplementedError` |

回归测试 `test_init_never_writes_an_auth_mode_this_install_cannot_serve` 模拟扩展
缺失，断言 init 写出的 mode 必须能被 `get_auth_provider` 服务——对修复前的代码会
以 `bricked-OSS-install defect` 失败。原有的
`test_init_sets_auth_mode_token` 断言的正是那个错误的无条件行为，已改为按安装形态
取期望值。

> 这一条同时命中 CLAUDE.md 的两条规则：「必须从真实入口验证」与「永不用 editable
> 安装验证发布」。它们抓的是同一个缺陷。

## 1b. BUG-2（Ch2，未修）：导出产物静默只含 20/339 行，而答案指向它

Ch2 第二 beat（"List every device with its model and mgmt IP, and export it to
CSV"）**看起来成功**，最终答案是：

> The device inventory containing the name, model, and management IP for **all
> devices** has been exported to: `exports/queries/device_inventory.csv`

那个文件只有 **21 行（20 台设备）**。完整的 339 行导出确实存在，但在另一个
**答案从未提到**的文件名下（`query_20260805_155713.csv`，20271 字节）。

审计库（零 LLM）还原的链条：

| 时刻 | 调用 | 结果 |
|---|---|---|
| 15:57:13 | `execute_sql` | 完整 339 行写入 `exports/queries/query_….csv`，返回**截断预览** |
| 15:57:47 | `format_and_export` | 从预览写出 `device_inventory.csv`（1265 字节）|
| 15:57:52 | `olav_delegate` | 答案指向 `device_inventory.csv`，称其为 "all devices" |

**工具契约是对的，别改工具。** `execute_sql` 实现了 "cap to context, full to
file"，并把两件事都告诉了模型：

```
FULL results (339 rows) exported to exports/queries/query_….csv.
Only first 20 rows returned to context to prevent bloat.
```

`format_and_export(data: str, …)` 的文档也明说 `data` 是**字符串字面内容**。
所以 20 这个数字的来源是 tier 的上下文行数上限（doctor 报 `tier=medium` →
`MAX_ROWS_TO_CONTEXT=20`，正是 CLAUDE.md 的 10/20/50 表），模型只能拿到 20 行，
它就把 20 行写成了文件。

**这是 agent 行为问题**：被明确告知完整结果已在磁盘上，仍然用受上下文限制的路径
重新导出，并把用户指向截断版。按 CLAUDE.md 该走转向层（`*.guide.yaml` →
`usage_guide`）修，而不是改代码——「Steer behavior via memory, not code」。

危害等级不低：Ch2 的卖点原话是「the data is exact, not hallucinated」。数据确实
没被编造，但**被静默截断了**，而文件存在、格式正确、看不出问题。录 demo 时若打开
那份 CSV，屏幕上就是 20 行。

## 1c. 观察（Ch2 第一 beat）：最终答案偶发为空

Ch2 第一 beat rc=0、148s、子 agent 4 次 `execute_sql` 后**正确答出**（审计库里
`task` 的返回是 `'Based on the most recent import … Most Recent Import
Timestamp: 2026-08-05T15:49:33 …'`），但 stdout 上只有开场白，**最终答案没有被
打印**。编排器丢掉了子 agent 的输出——正是 CLAUDE.md「orchestrator 必须原样返回
子 agent 输出」要防的那件事。

不是普遍现象：Ch1、Ch2-csv、Ch3 都正常输出。观察到 1/4。`agents/agent.py:677`
的注释描述了一个同形失效：「synthesis step after a large ToolMessage 返回
0 completion_tokens 空内容」——`_ValidatingSQLiteCache` 只防止把空响应**缓存**
下来，不会重试，所以用户就是什么都看不到。

要按 CLAUDE.md 的 N≥3 规则定性还需专门测量，而这里有个障碍值得单独记：
**没有关闭 LLM 缓存的开关**（`agents/agent.py:685` 无条件 `set_llm_cache`，
grep 不到 `OLAV_DISABLE_LLM_CACHE` 之类）。缓存按 prompt 命中，所以重复同一
prompt 采样并不独立，只能手删 `~/.olav/cache/`。要求 N≥3 的项目，应该提供这个
开关。

## 1d. Ch4 镜像名：**不是缺陷，是 1/3 变异**（我在 N=1 上误判过一次）

Ch4 第一 beat 原话是 **"Deploy batfish/allinone, ports 9996 9997"**。第一次运行
生成的 compose 是：

```yaml
services:
  batfish:
    image: batfish/batfish:latest      # ← prompt 说的是 batfish/allinone
    ports: ["9996:9996", "9997:9997"]  # ← 端口正确
```

我当即把它记成了一个真缺陷。**错了**——按 CLAUDE.md 的 N≥3 规则补采样后：

| run | 生成的镜像 | |
|---|---|---|
| 1 | `batfish/batfish:latest` | ❌ |
| 2 | `batfish/allinone:latest` | ✅ |
| 3 | `batfish/allinone` | ✅（无 tag，docker 默认 latest）|

2/3 正确，所以这是 **LLM 变异，不是系统性 bug**。留在文档里有两个理由：

1. **它仍是录制风险。** 本地只缓存了 `batfish/allinone:*`，而 runsheet 的 Setup
   正是靠这个缓存让「self-service deploy 在镜头前很快」。1/3 的概率会写成一个
   缓存未命中的镜像名，镜头前变成 2GB 拉取。单镜到底的 demo 值得先跑一次预热，
   或在 prompt 里把镜像名写成 `batfish/allinone:latest`（带 tag 更不容易漂）。
2. **它是「N=1 不是信号」的现成例子。** 我差点把一次变异写成缺陷提交，和
   CLAUDE.md 记录的 V2_VALIDATION_RETROSPECTIVE §M4 是同一个坑。

端口三次全对。

## 1e. Ch4 的 HITL 门无法在一次性 CLI 中通过（非缺陷，但限制了本轮验证）

部署 beat 停在 agent 的**对话式确认**上：

```
**Confirmation Required:**
I plan to execute `deploy_service(name='batfish', confirmed=True)` …
Confirm?
```

`--auto-approve --dangerously-skip-permissions` 关掉的是 OLAV 的权限门，而这一步
是 agent 用一轮对话问的。一次性 `olav --agent …` 没有第二轮可答，于是容器永不启动
（runsheet 自己也写明「The deploy asks for a one-key confirmation — that HITL
gate is by design」）。

好处是 compose 文件在确认**之前**就写好了，所以每次运行都留下证据，可以只针对
「镜像名」这一个问题做 N≥3 采样而不必真部署。

## 1f. 环境约束：并发跑 agent 会让共用端点的嵌入静默失效（**我又一次先下错结论**）

`192.168.8.12:11433` 同时提供 `gemma4-31b-agent`（LLM）与 `embeddinggemma-300m`
（嵌入）。我在并发跑 §1d 的采样时看到：

```
embed_text failed: Error code: 500 -
{'error': {'message': 'model name=embeddinggemma-300m failed to load'}}
```

`olav kb search` 随之静默退化成非语义路径（返回一批毫不相关的 guide，全部
`conf=1.00`）。我据此写下了「单槽互斥，agent 运行期间 AutoRecall 拿不到任何
guide」——**这个结论是错的**，串行复测直接推翻：

| 步骤 | 结果 | 之后 `loaded` |
|---|---|---|
| A 空闲时请求嵌入 | ✅ 返回向量 | `embeddinggemma-300m` |
| C 紧接着请求 LLM | ✅ 返回补全 | `gemma4-31b-agent` |
| D 再请求嵌入 | ✅ 返回向量 | `embeddinggemma-300m` |

服务器**确实按需换页**，串行请求下两者都正常。500 只在**并发**（两个 agent 进程
＋探针同时打）时出现。所以：

- **§1b 的定性不变**：转向层当时是可用的，agent 不是「没拿到 guide」。
- 真正的注意事项换成了：**不要在同一台 swap 服务器上并发跑 agent**。会 500，而且
  OLAV 是静默降级——AutoRecall 拿不到向量就跳过，不报错。并行跑 e2e 套件时尤其
  要注意这一点。
- 附带解释了耗时：每次 LLM↔嵌入交替都要重新加载模型，这也是今天各 beat 普遍偏慢
  的一部分原因（早先那轮基准里 gemma4 第一格 91s、后三格 53s，同一现象）。

同一天内我第二次在 N=1 上给出错误定性（另一次是 §1d）。两次都是靠补做对照实验
纠正的，记在这里当作提醒：**先测串行/并发对照，再写结论。**

## 1g. Ch4 ★★★ beat 失败：agent 挑错设备，然后把数据报成「不存在」

runsheet 里三星的那一拍（"Write a change plan to add a redundant eBGP uplink on
the **alpha border router**, mirroring the existing AARNet peer"）跑完
rc=0、377s、约 10 次 SQL，**没有产出变更计划**，最终答案是索要数据：

> I am currently blocked because the platform's current data store contains **no
> record** of the existing AARNet BGP peer configuration on the
> `alpha-wan-6880v` router. … **Missing Data**: There are no BGP
> configurations, peer IPs, AS numbers, or route-maps for "AARNet" in
> `netops.raw_output_store` or `netops.parsed_outputs`.

零 LLM 直接查库，事实完全相反：

| 检查 | 结果 |
|---|---|
| `netops.devices` 里有 `alpha-border-4500x.net.demo.internal`？ | **有**（hostname 字面含 "border"）|
| 它的 `show running-config` 提到 AARNet？ | **提到**（34759 字符那份，另有 `show running-config all` 88786 字符）|
| 它的 running-config 含 `router bgp`？ | **含** |
| 入库是否完整？ | devices 339 = raw_output_store 唯一设备 339，**0 个孤儿** |

agent 分析的是 `alpha-wan-6880v`——**另一台设备**。prompt 说的是「alpha border
router」，一个 `hostname ilike '%alpha%border%'` 就能命中。

**一个加剧因素（真缺陷）**：`netops.devices.role` 在 339 台设备上**全为 NULL**，
而 `execute_sql` 的 SCHEMA_HINT 恰恰把它宣传给模型：

```
Schema reminder: netops.devices(hostname,platform,ip_address,role) | …
```

模型被告知有 `role` 可用于「哪台是 border」，查出来全空，只能回退到猜 hostname，
于是猜错。这是**提示与数据不一致**：要么导入时填充 `role`（hostname 启发式 + CDP
拓扑位置都够用），要么在它恒为 NULL 时别写进 SCHEMA_HINT。目前两者都没做。

**N≥3 未能达成，如实说明。** 补跑的两次都死在端点上，不能计为行为样本：

| run | 结果 |
|---|---|
| 1 | 干净完成（rc=0, 377s），选错设备、未产出计划 —— 上述唯一有效观察 |
| 2 | `openai.InternalServerError: 500 model name=gemma4-31b-agent failed to load` |
| 3 | `openai.InternalServerError: proxy error: Failed to read connection` |

CLAUDE.md 对此有明文：「LLM-endpoint 的红**往往**是 infra 而不是代码，先确认再
去改代码」。所以本条**只有 N=1 的干净证据**，不能声称是系统性失败——但也不能因此
淡化：三次尝试，`exports/change_plans/` **始终为空**，runsheet 的三星产物一次都

顺带印证 §1f：这台 swap 服务器在我这一天反复 LLM↔嵌入换页后进入了不稳定状态

## 1i. 坑：同机两套部署会共用 docker compose 项目名

`deploy_service` 把 compose 文件写到 `<OLAV_HOME>/.olav/services/<name>/`，项目名
由目录名推导——两套部署都得到 `batfish`，容器名都是 `batfish-batfish-1`。我在
`~/olav-test` 里执行 `docker compose up -d`，compose **复用并重启了 7 月
`~/olav` 部署的那个容器**（`docker inspect` 里的
`com.docker.compose.project.working_dir` 仍指向 `/home/olav/olav/...`）。

后果：一套部署的服务操作会静默作用到另一套的容器上。演示机上尤其危险——以为在
测试环境起服务，实际动了录制环境。建议项目名带上部署标识
（`-p olav-<hash(OLAV_HOME)>`）。

（本轮因此无需"还原"：容器现在是 `allinone:latest` 运行中，与我接手时一致，旧
compose 文件未被改动。）

## 3. 观察：`OLAV_HOME` 并不隔离 LLM 缓存与 checkpoint

```python
# core/config.py:1334
USER_CACHE_DIR      = Path.home() / ".olav" / "cache" / _username
USER_CHECKPOINT_DIR = Path.home() / ".olav" / "checkpoints" / _username
```

- 同一台机器上的两套 `OLAV_HOME` 部署**共享** `llm_cache.db` 和 checkpoints。
- 对**录 demo** 尤其要紧：LLM 缓存按 prompt 命中且无条件启用
  (`agents/agent.py:685`)。本轮验证用的 prompt 是 runsheet 原话，也就是 7 月
  demo 跑过的原话——如果不先把旧缓存挪走，跑出来的「通过」可能来自缓存，毫无
  价值。本轮已把 VM 上遗留的 `~/.olav`（含 12M `llm_cache.db`）改名挪开。

用户自己的 `reset-demo.sh` 已经把 `~/.olav` 当一次性目录整体删除，说明这个坑
之前踩过。建议至少在 runsheet 的 Setup 段写明。

## 7. 端点 500 的真根因（2026-08-05 第二轮，**§1f 再次修正**）

清理 demo 主机重装后，Ch1 又在 103s 死于
`500 model name=gemma4-31b-agent failed to load`。这已经是今天第五次同形失败
（Ch1、Ch4 三次、Ch5 收尾），值得停下来查到底。

我先猜是「AutoRecall 每步都嵌入 → 单槽服务器反复换页 → 换崩」。**做了对照，猜错了**：

| 实验 | 结果 |
|---|---|
| 串行交替 LLM → 嵌入 → LLM …（8 轮）| **8/8 全部成功** |
| **同时**发一个 LLM 和一个嵌入请求（3 轮）| **3/3 有一方 500**，且交替谁输 |

报错措辞本身就是提示：`failed to **load**` 是「换入模型失败」，即内存被占——指向
**同时请求**，不是交替。

所以真根因是：**OLAV 会在生成进行中并发发出嵌入请求**（AutoRecall / memory 写入），
而 `192.168.8.12:11433` 是单槽 swap 服务器，同时承载 LLM 与嵌入模型时必有一方
`failed to load`。这解释了今天全部五次失败，也解释了为什么 `olav init` /
`olav doctor` 从不失败——它们只发孤立的短请求。

**7 月 demo 之所以稳，是因为嵌入在另一台主机**（`192.168.8.50:11434`）。那台现在
下线，我在 DRIFT-2 里把嵌入改指到 8.12 —— **这个「修复」本身制造了冲突**。当时
它让 `guides primed` 从 0 变 17，是必要的一步，但代价没被发现。

### 7.1 结论与建议

- **demo/评测主机必须让嵌入端点独立于 LLM 端点。** 这是 runsheet「Setup (off
  camera)」应当写明的第三项前提（前两项是 LLM 端点与 Batfish 镜像预缓存）。
- 若没有第二台服务器，用 `pip install 'olav[local-embed]'` +
  `embedding.mode=local`（默认 `BAAI/bge-small-zh-v1.5`，512 维）把嵌入放到 CPU，
  完全避开端点竞争。注意换维度要先清 `memory.lance`，否则按设计 fail-fast
  （`EmbeddingDimMismatchError`）。
- 也可以在服务器侧让 llama-swap 同时常驻两个模型（31B Q4 ≈18G + 300M ≈0.6G，
  显存够），但那是推理主机的配置，不在本仓库范围内。

### 7.2 我在这条结论上错了两次，都靠对照实验纠正

§1f 第一版：「单槽互斥，agent 运行期间 AutoRecall 全程失效」——串行复测推翻。
§1f 第二版：「只在我并发跑多个 agent 时出现」——**也不完整**：单个 agent 运行内部
就有并发（生成中嵌入），所以不需要我并发跑多个 agent 也会触发。第三版（本节）才
和全部观测一致。

教训与 §1d 相同但更贵：**报错措辞值得逐字读**（`failed to load` ≠ `unavailable`），
**而且假设要拆成能单独否证的对照**（串行 vs 并发），否则会像我一样连续两次给出
自洽但错误的解释。

### 9.1 317 vs 339 —— memory 能解决

### 9.2 最终答案缺失 —— memory 解决不了，**而且我先前的定性是错的**

我此前记的是「编排器丢掉了子 agent 的输出」。真实机制更具体：

`NL-CLI-SILENT-FINAL` 的两层兜底**全部以 `if not final_content` 为条件**，而这里
`final_content` **不是空的**——模型在委派**之前**先流出一段「I will check the
netops views…」的铺垫，那段就把 `final_content` 填上了。于是：

1. 铺垫被流式打印（用户看到一个计划）
2. 委派返回真正的答案
3. 模型不再说话
4. 所有兜底因「非空」被跳过

**我第一版 Tier 0 也是以「空」为条件的，所以在 VM 上重跑毫无变化**——这一步实测
证伪了我自己的第一版设计。

改成按**顺序**判定：每次 delegate 工具返回时记录当时的流式块数，若之后再无新块，
说明答案被搁在那个工具结果里，原样打印。原样而非再合成也是
ADR-0003/0005/0006 对 thin router 的要求，且不需要 LLM 调用，因此不会像 Tier 1
那样失败（Tier 1 重试 3 次并吞掉所有异常，在这台端点上很容易全灭）。

另加最后兜底：任何一轮都不允许静默结束——空屏 + rc=0 与「这个问题没有答案」无法
区分。

**未完成的部分**：端到端确认两次都死在
`500 model name=gemma4-31b-agent failed to load`（§7 的并发问题）。单元测试 12 个
全过，但**Tier 0 在真实运行中是否生效尚未验证**，端点稳定后需重跑。

### 9.3 两条测试是因为我自己的断言踩了坑才存在

先用子串搜 `if not final_content`，命中了**解释这个 bug 的注释**；改成剔除注释的
切片，切片末尾又越界到 Tier 1 的守卫行。最后改成按位置断言。与 §4.8 里 learner
守卫必须用 AST 判定是同一类教训：**对源码做断言时，别用子串搜散文。**


## 10. §9 修复的回归：中间件自己的 LLM 输出被当成答案打印（2026-08-06）

### 症状
第三轮 runsheet 的 Ch1/Ch2，答案后面紧跟一段裸 JSON：

```
We just imported **339 devices**, all of which are on the **cisco_ios** platform.
```json
[ { "text": "When execute_sql exports full results to CSV, cite that file path ...",
    "category": "decision", "importance": 1.0, "tags": ["execute-sql", ...] } ]
```

这是 `MemoryCapturePlugin` 在 `aafter_agent` 里调 LLM 抽取记忆时的原始输出。

### 为什么 §9 的修复会放出它
§9 把 `on_chat_model_end` 的守卫从「全局 `not _chunks`」换成「本轮 `_chunks_this_turn == 0`」。
capture 的那次调用同样是 **depth 0**、同样**不流式**，于是新守卫对它成立 —— 旧守卫是靠
「_chunks 已经有内容了」这个副作用顺带挡住的，属于**巧合而非设计**。

### 判别式：靠节点名，不是靠深度
`langchain.agents.factory` 里两处硬事实：

- agent 自己的模型调用：`graph.add_node("model", ...)`
- 中间件钩子：`graph.add_node(f"{m.name}.after_agent", ...)`

所以 capture 的事件带的是 `langgraph_node="memory_capture.after_agent"`，而答案是 `"model"`。
`main.py` 新增 `_is_agent_turn(event)`，在 `on_chat_model_stream` / `_start` / `_end` 三处都过一遍。
**fail open**：没有节点元数据时判为 agent 的轮次 —— 误丢答案（静默 run）比多打一段 JSON 严重得多。

守卫：`tests/unit/test_middleware_llm_not_printed.py`（32 项）。测试用 AST 把 `main.py` 里
真实的嵌套函数取出来跑，而不是断言散文 —— 本文件历史上有三次「断言子串、行为其实是坏的」。
其中两项直接把 langchain 的节点命名约定钉死，改名时会红。

## 11. 顺带查出：OLAV 中间件的 `aafter_agent` 每次查询跑两遍

查 §10 根因时发现的结构性问题，**尚未修**。

`agents/agent.py:1091` 附近的注释写着「deepagents 0.5.2 接受 `middleware=` 但不挂载」，
所以 `main.py:1862` 手工再调一遍每个中间件的 `aafter_agent`。该注释在 0.6.x 升级后已过期：

```python
# deepagents 0.6.7, create_deep_agent()
if middleware:
    deepagent_middleware.extend(middleware)
```

且 OLAV 的插件确实都是合法 `AgentMiddleware` 子类（实测 `issubclass(...) is True`），
langchain 会为每个实现 `aafter_agent` 的中间件建节点。于是 **图内跑一次 + main.py 手工跑一次**。

代价：每次查询多一次 capture LLM 往返；记忆表里出现同内容多份（实测 `n=3`）。

### 为什么不能简单删掉手工那次
两条实测约束：

1. **langgraph 静默丢弃未声明的 state key**。`OutputFormatterPlugin` 写的
   `state["_output_supplements"]` 不在任何 `state_schema` 里，最小复现显示该键在
   `invoke()` 返回值中直接消失 —— 也就是说**图内那次的 supplements 到不了用户**，
   手工那次才是唯一生效路径（自动导出提示、save-assertion 警告都靠它）。
2. 反过来，`QueryPatternCapturePlugin._msg_tool_calls` 只从 `AIMessage.tool_calls` 取参数，
   而 `main.py` 喂的合成 state 把 args 挂在 tool 角色的 dict 上、assistant 消息没有
   `tool_calls` —— 也就是说**手工那次喂的形状它读不了**，图内那次才有效。

即两条路径各自只有一半有效，谁都不能单独删。

### 建议的修法（未实施）
在 `OutputFormatterPlugin` / `SaveAssertionMiddleware` 上声明带 `_output_supplements`
的 `state_schema`，改从图的最终 state 读 supplements，然后删掉 `main.py` 的手工循环。
需要配套一条「hook 只执行一次」的回归测试。

**没有当场动手的理由**：这是发布分支、runsheet 正在跑，而这类改动按 CLAUDE.md 的口径
需要 N≥3 的行为验证才能算关掉，来不及在本轮 demo 前做完。用户可见的症状（§10）已修并有守卫。

## 12. Ch5 暴露的第二处显示缺陷：转发内容按 Python 字面量原样打印（2026-08-06）

第三轮 Ch5 的实际输出：

```
> ⚠️ **Results truncated**: showing 50 of 27523 findings. Raise the profile\'s
`max_findings_per_job` to see more.\
```

Tier 0 从 delegate 结果里取答案时，是对**消息对象的 `str()`** 做正则，且只还原了 `\n`：

```python
_inner = re.findall(r"content='(.*?)'\s*,?\s*name=", _raw, re.DOTALL)
_text = (_inner[-1] if _inner else "").replace("\\n", "\n").strip()
```

两个后果：`\'`、`\\` 等其余转义原样进终端；而且当正文**自带撇号**时 `repr` 会改用双引号，
单引号锚定的模式直接匹配不到——恰好就是最容易出现撇号的那类句子。

改为匹配完整的字符串字面量并交给 `ast.literal_eval` 解码（两种引号都匹配），
抽成模块级 `_decode_relayed_content()`。守卫：`tests/unit/test_relayed_content_decoding.py`。

> **⚠️ 更正（同日，装新 wheel 复跑后实测）**：上面这条修复是对的，但**它不是 Ch5 那段
> 转义的成因** —— 我归因错了。装上修复后重跑 Ch5，终端输出**一字未变**，仍是
> `profile\'s` + 行尾 `\`。沿工具链取原文才定位到真正的来源：
>
> | 环节 | 原文 |
> |---|---|
> | 磁盘上的报告 `.md` | `profile's` ✅ 干净 |
> | `execute_skill_script` 返回 | `profile's` ✅ 干净 |
> | `task` 返回 | `profile\'s` ❌ 已转义 |
>
> 转义是 **`task` 工具构造返回值时 `repr` 出来的**：正文里同时含 `"`（findings 里的
> `"🔴 down"`）和 `'`，Python 的 repr 于是选单引号并把撇号转义成 `\'`。
> 而 audit 编排器是 `task_return_direct=True`（`agent.py` 的 `_patched_build_task_tool`），
> 那份 repr 字符串**直接成为最终消息**，走的是 model_end 打印路径，**根本不经过 Tier 0**——
> 所以 Tier 0 的解码器再正确也碰不到它。
>
> **再一层（同日续查）**：用 langchain 亲手构造一份真实载荷跑解码器，发现它返回**空串**——
> 于是查出一个存在已久的哑弹。`_build_task_tool` 构造的是
> `ToolMessage(content, tool_call_id=tool_call_id)`，**没有 `name`**，所以 repr 里
> `content=` 后面跟的是 `tool_call_id=`；而 Tier 0 的正则（旧版和我的第一版都是）
> 锚在 `\s*,?\s*name=` 上 —— **它对真正的 `task` 结果从来没匹配上过**，一直静默返回 ""。
> 手写的测试 fixture 每一份都带了 `name='task'`，所以谁都没发现。
>
> 改为只匹配完整字符串字面量、不锚定后继键名（`_RELAYED_CONTENT_RE`），
> 并新增用 `Command(...)`/`ToolMessage(...)` **由库本身构造**载荷的测试
> （`TestTheRealDeepagentsPayload`）——手写 fixture 正是这次漏检的成因。
>
> 教训与 §7、§1f 同类：改完必须在真实入口复跑一次再宣布修好。这次是复跑救了记录。

顺带修掉一处**测试自身的坏味道**：`test_silent_final_delegate_tier0.py` 原先在测试里
复制了一份正则，再断言 main.py 里存在与之匹配的正则——它守的是「有个模式」而不是
「Tier 0 用的模式对」，而且逻辑一抽成函数它就红了（行为其实变好了）。现改为直接调用
被测函数。

另：叙述里单独一行 `[]` 不是泄漏，是编排器自己吐的空数组答案（gemma4 在答案被
sub-agent 截走时的常见产物），Tier 0 随后补上了真答案。
