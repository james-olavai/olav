## 1. BUG-1（致命，已修）：`olav init` 让纯开源安装当场变砖

`init.py` 在创建 admin 用户后**无条件**把 `auth.mode` 写成 `token`。而
`get_auth_provider("token")` 在没有 olav-ent 时**故意** fail-fast（把预期的登录
静默降级成 OS 身份是安全意外，见 `provider.py` 的注释）。

于是纯 `olav + olav-netops` 安装的实际表现是：

```
olav init      → ✓ 成功，还打印了 token 和 web 登录链接
olav doctor    → ✓ healthy (9/9 checks passed)
olav "任何问题" → NotImplementedError: auth.mode='token' requires olav-ent
```

**两个绿色健康信号在前，第一个真问题就死。** 这直接堵死 Ch1 及之后所有 beat。

修复：仅当 `olav.enterprise.auth.token` 可导入时才切换 mode；admin 用户和 token
照旧创建（装上 olav-ent 立即可用），并在 init 输出里明说这套安装走 OS 身份。

**为什么本地从未发现**：dev 机上 `olav.enterprise` 在 path 上，`token` 能解析，
那次写入看起来毫无害处。我在 VM 上现场对照过：

| | `olav.enterprise` | `get_auth_provider("token")` |
|---|---|---|
| dev 机（editable） | PRESENT | `TokenAuthProvider` |
| 测试 VM（wheel） | absent | `NotImplementedError` |

回归测试 `test_init_never_writes_an_auth_mode_this_install_cannot_serve` 模拟扩展
缺失，断言 init 写出的 mode 必须能被 `get_auth_provider` 服务——对修复前的代码会
以 `bricked-OSS-install defect` 失败。原有的
`test_init_sets_auth_mode_token` 断言的正是那个错误的无条件行为，已改为按安装形态
取期望值。

> 这一条同时命中 CLAUDE.md 的两条规则：「必须从真实入口验证」与「永不用 editable
> 安装验证发布」。它们抓的是同一个缺陷。

## 1b. BUG-2（Ch2，未修）：导出产物静默只含 20/339 行，而答案指向它

Ch2 第二 beat（"List every device with its model and mgmt IP, and export it to
CSV"）**看起来成功**，最终答案是：

> The device inventory containing the name, model, and management IP for **all
> devices** has been exported to: `exports/queries/device_inventory.csv`

那个文件只有 **21 行（20 台设备）**。完整的 339 行导出确实存在，但在另一个
**答案从未提到**的文件名下（`query_20260805_155713.csv`，20271 字节）。

审计库（零 LLM）还原的链条：

| 时刻 | 调用 | 结果 |
|---|---|---|
| 15:57:13 | `execute_sql` | 完整 339 行写入 `exports/queries/query_….csv`，返回**截断预览** |
| 15:57:47 | `format_and_export` | 从预览写出 `device_inventory.csv`（1265 字节）|
| 15:57:52 | `olav_delegate` | 答案指向 `device_inventory.csv`，称其为 "all devices" |

**工具契约是对的，别改工具。** `execute_sql` 实现了 "cap to context, full to
file"，并把两件事都告诉了模型：

```
FULL results (339 rows) exported to exports/queries/query_….csv.
Only first 20 rows returned to context to prevent bloat.
```

`format_and_export(data: str, …)` 的文档也明说 `data` 是**字符串字面内容**。
所以 20 这个数字的来源是 tier 的上下文行数上限（doctor 报 `tier=medium` →
`MAX_ROWS_TO_CONTEXT=20`，正是 CLAUDE.md 的 10/20/50 表），模型只能拿到 20 行，
它就把 20 行写成了文件。

**这是 agent 行为问题**：被明确告知完整结果已在磁盘上，仍然用受上下文限制的路径
重新导出，并把用户指向截断版。按 CLAUDE.md 该走转向层（`*.guide.yaml` →
`usage_guide`）修，而不是改代码——「Steer behavior via memory, not code」。

危害等级不低：Ch2 的卖点原话是「the data is exact, not hallucinated」。数据确实
没被编造，但**被静默截断了**，而文件存在、格式正确、看不出问题。录 demo 时若打开
那份 CSV，屏幕上就是 20 行。

## 1c. 观察（Ch2 第一 beat）：最终答案偶发为空

Ch2 第一 beat rc=0、148s、子 agent 4 次 `execute_sql` 后**正确答出**（审计库里
`task` 的返回是 `'Based on the most recent import … Most Recent Import
Timestamp: 2026-08-05T15:49:33 …'`），但 stdout 上只有开场白，**最终答案没有被
打印**。编排器丢掉了子 agent 的输出——正是 CLAUDE.md「orchestrator 必须原样返回
子 agent 输出」要防的那件事。

不是普遍现象：Ch1、Ch2-csv、Ch3 都正常输出。观察到 1/4。`agents/agent.py:677`
的注释描述了一个同形失效：「synthesis step after a large ToolMessage 返回
0 completion_tokens 空内容」——`_ValidatingSQLiteCache` 只防止把空响应**缓存**
下来，不会重试，所以用户就是什么都看不到。

要按 CLAUDE.md 的 N≥3 规则定性还需专门测量，而这里有个障碍值得单独记：
**没有关闭 LLM 缓存的开关**（`agents/agent.py:685` 无条件 `set_llm_cache`，
grep 不到 `OLAV_DISABLE_LLM_CACHE` 之类）。缓存按 prompt 命中，所以重复同一
prompt 采样并不独立，只能手删 `~/.olav/cache/`。要求 N≥3 的项目，应该提供这个
开关。

## 1d. Ch4 镜像名：**不是缺陷，是 1/3 变异**（我在 N=1 上误判过一次）

Ch4 第一 beat 原话是 **"Deploy batfish/allinone, ports 9996 9997"**。第一次运行
生成的 compose 是：

```yaml
services:
  batfish:
    image: batfish/batfish:latest      # ← prompt 说的是 batfish/allinone
    ports: ["9996:9996", "9997:9997"]  # ← 端口正确
```

我当即把它记成了一个真缺陷。**错了**——按 CLAUDE.md 的 N≥3 规则补采样后：

| run | 生成的镜像 | |
|---|---|---|
| 1 | `batfish/batfish:latest` | ❌ |
| 2 | `batfish/allinone:latest` | ✅ |
| 3 | `batfish/allinone` | ✅（无 tag，docker 默认 latest）|

2/3 正确，所以这是 **LLM 变异，不是系统性 bug**。留在文档里有两个理由：

1. **它仍是录制风险。** 本地只缓存了 `batfish/allinone:*`，而 runsheet 的 Setup
   正是靠这个缓存让「self-service deploy 在镜头前很快」。1/3 的概率会写成一个
   缓存未命中的镜像名，镜头前变成 2GB 拉取。单镜到底的 demo 值得先跑一次预热，
   或在 prompt 里把镜像名写成 `batfish/allinone:latest`（带 tag 更不容易漂）。
2. **它是「N=1 不是信号」的现成例子。** 我差点把一次变异写成缺陷提交，和
   CLAUDE.md 记录的 V2_VALIDATION_RETROSPECTIVE §M4 是同一个坑。

端口三次全对。

## 1e. Ch4 的 HITL 门无法在一次性 CLI 中通过（非缺陷，但限制了本轮验证）

部署 beat 停在 agent 的**对话式确认**上：

```
**Confirmation Required:**
I plan to execute `deploy_service(name='batfish', confirmed=True)` …
Confirm?
```

`--auto-approve --dangerously-skip-permissions` 关掉的是 OLAV 的权限门，而这一步
是 agent 用一轮对话问的。一次性 `olav --agent …` 没有第二轮可答，于是容器永不启动
（runsheet 自己也写明「The deploy asks for a one-key confirmation — that HITL
gate is by design」）。

好处是 compose 文件在确认**之前**就写好了，所以每次运行都留下证据，可以只针对
「镜像名」这一个问题做 N≥3 采样而不必真部署。

## 1f. 环境约束：并发跑 agent 会让共用端点的嵌入静默失效（**我又一次先下错结论**）

`192.168.8.12:11433` 同时提供 `gemma4-31b-agent`（LLM）与 `embeddinggemma-300m`
（嵌入）。我在并发跑 §1d 的采样时看到：

```
embed_text failed: Error code: 500 -
{'error': {'message': 'model name=embeddinggemma-300m failed to load'}}
```

`olav kb search` 随之静默退化成非语义路径（返回一批毫不相关的 guide，全部
`conf=1.00`）。我据此写下了「单槽互斥，agent 运行期间 AutoRecall 拿不到任何
guide」——**这个结论是错的**，串行复测直接推翻：

| 步骤 | 结果 | 之后 `loaded` |
|---|---|---|
| A 空闲时请求嵌入 | ✅ 返回向量 | `embeddinggemma-300m` |
| C 紧接着请求 LLM | ✅ 返回补全 | `gemma4-31b-agent` |
| D 再请求嵌入 | ✅ 返回向量 | `embeddinggemma-300m` |

服务器**确实按需换页**，串行请求下两者都正常。500 只在**并发**（两个 agent 进程
＋探针同时打）时出现。所以：

- **§1b 的定性不变**：转向层当时是可用的，agent 不是「没拿到 guide」。
- 真正的注意事项换成了：**不要在同一台 swap 服务器上并发跑 agent**。会 500，而且
  OLAV 是静默降级——AutoRecall 拿不到向量就跳过，不报错。并行跑 e2e 套件时尤其
  要注意这一点。
- 附带解释了耗时：每次 LLM↔嵌入交替都要重新加载模型，这也是今天各 beat 普遍偏慢
  的一部分原因（早先那轮基准里 gemma4 第一格 91s、后三格 53s，同一现象）。

同一天内我第二次在 N=1 上给出错误定性（另一次是 §1d）。两次都是靠补做对照实验
纠正的，记在这里当作提醒：**先测串行/并发对照，再写结论。**

## 1g. Ch4 ★★★ beat 失败：agent 挑错设备，然后把数据报成「不存在」

runsheet 里三星的那一拍（"Write a change plan to add a redundant eBGP uplink on
the **alpha border router**, mirroring the existing AARNet peer"）跑完
rc=0、377s、约 10 次 SQL，**没有产出变更计划**，最终答案是索要数据：

> I am currently blocked because the platform's current data store contains **no
> record** of the existing AARNet BGP peer configuration on the
> `alpha-wan-6880v` router. … **Missing Data**: There are no BGP
> configurations, peer IPs, AS numbers, or route-maps for "AARNet" in
> `netops.raw_output_store` or `netops.parsed_outputs`.

零 LLM 直接查库，事实完全相反：

| 检查 | 结果 |
|---|---|
| `netops.devices` 里有 `alpha-border-4500x.net.demo.internal`？ | **有**（hostname 字面含 "border"）|
| 它的 `show running-config` 提到 AARNet？ | **提到**（34759 字符那份，另有 `show running-config all` 88786 字符）|
| 它的 running-config 含 `router bgp`？ | **含** |
| 入库是否完整？ | devices 339 = raw_output_store 唯一设备 339，**0 个孤儿** |

agent 分析的是 `alpha-wan-6880v`——**另一台设备**。prompt 说的是「alpha border
router」，一个 `hostname ilike '%alpha%border%'` 就能命中。

**一个加剧因素（真缺陷）**：`netops.devices.role` 在 339 台设备上**全为 NULL**，
而 `execute_sql` 的 SCHEMA_HINT 恰恰把它宣传给模型：

```
Schema reminder: netops.devices(hostname,platform,ip_address,role) | …
```

模型被告知有 `role` 可用于「哪台是 border」，查出来全空，只能回退到猜 hostname，
于是猜错。这是**提示与数据不一致**：要么导入时填充 `role`（hostname 启发式 + CDP
拓扑位置都够用），要么在它恒为 NULL 时别写进 SCHEMA_HINT。目前两者都没做。

N≥3 采样结果见下（本轮串行跑，避免 §1f 的并发问题）。

## 2. 环境/文档漂移（4 项，非代码缺陷）

**DRIFT-1 — runsheet Ch0 的命令已弃用。** `olav skill install olav-netops` 仍然
工作，但打印 `warning: olav skill is deprecated; use olav agent instead. Forwarding…`。
runsheet 正文该更新为 `olav agent install`。

**DRIFT-2 — runsheet 的「Setup (off camera)」没提嵌入端点，而它是硬前提。**
7 月 demo 配置里的 `192.168.8.50:11434` 现已下线。嵌入不可用时 `olav init`
**不会失败**，只是安静地降级：

```
guides: ✓ guides primed: 0 (16 skipped)
indexes: ✓ router(⚠ Connection error.), memory(ready)
```

按 CLAUDE.md，`usage_guide` 是 AutoRecall 注入**每一次**模型调用的转向层
(ADR-0015)，router 索引决定路由。0 guides + 空 router 是一个**实质不同**的
agent 环境，却顶着 `✓` 通过。改指 `192.168.8.12:11433` /
`embeddinggemma-300m`（CLAUDE.md 记录的 CI 用法）后恢复为
`router(21 entries)` + `guides primed: 16`（装完 netops 累计 46）。
runsheet 的 Setup 段应把嵌入端点列为和 LLM 端点同等的前提。

**DRIFT-3 — runsheet 写的模型别名已不可用。** `gemma4-31b-it-qat` 在
`192.168.8.12:11433` 上仍列出但 `unloaded`，实际调用返回
`500 model name=gemma4-31b-it-qat failed to load`。当前 `loaded` 且可生成的是
`gemma4-31b-agent`（也是平台侧现在实际在用的别名）。**注意这不是 doctor 漏检**：
`LLMFactory.check_connectivity()` 会做一次真实 `llm.invoke`，所以它当时报的 ✓ 是
真生成成功，之后的 500 是 swap 服务器的瞬时状态。

**DRIFT-4 — 撤回：归档规模与 runsheet 一致。** 我先按归档里的目录名数出 238 台，
以为对不上 runsheet 的 339。实际导入后 `netops.devices` **正好 339** 行——目录名
不等于设备数（CDP 邻居发现等会补出更多）。记在这里是因为教训是通用的：
**agent 的自述和我的静态计数都不算证据，落库的行数才算**（本轮两者恰好都要靠
DB 查询才能判定谁对）。

## 3. 观察：`OLAV_HOME` 并不隔离 LLM 缓存与 checkpoint

```python
# core/config.py:1334
USER_CACHE_DIR      = Path.home() / ".olav" / "cache" / _username
USER_CHECKPOINT_DIR = Path.home() / ".olav" / "checkpoints" / _username
```

两者**硬编码 `Path.home()`**，不受 `OLAV_HOME` 影响，而 `olav doctor` 会打印
`workspace … (OLAV_HOME pinned)`，读起来像是整个部署都被钉住了。注释写的是
"user-isolated"，所以按 OS 用户隔离大概是设计意图，不是 bug——但后果值得写下来：

- 同一台机器上的两套 `OLAV_HOME` 部署**共享** `llm_cache.db` 和 checkpoints。
- 对**录 demo** 尤其要紧：LLM 缓存按 prompt 命中且无条件启用
  (`agents/agent.py:685`)。本轮验证用的 prompt 是 runsheet 原话，也就是 7 月
  demo 跑过的原话——如果不先把旧缓存挪走，跑出来的「通过」可能来自缓存，毫无
  价值。本轮已把 VM 上遗留的 `~/.olav`（含 12M `llm_cache.db`）改名挪开。

用户自己的 `reset-demo.sh` 已经把 `~/.olav` 当一次性目录整体删除，说明这个坑
之前踩过。建议至少在 runsheet 的 Setup 段写明。

## 4. 顺带修正一处用户可见报错的指引

`_ENT_AUTH_MSG` 让卡住的操作者去看 `dev_docs/111`，而那份文档是
《DuckDB Write-Concurrency: Tiered Model》，与 auth 分层无关。改指
`dev_docs/31 ENTERPRISE_FEATURES`（ent auth 的实际出处）。

代码注释里 "dev_docs/111 tiered model" 是既有简写惯例（`os_identity.py`、
`service.py`、多个测试都在用），**未动**——只改用户可见的这一条。

## 5. 复现方式

```bash
# 本机
uv build && (cd olav-netops && uv build)
uv run --with twine twine check dist/*.whl olav-netops/dist/*.whl

# VM（sshpass 未装，用 paramiko helper；见 job tmp 的 vm.py）
python3 -m venv .venv
.venv/bin/pip install ./olav-0.25.1-py3-none-any.whl './olav_netops-0.25.1-py3-none-any.whl[sim]'
export OLAV_HOME=$HOME/olav-test
olav init && olav agent install olav-netops && olav doctor
```

Ch2–Ch5 在 runsheet 里是 `[TUI]` beat，后台 agent 无法驱动 TUI，故改走
文档化的一次性路径 `olav --agent <name> "<原话>"`（`/workspace <name>` ↔
`--agent <name>`），prompt 逐字照抄，验的是 agent 行为而非改写后的近似。
驱动脚本：job tmp 的 `runsheet.sh`。

**这个替代方式有一处必须说明的偏差**：TUI 里 Ch1→Ch5 是**同一个会话**，而每次
`olav --agent` 都是全新会话。所以 Ch2 的原话「what we **just** imported」在这里
没有对话上下文可依。agent 自己说明了这一点，然后改为查询「最近一次导入」并给出
正确答案——就本轮而言这比原路径更强（无上下文也做对了），但复现 demo 观感时应当
用 `--session <id>` 串起来，或直接在 TUI 里跑。

wheel 卫生：两个 wheel 顶层分别只有 `olav/` 和 `olav_netops/`，无 `.env`/
`.pypirc`/密钥类文件名，netops 带上 160 个 workspace 文件，`twine check` 双 PASSED。
