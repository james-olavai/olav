# 92. deepagents 0.6.7 新特性集成 + 垃圾代码清理

**Date**: 2026-06-01
**Scope**: deepagents 0.6.7 特性落地 + _deepagents_bridge.py / agent.py 清理

本文记录 deepagents 0.6.7 落地决策，覆盖四个优先级：
- **P1**: `RubricMiddleware(on_evaluation=...)` → 结构化审计日志

## 1. 背景

v0.20 将 `rubric_middleware: true` + `enable_todo_list: true` 推广到所有 20 个
SKILL.md 文件。RubricMiddleware 现在已在每个 opted-in sub-agent 的中间件栈中注入，
但注入时仅使用了 `model` + `max_iterations` 两个参数：

```python
# agent.py 旧代码（v0.20 前）
_middleware.append(_RubricMW(model=sa_llm, max_iterations=2))
```

deepagents 0.6.7 中 `RubricMiddleware` 新增 `on_evaluation` 回调参数，
允许在每次自评循环结束时收到结构化的 `RubricEvaluation` 对象。

## 2. P1 — on_evaluation 回调 (已实现)

### 2.1 为什么需要

`RubricMiddleware` 的自评结果（通过 / 失败的标准、重试次数）目前静默。
运维人员无法：
- 知道某个 agent 是否触发了重试
- 知道哪条 rubric 标准最常失败（驱动 prompt 迭代）
- 在 `audit_events` 表中查询评估历史

### 2.2 实现方案

在 `agent.py::_build_subagents()` 内定义一个闭包：

```python
def _make_rubric_callback(agent_name: str):
    def _on_evaluation(evaluation) -> None:
        try:
            payload = {
                "agent": agent_name,
                "passed": getattr(evaluation, "passed", None),
                "iterations": getattr(evaluation, "iterations", None),
                "criteria": [
                    {
                        "name": getattr(c, "name", str(c)),
                        "passed": getattr(c, "passed", None),
                        "reason": getattr(c, "reason", None),
                    }
                    for c in (getattr(evaluation, "criteria", []) or [])
                ],
            }
            logger.info("rubric_evaluation agent=%s passed=%s iterations=%s",
                        agent_name,
                        payload["passed"],
                        payload["iterations"])
            logger.debug("rubric_evaluation detail: %s", payload)
        except Exception as _log_exc:
            logger.debug("rubric_evaluation callback error: %s", _log_exc)
    return _on_evaluation
```

调用时：
```python
_middleware.append(_RubricMW(
    model=sa_llm,
    max_iterations=2,
    on_evaluation=_make_rubric_callback(name),
))
```

### 2.3 为什么不写入 audit_events 表

`audit_recorder.record()` 需要 `run_id` / `session_id`，在 `_build_subagents()` 中
这些值不在作用域内（build 时还没有 invocation context）。
Logger 是正确的选择：
- `agent_name` / `passed` / `iterations` 始终可用
- 日志可转发到任何 syslog/ELK 管道
- 不引入跨边界依赖

后续：若需要持久化，可在运行时通过 LangGraph callback 把 `rubric_evaluation`
日志行解析写入 `audit_events`。

## 3. P2 — permissions 显式传参 (已实现)

### 3.1 现状

```python
# agent.py 旧代码
_create_kwargs: dict = dict(...)
if _fs_permissions is not None:
    _create_kwargs["permissions"] = _fs_permissions
```

条件写法是防御性补丁，不是架构决策。`create_deep_agent()` 接受
`permissions=[]` 作为"不授予任何文件系统权限"的显式意图。
条件写法留下了"_fs_permissions 是 None 时行为未定义"的隐患。

### 3.2 实现

```python
_create_kwargs["permissions"] = _fs_permissions or []
```

`_fs_permissions` 为 `None` 时等价于 `[]`（不授予 FS 权限），
与 deepagents 0.6.7 的 FilesystemPermission 语义一致。

## 5. P3 — HarnessProfile (推迟)

deepagents 0.6.7 引入 `register_harness_profile()` / `HarnessProfile`，
允许在模块加载时预定义 middleware stack 模板。

**评估结论**：推迟。原因：
- `_build_subagents()` 当前在 build 时动态组装 middleware，依赖运行时参数
  （`sa_llm`、`metadata`、`name` 等），这些值在模块加载时不可用。
- `HarnessProfile` 适合静态、可复用的 stack 描述，不适合动态组装。
- 重构为 HarnessProfile 会增加代码量和间接层，不带来明显运行时收益。
- 等 0.7.x HarnessProfile API 稳定后重新评估。

## 6. P4 — ProviderProfile (推迟)

`ProviderProfile` 允许把 `should_use_prompt_caching()` 逻辑内嵌到
deepagents 的 provider 检测体系。

**评估结论**：推迟。原因：
- `should_use_prompt_caching()` 当前只有 12 行，功能完整且有单元测试。
- `ProviderProfile` API 在 0.6.x 仍处于 experimental 状态。
- OLAV 的 provider 检测依赖 `olav.core.config.get_llm_config()`，
  与 deepagents 的 provider 发现机制存在阻抗失配。
- 替换后 `test_should_use_prompt_caching_*` 测试需要全部重写。
