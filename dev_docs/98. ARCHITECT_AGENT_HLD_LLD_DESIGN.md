# ARCHITECT Agent — HLD/LLD Design Proposal

**Status**: Proposal (pre-implementation)  
**Date**: 2026-06-24  
**Context**: Extension of OLAV's reasoning capability from device verification to
architecture design generation. Motivated by the observation that if agents can
reason over existing network state to produce change plans, they should also be
able to reason over customer requirements and documents to produce HLD/LLD.

---

## 1. Why a New Domain

`architect` is NOT a sub-domain of `netops` or `audit`. The distinction is temporal
and directional:

| Domain | Time horizon | Input | Output |
|---|---|---|---|
| `netops` | Present | Live snapshots | Change plan CLI |
| `audit` | Present | DB snapshots | Health report |
| `architect` | **Future** | Requirements + docs | HLD → LLD design |

Adding `architect` sub-agents to `netops` would pollute the routing table and
conflate operational intent with design intent. This is a new top-level domain
per ADR-0004.

**Allowed dependency direction**: `architect` → `netops` (read topology DB,
delegate to `simulator` for validation). Never the reverse.

## 3. HLD Sub-agent

### 3.1 Nature of the task

HLD is **dialogue-driven collaborative design**, not autonomous document analysis.
The human architect is a co-author throughout. The agent's role is:
- Structured requirements elicitation
- Document evidence gathering
- Gap detection and targeted questioning
- Incremental chapter drafting with human review at each step
- Design decision traceability

This distinguishes it from `audit/explorer` (autonomous investigation) and from
`analyzer` (change planning against existing state).

### 3.2 Workflow — Five Phases

#### Phase 0: Kickoff Dialogue

Trigger: user says "start HLD" / "new design project X"

The agent outputs a **structured requirements questionnaire** covering:
1. Business context — what problem is being solved, for whom
2. Scale constraints — sites, device count, traffic volume, user count
3. Vendor/platform preferences — existing contracts, inventory constraints
4. Protocol constraints — existing BGP/OSPF domains, MPLS/SD-WAN requirements
5. Redundancy requirements — RTO/RPO, which layers can have single points of failure
6. Compliance/security — data segmentation, audit requirements
7. Available documents — what files exist and where

Human answers → agent summarises as **requirements matrix** → human confirms →
saved to `design_runs` record.

#### Phase 1: Context Build (Document Survey + Gap Analysis)

**Prerequisite — memory-curator must run first.**  Before Phase 1 starts,
all documents in the project directory must be ingested into LanceDB via
`memory-curator`.  This is not optional pre-processing — it is the
"database modelling" step for HLD, equivalent to what `netops.*` schema
is for change plans.  Without it, `olav_recall_memory` has nothing to
query and every gap will appear as "missing" even when the answer exists
in a document.

Phase 1 is **script-driven**, not narrative.  The agent calls
`inspect_requirements.py` (a deterministic script, no LLM involvement)
which cross-references the requirements matrix from Phase 0 against
LanceDB and returns a **three-bucket report** — the same structure used
by `analyzer/scripts/inspect_devices.py`:

```python
# inspect_requirements.py returns:
{
    "confirmed": {
        "sites":     {"value": ["SH-DC1","BJ-DC2","GZ-DC3"],
                      "source": "site_survey_2025.pdf", "evidence_id": "ev_abc"},
        "bandwidth": {"value": "≥10G",
                      "source": "requirements_v2.docx",  "evidence_id": "ev_def"},
    },
    "partial": {
        "redundancy": {"partial_value": "dual-active mentioned",
                       "missing_detail": "RTO not defined",
                       "source": "meeting_notes_2025-11-03.md"},
    },
    "missing": ["ip_space", "security_zoning", "vendor_preference"],
}
```

The LLM's role in Phase 1 is narrow: convert `partial` and `missing`
entries into **1–3 targeted questions** for the human, ranked by how
much they block topology decisions.  It does not decide what is missing
— the script decides that.

Phase 1 output shown to human (generated from the three-bucket result):

```markdown
## Confirmed (from documents)
- Core sites: 3 (SH/BJ/GZ) — source: site_survey_2025.pdf
- Uplink bandwidth: ≥10G   — source: requirements_v2.docx

## Need clarification (1 question)
- Redundancy: meeting notes say "dual-active" but RTO is not defined.
  → What is the RTO target? Sub-second / <30s / minutes acceptable?

## Missing (need your input — 2 items, topology-blocking first)
1. IP address space: no document mentions this.
   → Existing IP space? IPv4/IPv6 dual-stack required?
2. Security zoning: no document covers this.
   → DMZ / production / management three-zone isolation needed?
```

Human answers → agent calls `inspect_requirements.py` again with updated
matrix → iterates until `missing` and `partial` lists are empty for all
`blocks_topology: true` dimensions.

#### Phase 2: Skeleton Proposal

Once the requirements matrix has no critical gaps, agent proposes a **chapter
skeleton** with a one-sentence scope for each chapter:

```markdown
## Proposed HLD Structure

1. Executive Summary       — objectives, key decisions, expected outcomes (1 page)
2. Business Requirements   — requirements matrix with document/conversation traceability
3. Logical Topology        — layered architecture (Core/Dist/Access or Spine-Leaf), protocol selection
4. Physical Topology       — inter-site connectivity, device role assignment
5. Routing & Protocol      — BGP/OSPF design, AS numbering, routing policy
6. Redundancy & HA         — failure domain partitioning, failover mechanisms, RTO/RPO mapping
7. Address Planning        — IP space allocation strategy, VLAN/VRF naming convention
8. Security Zoning         — zone definitions, policy framework
9. Risks & Constraints     — known risks, design limitations, open items

Confirm this structure? Add / remove / reorder chapters as needed.
```

**HITL gate**: human must explicitly confirm/modify the skeleton before Phase 3.

After skeleton approval:
```python
write_todos([chapter title for each approved chapter])
```

#### Phase 3: Chapter Loop

Each chapter is driven by the **Plan-Act-Reflect** pattern (see
`analyzer/references/plan_act_reflect_workflow.guide.yaml`).  The same
rule that applies to change plans applies here: *each stage must produce
a named artifact; if you cannot name the artifact, the stage is not
concrete enough.*

```
┌──────────────────────────────────────────────────────────────┐
│  Chapter N — Plan-Act-Reflect micro-cycle                    │
│                                                              │
│  PLAN                                                        │
│  1. write_todos for this chapter:                            │
│     - recall evidence  → artifact: evidence list            │
│     - draft content    → artifact: chapter markdown draft   │
│     - reflect          → artifact: [PENDING] list           │
│     - human review     → artifact: approved chapter         │
│                                                              │
│  ACT                                                         │
│  2. olav_recall_memory(query="<chapter topic>")              │
│     + pull relevant fields from requirements matrix          │
│     → evidence list in context                               │
│                                                              │
│  3. Draft chapter                                            │
│     — every design decision: WHAT + WHY + source citation   │
│     — unknown info → mark with [PENDING: <question>]        │
│     → chapter draft in context                               │
│                                                              │
│  REFLECT (before showing to human)                           │
│  4. Check against this list — do NOT skip:                   │
│     □ Every design decision has a source citation?           │
│     □ Any [PENDING] markers remain? (= chapter incomplete)  │
│     □ Next chapters depend on anything unconfirmed here?    │
│     □ Is the artifact concrete data, not hand-wavy prose?   │
│     If any □ fails → add remediation step, re-draft first.  │
│                                                              │
│  5. Output draft + PENDING list to human                     │
│     "Chapter N draft — N items need your input..."          │
│                                                              │
│  ITERATE                                                     │
│  6. Human review:                                            │
│     A. Approve → write_todos done, format_and_export append  │
│     B. Request change → revise → return to REFLECT           │
│     C. Answer PENDING → fill in → return to REFLECT          │
│                                                              │
│  7. Chapter complete → next chapter                          │
└──────────────────────────────────────────────────────────────┘
```

Key rules:
- **[PENDING: X] markers**: agent never fabricates missing information.
  Unknown facts are explicitly flagged.  The Reflect checklist enforces
  this — a chapter with any unresolved `[PENDING]` marker fails the check
  and cannot be submitted to the human as "ready for review".
- **Rationale tracking**: every design decision records WHY, not just WHAT.
- **Incremental file write**: each approved chapter is immediately appended
  to the HLD file via `format_and_export(mode="append")`.  A context window
  reset does not lose completed chapters.
- **Cross-chapter gaps**: if Chapter 5 drafting reveals a gap from Chapter 4
  (e.g. physical bandwidth needed for protocol design), add to
  `questions_backlog` with `blocks_chapter=5` and surface after the
  current chapter closes.
- **Anti-hallucination**: "HLD chapters written without staged planning tend
  to embed fabricated design decisions not grounded in any requirement or
  document."  The Reflect checklist is the enforcement mechanism.

#### Phase 4: Sign-off

All chapters complete → agent presents a summary:

```
HLD complete: exports/designs/HLD_<project>_<date>.md
9 chapters, X design decisions, Y document citations.

Key decisions:
- Topology: Spine-Leaf (reason: east-west dominant traffic, 3 DC nodes)
- Routing: eBGP (reason: multi-AS, existing Cisco+Juniper mixed fleet)
- Redundancy: dual-active (reason: RTO <30s, confirmed meeting 2025-11-03)
...

Approve this HLD? Approval triggers LLD phase.
```

Human approves → HLD status set to `approved` in `design_runs` → structured
constraint set exported for LLD sub-agent input.

### 3.4 Small-model considerations

**`memory-curator` is a mandatory prerequisite, not optional pre-processing.**
It is the "database modelling" step for HLD — converting unstructured documents
into queryable LanceDB entries — exactly as `netops.*` schema is the prerequisite
for change plans.  Skipping it leaves `olav_recall_memory` with nothing to
query, forcing the LLM to hallucinate design decisions from training data rather
than project-specific documents.  The `hld` agent should refuse to proceed past
Phase 0 if the project document directory has not been ingested.

Additional mitigations:

1. **Script-driven gap analysis**: `inspect_requirements.py` runs deterministically
   (no LLM) to produce the three-bucket report.  The LLM only converts the
   `missing` list into natural-language questions — it does not decide what is
   missing.  This eliminates a major hallucination surface.
2. **Scoped recall per chapter**: each `olav_recall_memory` query is scoped to
   the current chapter topic.  The agent never loads the entire document corpus
   into context simultaneously.
3. **Chapter scope bounding**: each chapter is an independently bounded task.
   Plan-Act-Reflect's Reflect checklist enforces that every claim is grounded
   before the chapter is marked complete.
4. **Structured state survives context resets**: `design_runs` / `design_decisions`
   / `questions_backlog` tables let the agent reconstruct its position from DB
   state, not conversation history.

## 4. LLD Sub-agent

### 4.1 Nature of the task

LLD is **generative reasoning followed by infrastructure validation**.

The critical distinction from change plan:

| | Change Plan | LLD |
|---|---|---|
| First step | READ existing state (DB drives everything) | REASON from HLD constraints (no state to read) |
| DB role | Primary input — state determines what to generate | Validation tool — check generated specs for conflicts |
| Fat tool input | SQL query results (known data) | Reasoning output (LLM-created structure) |
| Simulator necessity | Optional (config already exists) | Mandatory (config does not exist; synthetic snapshot only path) |
| Guide.yaml role | Auxiliary (CLI format rules) | Core knowledge source (design principles live here) |

There is **no existing data to query in the generation phase**.  The LLM
reasons from HLD constraints and injected design-pattern guides to produce
a design skeleton, then fat tools fill in the deterministic values, and
only then does the infrastructure (DB + Batfish) act as a validation oracle.

### 4.2 Workflow — Three Phases

#### Phase 1: Reason (pure LLM, no DB)

Input: HLD constraint set from `design_runs.hld_constraints_json`.

The LLM works entirely from reasoning — no SQL queries at this stage.
`thinking_mode: enabled` is essential here.  `olav_recall_memory` injects
design-pattern guides as the knowledge source.

Questions the LLM must answer from HLD constraints alone:

```
Topology arithmetic:
  3 spines × 9 leaves = 27 point-to-point links → need 27 × /31
  How many loopbacks? → 1 per device (spine + leaf)

IP segmentation:
  Given 10.0.0.0/8 from HLD:
  → p2p links:       10.0.0.0/24  (128 × /31, enough for 27 links)
  → spine loopbacks: 10.0.255.0/27 (32 addresses, enough for 3 spines)
  → leaf loopbacks:  10.0.254.0/27 (32 addresses, enough for 9 leaves)
  → mgmt:            10.0.253.0/24

BGP AS design:
  eBGP chosen in HLD → private AS range 65000–65535
  Spine shared AS or individual?
  → shared (65000) — simpler policy, standard for DC fabric
  Leaf AS: 65001–65009 (one per leaf)

VRF/VLAN segmentation:
  production / management / out-of-band as per HLD security zoning
```

Phase 1 output: **design skeleton** — structure and rules, no exact values yet:

```json
{
  "p2p_scheme":     {"pool": "10.0.0.0/24", "prefix_len": 31},
  "loopback_spine": {"pool": "10.0.255.0/27"},
  "loopback_leaf":  {"pool": "10.0.254.0/27"},
  "bgp_spine_as":   65000,
  "bgp_leaf_as_base": 65001,
  "vrf_list":       ["PROD", "MGMT", "OOB"],
  "link_count":     27,
  "device_list":    ["spine-01","spine-02","spine-03","leaf-01",...]
}
```

HITL gate after Phase 1: present the design skeleton and AS/IP strategy to
the human architect before filling in exact values.  Structural errors
(wrong AS range, wrong IP segmentation) are far cheaper to fix here than
after full specification.

#### Phase 2: Specify (LLM gives structure → fat tools fill exact values)

Once the skeleton is approved, exact value assignment is **deterministic
math** — the LLM must not compute it iteratively (subnet-by-subnet loops
produce drift errors).  Fat tools handle this in one call:

```python
# ip_allocation_planner.py
# Input: approved design skeleton (JSON)
# Python computes every address assignment deterministically
# Output: complete allocation table — no LLM math involved
{
  "p2p_links": [
    {"a_device": "spine-01", "a_iface": "Eth1/1", "a_ip": "10.0.0.0/31",
     "b_device": "leaf-01",  "b_iface": "Eth1/1", "b_ip": "10.0.0.1/31"},
    ...  # all 27 links
  ],
  "loopbacks": [
    {"device": "spine-01", "ip": "10.0.255.1/32"},
    ...
  ]
}

# protocol_param_generator.py
# Input: BGP design rules from skeleton
# Output: complete neighbor matrix
{
  "bgp_sessions": [
    {"local": "spine-01", "local_as": 65000, "local_ip": "10.0.0.0",
     "remote": "leaf-01", "remote_as": 65001, "remote_ip": "10.0.0.1"},
    ...  # all 27 sessions
  ]
}
```

Phase 2 output: **complete LLD specification** — every device, interface,
IP, AS number, VRF assignment fully determined.

#### Phase 3: Validate (existing infrastructure as oracle)

Only in Phase 3 does the agent touch the DB and simulator.
DB queries here are conflict checks, not design drivers:

```
Conflict checks (DB):
  inspect_interfaces(devices=[]) → does any proposed IP already exist?
  inspect_devices(devices=[])    → does any proposed AS already exist?
  → if conflict → return to Phase 1 with specific constraint added

Config-layer validation (Batfish):
  analyzer generates mock CLI from Phase 2 spec
  task("simulator", "bgpSessionCompatibility on synthetic snapshot")
  task("simulator", "ospfSessionCompatibility on synthetic snapshot")
  → PASS: proceed to HITL final approval
  → conflicts found: return to Phase 2 with conflict details,
    revise affected sections only, re-validate

HITL gate: present complete LLD + validation results to human
  → approve → emit final documents
  → request changes → return to Phase 1 or 2 as appropriate
```

#### Emit

```
exports/designs/LLD_<project>_<date>.md     — human-readable full spec
lld_constraints_<project>.json              — structured, consumable by analyzer
```

### 4.3 LLD document structure

The markdown output follows the same section pattern as a change plan,
one abstraction level up — vendor-agnostic specs instead of vendor CLI:

```
# LLD: <Project Name>

## Summary         — what is being designed and why (2 sentences)
## Scope           — sites, device count, layers (L2/L3/L4)
## IP Allocation   — complete table: device / interface / IP / subnet / VRF
## Interface Spec  — per-device: interface / role / neighbor / speed
## Routing Design  — BGP AS assignments, neighbor matrix, OSPF areas
## VRF/VLAN        — segmentation assignments and policy boundaries
## Reversibility   — what must be undone to decommission this design
                     (equivalent of change plan rollback)
## Validation      — (device, show command, expected output) table
                     (equivalent of change plan post-checks)
## Risks           — 1–3 bullets
```

The **Reversibility** section is the LLD equivalent of change plan rollback
— it must exist for every LLD.  If the design cannot be reversed, that is
itself a risk that must be documented.

### 4.4 LLD to Analyzer interface

Phase 2 structured output feeds directly into `analyzer` for CLI generation:

```json
{
  "topology_type": "spine-leaf",
  "sites": ["SH-DC1", "BJ-DC2", "GZ-DC3"],
  "routing_protocol": "eBGP",
  "redundancy_model": "dual-active",
  "ip_allocations": [
    {"device": "spine-01", "interface": "Eth1/1", "ip": "10.0.0.0/31"},
    ...
  ],
  "bgp_neighbors": [
    {"local": "spine-01", "remote": "leaf-01",
     "local_as": 65000, "remote_as": 65001},
    ...
  ],
  "vrf_assignments": [...],
  "vendor_constraints": ["Cisco Nexus", "Juniper QFX"]
}
```

### 4.5 Simulator integration for new designs

`simulator` normally runs against an existing snapshot.  For LLD validation
of a new design (no snapshot exists yet):

1. `analyzer` converts LLD interface specs to minimal vendor CLI stubs
2. Batfish `init_snapshot_from_string` ingests the stubs as a synthetic snapshot
3. `simulator` runs `bgpSessionCompatibility` / `ospfSessionCompatibility`
4. Conflicts returned → LLD Phase 2 revision → re-validate

This catches design errors (AS conflicts, subnet overlaps, incompatible
timer policies) at config-layer before any physical work begins.

## 5. DB Schema

Three new tables in the `architect` schema (separate from `netops`):

```sql
-- Design run lifecycle (analogous to netops.exploration_runs)
CREATE TABLE architect.design_runs (
    run_id         VARCHAR PRIMARY KEY,
    project_name   VARCHAR NOT NULL,
    phase          VARCHAR NOT NULL,  -- kickoff/context/skeleton/chapter_loop/hld_approved/lld_draft/lld_approved
    current_chapter INT,
    hld_file_path  VARCHAR,
    lld_file_path  VARCHAR,
    hld_constraints_json VARCHAR,     -- structured output of finish_hld()
    created_at     TIMESTAMP,
    updated_at     TIMESTAMP
);

-- Evidence extracted from documents (traceability)
CREATE TABLE architect.design_evidence (
    evidence_id    VARCHAR PRIMARY KEY,
    run_id         VARCHAR NOT NULL,
    source_file    VARCHAR,           -- document filename
    source_type    VARCHAR,           -- document / conversation / standard
    content        VARCHAR NOT NULL,  -- extracted fact/constraint
    relevant_chapters VARCHAR[],
    recorded_at    TIMESTAMP
);

-- Approved design decisions (chapter-level)
CREATE TABLE architect.design_decisions (
    decision_id    VARCHAR PRIMARY KEY,
    run_id         VARCHAR NOT NULL,
    chapter        INT,
    chapter_title  VARCHAR,
    decision       VARCHAR NOT NULL,  -- what was decided
    rationale      VARCHAR NOT NULL,  -- why
    source_type    VARCHAR,           -- document / conversation / standard
    source_ref     VARCHAR,           -- evidence_id or conversation summary
    status         VARCHAR,           -- confirmed / pending / superseded
    recorded_at    TIMESTAMP
);

-- Open questions backlog
CREATE TABLE architect.questions_backlog (
    question_id    VARCHAR PRIMARY KEY,
    run_id         VARCHAR NOT NULL,
    raised_in_chapter INT,
    blocks_chapter INT,               -- NULL if non-blocking
    question       VARCHAR NOT NULL,
    priority       VARCHAR,           -- critical / nice_to_have
    status         VARCHAR,           -- open / answered
    answer         VARCHAR,
    answered_at    TIMESTAMP,
    created_at     TIMESTAMP
);
```

## 7. Architect Orchestrator

Thin router between `hld` and `lld`. Does not write reports or designs itself.

Routing rules:
- "start HLD / new project / design from scratch" → `hld`
- "continue HLD / next chapter / review chapter" → `hld`
- "start LLD / technical spec / IP allocation" → `lld` (requires approved HLD run_id)
- "validate design / check BGP compat" → `lld` (which delegates to `simulator`)

The orchestrator holds no design state itself — all state lives in `architect.*`
tables and the file system.

## 8. Key Design Principles

| Principle | Application |
|---|---|
| Dialogue-first, not autonomous | HLD never proceeds past skeleton without human confirmation |
| Explicit unknowns | `[PENDING: X]` markers + `questions_backlog` — never fabricate missing info |
| Decision traceability | Every design decision has source (document / conversation / standard) |
| Incremental persistence | Each approved chapter appended to file immediately — context reset safe |
| Small-model compatible | Per-chapter scoped recall; fat tools for bulk IP/protocol generation; structured state survives context resets |
| Validation before implementation | LLD validated by simulator before reaching analyzer; design errors caught at config-layer, not in production |

## 11. Lessons from Change Plan Experience

Derived from reading `analyzer/scripts/generate_change_plan.py`,
`inspect_devices.py`, and `references/plan_act_reflect_workflow.guide.yaml`.

### 11.1 Three-bucket pattern (inspect_devices.py → inspect_requirements.py)

`inspect_devices.py` returns `found / unknown_facts / unknown_devices`.
The LLM never decides what device facts are missing — the script does that
deterministically.  The LLM only uses the result to decide what to ask.

`inspect_requirements.py` must follow this pattern exactly:
`confirmed / partial / missing` for requirement dimensions.  This makes
Phase 1 gap analysis **testable and deterministic**, not dependent on the
LLM's interpretation of what's missing from the documents.

### 11.2 Fat tool pattern (generate_change_plan.py → ip_allocation_planner.py)

`generate_change_plan.py` was created because gemma4 would otherwise make
60–80 per-device SQL queries, overflowing context.  Input: SQL results
(existing data).  Output: complete markdown.  Python iterates; LLM never
sees the loop.

`ip_allocation_planner.py` solves the same looping problem for LLD — but
the input is different.  For change plan the fat tool reads from the DB.
For LLD, **there is no DB to read from** in the generation phase.  The
fat tool receives a **design skeleton produced by LLM reasoning** (Phase 1
output: pool CIDRs, prefix lengths, device list) and computes the exact
address assignments deterministically.

The pattern is the same — Python does the math, LLM never loops per-subnet —
but the upstream data source shifts from SQL to LLM reasoning.  This is the
key structural difference between the two fat tools.

### 11.3 Plan-Act-Reflect as the loop driver

The guide.yaml rule: *"each stage must produce a named artifact — if you
cannot name the artifact, the stage is not concrete enough."*

Applied to HLD:
- Each chapter IS the artifact.
- The Reflect checklist for HLD chapters is: every design decision has a
  source citation; no unresolved `[PENDING]` markers remain; next chapters
  have no unconfirmed dependencies.
- "HLD chapters written without staged planning tend to embed fabricated
  design decisions not grounded in any requirement or document" — this is
  the HLD equivalent of the change plan warning about hallucinated CLI.

### 11.4 Direct reuse — no rebuild needed

LLD already has access to the state data it needs through `analyzer`'s
existing scripts.  Call with `skill_name="analyzer"`:
- `inspect_devices.py` — existing platform/vendor/AS facts before designing
- `inspect_interfaces.py` — existing IP assignments before allocating new space
- `describe_table.py` — schema introspection for any unfamiliar `netops.*` table

### 11.5 The structural difference: HLD input is unstructured

Change plan's input is structured SQL (queryable, deterministic).
HLD's input is documents + conversation (unstructured, potentially contradictory).

`memory-curator` → LanceDB is the "upstream fat tool" that bridges this gap:
it converts unstructured inputs into a queryable form before the design loop
starts.  Without this pre-processing step, the HLD agent is in the same position
as an `analyzer` asked to write change plans with no DB — it will hallucinate.

This is why `memory-curator` ingestion is a **hard prerequisite**, not a nice-to-have.

## 10. Open Questions

1. **Document pre-ingestion UX**: does the user run `memory-curator` manually before
   starting HLD, or does `hld` trigger ingestion inline on first reference to a file?
   Inline is simpler for the user; pre-ingestion gives better recall quality.

2. **Synthetic snapshot format for LLD validation**: Batfish `init_snapshot_from_string`
   requires a specific directory structure. The `ip_allocation_planner` + `interface_spec_builder`
   outputs need to be assembled into this format. Whether `analyzer` or `lld` owns
   this assembly step is TBD.

3. **Multi-project state**: `design_runs` supports multiple concurrent projects.
   The orchestrator needs a "which project are we working on" context mechanism
   (either explicit `run_id` from user, or recall most recent open run).

4. **HLD chapter schema flexibility**: different network types (DC fabric vs campus
   vs WAN) have different standard chapter structures. The `hld_chapter_schema.guide.yaml`
   should be parameterised by network type rather than a single fixed template.
