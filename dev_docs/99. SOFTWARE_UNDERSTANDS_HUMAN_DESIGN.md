## 0. Framing — two loci of "understanding"

"Software should understand the human, not the human the software" is not a
single design axis for an agent-native system — it splits into two layers
that pull in different directions:

1. **Human ↔ agent.** The end user's/operator's experience should require no
   manual reading of docs/config schemas before the system is useful. This is
   the layer this doc focuses on.
2. **Agent ↔ system internals.** The LLM itself must be treated as a
   constrained, fallible reader — tool schemas, prompts, and control flow
   must be engineered *for the model's actual comprehension ceiling*
   (small-model-first). This layer is **already** OLAV's stated philosophy
   (CLAUDE.md "Design Principles (small-model-first)") and is not revisited
   here except as the reusable machinery that layer 1 should borrow.

The finding of this review: layer 2 is mature; layer 1 (the human-facing
surface — first run, configuration, failure recovery) still largely follows
the old "human must understand the software" model. The proposals below are
about extending layer-2 machinery (memory-driven steering, deterministic
gates) downward into layer 1, not inventing new architecture.

## 1. Current-state audit (verified against code, 2026-07-01)

### 1.1 First-run onboarding

| Behavior today | Location | Problem |
|---|---|---|
| `olav init` deploys `.olav/` scaffolding, returns a ✓/⚠ status table | `src/olav/cli/commands/init.py:75-194` | No interactive guidance; user must interpret the table |
| Bare `olav` launches the TUI directly, no state check | `src/olav/cli/main.py:2518-2526` | No detection of missing/incomplete `.olav/` before entering the agent |
| Config load returns empty dict if files missing, no error | `src/olav/core/config.py:110-206` | Silent degradation instead of fail-fast |
| First-run tips are a static, randomly-weighted pool | `src/olav/cli/tui_overlay.py:154-164` (`OLAV_TIPS`) | Tips assume operator familiarity (`/audit run <profile>`) regardless of actual workspace state |
| `api_key` empty → failure surfaces late, as a langchain error | `src/olav/core/llm.py:391-414` | Not fail-fast; cryptic for a first-time user |
| Natural-language CLI routing already exists | `src/olav/cli/main.py:181-294` | This part already matches the target philosophy — unknown tokens go straight to the agent as a query, no exact-syntax requirement |

**Key finding**: everything in `init.py` except the LLM `api_key` is already
idempotent and requires zero user input (directory creation, both DuckDBs,
workspace deploy, embedding model download, index warmup, registry rebuild,
**and** admin-user + token creation — the latter derives fully from `$USER`
env, `init.py:196-287`). Embedding is *already* zero-config by default
(`embedding.mode="local"`, `BAAI/bge-small-zh-v1.5`, auto-downloaded,
`defaults.py:47-62`, `embedder.py:81-149`) — no API key needed unless the
user opts into a cloud embedding provider. **The only genuinely irreducible
user input is the LLM `api_key`.** The gap is pure ritual (no auto-invoke
wiring), not a technical constraint.

### 1.2 Self-configuration (changing LLM/embedding provider via conversation)

| Capability | Exists? | Location |
|---|---|---|
| Natural-language "switch my embedding to X" that persists to `api.json` | **No** | — |
| `olav config evolve` | Exists, but unrelated — OpenConfig schema-mapping evolution, not LLM/embedding config | `src/olav/cli/commands/config_evolve.py` |
| `/model <name>` session override | Exists, but session-scoped only, 3 hardcoded options, does not persist | `src/olav/cli/commands/builtin.py:355-392` |
| Admin agent can write `api.json` | Yes, but via a generic full-file overwrite tool, not a field-level config tool | `src/olav/data/workspace/admin/editor/scripts/write_workspace_file.py:52-93` |
| Named field-level config tools (`update_llm_config`, `switch_provider`, etc.) | **No** | — |
| Validate-before-commit (test new config before writing it) | **No** — `test_connectivity()` exists but is only called once, during `olav init` | `src/olav/core/llm.py:400-414` |

**Risk if built naively**: letting an agent overwrite the whole `api.json` by
re-emitting JSON is exactly the failure mode CLAUDE.md already warns about
("small models lose the round-trip re-emitting JSON-encoded content as the
next tool's args" — Tool Architecture section). A config-mutation tool must
take structured (Pydantic) args, not a JSON blob to overwrite.

### 1.3 LLM / embedding fallback

| Behavior today | Location | Gap |
|---|---|---|
| Embedding fallback (API mode → local model) | `src/olav/core/llm.py:444-468`, gated by `config.fallback_enabled` | Exists, but static/one-directional, not "revert to last-known-good" |
| LLM fallback | **None** — `init_chat_model()` failure is caught, logged, and **re-raised** | `src/olav/core/llm.py:391-395` |
| Retry | HTTP-level only (`max_retries=5` for non-OpenAI-compatible endpoints) | `src/olav/core/llm.py:335` | Not a fallback, just a retry budget on the same endpoint |
| Last-known-good config snapshot / rollback | **None** — config loading is pure read-forward, no transaction/versioning | `src/olav/core/config.py:155-206` | A user-supplied config that breaks the LLM has no automatic recovery path |

## 2. Design principle

Do not build new architecture for this. OLAV already has the two mechanisms
this problem needs — they just aren't wired to the CLI/config layer yet:

- **Deterministic gate before LLM involvement** — matches the existing
  house rule "deterministic grader > LLM grader" (CLAUDE.md, dev_docs/97).
  Cold-start and config-validation checks must not depend on the LLM being
  configured correctly, since that is precisely the thing being validated.
- **Memory-driven steering instead of hardcoded prompts/tips** — the
  `*.guide.yaml` + AutoRecall mechanism (ADR-0015) that already personalizes
  sub-agent behavior should also drive the first-run tip/guidance surface,
  scoped by detected workspace state instead of served from a static random
  pool.

## 3. Proposed improvements (prioritized, not yet built)

### 3.1 Extract a shared, reusable config validator — **DONE 2026-07-01**
Promoted `test_connectivity()`-style logic into `LLMFactory.check_connectivity()`
/ `check_embedding_connectivity()` (`src/olav/core/llm.py`) — both return
`(ok, detail)` instead of a bare bool, so callers get an actionable reason,
not just pass/fail. `test_connectivity()` kept as a bool-returning wrapper
for backward compat (existing callers/tests monkeypatch it directly).

New `olav doctor` / `olav doctor --json` command (`src/olav/cli/commands/doctor.py`)
consumes both — checks scaffolding + LLM + embedding, zero LLM calls to
judge itself, each failure carries a `fix:` hint. Wired into
`_KNOWN_COMMANDS` + subparser + dispatch in `main.py`. Tests:
`tests/unit/test_doctor_command.py`, `tests/unit/test_llm_check_connectivity.py`.
Verified live against this repo (`olav doctor` correctly flagged a real
local-embedding failure — missing `libcudnn.so.9` — with an actionable hint).

**TUI follow-up 2026-07-03** (interface-coverage review found doctor was
CLI-only): added a `/doctor` slash command via the tui_overlay pattern —
registered next to `/workspace` in `_patch_workspace_command`, dispatched
by `_dispatch_doctor`, which runs the same `DoctorCommand` in a worker
thread (`asyncio.to_thread` — the probes are blocking network calls that
would otherwise freeze the Textual event loop and look like a hang) and
shows the report as a notification (20s timeout, warning severity when
unhealthy). `/doctor` added to the workspace-alias `reserved` set so a
workspace named "doctor" can't shadow it. This also partially closes
§7.2's TUI gap: a user hitting a mid-turn LLM failure can now diagnose
in place instead of exiting to a shell. Tests in `test_tui_overlay.py`
(registration, healthy/unhealthy severity, original handler not reached);
verified semi-live with real probes (LLM connected, embedding correctly
flagged as down, warning severity).

### 3.2 Collapse `olav init` into lazy first-run bootstrap — **DONE 2026-07-01**
Added `_ensure_bootstrapped()` in `src/olav/cli/main.py`, called on the
fallback path (bare `olav` / natural-language query — i.e. exactly the
"about to launch an agent" paths, not any explicit subcommand). On missing
`.olav/config/api.json` it silently runs `InitCommand().execute()` (already
fully idempotent). Reads/writes `api.json` directly rather than via
`ConfigLoader` (a process-wide singleton that would cache a stale "missing"
state if touched before the file exists). If `llm.api_key` is still empty:
prompts inline on a TTY and persists the answer; on a non-TTY (CI, piped)
prints an actionable message and exits rather than hanging or crashing
later inside langchain. `olav init` unchanged as an explicit command (CI
still calls it directly). Tests: `tests/unit/test_lazy_bootstrap.py`
(11 cases, including a real-entry-point test that drives `cli_main_impl()`
end-to-end to prove the wiring, per CLAUDE.md's Definition-of-Done rule).

### 3.3 State-aware first-run guidance — **DONE 2026-07-01 (revised scope)**
Original proposal (replace the static `OLAV_TIPS` pool with `*.guide.yaml`
entries injected via AutoRecall) was **corrected during design review**:
AutoRecall/guide injection is scoped per active agent/workspace, but
`OLAV_TIPS` and doctor's checks are agent-agnostic (they run before any
agent is guaranteed reachable, or apply regardless of which workspace is
active) — tying them to one agent's guide scope would silently stop working
the moment a user starts in a non-default agent (`--agent netops`, etc.).

Corrected design — three-layer pipeline, doctor never fixes anything itself:
1. **doctor (deterministic, zero-LLM)** — diagnoses. Only mode possible
   *before* the LLM is confirmed reachable (§3.2's hard gate is this: you
   cannot use an LLM to judge whether the LLM is broken).
2. **core (default agent) — redirect awareness** — once the LLM path is
   confirmed alive, non-blocking findings (e.g. embedding degraded) are
   handed to the user, not silently absorbed. §3.6 covers the "wrong agent
   for this request" half; this section covers the "first screen should
   say what's actually wrong" half.
3. **admin (or whichever agent has write tools) — remediates** — the only
   layer that should ever *act* on a finding, via §3.4's field-level config
   tool once built, conversationally, not via a hardcoded fix string.

**Part (a) — doctor's checks are now agent-callable, reusing the exact same
code, not a new duplicate script.** While scoping this, found that
`admin/ops`'s existing `check_health.py` script (already callable by the
`ops` sub-agent via `execute_skill_script`) had its own, *shallower*
LLM-config check — it verified a key was *present*, never that it actually
*worked*. This was exactly the doctor/admin duplication risk raised during
design review. Fixed by extending `_check_env()` in
`src/olav/data/workspace/admin/ops/scripts/check_health.py` to call the
same `LLMFactory.check_connectivity()` / `check_embedding_connectivity()`
§3.1 built for `olav doctor` (new `llm_connectivity: bool = True` param,
skippable for a fast config-shape-only pass). One shared validator, two
callable surfaces (CLI for humans/scripts, script-tool for agents) — zero
duplicated logic. A user can now ask the `ops` sub-agent "why isn't X
working?" and get a live answer instead of only "is a key present?".
Tests: `tests/unit/test_check_health_llm_connectivity.py`; verified live
(the script correctly flagged the same real embedding failure `olav doctor`
found, from one shared source of truth).

**Part (b) — non-blocking findings surface once, on the actual first run.**
Added `_check_first_run_health()` in `main.py`, called from
`_ensure_bootstrapped()` only when bootstrap did fresh work (not on every
launch — a live probe on every single startup was rejected as an
unacceptable latency tax on returning users). It calls
`LLMFactory.check_embedding_connectivity()` (the LLM path itself is about
to be exercised by the user's first message, so it isn't re-probed here)
and, on failure, calls `tui_overlay.set_first_run_finding(msg)`. The
welcome-footer patch (`_patch_welcome_footer()` in `tui_overlay.py`) now
checks `consume_first_run_finding()` before falling back to
`random.choice(OLAV_TIPS)` — a real finding wins, and is consumed once so
it doesn't repeat on later restarts/workspace swaps within the same
session. Tests: `tests/unit/test_lazy_bootstrap.py` (health-check
call/no-call cases), `tests/unit/test_tui_overlay.py` (finding beats random
tip, consumed exactly once). Verified live against this repo's real broken
embedding.

### 3.4 Field-level self-configuration tool — **DONE 2026-07-02**
Added `update_llm_config(api_key, model, model_provider, base_url)` /
`update_embedding_config(mode, api_key, model)` /
`rollback_config()` as `@tool`s in
`src/olav/data/workspace/admin/editor/tools/update_config.py` (plain
scalar args, not a JSON blob — the risk flagged in §1.2). Landed on
`admin/editor` specifically (its existing "hands" tool,
`write_workspace_file`, is a raw full-file overwrite with zero
validation — exactly the wrong tool for this) as a sub-agent-scoped
`tools/` directory, registered in `editor/SKILL.md`'s `tools:` list (the
authoritative filter `_load_tools_from_skill` reads — a file existing in
`tools/` without a matching frontmatter entry never loads).

Extended §3.1's validators rather than writing new ones: `get_chat_model`
gained an `api_key` override (already had `model`/`base_url`/
`model_provider`, `api_key` was the missing one); `get_embeddings` gained
`mode`/`api_key`/`model` overrides plus a `strict` flag that skips the
API→local embedding fallback (needed so a bad *candidate* key surfaces as
a real failure instead of being silently masked by the production
fallback behaviour). `check_connectivity(overrides=...)` and
`check_embedding_connectivity(overrides=..., strict=...)` forward these
through — same two functions `olav doctor` and `check_health` already
call, now also the validate-before-commit gate for a config that isn't
committed yet. Commit path: field-level merge into `api.json` (only the
changed keys — every other key, including ones the tool doesn't know
about, is preserved verbatim) and an immediate `ConfigLoader._loaded =
False` cache-bust so the change is live on the *next* LLM/embedding call
in the same session, not after a restart.

Tests: `tests/unit/test_update_config_tools.py`,
`tests/unit/test_llm_check_connectivity.py` (override plumbing). Verified
live against this repo with a real API call: an intentionally invalid
candidate key was rejected with the real 401 from the provider surfaced
verbatim, and `api.json` was byte-for-byte unchanged.

### 3.5 Last-known-good snapshot + explicit rollback — **DONE 2026-07-02
(scope narrowed from the original proposal)**
Snapshot half built as designed: `src/olav/core/config_snapshot.py`'s
`snapshot_api_json()` copies `api.json` → `api.json.lastgood` right before
every successful §3.4 commit (captures the config that was working a
moment ago, not the one replacing it).

**The "runtime fallback" half was deliberately *not* built as originally
scoped** — the plan called for a catch-and-revert branch inside
`llm.py`'s `get_chat_model()` exception handler (the hot path called on
essentially every agent turn) that would automatically detect repeated
failures and silently swap in the last-known-good config. Rejected during
implementation for being the wrong trade-off: an automatic revert deep in
the hottest call path is hard to test safely, hard to reason about
("repeated" over what window? per-process? per-session?), and — despite
the doc's own "must be a reported action, not a hidden one" requirement —
genuinely difficult to notify the user about cleanly from that layer, since
`get_chat_model()` has no uniform path back to whatever UI surface (TUI
turn, single CLI query, agent-internal call) is active at the time.

Built instead: `rollback_config()` (§3.4, same file) — an explicit,
agent-callable undo of the single most recent `update_*_config` change.
This satisfies the actual user-facing need ("I changed my LLM config and
it broke, undo it") without the automatic-revert risk, and is
unambiguous by construction — it only ever runs when someone (user or
agent, in conversation) asks for it, so there is no "did it silently
revert or not" question to answer. Trade-off accepted: this does not
protect against a config that passes validation at commit-time but fails
later (quota exhaustion, model deprecation) — that class of failure still
surfaces as a normal LLM error, same as before this work, with the fix
now one `rollback_config()` call away instead of a manual `api.json` edit.

### 3.6 Core's cross-domain redirect awareness — **DONE 2026-07-01**
Surfaced while scoping §3.3: "which agent handles config/health-check
requests" turned out to be a real, separate gap from doctor/self-config.
`admin` (`.olav/workspace/admin/`) already owns config writes and
health/log diagnostics — but `core`, the *default* agent a bare `olav`
lands in, had **zero runtime awareness** that `admin` (or `audit` /
`devops` / `netops`) exist, so it could neither redirect a misplaced
request nor avoid attempting something outside its own tools.

Two compounding findings from `src/olav/core/router.py` and
`src/olav/data/workspace/core/SKILL.md`:
- A full semantic + keyword + LLM-fallback cross-workspace router
  (`route_query()`) already exists but is **dead code** — never called
  from the message-dispatch path. Reviving it to *auto*-switch agents is a
  bigger, separate architectural decision (it would change the current
  "user manually controls which top-level agent is active" model via
  `/workspace <name>`) — out of scope here.
- core's own `SKILL.md` already listed sibling agents in an "Available
  agents" section, but the content was wrapped in
  `<!-- BEGIN_AGENT_ROUTING --> ... <!-- END_AGENT_ROUTING -->` HTML
  comments — invisible to the LLM's actual system prompt. This is the same
  "shipped but unreachable" failure class CLAUDE.md's Definition-of-Done
  section calls out for other features (trace-learn loop, `/trace-review`).
  Those markers were consumed by `refresh.py:_update_main_agent_routing`,
  but it targeted `core/prompts/system.md` — a file that does not exist in
  the current (post-SKILL.md-migration) architecture, so the function
  always no-op'd. **Follow-up 2026-07-02**: removed the function, its two
  marker constants, and `_ROUTING_TABLE_SKIP` entirely (true dead code,
  unlike `route_query()` — see below), plus `refresh_workspace()`'s
  now-meaningless `routing_updated`/note plumbing. This surfaced
  `tests/unit/test_refresh_command.py` as sitting in
  `tests/unit/conftest.py`'s `collect_ignore` list (deferred stale-test
  debt, unrelated mechanism — see box below) with 9/24 failing tests, 4 of
  which were for the now-deleted function. Fixed the other 5 (two real
  staleness bugs: a `_scan_agents` test asserted the *opposite* of the
  correct post-ADR-0008 SKILL.md-preference behavior, and every
  `_write_platform_md` test still asserted the pre-rename `PLATFORM.md`
  filename instead of the current `olav.md`) and removed the file from
  `collect_ignore` — 20/20 passing, back in the regular suite.

  **Aside — a scare that turned out to be nothing**: investigating why
  these 9 failures never showed up in this session's "full suite" runs
  led to briefly suspecting a systemic pytest bug (17 files silently
  missing from `pytest tests/unit` directory-recursive collection vs.
  file-list collection — 333 tests, ~17% of the suite). Root cause:
  `tests/unit/conftest.py`'s `collect_ignore` list, working exactly as
  documented (each entry dated with a reason) — not a hidden CI blind
  spot. One genuinely stale entry found and removed in passing:
  `test_threads_search.py`, a file that no longer exists on disk.

Fix (smaller, lower-risk than reviving the router): replaced the hidden
block with a live "## Cross-domain redirects" section — same pattern
`admin`'s `SKILL.md` already uses successfully for its own out-of-scope
requests — telling core to say so plainly and point the user at
`/workspace <name>` (or `olav --agent <name>`) rather than trying to
handle it itself or delegating to `olav_delegate` (which only reaches
core's own sub-agents, not sibling top-level agents). Edited in both
on-disk copies — the tracked source (`src/olav/data/workspace/core/SKILL.md`)
and the untracked runtime mirror (`.olav/workspace/core/SKILL.md`, normally
`git:ignore`/regenerated by `olav init` per CLAUDE.md's workspace layout) —
kept in sync here so the change is live in this dev environment without a
fresh `olav init`. Verified `olav refresh` does not clobber the edit (it only
touches the now-dead `system.md` routing path) and
`test_workspace_drift_gate.py` / `test_installer_source_has_modified_tools.py`
still pass.

### 3.7 General usage-tip KB via `*.guide.yaml` — **DONE 2026-07-02, deliberately narrow**
Follow-up question during review: should §3.6's redirect logic move from
static SKILL.md text into `*.guide.yaml` + AutoRecall (LanceDB), both to
shrink SKILL.md and to get memory-driven steering "for free"? **Decided
no for the redirect logic specifically** — AutoRecall is semantic-
retrieval-triggered, not guaranteed-present-every-turn, and cross-domain
routing is exactly the case where a miss is expensive (a confused
first-time user gets no redirect at all instead of a slightly-imprecise
one). The §3.6 static block stays as is.

What *did* move to guide.yaml: two new, narrower usage-tip guides that
extend (not replace) §3.6 — `scheduled_recurring_checks.guide.yaml` and
`audit_profile_usage.guide.yaml` under `core/references/` (same
convention as the existing `syslog_search_during_troubleshooting.guide.yaml`).
These cover "how do I automate/schedule X" and "how do I run a health
check profile" — questions where core needs to explain *both* which
agent owns it *and* the actual command syntax (`manage_cron(...)`,
`/audit run <profile>`), which is too much detail to keep duplicating in
the always-on SKILL.md block. A retrieval miss here just means a less
detailed answer, not a stuck user — an acceptable trade for the two
guides, not for the routing table itself. Verified via
`discover_guides()` (44 guides total in the workspace, both new intents
present and parse correctly); full LanceDB priming untestable in this dev
environment (local embedding backend down — the same finding `olav
doctor`/§3.1 already surfaces) but the loading pipeline itself is
pre-existing and already covered by `tests/unit/test_guide_kb.py`.

### 3.8 E2E behavioural coverage for §3.4/§3.5 — **DONE 2026-07-02, surfaced a real pre-existing bug**
Added `TestAdminUpdateLLMConfigRejection` / `TestAdminRollbackConfig` to
`tests/e2e/test_admin_e2e.py` (LLM-gated, `ADMIN_E2E_ENABLED=1`, matching
the file's existing pattern) plus two always-on structural checks
(`update_config.py` exists, `editor/SKILL.md` declares the three tool
names). Running this for real (not just direct `@tool.invoke()`, but a
genuine `olav --agent admin "..."` conversation) immediately surfaced a
significant **pre-existing, unrelated bug**: `admin/SKILL.md`'s routing
table still said `task("developer", req)` everywhere — "developer" was
renamed to "editor" in rev ~282 and the top-level router was never
updated. `installer` (a real, separate sub-agent) wasn't routed to at
all either. Result: any admin request that should reach `editor`
(including every self-config request) got no matching route, and the
model fell back to raw filesystem tools (`ls`/`glob`/`grep` hunting for
where API keys might live) until it hit the 90s test timeout — a
textbook "shipped but unreachable" case, just not one from this week's
work. Fixed `admin/SKILL.md`'s routing rules and Specialists list
(`developer`→`editor`, added `installer` as its own target, added an
explicit self-config routing bullet), synced to both on-disk copies.
Re-running confirmed the agent now says "routing to the **editor**
subagent" and calls `update_llm_config` directly.

**Safety design for these tests**: they must never leave the shared
dev-environment `.olav/config/api.json` mutated as a side effect of a
test run. Two layers: (1) narrow, single-call prompts ("call this tool
exactly once with this exact value, do not retry") rather than
open-ended ones — an earlier open-ended prompt ("update my key and tell
me if it worked") led the agent to retry with *other* field values after
the first rejection, one of which happened to be a legitimately valid
candidate (setting `model` to its own already-current value) and
committed for real; (2) an autouse `_protect_api_json` fixture that
snapshots both `api.json` and any `.lastgood` file before the LLM call
and hard-fails (after restoring the original bytes) if either changed —
independent of what the agent actually did. This fired once during
iteration (the tightened prompt still didn't fully eliminate an extra
tool call) and correctly restored the file with zero lasting effect —
consistent with this repo's own house position that a single LLM
behavioural run isn't grounds for treating variance as a regression
(CLAUDE.md, "Agent-behaviour issues need N≥3 runs to call closed"). The
tests are also already LLM-gated/opt-in, so this variance cannot affect
the default `pytest tests/unit tests/governance` merge-gate run.

## 4. Non-goals / explicit scope boundaries

- Not proposing to remove the explicit `olav init` / `olav config` commands
  — they remain for CI and scripted/advanced use.
  the CI harness already invokes them (`.gitea/workflows/ci.yml`).
- Not proposing an LLM-based judge for config validity — §3.1 must stay a
  deterministic connectivity/shape check, consistent with the house
  preference for deterministic graders.
- Not proposing to change `embedding.mode="local"` as the default — it
  already satisfies the "zero-config" bar; only cloud-embedding opt-in needs
  a credential.

### 7.1 Empty-state guidance — "installed, now what?" — **DONE 2026-07-02**
The next break in the exact chain §3.2/§3.3 completed: bootstrap passes,
LLM works, TUI opens — and the workspace has zero devices/snapshots.
"What devices are on my network?" returns empty results with no hint that
the real problem is "no data imported yet, step one is X". ADR-0009's
"empty collection arg = discovery" covers per-tool emptiness; **nothing
covered whole-domain emptiness**.

Implemented exactly per the §7.6 boundary design — platform owns the slot,
extension owns the check:

- **Platform** (`main.py:_run_extension_first_run_checks`): discovers the
  new `olav.first_run_checks` entry-point group and queues each provider's
  finding via `tui_overlay.add_first_run_finding`. Called from
  `_ensure_bootstrapped` on **every** agent launch — unlike §3.3's
  embedding probe (fresh-bootstrap-only), because the contract requires
  checks be deterministic/local (file stat + read-only DuckDB count, no
  LLM/network), cheap enough for every start, and the empty-data state
  persists well past first run. Never raises; a broken provider is
  skipped, the rest still run.
- **tui_overlay**: finding slot generalised from a single value to a list
  (`add_first_run_finding` appends, `set_first_run_finding` keeps its
  replace/clear semantics for §3.3, `consume_first_run_finding` joins +
  clears) so §3.3's embedding finding and §7.1 findings coexist on the
  welcome screen.
- **Extension** (`olav-netops/src/olav_netops/first_run.py:check_netops_data`,
  registered in `olav-netops/pyproject.toml`): three-state ladder —
  workspace not deployed → silent; DB or `netops.devices` table missing →
  "run /netops_init"; table present but zero rows → "import a snapshot or
  collect from devices"; data present or state undeterminable → silent.
  Distinguishes `duckdb.CatalogException` (init never ran — that IS the
  finding) from other errors (locked DB etc. — stay silent).

Tests: `tests/unit/test_first_run_checks.py` (platform discovery, broken-
provider isolation, coexistence with §3.3, every-launch wiring),
`tests/unit/test_netops_first_run_check.py` (all six ladder states).
Verified live: this repo's real DB (348 devices) correctly returns silent-
healthy through the full entry-point discovery path.

Two side-findings fixed during implementation: (1) the dev venv had a
stale olav-netops 0.20.0 install while its pyproject said 0.21.0 — the
entry-point-refreshing reinstall corrected the parity drift; (2)
`test_tui_overlay.py`'s `_fresh_overlay` fixture left the parent-package
attribute `olav.cli.tui_overlay` pointing at its re-imported module while
monkeypatch teardown restored the original into `sys.modules` — from then
on `import a.b as x` (resolves via package attr) and `from a.b import f`
(resolves via sys.modules) yielded **two different module objects with
two copies of module-level state**, an order-dependent poison that §7.1's
new list-state made visible. Fixed in the fixture (a no-op
`monkeypatch.setattr` before the delete records the attr for teardown
restoration); verified in both test orderings.

Sample-data offering ("try the ask-answer loop before connecting real
devices") deferred — the finding text points at import/collect paths;
bundling demo data is a packaging decision (see the 5.9GB bundle
constraint in dev_docs' e2e data strategy).

### 7.2 Runtime failure → actionable recovery hint — **DONE 2026-07-02**
The gap §3.5 deliberately left: mid-session LLM failure (quota, model
retired) still surfaced as a raw provider exception. doctor and
`rollback_config` existed but nothing connected the *moment of failure*
to them.

Implemented as `_llm_failure_hint(e)` (`main.py`) + one call in
`cli_main_impl`'s outer exception handler: classifies the error
(auth/401 → "key invalid or expired"; 429/402/quota → "rate-limiting or
out of quota"; APIConnectionError/APITimeoutError → "endpoint
unreachable"; other API-class errors → generic) and appends one line
naming the next step — `olav doctor` to diagnose, and the admin rollback
phrase if it started after a config change. The gate is deliberately
conservative (openai-client error class names + unambiguous HTTP
auth/quota signals, not generic words like "connection") because the
outer handler catches *everything* the CLI does — a DuckDB or filesystem
error must not receive LLM advice. The pre-existing `_is_api_error`
traceback-suppression check was folded into the same classification
(hint present ⇒ suppress traceback), widening suppression slightly but
keeping one classification instead of two drifting ones.

Tests: `tests/unit/test_llm_failure_hint.py` (classification ladder,
non-API errors get None, wiring through a real `cli_main_impl` run with
a captured console). Verified live: `OLAV_LLM_API_KEY=sk-broken olav
"hello"` → real provider 401 → error + hint, no traceback noise.
Behavioural e2e added 2026-07-03: `test_admin_e2e.py::TestRuntimeFailureHint`
(LLM-gated) runs that exact broken-key query as a subprocess and asserts
the hint (doctor + rollback phrase) appears with no traceback — 3/3 live.

Deliberately NOT covered: failures inside an interactive TUI turn — that
loop is owned by deepagents-code, not our catch site; revisit only if
users report raw errors there too. Mitigated 2026-07-03 by the in-TUI
`/doctor` command (§3.1 TUI follow-up): the user seeing a raw mid-turn
error can now diagnose without leaving the TUI, even though the error
text itself isn't decorated there.

### 7.3 Returning-user session continuity — **DONE 2026-07-03**
`olav sessions` listed sessions; L1/L2 capture existed — but a returning
user got an amnesiac greeting.

Implemented as `_check_returning_user_context()` (`main.py`, called from
`_ensure_bootstrapped` on every launch) + a new `set_welcome_context` /
`consume_welcome_context` slot in `tui_overlay`. **Deterministic and
zero-LLM by design**: the "context" is the user's most recent recorded
query verbatim (`audit_messages` ⋈ `audit_runs` for user scoping, one
read-only indexed query) with a humanized age — no LLM summarization at
startup (§2's deterministic-gate principle; the sessions table's `title`
column was considered but is unpopulated for CLI sessions, while
`audit_messages` is always written). Silent when: no audit DB (true
first run), last activity > 7 days (stale context is noise, not
orientation), another user's history, or any error. Rendered as its own
dim line on the welcome screen — deliberately NOT through the ⚠ findings
prefix (orientation is not a warning) — and coexists with a §3.3/§7.1
finding below it; consumed once so workspace swaps within a session
don't re-show it.

Tests: `tests/unit/test_returning_user_context.py` (recency ladder, user
scoping, truncation, corrupt-DB silence, bootstrap wiring),
`test_tui_overlay.py` (real footer render: context + finding coexist,
both consumed exactly once). Verified live against this repo's real
audit history: produced "Welcome back — last time (21h ago):
“hello, quick test”" — the actual query from §7.2's verification run.

### 7.4 Generalized undo for agent write-actions — **DONE 2026-07-03**
`rollback_config` covered config only. Cron additions and workspace file
writes had no "undo that".

Implemented as a platform undo journal + per-script recording + one
agent-callable revert script, keeping §3.5's explicit-undo philosophy
(never automatic, only on request):

- **`src/olav/core/undo_journal.py`** — one JSON entry per action under
  `.olav/run/undo/` (runtime dir, never committed), capped at 20.
  `record_action(kind, description, data)` / `list_actions()` /
  `undo_last()` with kind handlers: `file_write` (restore prior bytes,
  or delete if the file didn't exist), `cron_add` (remove), `cron_update`
  (restore previous schedule), `cron_remove` (re-add from stored spec).
  Single-step most-recent-first — call again to undo the action before.
  Failed reverts keep the entry (retryable); file restores re-validate
  containment inside the project root (defense in depth on top of
  write_workspace_file's own check).
- **`write_workspace_file.py`** (editor): captures prior content before
  the write, journals after success; result carries `undo_recorded` so
  the agent never claims undo coverage that doesn't exist (journal
  failure soft-fails the recording, never the write).
- **`manage_cron.py`** (ops): add/update/remove journal the matching kind
  with enough data to revert (update stores the previous schedule,
  remove stores the full job spec).
- **`undo_last_action.py`** (new editor script, name-form registered in
  editor SKILL.md; `list_only=True` previews): what the sub-agent calls.
  Routing added in admin SKILL.md ("undo that / revert the last change /
  撤销" → editor) and editor's decision tree, explicitly separated from
  `rollback_config` (config has its own validated path).

Tests: `tests/unit/test_undo_journal.py` (11 — round-trip, cap pruning,
all four kind reverts via fake CronTab, outside-root refusal, empty/
unknown-kind/failed-revert handling), `tests/unit/
test_write_action_undo_wiring.py` (5 — the deployed runtime scripts
journal and revert end-to-end), structural e2e in `test_admin_e2e.py`.
Existing `test_manage_cron_tool.py` gained an autouse journal-isolation
fixture (its calls would otherwise write entries into the repo's real
`.olav/run/undo/`) and one exact-dict assertion updated for the new
`undo_recorded` field. Verified live via subprocess exactly as
`execute_skill_script` invokes it: write → journaled → undo removed the
file and consumed the entry, zero residue.

Behavioural e2e added 2026-07-03 (follow-up review caught that only
structural e2e existed): `test_admin_e2e.py::TestAdminUndoLastAction`
(LLM-gated) seeds one synthetic journal entry pointing at a scratch file
it owns, asks the agent "Undo my last file change" in a real
conversation, and asserts the file content actually reverted
(MODIFIED→ORIGINAL) — proving the full admin-router → editor →
`undo_last_action` → journal-revert chain, not just the script in
isolation. An autouse `_protect_undo_journal` fixture snapshots/restores
the whole journal dir so the test can neither consume a real user's
pending undo entry nor leave its seed behind. One fixture-scope trap hit
during authoring: the class caches the agent run but the autouse fixture
tears down per-test, deleting the scratch file before later tests read
it — the file state is therefore snapshotted into a class attribute
immediately after the run and asserted from there. 4/4 live; zero
residue confirmed after the run.

Deliberately NOT covered: service deploys (docker compose up has no
clean single-file revert — needs its own design), and multi-step
history/selective undo (same one-slot-at-a-time semantics as
`rollback_config`; revisit if real usage demands a history).

### 7.6 Boundary analysis: netops init stays separate (decided, not new work)
Question raised while scoping §7.1: platform (`olav`) and netops
(`olav-netops`) are separate delivery units — should netops init be its
own step? **It already is, and the current architecture is correct**:

- `olav init` / §3.2 lazy bootstrap — platform scaffolding only. Already
  contains zero netops semantics.
- `olav skill install olav-netops` — deploys the netops workspace.
- `/netops_init` — netops-owned data init (DuckDB tables, seed
  templates), registered via the `olav.slash_commands` entry point
  (`olav-netops/pyproject.toml`); tables likewise auto-register via
  `olav.ingest_tables`. Both are the allowed reverse-coupling form
  (entry-point discovery), per the repo boundary rules.

So the answer to "should netops init be separate" is yes — **do not fold
`/netops_init` into the §3.2 platform bootstrap**, which would hardcode
network-domain semantics into core (explicitly forbidden). What §7.1
needs instead is a **first-run contract**: a new entry-point group (e.g.
`olav.first_run_checks`) where an installed extension registers a
deterministic "am I initialized? if not, what should the user do first?"
provider. Platform bootstrap discovers and runs whatever is registered,
surfacing results through the existing §3.3 finding slot. Netops owns the
check logic and the wording ("no devices imported — run /netops_init or
import a snapshot"); platform owns only discovery + display. An
uninstalled or not-yet-initialized extension then degrades to silence,
not to a platform-side special case.
