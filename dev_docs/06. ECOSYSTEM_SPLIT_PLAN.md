## 1. 核心设计：Workspace 声明式创建

### 1.1 基本原则

> **Workspace 不是用户创建的，是 skill 包声明的。**
>
> 用户只做一件事：`olav skill install <url>`。
> Workspace 在哪、叫什么、包含什么 agent —— 全由 skill 包的 `workspace.yaml` 声明。

类比：
- Docker Compose：你不手动创建 network，`docker-compose.yml` 声明它
- Kubernetes：你不手动建 namespace，`Deployment.yaml` 声明它
- Olav：你不手动建 workspace，`workspace.yaml` 声明它

### 1.2 Workspace 声明文件

每个 skill git repo 的根目录放一个 `workspace.yaml`：

```yaml
# olav-netops-skills/workspace.yaml
kind: Workspace
name: netops
version: "1.0.0"
description: "Network Operations — device management, topology, fault diagnosis"
source: https://github.com/org/olav-netops-skills

set_active: true

# ★ 强耦合依赖：skill 包必须配合 pip 包使用（见 §11.1）
requires:
  packages:
    - olav-netops>=0.12.0       # entry points: ingest_tables, domain_prompts, slash_commands
  binaries:
    - ssh
  env_hint:
    - NORNIR_HOSTS_YAML

# 域数据库 schema 命名空间（见 §11.2）
db_schema: netops

init_command: "olav netops init"

agents:
  quick:
    description: "Fast queries — SQL, CLI, KB search"
    tools:
      - execute_sql
      - execute_cli
      - search_commands
      - search_knowledge
      - web_search
    static_context:
      - references/SCHEMA_REFERENCE.md

  ops:
    description: "Deep fault analysis"
    subagents:
      - diff
      - probe
      - topology
      - sim
      - lab

  config:
    description: "Domain data maintenance"
    subagents:
      - sync
      - learner
      - schema
```

## 2. `olav skill install` 完整语义

### 2.1 标准安装（workspace 来自声明）

```bash
olav skill install https://github.com/org/olav-netops-skills
```

流程：
1. `git clone` 到 `.olav/skills-cache/netops-skills/`
2. 读取根目录 `workspace.yaml`，解析 `name: netops`
3. **检查 pip 依赖**：`olav-netops>=0.12.0` 是否已安装
   - 若缺失：`pip install olav-netops>=0.12.0`（自动安装）
   - 或提示用户：`需要先运行 pip install olav-netops>=0.12.0`
4. 检查二进制依赖：`ssh` 是否存在
5. 创建 `.olav/workspace/netops/`
6. 从 `workspace.yaml` 的 `agents` 生成 AGENT.md / SKILL.md / MANIFEST.yaml
7. 复制 tools、references、prompts 等文件
8. 写入锁文件 `.olav/workspace/netops/workspace.yaml`
9. 若 `set_active: true`，更新 settings.json
10. 输出：`已安装 netops workspace (3 agents, 12 skills)。运行 olav netops init 初始化数据。`

### 2.2 指定 workspace 名（重命名）

```bash
olav skill install https://github.com/org/olav-netops-skills --workspace mynetops
```

### 2.3 向已有 workspace 追加 skills（merge）

```bash
olav skill install https://github.com/org/extra-probes --merge-into netops
```

`extra-probes` 声明 `kind: SkillPack`，安装时追加到目标 workspace：
```yaml
kind: SkillPack
target_workspace: netops
target_agent: ops
```

### 2.4 安装到新建 workspace（无声明文件的裸 skill）

```bash
olav skill install ./my-local-skill --workspace myworkspace --agent ops
```

现有 `.olav/workspace/quick/`、`.olav/workspace/ops/` 平铺结构，

```python
# src/olav/core/workspace.py（新建，唯一路径解析入口）

def resolve_workspace_path(workspace: str | None, agent: str) -> Path:
    """统一 workspace 路径解析 — 全局唯一入口。

    所有代码通过此函数获取 workspace 路径，不直接拼接字符串。
    """
    base = Path(".olav/workspace")
    active = workspace or get_active_workspace()

    # 新结构：嵌套

    # 旧结构：平铺（向后兼容）
    flat = base / agent / "AGENT.md"
    if flat.exists():
        return flat.parent

    raise FileNotFoundError(
        f"No AGENT.md for workspace={active}, agent={agent}"
    )

def get_active_workspace() -> str:
    """从 settings.json 读取 active_workspace，默认 'core'。"""
    ...
```

> **关键：** 代码中现有 27 处 `.olav/workspace/` 硬编码路径必须全部改为调用此函数。
> 不在 27 处各自加 fallback，只在这一处统一处理。

## 5. `core` workspace：永远存在，不可卸载

```
.olav/workspace/
└── core/
    ├── workspace.yaml             ← kind: BuiltinWorkspace（不可删除标记）
    └── SKILL.md                   ← 平台工具
```

### 5.1 Core Skills 全局挂载机制

Core skills 对所有 workspace 的所有 agent 可见，无需在每个 AGENT.md 里重复声明。

**实现方式：** `OLAVAgent.__init__()` 初始化时自动加载 core workspace 的工具：

```python
# src/olav/agents/agent.py（修改 _load_orchestrator_tools）

def _load_orchestrator_tools(self, olav_config: dict) -> list:
    tools = []

    # ① 始终加载 core workspace 工具（全局可用）
    core_skill = self.olav_base_path / "workspace" / "core" / "SKILL.md"
    if core_skill.exists():
        tools.extend(self._load_tools_from_skill(core_skill))

    # ② 加载当前 agent 的 workspace 工具
    skill_path = self._agent_dir / "SKILL.md"
    if skill_path.exists():
        tools.extend(self._load_tools_from_skill(skill_path))

    return tools
```

这样任何 workspace 的任何 agent 都能调用 `recall_memory`、`execute_sql`、`skill_builder` 等 core tools。

## 11. 代码审计发现的 6 个设计风险（已解决）

### 11.1 Entry Points 与 Skill 分离的强耦合

**问题：** `olav-netops` 通过 5 个 entry point group 注册 15 个入口（ingest_tables、
domain_prompts、slash_commands、reload_hooks、config_commands）。平台启动时通过
`importlib.metadata.entry_points()` 加载。如果用户只装了 `olav-netops-skills`（git skill）
没装 `olav-netops`（pip），这些全部失效。

**解决方案：**
1. `workspace.yaml` 的 `requires.packages` 声明 `olav-netops>=0.12.0`
2. `olav skill install` 检查依赖，缺 pip 包时自动提示或自动安装
3. 安装顺序强制：先 `pip install olav-netops`，后 `olav skill install`
4. 文档明确：**skill 包 + pip 包 = 完整域能力，缺一不可**

### 11.2 数据库隔离策略

**现状：** 4 个独立数据库文件，职责已分离：

| 数据库 | 用途 | 写入者 | 域间冲突风险 |
|--------|------|--------|-------------|
| `main.duckdb` | 域业务数据 | ingest_manager, tools | ⚠️ 高 |
| `audit.duckdb` | 审计日志 | audit_recorder (append-only) | ✅ 无 |
| `memory.lance` | 语义记忆 | memory middleware | ✅ 低（row-level scope） |
| `olav_registry.duckdb` | API schema 注册 | api_registry | ✅ 已有 api_name 隔离 |

**真正的风险不是"多域冲突"，而是"agent 越权写入"：**

`ingest_base.py` 已用 `CREATE SCHEMA netops` 做了命名空间隔离（`netops.devices`），
表名冲突问题已解决。但 `execute_sql` 工具以 **read-write** 模式打开 `domain.duckdb`，
且不过滤 SQL 类型——agent 生成的 SQL 可以执行 `DROP TABLE`、`DELETE FROM`、`UPDATE`，
破坏任何域的数据。

#### 三层防御方案

**Layer 1：Schema 命名空间隔离（已有，强化为规范）**

```sql
CREATE SCHEMA IF NOT EXISTS netops;   -- 网络运维域
CREATE SCHEMA IF NOT EXISTS itsm;     -- ITSM 域
-- 跨域查询自然可用：
SELECT * FROM netops.devices d JOIN itsm.tickets t ON d.hostname = t.device_name
```

- `workspace.yaml` 声明 `db_schema: netops`
- `ingest_base.py` 已实现 `qualified_name = f"{schema_name}.{table_name}"`
- 不同域的表绝不同名冲突

**Layer 2：工具级读写权限控制（新增，最关键）**

```python
# execute_sql 工具默认以 read_only 模式打开数据库
# 写操作必须通过 approval gate

def db_query(sql: str, params: list | None = None) -> list[dict]:
    # SQL 类型检测
    sql_type = _classify_sql(sql)  # SELECT / INSERT / UPDATE / DELETE / DDL / OTHER

    if sql_type == "SELECT":
        # 只读查询 — read_only=True，安全
        with duckdb.connect(str(MAIN_DB_PATH), read_only=True) as conn:
            return _execute(conn, sql, params)

    # 写操作 — 经过 approval gate
    from olav.platform.safety.approval import check_approval
    approval = check_approval(sql, device="database")
    if approval.requires_approval:
        return [{"status": "requires_approval", "sql": sql, "reason": approval.reason}]

    with duckdb.connect(str(MAIN_DB_PATH)) as conn:
        return _execute(conn, sql, params)


def _classify_sql(sql: str) -> str:
    """分类 SQL 语句类型。"""
    normalized = sql.strip().upper()
    if normalized.startswith("SELECT") or normalized.startswith("WITH"):
        return "SELECT"
    if normalized.startswith(("INSERT", "UPSERT", "COPY")):
        return "INSERT"
    if normalized.startswith(("UPDATE", "DELETE", "TRUNCATE")):
        return "MUTATE"
    if normalized.startswith(("CREATE", "DROP", "ALTER")):
        return "DDL"
    return "OTHER"
```

**Layer 3：域级写入限制（可选，企业级）**

在 `olav-ent` 中实现更细粒度的控制：

```python
# 企业版：根据当前 workspace 限制可写入的 schema
# netops workspace 的 agent 只能写 netops.* 表
# 不能写 itsm.* 或 main.* 表
```

**不做文件级隔离的理由：**

1. **跨域查询是核心价值**——"哪些 BGP 故障对应了 ITSM P1 工单？" 需要 JOIN 两个 schema
2. DuckDB 单文件架构的并发锁已经是瓶颈，多文件只会更糟
3. `audit.duckdb` 和 `memory.lance` 已经物理分离（写入模式不同）
4. 业务数据通过 schema 命名空间 + 工具级权限控制足够安全

#### 域注册规范

每个域包通过 `workspace.yaml` 声明自己的 db_schema：

```yaml
# workspace.yaml
db_schema: netops     # 声明该域的 DuckDB schema 名称
```

`ingest_base.py` 的 `BaseIngestTable` 子类必须设置 `schema_name`：

```python
class ParsedOutputsTable(BaseIngestTable):
    schema_name = "netops"          # 强制要求，不能是 "main"
    table_name  = "parsed_outputs"
```

`olav workspace validate` 检查所有表是否使用了正确的 schema 前缀。

### 11.3 workspace.yaml 与 MANIFEST.yaml 共存关系

**问题：** 现有系统用 `MANIFEST.yaml`（agent_registry.py 处理），新设计引入
`workspace.yaml`。两者如何共存？

**解决方案：** 两者是不同层级的声明，互不替代：

| 文件 | 层级 | 职责 | 谁读取 |
|------|------|------|--------|
| `workspace.yaml` | workspace | 整个域的声明（agents、依赖、来源） | `olav skill install` / `olav workspace` |
| `MANIFEST.yaml` | agent | 单个 agent 的路由关键词、依赖检查 | `agent_registry.discover_agents()` |

`olav skill install` 在创建 agent 目录时同时生成 `AGENT.md` 和 `MANIFEST.yaml`。

### 11.4 Checkpoint Workspace 隔离

**问题：** checkpoint 路径 `~/.olav/checkpoints/{user}/{agent_id}/`。
两个 workspace 都有 `quick` agent 时，checkpoint 文件冲突。

**解决方案：** checkpoint 路径加入 workspace 维度：

```python
# src/olav/core/checkpointer.py（修改）
def create_checkpointer(agent_id: str, username: str, workspace: str = "core"):
    checkpoint_dir = (
        Path.home() / ".olav" / "checkpoints" / username / workspace / agent_id
    )
    ...
```

路径变为：`~/.olav/checkpoints/{user}/{workspace}/{agent_id}/checkpoints.duckdb`

### 11.5 Router 硬编码 Agent 列表

**问题：** `src/olav/core/router.py` 的 LLM fallback 路由写死了
`valid_agents = ["olav", "config", "audit", "ops", "quick"]`。
新 workspace 安装的 agent 不会被路由到。

**解决方案：** 从当前活动 workspace 动态构建路由候选：

```python
def _get_valid_agents() -> list[str]:
    """从活动 workspace 的目录结构动态发现可用 agent。"""
    ws_path = resolve_workspace_root()  # .olav/workspace/<active>/
    if not ws_path.is_dir():
        return ["quick"]
    return [
        d.name for d in ws_path.iterdir()
        if d.is_dir() and (d / "AGENT.md").exists()
    ]
```

### 11.6 27 处硬编码路径

**问题：** 代码中 27 处直接拼接 `.olav/workspace/` 字符串，包括：

| 位置 | 硬编码 |
|------|--------|
| `agents/query_runner.py:22` | `workspace/quick/references/SCHEMA_REFERENCE.md` |
| `platform/services/registry.py:58` | `workspace/ops/tools/_generated` |
| `cli/main.py:126` | `workspace/audit/profiles/` |
| `cli/main.py:1019-1043` | agent 枚举只扫一层 |
| `core/config.py:279` | audit profiles 路径 |
| `cli/admin.py:338,372,467` | knowledge tools 路径 |

**解决方案：** 新建 `src/olav/core/workspace.py`，提供三个函数：

```python
def resolve_workspace_path(workspace: str | None, agent: str) -> Path:
    """解析 workspace+agent 到目录路径（带平铺 fallback）。"""

def resolve_workspace_root(workspace: str | None = None) -> Path:
    """返回 workspace 根目录（如 .olav/workspace/netops/）。"""

def get_active_workspace() -> str:
    """从 settings.json 读取 active_workspace。"""
```

27 处硬编码逐步替换为调用这三个函数。**不在每处加 fallback**，统一在
`resolve_workspace_path()` 内处理新旧结构兼容。

## 12. 升级路径

### 12.1 平铺 → 嵌套迁移

已有用户的 `.olav/workspace/quick/`、`.olav/workspace/ops/` 不会自动迁移。
提供显式迁移命令：

```bash
olav workspace migrate --workspace netops
```

流程：
1. 扫描 `.olav/workspace/` 下的平铺 agent 目录
2. 创建 `.olav/workspace/netops/`
3. 移动 `quick/ → netops/quick/`、`ops/ → netops/ops/` 等
4. 生成 `workspace.yaml` 锁文件
5. 更新 `settings.json: active_workspace = "netops"`
6. 在旧位置留软链接（可选，`--no-symlink` 跳过）

**不迁移也不会 break**——`resolve_workspace_path()` 的 fallback 保证旧结构继续工作。

### 12.2 pip upgrade olav

`olav` core 升级时：
1. `src/olav/skills/` 里的 core skills 随 wheel 更新
2. `olav init` 检测 `.olav/workspace/core/` 是否需要刷新
3. 不触碰域 workspace（`netops/`、`itsm/` 等）
4. Checkpoint、memory 数据不变

### 12.3 olav workspace upgrade

```bash
olav workspace upgrade netops
```

流程：
1. 读取锁文件 `workspace.yaml` 的 `source` 和 `commit`
2. `git fetch` 检查是否有新 commit
3. 检测 `local_modifications`：对比锁文件记录的 commit 时的 file hash
   - 若有本地修改：备份到 `.olav/workspace/.archive/netops_<timestamp>/`
4. 拉取新版本，重新生成 agent 目录
5. 更新锁文件的 `version`、`commit`、`installed_at`

### 12.4 olav-netops pip 升级

Entry points 升级时，新表定义/新命令自动生效（`importlib.metadata` 是动态的）。
workspace 里的工具文件不受影响（它们来自 `olav-netops-skills` git repo）。

**注意版本兼容：** `olav-netops-skills` 的 `workspace.yaml` 声明
`requires.packages: ["olav-netops>=0.12.0"]`。如果 skills 需要 1.0 但 pip 包还是 0.12，
`olav workspace validate` 会报警。

## 13. Core Skills 工具文件打包方式

`src/olav/skills/` 在 wheel 内（属于 `src/olav/` 包树），但部署到 `.olav/workspace/core/` 时需要处理：

Core skills 在 `src/olav/skills/` 内，应该直接 `from olav.core.memory import ...`，

指向 `src/olav/skills/` 的路径引用或生成 thin wrapper。

## 14. 反模式

| ❌ 禁止 | ✅ 替代 |
|---|---|
| `src/olav/core/` 里放网络运维代码 | 迁入 `olav-netops/src/olav_netops/` |
| `olav init` 创建 YANG/VIEW/netops 表 | 只初始化空库 + core workspace |

| 用户编辑 workspace.yaml 锁文件 | 修改 skill git repo 的 workspace.yaml，重新 install |
| 把 SCHEMA_REFERENCE 写在 core workspace | 属于各域的 quick/references/ |
| workspace 和 agent 一层扁平化 | workspace = 域，agent = 域内角色，两层分开 |
| olav init 后直接可用网络运维功能 | 需要 skill install + netops init |
| 只装 olav-netops-skills 不装 olav-netops pip | 两者强耦合，entry points 依赖 pip 包 |

| 不同域的表不加 schema 前缀 | 强制 `CREATE SCHEMA <domain>` 命名空间 |
