## 1. Purpose

This document defines **Option A** for OLAV: a native control-plane semantic engine built on top of canonical state, semantic views, and the shared topology contract.

Its purpose is to close the gap between:

- graph-assisted Ops reasoning in the NetworkX sandbox
- strict empirical validation in CLAB

The semantic engine is the missing middle layer.

It should provide deterministic protocol reasoning that is stronger than heuristics, while remaining aligned with OLAV's schema-on-read architecture.

---

## 2. Position in the Architecture

The three-stage architecture is:

```text
semantic views + topology_links + schema_catalog
        ↓
control-plane semantic engine
        ↓
Ops NetworkX sandbox and CLAB CAB workflows
```

This means:

1. the semantic engine does not replace the sandbox
2. the sandbox orchestrates and explains semantic results
3. CLAB remains the final strict validation stage

The semantic engine is therefore a **deterministic reasoning service**, not a user-facing workflow by itself.
It is also an advisory-only component and must not write to production devices.

---

## 3. What Problem It Solves

The current graph layer can model:

- devices
- adjacencies
- protocol state attachments
- blast radius
- dependency expansion

But it cannot by itself answer the questions that matter most for routing safety:

1. which path wins after a policy change
2. which prefixes move after a failure
3. whether a route becomes unreachable
4. whether an alternative path is valid
5. whether a policy introduces blackholes or loops

The semantic engine exists to answer those questions with deterministic code rather than free-form LLM reasoning.
Its output is recommendation-quality reasoning, not direct execution authority.

---

## 4. Design Principles

### 4.1 Canonical Inputs Only

The engine must consume canonical state contracts, not prompt-specific interpretations.

Primary sources:

- semantic views
- `topology_links`
- inventory contract
- `schema_catalog`

Raw snapshot reads are allowed only as a controlled fallback for missing semantic projections.

### 4.2 Deterministic First

Protocol reasoning must be done by code and fixed algorithms.

The LLM may choose what scenario to evaluate, but it must not be the protocol solver.

### 4.3 Explainable Outputs

The engine must return not only conclusions, but also a trace of why the conclusion was reached.

### 4.4 Incremental Scope

OLAV should not try to solve every protocol at once.

The engine should be delivered in bounded phases.

---

## 5. Scope of the First Version

The first useful version should cover four capabilities.

### 5.1 BGP Best-Path Reasoning

Support at least:

- neighbor propagation
- local-pref comparison
- AS-path length comparison
- MED comparison where relevant
- eBGP versus iBGP preference
- next-hop validity checks
- best-path selection per prefix

### 5.2 IGP Path Computation

Support at least:

- OSPF adjacency state
- interface cost handling
- shortest-path computation
- next-hop derivation from the active topology

### 5.3 Policy Evaluation IR

Support a canonical internal representation for common policy behavior:

- prefix-set match
- community match
- local-pref set
- MED set
- next-hop set
- permit / deny

This must be canonicalized before evaluation. The engine should not depend on raw vendor syntax as its execution format.

### 5.4 Invariant Checks

Support at least:

- reachability
- no-blackhole
- no-loop
- expected next-hop stability or change
- blast-radius boundary checks

---

## 6. Internal Layers

The engine should be split into five internal layers.

### 6.1 Canonical State Loader

Responsible for:

- reading semantic views
- normalizing device identity
- normalizing protocol object identity
- packaging a stable scenario input bundle

### 6.2 Topology and Reachability Layer

Responsible for:

- reading `topology_links`
- building the canonical graph form
- exposing graph paths and adjacency constraints to the protocol layers

This layer may use `networkx` or a faster graph backend, but it remains a substrate layer.

### 6.3 Policy IR Layer

Responsible for:

- converting vendor or canonical policy rows into an internal policy IR
- evaluating policy matches and actions deterministically
- returning transformed route attributes

### 6.4 Protocol Solver Layer

Responsible for:

- BGP propagation
- path candidate generation
- best-path selection
- IGP path computation
- route eligibility checks

### 6.5 Invariant Layer

Responsible for:

- evaluating expected properties of the network after a scenario
- producing pass/fail results with explanation traces

---

## 7. Recommended Technical Stack

The recommended stack is:

1. `networkx` for graph substrate in the first version
2. `ipaddress` for IP and prefix semantics
3. `pytricia` for prefix lookup and longest-prefix-match behavior
4. optional `z3-solver` for higher-confidence invariant checks

`networkx` is acceptable in the first implementation because the current problem is semantic correctness, not graph scale.

If performance becomes a bottleneck later, the graph substrate can move to `rustworkx` without changing the higher-level contracts.

---

## 8. Relationship to the NetworkX Sandbox

The semantic engine should be callable from the sandbox.

The workflow should be:

1. sandbox gathers the relevant scenario
2. sandbox calls the semantic engine for deterministic protocol reasoning
3. sandbox interprets the result for the operator
4. sandbox decides whether to escalate to CLAB

This means the sandbox remains the orchestration and explanation surface, while the engine becomes the deterministic core.

Neither layer is allowed to execute production changes directly.

---

## 9. Relationship to CLAB CAB

The semantic engine should also feed the CLAB CAB path.

The workflow should be:

1. use the semantic engine to predict expected impact
2. replay the proposed change in CLAB
3. compare predicted protocol outcomes to observed lab outcomes
4. downgrade confidence or reject the change when prediction and observation diverge

This creates a strong control loop:

- deterministic prediction
- empirical validation
- model correction when they disagree

The final production action still belongs to the human engineer.

---

## 10. Input and Output Contract

### 10.1 Input Contract

The engine should receive a scenario package shaped roughly like:

```json
{
  "snapshot_id": "2026-03-20",
  "devices": ["R1", "R2", "R3"],
  "protocols": ["bgp", "ospf"],
  "topology": "topology_links projection",
  "protocol_state": "semantic view projection",
  "policies": "canonical policy IR inputs",
  "proposed_change": "canonical change delta"
}
```

### 10.2 Output Contract

The engine should return structured results such as:

```json
{
  "reasoning_mode": "protocol_semantic_engine",
  "protocols_evaluated": ["bgp", "ospf"],
  "predicted_changes": [
    {
      "prefix": "10.99.0.0/24",
      "device": "R1",
      "old_next_hop": "R2",
      "new_next_hop": "R3",
      "cause": "local_pref raised by import policy"
    }
  ],
  "invariants": [
    {
      "name": "no_blackhole_for_10.99.0.0/24",
      "passed": true,
      "explanation": "A valid path remains via R3"
    }
  ],
  "explanation_trace": [
    "R1 receives two candidates for 10.99.0.0/24",
    "policy on R1 raises local-pref for neighbor R3",
    "best path changes from R2 to R3"
  ]
}
```

## 11. Delivery Phases

### Phase 1

- canonical state loader
- graph substrate integration
- BGP best-path MVP
- basic invariants

### Phase 2

- OSPF path computation
- policy IR expansion
- richer explanation traces

### Phase 3

- optional solver-backed invariants
- broader policy and protocol coverage
- tighter CLAB prediction versus observation comparison

---

## 12. Required Codebase Changes

The design implies new implementation modules such as:

- `control_plane_ir.py`
- `policy_ir.py`
- `bgp_solver.py`
- `ospf_solver.py`
- `invariants.py`
- `scenario_loader.py`

The current simulation and sandbox layers should call these modules rather than re-implement protocol logic ad hoc.

---

## 13. Non-Goals

The first version is not trying to be:

1. a complete Batfish replacement
2. a full multi-vendor parser framework
3. a data-plane packet-level simulator
4. a reason to bypass CLAB validation

The goal is narrower:

- deterministic protocol reasoning for the most valuable change and failure questions

---

## 14. Final Position

Option A should be implemented as a dedicated control-plane semantic engine that:

1. consumes canonical OLAV state contracts
2. performs deterministic protocol reasoning
3. feeds both the Ops sandbox and the CLAB CAB path
4. makes OLAV materially stronger than graph heuristics alone
5. remains advisory-only for production operations

This is the correct way to close the remaining semantic gap.

`networkx` remains useful, but only as one substrate inside this design, not as the whole answer.
