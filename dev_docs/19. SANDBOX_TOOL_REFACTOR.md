# 19. Sandbox Tool Refactor — Agent 工具层精简

**Date:** 2026-03-31
**Status:** 设计确认，待实施
**Depends on:** §15 Hermes、§18 Ecosystem Split

---

## 1. 问题

当前 `ops/` workspace 存在大量 `@tool` 封装函数，这些工具：

- 被 @tool 的参数签名限制，agent 遇到参数不足时需要 workaround
- 重复封装了 agent 完全可以自己写的逻辑（httpx 调用、pandas 分析、shell 命令）
- 导致 workspace 工具集臃肿（ops/lab 有 15+ @tool），增加 token 消耗和选择复杂度

**根本矛盾**：@tool 是为"重复使用的固定接口"设计的，但很多工具实际上每次都在做不同的事情。

---

## 2. 核心原则

```
写/变更外部系统  →  必须是 @tool（强制审批门 + 审计链）
读/计算/纯逻辑  →  sandbox（agent 自写代码，更灵活）
```

| 类型 | 机制 | 理由 |
|------|------|------|
| 网络设备 CLI 变更 | `execute_cli` @tool + `requires_approval()` | 不可逆，需 HITL |
| 数据库写入 | `execute_sql` @tool + `read_only=True` 强制 | 防止意外变更 |
| 审计记录 | `record_network_event` @tool | append-only 强制 |
| 语义记忆写入 | `recall_memory` @tool + `scan_content()` | 注入扫描不能绕过 |
| 数据读取/计算/分析 | `run_python_code` sandbox | agent 自写，无限制 |
| Shell 探测命令 | `execute` (LocalShellBackend) | 系统工具已有 |
| HTTP API 调用 | `run_python_code` + httpx 或 `service_call` | 动态参数需求多变 |

## 3. 可以删除的工具（sandbox 化）

### 3.1 ops/lab/tools — 5 个 ContainerLab API 封装层

| 文件 | 当前功能 | 替代方式 |
|------|---------|---------|
| `_build_topology_yaml.py` | 构建 CLAB topology YAML | `run_python_code`: agent 自己 build |
| `_get_definition_schema.py` | 获取 CLAB API schema | `run_python_code` + httpx GET |
| `_query_api_schema.py` | 查询 CLAB API schema | `run_python_code` + httpx GET |

| `call_api.py` | 封装 httpx ContainerLab 调用 | `run_python_code` + httpx |

这 5 个工具本质是"帮 agent 调 ContainerLab REST API"。agent 用 `run_python_code` + httpx 直接调用更灵活，参数不再受签名限制。

### 3.2 ops/diff/tools — diff 三件套

| 文件 | 当前功能 | 替代方式 |

| `diff_topology_drift.py` | 拓扑漂移对比 | `run_python_code` + duckdb |
| `diff_routing_drift.py` | 路由漂移对比 | `run_python_code` + duckdb |
| `diff_configs.py` | 配置对比 | `run_python_code` + difflib |

agent 自己写 SQL + Python 对比逻辑，可以任意定制阈值、输出格式、过滤条件。

### 3.3 ops/tools — 纯计算工具

| 文件 | 当前功能 | 替代方式 |
|------|---------|---------|
| `format_and_export.py` | 数据格式化导出 | `run_python_code` + pandas/tabulate |
| `take_snapshot.py` | 触发 snapshot | `run_python_code`: `olav netops snapshot` CLI |

### 3.4 ops/probe/tools — 网络探测

| 文件 | 当前功能 | 替代方式 |
|------|---------|---------|
| `ping_device.py` | ping | `execute`: `ping -c3 <host>` |
| `traceroute.py` | traceroute | `execute`: `traceroute -n <host>` |
| `port_scan.py` | 端口扫描 | `execute`: `nmap -p <ports> <host>` |

`LocalShellBackend` 已注入 `execute` shell 工具，系统命令直接可用。

## 4. 必须保留为 @tool 的（安全边界，8 个）

```
execute_cli              ← 网络设备变更，requires_approval() 门禁
execute_sql              ← read_only=True 强制，mutation 需审批
recall_memory            ← scan_content() 注入扫描
web_search               ← 外部网络访问（受控）
record_network_event     ← 审计数据库 append-only
service_call             ← 统一认证 HTTP 入口（带 JWT/Bearer 管理）
execute_cli_parallel     ← 批量设备变更，同样需要 approval 门
search_commands          ← 命令库查询（只读，保留方便）
```

`service_call` 也应暴露给 `run_python_code` 执行环境：

```python
# agent 在 run_python_code 里直接调用已注册服务
from olav.platform.services.client import service_call
devices = service_call("netbox", "GET", "/api/dcim/devices/", params={"site": "dc1"})
_result = devices
```

## 5. 改造后的工具集

```
@tool 安全边界（8个）          sandbox（agent 自写）
────────────────────           ──────────────────────────────────
execute_cli                    run_python_code  ← 数据处理/API调用/分析/仿真
execute_sql (read-only)        execute (shell)  ← ping/traceroute/nmap/文件操作
execute_cli_parallel
recall_memory
web_search
record_network_event
service_call
search_commands
```

从约 **25 个工具** 精简到 **8 个 @tool + 2 个 sandbox 入口**。

## 6. service_call 在 sandbox 中的使用

为了让 `run_python_code` 能调用已注册服务（带认证），需要确保执行环境可以 import：

```python
# .olav/workspace/core/tools/run_python_code.py 的执行环境
# 已安装 olav 包 → service_call 可直接 import

# agent 写的代码示例
from olav.platform.services.client import service_call
import json

result = service_call("netbox", "GET", "/api/dcim/devices/", params={"limit": 10})
_result = result
```

无需修改 `run_python_code.py`，因为执行环境已在当前 Python venv 中。

## 7. 对 LifecycleManager 的影响

`LifecycleManager.wait_healthy()` 原本设计为被 @tool 调用。

改造后，skill 的 tool 可以这样写（仍是 @tool，因为涉及容器启停）：

```python
@tool
def ensure_netbox_healthy() -> dict:
    """确保 NetBox 容器健康运行，必要时自动拉起。"""
    from olav.platform.services.lifecycle import LifecycleManager
    mgr = LifecycleManager(
        "netbox",
        compose_file="/home/yhvh/Olav/.olav/services/netbox/docker-compose.yml",
    )
    return mgr.wait_healthy(timeout=120, poll_interval=5)
```

容器启停属于"变更外部系统"，保留为 @tool 是正确的。
