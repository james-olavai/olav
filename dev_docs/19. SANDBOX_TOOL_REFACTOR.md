# 19. Sandbox Tool Refactor — Agent 工具层精简

**Date:** 2026-03-31
**Revised:** 2026-04-02 (经真实 E2E 测试修订)
**Status:** 方案修订完成，仅 3 个工具可安全 sandbox 化

---

## 1. 修订背景

原方案计划删除 13 个工具（全部 sandbox 化）。**真实 E2E 测试暴露了过激 sandbox 化的根本失控问题：**

```
LLM 写的 httpx：response["returnCode"]    ← CLAB 实际字段名是 "return_code"（静默失败）
LLM 构建 URL：/api/v1/exec               ← 实际是 /api/v1/labs/{name}/exec（404）
LLM 忘记 JWT Bearer header               ← 401，无提示
LLM 跳过 fix_srl_topology               ← CLAB 节点永远起不来
```

---

## 2. 核心判断框架

```
保留 @tool 的条件（满足任一即保留）:
  A. 写外部系统（需 approval 门）
  B. 多步骤强制序列（顺序不可乱）
  C. 接口契约（字段名/URL/Auth 必须精确，LLM 写错静默失败）
  D. 业务逻辑已编码（确定性算法，不应每次重写）
  E. 关键验证路径（diff/probe/check 的正确性至关重要）

可以 sandbox 的条件（全部满足方可）:
  A. 纯计算/数据变换，无外部副作用
  B. 出错可见可重试（不会静默失败）
  C. 结果灵活性比确定性更重要
  D. 等效于 1-2 条 shell 命令
```

## 4. "限制性 sandbox" 模式

`run_python_simulation` 是正确的 sandbox 架构示范：

```python
# 限制性 sandbox（推荐）：只暴露特定对象，无 HTTP 出口
sandbox.env = {
    "db":       DatabaseProxy(MAIN_DB_PATH, read_only=True),  # 只能读 netops 数据
    "sim":      SimulationProxy(),                             # 只能写内存克隆
    "nx":       networkx,                                      # 图计算
    "netutils": netutils,                                      # IP 工具
}
# ❌ 不暴露 httpx、subprocess、os.environ → 无法触达生产系统

# 通用 sandbox（谨慎用于基础设施操作）
run_python_code(code)  # 可 import 任何包 → 灵活但不可控
```

**规则：不要用 `run_python_simulation` 做基础设施操作**（如 httpx 推配置），只用于数据分析和 What-If 仿真。

## 1. 问题

当前 `ops/` workspace 存在大量 `@tool` 封装函数，这些工具：

- 被 @tool 的参数签名限制，agent 遇到参数不足时需要 workaround
- 重复封装了 agent 完全可以自己写的逻辑（httpx 调用、pandas 分析、shell 命令）
- 导致 workspace 工具集臃肿（ops/lab 有 15+ @tool），增加 token 消耗和选择复杂度

**根本矛盾**：@tool 是为"重复使用的固定接口"设计的，但很多工具实际上每次都在做不同的事情。

---

## 2. 核心原则

```
写/变更外部系统  →  必须是 @tool（强制审批门 + 审计链）
读/计算/纯逻辑  →  sandbox（agent 自写代码，更灵活）
```

| 类型 | 机制 | 理由 |
|------|------|------|
| 网络设备 CLI 变更 | `execute_cli` @tool + `requires_approval()` | 不可逆，需 HITL |
| 数据库写入 | `execute_sql` @tool + `read_only=True` 强制 | 防止意外变更 |
| 审计记录 | `record_network_event` @tool | append-only 强制 |
| 语义记忆写入 | `recall_memory` @tool + `scan_content()` | 注入扫描不能绕过 |
| 数据读取/计算/分析 | `run_python_code` sandbox | agent 自写，无限制 |
| Shell 探测命令 | `execute` (LocalShellBackend) | 系统工具已有 |
| HTTP API 调用 | `run_python_code` + httpx 或 `service_call` | 动态参数需求多变 |

## 6. service_call 在 sandbox 中的使用

为了让 `run_python_code` 能调用已注册服务（带认证），需要确保执行环境可以 import：

```python
# .olav/workspace/core/tools/run_python_code.py 的执行环境
# 已安装 olav 包 → service_call 可直接 import

# agent 写的代码示例
from olav.platform.services.client import service_call

result = service_call("netbox", "GET", "/api/dcim/devices/", params={"limit": 10})
_result = result
```

无需修改 `run_python_code.py`，因为执行环境已在当前 Python venv 中。

## 7. 对 LifecycleManager 的影响

`LifecycleManager.wait_healthy()` 原本设计为被 @tool 调用。

改造后，skill 的 tool 可以这样写（仍是 @tool，因为涉及容器启停）：

```python
@tool
def ensure_netbox_healthy() -> dict:
    """确保 NetBox 容器健康运行，必要时自动拉起。"""
    from olav.platform.services.lifecycle import LifecycleManager
    mgr = LifecycleManager(
        "netbox",
        compose_file="/home/yhvh/Olav/.olav/services/netbox/docker-compose.yml",
    )
    return mgr.wait_healthy(timeout=120, poll_interval=5)
```

容器启停属于"变更外部系统"，保留为 @tool 是正确的。
