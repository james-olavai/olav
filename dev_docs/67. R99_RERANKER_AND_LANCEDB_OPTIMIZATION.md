## Why now

R98 closed with a key finding: **memory is what steers small models**. Demo7 Ch8 #6 succeeded because L1 precedent + directive guide were injected by AutoRecall. But the experimental top-K showed something off:

```
Top-5 hits for "Write a bash script to backup running-config from all routers":
  1. [query_pattern] Q: Write a bash script to backup running-config...   ← past user query, NOT an answer
  2. [query_pattern] Q: Write a bash backup script for routers R1-R4...   ← same
  3. [operational_event] Action: format_and_export Args: {"data": "..."}  ← actual precedent (the answer)
  4. [fact] Routers R1, R2, R4 have BGP sessions stuck...                  ← unrelated
  5. [fact] Routers R1, R2, R4 have BGP...                                 ← duplicate-ish
```

`query_pattern` rows ranked above the actual answer because their `text` literally is the user's query — bi-encoder cosine similarity is highest there. **Vector retrieval surfaces "looks like the question"**; we want **"answers the question"**.

This is the textbook problem that **rerankers solve**. We've been compensating with hand-rolled diversifiers + per-category quotas (`AutoRecallMiddleware._diversify_by_category`, ~150 LOC) — they help but don't fix root cause and are bespoke. LanceDB 0.7+ now ships native reranker integration; let's use it.

---

## Goals

* Fix the "irrelevant first-stage hits dominate top-K" problem so the directive memory wins on Ch8 vague-prompt scenario **without** needing an L1 precedent in the store.
* Drop or simplify ~150 LOC of hand-coded diversifier and per-category quota logic.
* Improve cross-language retrieval (zh ↔ en) — current OLAV deployments mix languages and BM25 doesn't handle that well.
* Stay within local-Ollama deploy story — no new vendor dependency.

Non-goals (out of scope for R99):
* Adaptive feedback / "did the LLM actually cite this memory" learning (R100+ candidate)
* Federated cross-team retrieval (L3 enterprise feature)
* Replacing LanceDB

---

## Design: two-tier optimization

### Tier 1 — Native reranker (the lever)

Replace the diversifier with LanceDB's native rerank chain:

```python
# Pseudocode for AutoRecallMiddleware._gather_candidates (after refactor)
results = (
    tbl.search(query_vector)                    # bi-encoder candidates
       .where(scope_filter, prefilter=True)     # per-agent scope
       .limit(50)                                # large candidate pool
       .rerank(
           query=user_text,                      # cross-encoder rerank
           reranker=self._reranker,              # injected, configurable
           normalize_score=True,
       )
       .limit(top_k)                             # final precision pool
       .to_list()
)
```

**Reranker model selection**: `bge-reranker-v2-m3`
* Multilingual native (zh + en + 100+ langs)
* ~570 MB Q4_K_M quantized — fits comfortably alongside qwen3.6:27b on Ollama
* Fast: ~50-200ms for 50 candidates on 4 GB GPU
* Open weights, no API key

```bash
# One-time provisioning on the Ollama box
ollama pull bge-reranker-v2-m3
```

LanceDB integration via OpenAI-compatible reranker adapter:

```python
from lancedb.rerankers import OpenaiReranker

reranker = OpenaiReranker(
    api_key="ollama",                                  # sentinel
    base_url="http://192.168.100.12:11434/v1",         # same Ollama
    model_name="bge-reranker-v2-m3",
)
```

If `OpenaiReranker` doesn't expose this exact wiring, fall back to writing a thin custom subclass of `lancedb.rerankers.Reranker`:

```python
class OllamaReranker(Reranker):
    def rerank_hybrid(self, query, vector_results, fts_results):
        merged = self._fuse(vector_results, fts_results)
        scores = self._score_with_ollama(query, merged)
        return self._sort_by_score(merged, scores)
```

**Configurable** via `.olav/config/api.json`:

```json
"reranker": {
  "enabled": true,
  "model": "bge-reranker-v2-m3",
  "base_url": "http://192.168.100.12:11434/v1",
  "candidate_pool": 50,
  "final_top_k": 10
}
```

`enabled: false` falls back to the current diversifier path — graceful degradation when no reranker available.

### Tier 2 — LanceDB-native hybrid_search

LanceDB 0.8+ ships `tbl.hybrid_search(query_vector, query_text)` that internally fuses vector + FTS via reciprocal rank fusion, parameterized via:

```python
results = (
    tbl.hybrid_search(query_vector, user_text)
       .where(scope_filter, prefilter=True)
       .limit(50)
       .rerank(reranker=reranker)
       .limit(top_k)
       .to_list()
)
```

This **replaces** the custom `hybrid_search` function in `olav.core.memory.__init__` (currently ~70 LOC) with a single chained call. Net code delta is negative.

### Tier 3 (deferred) — Multi-vector for directive guides

A guide row could carry **two** vector columns:
* `text_vector` — full body (current)
* `intent_vector` — embedding of just the `intent` + `keywords` fields

```python
# query both, fuse via RRF; LanceDB supports per-column query in 0.9+
intent_hits = tbl.search(query_vec, vector_column_name="intent_vector").limit(20)
body_hits = tbl.search(query_vec, vector_column_name="text_vector").limit(20)
merged = rrf_merge(intent_hits, body_hits)
```

Reasoning: the directive's `body` is long prose; its `intent + keywords` are a tighter semantic anchor. A user query like "save the report" matches "save_class_directive" intent vector before it matches the 600-token body. **Defer** this until the reranker work is in place — simpler to evaluate the lift independently.

## Risks / open questions

* **Ollama reranker endpoint** — the exact API shape for cross-encoder rerank on Ollama is less standardized than chat completions. May need to write a small proxy or use the `/api/embeddings` endpoint with paired (query, passage) inputs and compute scores client-side. Investigate first.
* **Latency on hot path** — reranker adds ~50-200ms per AutoRecall call. For local 27B agent flows (~55s/LLM call) this is noise. For cloud-API flows (~1-3s/call) it's noticeable but tolerable. Document the trade-off.
* **Cache compatibility** — existing embed-cache (`olav.core.embedder._embed_cache`) handles single embeddings. Reranker batches `(query, doc)` pairs and isn't easily cacheable in the same way. May add a separate `(query_hash, doc_id) → score` LRU.
* **Tier 3 multi-vector** — depends on LanceDB's per-column search API which is still settling in 0.9+. Validate before committing to it.
* **Local fallback** — if Ollama is unreachable, AutoRecall must keep working with the legacy diversifier. The `enabled: false` flag covers this; verify it under failure injection in tests.
* **Memory bloat** — bge-reranker-v2-m3 is ~570 MB on disk + ~4 GB GPU at inference. Confirm headroom on the Ollama box (it's also serving qwen3.6:27b at ~26 GB).

## Success criteria

R99 ships when all of:

1. Reranker on by default in `.olav/config/api.json` (with disable flag).

3. Ch8 vague-prompt experiment: directive guide ranks **first** in top-K **without** an L1 precedent in the store. (Validates that reranker is doing real work.)
4. Latency increase under typical AutoRecall call: ≤ 250ms p95.
5. All existing tests green; new test covering reranker on/off symmetry.
6. olav-doc `memory-architecture.md` mentions the two-stage retrieval (bi-encoder + cross-encoder rerank).

## Decision log

* **Reject Cohere / Jina hosted rerank**: locks us into vendor billing. We're committed to local-first.
* **Reject custom cross-encoder fine-tuning**: way out of scope for R99.
* **Defer multi-vector (Tier 3)**: extra schema migration, evaluate independently after Tier 1 lands.
* **Adaptive recall feedback (R100+)**: depends on reliable "did the LLM actually cite this memory" detection — needs its own design pass, not piggybacked on R99.

---

## What this does NOT replace

* L1 capture — still grows the store from observation.
* L2 pattern extraction — still distills N samples into reusable patterns.
* Directive guides — still the explicit team-rule mechanism.
* Scope isolation — unchanged.

R99 is purely a **retrieval quality** optimization. The downstream consumers (AutoRecall injection format, agents reading `<relevant-memories>` blocks) don't change at all.
