## Tier 1 empirical result (2026-04-28) — Ollama-served rerank does not work

A/B tested both `bbjson/bge-reranker-base` (v1) and `dengcao/bge-reranker-v2-m3` (v2-m3, BERT family) against a frozen demo7 LanceDB (25 rows: 4 directive guides + 8 operational events + 3 query patterns + 7 facts + 2 decisions + 1 services pattern). Same Ch8 query, same first-stage candidate set, only the reordering pass differs.

| memory | category | baseline rank (nomic-768) | v2-m3 reranked rank |
|---|---|---|---|
| `directive-write-tool-call-global` | expert_knowledge | 9 | **21** |
| `directive-write-tool-call-core` | expert_knowledge | 10 | **22** |
| `directive-write-tool-call-services` | expert_knowledge | 11 | **23** |
| `directive-write-tool-call-ops` | expert_knowledge | 12 | **24** |
| `opev-17b...` (format_and_export precedent) | operational_event | 4 | **17** |
| `opev-95c...` (format_and_export precedent) | operational_event | 5 | **18** |
| `qp_57f...` (literal past query — should be DEMOTED) | query_pattern | 1 | 1 |

The directive guides went from "buried but reachable" (9-12) to "unreachable" (21-24, beyond top-K=10). Format-and-export precedents — the actual answer — also got pushed down. v1 had previously shown the same pattern.

**Root cause** (predicted in the original risks section): Ollama's `/api/embeddings` endpoint exposes BERT-class reranker models as bi-encoders. The cross-encoder rerank head (CLS → linear classifier → relevance score) is not preserved through GGUF conversion. So the reranker becomes "another embedder with a different latent space," and that latent space — trained for relevance scoring as a *paired-input* model — gives garbage when split apart and used as bi-encoder cosine. Empirically it clusters by something other than query→answer relevance, and ranks abstract/admonitory directive text *farther* from the concrete query than the first-stage general-purpose embedder does.

Additionally: v2-m3 returned HTTP 500 from `/api/embeddings` on long inputs (the 60+ KB `format_and_export` script bodies), even after truncation to 750/375/200 chars. Affected rows fell to NaN-score and sank to the bottom — a separate Ollama-side robustness gap.

**Decision**: keep `OllamaEmbeddingReranker` + middleware plumbing in source so future cross-encoder paths can plug in via the same factory. Set `enabled: false` in `.olav/config/api.json` with an explanatory `_comment`. Do not ship Tier 1 as designed.

**Forward options if cross-encoder rerank is wanted later**:
1. **Sidecar service** — small `transformers`-based HTTP server next to Ollama, loads `bge-reranker-v2-m3` via `FlagEmbedding.FlagReranker`, exposes a `/score` endpoint taking `(query, [docs])` → list of relevance floats. Then `OllamaEmbeddingReranker` becomes `SidecarReranker`. ~50 LOC service + ~600 MB extra deps on the inference box (not on the OLAV wheel).
2. **LanceDB-native `CrossEncoderReranker`** — uses `sentence_transformers` directly. Pulls 600+ MB of ML deps into the OLAV install — not acceptable per the original goal of "stay within local-Ollama deploy story."
3. **Sharper first-stage filtering** — accept that bi-encoder is the only retrieval signal we have, and lift precision via category quotas + scope-priority + smarter directive promotion (returns to the path R98 was already on).
4. **Wait for Ollama to expose `/api/rerank`** — upstream issue tracker has interest in this; the API shape would solve the GGUF head-loss problem cleanly.

The **realistic next step** is (3): the diversifier path was working (Ch8 #6 passed) and is the documented L1+L2+directive architecture. Tier 1 was an optimization, not a correctness fix. Park R99 here.

## S1 — Corpus-design fix beats model swap (2026-04-28)

After Tier 1 was abandoned, a Cohere reranker probe (via local proxy at `127.0.0.1:3300/v1`, `cohere/rerank-v3.5`) confirmed cross-encoder rerank IS achievable and produces clean signal — but it also exposed that **the real problem isn't the model, it's the corpus**.

### Cohere baseline diagnostic

Same demo7 store, same Ch8 query. Cohere/rerank-v3.5 ranks:

| memory | baseline cosine | cohere rel. score | cohere rank |
|---|---|---|---|
| `qp_*` (literal user-query echoes) | 0.77-0.88 | **0.94-0.96** | 1-3 |
| `format_and_export` precedent | 0.62 | 0.84-0.85 | 4-5 |
| `directive-write-tool-call-*` | 0.38 | 0.74 | 6-9 |
| Random facts | 0.40 | 0.04-0.26 | 10+ |

Cohere is faithfully scoring relevance — and it tells us that `query_pattern` rows (storing the *verbatim user query* as their main text) ARE the most relevant text to a similar future query. That's not a model bug. It's corpus design.

### Root cause

`QueryPatternCapturePlugin` was writing:

```
text = f"Q: {user_query}\nWorking SQL: {sql}"
```

The embedded text is dominated by the verbatim user_query. Future similar queries hit ~0.88-0.95 cosine in bi-encoder space and 0.94-0.96 cross-encoder relevance — drowning directive (~0.74) and format_and_export precedents (~0.84). No reranker can fix this because the text genuinely IS the most relevant.

### Fix (committed)

`src/olav/plugins/middleware/query_pattern_capture.py:226-234`:

```python
# was:
text = f"Q: {user_query}\nWorking SQL: {winner['sql']}"

# now:
tags = _extract_keywords(user_query)
keyword_str = ", ".join(tags) if tags else "(no keywords)"
text = (
    f"Working SQL for queries about: {keyword_str}\n"
    f"{winner['sql']}"
)
```

Verbatim user_query stays in `metadata.intent` so L2 distillation (`pattern_extractor`) still has full context. Embedded text is anchored on extracted keywords + SQL only — retrieval signal becomes "what kind of SQL solves this kind of intent" instead of "what user-prose does this echo."

### Empirical lift (demo7, post-migration)

Same A/B harness, after re-embedding the 3 existing query_pattern rows with new format:

| memory | bi-encoder rank<br>(BEFORE S1) | bi-encoder rank<br>(AFTER S1) | rerank-v3.5 rank<br>(BEFORE S1) | rerank-v3.5 rank<br>(AFTER S1) |
|---|---|---|---|---|
| `format_and_export` (the actual answer) | 4-5 | **1-2** ✓ | 3-5 | **1-2** ✓ |
| `directive-write-tool-call-*` | 9-12 | 9-12 | 6-9 | **3-6** ✓ |
| `query_pattern` (literal echoes) | 1-3 | **3-5** ✓ | 1-4 | **7-9** ✓ |

The corpus fix alone — no reranker, no infrastructure change — promotes the actual answer from rank 4-5 to rank **1-2** in the bi-encoder baseline. Pair S1 with rerank → directive at rank 3 (was buried at 9-12 before either fix).

### In-vivo verification

Demo7 wheel rebuild + reinstall + fresh run on a different write-class task ("save markdown table to exports/devices_summary.md"). Verified:

* `qp_3fad9abbe603` (newly-captured row from this run) uses new format:
  `"Working SQL for queries about: save, markdown, table, exports, devices_summary, sql\nSELECT hostname, ip_address, platform FROM netops.devices ORDER BY name"`
* No verbatim user-query string in `text` (regression-tested by `tests/unit/test_query_pattern_capture_text_format.py`)
* `metadata.intent` still has the original prompt for L2
* Agent emitted `format_and_export` cleanly (3 tool calls total: 1 wrong-column SQL → self-correction → write)

### Decision

S1 supersedes the rerank line as the immediate fix. Rerank plumbing stays in source behind `enabled:false` for future revisit (when there's a llama-server/sidecar path that exposes a real cross-encoder `/score` endpoint). Park R99 Tier 1 — the corpus problem was masquerading as a retrieval problem; once corpus is right, vanilla bi-encoder cosine puts the right rows on top.

## Why now

R98 closed with a key finding: **memory is what steers small models**. Demo7 Ch8 #6 succeeded because L1 precedent + directive guide were injected by AutoRecall. But the experimental top-K showed something off:

```
Top-5 hits for "Write a bash script to backup running-config from all routers":
  1. [query_pattern] Q: Write a bash script to backup running-config...   ← past user query, NOT an answer
  2. [query_pattern] Q: Write a bash backup script for routers R1-R4...   ← same
  3. [operational_event] Action: format_and_export Args: {"data": "..."}  ← actual precedent (the answer)
  4. [fact] Routers R1, R2, R4 have BGP sessions stuck...                  ← unrelated
  5. [fact] Routers R1, R2, R4 have BGP...                                 ← duplicate-ish
```

`query_pattern` rows ranked above the actual answer because their `text` literally is the user's query — bi-encoder cosine similarity is highest there. **Vector retrieval surfaces "looks like the question"**; we want **"answers the question"**.

This is the textbook problem that **rerankers solve**. We've been compensating with hand-rolled diversifiers + per-category quotas (`AutoRecallMiddleware._diversify_by_category`, ~150 LOC) — they help but don't fix root cause and are bespoke. LanceDB 0.7+ now ships native reranker integration; let's use it.

---

## Goals

* Fix the "irrelevant first-stage hits dominate top-K" problem so the directive memory wins on Ch8 vague-prompt scenario **without** needing an L1 precedent in the store.
* Drop or simplify ~150 LOC of hand-coded diversifier and per-category quota logic.
* Improve cross-language retrieval (zh ↔ en) — current OLAV deployments mix languages and BM25 doesn't handle that well.
* Stay within local-Ollama deploy story — no new vendor dependency.

Non-goals (out of scope for R99):
* Adaptive feedback / "did the LLM actually cite this memory" learning (R100+ candidate)
* Federated cross-team retrieval (L3 enterprise feature)
* Replacing LanceDB

## Design: two-tier optimization

### Tier 1 — Native reranker (the lever)

Replace the diversifier with LanceDB's native rerank chain:

```python
# Pseudocode for AutoRecallMiddleware._gather_candidates (after refactor)
results = (
    tbl.search(query_vector)                    # bi-encoder candidates
       .where(scope_filter, prefilter=True)     # per-agent scope
       .limit(50)                                # large candidate pool
       .rerank(
           query=user_text,                      # cross-encoder rerank
           reranker=self._reranker,              # injected, configurable
           normalize_score=True,
       )
       .limit(top_k)                             # final precision pool
       .to_list()
)
```

**Reranker model selection**: `bge-reranker-v2-m3`
* Multilingual native (zh + en + 100+ langs)
* ~570 MB Q4_K_M quantized — fits comfortably alongside qwen3.6:27b on Ollama
* Fast: ~50-200ms for 50 candidates on 4 GB GPU
* Open weights, no API key

```bash
# One-time provisioning on the Ollama box
ollama pull bge-reranker-v2-m3
```

LanceDB integration via OpenAI-compatible reranker adapter:

```python
from lancedb.rerankers import OpenaiReranker

reranker = OpenaiReranker(
    api_key="ollama",                                  # sentinel
    base_url="http://192.168.100.12:11434/v1",         # same Ollama
    model_name="bge-reranker-v2-m3",
)
```

If `OpenaiReranker` doesn't expose this exact wiring, fall back to writing a thin custom subclass of `lancedb.rerankers.Reranker`:

```python
class OllamaReranker(Reranker):
    def rerank_hybrid(self, query, vector_results, fts_results):
        merged = self._fuse(vector_results, fts_results)
        scores = self._score_with_ollama(query, merged)
        return self._sort_by_score(merged, scores)
```

**Configurable** via `.olav/config/api.json`:

```json
"reranker": {
  "enabled": true,
  "model": "bge-reranker-v2-m3",
  "base_url": "http://192.168.100.12:11434/v1",
  "candidate_pool": 50,
  "final_top_k": 10
}
```

`enabled: false` falls back to the current diversifier path — graceful degradation when no reranker available.

### Tier 2 — LanceDB-native hybrid_search

LanceDB 0.8+ ships `tbl.hybrid_search(query_vector, query_text)` that internally fuses vector + FTS via reciprocal rank fusion, parameterized via:

```python
results = (
    tbl.hybrid_search(query_vector, user_text)
       .where(scope_filter, prefilter=True)
       .limit(50)
       .rerank(reranker=reranker)
       .limit(top_k)
       .to_list()
)
```

This **replaces** the custom `hybrid_search` function in `olav.core.memory.__init__` (currently ~70 LOC) with a single chained call. Net code delta is negative.

### Tier 3 (deferred) — Multi-vector for directive guides

A guide row could carry **two** vector columns:
* `text_vector` — full body (current)
* `intent_vector` — embedding of just the `intent` + `keywords` fields

```python
# query both, fuse via RRF; LanceDB supports per-column query in 0.9+
intent_hits = tbl.search(query_vec, vector_column_name="intent_vector").limit(20)
body_hits = tbl.search(query_vec, vector_column_name="text_vector").limit(20)
merged = rrf_merge(intent_hits, body_hits)
```

Reasoning: the directive's `body` is long prose; its `intent + keywords` are a tighter semantic anchor. A user query like "save the report" matches "save_class_directive" intent vector before it matches the 600-token body. **Defer** this until the reranker work is in place — simpler to evaluate the lift independently.

## Risks / open questions

* **Ollama reranker endpoint** — the exact API shape for cross-encoder rerank on Ollama is less standardized than chat completions. May need to write a small proxy or use the `/api/embeddings` endpoint with paired (query, passage) inputs and compute scores client-side. Investigate first.
* **Latency on hot path** — reranker adds ~50-200ms per AutoRecall call. For local 27B agent flows (~55s/LLM call) this is noise. For cloud-API flows (~1-3s/call) it's noticeable but tolerable. Document the trade-off.
* **Cache compatibility** — existing embed-cache (`olav.core.embedder._embed_cache`) handles single embeddings. Reranker batches `(query, doc)` pairs and isn't easily cacheable in the same way. May add a separate `(query_hash, doc_id) → score` LRU.
* **Tier 3 multi-vector** — depends on LanceDB's per-column search API which is still settling in 0.9+. Validate before committing to it.
* **Local fallback** — if Ollama is unreachable, AutoRecall must keep working with the legacy diversifier. The `enabled: false` flag covers this; verify it under failure injection in tests.
* **Memory bloat** — bge-reranker-v2-m3 is ~570 MB on disk + ~4 GB GPU at inference. Confirm headroom on the Ollama box (it's also serving qwen3.6:27b at ~26 GB).

## What this does NOT replace

* L1 capture — still grows the store from observation.
* L2 pattern extraction — still distills N samples into reusable patterns.
* Directive guides — still the explicit team-rule mechanism.
* Scope isolation — unchanged.

R99 is purely a **retrieval quality** optimization. The downstream consumers (AutoRecall injection format, agents reading `<relevant-memories>` blocks) don't change at all.
