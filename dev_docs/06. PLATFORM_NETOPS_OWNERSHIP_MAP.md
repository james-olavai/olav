# 12. Platform / NetOps Ownership Map

**Status:** Design  
**Version:** v0.1 (2026-03-20) — Ownership Alignment  
**Depends on:** `dev_docs/olav_platform.md`, `07. OPENCONFIG_SCHEMA_DESIGN.md`, `08. LEGACY_CUT_LINE.md`, `09. NETWORKX_SANDBOX_DESIGN.md`, `10. CLAB_CAB_AGENT_DESIGN.md`, `11. CONTROL_PLANE_SEMANTIC_ENGINE.md`

---

## 1. Purpose

This document fixes a recurring ambiguity in the 07-11 design set:

- some documents define platform-facing contracts
- some documents define NetOps-only capabilities
- current implementation references still live in the root repo and can make ownership look mixed

This file defines the intended ownership boundary.

---

## 2. Split Principle

The split rule is:

1. `olav-platform` owns reusable control-plane mechanisms
2. `olav-netops` owns network-specific vocabulary, reasoning, collection, simulation, and validation
3. root-repo implementation paths do not override conceptual ownership

So when a design doc references `src/olav/...` today, that path should be treated as a temporary implementation location unless the capability is clearly platform-generic.

---

## 3. Ownership by Capability

### 3.1 `olav-platform`

Platform should own:

- agent orchestration
- audit and trace pipeline
- sandbox runtime and isolation primitives
- shared state access contracts
- inventory abstraction interface
- raw snapshot contract pattern
- schema-on-read mechanism
- semantic view mechanism
- compatibility-layer governance
- workspace control plane and lifecycle

Platform should not own network protocol semantics by default.

### 3.2 `olav-netops`

NetOps should own:

- OpenConfig / YANG network vocabulary bootstrap
- network domain metadata and taxonomy
- topology ETL and topology semantics
- graph-based Ops investigation helpers
- control-plane semantic engine
- protocol solvers such as BGP / OSPF
- policy IR for network policy evaluation
- CLAB lab validation and network assertions
- network-specific render/export paths

## 6. Current Mixed Reality

The current repository is still in a partial-decoupling state.

That means:

1. docs may point at root `src/olav/*` modules that will later move or be split
2. some platform mechanisms still carry network-default assumptions
3. some NetOps capabilities still appear under platform-looking paths

This is an implementation transition issue, not a reason to collapse the conceptual split.

---

## 7. Guardrails

To avoid re-mixing platform and netops concerns, future design and code changes should follow these rules.

### 7.1 Allowed in `olav-platform`

- generic contracts
- generic runtimes
- generic agent lifecycle
- generic storage and audit
- generic sandbox isolation and call boundaries

### 7.2 Not Allowed in `olav-platform` by Default

- BGP best-path semantics
- OSPF path reasoning
- LLDP/CDP topology business semantics
- CLAB-specific validation workflows
- network policy IR as default platform feature

### 7.3 Allowed in `olav-netops`

- any network-domain data model, solver, or validation logic built on platform contracts

---

## 8. Final Position

The 07-11 design set should be interpreted as follows:

1. `07` and `08` define the platform-facing contract layer, illustrated through NetOps
2. `09`, `10`, and `11` define NetOps domain capabilities built on top of that contract layer
3. current root-repo module references are transitional and must not be mistaken for final package ownership

This interpretation keeps the OLAV platform split coherent while preserving the current design momentum.
