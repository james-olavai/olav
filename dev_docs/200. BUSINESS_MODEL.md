# OLAV Business Model — Tools + Services, Not Content Vendor

**Status**: Decision (2026-04-26)
**Owner**: founders
**Supersedes**: implicit assumption that "content packs / vetted guides
should be the commercial product"

This document records a strategic decision about what OLAV monetises
and what it gives away.  Subsequent product/architecture decisions
(Phase 2/3 of `dev_docs/61`, repository split policy, hiring, marketing
positioning) inherit from this.

## TL;DR

* **Open**: the platform, the RAG mechanism, the memory + recall
  framework, the ingestion CLI, 3-5 sample guides, and a
  community-contributed guide library.
* **Commercial services**: knowledge distillation, custom agent
  development, model fine-tuning.
* **Not commercial**: vetted-content subscriptions, vertical/industry
  guide packs, "premium" RAG features.

The customer is the expert on their own network.  We don't compete
with them on content; we tool them up to capture and operationalise
their own expertise, then sell high-touch services that turn that
captured knowledge into durable assets.

## Decision

OLAV is positioned as **infrastructure + high-touch services**, not
as a content vendor.  Concretely:

### Open (BSL-1.1, current)

| Layer | Examples |
|---|---|
| Platform core | CLI, runtime, plugin contracts, DuckDB, LanceDB |
| RAG mechanism | `prime_usage_guides`, `AutoRecall`, diversifier, SaveAssertion, query_pattern capture |
| Recall optimisation | Tags FTS, scalar indexes, score thresholds, cross-encoder rerank — all the work in `dev_docs/61` § "LanceDB recall optimisation" |
| Schema + tooling | `UsageGuide` dataclass, `discover_guides()`, golden-test pattern |
| Ingestion CLI | `olav kb distill / suggest / interview / scaffold-test` (Phase 4 in tracking) |
| Bench harness | `tests/integration/test_smallmodel_recall_bench.py`, `tools/compare_bench.py` |
| Sample guides | 3-5 reference YAMLs that ship with `olav-netops` |
| Documentation | Authoring / golden-test / capture-workflow / fine-tuning playbooks |

### Open (Apache 2.0, NEW repository)

| Layer | Examples |
|---|---|
| Community guides | `github.com/olav-ai/community-guides` — PR-contributed BGP / OSPF / audit / change-management guides |

### Commercial services

| Service | Model | Examples |
|---|---|---|
| **Knowledge distillation** | Project + retainer | Audit customer's runbooks / Slack / incident reports → vetted YAML guides + golden tests + skill packs |
| **Custom agent development** | Project | New skill for customer's NMS / SOAR / proprietary tooling; vendor API integrations |
| **Model fine-tuning** | Project + recurring updates | Train small model (qwen-2.5-7b / llama-3-8b LoRA) on customer's accumulated query_pattern + correct outputs; deploy as customer-specific instance; quarterly refresh |
| **Implementation + training** | Project | Onboarding, golden-test methodology workshops, ops-team enablement |

## Rationale

### Why we can't win at content

Industry-specific runbooks (BGP best practices, SOX audit profiles,
NIST hardening checks, telco/finance/healthcare verticals) require:

1. **Domain depth we don't have** — a 30-year network engineer at a
   customer site knows their topology, change-windows, and quirks
   better than any vendor.
2. **Vertical-specific knowledge that doesn't transfer** — a finance
   PCI-DSS audit profile is irrelevant to a telco MEC deployment.
3. **Continuous maintenance** — RFCs change, vendors deprecate
   commands, regulations update.  Maintaining 200+ verticals is a
   full-time content team.

If we tried, we'd be Cisco DNA / Juniper Apstra / Splunk Premium Apps,
and lose against incumbents with much deeper vertical expertise.

### Why tools + services wins

The customer **already** has the expertise — in heads, in Slack
threads, in stale runbooks, in incident post-mortems, in
SOPs/MOPs nobody re-reads.  The blocker is **operationalising it**:
turning tribal knowledge into repeatable agent behavior.

OLAV's value proposition becomes: *give us your existing knowledge
in any form, we turn it into a working agent that captures your
ops style*.  This:

1. **Differentiated by the customer's own data** — moat is per-customer
2. **Network effect via OSS guides** — community library demonstrates
   "people use this", makes services credible
3. **Fine-tuning is true lock-in** — once a customer has 10K+
   query/answer pairs and a per-customer LoRA, replacing OLAV is a
   migration project
4. **High average contract value** — service projects $50–300K vs
   subscription $5–20K/seat
5. **Aligned incentives** — we win when the customer's ops team gets
   better, not when we lock them into more content

### Industry precedent

| Company | Open core | Commercial differentiation |
|---|---|---|
| HuggingFace | transformers, datasets, accelerate | Inference Endpoints, AutoTrain, Spaces Pro |
| Databricks | Apache Spark | Lakehouse, MLflow Enterprise, services |
| HashiCorp | Terraform / Vault / Consul OSS | Cloud + Sentinel + Enterprise features |
| Cloudera | Hadoop ecosystem | Cloudera Manager, Cloudera DataFlow + services |
| Couchbase | Server core | Sync Gateway, support, enterprise features |
| Confluent | Kafka | Confluent Cloud, ksqlDB, services |

All built durable businesses without monetising content. Our model
is closer to HuggingFace + Cloudera consulting hybrid.

## Implications for current and future work

### Architecture (`dev_docs/61` Phase 2/3 unchanged, framing shifts)

* The reason to invest in **memory-driven usage guides** is not
  "we'll ship better guides than incumbents", it's "*customers
  inject their guides and the recall layer makes them work even at
  small N (5-10 guides per intent)*".
* All Phase 3 LanceDB optimisations (Tags FTS, score threshold,
  cross-encoder rerank, multi-vector) are essential because customer
  data is sparse — quality recall on 20 guides matters more than on
  2,000.

### New roadmap items (was: "out of scope")

| New | Status | Why |
|---|---|---|
| `olav kb distill <docs>` | Phase 4 | LLM extracts intent + body from customer markdown/Slack/runbooks → guide YAML draft |
| `olav kb suggest-guides` | Phase 4 | scan query_pattern memories for unmet intents → propose guide drafts |
| `olav kb interview` | Phase 4 | conversational guide-authoring (agent asks ops engineer questions, generates YAML) |
| `olav kb import-from slack/teams` | Phase 4 | bulk import Q&A pairs from chat history |
| `olav export training-data` | Phase 5 | export query/answer triples for fine-tuning |
| `olav fine-tune` workflow | Phase 5 | training pipeline + LoRA serving |
| Authoring documentation | parallel | "how to capture tribal knowledge" — direct services-funnel content |

These tools **must be open** — they're how customers self-serve
to the point where commercial services have something to refine.

### Things we are NOT building

* No "Premium guide library" subscription
* No vertical packs (telco / finance / healthcare bundles)
* No vendor-curated content marketplace
* No "OLAV Pro" tier with extra recall features

If we feel the urge to ship one of these, re-read this document.
The temptation is real (it looks like easy money) but it puts us in
a content arms race we can't win.

## Risks and boundaries

| Risk | Mitigation |
|---|---|
| Services don't scale like SaaS | Accepted. 10-30 customers/year × $100-300K is sustainable; PMF first, scale later |
| Customers want "we'll write all your guides forever" | Engagement model is **transfer + retainer**, not "write content forever". Customer team owns guides post-engagement, we update toolchain + provide refresh services |
| Open-core competitors fork OSS, undercut on services | Possible. Defence: services quality, fine-tuning IP, customer relationships, the community guides repo network effect |
| BSL-1.1 transition (4yr) approaches | By then, services + LoRA differentiation > license barrier. License conversion is a non-event |
| Fine-tuning data ownership disputes | Contract clarity: customer owns their data + the trained adapter; we own pipeline IP. Standard MLOps split |
| "Why pay services when guides are open?" | Because writing a working guide library + golden tests + fine-tuning your own model is 3-6 months of expert work; we do it in 6-8 weeks |

## When to revisit this decision

This is a strategy commitment, not a hypothesis under test.  Revisit
only if:

1. We close 10+ services engagements and recognise that 80% of work is
   actually "rewrite the same BGP guide for each customer" — would
   suggest content commoditisation argues for a vetted library.
2. A funding round materially changes time-to-revenue requirements
   (services scale slower than SaaS).
3. Industry consolidation makes a major content competitor (e.g.
   Cisco/Juniper) ship a free OLAV-equivalent with their content
   bundled — would force re-positioning.

Until then: tools + services.  Phase 2/3/4 of `dev_docs/61` and the
new ingestion/fine-tuning workflows in `dev_docs/62` are the
implementation of this strategy.
