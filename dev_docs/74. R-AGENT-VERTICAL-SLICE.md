# R-AGENT-VERTICAL-SLICE — 把分析能力按意图切成窄 sub-agent

**Status:** proposed (2026-05-09)
**Predecessor:** dev_docs/73. AGENT_HIERARCHY_REFACTOR.md (Phase A-D 已完成)
**Driver:** gemma4:31b nothink 工具选择幻觉 / analyze 工具数量 vs 可靠性 tradeoff

## 起因

R-AGENT-HIERARCHY Phase D 落地后，analyze 走 inspector 模式（5 个 inspect_*
@tool + format_and_export），drift 测试 E2E PASS。但生产级审计暴露问题：

1. `inspect_blast_radius` 静默 false positive（不存在的 link 返回 "fully connected"）
2. drift 报告 root cause 段是 LLM 自由发挥，无 evidence 链接
3. 完全缺失日志/syslog/SQL 钻取能力 —— 故障分析 50% 工作量在日志里
4. 复杂场景（路径仿真 / 路由策略 / ECMP）完全空白

把缺口工具加回去会把 analyze 推到 8-10 工具 —— gemma4 nothink 经验值
> 9 工具进入"中危区"，工具选择错误率 10-20%。

## 核心 insight

**orchestrator 已经是路由模型**（Patch D' Step 2.5 之后只有
`recall_memory` + `web_search` + `task` 三个工具）。它本来就该承担
"问什么 → 找谁"决策。**让 orchestrator 在意图层路由，sub-agent 只
专注一件事**，每个 sub-agent 工具数 ≤ 6 永远不进危险区。

设计原则：
- orchestrator 知道 sub-agent **能力描述**（capability），**不知道**
  sub-agent 内部用哪些工具
- 每个 sub-agent SKILL.md 写清能力边界 + 单一 workflow
- 跨域查询（drift + 日志查变化设备）由 orchestrator 串
  `task("diff", ...) → task("investigate", ...)`

## 提议架构

```
netops/                    orchestrator（intent 层路由）
├── inspect/               能力：状态/拓扑/路由 Q&A          3 工具
│   inspect_devices, inspect_topology, inspect_routing
├── whatif/                能力：故障 what-if reachability  1 工具
│   inspect_blast_radius (with 存在性校验)
├── diff/                  能力：snapshot 对比               1 工具
│   analyze_drift (thick analyzer, 跨源验证)
├── investigate/           能力：日志/证据钻取               1 工具
│   query_evidence (syslog/command_output/config 三合一)
├── sim/                   能力：变更规划                    5 工具（不变）
│   4 inspector + submit_change_plan
├── lab/                   不变
├── collect/               不变
├── topology/              不变
└── learner/               不变
```

每个新 sub-agent 工具数：1-3，远低于 9 工具危险区。

## orchestrator 决策表

netops/prompts/orchestrator.md 加 dispatch table，配合 intent-keyed
memory（Patch J 验证有效）：

| 用户意图 | 路由到 |
|---|---|
| 设备/拓扑/状态查询 | inspect |
| 故障影响 / what-if | whatif |
| 快照对比 / drift report | diff |
| 故障定位 / 日志 / 为什么 | investigate |
| 变更方案 / CAB | sim |
| 拓扑发现 / LLDP/CDP | topology |
| 命令解析学习 | learner |
| 实验环境 | lab |
| CLI 采集 | collect |

orchestrator 只看用户问题的 intent 词，不需要知道
"inspect_drift_topology vs inspect_drift_routing 怎么选"。

## 实现细节

### investigate sub-agent（Step 1）

```
netops/investigate/
├── SKILL.md
├── prompts/system.md       — 一个 workflow：根据问题选 source 调 query_evidence
└── tools/
    └── query_evidence.py   — Literal["syslog","command_output","config"]
```

`query_evidence` 内部分发：
- `source=syslog` → 查 syslog 表，按 device + time_range + pattern 过滤
- `source=command_output` → 查 `parsed_outputs` / `raw_output_store`，按 device + command
- `source=config` → 查 raw running-config 文本，按 pattern grep

返回 `{matches: [{timestamp, device, source_table, content}], total, truncated}`。

### orchestrator capability description（关键设计点）

netops/prompts/orchestrator.md 描述 sub-agent 时**只写能力边界**：

```
## Sub-agents

### investigate
Use when user asks: 为什么/why/故障定位/log/syslog/查看输出/具体内容
Investigate questions about *what's recorded* (events, errors, command
outputs, config snippets). Returns matched lines with timestamps.

### diff
Use when user asks: 对比/drift/什么变了/差异/between snapshots
Compares two snapshots and returns structured findings with evidence.

### inspect
Use when user asks: 拓扑/邻居/状态/BGP up/OSPF/AS号/loopback
Returns current state of devices/links/sessions.

### whatif
Use when user asks: 故障/down/挂了/影响/blast radius
Simulates failure and returns reachability impact.

### sim
Use when user asks: 计划变更/添加 BGP/CAB/change plan
Designs change implementation, emits TCF spec.
```

**不出现工具名。** orchestrator 只看意图分类。

### 跨域多步查询

orchestrator system.md 加一条 workflow：

```
## Multi-hop workflows

If user asks something that spans capabilities, chain task() calls:
- "drift + 给我看变化的设备的日志":
  1. task("diff", ...) → 拿 findings
  2. 从 findings 提变化的 device names
  3. task("investigate", ...) for each device
- "故障设备 + 影响范围":
  1. task("investigate", ...) → 找出 down 的设备
  2. task("whatif", remove_devices=[...])
```

## 安装方式（重要约束）

netops 在 dev 工作流中是**源码安装（editable）**，不是 wheel：

```bash
# 源码 olav-netops 是 editable-installed 到 demo7
# 修改 src/olav_netops/*.py 后无需重建 wheel —— 直接生效
# 但修改 .olav/workspace/* 还需要 olav agent install 同步
```

dev 流程：

1. 编辑 `olav-netops/src/...` —— Python 源码即时生效
2. 编辑 `olav-netops/.olav/workspace/netops/...` —— 需要
   `cd /home/yhvh/olav-demo7 && .venv/bin/olav agent install /home/yhvh/Olav/olav-netops`
3. workspace 同步后 `olav refresh` 重建路由表
4. 测试

不需要：
- ~~uv build --wheel~~
- ~~uv pip install --force-reinstall~~

## Risks

| Risk | 应对 |
|---|---|
| orchestrator 拿不准 intent，路由错 | dispatch table 用关键词清晰分割；intent-keyed memory guide 兜底 |
| 跨域查询信息丢失（task() 间） | orchestrator system.md 显式教 multi-hop workflow |
| sub-agent 数量膨胀维护成本 | 每个 sub-agent ≤ 200 行 SKILL.md + 1 个工具，单点维护 |
| 与现有 analyze 共存期路由冲突 | Step 1 期 analyze 维持现状，investigate 仅承接 *新增* 日志意图 |

## 不在范围

本文档仅讨论 analyze 这一支的纵向切分。**不动**：
- sim 内部结构（4 inspector + submit_change_plan 已稳定）
- audit / devops orchestrator
- core / services 平台 agent
