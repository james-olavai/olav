## 1. 背景：为什么要评估

现状：
- OLAV 的 TUI 是 deepagents-cli 的"壳 + overlay"（`src/olav/cli/tui_overlay.py` 做 monkey-patch）
- OLAV 自己维护了一套 workspace / agent / skill / plugin / slash-command 体系
- 两套体系高度重叠 —— 做的事情是同一类（LangGraph agent + tools + skills + memory）
- overlay 是版本脆弱的，对 deepagents-cli 私有内部做 monkey-patch

问题：
- 是否应该把 OLAV 的 workspace 抽象 **整体迁移** 到 deepagents-cli 原生约定，避免重复造轮子？
- 如果迁移，能直接让多少功能变成"免费拿到"（native `/agents`、`/threads`、`/mcp`、skill 生态）？
- 工作量和风险是多少？

本文档是决策前的研究材料，**不是实施计划**。实施计划在决策后另开新文档。

## 2. 两个模型的并排对照

### 2.1 OLAV 的 workspace 模型

```
.olav/workspace/
├── core/
│   ├── AGENT.md               ← 主 agent 定义（name/description/prompt）
│   ├── MANIFEST.yaml          ← 含 slash_commands 声明
│   ├── tools/                 ← Python 工具模块
│   ├── prompts/system.md      ← 系统提示
│   ├── references/            ← 背景文档
│   └── <skill_name>/
│       ├── SKILL.md           ← 技能定义
│       └── tools/             ← 技能专属工具
├── ops/
│   ├── AGENT.md
│   ├── <sub_agent_name>/
│   │   └── AGENT.md           ← 子 agent
│   └── <skill_name>/SKILL.md
├── audit/ ...
└── PLATFORM.md                ← 平台级共享上下文
```

**Runtime 组装**（`src/olav/agents/agent.py:OLAVAgent`）：
1. 扫描 workspace tree
2. 载入 AGENT.md / SKILL.md / MANIFEST.yaml
3. Python 发现 `tools/*.py` 中的 `@tool` 装饰器
4. 通过 `plugin_registry` 注入 callback plugins（audit / guardrails / memory / UKS）
5. 用 `create_deep_agent(tools=..., middleware=...)` 构建 LangGraph 图
6. 挂 `.graph.with_config({"callbacks": cbs})`

### 2.2 deepagents-cli 的原生模型

```
~/.deepagents/<cli_agent>/          ← 用户级 (全局)
├── AGENTS.md                       ← 主 memory/instructions
├── agents/
│   └── <subagent>.md               ← 子 agent（YAML frontmatter + 正文）
└── skills/
    └── <skill>/SKILL.md

<project_root>/.deepagents/         ← 项目级 (覆盖用户级)
├── AGENTS.md
├── agents/
│   └── <subagent>.md
└── skills/
    └── <skill>/SKILL.md

<pkg>/built_in_skills/              ← 内置 skill（remember / skill-creator）
```

**Runtime 组装**：
- `deepagents_cli` 主进程启动 langgraph subprocess (`DEEPAGENTS_CLI_SERVER_ASSISTANT_ID=<name>`)
- subprocess 读 `AGENTS.md` 作为 system prompt
- `SkillsMiddleware` 自动扫描用户级 + 项目级 + 内置 skills
- `MemoryMiddleware` 绑定 AGENTS.md 做 memory
- 工具来源：deepagents 内置（shell/read/write）+ MCP 服务器（配置在 `~/.deepagents/config.toml`）+ subagent 专属工具
- Middleware 全部是 `langchain.agents.middleware.AgentMiddleware` 子类

### 2.3 概念映射表

| OLAV 概念 | deepagents 原生等价 | 契合度 | 说明 |
|---|---|---|---|
| Workspace 根目录 | `~/.deepagents/<name>/` 或 `.deepagents/agents/` | ★★★ | 命名/位置不同，用途相同 |
| `AGENT.md` | `AGENTS.md` | ★★★ | 格式一致，改名即可 |
| `MANIFEST.yaml` | 无对应 | ★☆☆ | deepagents 没有 "agent manifest" 概念；`slash_commands` 字段无处安放 |
| 子 agent `<agent>/<sub>/` | `<agent>/agents/<sub>.md`（YAML frontmatter + 正文） | ★★★ | schema 可以直接转换 |
| 技能 `<agent>/<skill>/SKILL.md` | `<agent>/skills/<skill>/SKILL.md` | ★★★ | SKILL.md frontmatter 格式一致（name / description） |
| Workspace-local tools (`tools/*.py`) | 传给 `create_deep_agent(tools=[...])` | ★★☆ | deepagents 不扫描目录加载工具，要用一个 loader 手动注入 |
| Callback plugins（audit / guardrails / memory / UKS-capture / memory-recall） | `AgentMiddleware` 子类 | ★★★ | 都挂在 LangGraph 流水线上，基类不同 |
| `AuditCallbackPlugin.bind_run(run_id)` 构造后绑定 | 无 | ★☆☆ | middleware 生命周期是图构造期；run-level 上下文需要走 state/context 注入 |
| 服务注册 (`services.yaml` → API-as-tool) | MCP 服务器 | ★★☆ | 功能对等，协议不同 |
| HITL 审批 (`_hitl_audit_scope` 包装) | `InterruptOnConfig` middleware | ★★★ | deepagents 原生支持 |
| Checkpointer（会话持久化） | LangGraph checkpointer | ★★★ | 两边都用 LangGraph，只是路径不同 |
| Custom slash commands (`/trace-review`, `/workspace`) | 静态 `COMMANDS` tuple，无 plugin API | ★☆☆ | 目前靠 monkey-patch 注入 |
| `olav_delegate(subagent_name)` 内部代理 | `SubagentToolMiddleware`（自动暴露 `task` 工具） | ★★★ | deepagents 的子 agent 调用更直接 |

### 2.4 契合度汇总

| 契合度 | 项目数 | 占比 |
|---|---|---|
| ★★★（直接映射） | 9 | 60% |
| ★★☆（功能对等，需适配） | 3 | 20% |
| ★☆☆（无对应，需独立保留） | 3 | 20% |

## 3. 可以被 deepagents 原生替代的 OLAV 命令

迁移后，这些 OLAV 命令可以**直接删除**，用户用原生 UX 即可：

| OLAV 命令 | deepagents 原生替代 | 备注 |
|---|---|---|
| `olav list` | `/agents`（TUI 内）+ `-a <name>` CLI 参数 | 自动扫描 agent 目录 |
| `olav sessions` | `/threads` + `-r <id>` | LangGraph 线程管理 |
| `olav --resume <id>` | `olav -r <thread_id>` | 同义 |
| `/workspace <name>` (overlay) | `/agents` | 前提：切到 `server_kwargs=` 模式 |
| `/trace-review` | `/trace` + `/tokens` + tool display | 大体覆盖，细节 UX 略有差别 |
| `/model` / `/tokens` / `/clear` / `/offload` | native | 本来就不是 OLAV 自家的 |
| OLAV skill manifest slash 命令 | deepagents skill + `/skill:<name>` | 要保留的就写成 skill |

**合计：7 个命令**可以从 OLAV 代码库里移除。

### 3.1 必须保留的 OLAV 命令（平台级）

这些是 TUI 框架之外的职责，不管切不切都要留：

| 命令 | 功能 | 原因 |
|---|---|---|
| `olav admin add-user / list-users / rotate-token / revoke-token` | 用户/Token 管理 | OLAV 的多用户 auth 模型，deepagents 不关心 |
| `olav init` | DB / workspace / embedder 初始化 | 平台首次安装 |
| `olav service start --all` | 启动 web (2280) / syslog (5514) / daemon | 带外服务，和 TUI 无关 |
| `olav log list / export raw/sft/trajectory` | 审计日志 / 训练数据导出 | OLAV 专有格式 |
| `olav kb import / search / export / graph / sync` | 知识库 + Obsidian 同步 | OLAV 专有能力 |
| `olav skill install <path>` | 从本地目录安装 skill + 自动 pip install | deepagents 无此 convenience；OLAV 可简化为复制到 `~/.deepagents/<agent>/skills/` |
| `olav refresh` | 重建 agent 路由索引 | deepagents 启动时自动扫描，此命令退化为 noop |
| `olav workspace ...` | OLAV workspace 命令行工具 | 随迁移消失 |

## 4. 需要重做的部分（30% 不契合的地方）

### 4.1 Plugin → Middleware 重写

**当前**：`plugin_registry` 管 5 个 callback plugin：
- `AuditCallbackPlugin` — 记录 tool_calls / llm_events / user_turns 到 audit.duckdb
- `GuardrailsPlugin` — 审批规则 (`approval_rules.yaml`)
- `MemoryCapturePlugin` — 把对话里的结论写进 memory LanceDB
- `UKSCapturePlugin` — 知识库自动沉淀
- `MemoryRecallPlugin` — 响应前检索 memory 注入 prompt

**迁移**：每个改写成 `AgentMiddleware` 子类：

```python
from langchain.agents.middleware import AgentMiddleware

class AuditMiddleware(AgentMiddleware):
    def before_agent(self, state, runtime):
        # run_id 从 state 或 config 取，不再靠 bind_run()
        ...
    def after_model(self, state, runtime): ...
    def after_tool_call(self, state, runtime): ...
```

**硬骨头**：`AuditCallbackPlugin.bind_run(run_id)` 是**构造后**绑定 run_id 的，`AgentMiddleware` 没有等价机制。三个方案：

1. **通过 context 传递** — `create_deep_agent(context_schema=OlavContext)` 时注入 run_id
2. **通过 state 扩展** — middleware 定义 `state_schema` 加 `run_id` 字段
3. **每次 run 重建 middleware 实例** — 性能差

推荐方案 1（context 扁平、LangGraph 原生支持）。

### 4.2 Workspace-local 工具发现

**当前**：
- `OLAVAgent` 扫描 `.olav/workspace/<agent>/tools/*.py` 和 `<agent>/<skill>/tools/*.py`
- 自动发现 `@tool` 装饰的函数

**迁移**：写一个 `olav.server.tool_loader`，扫描目录，返回 `list[BaseTool]`，由 factory 传给 `create_deep_agent(tools=...)`。约 80 LOC。

### 4.3 Slash command 扩展

**当前**：
- `MANIFEST.yaml` 里 `slash_commands` 条目（kind=`shell` / `llm`）
- OLAV 的 `src/olav/cli/commands/builtin.py` registry

**deepagents 原生没有 plugin API**，两条路：

1. **放弃 workspace slash command，重写成 skill** — `/skill:<name>` 约定式调用
2. **保留 overlay 的 monkey-patch 路线** — 把一小部分必须的命令继续注入
3. **向上游贡献 plugin API** — 提交 PR 加 `deepagents_cli.slash_commands` 入口点组。被接受后我们变成正式插件

长期推荐路线 3，短期可以选 1 或 2。

### 4.4 Services → MCP

`services.yaml` 当前映射成动态 api-as-tool：

```yaml
netbox:
  base_url: http://netbox:8000
  auth: token
  kind: readonly
```

→ 变成 OLAV 运行时生成的一组工具（`netbox_get_devices`、`netbox_update_device` 等）。

**迁移**：每个 service 变成一个 MCP server 进程或 in-process MCP 适配器。deepagents-cli 通过 `/mcp` 管理。

**对比**：
- 现状：单进程，10 个 service = 10 组工具在同一个 graph 里
- 迁移后：10 个子进程（stdio MCP），多进程 IPC 开销；或者 in-process MCP（没有进程边界，但协议转换开销）

两者都可行，但**服务越多，MCP 路线启动慢**。对 ops agent 加载 6 个服务，启动延迟可能 +2-3s。

## 5. 整体迁移所需工作

### 5.1 分阶段分解

| Phase | 内容 | 规模 | 独立价值 | 风险 |
|---|---|---|---|---|
| **P1** 文件格式对齐 | `AGENT.md`→`AGENTS.md`，子 agent 改 YAML frontmatter，目录重组，符号链接兼容 | ~200 LOC + 迁移脚本 | 零 —— 纯过渡 | 低 |
| **P2** Tool loader 桥接 | workspace tree → `list[BaseTool]`；`OLAVAgent` 保持兼容 | ~100 LOC + 单元测试 | 零 | 低 |
| **P3** 5 个 Plugin → AgentMiddleware | 重写 + run-context 机制 + 单元测试 + 回归 | ~800 LOC + 大改 | **中** —— 也能用在 `langgraph dev` 场景 | **中高** —— 语义回归风险 |
| **P4** `services.yaml` → MCP | MCP server 适配器 or in-process 转换 | ~300 LOC/service × N | **中** —— 可以单独产品化 | 中 |
| **P5** `langgraph.json` + graph factory | 让 subprocess 能拉起 OLAV 图 | ~50 LOC + 集成测试 | **高** —— 独立就有用（LangSmith Studio / langgraph dev / 远程部署） | 低 |
| **P6** 切换 `simple_cli` 到 `server_kwargs=` | 删除 tui_overlay.py，接原生 `/agents` | ~100 LOC 净减 | 零 —— 依赖 P1-P5 | 低 |
| **P7** E2E + CI + 迁移文档 | Tier-1/2 套件跑通，升级 runbook | 测试代码不算 LOC | — | — |

**合计：2.5–3 周集中开发**（按一个人算）

### 5.2 关键风险

1. **deepagents-cli 迭代速度快** —— 0.0.37 → 0.0.41 重写了整个 TUI 层。迁移后我们 **更紧** 地耦合它的内部，一次类似规模的上游重构就要再改一遍。
2. **Middleware API 还在动** —— `AgentState` / `context` schema / `state_schema` 三个都在 langchain 1.x 里频繁变化。迁到 `AgentMiddleware` 意味着这块裸露。
3. **Checkpointer 共存** —— deepagents-cli 在 server_kwargs 模式下自己管 checkpointer。OLAV 的 audit DB 钩子能不能继续附着在一边，还是得把 audit 完全外部化（独立 sidecar 进程），没验证过。
4. **性能** —— 子进程 spawn + stdio MCP 的累加，冷启动 +3-5s 体感明显。现在 `olav --agent ops "..."` 是 ~0.5s 冷启动。

## 6. 推荐路线

### 6.1 不要一次性迁移

理由：
- 风险集中爆发，一旦中途受阻，回退成本高
- OLAV 目前能工作、27 个测试、overlay 仅 ~300 LOC
- 用户短期不会明显感知差别

### 6.2 分阶段建议顺序

```
【现在 – 已完成】
  ✓ overlay（/workspace + /ops /audit 别名）
  ✓ keyring_store（per-env 文件回退）
  ✓ 27 unit tests，CI 绿

【下一步 — P5（独立价值，2-3 天）】
  写 langgraph.json + src/olav/server/graph_factory.py
  → 可以用 `langgraph dev` 本地跑 OLAV
  → 可以接 LangSmith Studio 做调试
  → 不动 TUI，overlay 原样
  决策点：factory 能不能顺利构造出 OLAV 图？能，说明 P3/P6 可行

【中期 — P3（大工程，1-2 周）】
  5 个 plugin → AgentMiddleware，附带 context 设计
  → 这件事本身就有价值（langgraph dev 场景的 audit/guardrails）
  → P6 的前置条件
  决策点：middleware 回归测试全绿吗？

【后期 — P1+P2+P4+P6 合并为"切换" release，1 周】
  文件格式 + tool loader + services → MCP（或保留）+ 接原生 /agents
  → 一次性发布为 v0.21.0
  → tui_overlay.py 变成 legacy-compat shim 或删除

【收尾 — P7】
  CI 适配 + 升级 runbook
```

### 6.3 反向条件：什么时候**不应该**迁

- OLAV 的企业路线和 deepagents 分岔（NetOps/AIOps-specific 特性上游不会接受）
- deepagents-cli 上游 cadence 超过团队能承受的测试预算
- 目标是把 OLAV 打成单文件二进制 / docker / edge bundle，不想暴露 Python + LangGraph 依赖栈

### 6.4 正向条件：什么时候**应该**迁

- OLAV 目标是"AIOps domain profile for deepagents"，而不是独立 agentic platform
- 需要白嫖 `/agents` / `/mcp` / `/threads` / skill 生态
- 愿意给 deepagents 上游提 PR 保证长期兼容

## 7. 决策点清单

迁移前必须回答的问题：

1. **OLAV 产品形态**：独立 AIOps 平台，还是 deepagents 的一个 profile？
2. **上游关系**：愿意把 middleware / plugin API 贡献给 deepagents 上游？
3. **回退路径**：迁移失败时，能否回到当前 overlay 版本？（答：能，因为是渐进式）
4. **用户影响**：`.olav/workspace/` 是否会消失？（答：会，用户要迁移到 `.deepagents/`）
5. **olav-netops 协同**：netops 用 entry points 注册 agent，迁移后入口改成 deepagents skills 吗？

## 9. 附录：快速迁移脚本草图

仅供参考，不是交付物。

```bash
# P1 — 目录格式对齐（一次性脚本）
for agent in .olav/workspace/*/; do
    name=$(basename "$agent")
    # 1. 移动到 .deepagents/agents/
    mkdir -p ".deepagents/agents/$name/agents"
    mkdir -p ".deepagents/agents/$name/skills"

    # 2. AGENT.md → AGENTS.md
    cp "$agent/AGENT.md" ".deepagents/agents/$name/AGENTS.md"

    # 3. 子 agent: 每个 <sub>/AGENT.md → agents/<sub>.md（带 frontmatter）
    for sub in "$agent"*/; do
        sub_name=$(basename "$sub")
        [ -f "$sub/AGENT.md" ] && cat "$sub/AGENT.md" > ".deepagents/agents/$name/agents/$sub_name.md"
    done

    # 4. skill 迁移
    for skill in "$agent"*/SKILL.md; do
        skill_name=$(basename "$(dirname "$skill")")
        cp -r "$(dirname "$skill")" ".deepagents/agents/$name/skills/$skill_name"
    done
done
```

```python
# P5 — graph_factory 草图
# src/olav/server/graph_factory.py
import os
from langgraph.pregel import Pregel

def build() -> Pregel:
    """Called by langgraph dev subprocess; reads
    DEEPAGENTS_CLI_SERVER_ASSISTANT_ID env and builds the OLAV graph
    for that agent name.

    Stays in-sync with olav.cli.main.create_olav_agent_with_backend
    until we finish Phase 3 (middleware migration) and can call
    create_deep_agent directly.
    """
    assistant_id = os.environ.get("DEEPAGENTS_CLI_SERVER_ASSISTANT_ID", "core")
    from olav.cli.main import create_olav_agent_with_backend
    graph, _backend = create_olav_agent_with_backend(assistant_id)
    return graph
```

### 11.1 netops 安装受影响程度：**中等 + 改名；用户命令改为 `olav agent install`**

> **补正（见 §16）**：最初估计 "用户命令 `olav skill install` 不变"。调查发现 deepagents-cli
> 自带 `deepagents skills <create|list|info|delete>` 子命令，**没有** `skills install`
> 但语义上会和 OLAV 的老名字冲突（"skill" 在 deepagents 里指单个 `SKILL.md`，在 OLAV 里指整个
> agent 包）。因此 **`olav skill install` 改名为 `olav agent install`**，老命令保留 3 个版本的
> deprecation alias。

**当前流程（v0.19）**：

```
olav skill install /path/to/olav-netops/
  │
  ├── 读 olav-netops/workspace.yaml
  ├── 读每个 sub-workspace 的 .olav/workspace/<name>/MANIFEST.yaml
  ├── pip install -e /path/to/olav-netops
  ├── 复制 .olav/workspace/ops/ → <project>/.olav/workspace/ops/
  ├── 复制 .olav/workspace/audit/ / topology/ / command_learner/ / services/
  ├── inject_into_core.tools: 复制 tools/execute_cli.py 等到 core/tools/
  ├── 运行 olav refresh（重建路由索引）
  └── 可选：运行 init_command: /netops_init --dry-run
```

**迁移后流程（目标态）**：

```
olav agent install /path/to/olav-netops/          ← 首选命令
olav agent install git+https://.../olav-netops.git  ← 支持 git URL
olav agent install git+https://.../olav-netops.git@v0.19.0  ← 锁 tag
olav agent install https://.../olav-netops.tar.gz   ← archive
olav skill install /path/to/olav-netops/          ← 兼容，打印 deprecation 警告
  │
  ├── 读 olav-netops/workspace.yaml          ← 保持不变（OLAV 专用安装 manifest）
  ├── 读每个 sub-agent 的 AGENTS.md + agents/*.md
  ├── pip install -e /path/to/olav-netops    ← 不变
  ├── symlink agent 目录 → <project>/.deepagents/agents/ops/    ← 路径变了，改 symlink
  │                      <project>/.deepagents/agents/audit/
  │                      <project>/.deepagents/agents/topology/
  │                      <project>/.deepagents/agents/command_learner/
  │   （Windows 降级为 copytree；可用 --copy 强制）
  ├── inject_into_core.tools: 注册到 OLAV tool_loader Python 层  ← 方式变了
  │   （不再是文件复制，改为 entry point 或内部注册表）
  ├── 无 refresh（deepagents 启动时自动扫描）
  └── 可选：init_command 不变
```

**用户可见变化**：

| 维度 | 变化 |
|---|---|
| 用户命令 | `olav skill install <path>` → **`olav agent install <path\|git_url>`**；老名字保留 deprecation alias |
| Git URL 直装 | **新增**：`olav agent install git+https://...@tag` |
| 文件落地 | `.olav/workspace/` → `.deepagents/agents/`（symlink，Windows copytree 回退） |
| 命令后验证 | `olav list` 被 `/agents`（TUI）+ `olav -a <name>` 替代 |
| 安装失败回滚 | 需要重写（当前靠删除 workspace 目录，迁移后目录变了） |
| pyproject.toml 依赖 | **无变化** —— Python 包依然 `pip install` 到同一个 venv |

**内部必须重写的部分**：

1. `src/olav/cli/commands/skill.py:_install` 中所有路径常量（`workspace_root` → `deepagents_agents_root`）
2. `_copy_skill_files` 的目标路径
3. `_create_agent_dir` / `_write_lock_file` 的落地位置
4. `inject_tools_into_core` 改为运行时注入（不再拷文件）
5. `workspace.yaml` 里的 `inject_into_core.tools` 语义变成"在 core agent 构造时也把这些工具加载进去"

**olav-netops 端要不要改**？

只有**最小改动**：
- `workspace.yaml` 的 `workspaces` 列表保留，但每个 sub-workspace 内部：
  - `AGENT.md` → `AGENTS.md`（1 个文件改名）
  - 子 agent 目录格式从 `<parent>/<sub>/AGENT.md` → `<parent>/agents/<sub>.md`（YAML frontmatter 化）
  - `MANIFEST.yaml` 的 `slash_commands` 字段暂时保留但改由 OLAV 自己解析（deepagents 不认）
- entry points 全保留：`olav.domain_prompts` / `olav.tables` / `olav.slash_command_reload_hooks` / `olav.catalog_providers` 都是 OLAV 平台机制，**不动**

**结论**：用户层零感知；内部安装器重写约 ~300 LOC；olav-netops 做一次机械式文件转换（脚本化）。P1 阶段完成。

### 11.2 当前 agent 编排方式受影响程度：**小，MVC 架构保留，调用符号改名**

**当前编排（v0.19.0 ARCH-23 MVC）**：

```
core（orchestrator）
  ├── execute_sql    (直接 @tool)
  ├── recall_memory  (直接 @tool)
  ├── web_search     (直接 @tool)
  └── olav_delegate(subagent_name=...)
        ├── db_query     — 深度 SQL 查询
        ├── api_query    — 服务 API 调用
        ├── remote       — SSH / sandbox 执行
        ├── admin        — 平台管理
        └── writer       — 统一输出格式化

ops / audit / topology / command_learner — 顶层 agent，各自独立
```

跨 agent 路由：
- 语义路由器（`olav.core.router`）根据 keywords + 置信度，决定是否从 core 委派给 ops/audit/...
- 用户显式 `--agent ops "…"` 绕过路由

**迁移后编排（目标态）**：

```
core（LangGraph 主图，deepagents-cli 子进程）
  ├── execute_sql / recall_memory / web_search   (同上)
  └── task(subagent_name, prompt)  ← deepagents 原生子 agent 工具
        ├── db_query / api_query / remote / admin / writer
        (每个是 .deepagents/agents/core/agents/<name>.md)

顶层切换：
  /agents  (TUI 内)  → 切到 ops / audit / topology / command_learner
  olav -a ops "…"   (CLI)  → 启动时选 ops
```

**编排变化对照**：

| 维度 | 当前 | 迁移后 | 破坏性 |
|---|---|---|---|
| 顶层 agent 数量 | 5（core/ops/audit/topology/command_learner） | 5（同上） | 无 |
| 主 agent 启动方式 | `--agent <name>` | `-a <name>`（同义别名） | 无 |
| 主 agent 动态切换 | `/workspace <name>`（overlay） | **`/agents`（原生）** | ✅ 改进 |
| 子 agent 调用工具名 | `olav_delegate(subagent_name=...)` | `task(subagent=...)` | LLM prompt 里的提示词要改（受影响但不重） |
| 子 agent 定义位置 | `.olav/workspace/core/<sub>/AGENT.md` | `.deepagents/agents/core/agents/<sub>.md` | 文件搬家 |
| 子 agent MVC 5 个角色 | writer/admin/api_query/db_query/remote | 同上 | 无 |
| 跨顶层路由（core→ops） | OLAV 语义路由器 | deepagents `task` + 子 agent，或 `/agents` 手动切 | **行为变化** |
| 路由 keywords | `MANIFEST.yaml:route_keywords` | 无对应 —— deepagents 用 LLM 分类 | 重构 |
| 跨 agent 数据库访问 | 共享 `.olav/databases/` | **不变**（DB 不属于 TUI 层） | 无 |

**关键不兼容点：跨顶层路由**

当前 ops / audit 等顶层 agent 都能被 core 按 keyword 自动路由过去。deepagents 原生没有这个概念，它假设：
- 用户显式 `-a ops` 启动
- 或者在 core 内，把 ops 的能力暴露为 `task(subagent=...)` 的子 agent

**选择方案（决策采纳）**：
- 保留 5 个顶层 agent（保持独立身份，`/agents` 可切换）
- **同时** 把 ops/audit/topology 的关键工具 **也** 作为 core 的 subagent 注册，用户在 core 下直接说"检查 BGP"也能走
- 语义路由器（olav.core.router）保留为 core 的 subagent 选择器，不再做"切换顶层"

这让用户有两条路：
1. 显式切："我要做网络深度分析" → `/agents` → ops
2. 自然聊：在 core 下问 → LLM 通过 `task(subagent=ops_bgp_helper)` 直接解决

**对 olav-netops 的影响**：
- ops/audit/topology/command_learner 作为顶层 agent 注册方式见 §11.3
- 同时将部分关键 workflow（如 take_snapshot / check_bgp_health）注册为 core 的 subagent，让 core 下也能触发

**结论**：MVC 架构（5 subagent）完全保留；跨顶层路由规则有行为变化（需要少量用户教育）；LLM prompt 里的 `olav_delegate` 提示词要全局替换成 `task`。P3 阶段完成（middleware 重写）+ P1 阶段完成（目录格式）。

### 11.3 新 agent 注册方式受影响程度：**大，方式完全变，但对开发者更简单**

**当前注册方式（v0.19）**：

| 角色 | 步骤 |
|---|---|
| 平台集成者（olav-netops 这类扩展） | (a) `pyproject.toml` 声明 entry points（`olav.domain_prompts` / `olav.tables` / `olav.catalog_providers` / …）<br>(b) `workspace.yaml` 声明 workspaces 列表<br>(c) 每个 workspace 里写 `AGENT.md` + `MANIFEST.yaml` + `tools/`<br>(d) `pip install` + `olav skill install` |
| 终端用户（在项目里加个 agent） | 在 `.olav/workspace/<name>/` 手写 `AGENT.md` + `tools/` → `olav refresh` |
| 动态注册 | `olav refresh` 重建路由索引 / `/reload` 热加载 |

**迁移后注册方式（目标态）**：

| 角色 | 步骤 |
|---|---|
| 平台集成者（olav-netops） | (a) `pyproject.toml` 平台 entry points **保留**（tables / catalog / domain prompts 不属于 TUI 层）<br>(b) `workspace.yaml` 保留为 OLAV 安装 manifest<br>(c) 每个 agent 里写 `AGENTS.md` + `agents/*.md`（subagent）+ `skills/<name>/SKILL.md`<br>(d) 用户装：**`olav agent install <path\|git_url>`**（支持 `git+`/`archive`/本地路径三种形态） |
| 终端用户（在项目里加个 agent） | 在 `.deepagents/agents/<name>/` 放 `AGENTS.md` → **启动时自动发现，无需 refresh** |
| 动态注册 | 无需 —— TUI 启动扫描一次 |

**Entry point 迁移表（关键）**：

| 当前 entry point group | 用途 | 迁移后 |
|---|---|---|
| `olav.tables` | 数据库 schema 注入 | **不变**（DB 层不属于 TUI） |
| `olav.catalog_providers` | Tool catalog 生成 | **不变**（OLAV 平台层） |
| `olav.domain_prompts` | 注入领域 prompt 到 core | **不变** —— 但会被 AGENTS.md 模板消费而不是直接拼字符串 |
| `olav.slash_command_reload_hooks` | Slash 命令重载钩子 | **废弃** —— slash 命令走 deepagents skill `/skill:<name>` 约定 |
| `olav.cli_config_commands` | CLI config 扩展 | **保留**（OLAV CLI 层） |
| `olav.sandbox_prologues` | Sandbox 环境注入 | **不变** |
| `olav.diff_hooks` | Snapshot diff 集成 | **不变** |
| `olav.domain_agents`（假设新增） | 向 deepagents 暴露顶层 agent | **新增** —— 把 olav-netops 的 `.deepagents/agents/ops/` 指向包内路径 |

**新增（如何注册顶层 agent）**：

deepagents 原生扫描 `~/.deepagents/<name>/` 和 `<project>/.deepagents/agents/<name>/`，两条路：

**方案 A — 物理安装**（物理拷贝到目标目录）：
```
olav agent install /path/to/olav-netops --copy
  → pip install + 把包内 agents/ 目录 copytree 到项目 .deepagents/agents/
```
- 优点：完全原生，deepagents 看到的就是文件；兼容 Windows 无 symlink 权限
- 缺点：安装成本高（拷贝），升级要重装

**方案 B — 符号链接（推荐，默认）**：
```
olav agent install /path/to/olav-netops
  → pip install + 在项目 .deepagents/agents/ 下创建 symlink
    → site-packages/olav_netops/agents/ops/
```
- 优点：升级 Python 包自动生效，无需重装
- 缺点：Windows 符号链接权限问题（Developer Mode 或 admin）；检测到权限不足时**自动降级**为方案 A
- `--copy` 参数可显式强制物理拷贝

**方案 C — Entry point 驱动的运行时合成**：
```python
# deepagents-cli 启动时（在我们的 graph_factory 里）：
for ep in entry_points(group="olav.domain_agents"):
    agents_dir = ep.load()  # Path to package-bundled agents/
    _merge_into_deepagents_view(agents_dir)
```
- 优点：零拷贝，纯运行时
- 缺点：要 monkey-patch 或 fork deepagents 的 agent 发现路径

**采纳方案 B**（符号链接 + 平台 entry points 不动）。olav-netops 只要：
- 把 `.olav/workspace/*/` 改成 `agents/*/`（用 AGENTS.md 替代 AGENT.md）
- 在 wheel 里打包这些
- `olav skill install` 在目标项目建立 symlink

**对终端用户的冲击（增加简单性）**：

- **以前**：写 `AGENT.md` + `MANIFEST.yaml`（两个格式）+ 记得跑 `olav refresh`
- **现在**：写 `AGENTS.md`（一个文件，YAML frontmatter）→ 下次启动自动出现
- subagent 改成单个 markdown 文件（不用目录），开发体验大幅简化

**结论**：注册机制完全改写，但对开发者**更简单**（文件少、约定俗成）。平台 entry points 保留 5 个、废弃 1 个、新增 1 个。P1 阶段 + P2 阶段（tool loader）完成。

### 11.4 Support agent 是否一并做掉：**不并做，但迁移要为 support 留空间**

**为什么不并做**：

1. **作用域爆炸**。迁移本身已经是 2.5-3 周；support 按 `52. SUPPORT_AGENT_DESIGN.md` 估计 1 周。绑定发布到同一个里程碑 = 4 周高风险里程碑。
2. **support 是增量功能**。它不修复迁移期的任何问题；即使没有它，迁移该过也过得去。
3. **support 依赖迁移结果**。支持 bundle / workspace audit / health check 最好在新架构下稳定后再加，否则一期代码/二期代码都有 support 适配逻辑，双倍维护。
4. **价值交付节奏**。先把"迁到 deepagents 拿到 `/agents` `/mcp` `/threads` 等原生能力"这件事单独交付，用户立刻受益；support 下一个 milestone 做。

**为什么"要留空间"**：

support 落地时要在 `.deepagents/agents/core/skills/support/SKILL.md` 这个新路径，不再是 `.olav/workspace/core/support/`。迁移的 P1（目录格式对齐）和 P2（tool loader）如果只照顾现有 core/ops/audit/topology/command_learner 5 个 agent，将来 support 进来就得再迁一次。

**具体技术要求**：

- P1 的文件格式对齐脚本 **要能处理**"目标 SKILL.md 还不存在于 `.deepagents/agents/core/skills/` 的情况"，不要硬写入 5 个已知 skill 名单
- P2 的 tool_loader **要能加载**"在 skill 目录里以 `.py` 结尾的任意工具"，不要只硬编码当前几个工具模块
- P3 的 middleware **要预留 config 上下文槽位**让 support 的 `build_support_bundle` 将来能拿到 run_id / audit_recorder
- doc 站（`olav-doc`）在迁移后应该也同步调整 search_docs 用的 RAG 索引路径

**决策**：
- support agent **推迟到 v0.22.0 之后**
- 迁移本身不包含 support 代码
- 但迁移的抽象层（tool_loader / middleware / skill format）要通用到 support 落地时零改造
- `52. SUPPORT_AGENT_DESIGN.md` 状态保持 "Draft / 待评审（未实施）"，等 v0.20.3 稳定后在 **v0.21.0** 单独排期

**结论**：不顺手做；但在迁移设计中 **为 support 预留适配面**，避免将来重复迁移。

## 16. deepagents-cli 原生 skill 安装能力调查（回答用户补问）

**用户问题**：netops 只发布在 git 上（不上 PyPI），pip 安装；deepagents-cli 有没有原生的 skill 安装工具可以代替 OLAV 的 `olav skill install`？

### 16.1 调查结果：**没有**

deepagents-cli v0.0.41 的 CLI 顶层 verbs（`deepagents --help`）：

```
deepagents [OPTIONS]                         启动交互
deepagents agents   <list|reset>             agent 管理
deepagents skills   <list|create|info|delete> skill 管理
deepagents threads  <list|delete>            会话管理
deepagents update                            更新自身
deepagents init [NAME]                       新项目脚手架
deepagents dev    --config deepagents.toml   本地 dev server
deepagents deploy --config deepagents.toml   打包部署
```

`deepagents skills` 具体子命令：

| 子命令 | 功能 | 能从 git/path 装吗？ |
|---|---|---|
| `list / ls` | 列 skill | — |
| `create <name>` | **本地创建空 skill 脚手架** | ❌ |
| `info <name>` | 查看 skill 元数据 | — |
| `delete <name>` | 删 skill | — |

**没有** `skills install <path>` / `skills install <git_url>` / `skills add` / `skills import`。源码内也没有任何 install / clone / download / from_url 类辅助函数（逐模块 grep 过，仅 `detect_install_method()`，那是 deepagents 自己升级用的）。

### 16.2 deepagents-cli 的 skill 安装"事实标准"

从源码和官方脚手架推断，deepagents 用户现在是这样装 skill 的：

```bash
# 手动路线 — 从 git 克隆到 skill 目录
git clone https://github.com/someorg/awesome-skill ~/.deepagents/agent/skills/awesome-skill

# 或者
mkdir -p .deepagents/skills/my-skill
cat > .deepagents/skills/my-skill/SKILL.md <<EOF
---
name: my-skill
...
EOF
```

换句话说，**deepagents 把 skill 的分发交给用户自己**（git clone / 手写文件 / 复制目录），CLI 不参与。

### 16.3 对 OLAV 的影响

这直接影响 §11.1 的结论，需要补正：

**§11.1 补正**：`olav skill install` **必须保留并重写**，不能替换为任何 deepagents 原生命令。

理由：
1. netops 上 PyPI 前，**git + `olav skill install <path>`** 是唯一的分发渠道
2. deepagents 没有"从 git/archive/path 安装"的能力
3. 安装时要做的几件事，deepagents 一个都不管：
   - `pip install -e <path>` 把 Python 包装进 venv
   - `pyproject.toml` 的依赖解析
   - `requirements.txt` 回退
   - entry point 注册（`olav.tables` / `olav.domain_prompts` / ...）
   - `inject_into_core.tools` 的共享工具注册
   - 多 workspace 的批量落地

deepagents 的职责只是"在正确的位置找到 AGENTS.md / SKILL.md 并加载"，**package-level 分发是 OLAV 的责任**。

### 16.4 职责划分（迁移后明确）

| 层级 | 谁来做 | 命令 | 例子 |
|---|---|---|---|
| Package 级（git/pip 安装 + entry points） | **OLAV** | `olav skill install <path\|git_url>` | `olav skill install ~/repo/olav-netops/` |
| Agent 级（写 AGENTS.md + subagents）| deepagents（文件约定） | 无需命令，写文件即可 | 手写 `.deepagents/agents/my-agent/AGENTS.md` |
| Skill 级（单个 SKILL.md CRUD）| deepagents-cli | `deepagents skills create/list/info/delete` | `deepagents skills create my-skill` |

**命名建议**：为了和 deepagents 的 `skills` verb 清晰区分，OLAV 的 `olav skill install` 应该改名，候选：

| 候选 | 优劣 |
|---|---|
| `olav extension install` | 语义清晰；但和 Python `extension` 有混淆 |
| `olav agent install` | **首选**；强调它装的是"一个完整 domain agent"，不是一个 skill |
| `olav package install` | 太泛；和 pip 冲突 |
| `olav skill install` 不变 | 和 `deepagents skills create` 冲突感强，不推荐 |

**推荐采纳 `olav agent install <path|git_url>`**，老命令 `olav skill install` 保留 3 个版本的 deprecation alias。

### 16.5 netops 分发 workflow（迁移后）

**开发者侧**：
```
olav-netops 仓库
├── pyproject.toml            # 入口点 + 依赖（保留）
├── workspace.yaml            # OLAV 安装 manifest（保留）
└── src/olav_netops/agents/   # ← 新增：AGENTS.md + agents/ + skills/ 的源
    ├── ops/
    │   ├── AGENTS.md
    │   ├── agents/
    │   │   ├── analysis.md
    │   │   ├── lab.md
    │   │   └── devops.md
    │   └── skills/
    │       └── netops_init/SKILL.md
    ├── audit/ ...
    ├── topology/ ...
    └── command_learner/ ...
```

**用户侧**：
```bash
# git + editable install（首选，支持本地开发）
git clone https://github.com/yourorg/olav-netops.git ~/olav-netops
olav agent install ~/olav-netops

# 或 git URL 一步到位
olav agent install git+https://github.com/yourorg/olav-netops.git

# 或 release tarball
olav agent install https://github.com/yourorg/olav-netops/archive/refs/tags/v0.19.0.tar.gz
```

**OLAV 做的事（内部）**：
1. 如果是 git URL → `git clone` 到 tmp
2. 如果是 archive URL → `curl | tar x` 到 tmp
3. 如果是本地路径 → 直接用
4. 读 `pyproject.toml` → `pip install -e <path>`（在 OLAV venv 里）
5. 读 `workspace.yaml` → 找出 agents 列表（ops/audit/topology/command_learner）
6. 对每个 agent：`src/olav_netops/agents/<name>/` → symlink 到 `<project>/.deepagents/agents/<name>/`
7. 注册 entry points（自动，pip install 附带）
8. 可选：运行 `init_command: /netops_init --dry-run`

**启动时（deepagents subprocess）**：
1. deepagents 扫描 `<project>/.deepagents/agents/` 看到 ops/audit/topology/command_learner
2. `/agents` 列表显示这 4 个 + core
3. 选中后读 `AGENTS.md` + `agents/*.md` + `skills/*/SKILL.md`
4. 加载工具（OLAV tool_loader 提供），构图

### 16.6 相关风险

**Symlink 在 Windows 上** —— 需要 Developer Mode 或 admin。对 Windows 用户可能成为阻碍。解决：
- 默认 symlink（Linux/macOS 主力场景）
- 检测到 Windows 且无权限时自动降级为 `shutil.copytree`
- 提供 `--copy` 显式参数强制拷贝

**git 发布不可复现** —— 没有版本锁定。建议：
- `workspace.yaml` 里带 `version` 字段，安装时 checkout 具体 tag
- 或者用户直接 `olav agent install git+https://github.com/.../olav-netops.git@v0.19.0`

**entry point 不同步** —— pip install 后进程需要重新加载。解决：`olav agent install` 后提示 "重启 TUI 以加载新 agent"，或者自动 exec self。

### 16.7 文档更新范围

- §11.1（netops 安装）已经在本次 edit 中隐含更新，但命令名称 `olav skill install` 要在 §12 和 §13 里一并改成 `olav agent install`
- 新增 `olav agent install` 的 CLI 定义：`src/olav/cli/main.py` 里加 subparser，`src/olav/cli/commands/agent_install.py` 重用 `src/olav/cli/commands/skill.py:_install` 的大部分逻辑
- 迁移脚本 P1 的输入端是 `.olav/workspace/*/`（老格式），输出端是 `src/olav_netops/agents/*/`（打包侧）—— olav-netops 仓库自己做一次转换 commit

### 16.8 小结（一句话）

> deepagents 不提供包级 skill 安装工具，所以 OLAV 的 `olav skill install` **不能被替代，必须重写并改名为 `olav agent install`**；netops 的 git 分发 workflow 在迁移后由 OLAV 继续独立维护，deepagents 只负责发现和加载已经落地的文件。
