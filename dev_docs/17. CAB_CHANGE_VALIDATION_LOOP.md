# 17. CAB Change Validation Loop Design

**Status:** Design
**Version:** v0.1 (2026-03-29)
**Depends on:** `09. NETWORKX_SANDBOX_DESIGN.md`, `10. LAB_AGENT_DESIGN.md`, `13. TEST_AND_GHOST_BASELINE.md`

---

## 1. 设计目标

定义 ops-sim（理论验证）与 ops-lab（实验验证）之间的协作流程，产出一份满足 CAB 审批要求的变更文档。

核心设计决策：**Markdown 作为 agent 间唯一交换格式**。

- 人类可在任意节点介入、审阅、修改
- LLM 天然擅长读写，无需定义结构化 schema
- 批注逐轮累积 → 自动形成审计轨迹
- 最终文档即 CAB 报告，无需二次整理

---

## 2. 整体流程

```
orchestrator
  │
  ├─► ops-sim
  │     查询 DB → networkx 模拟 → 生成 change.md（含 Expected State）
  │
  │   change.md (v1)
  │     ↓
  ├─► ops-lab
  │     读取 change.md → 部署 lab → 实验验证 → 批注结果
  │     │
  │     ├─ 有 ❌ → 打回 ops-sim，附 change.md (vN+1 含批注)
  │     │           ops-sim 读取最新批注 → 修正模拟 → 更新文档
  │     │           loop...
  │     │
  │     └─ 全部 ✅ → 标记 APPROVED → 返回 orchestrator
  │
  └─► orchestrator 归档 change.md 为最终 CAB 报告
```

**最大迭代次数：3 轮**。超过后标记 `HUMAN_REVIEW_REQUIRED`，停止循环，由人工接管。

---

## 3. change.md 文档结构

每次迭代都在同一文件上追加，不替换旧内容。

```markdown
# Change: <变更标题>

**Change-ID:** CHG-YYYYMMDD-NNN
**发起时间:** YYYY-MM-DD HH:MM
**涉及设备:** R2, R3
**变更类型:** OSPF Area 扩展 / BGP 邻居新增 / 接口 IP 调整 / ...

---

## 变更描述

一句话描述变更意图及业务原因。

## 理论分析 (ops-sim)

### 当前状态（snapshot DB）

| 设备 | 协议 | 关键参数 | 状态 |
|---|---|---|---|
| R2 | BGP | AS 65001, neighbor 10.1.1.2 | ESTABLISHED |
| R3 | OSPF | Area 0, eth1/1 cost 10 | FULL |

### 变更内容

```diff
+ R3 OSPF: 新增 Area 1，接口 ethernet-1/2.0
+ R3 BGP:  新增 neighbor 10.2.2.2 peer-as 65003
```

### networkx 模拟结论

- 路径完整性：✅ R1→R4 仍可达（3跳）
- 无路由环路：✅
- BGP 收敛预测：✅（AS-path 无冲突）
- ⚠️ 注意：networkx 不验证路由策略语义，route-map 效果需 lab 确认

### Expected State（lab 验证基准）

> lab 必须逐条验证以下条目，全部 ✅ 方可批准。

| # | 设备 | 验证点 | 期望值 |
|---|---|---|---|
| 1 | R3 | OSPF neighbor on ethernet-1/2 | FULL |
| 2 | R3 | OSPF Area 1 存在 | area 0.0.0.1 |
| 3 | R3 | BGP neighbor 10.2.2.2 | ESTABLISHED |
| 4 | R2 | BGP neighbor R3 | ESTABLISHED |

## 4. 批注格式约定

| 标记 | 含义 |
|---|---|
| `[LAB-REVIEW-N]` | 第 N 轮 lab 实验批注 |
| `[SIM-REVISION-N]` | 第 N 轮 sim 修正记录 |
| ✅ | 验证通过 / 已解决 |
| ❌ | 验证失败 / 需修正 |
| `APPROVED` | lab 全部通过，可提交 CAB |
| `HUMAN_REVIEW_REQUIRED` | 超过 3 轮未收敛，需人工接管 |

**规则：**
- sim 只处理最新一轮 `[LAB-REVIEW-N]` 中的 ❌ 条目，忽略已有 [SIM-REVISION] 覆盖的旧问题
- lab 每轮重新部署，对 Expected State 表格逐行核对
- 批注追加不替换，保留完整迭代历史

---

## 5. 终止条件

| 条件 | 处理 |
|---|---|
| Expected State 全部 ✅ | `APPROVED`，归档，销毁 lab |
| 迭代达到 3 轮仍有 ❌ | `HUMAN_REVIEW_REQUIRED`，保留 lab，通知人工 |
| sim 明确无法建模某问题 | 在文档中注明边界，该条目标记 `MANUAL_VERIFY`，其余继续 |

## 6. Orchestrator 职责

orchestrator 拥有 change.md 的生命周期：

```
1. 指示 sim 生成 change.md（含 Change-ID、Expected State）
2. 将文件路径传给 lab
3. 接收 lab 返回的状态（APPROVED / 打回 / HUMAN_REVIEW_REQUIRED）
4. 若打回：将 annotated change.md 路径传回 sim，迭代计数 +1
5. 若超限：停止循环，报告人工
6. 若 APPROVED：归档至 exports/cab-reports/CHG-YYYYMMDD-NNN.md
```

文件存储路径：`exports/cab-reports/<Change-ID>.md`

## 7. 设计边界

### ops-sim 负责

- 查询 snapshot DB（current state）
- networkx 拓扑模拟（路径、环路、可达性）
- 生成 change.md 初稿，填写 Expected State 表格
- 读取 `[LAB-REVIEW-N]` 批注，修正方案

### ops-sim **不负责**

- 路由策略语义验证（route-map/policy 过滤效果）
- 协议收敛时序
- 供应商特定行为（SRL vs IOS-XR 差异）

以上由 lab 实验验证覆盖，无法验证的在文档中标注 `MANUAL_VERIFY`。

### ops-lab 负责

- 读取 Expected State 表格
- 部署 ContainerLab → 推配置 → 执行 ReAct 验证循环
- 在文档中追加 `[LAB-REVIEW-N]` 批注
- 判断 APPROVED 或打回

### ops-lab **不负责**

- 修改变更方案
- 推断问题根因（仅记录现象，由 sim 分析）
